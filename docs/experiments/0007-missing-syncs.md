# 0007. 빠진 sync를 누가 알아채는가

이슈 #20의 검증 기록이다.

- 환경: macOS (Apple silicon), APFS, debug 빌드
- 도구: 엔진(`db.rs`)에서 sync 호출을 하나씩 지운 네 버전. 각 버전에서 테스트 세 묶음을 돌렸다.

**질문**: sync를 하나 빠뜨리는 것은 DB에서 가장 흔하고 가장 안 보이는 버그다. 정전이 나기 전에는 아무 차이가 없기 때문이다. 진짜 디스크 위의 테스트와 가짜 디스크(`SimFs`) 위의 정전 테스트 중 누가 이 버그를 알아챌까?

## 결과

| 지운 sync | 진짜 디스크 통합 테스트 (7개 파일) | 정답 모델 테스트 (진짜 디스크) | 가짜 디스크 정전 테스트 |
|---|---|---|---|
| E1. 새 DB를 만든 뒤 디렉터리 sync | 잡음, 단 **호출 순서를 적어 두는 테스트** 하나뿐 | 통과 (못 잡음) | 잡음: 파일이 통째로 사라짐 |
| E2. 새 DB를 만든 뒤 데이터 sync | 통과 (못 잡음) | 통과 | 잡음: 빈 파일이나 찢긴 메타 |
| E3. 커밋에서 메타보다 먼저 하는 sync | 통과 (못 잡음) | 통과 | 잡음: 메타가 안 바뀐 커밋이 sync 없이 끝남 |
| E4. 커밋에서 메타를 쓴 뒤 sync | 통과 (못 잡음) | 통과 | **처음엔 통과 (못 잡음)** → 테스트를 고친 뒤 잡음 |

## 의미

- **진짜 디스크 테스트는 sync가 빠져도 거의 모른다.** 정전이 없으니 운영체제의 캐시가 언제나 최신 내용을 돌려준다. E1을 잡은 것도 동작이 아니라 "이 순서로 불렀다"를 적어 둔 테스트였다. 호출 목록을 적는 테스트는 무엇을 부르는지만 확인할 뿐, 그 호출이 왜 필요한지는 모른다.
- **E3이 보여 준 것.** 키 하나를 고쳐 리프만 바뀌는 커밋은 메타가 그대로라 두 번째 sync를 건너뛴다. 그래서 첫 sync가 빠지면 그 커밋은 **sync를 한 번도 하지 않고 OK를 준다.** 가짜 디스크의 정전이 그 커밋을 지웠다.
- **E4가 내 테스트의 빈틈을 보여 줬다.** 처음 쓴 테스트는 커밋 20번을 다 하고 정전을 일으켰다. 그러면 메타를 바꾼 커밋 뒤에 오는 커밋의 첫 sync가 앞 메타까지 금고에 넣어 줘서 버그가 가려진다. 위험한 순간은 "메타를 바꾼 커밋 **직후**"뿐이다. 테스트를 "커밋 1~40번 각각의 직후에 정전, 시드 20개씩"으로 바꾸자 E4도 잡혔다. **정전 테스트는 어디서 끊느냐가 핵심이다.** 09번이 `fail_after`로 커밋 안의 모든 지점을 훑어야 하는 이유이기도 하다.
- 지금 엔진(아무것도 지우지 않은 버전)은 고친 테스트를 통과한다. 커밋이 끝난 **뒤**의 정전에서는 응답한 커밋이 모두 남는다. 커밋 **도중**의 정전은 09번이 다룬다. 04번 회고에 적은 대로, 분할 중에 끊기면 지금 설계는 깨진다.
