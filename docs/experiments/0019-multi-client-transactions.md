# 0019. 여러 클라이언트와 접속별 트랜잭션 — 서버 죽이기, 클라이언트 얼리기, 메모리 재기

이슈 #37, 설계 `docs/design/0025-multi-client-transactions.md` Q12. 이번 티켓에서 서버의 접속마다 세션이 하나씩 붙었다. 네트워크 너머의 클라이언트가 `BEGIN`을 보내고 원하는 만큼 트랜잭션을 들고 있을 수 있게 된 것이다. 그래서 세 가지를 확인했다.

1. 접속 여럿이 트랜잭션 중일 때 **서버 프로세스가 죽으면** 무엇이 남나.
2. 클라이언트가 **끊었다는 말도 없이(FIN 없이) 멈추면** 서버가 트랜잭션을 언제 놓아주나.
3. 오래 열린 트랜잭션이 **메모리**를 얼마나 붙잡나, 트랜잭션 하나가 쓰기 모음에 얼마나 쌓을 수 있나.

**비유**: 식당 손님(클라이언트)마다 전용 장바구니(세션)를 준다. ① 가게 전기가 나가면 결제 안 한 장바구니는 사라지고, 결제 중이던 것은 "다 됨" 아니면 "하나도 안 됨"이어야 한다. ② 손님이 장바구니를 든 채 의자에서 잠들면(SIGSTOP) 점원이 60초 뒤 장바구니를 비우고 자리를 정리한다. ③ 장바구니를 오래 들고 있으면 창고가 옛 진열 상태를 지워 버리지 못한다. 그게 얼마나 쌓이나를 쟀다.

도우미: `crates/oakdb-server/examples/multi_client_faults.rs`. Apple M3, macOS 27.0.1, APFS, `F_FULLFSYNC`, release 빌드.

```
cargo build --release -p oakdb-server --bin oakdb --example multi_client_faults
target/release/examples/multi_client_faults kill 20
target/release/examples/multi_client_faults sigstop
target/release/examples/multi_client_faults memory held 100000   # 그리고 none
target/release/examples/multi_client_faults write-set 64
```

## 1. 트랜잭션 중에 서버를 `kill -9`

실제 `oakdb serve`(실제 디스크)를 띄우고 다음을 동시에 돌린다.

- 쓰는 접속 8개: `BEGIN` → `INSERT` 5행 → `INSERT` 5행 → `COMMIT`을 끝없이 반복. 행마다 (접속 번호, 트랜잭션 번호)를 적는다.
- 쥐고 있는 접속 1개: `BEGIN` → `INSERT` 2행 뒤 **커밋하지 않고** 계속 들고 있음.
- 0.1~1.5초 사이 무작위 시각에 서버를 `SIGKILL`. 같은 디렉터리로 다시 띄워 확인.

| 확인 | 기대 |
|---|---|
| `COMMIT`이 `DONE`으로 돌아온 트랜잭션 | 10행 모두 있음 |
| `COMMIT`을 보냈는데 답을 못 받은 트랜잭션 | 10행 모두 있거나 모두 없음 |
| 커밋하지 않은 트랜잭션 | 하나도 없음 |

| 라운드 | 응답받은 커밋 | 답 못 받은 COMMIT | 그중 남은 것 | 반쪽 트랜잭션 | 열린 트랜잭션의 행 |
|---|---|---|---|---|---|
| 20 | 25 596 | 130 | 71 | **0** | **0** |

- **20라운드 모두 통과.** 응답받은 25 596개는 모두 10행 그대로였고, 반쪽(일부 행만 있음)은 하나도 없었다. 들고만 있던 트랜잭션의 행은 20번 모두 없었다.
- 답 못 받은 `COMMIT` 130개 중 71개(55%)는 다시 열어 보니 **있었다.** WAL에 쓰고 sync까지 갔는데 응답 프레임을 보내기 전에 죽은 경우다. 약속 위반이 아니다. 통신 규칙(`docs/protocol.md` 2-1절)이 "COMMIT을 보낸 뒤 응답 전에 끊기면 결과를 모른다"고 적어 둔 바로 그 경우다. 클라이언트는 다시 접속해 확인해야 한다.
- 처리량은 8접속 합쳐 초당 약 1 600 트랜잭션(트랜잭션마다 `QUERY` 4번, 10행). 그룹 커밋(#28)이 여러 접속의 `COMMIT`을 sync 한 번에 묶는다.
- 새로 확인한 것은 사실 "엔진과 SQL 층이 이미 해 둔 일이 네트워크 너머에서도 그대로냐"다. 미커밋 쓰기는 세션이 쥔 `Txn`의 메모리에만 있고 WAL에 간 적이 없으므로, 프로세스가 죽으면 흔적이 생길 길이 없다(실험 0018과 같은 이유).

## 2. 트랜잭션 중인 클라이언트를 `SIGSTOP`

FIN 없는 끊김을 흉내 낸다. 노트북 덮개를 닫았거나 랜선이 빠진 것처럼, 소켓은 열려 있는데 아무 말이 없다.

- 서버는 이 프로세스 안에서 트랜잭션 중 시간 제한 2초(`--idle-in-transaction-timeout 2`와 같음)로 띄우고, **진짜 `oakdb cli`** 를 자식 프로세스로 띄워 `BEGIN; INSERT INTO t VALUES (1, 1);`을 보낸 뒤 `SIGSTOP`.
- 그동안 다른 접속이 `UPDATE t SET n = n + 1 WHERE id = 0`을 쉬지 않고 자동 커밋(메모리 파일 시스템이라 초당 약 3만 7천 번).
- 0.25초마다 엔진 `Stats`를 찍었다.

| 시각 (초) | 접속 수 | 열린 트랜잭션 | 칠판에 남은 커밋 (`kept_commits`) |
|---|---|---|---|
| 0.00 | 2 | 1 | 0 |
| 0.51 | 2 | 1 | 19 863 |
| 1.02 | 2 | 1 | 41 186 |
| 1.78 | 2 | 1 | 71 183 |
| — | `oakdb: 127.0.0.1:50716 idle in a transaction for 2s; rolled back and closed` | | |
| 2.04 | 2 | 0 | **0** |
| 3.08 | **1** | 0 | 0 |

- **2초가 지나자 서버가 롤백하고 끊었다.** 그 순간 칠판에 쌓였던 커밋 7만여 개가 한꺼번에 지워졌다(`kept_commits` 71 183 → 0). 얼어붙은 클라이언트 하나가 엔진의 충돌 칠판을 계속 키우던 것이 멈췄다.
- 접속 수가 2에서 1로 내려가기까지 1초가 더 걸렸다. 서버는 `0x47`을 보낸 뒤 클라이언트가 읽을 시간을 1초(`LINGER`) 준다. 얼어 있는 클라이언트는 읽지 못하므로 1초를 다 쓰고 닫는다. 그동안에도 트랜잭션은 이미 롤백되어 있다(롤백 → 알림 → 끊기 순서).
- 열린 트랜잭션이 가끔 1로 보이는 것(2초 뒤)은 다른 접속의 자동 커밋 문장 자체다. 그 문장도 엔진 트랜잭션 하나라서 찍는 순간에 걸리면 1이 된다.
- `SIGCONT`로 깨운 CLI에 `SELECT`를 보내게 하자, CLI는 서버가 남겨 둔 `0x47`을 읽고 이렇게 끝났다(종료 코드 1).

```
ERROR 0x47 idle in a transaction for more than 2s; the transaction was rolled back and the connection closed
connection closed by server; the open transaction was rolled back
```

- 다른 접속에서 본 행 1은 **없었다.**
- 이 시간 제한이 없던 지난 티켓까지는, 같은 상황에서 트랜잭션이 **서버를 다시 띄울 때까지** 열려 있었을 것이다. 접속 스레드가 영원히 읽기에서 기다리기 때문이다.

## 3. 메모리

### 3-1. 트랜잭션 하나를 연 채 다른 접속이 10만 번 커밋 (설계 Q7)

메모리 파일 시스템(`SimFs`) 위의 서버. 1만 행 표를 만든 뒤, 한 접속이 `BEGIN`하고 행 하나를 읽은 채 가만히 있고(held), 다른 접속이 무작위 행 하나를 고치는 자동 커밋을 10만 번 한다. 비교로, 트랜잭션을 열지 않고 같은 일을 한다(none). `SimFs`는 WAL도 메모리에 두므로 두 경우를 **각자 다른 프로세스에서** 돌려 차이를 봤다. 각 두 번.

| 단계 | held RSS (MiB) | held `kept_commits` | none RSS (MiB) |
|---|---|---|---|
| 1만 행 넣은 뒤 | 12.7 / 12.5 | 0 | 12.4 / 12.4 |
| 2만 5천 커밋 | 32.6 / 31.0 | 25 000 | 29.7 / 27.6 |
| 5만 커밋 | 34.4 / 32.2 | 50 000 | 29.7 / 27.6 |
| 10만 커밋 | **40.3 / 37.6** | **100 000** | **29.8 / 27.6** |
| 트랜잭션 끝난 뒤 | 40.3 / 37.6 | **0** | 29.8 / 27.6 |

- 열린 트랜잭션 하나가 10만 커밋 동안 **약 10 MiB**(커밋 하나에 약 100바이트)를 더 붙잡았다. 커밋마다 키 하나(행 키 약 10바이트)와 `Arc`, 해시맵 칸, 덱 칸이 칠판에 남는다.
- 옛 트리 페이지는 생각보다 작았다. 표 전체가 1만 행 × 약 110바이트 ≈ 1.1 MiB라, 스냅샷이 붙잡을 수 있는 옛 페이지도 최대 그 정도다. 큰 표에서는 이쪽이 커진다.
- **트랜잭션이 끝나자 `kept_commits`는 0으로 돌아왔다.** RSS는 돌아오지 않았다. 할당기가 받은 메모리를 운영체제에 바로 돌려주지 않고 다음 할당에 다시 쓰기 때문이다(Java로 치면 GC 뒤에도 힙 크기가 줄지 않는 것). 다시 자라지는 않는다.
- 초당 3만 7천 커밋이 1분 이어지면 220만 커밋, 약 220 MiB다. Q5의 60초 시간 제한이 노는 트랜잭션은 이 안에서 끊는다. **쉬지 않고 문장을 보내는** 긴 트랜잭션은 못 끊으므로 경고 로그(`--warn-transaction-age`, 기본 5분)와 `Stats`로 보이게만 했다(설계 Q7-B). 실제 디스크에서는 커밋이 sync에 묶여 이 속도가 한참 낮다(1의 초당 1 600).

### 3-2. 트랜잭션 하나에 쌓을 수 있는 양 (설계 Q6)

한 접속이 `BEGIN` 뒤 1 KiB BLOB 행을 256행씩 `INSERT`해 64 MiB를 쌓고 `ROLLBACK`.

| 쌓은 양 (MiB) | 서버 RSS (MiB) | RSS 증가 / 쌓은 양 |
|---|---|---|
| 8 | 19.5 | 2.13 |
| 16 | 31.5 | 1.81 |
| 32 | 55.0 | 1.64 |
| 64 | 102.3 | **1.56** |

- 쌓은 양의 약 1.6배를 메모리에 쓴다(행 키·값의 `Vec`, `BTreeMap` 칸, SQL 문장을 읽는 동안의 임시 공간).
- **상한이 없다.** 클라이언트 하나가 `INSERT`를 계속 보내면 서버 메모리가 계속 큰다. 설계 Q6에서 "위험으로 기록하고 따로 티켓"으로 정한 그대로다. 접속 512개가 모두 이러면 512배다.
- `ROLLBACK`은 64 MiB를 버리는 데 약 7ms.

## 결론

| 질문 | 답 |
|---|---|
| 서버가 죽으면 | 응답한 커밋은 모두 있고, 반쪽은 없고, 미커밋은 없다 (20라운드, 25 596 커밋) |
| FIN 없이 사라진 클라이언트 | 시간 제한(기본 60초)에 롤백되고 끊긴다. 그 순간 칠판도 비워진다 |
| 오래 열린 트랜잭션의 대가 | 커밋 하나에 약 100바이트(칠판) + 옛 페이지. 끝나면 칠판은 0으로 |
| 트랜잭션 하나의 쓰기 모음 | 쌓은 양의 약 1.6배, 상한 없음 (따로 티켓 감) |
