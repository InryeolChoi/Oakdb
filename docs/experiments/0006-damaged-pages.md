# 0006. 망가진 페이지를 알아채는가

이슈 #19의 검증 기록이다.

- 환경: macOS (Apple silicon), APFS, debug 빌드
- 도구: `crates/oakdb/examples/checksum_faults.rs`

**질문**: 디스크의 페이지가 조용히 바뀌면(비트 하나, 반쯤 쓴 페이지, 엉뚱한 자리에 쓴 페이지) DB는 알아챌까? 체크섬을 넣기 전(`main`)과 넣은 뒤(이 브랜치)를 같은 도구로 비교한다.

```sh
cargo run --example checksum_faults -- /tmp/oak-exp6
```

키 400개(100바이트 값)와 긴 값 하나(부록 5장), 지운 긴 값이 남긴 빈 페이지가 있는 35장짜리 파일을 만든다. 닫은 파일의 사본을 일곱 가지로 망가뜨리고 다시 연다. 열리면 모든 키가 제 값을 돌려주는지 확인한다. 도구는 공개 API와 파일 바이트만 쓰므로 두 버전에서 똑같이 돈다.

## 결과

| 망가뜨린 방법 | main (체크섬 없음) | 이 브랜치 (체크섬) |
|---|---|---|
| 1. 리프 안 값의 바이트 하나 (실험 0001과 같음) | **열림, 키 1개가 틀린 값** | 거절: `page 9 has a wrong checksum` |
| 2. 반쯤 쓴 페이지 (앞 절반은 새 버전, 뒤 절반은 옛 버전) | 거절: `keys are not in order` | 거절: `page 9 ...` |
| 3. 멀쩡한 페이지를 엉뚱한 자리에 씀 | 거절: `keys are outside the range of their parent` | 거절: `page 9 ...` |
| 4. 긴 값의 부록에서 비트 하나 | **열림, 긴 값이 틀림** | 거절: `page 30 ...` |
| 5. 빈 페이지에서 비트 하나 | 거절: `free page is not empty` | 거절: `page 25 ...` |
| 6. 메타 슬롯 A의 쓰지 않는 자리에서 비트 하나 | 열림, 이상 없음 | 거절: `page 0 ...` |
| 7. 메타 슬롯 B에서 비트 하나 | 열림, 이상 없음 | 열림, 이상 없음 |

## 의미

- **조용히 틀린 값을 돌려주는 경우가 2가지에서 0가지가 됐다.** 1번과 4번이다. 실험 0001에서 "구조 검사는 값 바이트가 바뀐 것을 잡지 못한다"고 적은 문제가 이제 막힌다. 4번은 06번의 부록 페이지가 생기면서 새로 늘어난 경우였다.
- **main이 2·3·5번을 잡은 것은 운이었다.** 반쯤 쓴 페이지는 우연히 키 순서가 깨져서, 엉뚱한 자리의 페이지는 우연히 범위 검사에 걸려서 잡혔다. 바뀐 바이트가 구조와 상관없는 자리였다면 지나갔을 것이다. 체크섬은 어느 바이트가 바뀌든 잡고, 오류에 **어느 페이지**인지 적는다.
- **3번은 페이지 번호를 섞은 덕이다.** 옮겨진 페이지는 내용과 체크섬이 모두 멀쩡하다. 체크섬을 계산할 때 페이지 번호를 넣었기 때문에 "9번 자리에 있는데 10번의 지문"이라서 걸린다.
- **6번은 전에는 아무도 몰랐던 손상이다.** 메타 페이지의 안 쓰는 자리라 당장 해는 없다. 그래도 그 장이 망가지고 있다는 신호다.
- **7번(메타 B)은 일부러 남겨 둔 빈칸이다.** 지금은 열 때 메타 A만 읽는다. B를 읽고, A가 망가졌을 때 B로 넘어가는 규칙은 두 장을 번갈아 쓰는 #23에서 만든다(설계 결정 2). B의 체크섬 자체는 이미 써 두었다.
- **체크섬은 알아채기만 한다.** 일곱 경우 모두 데이터를 되살리지는 못한다. 되살리는 일은 WAL(#22)의 페이지 사본이 맡는다. 체크포인트 뒤에 생긴 손상은 사본이 없으니 오류로 알리는 것이 최선이다(ADR 0008).
