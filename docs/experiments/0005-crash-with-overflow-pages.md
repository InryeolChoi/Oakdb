# 0005. 긴 값을 쓰거나 지우다가 멈추면

이슈 #18의 검증 기록이다.

- 환경: macOS (Apple silicon), APFS, debug 빌드
- 도구: `crates/oakdb/examples/overflow_crash.rs`

**질문**: 긴 값 하나를 쓰는 커밋은 리프 한 장과 부록(overflow) 여러 장을 쓴다. 빈 페이지를 다시 쓰기도 하고, 지울 때는 부록을 빈 페이지로 바꿔 쓴다. 그 사이에 프로세스가 죽으면 어떻게 될까?

```sh
cargo run --example overflow_crash -- /tmp/oak-exp5
```

실험 0004와 같은 방법이다. 정해진 횟수만큼 쓰기를 통과시킨 뒤, 그다음 쓰기부터는 모두 실패하는 가짜 파일시스템을 끼웠다. 커밋은 바뀐 페이지를 **페이지 번호 순서로** 쓰고, 그다음에 메타 페이지를 쓴다. 긴 값(부록 5장)을 쓰는 커밋은 리프(페이지 2) → 부록 5장 → 메타, 모두 7번 쓴다. 1번, 3번, 6번 쓴 뒤에 멈춰 봤다.

## 결과

| 경우 | 1번 뒤 멈춤 | 3번 뒤 | 6번 뒤 (메타 직전) |
|---|---|---|---|
| ① 새 페이지에 긴 값 쓰기 | 열리지 않음 | 열리지 않음 | 열리지 않음 |
| ② 빈 페이지를 재사용해 긴 값 쓰기 | 열리지 않음 | 열리지 않음 | 열리지 않음 |
| ③ 긴 값 지우기 | 열리지 않음 | 열리지 않음 | 열리지 않음 |

**9가지 모두 DB가 열리지 않았다.** 열 때 나온 오류와 이유:

| 경우 | 오류 | 왜 |
|---|---|---|
| ① | `page number is outside the file` | 리프가 페이지 2라서 **가장 먼저** 써진다. 리프는 새 부록(페이지 3~7)을 가리키는데, 메타는 아직 "페이지 3장"이다 |
| ② 1·3번 | `overflow chain runs into a page that is not overflow` | 리프는 새 부록을 가리키는데, 그 페이지들은 디스크에서 아직 빈 페이지다 |
| ② 6번 | `page is reached twice` | 부록은 다 써졌는데, 메타는 그 페이지들을 아직 빈 페이지 목록의 일부로 본다. 한 페이지를 두 곳에서 쓰고 있다 |
| ③ | `page is neither in use nor free` | 리프에서 값이 빠졌는데, 메타의 빈 페이지 목록에는 그 부록이 아직 없다. 어디에도 속하지 않는 페이지가 생겼다 |

## 의미

- **①은 쓰는 순서 때문이다.** 03번은 "메타를 마지막에 쓰면 메타가 없는 페이지를 가리키지는 않는다"고 했다. 하지만 리프가 새 페이지보다 번호가 작아서 먼저 써지면, 리프가 아직 없는 페이지를 가리킨다. 새 페이지를 먼저 쓰도록 순서를 바꾸면 "1·3번 뒤 멈춤"은 커밋이 없던 일이 된다. 하지만 리프를 쓰고 메타를 쓰기 전에 멈추면 여전히 열리지 않는다. 실험 0004 경우 3과 같은 이유로 순서를 손보지 않았다.
- **②는 재사용이 만든 새 경우다.** 06 전에는 새 페이지가 늘 파일 끝에 붙었다. 이제는 빈 페이지 자리에 부록을 쓰므로, 멈추면 "빈 페이지이자 부록"인 페이지가 생긴다. 이걸 그냥 열면 다음 커밋이 쓰고 있는 페이지를 새 값에 내줘서 데이터가 덮어써진다. 열 때 검사(설계 4절)가 그것을 막았다.
- **③은 검사를 엄격하게 만든 대가다.** "어디에도 속하지 않는 페이지"는 공간을 잃을 뿐 데이터를 망가뜨리지는 않는다. 그래도 지금 검사는 열기를 거부한다. 덕분에 "빈 리프를 빈 페이지 목록에 안 넣음" 같은 버그를 테스트가 잡았다(변이 검사 M5). 이 대가를 받아들일지는 PR에서 정한다.
- 세 경우 모두 **조용히 틀린 값을 돌려주지는 않았다.** 시끄럽게 실패했다. 고치는 일은 WAL(#22)이 맡는다. 커밋의 모든 페이지와 새 메타가 로그에 들어간 다음에야 성공으로 치고, 다시 열 때 로그를 재생하면 9가지 모두 "전부" 또는 "전무"가 된다. 이 9가지는 #21(정전 실험)과 WAL 티켓의 시험 목록에 더한다.
