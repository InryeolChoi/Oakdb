# 0012. 길이만 닿는 쓰기를 더한 정전 실험

이슈 #56의 검증 기록이다. 가짜 디스크(`SimFs`)의 정전에 "끝을 넘는 쓰기가 **길이만 닿고 내용은 0**"인 운명을 더했다(설계 0013). 그 뒤 세 가지를 확인했다. 엔진이 여전히 약속을 지키나, 예전에 못 잡던 변이 C3·C16을 이제 잡나, 예전 시드의 뜻이 얼마나 바뀌었나.

PR #58 리뷰(P4)에서 처음 모델이 **실제보다 험하다**는 것이 나왔다. "끝"을 쓸 때 재서, 비우기가 사라지면 0이 디스크에 남은 옛 내용을 덮었다. 실제 저널은 그런 상태를 못 만든다. 그래서 "끝"을 **정전 때 디스크의 길이**로 바꿨다(설계 0013 9절). 아래 표는 리뷰 전과 뒤를 나란히 적는다.

- 환경: Apple M3 (Mac15,13), macOS 27.0.1. 정전 실험은 가짜 디스크라 OS와 무관하고, 회귀 테스트는 CI에서 macOS·Linux 둘 다 돈다
- 도구: `crates/oakdb/examples/crash_sim` (보고에 "길이만"·길이 변경·파일 이름을 찍고, `sweep`이 체크포인트 도중 정전을 따로 세고 "길이만"이 나온 시드 수를 셈), `docs/experiments/scripts/mutants.py`

```sh
cargo run --release --example crash_sim -- sweep 0 100000
cargo run --release --example crash_sim -- every 7 8     # 42, 11, 23, 99도
python3 docs/experiments/scripts/mutants.py sim
python3 docs/experiments/scripts/mutants.py checkpoint
python3 docs/experiments/scripts/mutants.py wal
```

## 1. 정전 실험

| 결과 | 0010 (체크포인트 섞음) | 0012 리뷰 전 (끝 = 쓸 때) | 0012 리뷰 뒤 (끝 = 정전 때 디스크) |
|---|---|---|---|
| 시드 0~99,999 약속 지킴 | 100,000 | **100,000** | **100,000** |
| 그중 "길이만"이 나온 시드 | — | 12,919 (12.9%) | 12,919 (12.9%) |

지금 엔진은 `set_len` 뒤에 언제나 sync를 하므로, 두 규칙이 갈리는 경우("자르기가 사라진 뒤 끝을 넘는 쓰기")가 생기지 않는다. 그래서 숫자가 같다.

**모든 정전 시점** 훑기 (시점마다 정전 시드 8개, 리뷰 전후 같음):

| 작업 시드 | 커밋 | 정전 시점 | 하나라도 깨지는 시점 |
|---|---|---|---|
| 7 | 28 | 179 | **0** |
| 11 | 4 | 16 | **0** |
| 23 | 17 | 87 | **0** |
| 42 | 14 | 94 | **0** |
| 99 | 24 | 172 | **0** |

**엔진 버그는 나오지 않았다.** 새 고장이 엔진에 보여 주는 것은 세 자리다.

| 자리 | "길이만"이면 | 엔진이 버티는 이유 |
|---|---|---|
| 커밋을 WAL 끝에 덧붙임 | 마지막 커밋 자리가 0 | 0은 레코드 종류가 아니라 재생이 거기서 멈춘다. 응답하지 않은 커밋이라 잃어도 된다 |
| 체크포인트가 데이터 파일을 늘림 | 새 페이지가 0 | 아직 표지를 안 썼다. 열면 옛 표지 + WAL로 다시 옮긴다 |
| WAL 머리말 (비운 뒤) | 20바이트 0 | P1 수정: 20바이트 이하 WAL은 머리말이 없는 것으로 보고 새로 씀 |

### 변이를 심고 같은 실험 (10만 시드)

| 심은 것 | 0010 | 리뷰 전 | 리뷰 뒤 | 오류 |
|---|---|---|---|---|
| C16 (P1 수정 뺌: 20바이트 0 WAL 거절) | 0 | 811 | **811** (만드는 도중 150, 체크포인트 도중 661) | `WAL header is damaged` |
| C3 (비우기 뒤 sync 뺌) | 0 | 316 | **0** | — |

- **C16은 실제와 같은 이유로 잡힌다.** 비우기는 sync로 굳어 있고, 그 뒤 머리말이 "길이만" 닿아 20바이트 0 WAL이 남는다. 실제 ext4 writeback·XFS가 만들 수 있는 상태다. `crash_sim one 109`:

```text
power cut in the checkpoint after commit 7, or not at all
unsynced writes at the crash:
  oakdb.wal page 0: length only, zeros from byte 0
```

- **C3의 316건은 모델이 만든 상태였다.** 리뷰 전 C3가 깨지던 모양은 모두 "비우기는 사라지고, 머리말은 길이만 닿아 옛 WAL 앞 20바이트를 0으로 덮음"이었다. 실제 파일 시스템은 늘리기만 남기고 앞선 자르기를 잃지 않는다. 리뷰 뒤 모델에서는 비우기가 사라지면 머리말 쓰기가 옛 WAL 안쪽이라 "길이만"이 될 수 없고, C3를 심어도 0건이다.
- **C3가 실제로 잃는 것이 없다는 근거** (설계 0013 2절 표): 둘 다 사라짐 → 옛 회차 WAL이라 버림 / 비우기 닿고 머리말 길이만 → 20바이트 0 → P1 수정 / 비우기 사라지고 머리말 닿음 → 옛 레코드가 새 머리말의 사슬을 잇지 못해 cut 파일로 감(이미 장부에 옮긴 커밋). C3를 심고 체크포인트 시점별 테스트(마지막 연산 4개 × 시드 64개, 그리고 모든 연산 × 시드 8개)와 10만 시드를 돌려 **깨지는 경우 0**을 확인했다. 엔진의 sync는 방어용으로 남긴다.

## 2. 변이 검사

| 모드 | 0010 | 리뷰 전 | 리뷰 뒤 |
|---|---|---|---|
| `sim` (SimFs 버그) | 14/14 | 20/20 | **20/20** |
| `checkpoint` (C1~C19) | 18/19 (C3 놓침) | 19/19 | **18/19** (C3는 예상된 생존) |
| `wal` (W1~W11) | 11/11 | 11/11 | **11/11** |

**C3는 "예상된 생존"이다.** 실제 모델에선 필요 없는 sync라서, 잡히지 않는 것이 맞다. `mutants.py`의 이름과 주석에도 "expected to survive"라고 적었다. 구멍이 아니다.

이 고장 모델의 SimFs 버그 (리뷰 뒤 목록):

| 심은 버그 | 잡은 테스트 (일부) |
|---|---|
| "길이만"이 안 나옴 | `a_write_past_the_end_can_land_as_its_length_alone_with_zeros` 외 4개 |
| "길이만"인데 내용을 씀 | 같은 5개 |
| "길이만"인데 파일이 안 늘어남 | 같은 5개 |
| 0을 쓰기 시작부터 (디스크 끝이 아니라) | `only_the_part_past_the_old_end_reads_as_zeros` |
| 끝 안쪽 쓰기도 "길이만" | `a_crash_reports_what_became_of_each_unsynced_change` 외 3개 |
| **옛 규칙: 끝을 쓸 때 잼** (리뷰 뒤 더함) | `zeros_never_cover_bytes_the_disk_still_holds`, `a_write_into_grown_space_is_inside_the_file_once_the_growth_landed` |

리뷰 전 목록의 "끝을 정전 때 디스크로 잼"은 이제 올바른 동작이라 빠지고, 그 자리에 옛 규칙이 변이로 들어갔다.

C16을 잡는 엔진 테스트: `a_power_cut_while_the_wal_starts_again_keeps_every_commit`, `a_cut_while_writing_the_wal_header_can_leave_its_length_and_zeros`, 고정 시드 109(`a_wal_header_that_landed_as_zeros_opens`), `every_seed_keeps_the_promise`, 기존 P1 테스트 3개. `mutants.py checkpoint`는 cargo가 처음 실패한 테스트 파일에서 멈추므로 `crash.rs`의 결과를 보이지 않는다. `crash.rs`만 따로 돌려 확인했다.

## 3. 시드의 뜻이 바뀌었나 (완료 조건 5)

새 운명은 주사위를 더 던지지 않는다(설계 0013 3절). 그래서 **보고에 "길이만"이 없는 시드는 디스크가 예전과 똑같다.** 10만 시드 중 87.1%가 그렇다.

`tests/crash.rs`의 고정 시드. 리뷰(P2) 뒤 주석을 지금 하는 일로 모두 다시 썼다.

| 시드 | 예전 (0008, WAL 전) | 지금 하는 일 (`crash_sim one`) | "길이만" |
|---|---|---|---|
| 184 | 만드는 도중, 열 수 없는 파일 | 새 WAL 머리말을 쓰기 직전 정전, 디렉터리 sync 전이라 WAL이 사라짐 | 없음 |
| 536 | 만드는 도중, 메타 뒤 | WAL을 열기 직전 정전, 빈 데이터 파일만 남음 | 없음 |
| 213 | 새 페이지 없이 닿은 페이지 | 첫 연산 전에 정전 | 없음 |
| 84 | 찢어진 잎 | 커밋 5의 WAL 쓰기 전에 정전, 응답한 커밋 5개 | 없음 |
| 319 | 분할 도중 | 커밋 1의 sync에서 정전, WAL 쓰기가 통째로 남아 커밋이 있음 | 없음 |
| 1680 | 잎 두 개 커밋 | 커밋 4 뒤 체크포인트, 표지를 썼지만 sync 전 (남음) | 없음 |
| 406 | 잎 두 개 커밋 | 커밋 3 뒤 체크포인트, 비우기 뒤 sync에서 정전, 비우기 사라짐 → 옛 WAL 버림 | 없음 |
| 159 | 페이지 sync와 메타 사이 | 커밋 24 뒤 체크포인트, 페이지를 옮기다 정전, 한 페이지 찢김 | 없음 |
| 529 | 쓰는 중인 페이지를 가리키는 빈 목록 | 커밋 9 뒤 체크포인트, 페이지를 옮기다 정전, 데이터 파일 끝의 page 14가 **길이만** | **있음** |
| 109 (새로) | — | 커밋 7 뒤 체크포인트, 머리말 sync에서 정전, 20바이트 0 WAL (C16을 잡음) | 있음 |

- 9개 중 8개는 디스크가 예전과 같다. 529만 page 14가 "사라짐"에서 "길이만"으로 바뀌었고, 여전히 약속을 지킨다.
- 이 시드들의 **예전 모습은 WAL(#22)부터 이미 재현되지 않는다.** 연산 순서가 바뀌었기 때문이다. 지금은 "예전에 깨지던 시드가 계속 약속을 지키나"를 보는 테스트이고, 그 뜻은 그대로다.
- 리뷰 전에는 C3를 잡는 시드 349도 고정했다. 그 시드는 C3가 연산 수를 하나 바꿀 때만 머리말 sync에서 끊겼다(리뷰 P1). C3가 실제로 필요 없는 sync가 되면서 뜻이 없어져 지웠다.

| 가설 | 판정 | 근거 |
|---|---|---|
| 길이만 닿는 쓰기를 더하면 P1 수정을 빼는 것(C16)을 정전 실험이 잡는다 | **채택** | 811시드, 고정 시드 109, 시점별 테스트 |
