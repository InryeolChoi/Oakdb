# 0017. loom — 커밋 대기열의 모든 실행 순서

이슈 #29, 설계 `docs/design/0024-concurrency-verification.md` V8~V10. 커밋 스레드의 대기열(`commit_queue`: 요청 받기 → 묶기 → 처리기에 넘기기 → 닫히면 끝내기)을 loom으로 돌렸다. loom은 잠금·조건 변수·채널을 자기 가짜로 바꾸고, 스레드가 번갈아 갈 수 있는 순서를 전부 실행한다.

**비유**: 창구 절차서 한 장을 놓고 "손님 둘이 동시에 오면? 직원이 퇴근하는 순간 손님이 오면?"을 경우의 수 하나도 빼지 않고 따져 보는 것. 그림책 1-5의 "가능한 순서 전부 돌리기"다.

## 1. 모델 세 개

모두 실제 엔진이 쓰는 `Queue`와 `serve`를 그대로 쓴다. 디스크만 가짜 처리기로 바꿨다. 가짜 처리기는 묶음을 잠금 안에서 지도에 공개한 뒤 답한다(엔진이 sync 뒤에 하는 일과 같은 순서).

| 모델 | 스레드 | 확인하는 것 |
|---|---|---|
| answered once, read your writes | 커밋 스레드 + 손님 N + 메인 | 모든 커밋이 답을 **정확히 한 번** 받는다. `Ok`를 받은 손님이 곧바로 읽으면 자기 쓰기가 보인다. 대기열을 닫으면 커밋 스레드가 끝난다(교착 없음) |
| checkpoint order | 커밋 스레드 + 손님 N-1 + 메인 | 메인이 커밋 → 정리 → 커밋을 기다리지 않고 연달아 보낸다. 정리는 앞 커밋을 보고, 뒤 커밋은 보지 않는다. 다른 손님의 커밋이 섞여 묶여도 같다 |
| stopped | 커밋 스레드 + 손님 N + 메인 | 첫 묶음 뒤 엔진이 멈춘다. 그 뒤 커밋은 모두 `Stopped`를 받고, `Ok`를 받은 커밋이 정확히 공개된 커밋이다 |

## 2. 순서 수와 시간

`LOOM_CLIENTS=N LOOM_MAX_PREEMPTIONS=P RUSTFLAGS="--cfg loom" cargo test -p oakdb --release --lib loom -- --nocapture --test-threads 1`. Apple M3, macOS 27.0.1.

| 손님 N | 끼어들기 상한 P | answered once | checkpoint order | stopped | 합계 시간 |
|---|---|---|---|---|---|
| **2** | **2** (CI) | 6,147 / 0.24s | 1,504 / 0.06s | 4,988 / 0.17s | **0.5초** |
| 2 | 3 | 27,524 / 1.8s | 6,323 / 0.3s | 15,164 / 1.0s | 3.1초 |
| 3 | 2 | 394,146 / 32s | 14,493 / 1.0s | 197,487 / 16s | 49초 |
| 3 | 3 (수동) | **8,298,800 / 659s** | 395,958 / 27s | 3,227,102 / 251s | 약 15분 |

- **모두 통과.** 830만 가지 순서 어디에서도 답을 못 받거나 두 번 받는 손님, 자기 쓰기를 못 보는 손님, 교착이 없었다.
- **손님 한 명, 끼어들기 한 번이 순서를 수십 배로 늘린다.** 2·2에서 3·3으로 가면 1,350배다. 그림책 1-5의 계산기가 보여 준 폭발이 실제 숫자로 나왔다. 그래서 CI는 2·2(빌드 포함 1~2분)만 돌리고, 3·3은 `loom.yml`을 손으로 돌린다.

## 3. loom이 정말 잡나: 대기열에 버그 셋을 심어 봤다

검사기와 같은 요령이다. 대기열 코드를 잠깐 바꾸고 2·2 모델을 돌렸다(스크립트로 바꾸고 바로 되돌렸다. 커밋하지 않았다).

| 심은 버그 | loom 결과 | 일반 테스트였다면 |
|---|---|---|
| M1. `send`가 커밋 스레드를 깨우지 않음 (`notify_one` 빠짐) | 첫 모델에서 `deadlock` | 기다리는 커밋 스레드가 영원히 잠듦. 테스트가 멈춰서 알 수는 있다 |
| M2. 묶음을 끊은 정리 요청을 버림 | checkpoint order에서 `deadlock` (정리 요청한 쪽이 답을 영원히 기다림) | 정리 요청이 **커밋 묶음 바로 뒤에** 줄 서야만 생긴다. 무작위 테스트로는 운에 달림 |
| M3. 커밋 스레드가 첫 요청을 기다리지 않음 (`recv` 대신 `try_recv`) | `deadlock` | 스레드가 시작하자마자 끝남. 첫 커밋이 늦게 오면 생긴다 |

### 모델을 만들지 않은 성질: "`received` 수가 오르면 요청은 이미 대기열 안"

설계 V8 표에 있던 이 성질(설계 0021 Q6)은 loom 모델로 만들지 않았다(PR #79 리뷰 P9).

- **이유 1: loom이 볼 것이 없다.** `Db::ask`는 `requests.send(...)`가 돌아온 **뒤에** 같은 스레드에서 `received`를 올린다. 한 스레드 안의 앞뒤 순서이고, `send`가 대기열 잠금을 놓은 뒤라 그 요청은 이미 `items`에 들어 있다. 다른 스레드가 수를 보고 대기열을 보면, 잠금을 거쳐 보므로 요청이 보인다. 끼어들기로 뒤집힐 수 있는 순서가 없다.
- **이유 2: 모델이 `Db`를 써야 한다.** `received`는 `Db`의 카운터(`std::sync::atomic`, loom 바깥)이고, loom 모델은 `Db` 없이 대기열과 `serve`만 돈다. 이 성질 하나를 위해 `Db`를 loom 아래로 옮기면 파일 시스템·스레드 시작까지 loom에 넣어야 한다.
- **대신**: 이 순서는 `Db::ask`의 주석과, 이 수를 기다리는 엔진 테스트(설계 0021의 그룹 커밋 테스트)가 지킨다. 같은 이유로 `Db::drop`도 모델에서는 `queue.close()`로 흉내 낸다.

M2가 loom의 쓸모를 보여 준다. "정리 요청이 커밋 바로 뒤에 바구니에 들어와 있고, 마침 커밋 스레드가 그 묶음을 꺼내는 중"이라는 좁은 순서를 loom은 빠짐없이 만든다.

## 4. 만들면서 바꾼 것

**loom의 채널은 "보내는 쪽이 다 사라졌다"를 모른다.** 엔진은 `Db`를 버릴 때 요청 채널의 보내는 쪽을 버리고, 커밋 스레드는 `recv()`가 `Err`를 돌려주면 끝났다. loom의 `mpsc`에서는 이 `recv()`가 영원히 기다리는 것으로 보여, loom이 교착이라며 멈췄다. 그래서 대기열을 `Mutex<VecDeque> + Condvar + 닫힘 표시`로 직접 짰다(약 60줄). 이 대기열은 실제 엔진과 loom 모델이 함께 쓴다. 표준 채널을 그대로 두고 모델에서만 다른 것을 쓰면, loom이 검증한 것이 실제 코드가 아니게 된다. 손으로 짠 동시성 코드가 늘어난 대신, 그 코드는 이제 loom이 모든 순서에서 확인한다.

워크스페이스 테스트 828개는 대기열을 바꾼 뒤에도 모두 통과했다.
