# 0008. 정전 실험: 지금 설계는 어디서 깨지나

이슈 #21의 검증 기록이다. 10번(WAL)이 무엇을 고쳐야 하는지 보여 주는 "고치기 전" 사진이다.

- 환경: macOS (Apple silicon), 가짜 디스크(`SimFs`). 디스크 쪽 결과는 OS와 무관하다
- 도구: `crates/oakdb/examples/crash_sim` (엔진 공개 API만 사용)

```sh
cargo run --example crash_sim -- sweep 0 10000   # 시드 1만 개
cargo run --example crash_sim -- one 159         # 시드 하나 재현
cargo run --example crash_sim -- every 7 16      # 작업 하나의 모든 정전 시점
```

**질문**: 커밋 도중 아무 시점에서나 전원이 나가면, 다시 열었을 때 약속이 지켜질까?

1. 다시 열린다.
2. 응답(OK)한 커밋은 모두 있다.
3. 정전에 걸린 커밋은 전부 있거나 전부 없다.

**시드 하나가 정하는 것**:
- 작업: 커밋 1~30개, 커밋마다 put·delete 1~8개. 값의 1/6은 부록 페이지에 들어가는 긴 값이다.
- 정전 시점: "디스크를 바꾸는 작업 n번 뒤", 전체 작업 수 안에서 고른다.
- 정전 때 무엇이 남을지 정하는 시드.

## 깨지는 방식 다섯 가지 (가장 짧은 예)

각 시드는 `tests/crash.rs`에 `#[ignore = "needs the WAL (#22)"]` 테스트로 남겼다. WAL이 들어오면 `ignore`를 떼고 통과해야 한다.

### 1. 만들다 만 DB는 열리지 않는다 (시드 184, 536)

새 DB를 만들 때 쓰는 순서는 이렇다: 리프(페이지 2) → 메타 A·B → sync → 디렉터리 sync.

- 시드 184: 3번째 작업 뒤에 끊겼다. 페이지 2는 찢겨서 남았고 메타는 쓰이지 않았다. 파일이 비어 있지 않으니 엔진은 "있는 DB"로 열려다 `not an Oakdb data file`로 거절한다.
- 시드 536: 반대로 메타가 남고 리프가 사라져서 `shorter than its meta page says`.

잃은 커밋은 없다. 그래도 사용자는 파일을 손으로 지워야 다시 쓸 수 있다. 스펙의 "재시작하면 자동으로 복구된다"(사용자 스토리 23)를 어긴다.

### 2. 찢긴 페이지는 알아채기만 한다 (시드 84, 495)

```
page 2: torn, sectors #.###..#     ← 8칸 중 5칸만 새 내용
verdict: page 2 has a wrong checksum
```

07번 체크섬이 제 할 일을 했다. 조용히 틀린 값을 돌려주지 않고 거절한다. 하지만 되살릴 사본이 없어서 DB 전체가 열리지 않는다. 가장 흔한 실패다(1,604건).

### 3. 리프는 남고 그 리프가 가리키는 새 페이지는 사라진다 (시드 213, 319)

- 시드 213: 첫 커밋이 페이지 2(첫 리프)를 덮어쓴 직후 끊겼다. 이 커밋이 파일 끝에 새로 붙일 페이지(분할로 생긴 리프나 긴 값의 부록)는 쓰이기 전이었다. 페이지 2는 남았고, 그 페이지가 아직 없는 파일 밖의 페이지를 가리키게 됐다.
- 시드 319: 한 커밋이 쓴 페이지 넷(2~5) 중 둘은 남고, 하나는 사라지고, 하나는 찢겼다. 열 때 리프끼리의 사슬이 끊긴 것으로 나타났다.

### 4. 반쪽 커밋 (시드 1680)

```
power cut during commit 5
unsynced writes at the crash:
  page 2: kept
  key: acknowledged / cut commit / after the crash
    24: absent / 225 bytes / 225 bytes (NEW)
    55: absent / 71 bytes / 71 bytes (NEW)
   105: absent / 7381 bytes / absent (old)
   106: 310 bytes / 6 bytes / 310 bytes (old)
   140: absent / 393 bytes / absent (old)
```

커밋 5는 리프 두 장을 고친다. 페이지 번호 순서로 쓰는데, 첫 장(페이지 2)을 쓴 직후에 끊겼다. 첫 장의 키(24, 55)는 새 값이고 둘째 장의 키(105, 106, 140)는 옛 값이다. 열리고 읽히기까지 해서 **오류 없이 틀린 상태**를 보여 준다. 가장 위험한 경우다.

### 5. 디스크가 완벽해도 깨진다 (시드 159)

```
power cut during commit 11
unsynced writes at the crash:
                                   ← 없음: 남거나 사라질 쓰기가 하나도 없었다
verdict: page is reached twice
```

커밋 11의 페이지는 모두 쓰고 sync까지 끝났다. 전원은 메타 페이지를 쓰려던 순간 나갔다. 디스크는 아무것도 잃거나 찢지 않았다. 그런데도 깨진다. 제자리에서 덮어쓴 새 페이지와 옛 메타(옛 루트, 옛 빈 페이지 목록)가 서로 맞지 않기 때문이다. "메타를 마지막에 쓰면 안전하다"는 생각은 **덮어쓰지 않을 때만** 맞는다. 덮어쓴 순간 옛 메타가 가리킬 옛 페이지가 없다.

## 덤: 엔진 버그 하나 (시드 529, 7872)

debug 빌드에서 다시 열다가 **panic**이 났다. 메타 쓰기가 사라져 옛 빈 페이지 목록의 머리가 이미 다시 쓰인 페이지를 가리켰다. 열 때 하는 검사(`Tree::check`)는 빈 페이지 목록을 `std::iter::successors`로 따라간다. 이 반복자는 지금 페이지를 돌려주기 **전에** 다음 페이지 번호를 읽는다. 그래서 "종류부터 확인한다"는 주석과 달리 리프에서 `next()`를 불렀고, `debug_assert`에 걸렸다. release 빌드에서는 뜻 없는 숫자를 읽은 뒤 종류 검사가 거절하므로 해는 없다. 06번 정리 때 들어간 버그이고, WAL과 상관없이 고칠 수 있다. `tests/crash.rs`에 ignore 테스트로 남겼다(PR에서 결정).

## 의미

- **약속 1(다시 열린다)이 가장 많이 깨진다.** 거의 모든 실패가 "열기 거절"이다. 07번 체크섬과 04·06번의 구조 검사 덕분에 대부분 **조용히 틀리는 대신 시끄럽게 거절**한다. 시끄러운 실패는 고칠 수 있다. WAL의 페이지 사본이 그 재료다.
- **조용히 틀리는 경우는 반쪽 커밋 하나뿐이다(2.8%).** 페이지 단위 검사로는 잡을 수 없다. 각 페이지는 멀쩡하고 서로 어긋날 뿐이다. 커밋을 한 덩어리로 남기는 로그만이 해결한다.
- **응답한 커밋은 한 번도 사라지지 않았다.** sync 뒤에 OK를 주는 규칙은 지켜지고 있다. 문제는 "응답한 뒤의 다음 커밋이 앞 커밋까지 망가뜨려 DB가 안 열리는 것"이다. 열리지 않으면 응답한 커밋도 못 읽는다.
- **10번(WAL)이 할 일이 이 표로 정해졌다.** 커밋의 페이지 사본을 로그에 먼저 쓰고 sync한 뒤 OK를 준다. 데이터 파일은 체크포인트(11번)에서 고친다. 그러면 1~5번 모두 "로그를 다시 적용"해서 고칠 수 있다. 1번(만들다 만 DB)은 "만들기"도 로그 위에서 하거나, 빈 파일을 새 DB로 보는 규칙이 필요하다.
