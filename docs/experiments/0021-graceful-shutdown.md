# 0021. 서버 정상 종료 — 부하 중 SIGTERM, 종료 도중 kill -9, 두 번째 Ctrl-C, 멈춘 엔진

이슈 #38, 설계 `docs/design/0028-graceful-shutdown.md` Q13. 이번 티켓에서 `oakdb serve`가 SIGINT·SIGTERM을 받으면 문을 닫고, 실행 중인 문장을 끝내 응답하고, 남은 접속에 `ERROR 0x49`를 보내고, 마지막 체크포인트를 한 뒤 끝나게 되었다. 실험은 그 약속이 **실제 프로세스와 실제 신호**에서 지켜지는지 본다.

**비유**: 식당 마감. ① 손님이 꽉 찬 저녁에 "마감!"을 100번 외쳐 본다. 계산한 손님의 영수증이 사라지거나, "마감입니다"라고 돌려보낸 손님의 주문이 장부에 들어가거나, 아무 말 없이 쫓겨난 손님이 하나라도 있으면 실패다. ② 마감 정리 도중 정전(kill -9). ③ 사장이 "당장 닫아!"를 한 번 더 외친다. ④ 주방이 이미 고장 난 상태(엔진 멈춤)에서 마감한다.

도우미: `crates/oakdb-server/examples/shutdown_faults.rs`. Apple M3, macOS 27.0.1, APFS, `F_FULLFSYNC`, release 빌드. 이 기록의 숫자는 macOS에서 잰 것이다. Linux는 CI에서 같은 불변식을 작게(`tests/signal.rs`, 5라운드) 돌린다.

```
cargo build --release -p oakdb-server --bin oakdb --example shutdown_faults
target/release/examples/shutdown_faults sigterm 100
target/release/examples/shutdown_faults kill9 50
target/release/examples/shutdown_faults second 20
```

## 1. 부하 중 SIGTERM ×100

실제 디렉터리에 `oakdb serve --shutdown-grace 2`를 띄우고, 클라이언트 8개가 각자 고유 id로 쉬지 않고 쓴다(셋 중 하나는 `BEGIN` → `INSERT` 2개 → `COMMIT`, 나머지는 자동 커밋 `INSERT`). 50~500 ms 사이 무작위 시각에 `SIGTERM`. 요청마다 결과를 적는다: 성공 / `0x49` / **응답 없이 끊김** / 그 밖의 오류. 끝난 뒤 같은 디렉터리로 다시 띄워 확인한다.

| 확인 | 기대 | 결과 (100라운드) |
|---|---|---|
| 종료 코드 0, WAL이 헤더(20바이트)뿐 | 100번 모두 | **100** |
| 응답받은 커밋이 사라짐 | 0 | **0** (커밋된 id 11 281개) |
| `0x49`를 받은 id가 쓰여 있음 | 0 | **0** (`0x49`를 받은 id 1 207개) |
| 응답 없이 끊긴 요청 | 0 | **0** (요청 19 397개) |
| 그 밖의 오류 | 0 | 0 |

종료에 걸린 시간(신호 → 프로세스 끝): 최소 40 ms, 중간값 105 ms, 최대 283 ms.

- **설계 Q6의 약속이 그대로 섰다.** "정상 종료에서는 결과 모름이 없다"가 100라운드 동안 한 번도 깨지지 않았다.
- `0x49`를 받은 id가 하나도 쓰이지 않았다는 것은 **"실행한 문장의 응답이 언제나 `0x49`보다 먼저"** 이고 **"`0x49`가 답한 요청은 실행되지 않았다"** 는 뜻이다. 유예(2초)보다 오래 걸린 종료가 없었으므로, 트랜잭션은 모두 유예 안에서 `COMMIT`까지 마쳤고 `0x49`는 그다음 요청(`BEGIN`이나 자동 커밋 `INSERT`)의 답으로 왔다. 유예가 끝나 롤백되는 길은 `tests/shutdown.rs`가 본다.
- 커밋 스레드가 쉬지 않고 sync하는 와중에 100번 신호를 보내도 **신호로 죽은 적이 한 번도 없다.** 마스크가 커밋 스레드에도 걸려 있다는 증거다(설계 Q1: 마스크를 `Db::open`보다 먼저).

## 2. 종료 도중 `kill -9` ×50

`--shutdown-grace 0.3`. 커밋하지 않은 트랜잭션 하나(id −1)를 열어 두고, 클라이언트 8개의 부하 중 `SIGTERM`, 그 뒤 0~450 ms 무작위 시각에 `SIGKILL`. 유예 중, 유예 뒤 정리 중, 마지막 체크포인트 중 어디에서든 죽는다.

| 확인 | 기대 | 결과 (50라운드) |
|---|---|---|
| 다시 띄우면 열림 | 50 | **50** |
| 응답받은 커밋이 사라짐 | 0 | **0** |
| 열어 둔 트랜잭션의 행(−1) | 없음 | **50번 모두 없음** |
| 응답 없이 끊긴 요청 | 생길 수 있음 | 16 |
| 답 못 받은 커밋 중 남은 것 | 있거나 없거나 | 25개 중 15개 |

- SIGKILL은 정상 종료가 아니므로 "응답 없이 끊김"이 생기는 것이 맞다(설계 Q10 표의 아래 줄). 그래도 **응답한 커밋은 하나도 잃지 않았고**, 체크포인트 도중에 죽어도 다음 시작이 WAL을 재생해 열렸다(설계 0011의 약속을 실제 프로세스로 확인).
- 답 못 받은 커밋의 60%가 남아 있었다. sync까지 끝났는데 응답을 보내기 전에 죽은 경우다. 실험 0019와 같은 모양이다.

## 3. 두 번째 Ctrl-C ×20

`--shutdown-grace 60`. 커밋한 행 하나(1), 커밋하지 않은 트랜잭션 하나(2)를 열어 둔다. `SIGINT` → 로그에 `shutting down:`이 찍히면 → `SIGINT` 한 번 더.

| 확인 | 기대 | 결과 |
|---|---|---|
| 종료 코드 | 130 | **20번 모두 130** |
| 두 번째 신호 뒤 1초 안에 끝남 | 예 | **20번 모두** (유예 60초를 기다리지 않음) |
| 다시 띄우면 정확히 {1} | 예 | **20** |

같은 시나리오의 `SIGTERM` → 143은 `tests/signal.rs`가 두 OS CI에서 본다.

## 4. 멈춘 엔진에서 종료

디스크 실패를 실제 프로세스 밖에서 만들 방법이 없어(설계 Q13이 허락한 대로) **프로세스 안 테스트로 대신했다**: `tests/shutdown.rs`의 `on_a_stopped_engine_the_final_checkpoint_fails_and_answered_commits_survive`. `SimFs::fail_once_after(0)`으로 다음 sync를 한 번 실패시켜 엔진을 멈추고(`0x25`), 손잡이를 당긴다.

| 확인 | 결과 |
|---|---|
| `Shutdown::checkpoint`가 `Some(Err(Stopped))` → `is_clean() == false` → `oakdb serve`는 exit 1 | 통과 |
| 다시 열면 응답한 커밋(1)이 있음 | 통과 |

## 정리

| 실험 | 결과 |
|---|---|
| 1. 부하 중 SIGTERM ×100 | 응답 없는 끊김 0, 응답한 커밋 손실 0, `0x49` 받은 쓰기 0, exit 0 ×100 |
| 2. 종료 도중 kill -9 ×50 | 50번 모두 다시 열림, 응답한 커밋 손실 0 |
| 3. 두 번째 Ctrl-C ×20 | 130 ×20, 1초 안에 끝남, 다시 열면 온전 |
| 4. 멈춘 엔진 | 체크포인트 실패 보고 → exit 1, 응답한 커밋 있음 (프로세스 안 테스트로 대신) |

> **Linux 숫자는 아직 없다 (PR #84 리뷰 P14, 결정 D5).** 위 표는 모두 macOS다. 설계 Q11은 "두 OS CI에서 20회쯤"을 말했지만, CI 시간 때문에 `tests/signal.rs`의 부하 불변식은 **5라운드로 둔다**(사용자 결정). 눈 가린 테스터의 `tests/blind_shutdown.rs`가 같은 불변식을 5라운드 더 돌리므로 CI는 OS마다 10라운드를 본다. Linux 기계에서 `shutdown_faults sigterm 100`·`kill9 50`·`second 20`을 돌릴 기회가 오면 이 기록에 덧붙인다.
