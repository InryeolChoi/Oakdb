# 0014. 한 점 조회를 범위 조회로 바꾸면 느려지나 — A/B

이슈 #32, 설계 0019 W9. `WHERE pk = 값`을 엔진의 `get` 대신 양 끝이 같은 범위 조회(`scan`) 하나로 실행하기로 했다. 실행 길이 하나라 단순하지만, 커서를 하나 만드는 만큼 느려질 수 있다. PR #69 검증에서 이것을 재 보았다.

**비유**: 책 한 권을 찾을 때 "청구번호 100번 책 주세요"(`get`)와 "100번부터 100번까지 주세요"(`scan`)의 차이다. 사서가 같은 칸으로 가지만, 두 번째는 "어디까지"를 기억하는 메모지를 한 장 더 쓴다.

## 방법

| 항목 | 값 |
|---|---|
| A | 24e1e33 (main, `get`) |
| B | 90b7859 (PR #69, 한 점 `scan`) |
| 측정 | 1000행 표에서 `SELECT * FROM t WHERE id = k`를 2000번 실행한 문장당 평균 시간. `hit`는 있는 키, `miss`는 없는 키 |
| 반복 | 20라운드, ABBA 순서, 라운드마다 새 DB |
| 검정 | 양측 Mann-Whitney U, 중앙값 비율은 부트스트랩 95% CI. A/A 대조군 포함 |
| 환경 | Apple M3, macOS 27.0.1, release 빌드, 다른 빌드가 돌지 않을 때 |
| 도구 | `python3 docs/experiments/scripts/ab_sql.py 24e1e33 90b7859` (측정 프로그램 `docs/experiments/scripts/ab_versions/sql_point.rs`) |

## 결과

| 가설 | 측정 | 중앙값 A → B | 비율 (95% CI) | p | 판정 |
|---|---|---|---|---|---|
| 있는 키를 찾을 때 느려지지 않는다 | `hit` | 2.5 → 3.0 µs | 1.207 [0.835, 1.804] | 0.017 | 애매함. p는 작지만 CI가 1을 포함 |
| 없는 키를 찾을 때 느려지지 않는다 | `miss` | 2.2 → 2.7 µs | 1.215 [1.127, 1.281] | 8.8e-05 | **기각. 약 20% (+0.5 µs) 느려짐** |
| A/A 대조군 (`hit`) | | | 0.985 [0.862, 1.250] | 0.98 | 측정 신뢰 가능 |
| A/A 대조군 (`miss`) | | | 1.096 [0.942, 1.157] | 0.58 | 측정 신뢰 가능 |

## 결론

- 한 점 조회가 문장당 **약 0.5 µs(약 20%) 느려졌다.** W9의 "느려지지 않는다"는 그대로는 성립하지 않는다.
- 절대값으로는 커밋 한 번(약 3 ms)이나 네트워크 왕복의 수천분의 일이다.
- **사용자 결정: 받아들인다.** 실행 길이가 하나인 단순함을 택했다. `get` 지름길은 되살리지 않는다. 한 점 조회가 병목으로 보이면 그때 다시 잰다.
