# 0009. WAL 뒤의 정전 실험과 커밋 속도

이슈 #22의 검증 기록이다. 실험 0008("고치기 전" 사진)과 같은 도구, 같은 시드로 WAL을 넣은 엔진을 다시 시험했다. 커밋 속도는 WAL 전후 엔진 두 버전을 A/B로 비교했다.

- 환경: Apple M3 (Mac15,13), macOS 27.0.1, APFS, 내장 SSD. 정전 실험은 가짜 디스크(`SimFs`)라 OS와 무관하고, 회귀 테스트는 CI에서 macOS·Linux 둘 다 돈다
- 정전 실험 도구: `crates/oakdb/examples/crash_sim` (바뀌지 않음)
- A/B 도구: `docs/experiments/scripts/ab_versions.py` (이번에 더함)

```sh
cargo run --example crash_sim -- sweep 0 10000                    # debug
cargo run --release --example crash_sim -- sweep 10000 100000     # release
cargo run --release --example crash_sim -- every 7 16
python3 docs/experiments/scripts/ab_versions.py 808c510 <rev> 20 200
```

## 1. 정전 실험

| 결과 | WAL 전 (0008, 시드 0~9999) | WAL 뒤 debug (0~9999) | WAL 뒤 release (10,000~109,999) |
|---|---|---|---|
| ✅ 약속 지킴 | 51% | **10,000 / 10,000** | **100,000 / 100,000** |
| ❌ 열기 실패 | 46% | 0 | 0 |
| ❌ 반쪽 커밋 | 2.8% | 0 | 0 |
| 응답한 커밋 사라짐 | 0 | 0 | 0 |

**모든 정전 시점**을 빠짐없이 훑은 결과(시점마다 정전 시드 16개):

| 작업 시드 | 커밋 | 정전 시점 (전 → 뒤) | 하나라도 깨지는 시점 (전 → 뒤) |
|---|---|---|---|
| 7 | 28 | 228 → 62 | 195 → **0** |
| 42 | 14 | 97 → 34 | 79 → **0** |
| 1000 | 17 | 109 → 40 | 86 → **0** |

정전 시점 수가 줄어든 것도 결과다. 예전 커밋은 페이지마다 쓰기 하나에 sync가 한두 번이었다. 지금은 **쓰기 한 번, sync 한 번**이다. 디스크를 바꾸는 작업이 커밋마다 2개로 줄어서, 커밋 사이에 끊길 수 있는 자리 자체가 적다.

0008에서 깨지는 방식마다 남긴 시드 7개(184, 536, 213, 84, 319, 1680·406, 159)는 `ignore`를 떼고 상시 테스트가 됐고, 모두 통과한다. "시드 0~1999 모두 약속 지킴"도 상시 테스트다.

### 가설 판정

| 가설 (설계 때 적은 것) | 판정 | 근거 |
|---|---|---|
| WAL이 0008의 깨지는 방식 5가지를 모두 막는다 | **채택** | 11만 개 시드에서 실패 0, 시드 7개 상시 통과 |
| 만들기를 WAL 첫 커밋으로 하면 "만들다 만 DB"가 사라진다 | **채택** | 시드 184·536 통과, `a_power_cut_while_creating_leaves_a_database_that_opens` |
| 꼬리를 자르지 않으면 응답한 커밋이 사라진다 | **채택** | 변이 W2(자르기 빼기)를 `garbage_after_the_last_commit_is_cut_off_so_later_commits_count`가 잡음 |

## 2. 변이 검사 (`mutants.py wal`)

WAL에 버그를 하나씩 심고 테스트가 잡는지 봤다. **8/8 잡음.** SimFs 버그 14개도 여전히 14/14다.

| 심은 버그 | 잡은 테스트 (일부) |
|---|---|
| W1 커밋이 sync하지 않음 | 시드 회귀 테스트들, `every_seed_keeps_the_promise` |
| W2 열 때 꼬리를 안 자름 | `garbage_after_the_last_commit_…` |
| W3 새 WAL인데 디렉터리 sync 안 함 | 시드 회귀 테스트들 |
| W4 도장 없는 페이지도 적용 | `pages_without_a_commit_record_are_not_applied` |
| W5 체크섬을 사슬로 잇지 않음 | `a_commit_out_of_its_place_in_the_chain_is_refused` |
| W6 커밋 뒤 끝 위치를 안 옮김 | 시드 회귀 테스트들 |
| W7 체크섬이 틀려도 계속 재생 | `replay_stops_at_the_first_…` |
| W8 마지막 커밋의 crc를 기억 안 함 | `replay_gives_the_latest_image_…` |

스크립트는 `--lib`가 실패하면 통합 테스트를 돌리지 않으므로, 표의 "잡은 테스트"는 처음 걸린 묶음까지만이다.

## 3. A/B: 커밋 속도

**질문**: WAL이 커밋을 느리게 하나, 빠르게 하나? 예전에는 페이지가 늘어나는 커밋만 sync가 두 번(페이지, 메타)이었고, 지금은 언제나 한 번이다. 대신 페이지마다 4,109바이트 레코드를 파일 끝에 붙인다.

**방법** (실험 0002와 같은 원칙)
- A = `808c510`(WAL 전 main), B = WAL 브랜치. 같은 측정 프로그램(`ab_versions/commit_time.rs`, 공개 API만 씀)을 두 버전에 각각 release로 빌드했다.
- 라운드마다 새 DB에 커밋 200번. 라운드의 **평균** 커밋 시간을 표본 하나로 친다. 20 대 20, ABBA 순서, 미리 한 번씩 돌려 버림.
- Mann-Whitney U(양측, 정규 근사), 중앙값 비율의 95% 부트스트랩 구간(2,000회), α = 0.05. **A/A 대조군**(A 대 A)을 같은 방식으로.
- 작업 두 가지: `grow`(커밋마다 새 키 + 1,000바이트 값, 리프가 자주 나뉨) / `overwrite`(작은 키 하나를 계속 덮어씀, 페이지 수 안 바뀜).

| 가설 | 중앙값 A → B | B/A (95% CI) | U | p | 판정 |
|---|---|---|---|---|---|
| `grow`: WAL 전후 커밋 시간이 다르다 | 3,908 → 2,989 µs | **0.765** [0.747, 0.797] | 400 | 6.3e-8 | **채택: 23% 빨라짐** |
| `overwrite`: 다르다 | 2,994 → 2,822 µs | 0.943 [0.928, 1.017] | 247 | 0.20 | 기각 (차이를 말할 수 없음) |
| A/A `grow` | 4,019 → 4,014 µs | 0.999 [0.942, 1.026] | 204 | 0.91 | 측정 신뢰 가능 |
| A/A `overwrite` | 3,003 → 3,003 µs | 1.000 [0.990, 1.014] | 179 | 0.57 | 측정 신뢰 가능 |

`grow`의 U = 400은 20 대 20이 **완전히 갈라졌다**는 뜻이다(B의 모든 라운드가 A의 모든 라운드보다 빠름). p는 이 표본 크기에서 나올 수 있는 최솟값이다.

### 해석

- **커밋 시간은 거의 sync 횟수로 정해진다.** `F_FULLFSYNC` 한 번이 약 3ms이고, 기록하는 바이트 수(4KB 몇 장)는 거의 상관없다. 그래서 sync를 두 번 하던 커밋이 한 번이 되자 1ms가 줄었다. 덮어쓰기는 원래 sync가 한 번이라 차이가 없었다. 실험 0002의 결론("커밋 시간의 대부분은 sync")과 같다.
- **바이트는 늘었다.** 같은 커밋이 이제 4,109바이트 레코드에 37바이트 도장을 더 쓰고, 파일이 끝없이 길어진다. 시간에는 안 보이지만 WAL 크기로 보인다. 체크포인트(#23)가 해결한다.
- 다음으로 커밋을 빠르게 할 방법도 sync 횟수다. 여러 커밋이 sync 한 번을 나눠 쓰는 그룹 커밋(#28)이 그 일을 한다.

## 4. 알려진 구멍 (리뷰가 찾음, PR #54에서 결정)

- **WAL 중간 손상**: 끝이 찢긴 것과 중간 레코드가 (정전이 아닌 이유로) 깨진 것을 구분하지 않는다. 깨진 곳 뒤를 잘라 내므로, 그 뒤의 응답한 커밋이 사라진다. 첫 레코드가 깨지면 빈 새 DB가 된다. 정전 모델(끝의 쓰기만 찢김)에서는 생기지 않아서 이 실험에는 나오지 않는다.
- **sync 실패 뒤 재시도**: 엔진 정지는 #24.
