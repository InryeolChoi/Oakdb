# 0013. 같은 부팅에서 다시 열 때의 캐시 구멍 — 실험

이슈 #59의 검증 기록이다. 설계는 `docs/design/0014-same-boot-cache.md`. 두 번에 걸쳐 고쳤다. 처음에는 열 때 읽은 메타 슬롯과 WAL을 **제자리에** 다시 썼고(be7dfdf까지), PR #60 검증 뒤 사용자가 "기술적으로 더 단단하게"를 골라 **새 파일 + rename**으로 바꿨다(016980c부터). 아래 표는 둘을 나란히 적는다.

- 환경: Apple M3 (Mac15,13), macOS 27.0.1. 정전·실패 실험은 가짜 디스크라 OS와 무관하고, 회귀 테스트는 CI에서 macOS·Linux 둘 다 돈다
- 도구: `crates/oakdb/examples/crash_sim` (끝에 `garbled`를 붙이면 쓰레기 칸 디스크), `docs/experiments/scripts/mutants.py`, `docs/experiments/scripts/ab_versions.py`

```sh
cargo run --release --example crash_sim -- sweep 0 100000            # 그리고 ... garbled
cargo run --release --example crash_sim -- every 7 8                 # 11, 23, 42, 99도, 그리고 ... garbled
python3 docs/experiments/scripts/mutants.py cache                    # checkpoint, failure, wal, sim도
python3 docs/experiments/scripts/ab_versions.py a5deefd <HEAD> 20 200 reopen,closed
```

## 1. 구멍이 실제로 있었나 (빨간 테스트)

| 커밋 | 무엇을 더했나 | 고치기 전 엔진에서 |
|---|---|---|
| 254ade0 | 가짜 디스크의 "잊는 sync"(`FailedSync::Forgets`), #24 실패 훑기 다섯 개를 두 방식으로 | 다섯 개 모두 실패: 같은 부팅에서 다시 열고 커밋 → 정전 → 응답한 커밋 잃음 |
| 172e6fb | 가짜 디스크의 "쓰레기 칸"(`TornSector::Garbled`)과 `rename`, 다시 열기 정전 테스트 네 개를 두 방식으로 | 제자리 덮어쓰기 엔진에서 네 개 모두 실패: `WAL follows checkpoint 2, but the newest meta slot holds checkpoint 1` |

눈 가린 테스터(구현을 안 읽고 이슈·설계만 보고 테스트 20개를 씀)의 테스트는 #59 전 엔진에서 14개가 실패했다. 그중에는 Linux식이 **아닌** 기본 방식에서 깨지는 경우도 있었다. sync는 파일마다라서, 정리 도중 메타 슬롯 sync가 실패한 뒤 다시 열면 새 WAL 머리말이 기다리던 슬롯보다 먼저 디스크에 닿을 수 있었다.

## 2. 정전 실험

| 결과 | #59 전 (실험 0012) | 제자리 덮어쓰기 | 새 파일 + rename (KeepsOld) | 새 파일 + rename (Garbled) |
|---|---|---|---|---|
| 시드 0~99,999 약속 지킴 | 100,000 | 100,000 | **100,000** | **100,000** |
| "길이만"이 나온 시드 | 12,919 | 12,569 | 12,805 | 12,805 |
| 모든 정전 시점 훑기 (작업 5개, 시점마다 시드 8개) 깨지는 시점 | 0 / 548 | 0 / 558 | **0 / 563** | **0 / 563** |

시점 수가 늘어난 것은 열기가 새 파일 열기·쓰기·길이 맞춤·sync·rename을 더 하기 때문이다. "길이만" 시드 수가 바뀐 것도 같은 이유다(연산 순서가 밀림).

`crash_sim`의 작업은 열기를 처음 한 번만 하므로, **다시 여는 도중의 정전**은 `disk_failure.rs`의 테스트가 따로 본다.

| 테스트 (`power_cuts_while_reopening`) | 정전 시점 | 시드 × 방식 | 결과 |
|---|---|---|---|
| 잊힌 커밋이 있는 DB | 열기의 모든 연산 | 8 × (KeepsOld, Garbled) | 통과 |
| 잊힌 정리 (정리의 모든 실패 지점마다) | 열기의 모든 연산 | 8 × 2 | 통과 |
| 정전 뒤의 DB | 열기의 모든 연산 | 8 × 2 | 통과 (제자리 덮어쓰기는 Garbled에서 실패) |
| 정상 종료 뒤의 DB | 열기의 모든 연산 | 8 × 2 | 통과 (제자리 덮어쓰기는 Garbled에서 실패) |
| 정리 도중 정전 (`checkpoint.rs`) | 정리의 모든 연산 | 8 × 2 | 통과. **#59 전부터** 정리는 하나뿐인 사본을 덮어쓰지 않았다 |

### 고정 시드

열기의 연산 수가 바뀌어 `tests/crash.rs`의 고정 시드 10개가 모두 다른 곳에서 끊긴다. 주석을 `crash_sim one`이 보여 주는 지금 모습으로 다시 썼다. 시드 109는 "정리의 WAL 머리말이 20바이트 0으로 닿음"(변이 C16을 잡는 시드)을 더는 만들지 않아, 같은 모습을 만드는 99로 바꿨다. C16을 심고 돌려 99가 잡는 것을 확인했다.

## 3. 처음 제안 "열 때 정리(B+)"는 왜 버렸나

제자리 덮어쓰기 때의 변이 K6(열 때 체크포인트)으로 확인했다. 잊힌 커밋이 있는 DB를 열다 정리의 6번째 연산에서 정전 → 다시 열기가 `overflow page does not hold its share of the value`로 거부했다. 정리가 데이터 파일에 실패한 커밋의 페이지를 쓴 뒤, 금고 속 WAL은 그 커밋 앞에서 끊겨 있어서 응답한 트리와 실패한 커밋의 페이지가 섞였다(설계 0014 2절).

## 4. 변이 검사

최종 코드(ddf44cd)에서 돌렸다. 변이 하나마다 관련 테스트 묶음 전체를 돌리고(`--no-fail-fast`), 잡은 테스트 이름을 모은다.

| 모드 | 0012 (#56) | 제자리 덮어쓰기 (be7dfdf) | 지금 |
|---|---|---|---|
| `cache` (#59) | — | 9/10 (K4 예상된 생존) | **18/19** (K7 놓침, 아래) |
| `sim` | 20/20 | 20/20 | **20/20** |
| `checkpoint` (C1~C19) | 18/19 (C3 예상된 생존) | 18/19 | **19/19** (C3를 이제 잡음, 아래) |
| `failure` (F1~F13, S1~S6) | — | 19/19 | **19/19** |
| `wal` (W1~W11) | 11/11 | 11/11 | **11/11** |

`cache` 모드의 변이:

| 변이 | 결과 | 잡은 테스트 (일부) |
|---|---|---|
| K1 열기: 메타 슬롯을 다시 안 씀 | 잡음 | 정리 실패 훑기, 잊힌 정리 뒤 다시 열기 |
| K2 열기: WAL이 같은 회차여도 슬롯을 다시 씀 (조건 뒤집기) | 잡음 | 다시 열기 정전 네 개 (Garbled) |
| K3 열기: WAL을 새 파일이 아니라 제자리에 | 잡음 | 다시 열기 정전 (Garbled) |
| K4 열기: rename 전에 새 WAL sync 안 함 | 잡음 | 다시 열기 정전 |
| K5 열기: rename 뒤 디렉터리 sync 안 함 | 잡음 | 고정 시드들, 만드는 도중 정전 |
| K6 열기: 슬롯을 새 WAL 뒤에 씀 (순서) | 잡음 | 잊힌 정리 뒤 다시 열기 |
| K7 열기: 남은 새 WAL 파일의 길이를 안 맞춤 | **놓침** | — |
| K8~K11 SimFs: 잊는 sync | 4/4 잡음 | `sim_fs.rs` |
| G1~G3 SimFs: 쓰레기 칸 | 3/3 잡음 | `sim_fs.rs` |
| R1~R5 SimFs: rename | 5/5 잡음 | `sim_fs.rs`, `fs_contract.rs` |

**K7은 테스트 구멍이다.** 길이를 안 맞추면 끊긴 열기가 남긴 더 긴 `oakdb.wal.new`의 꼬리가 새 WAL 뒤에 남는다. 보통은 그 꼬리가 다른 머리말의 사슬이라 재생이 버린다. 하지만 이런 순서가 있다.

1. 실패한 커밋 c6가 캐시에만 있다(잊는 sync).
2. 열기가 c1…c6를 wal.new에 쓰고 sync한 뒤, rename 직전에 정전이 난다. 디스크의 WAL에는 c6가 없다.
3. 다음 열기는 c1…c5를 읽고 **c6가 없는 상태로 연다.** 길이를 안 맞추면 wal.new에 c6가 남고, c6는 c5의 사슬에 이어진다.
4. 커밋 없이 다시 정전이 나면 **c6가 되살아난다.**

c6는 "결과 모름"인 커밋이라 있어도 되고 없어도 된다. 하지만 다시 열어서 "없음"을 본 뒤에 되살아나면 안 된다. 지금 코드는 길이를 맞추니 안전하다. 그러나 이 성질("한 번 본 결과는 바뀌지 않는다")을 보는 테스트가 없다. PR #60 판단할 것으로 올렸다.

**W2·W3은 자리를 옮겼다.** 꼬리를 잘라 내는 일과 열기 끝의 디렉터리 sync가 `wal::write_new`로 옮겨 가서, 같은 버그를 새 자리에 심도록 패턴을 바꿨다. W2는 새 WAL에 잘린 꼬리까지 쓰고, W3은 rename 뒤 디렉터리 sync를 뺀다.

**C3를 이제 잡는다.** #56 뒤로 "예상된 생존"이던 C3(정리의 WAL 비우기와 머리말 쓰기 사이 sync)를 `a_power_cut_anywhere_in_a_checkpoint_keeps_every_commit`의 Garbled 판이 잡는다. 비우기가 닿지 않은 채 머리말 쓰기가 찢겨 쓰레기가 되면, 옛 WAL 앞에 망가진 머리말이 붙는다. 그러면 "머리말이 망가진 긴 WAL"이라 열기가 거절한다. **방어용이라던 sync가 쓰던 칸을 망가뜨리는 디스크에서는 실제로 필요하다.**

## 5. A/B: 다시 열기 시간

`ab_versions.py`, 20라운드 × 커밋 200개, 라운드마다 새 DB, ABBA 순서, Mann-Whitney U. `reopen`은 커밋 뒤 버리고(정전처럼) 다시 여는 시간, `closed`는 `close()` 뒤 다시 여는 시간이다. 변이 검사를 멈춰 둔 채로 쟀다.

| 비교 | 모드 | A | B | B/A [95% 구간] | p | A/A 대조 |
|---|---|---|---|---|---|---|
| #59 전 (a5deefd) → 지금 (be91a68) | reopen | 1.94 ms | 12.07 ms | 6.24 [5.43, 9.03] | 6.3e-08 | 0.93, p 0.53 |
| | closed | 0.92 ms | 7.92 ms | 8.63 [7.34, 9.83] | 6.3e-08 | 0.98, p 1.00 |
| 제자리 덮어쓰기 (be7dfdf) → 지금 (be91a68) | reopen | 8.28 ms | 12.02 ms | 1.45 [1.24, 1.76] | 2.8e-07 | 0.96, p 0.12 |
| | closed | 5.85 ms | 8.31 ms | 1.42 [1.22, 1.65] | 1.5e-04 | 0.95, p 0.71 |

- **열기가 7~10 ms 느려졌다.** macOS에서 `F_FULLFSYNC`는 한 번에 수 ms가 든다. 정상 종료 뒤 열기는 #59 전 디렉터리 sync 1번에서, 새 파일 sync + rename + 디렉터리 sync로 늘었다.
- **새 파일 + rename은 제자리 덮어쓰기보다 약 3.7 ms 더 든다.** 새 inode를 만들고 rename하는 메타데이터 일이 늘어서로 보인다. 하나뿐인 사본을 덮어쓰지 않는 값이다.
- 첫 측정(PR #60 검증 때)은 #59 전이 11.4 ms였다. 그때는 다른 검사가 함께 돌고 있었다. 이번에는 다른 일을 멈추고 재서 절대값이 다르다. 비율과 A/A 대조로 판정한다.
- 커밋 경로의 코드는 바뀌지 않았다(첫 측정에서 커밋 시간 차이 없음).

| 가설 | 판정 | 근거 |
|---|---|---|
| Linux식 실패에서 같은 부팅에 다시 열면 응답한 커밋을 잃는다 | **채택** | 254ade0의 빨간 테스트 5개 |

| 비용은 열기에만 든다 | **채택** | 열기 +7~10 ms, 커밋 경로 코드 변화 없음 |
