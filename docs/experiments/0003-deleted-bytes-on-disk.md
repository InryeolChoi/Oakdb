# 0003. 지운 값은 디스크에서도 사라지는가

이슈 #14의 검증 기록이다.

- 환경: macOS (Apple silicon), APFS, debug 빌드
- 도구: `crates/oakdb/examples/deleted_bytes.rs`

**질문**: `delete`하고 커밋하면 엔진은 그 값을 더 이상 돌려주지 않는다. 그런데 데이터 파일을 직접 열어 보면 값의 바이트도 사라져 있을까?

알아보기 쉬운 값(`OAKDB-SECRET-VALUE-0123456789`)을 넣고 지운 뒤, 단계마다 두 가지를 확인했다. 엔진의 `get`이 값을 돌려주는지, 파일 바이트에서 그 문자열을 찾을 수 있는지다.

```sh
cargo run --example deleted_bytes -- /tmp/oak-exp3
```

| 단계 | `get` | 파일에 바이트가 남아 있나 |
|---|---|---|
| put 후 | 있음 | 있음 |
| delete 후 | 없음 | **있음** |
| 작은 put 20번 후 (정리 안 일어남) | 없음 | **있음** |
| 정리(compact)가 필요한 큰 put 후 | 없음 | 없음 |

## 관찰

- **지운 값은 파일에 그대로 남는다.** 삭제는 목차(슬롯)에서 항목을 지울 뿐, 셀 내용은 건드리지 않는다. 책 목차에서 한 줄을 지워도 그 쪽의 글자는 남아 있는 것과 같다.
- 남은 바이트는 **정리가 일어날 때만** 사라진다. 정리할 때 살아 있는 셀을 끝으로 당겨 붙이고 남은 빈칸을 0으로 채우기 때문이다. 그런데 정리는 새 셀이 가운데 빈칸에 안 들어갈 때만 일어난다. 그래서 쓰기가 적은 DB에서는 **언제까지고 남을 수 있다.**
- 첫 시도는 큰 put이 3400바이트라 정리 없이 빈칸에 들어갔고, 바이트도 남아 있었다. "정리하면 사라진다"를 보이려면 빈칸(3504바이트)보다 큰 값이 필요했다. 실험 도구에 이 계산을 주석으로 남겼다.

## 의미

- 일반적인 저장 엔진 대부분이 이렇게 동작한다. SQLite도 기본적으로 지운 내용을 바로 덮지 않으며, 덮으려면 `PRAGMA secure_delete`를 켠다.
- 앞으로 WAL(ADR 0007)이 들어오면 커밋마다 페이지 전체 사본이 로그에 남는다. 그러면 페이지에서 0으로 덮더라도 **WAL의 예전 사본에 값이 남는다.** 따라서 "지운 값이 디스크에서 사라진다"를 약속하려면 페이지와 WAL을 함께 설계해야 한다.
- 지금 할 수 있는 가장 싼 방법은 삭제할 때 셀 바이트를 0으로 채우는 것이다(셀 하나 크기의 `memset`). 할지 말지는 PR의 "판단할 것"으로 올렸다.
