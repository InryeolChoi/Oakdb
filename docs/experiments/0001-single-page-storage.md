# 0001. 한 장짜리 저장: 장애 실험

이슈 #13의 검증 기록이다. 단위·통합 테스트(32개, CI에서 macOS와 Linux 모두 실행) 말고, 실제 프로세스를 죽이고 실제 파일을 망가뜨려서 엔진이 어떻게 반응하는지 봤다.

- 환경: macOS (Apple silicon), APFS, release 빌드. 이 두 실험은 macOS에서만 돌렸다. 정전 실험은 가짜 파일시스템(#20)으로 옮겨 CI에서 두 OS 모두 돌릴 계획이다.
- 도구: `crates/oakdb/examples/commit_loop.rs`
  - `write <dir>`: 키 i = 값 i(u32)를 트랜잭션 하나에 하나씩 커밋하고, 커밋이 `Ok`를 돌려줄 때마다 i를 출력한다. 페이지가 차면 멈춘다.
  - `check <dir> <last>`: 0..=last가 모두 맞는 값으로 있는지 확인한다.

## 실험 1: 커밋 도중 프로세스 강제 종료 (SIGKILL)

**질문**: 커밋이 `Ok`를 돌려준 데이터는 프로세스가 갑자기 죽어도 남는가?

```sh
commit_loop write $DIR > acked.txt & pid=$!
sleep $T; kill -9 $pid
commit_loop check $DIR $(tail -n1 acked.txt)
```

| 죽인 시점 | 응답받은 커밋 | 다시 열어서 있는 키 | 결과 |
|---|---|---|---|
| 5ms | 0 | 1 | 통과 |
| 10ms | 1 | 2 | 통과 |
| 20ms | 2 | 3 | 통과 |
| 30ms | 16 | 17 | 통과 |
| 50ms | 15 | 16 | 통과 |
| 80ms | 27 | 28 | 통과 |
| 100ms | 34 | 35 | 통과 |
| 150ms | 50 | 51 | 통과 |
| 200ms | 65 | 66 | 통과 |
| 300ms | 87 | 88 | 통과 |

**관찰**

- 응답받은 커밋은 모두 남았다.
- 거의 매번 **응답받은 것보다 키가 하나 더 있다.** 커밋이 디스크 기록까지 마쳤지만, 프로세스가 "됐다"고 출력하기 전에 죽은 경우다. 이것은 허용된다. 약속은 "응답한 커밋은 남는다"이지 "응답하지 않은 커밋은 없다"가 아니다. 네트워크 서버(#12)에서도 똑같이, 클라이언트는 응답을 못 받은 커밋을 "결과를 알 수 없음"으로 다뤄야 한다.
- **한계**: SIGKILL은 프로세스만 죽인다. 운영체제의 페이지 캐시는 살아 있으므로, sync를 빼먹은 버그가 있어도 이 실험은 통과한다. 정전(캐시까지 날아감)은 가짜 파일시스템(#20)으로 실험한다.

**덤으로 본 숫자**: 페이지가 찰 때까지 커밋 253번에 약 1.03초, **커밋 한 번에 약 4ms**였다. 거의 전부 macOS `F_FULLFSYNC`(드라이브 캐시까지 비우기) 시간이다. 커밋마다 디스크 기록을 한 번씩 하면 초당 250번 정도가 한계라는 뜻이고, 여러 커밋을 묶어 한 번에 기록하는 그룹 커밋(ADR 0007)이 왜 필요한지 보여 준다. 이번 이슈는 따로 `docs/benchmarks/` 기록을 남기지 않았다. 비교할 대상(그룹 커밋, SQLite)이 아직 없어서, 숫자 하나로는 결론을 낼 수 없기 때문이다. 정식 측정은 그룹 커밋 벤치마크에서 한다.

## 실험 2: 데이터 파일의 바이트 하나 뒤집기

**질문**: 디스크에서 바이트가 망가지면 엔진이 알아차리는가?

페이지가 꽉 찬 DB(키 253개)를 복사해, 한 곳의 바이트를 `xor 0xFF`로 뒤집고 다시 열었다.

| 위치 | 결과 |
|---|---|
| 메타 `magic` (offset 4) | `Corrupt("not an Oakdb data file")` |
| 메타 `page_size` (offset 16) | `PageSizeMismatch { expected: 4096, found: 4351 }` |
| 리프 `kind` | `Corrupt("page is not a leaf page")` |
| 리프 `cell_count` | `Corrupt("page header is inconsistent")` |
| 리프 첫 슬롯의 offset | `Corrupt("cell length does not match its slot")` |
| 리프 `checksum` 자리 | **알아차리지 못함** (아직 쓰지 않는 필드) |
| 값의 마지막 바이트 | **틀린 값을 그대로 돌려줌** (키 0의 값이 바뀜) |

**관찰**

- 구조를 이루는 바이트(머리, 슬롯)가 망가지면 읽을 때 하는 검사가 잡는다. 덕분에 깨진 페이지 때문에 엉뚱한 메모리를 읽지는 않는다.
- **값 바이트가 망가지면 조용히 틀린 데이터를 돌려준다.** 구조 검사는 "말이 되는가"만 볼 뿐, "원래 그 내용인가"는 모른다. 스펙의 사용자 스토리 18-1("손상된 페이지를 읽으면 오류")을 지키려면 체크섬(#19)이 꼭 필요하다는 것을 직접 확인했다.
- `page_size` 바이트가 망가지면 "손상"이 아니라 "페이지 크기가 다르다"로 보고된다. 체크섬을 넣어도 페이지 크기는 체크섬보다 먼저 읽어야 하므로(체크섬 범위가 페이지 크기에 달려 있다), #19에서도 이 경우는 그대로일 것이다. 메타 슬롯 두 개 중 다른 슬롯과 비교하는 방법을 #19 설계 때 검토한다.

## 코드 리뷰에서 찾은 것

표준·스펙 두 방향으로 코드 리뷰를 했고, 실험 2와 같은 종류의 버그가 하나 나왔다. 페이지 머리의 `frag_bytes`가 망가져 0xFFFF 근처가 되면, 읽을 때는 통과하고 그 뒤 같은 키를 덮어쓸 때 u16이 넘쳐 **엔진이 패닉**했다. 손상된 디스크 데이터로 패닉이 나면 안 되므로, 읽을 때 "셀 영역 바이트 = 살아 있는 셀 + `frag_bytes`"가 정확히 맞는지 확인하게 고쳤다. 쓰지 않는 머리 필드(`reserved`, 리프의 `rightmost_child`)가 0인지도 함께 본다. 둘 다 `inconsistent_pages_are_refused` 테스트에 더했다.
