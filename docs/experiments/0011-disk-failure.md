# 0011. 전원이 켜진 채 디스크가 실패할 때

이슈 #24의 검증 기록이다. 가짜 디스크(`SimFs`)에 "디스크를 바꾸는 호출 n번 뒤 **한 번만** 실패"(`fail_once_after`)를 더하고, 커밋·정리·열기의 **모든 디스크 연산**에서 한 번씩 실패시켰다. 실패 뒤 엔진이 멈추는지, 다시 열면 약속을 지키는지 본다. 정전 실험(0010)이 그대로 통과하는지도 다시 돌렸다.

- 환경: Apple M3 (Mac15,13), macOS 27.0.1, APFS, 내장 SSD. 실험은 가짜 디스크라 OS와 무관하고, 테스트는 CI에서 macOS·Linux 둘 다 돈다
- 도구: `crates/oakdb/tests/disk_failure.rs`, `crash_sim` 예제(바꾸지 않음), `docs/experiments/scripts/mutants.py failure` (새 버그 목록)

```sh
cargo test --test disk_failure --test sim_fs --test checkpoint
cargo run --release --example crash_sim -- sweep 0 100000
cargo run --release --example crash_sim -- every 7 8     # 11, 23, 42, 99도
python3 docs/experiments/scripts/mutants.py failure      # checkpoint, wal도
python3 docs/experiments/scripts/ab_versions.py b4ce9e1 <rev> 10 200
```

## 1. 어디서 실패해도 약속을 지키나

**약속**: 실패를 만난 호출은 정해진 오류를 받는다(커밋 `OutcomeUnknown`, 정리·열기 `Io`). 그 뒤 모든 요청(`get`·`put`·`delete`·`scan`·빈 커밋·`checkpoint`)은 `Stopped`. `Db`를 버리고 다시 열면 응답한 커밋은 모두 있고, 실패한 커밋은 통째로 있거나 통째로 없다. 그 뒤에도 커밋·정전·다시 열기가 된다.

다시 열기는 실패 지점마다 다섯 번: **정전 없이** 바로, 그리고 **정전 시드 0~3**으로 정전시킨 뒤.

| 어디서 | 실패시킨 연산 | 다시 열기 | 약속 깨짐 |
|---|---|---|---|
| 커밋 (값 4개, 그중 5,000바이트 3개) | WAL 쓰기·sync **2개 전부** | 2 × 5 = 10 | **0** |
| 직접 부른 정리, 첫 회 (슬롯 두 장) | 전부 | 연산 수 × 5 | **0** |
| 직접 부른 정리, 세 번째 (슬롯 한 장) | 전부 | 연산 수 × 5 | **0** |
| 정리까지 하는 커밋 (1.6MB 값 셋째) | WAL 쓰기·sync, 정리의 앞 2개·가운데·끝 5개 | 9 × 5 = 45 | **0** |
| 열기: 새 DB 만들기 | 전부 | 연산 수 × 5 | **0** |
| 열기: 꼬리 자르기(`.cut` 파일 포함) | 전부 | 연산 수 × 5 | **0** |
| 열기: 옛 회차 WAL 새로 쓰기 | 전부 | 연산 수 × 5 | **0** |

- **커밋은 디스크 연산이 두 개뿐이다**(WAL 쓰기 한 번, sync 한 번, 설계 0010). 쓰기가 실패하면 아무것도 안 닿고, sync가 실패하면 바이트는 캐시에 있어서 정전 없이 다시 열면 **있고**, 정전 뒤에는 시드에 따라 있거나 없다. 테스트는 "있음"과 "없음"이 **둘 다** 나오는지도 확인한다. 결과를 알 수 없다는 말이 실제로 그렇다는 뜻이다.
- **정리까지 하는 커밋**: WAL 쓰기·sync에서 실패하면 `OutcomeUnknown`, 정리에서 실패하면 **`Ok`**(결정 4). 다시 열면 그 커밋은 언제나 있다.
- 정리 연산 전체를 훑지 않은 이유: 1.6MB 값 셋이면 정리가 페이지 1,000여 개를 쓴다. 정리 자체의 모든 연산은 바로 위 "직접 부른 정리" 두 줄이 훑는다.

### 가설 판정

| 가설 (설계 때 적은 것) | 판정 | 근거 |
|---|---|---|
| 실패 뒤 재시도하지 않아도 다시 열면 응답한 커밋은 모두 있다 | **채택** | 위 표 모든 줄 깨짐 0 |
| 실패한 커밋은 다시 열면 통째로 있거나 통째로 없다 | **채택** | 커밋 훑기에서 둘 다 나옴, 반쪽 0 |
| 멈춘 엔진은 디스크에 아무것도 쓰지 않는다 | **채택** | 변이 F5(잠금 뒤 확인 빼기)를 `every_request_after_a_failure_…`가 잡음 |
| 열기 도중 실패는 다시 열면 그만이다 | **채택** | 열기 세 경우 모두 깨짐 0 |

## 2. 정전 실험 (0010과 같은 도구, 바꾸지 않음)

| 결과 | 0010 | 0011 |
|---|---|---|
| 시드 0~99,999 약속 지킴 | 100% | **100,000 / 100,000** |

| 작업 시드 | 정전 시점 | 하나라도 깨지는 시점 |
|---|---|---|
| 7 | 179 | **0** |
| 11 | 16 | **0** |
| 23 | 87 | **0** |
| 42 | 94 | **0** |
| 99 | 172 | **0** |

정전 뒤의 요청이 이제 `Stopped`를 받는다. 도구는 "전원이 끊긴 뒤 실패했나"(`fs.ops() == cut_after`)만 보므로 그대로 맞다. 정전 실험에 "한 번 실패"를 섞지는 않았다. 도구가 "전원이 켜진 채 실패하면 버그"로 판정하는 구조라, 섞으면 판정 규칙을 둘로 나눠야 한다. 대신 위 1절의 전용 테스트가 모든 시점을 훑는다.

## 5. 이 실험이 못 보는 것

| 무엇 | 왜 못 보나 | 어디로 |
|---|---|---|
| Linux에서 sync가 실패한 페이지가 캐시에 "깨끗함"으로 남는 경우 (같은 부팅에서 다시 열면 디스크에 없는 바이트를 읽음) | 가짜 디스크의 sync 실패는 변경을 "계속 기다림"으로 둔다. 나중 sync가 그것을 굳혀 준다 | 설계 0012 결정 7, 별도 티켓 제안 |
| 실패한 쓰기가 앞부분만 남김(짧은 쓰기) | 가짜 디스크의 실패한 쓰기는 아무것도 남기지 않는다 | 엔진에게는 "쓰기 실패 + 찢긴 꼬리"와 같고, 찢긴 꼬리는 정전 실험이 덮는다 |
| 여러 스레드가 동시에 커밋하다 실패 | 테스트가 한 스레드다. 잠금 뒤 확인(변이 F5)은 "실패 전에 시작한 트랜잭션"으로 잡았다 | 커밋 스레드(#27), 그룹 커밋(#28) |
