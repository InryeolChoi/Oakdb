# 0005. 범위 조회 — 설계

이슈 #17. 트랜잭션 안에서 키 범위를 정렬된 순서로 읽는다. "d부터 h 전까지"처럼 읽는 기능이다. 나중에 SQL의 `WHERE id BETWEEN ...`이 이 위에서 돈다.

```rust
let txn = db.begin();
for item in txn.scan("d".."h") {
    let (key, value) = item?;
    // d, f 순서로 나온다
}
```

## 사용자가 정한 것

| # | 질문 | 결정 |
|---|---|---|
| 1 | 결과를 어떻게 돌려줄까 | **하나씩 꺼내는 `Iterator`**. 조회를 시작한 순간의 트리를 붙잡고 읽는다 |
| 2 | 항목 하나의 타입 | **`Result<(키, 값)>`**. 지금은 늘 `Ok`이지만, 페이지를 디스크에서 그때그때 읽게 되면 실패할 수 있다 |

표준을 그대로 따른 것:

- 범위는 Rust 표준 범위 문법(`RangeBounds`)으로 받는다. Java의 `NavigableMap.subMap(from, fromInclusive, to, toInclusive)`와 같은 일을 한다.
- 트랜잭션이 아직 커밋하지 않은 자기 쓰기도 결과에 섞여 나온다. 스펙 #12의 스토리 8("내 쓰기는 내가 본다")과 `get`의 규칙을 따랐다.

## 1. 범위를 적는 법

| 쓰는 법 | 뜻 |
|---|---|
| `txn.scan("d".."h")` | d 이상, h 미만 |
| `txn.scan("d"..="h")` | d 이상, h 이하 |
| `txn.scan("d"..)` | d 이상 끝까지 |
| `txn.scan(.."h")` | 처음부터 h 미만 |
| `txn.scan::<&[u8]>(..)` | 전부 |
| `txn.scan::<&str>((Excluded("d"), Included("h")))` | d 초과, h 이하 |

- 키 타입은 `AsRef<[u8]>`이면 무엇이든 된다(`&str`, `&[u8]`, `Vec<u8>`, `[u8; 4]`).
- **타입을 직접 적어야 하는 경우가 있다.** `..`처럼 키가 없는 범위나 `(Bound, Bound)` 튜플은 Rust가 키 타입을 하나로 정하지 못한다. 튜플 `(Bound<&str>, Bound<&str>)`는 "`&str`의 범위"로도 "`str`의 범위"로도 읽힌다. 그래서 `scan::<&str>`처럼 적어 준다.
- **시작이 끝보다 뒤인 범위는 비어 있다.** 오류도 panic도 아니다. `BTreeMap::range`는 이런 범위에서 panic하므로, 넘기기 전에 빈 범위로 바꾼다.
- 범위 끝의 키 길이는 검사하지 않는다. 저장하지 않고 비교에만 쓰기 때문이다.

## 2. 트리에서 읽기: 커서

```
           [루트]
          /      \
    [b d] → [f h] → [m p]       ← 리프끼리 옆 포인터로 이어짐
       ↑
   seek("c"): 리프를 찾고 "c 이상인 첫 칸"에 선다
   next: 칸을 하나씩 읽다가, 리프 끝에 닿으면 옆 리프로 넘어간다
```

- `Tree::seek(시작)`: 시작 키가 들어갈 리프로 내려가서, 그 리프 안의 첫 칸 번호를 찾는다(`Page::start_index`). 시작이 열려 있으면 가장 왼쪽 리프의 0번 칸이다.
- `Tree::next_entry(커서)`: 커서 칸의 항목을 돌려주고 한 칸 옮긴다. 리프 끝이면 옆 포인터를 따라간다. 마지막 리프 끝이면 `None`이다.
- 시작 키가 리프의 마지막 키보다 크면 커서는 리프 끝에 선다. 첫 `next`에서 옆 리프로 넘어가므로 따로 처리하지 않는다.
- 04번에서 빈 리프를 뺄 때 옆 포인터를 이어 두었기 때문에, 빈 리프를 만나는 일은 없다. 루트 하나뿐인 빈 트리만 예외인데, 그때는 바로 `None`이다.

**옆 포인터를 쓰는 이유.** 리프 하나를 다 읽을 때마다 루트에서 다시 내려가도 된다. 하지만 옆 포인터를 따라가면 다음 리프까지 한 걸음이다. B⁺-tree가 리프를 사슬로 잇는 이유가 바로 이것이다.

## 3. 내 쓰기와 합치기

트랜잭션의 쓰기는 커밋 전까지 `writes`(키 순서의 `BTreeMap`)에만 있다. 그래서 `Scan`은 정렬된 흐름 두 개를 **합치기(merge)** 한다. 합병 정렬의 합치는 단계와 같다.

| 다음 키 비교 | 하는 일 |
|---|---|
| 트리 쪽이 작음 | 트리 항목을 내보낸다 |
| 쓰기 쪽이 작음 | put이면 내보내고, delete면 건너뛴다 |
| 같음 | 쓰기가 이긴다. 트리 항목은 버린다 |

트리 쪽은 항목 하나를 미리 읽어 둔다(`committed`). 범위 끝을 넘으면 더 읽지 않는다.

## 4. 조회 중에 다른 커밋이 오면 (결정 1)

`Db`는 이제 트리를 `Mutex<Arc<Tree>>`로 들고 있다.

- **커밋**은 트리를 복제해 고친 다음, `Arc`를 **새 트리로 통째로 바꿔 끼운다.** 전에는 잠금 안의 트리를 덮어썼다.
- **조회**는 시작할 때 `Arc`를 하나 복제해서 가진다. 참조 수만 하나 느는 O(1) 작업이다. 그다음에는 잠금 없이 읽는다.
- 조회 중에 커밋이 와도, 조회는 옛 트리를 계속 읽는다. 옛 트리는 마지막 조회가 끝날 때 사라진다.

Java로 치면 `volatile` 참조를 새 불변 객체로 바꿔 끼우는 copy-on-write 리스트와 같다. 03번부터 페이지를 `Arc`로 나눠 가진 덕분에, 트리 복제도 바뀐 페이지만 복사한다.

**이것은 아직 스냅샷 격리가 아니다.** 스펙은 "트랜잭션이 **시작한 순간**의 스냅샷"을 읽으라고 한다. 지금은 `get`과 `scan`이 **부를 때마다** 그 순간의 최신 트리를 본다. 같은 트랜잭션 안의 `get` 두 번이 다른 값을 볼 수 있다. 스냅샷 티켓에서 `begin`이 `Arc`를 한 번 잡아 두면, 이번에 만든 구조가 그대로 스냅샷이 된다.

**대가.** `get`이 포인터를 한 단계 더 따라가게 됐다. 리프 한 장짜리 `get/hit`가 약 2ns(2.6%) 느려졌다(벤치마크 0005).

## 6. 이번에 하지 않은 것

- 거꾸로 읽기(큰 키부터): 리프에 왼쪽 포인터가 없다. SQL의 `ORDER BY ... DESC`가 필요해지면 다시 본다.
- 트랜잭션 시작 시점의 스냅샷: 스냅샷 티켓
- 조회 중 디스크 읽기 실패(`Err` 항목): 페이지 캐시가 들어올 때
