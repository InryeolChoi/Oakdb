# 0007. 페이지 체크섬 — 설계

이슈 #19. 모든 페이지에 **지문**을 넣는다. 장부 한 장마다 맨 위에 "이 장의 지문"을 적어 두고, 다시 펼쳤을 때 지문이 안 맞으면 누가 고쳤거나 물에 번진 것으로 본다. 지문에는 **페이지 번호도 섞는다.** 그래서 37쪽 내용이 52쪽 자리에 잘못 꽂혀 있어도 알아챈다.

지금까지 페이지 머리 0~4바이트는 "체크섬 자리, 지금은 0"이었다. 실험 0001은 값 바이트 하나를 바꿔도 아무도 모른다는 것을 보였다. 06번이 부록 페이지를 더하면서 그런 자리가 더 늘었다(실험 0006의 4번).

## 이미 정해진 것 (ADR 0008, research 0005 4절)

| 항목 | 내용 |
|---|---|
| 알고리즘 | CRC-32C (Castagnoli). InnoDB의 `crc32`, PostgreSQL WAL과 같다. Apple silicon과 x86-64 모두 CPU 명령이 있다 |
| 범위 | 페이지의 4~4096바이트, 그다음 페이지 번호(u64, 리틀 엔디언) |
| 틀리면 | **무조건 오류.** 0이면 건너뛰는 식의 예외가 없다 |
| 할 수 있는 것 | **알아채기만.** 고치는 일은 WAL(#22)의 페이지 사본이 맡는다 |

## 사용자가 정한 것

| # | 질문 | 결정 |
|---|---|---|
| 1 | CRC-32C 계산 코드 | **검증된 crate `crc32c`**. CPU 가속과 예비 경로가 있다. 의존성이 `libc`에 하나 는다 |
| 2 | 메타 페이지 | **체크섬을 넣고, 틀리면 거절만.** 메타 A가 틀렸을 때 B로 넘어가는 규칙은 두 장을 번갈아 쓰는 #23에서 |
| 3 | 오류 종류 | **기존 `Error::Corrupt`**, 메시지에 페이지 번호 (`page 9 has a wrong checksum`) |
| 4 | 버전 2 파일 | **형식 버전 3으로 올리고 2는 거절.** "0이면 검사 안 함" 예외를 두지 않는다 |

## 1. 지문 만들기

```text
checksum = CRC-32C( 페이지[4..4096] ‖ page_no를 8바이트 리틀 엔디언으로 )
페이지[0..4] = checksum (리틀 엔디언)
```

- 체크섬 자리(0~4)는 계산에서 뺀다. 자기 자신을 포함하면 계산할 수 없기 때문이다.
- 페이지 번호는 페이지 안에 따로 적지 않는다. 읽는 쪽은 어느 자리를 읽는지 이미 알기 때문에, 그 번호를 섞어 계산해 보면 된다.
- 모든 코드는 `checksum.rs` 한 곳에 있다. `sealed(page_no, bytes)`는 체크섬을 채운 사본을 돌려주고, `verify(page_no, bytes)`는 틀리면 `Corrupt`를 낸다.

## 2. 언제 계산하고 언제 검사하나

| 때 | 하는 일 |
|---|---|
| 파일에 쓸 때 (새 DB, 커밋, 메타) | `write_page`가 4KB 사본을 만들어 체크섬을 채운 뒤 쓴다 |
| 파일에서 읽을 때 (열기) | `read_page`가 체크섬부터 확인한 다음 `Page::from_bytes`에 넘긴다 |
| 메모리 안 | 체크섬 자리는 아무 뜻이 없다. 메모리에서 만든 페이지는 0, 파일에서 읽은 페이지는 읽은 값을 그대로 갖는다. 쓸 때마다 새로 채우므로 고칠 때마다 다시 계산하지 않는다 |

- 메모리의 페이지는 여러 트리가 `Arc`로 나눠 갖고 있어서 직접 고칠 수 없다. 그래서 쓸 때마다 사본을 만든다. 4KB 복사와 CRC 계산은 디스크 sync(약 3ms)에 비하면 아주 작다. 벤치마크 0007에서 잰다.
- 파일을 늘릴 때 생기는 새 페이지, 빈 페이지, 부록 페이지도 모두 같은 `write_page`를 지나간다. 체크섬 없이 파일에 들어가는 페이지가 없다.
- 지금은 열 때 모든 페이지를 읽으므로, 열 때 모든 체크섬을 검사한다. 페이지 캐시가 들어와 그때그때 읽게 되면 그때마다 검사한다.

## 3. 메타 페이지를 읽는 순서

체크섬은 "페이지 전체"로 계산하는데, 페이지 크기를 모르면 어디까지가 페이지인지 모른다. 또 버전 2 파일에는 체크섬이 없어서, 체크섬부터 보면 "체크섬이 틀림"이라는 엉뚱한 오류가 난다. 그래서 순서를 이렇게 했다.

1. 파일 맨 앞 52바이트만 읽어 **magic → 페이지 크기 → 형식 버전**을 확인한다 (`Meta::check_header`).
2. 메타 페이지 한 장을 다 읽고 **체크섬**을 확인한다.
3. 루트, 페이지 수, 빈 페이지 목록을 읽는다 (`Meta::decode`).

버전 2 파일은 1단계에서 `unknown format version 2`로 거절된다.

**대가 (리뷰에서 결정).** 메타 A의 형식 자리(magic, 페이지 크기, 버전)가 망가지면, 체크섬보다 1단계가 먼저 걸린다. 그래서 오류가 `page 0 has a wrong checksum`이 아니라 `not an Oakdb data file`이나 `unknown format version 7`로 나온다. 손상된 Oakdb 파일인지 아예 다른 파일인지 메시지만으로는 구분되지 않는다. 형식 자리가 틀릴 때 체크섬도 계산해 "손상으로 보임"을 덧붙이는 방법도 있지만, 그러면 페이지 크기가 다른 정상 파일까지 손상이라고 잘못 말할 수 있어서 두지 않았다. 어느 쪽이든 **열기를 거부한다는 점은 같다.**

## 4. 메타 슬롯 B

메타는 지금도 A(페이지 0)와 B(페이지 1)에 같은 내용으로 쓴다. 각자 자기 페이지 번호로 체크섬을 넣는다. 다만 **열 때는 A만 읽는다.** B가 망가져도 지금은 알아채지 못한다(실험 0006의 7번). A가 망가졌을 때 B로 넘어가는 규칙과 B 검사는 #23에서 함께 만든다(결정 2).

## 6. 이번에 하지 않은 것

- 메타 B 읽기와 B로 넘어가기: #23
- 망가진 페이지 고치기: WAL(#22). 체크섬은 알아채기만 한다
- 메모리의 페이지 다시 검사하기: 메모리 손상은 이 엔진이 다루는 범위 밖이다
- 체크섬을 끄는 옵션: PostgreSQL과 달리 끌 수 없다. 끌 이유가 될 만큼 비싸지 않다는 것을 벤치마크 0007로 보인다
