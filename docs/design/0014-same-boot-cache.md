# 0014. 같은 부팅에서 다시 열 때의 캐시 구멍 — 설계

이슈 #59. #24(디스크 기록 실패 처리) 리뷰에서 남긴 구멍이다(설계 0012 결정 7, 리뷰 P1). Linux에서 sync가 실패한 페이지는 OS 캐시에 "깨끗함"으로 남는다. 엔진은 멈추지만, **같은 부팅에서** 다시 열면 디스크에 없는 바이트를 캐시에서 읽고 그 뒤에 새 커밋을 붙인다. 그 뒤 정전이 나면 다시 연 뒤 응답한 커밋까지 잃는다.

**비유**: 캐시는 책상 위 메모지, 디스크는 금고다. sync는 "메모지 내용을 금고에 넣어"라는 명령이다. Linux는 sync가 실패해도 메모지에 "금고에 넣었음" 도장을 찍어 버린다. 그래서 다음 sync는 그 메모를 다시 넣으려 하지 않는다. 같은 부팅에서 다시 열면 엔진은 메모지를 읽고 금고에도 있다고 믿는다. 이번 티켓의 대책은 **메모지에서 믿은 것을 금고에 한 번 더 넣고 확인하는 것**이다. 같은 내용이라도 **다시 쓰면** 도장이 지워져 다음 sync가 진짜로 넣는다.

```
커밋 k2의 sync 실패 (Linux)
  캐시: [머리말][k1][k2]      ← 읽기는 이걸 본다
  금고: [머리말][k1]          ← k2는 영영 안 감, 그런데 "깨끗함"
같은 부팅에서 다시 열고 k3 커밋 (응답함)
  캐시: [머리말][k1][k2][k3]
  금고: [머리말][k1][ 0 ][k3] ← k3만 sync됨
정전 뒤 열기: k1 뒤에서 사슬이 끊김 → 응답한 k3를 잃음
```

## 정한 것

| # | 질문 | 결정 | 상태 |
|---|---|---|---|
| 1 | 가짜 디스크가 이 고장을 어떻게 흉내 내나 | **Linux식 실패를 하나 더 둔다.** `SimFs::set_failed_sync(FailedSync::Forgets)`: sync가 실패하면 기다리던 변경을 잊는다. 읽기에는 보이지만 나중 sync도 정전도 그것을 디스크에 주지 않는다. 같은 바이트를 **다시 쓸 때만** 디스크에 간다. 지금 방식(`KeepsWaiting`)이 기본이고, #24의 실패 테스트는 두 방식 모두 돌린다 | 사용자 결정 (추천안) |
| 2 | 엔진은 어떻게 막나 | **열 때 읽은 것을 다시 쓰고 sync한다**: 고른 메타 슬롯을 다시 쓰고 sync, 그다음 WAL을 마지막 온전한 커밋까지 통째로 다시 쓰고 꼬리를 잘라 sync. WAL을 새로 시작할 때는 읽기가 "비었다"고 해도 언제나 비우고 sync한다. 처음 추천한 "열 때 정리(B+)"는 2절의 이유로 바꿨다 | **사용자 확인 필요** (처음 결정은 B+) |
| 3 | 언제 하나 | **언제나.** 정전 뒤인지 같은 부팅인지 엔진은 구별할 수 없다 | 사용자 결정 (추천안) |

## 1. 가짜 디스크의 새 실패

| | `KeepsWaiting` (기본, #24) | `Forgets` (새로, Linux) |
|---|---|---|
| 실패한 sync 뒤 읽기 | 새 내용 | 새 내용 |
| 실패한 sync가 저장하려던 변경 | 계속 기다림: 다음 sync가 저장하거나 정전이 정함 | **잊음**: 다음 sync도, 정전도 디스크에 주지 않음 |
| 같은 바이트를 다시 쓰면 | 저장됨 | 저장됨 (새 변경이라서) |
| 실패한 쓰기·길이 바꾸기 | 아무것도 안 바꿈 | 같음. 잊는 것은 sync 실패뿐 |
| 정전을 넘어서 | — | 설정은 남는다 (OS의 성질) |

이걸 위해 sync는 이제 "읽기가 보는 내용"을 디스크로 베끼지 않고, **기다리던 변경을 디스크 내용 위에 순서대로 적용한다.** 둘은 잊힌 변경이 있을 때만 다르다.

**모델이 실제보다 험한 곳**: Linux는 4 KiB 페이지 단위로 "깨끗함"을 찍는다. 같은 페이지의 **다른 바이트**를 나중에 쓰면 페이지 전체가 다시 더러워져 잊힌 바이트도 함께 간다. 가짜 디스크는 바이트 단위라 그런 행운이 없다. 엔진이 그 행운에 기대지 않는지 보는 데는 이쪽이 낫다.

**모델 밖**: 디렉터리 sync 실패(파일 항목은 계속 "sync 안 됨"으로 남음), 짧은 쓰기·ENOSPC(설계 0012 1절과 같이 논증만).

## 2. 대책: 왜 "정리"가 아니라 "다시 쓰기"인가

처음 추천한 B+는 "열 때 정리(체크포인트)를 한 번 하고 메타 슬롯도 다시 쓴다"였다. 구현 전에 순서를 따져 보니 구멍이 있었다.

| 정리의 단계 | 그때 금고(디스크)의 상태 |
|---|---|
| 1. WAL의 페이지를 데이터 파일 제자리에 씀 → sync | 데이터 파일: 캐시에서 읽은 **최신** 페이지. 금고 속 WAL: 실패한 커밋 앞에서 끊김. 메타 슬롯: 옛 체크포인트 |
| (여기서 정전) | 열기는 옛 메타 + 끊긴 WAL을 재생한다. WAL에 이미지가 없는 페이지는 데이터 파일에서 읽는데, 그 페이지는 **실패한 커밋의 내용**으로 덮였다. 응답한 트리와 실패한 커밋의 페이지가 섞인다 |

평소 정리가 안전한 것은 "금고 속 WAL이 온전하다"는 전제 덕분이다(설계 0011). 같은 부팅에서 다시 열 때는 그 전제가 깨져 있다. 그래서 정리보다 먼저 WAL을 금고에 굳혀야 하는데, **WAL을 굳히고 나면 정리가 할 일이 없다.** WAL과 메타가 금고에 있으면 그 위에 붙는 커밋은 평소처럼 안전하다.

| 선택지 | 막는 것 | 비용 (열 때) | 결과 |
|---|---|---|---|
| B+. 열 때 정리 + 메타 다시 쓰기 | 정리 도중 정전이 없으면 전부 | 페이지 쓰기 + sync 4번 | **실제로 깨짐**: 변이 K6(열 때 정리)에서 잊힌 커밋이 있는 DB를 열다 정리의 6번째 연산에서 정전 → 다시 열기가 `overflow page does not hold its share of the value`로 거부 (실험 0013) |
| **다시 쓰기 (택함)** | 전부 | 메타 1쪽 쓰기 + sync, WAL 통째 쓰기(최대 약 4 MiB) + sync | 3절 |
| C. 캐시를 거치지 않고 읽기 | 전부 | OS별 코드, 정렬 제약 | 변경이 큼 |

## 3. 열기의 새 순서

```
읽기 (바꾸는 것 없음): WAL 재생, 메타 슬롯 고르기, 트리 읽기
1. 고른 메타 슬롯을 제자리에 다시 씀 → sync         (없으면 건너뜀)
2-a. WAL을 재생할 때: 잘린 꼬리는 .cut 파일에 보관
     WAL을 마지막 온전한 커밋까지 다시 씀 + 꼬리 자름 → sync
2-b. WAL을 새로 시작할 때: 비움 → sync, 머리말 → sync (언제나 비움)
3. 새 DB면 첫 커밋, 디렉터리 sync
```

| 같은 부팅의 경우 (설계 0012 7절 표) | 지금은 |
|---|---|
| 커밋의 WAL sync 실패 뒤 다시 열기 | 2-a가 실패한 커밋까지 다시 써서 굳힌다. 실패한 커밋은 "결과 모름"이라 남아도 된다 |
| 정리 도중 페이지 sync 실패 | 그 페이지들은 WAL에 있다. 2-a가 WAL을 굳히고, 다음 정리가 페이지를 다시 쓴다 |
| 정리 도중 메타 슬롯 sync 실패 | 열기는 캐시의 새 슬롯을 고르고 WAL을 새로 시작한다. 1이 그 슬롯을 먼저 굳혀서, 새 WAL 머리말이 금고 속 슬롯보다 앞서는 일(→ Corrupt)이 없다 |
| 정리 도중 WAL 비우기 sync 실패 | 읽기는 빈 WAL을 본다. 2-b가 "비었다"는 말을 믿지 않고 다시 비운다 |
| 새 DB 첫 커밋 실패 | 캐시의 첫 커밋을 읽고 "있는 DB"로 연다. 2-a가 굳힌다 |
| 꼬리 자르기 실패 | 2-a가 WAL을 다시 쓰고 다시 자른다 |
| `.cut` 파일 sync 실패 | 조사용 파일이라 그대로 (데이터에 영향 없음) |

**1이 2보다 먼저인 이유**: 2-b는 머리말에 고른 슬롯의 체크포인트 번호를 쓴다. 금고에 그 슬롯이 없는데 머리말이 먼저 닿으면 열기가 "WAL이 모든 슬롯보다 새롭다"며 거부한다(변이 K5).

**2-b의 "언제나 비움"은 방어용이다 (변이 K4, 예상대로 살아남음).** 비우기를 건너뛰어 금고에 옛 WAL이 남아도, 새 머리말 뒤의 옛 기록은 다른 머리말에서 이어진 체크섬 사슬이라 재생이 버린다. 설계 0013의 C3와 같은 논리다. 새 DB를 만들 때만 sync 하나가 늘어 싸다.

**데이터 파일의 다른 페이지**는 다시 쓰지 않는다. WAL에 없는 페이지는 sync가 **성공한** 정리가 쓴 것이다. 정리가 페이지 sync에서 실패했다면 그 페이지는 아직 WAL에 있어 재생이 덮는다.

## 4. 비용

| 열기 | 늘어난 일 |
|---|---|
| 정상 종료 뒤 (`close()`가 정리함, WAL은 머리말뿐) | 메타 1쪽 쓰기 + sync, 머리말 20바이트 다시 쓰기 + sync |
| 정전 뒤 | 위 + WAL 전체 다시 쓰기 (최대 `CHECKPOINT_AFTER` = 4 MiB 남짓) |

열기에만 드는 비용이고 커밋 경로는 그대로다. 성능 주장이 생기므로 다시 열기 시간을 A/B(+ A/A 대조)로 잰다(`ab_versions.py`의 reopen).

## 5. API 변화

| 무엇 | 변화 |
|---|---|
| `SimFs::set_failed_sync`, `FailedSync::{KeepsWaiting, Forgets}` | 새로 (가짜 디스크) |
| `Db::open_with` | 열 때 메타 슬롯과 WAL을 다시 쓰고 sync (공개 동작은 같음, sync가 늘어남) |
| `Wal::cut_to_tail` → `Wal::rewrite` | 안쪽 |
| `checkpoint::write_slot` | 정리와 열기가 함께 쓰는 슬롯 쓰기 |

## 6. 테스트 계획

| 테스트 | 무엇을 |
|---|---|
| `sim_fs.rs` 잊는 sync 네 개 | 읽기는 보임 / 나중 sync가 못 살림 / 다시 쓰면 살림 / 실패한 쓰기는 안 잊음 / 정전 뒤에도 설정 유지 |
| `disk_failure.rs`의 실패 훑기 다섯 개 | 커밋·정리·커밋 뒤 정리·열기 도중의 모든 실패 지점 × (정전 없음, 시드 4개) × **두 방식**. 정전 없음 = 같은 부팅에서 다시 열기 → 커밋 → 정전 → 응답한 것이 다 있나 |
| `a_power_cut_while_reopening_in_the_same_boot_...` | 잊힌 커밋이 있는 DB를 다시 여는 **모든 연산**에서 정전 → 응답한 것을 잃지 않음 |
| 변이 `cache` K1~K10 | 실험 0013 |
