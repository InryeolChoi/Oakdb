# 0014. 같은 부팅에서 다시 열 때의 캐시 구멍 — 설계

이슈 #59. #24(디스크 기록 실패 처리) 리뷰에서 남긴 구멍이다(설계 0012 결정 7, 리뷰 P1). Linux에서 sync가 실패한 페이지는 OS 캐시에 "깨끗함"으로 남는다. 엔진은 멈추지만, **같은 부팅에서** 다시 열면 디스크에 없는 바이트를 캐시에서 읽고 그 뒤에 새 커밋을 붙인다. 그 뒤 정전이 나면 다시 연 뒤 응답한 커밋까지 잃는다.

**비유**: 캐시는 책상 위 메모지, 디스크는 금고다. sync는 "메모지 내용을 금고에 넣어"라는 명령이다. Linux는 sync가 실패해도 메모지에 "금고에 넣었음" 도장을 찍어 버린다. 그래서 다음 sync는 그 메모를 다시 넣으려 하지 않는다. 같은 부팅에서 다시 열면 엔진은 메모지를 읽고 금고에도 있다고 믿는다. 이번 티켓의 대책은 **메모지에서 믿은 것을 금고에 한 번 더 넣고 확인하는 것**이다. 같은 내용이라도 **다시 쓰면** 도장이 지워져 다음 sync가 진짜로 넣는다. 단, 금고 속 장부 위에 덧쓰지 않고 **새 종이에 옮겨 적은 뒤 통째로 바꿔 끼운다.** 덧쓰다 정전이 나면 그 칸이 번진 잉크가 될 수 있어서다.

```
커밋 k2의 sync 실패 (Linux)
  캐시: [머리말][k1][k2]      ← 읽기는 이걸 본다
  금고: [머리말][k1]          ← k2는 영영 안 감, 그런데 "깨끗함"
같은 부팅에서 다시 열고 k3 커밋 (응답함)
  캐시: [머리말][k1][k2][k3]
  금고: [머리말][k1][ 0 ][k3] ← k3만 sync됨
정전 뒤 열기: k1 뒤에서 사슬이 끊김 → 응답한 k3를 잃음
```

## 1. 가짜 디스크의 새 실패

| | `KeepsWaiting` (기본, #24) | `Forgets` (새로, Linux) |
|---|---|---|
| 실패한 sync 뒤 읽기 | 새 내용 | 새 내용 |
| 실패한 sync가 저장하려던 변경 | 계속 기다림: 다음 sync가 저장하거나 정전이 정함 | **잊음**: 다음 sync도, 정전도 디스크에 주지 않음 |
| 같은 바이트를 다시 쓰면 | 저장됨 | 저장됨 (새 변경이라서) |
| 실패한 쓰기·길이 바꾸기 | 아무것도 안 바꿈 | 같음. 잊는 것은 sync 실패뿐 |
| 정전을 넘어서 | — | 설정은 남는다 (OS의 성질) |

이걸 위해 sync는 이제 "읽기가 보는 내용"을 디스크로 베끼지 않고, **기다리던 변경을 디스크 내용 위에 순서대로 적용한다.** 둘은 잊힌 변경이 있을 때만 다르다.

**모델이 실제보다 험한 곳**: Linux는 4 KiB 페이지 단위로 "깨끗함"을 찍는다. 같은 페이지의 **다른 바이트**를 나중에 쓰면 페이지 전체가 다시 더러워져 잊힌 바이트도 함께 간다. 가짜 디스크는 바이트 단위라 그런 행운이 없다. 엔진이 그 행운에 기대지 않는지 보는 데는 이쪽이 낫다.

**모델 밖**: 디렉터리 sync 실패(파일 항목은 계속 "sync 안 됨"으로 남음, 6절), 짧은 쓰기·ENOSPC(설계 0012 1절과 같이 논증만).

### 1-1. 쓰레기 칸과 rename (PR #60 검증 뒤)

| | 무엇 | 왜 |
|---|---|---|
| `TornSector::KeepsOld` (기본) | 찢긴 쓰기가 못 닿은 칸은 옛 바이트 그대로 | 설계 0008의 가정: 디스크는 칸(섹터)을 통째로 쓰거나 안 쓴다 |
| `TornSector::Garbled` | 못 닿은 칸 중 **디스크가 들고 있던 바이트를 덮어쓰던 부분**은 쓰레기(비트 반전)가 된다. 쓰기가 덮지 않은 같은 칸의 나머지는 그대로이고(SQLite의 powersafe overwrite 가정), 파일 끝을 넘는 부분은 전과 같다. 주사위를 더 굴리지 않아 같은 시드면 같은 칸이 닿는다 | 정전 때 쓰던 칸을 망가뜨리는 디스크가 있다. 엔진이 **하나뿐인 사본을 덮어쓰지 않는지** 이 방식이 잡는다 |
| `Fs::rename` | 같은 디렉터리 안에서 `to`를 한 번에 바꾼다. 열린 손잡이는 파일을 따라간다(가짜 디스크는 inode 번호로). rename에 밀려난 파일을 옛 손잡이로 계속 쓰는 것은 흉내 내지 않고 오류를 낸다(POSIX에서는 된다. 엔진은 그러지 않는다). 디렉터리 sync 전 정전이면 **앞에서부터 몇 개까지만** 닿는다(저널링 파일시스템처럼 순서대로). 안 닿은 rename은 바뀐 파일을 되돌린다 | 새 WAL을 옛 WAL과 바꿔 끼우는 데 쓴다. POSIX rename은 원자적이다 |

## 2. 대책: 왜 "정리"가 아니라 "다시 쓰기"인가

처음 추천한 B+는 "열 때 정리(체크포인트)를 한 번 하고 메타 슬롯도 다시 쓴다"였다. 구현 전에 순서를 따져 보니 구멍이 있었다.

| 정리의 단계 | 그때 금고(디스크)의 상태 |
|---|---|
| 1. WAL의 페이지를 데이터 파일 제자리에 씀 → sync | 데이터 파일: 캐시에서 읽은 **최신** 페이지. 금고 속 WAL: 실패한 커밋 앞에서 끊김. 메타 슬롯: 옛 체크포인트 |
| (여기서 정전) | 열기는 옛 메타 + 끊긴 WAL을 재생한다. WAL에 이미지가 없는 페이지는 데이터 파일에서 읽는데, 그 페이지는 **실패한 커밋의 내용**으로 덮였다. 응답한 트리와 실패한 커밋의 페이지가 섞인다 |

평소 정리가 안전한 것은 "금고 속 WAL이 온전하다"는 전제 덕분이다(설계 0011). 같은 부팅에서 다시 열 때는 그 전제가 깨져 있다. 그래서 정리보다 먼저 WAL을 금고에 굳혀야 하는데, **WAL을 굳히고 나면 정리가 할 일이 없다.** WAL과 메타가 금고에 있으면 그 위에 붙는 커밋은 평소처럼 안전하다.

| 선택지 | 막는 것 | 비용 (열 때) | 결과 |
|---|---|---|---|
| B+. 열 때 정리 + 메타 다시 쓰기 | 정리 도중 정전이 없으면 전부 | 페이지 쓰기 + sync 4번 | **실제로 깨짐**: 첫 구현 때의 변이 K6(열 때 정리)에서 잊힌 커밋이 있는 DB를 열다 정리의 6번째 연산에서 정전 → 다시 열기가 `overflow page does not hold its share of the value`로 거부 (실험 0013) |
| 다시 쓰기, 제자리에 | 칸이 옛것 아니면 새것인 디스크에서 전부 | 메타 1쪽 쓰기 + sync, WAL 통째 쓰기 + sync | 처음 구현. 2-1절의 이유로 버림 |
| **다시 쓰기, 새 파일로 (택함)** | 전부, 쓰던 칸을 망가뜨리는 디스크에서도 | WAL 통째(최대 약 4 MiB) 새 파일 + sync + rename, 메타는 필요할 때만 | 3절 |
| C. 캐시를 거치지 않고 읽기 | 전부 | OS별 코드, 정렬 제약 | 변경이 큼 |

### 2-1. 왜 "제자리 덮어쓰기"도 버렸나 (PR #60 검증 뒤)

처음 구현은 열 때마다 고른 메타 슬롯과 WAL 전체를 **제자리에** 다시 쓰고 sync했다. 같은 바이트라 "칸마다 옛것 아니면 새것"인 디스크에서는 안전하다. 하지만 #59 전의 설계가 지키던 성질을 깬다.

| | #59 전 | 제자리 덮어쓰기 | 지금 |
|---|---|---|---|
| 하나뿐인 확정 사본을 덮어쓰나 | 안 씀. 슬롯은 오래된 쪽에, WAL은 뒤에 붙이기만, 정리하는 페이지는 WAL에 사본 | **열 때마다 씀** | 안 씀. WAL은 새 파일에, 슬롯은 짝이 남는 경우에만 |
| 쓰다 칸이 망가지면 | — | 슬롯: DB가 안 열림. WAL: 응답한 커밋을 잃음 | 다른 슬롯과 금고 속 WAL로 열림 |
| 증거 | 정리 정전 실험이 `Garbled`에서도 통과 | `Garbled`로 다시 열다 정전 → `WAL follows checkpoint 2, but the newest meta slot holds checkpoint 1` (커밋 172e6fb의 빨간 테스트) | 실험 0013 |

## 3. 열기의 새 순서

```
읽기 (바꾸는 것 없음): WAL 재생, 메타 슬롯 고르기, 트리 읽기
1. WAL이 고른 슬롯보다 옛 회차를 가리키면: 그 슬롯을 제자리에 다시 씀 → sync
2. WAL을 재생할 때: 잘린 꼬리는 .cut 파일에 보관 (→ sync, 디렉터리 sync)
   새 WAL 내용 = 읽은 WAL의 마지막 온전한 커밋까지
   WAL을 새로 시작할 때: 새 WAL 내용 = 머리말
3. 새 WAL 내용을 oakdb.wal.new에 씀, 길이 맞춤 → sync
   → rename(oakdb.wal.new → oakdb.wal) → 디렉터리 sync
4. 새 DB면 첫 커밋
```

| 같은 부팅의 경우 (설계 0012 7절 표) | 지금은 |
|---|---|
| 커밋의 WAL sync 실패 뒤 다시 열기 | 3이 실패한 커밋까지 새 파일에 써서 굳힌다. 실패한 커밋은 "결과 모름"이라 남아도 된다 |
| 정리 도중 페이지 sync 실패 | 그 페이지들은 WAL에 있다. 3이 WAL을 굳히고, 다음 정리가 페이지를 다시 쓴다 |
| 정리 도중 메타 슬롯 sync 실패 | WAL은 옛 회차를 가리킨다. 1이 그 슬롯을 먼저 굳혀서, 새 WAL 머리말이 금고 속 슬롯보다 앞서는 일(→ Corrupt)이 없다 |
| 정리 도중 WAL 비우기 sync 실패 | 읽기는 빈 WAL을 본다. 3이 새 파일로 바꿔 끼우니 금고 속 옛 WAL은 남지 않는다 |
| 새 DB 첫 커밋 실패 | 캐시의 첫 커밋을 읽고 "있는 DB"로 연다. 3이 굳힌다 |
| 열기 도중 디렉터리 sync 실패 | 다시 열면 rename을 **새로** 하므로 디렉터리가 다시 더러워져 다음 sync가 저장한다 |
| `.cut` 파일 sync 실패 | 조사용 파일이라 그대로 (데이터에 영향 없음) |

**1을 WAL이 같은 회차를 가리킬 때 건너뛰는 이유**: WAL 머리말에 회차 n을 새로 쓰는 곳은 둘뿐이다. 정리의 3단계(슬롯 n의 sync가 **성공한** 뒤)와, WAL이 옛 회차였을 때의 열기 3(1에서 슬롯 n을 굳힌 뒤)이다. 나머지 열기는 이미 있던 머리말을 옮기거나(재생할 때), 정리의 3단계가 비운 WAL 뒤에 쓴다(머리말이 없을 때). 그러니 머리말이 n이면 슬롯 n은 이미 금고에 있다. 덮어쓰지 않으면 망가질 일도 없다. WAL이 비었거나 머리말이 없을 때도 마찬가지다. 그 WAL은 정리의 3단계가 비운 것이라 슬롯은 이미 굳었다.

**1이 안전한 이유**: WAL이 n−1을 가리키면 슬롯 n−1도 같은 이유로 금고에 있고, 금고 속 WAL(n−1)은 n−1 뒤의 커밋을 모두 들고 있다. 정리는 커밋이 실패하지 않은 엔진에서만 돌기 때문이다. 슬롯 n을 쓰다 망가지면 열기는 슬롯 n−1과 그 WAL을 재생한다. 정리가 이미 데이터 파일에 쓴 페이지는 모두 그 WAL에 사본이 있어 재생이 덮는다. 0011 설계에서 "② 도중 정전"과 같은 상태다.

**1이 3보다 먼저인 이유**: 3의 새 머리말이 n을 가리키는데 금고에 슬롯 n이 없으면 열기가 "WAL이 모든 슬롯보다 새롭다"며 거부한다(변이 K6).

**rename 뒤 디렉터리 sync가 커밋보다 먼저인 이유**: 새 커밋은 새 파일에 붙는다. rename이 금고에 닿기 전에 정전이 나면 이름은 옛 WAL을 가리키고, 응답한 커밋이 사라진다(변이 K5). 이 sync가 이번에 만든 데이터 파일 항목도 함께 굳혀서, 열기 끝의 디렉터리 sync는 뺐다.

**데이터 파일의 다른 페이지**는 다시 쓰지 않는다. WAL에 없는 페이지는 sync가 **성공한** 정리가 쓴 것이다. 정리가 페이지 sync에서 실패했다면 그 페이지는 아직 WAL에 있어 재생이 덮는다.

**남은 `oakdb.wal.new`**: 열기가 3에서 끊기면 이 파일이 남을 수 있다. 다음 열기는 그 파일을 열어 덮어쓰고 **길이를 맞춘다.** 남은 파일이 더 길고, 그 꼬리가 이번에 쓴 바이트의 사슬에 이어지는 커밋(이번 열기가 못 본 실패한 커밋)이면, 길이를 안 맞출 경우 다음 정전 뒤 그 커밋이 되살아난다(변이 K7, 결정 8). 가짜 디스크는 같은 길이로 `set_len`해도 변경으로 센다. 실제 파일 시스템에서는 아무 일도 안 하는 호출이라, 이 점에서는 모델이 실제보다 관대하다.

**`Wal::start`(정리의 3단계)는 #59 전으로 되돌렸다.** 처음 구현은 열 때 이 함수를 써서 "비었다고 읽혀도 언제나 비우기"를 넣었다(변이 K4, 살아남음). 이제 열기는 새 파일을 쓰니 그럴 필요가 없다.

## 4. 비용

| 열기 | 늘어난 일 (#59 전과 비교) |
|---|---|
| 정상 종료 뒤 (`close()`가 정리함, WAL은 머리말뿐) | 새 파일 열기 + 머리말 20바이트 쓰기 + sync + rename. 디렉터리 sync는 원래 있던 것을 옮김 |
| 정전 뒤 | 위 + WAL 전체 쓰기 (최대 `CHECKPOINT_AFTER` = 4 MiB 남짓) |
| WAL이 옛 회차를 가리킬 때 (정리가 슬롯 뒤에서 끊김) | 위 + 메타 1쪽 쓰기 + sync |

열기에만 드는 비용이고 커밋 경로는 그대로다. 다시 열기 시간을 A/B(+ A/A 대조)로 잰다(`ab_versions.py`의 reopen, closed).

## 6. 디렉터리 sync 실패 (리뷰 P3)

파일 내용과 달리 디렉터리 항목은 파일시스템의 **메타데이터**다. Linux의 주요 저널링 파일시스템은 메타데이터 기록이 실패하면 조용히 넘어가지 않는다.

| 파일시스템 | 메타데이터 기록 실패 때 | 출처 |
|---|---|---|
| ext4 (jbd2) | 저널을 멈춘다(abort). 그 뒤 메타데이터를 바꾸는 호출은 실패하고, 보통 읽기 전용으로 다시 마운트된다 | jbd2 패치 "abort journal if free a async write error metadata buffer" (2020) |
| XFS | 파일시스템을 강제 종료한다(`xfs_do_force_shutdown`). 그 뒤 모든 호출이 EIO로 실패한다 | Red Hat 지식 문서 "XFS filesystem shuts down due to I/O errors" |

그래서 "디렉터리 항목이 캐시에만 있고 다음 sync도 저장하지 않는" 구멍은 이 둘에서는 생기지 않고, 엔진의 다음 호출이 실패한다(설계 0012의 "멈춤"). 그래도 3의 rename이 열 때마다 디렉터리를 새로 바꾸니, WAL 항목은 다른 파일시스템에서도 다음 디렉터리 sync가 저장한다. 데이터 파일 항목은 처음 만들 때 한 번뿐이라 이 논증에 기댄다. 가짜 디스크에는 흉내 내지 않았다.

**macOS (APFS, 리뷰 P4)**: `F_FULLFSYNC`가 실패한 뒤 캐시가 어떻게 되는지는 문서가 없다. 이 대책은 "캐시가 무엇을 들고 있든 다시 써서 새로 sync"라서, Linux식이든 기다리는 쪽이든 같게 막는다(실패 훑기를 두 방식으로 돌리는 이유).

**모델의 한계 (리뷰 P5)**: 가짜 디스크는 바이트 단위로 잊는다(Linux는 4 KiB 페이지). 쓰레기 칸은 쓰기가 덮은 바이트만 망가뜨린다(powersafe overwrite). 한 칸에서 쓰지 않은 바이트까지 망가뜨리는 디스크라면 WAL 끝에 붙이는 커밋이 앞 커밋의 마지막 칸을 망가뜨릴 수 있는데, 이는 #59 전부터의 가정이다.
