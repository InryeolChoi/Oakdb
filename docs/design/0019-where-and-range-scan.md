# 0019. WHERE와 범위 조회 — 설계

이슈 #32. 0017에서 SQL 입구가 생겼지만 SELECT는 `WHERE <기본 키> = <값>` 하나만 알아들었다. 이번 티켓에서 WHERE가 **진짜 조건식**이 된다. `id > 10 AND name = 'kim'`, `age < 20 OR age IS NULL` 같은 식을 읽고, 기본 키에 대한 조건은 **범위 조회 한 번**(엔진의 `scan`, #17)으로, 나머지 조건은 **읽은 행마다 확인하는 거르기**로 실행한다. 뒤 티켓인 UPDATE/DELETE(#33)는 같은 WHERE를 그대로 쓰고, 타입 오류 정리(#34)와 BEGIN/COMMIT(#35)도 이 구조 위에 얹힌다. 그래서 이번에 정하는 것은 "WHERE가 무엇을 뜻하고, 어떻게 실행으로 바뀌는가"다.

**비유**: 표는 **청구번호(기본 키) 순으로 꽂힌 도서관 책장**이다.

| 손님의 부탁 | 사서가 하는 일 | DB에서는 |
|---|---|---|
| "청구번호 100~200번 책" | 100번 칸으로 바로 가서 200번까지만 훑는다 | 범위 조회 (`scan`) |
| "저자가 김씨인 책" | 저자순 목록이 없으니 책장 처음부터 끝까지 한 권씩 본다 | 전체 훑기 + 거르기 |
| "100~200번 중 저자가 김씨" | 100~200번만 훑으면서 저자를 본다 | 범위 조회 + 거르기 |

Java로 치면 표는 `TreeMap<Long, Row>`다. 범위 조회는 `map.subMap(100L, true, 200L, true)`, 거르기는 `.values().stream().filter(r -> r.author.equals("kim"))`다. 이번 티켓의 핵심은 WHERE 식을 보고 **`subMap`의 양 끝을 얼마나 좁힐 수 있는지** 알아내는 일(계획, plan)이다. 좁히지 못해도 결과는 맞다. 느릴 뿐이다.

```
"SELECT name FROM users WHERE id >= 10 AND id < 20 AND name <> 'kim'"
  파서   → Select { where: And(And(id >= 10, id < 20), name <> 'kim') }
  계획   → 범위: [키(10) 포함, 키(20) 제외)   거르기: 식 전체
  실행기 → scan(범위) 로 id 10..19 행만 읽고, 행마다 거르기 식이 참인 것만 남김
```

## 1. 문법과 우선순위 (W1, W2, W3)

```
select    := SELECT ("*" | 이름 ("," 이름)*) FROM 이름 [WHERE 식]
식        := and식 (OR and식)*
and식     := not식 (AND not식)*
not식     := NOT not식 | 원자
원자      := "(" 식 ")" | 피연산자 비교뒤
비교뒤    := 비교연산 피연산자 | IS [NOT] NULL
피연산자  := 이름 | 리터럴              (리터럴은 0017 그대로: 정수, '글자', X'..', NULL)
비교연산  := = | != | <> | < | <= | > | >=
```

재귀 하강에서 우선순위는 **함수가 부르는 순서**다. `식`이 `and식`을, `and식`이 `not식`을 부르므로 아래로 갈수록 단단히 묶인다. 0017과 같은 "규칙 하나에 함수 하나"라 코드도 이 표를 그대로 따라간다.

| 식 | 읽는 법 | 왜 |
|---|---|---|
| `a = 1 OR b = 2 AND c = 3` | `a = 1 OR (b = 2 AND c = 3)` | AND가 OR보다 단단 (곱셈이 덧셈보다 단단한 것과 같음) |
| `NOT a = 1 AND b = 2` | `(NOT (a = 1)) AND b = 2` | NOT은 비교보다 느슨, AND보다 단단 |
| `NOT NOT a = 1` | `NOT (NOT (a = 1))` | NOT은 겹쳐 쓸 수 있음 |
| `a < b < c` | 지원 안 함 | 비교 결과(참/거짓)를 다시 비교하는 셈이라 뜻이 헷갈림 |

### 연산자 선택지 (W1)

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 비교 6종 + AND/OR/NOT + 괄호 | 이슈 완료 기준을 딱 채움 | NULL을 찾을 방법이 없음(`= NULL`은 늘 모름, 2절) |
| **B. A + `IS [NOT] NULL`** | NULL 행을 고를 유일한 정상 방법. #33에서 "NULL인 행 지우기"가 됨 | 키워드 `IS` 하나 더 |
| C. B + `BETWEEN`, `IN` | 실제 SQL에서 자주 씀 | 둘 다 다른 연산자로 풀어 쓸 수 있음(`a >= 1 AND a <= 5`, `a = 1 OR a = 2`). `BETWEEN x AND y`의 `AND`가 논리 AND와 겹쳐 파서가 까다로워짐 |
| D. C + 산술 | `id + 1 = 5` | 넘침·0으로 나누기 같은 실행 중 오류가 생김. 계획이 "기본 키 = 상수"를 알아보기 어려워짐 |

**추천 B.** `BETWEEN`/`IN`/`LIKE`/산술 기호를 만나면 0017처럼 "지원 안 함: `BETWEEN`"이라고 이름을 댄다. 렉서는 이미 `<`, `<=`, `>`, `>=`, `<>`, `!=`, `+`, `/`를 낱말로 자르므로 손댈 곳이 없다.

### 피연산자 선택지 (W3)

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 왼쪽은 열, 오른쪽은 리터럴만 | 가장 단순 | `5 < id`가 문법 오류. 열끼리 비교 불가 |
| **B. 양쪽 다 열 또는 리터럴** | 자연스러움. `5 < id`는 계획이 `id > 5`로 뒤집으면 끝 | 열끼리 비교(`a = b`)도 타입 검사를 해야 함(3절, 어렵지 않음) |
| C. 양쪽에 아무 식 | 가장 일반적 | 산술이 없으면 쓸모가 없고 `(a = 1) = (b = 2)` 같은 이상한 식이 생김 |

**추천 B.** 산술이 없으니 피연산자에 괄호가 올 일이 없고, `(`는 언제나 "식 묶음"이다. 덕분에 파서가 앞을 더 내다볼 필요가 없다.

## 2. NULL: 3값 논리 (W4)

SQL의 조건은 참·거짓 말고 **모름(UNKNOWN)**이 하나 더 있다. Java의 `Boolean`이 `true`/`false`/`null` 세 가지일 수 있는 것과 비슷하다. NULL은 "값을 모른다"라서, 모르는 값과 무엇을 비교해도 결과는 "모름"이다. WHERE는 **참인 행만** 남긴다. 거짓과 모름은 둘 다 버린다.

| A | B | A AND B | A OR B | NOT A |
|---|---|---|---|---|
| 참 | 모름 | 모름 | 참 | 거짓 |
| 거짓 | 모름 | **거짓** | 모름 | 참 |
| 모름 | 모름 | 모름 | 모름 | **모름** |

(참·거짓끼리는 보통 논리와 같다.)

| 선택지 | `name`이 NULL인 행에 `NOT (name = 'kim')` | 장점 | 단점 |
|---|---|---|---|
| **A. 3값 논리** | 모름 → 버림 | SQLite·PostgreSQL·표준과 같은 답. 위 표 하나로 끝 | 값이 셋이라 `bool`이 아니라 작은 열거형이 필요 |
| B. 단순화: NULL 비교는 거짓 | 거짓 → NOT → 참 → **남김** | `bool` 그대로 | 다른 DB와 답이 다름. #33에서 `DELETE ... WHERE NOT (name = 'kim')`이 **NULL 행까지 지움** |

**추천 A.** B의 차이는 NOT이 끼는 순간에만 드러나 찾기 어려운 버그가 되고, #33에서 데이터를 지우는 쪽으로 터진다. A의 비용은 `enum Truth { True, False, Unknown }`과 세 줄짜리 표뿐이다.

- `col = NULL`, `col <> NULL`, `NULL = NULL`: 언제나 모름 → 행 없음. 0017의 `WHERE id = NULL` → 0행과 같다.
- `col IS NULL` / `col IS NOT NULL`: 언제나 참 또는 거짓(모름이 안 나옴).
- 기본 키는 NULL이 될 수 없으므로(0017 C5) `pk IS NULL`은 늘 거짓이다.

## 3. 타입이 다른 값의 비교 (W5)

열 종류는 INTEGER, TEXT, BLOB 하나씩이고, 열 하나에는 그 종류 값 또는 NULL만 있다(0017). 그래서 **비교 양쪽의 타입은 행을 하나도 읽기 전에 다 정해진다.**

| 선택지 | `WHERE age = 'ten'` (`age INTEGER`) | 장점 | 단점 |
|---|---|---|---|
| **A. 실행 전 `TypeMismatch` 오류** | 오류 | 0017의 `WHERE id = 'a'` → 타입 불일치와 같음. 오타를 바로 알려줌. 오류가 행 내용에 따라 달라지지 않음 | 없음에 가까움 |
| B. 거짓(또는 모름)으로 보고 0행 | 0행 | 실행이 멈추지 않음 | 오타가 "결과 없음"으로 숨음 |
| C. SQLite식: 타입끼리 순서를 정함(정수 < 글자 < 바이트) | 0행 | SQLite와 같음 | 열에 타입이 하나뿐인 Oakdb에서는 쓸 데가 없는 규칙 |

**추천 A.** 계획 단계(6절)에서 식을 한 번 훑으며 검사하므로 **오류가 나면 아무 행도 읽지 않는다.** 오류 종류는 기존 `TypeMismatch { column, expected, found }`를 그대로 쓴다. 열끼리(`a = b`) 다르면 왼쪽 열 이름으로 보고한다. #34는 이 검사가 이미 한곳에 모여 있는 것을 받아 메시지를 다듬기만 하면 된다.

같은 타입끼리의 순서는 **키 인코딩의 바이트 순서와 같아야 한다**(5절에서 범위와 거르기가 같은 답을 내려면).

| 타입 | 비교 | 키 인코딩 순서와 같은가 |
|---|---|---|
| INTEGER | i64 크기 | 같음 (부호 비트 뒤집기, 0017 2-1) |
| TEXT | UTF-8 바이트 사전순 (= Rust `String`의 `Ord`, 유니코드 코드포인트 순). 대소문자·언어별 정렬 없음 | 같음 (`00` 이스케이프 + 끝 표시) |
| BLOB | 바이트 사전순 | 같음 |

## 4. 어떤 조건을 범위 조회로 바꾸나 (W6)

원칙 하나: **범위는 넉넉하게, 판정은 정확하게.** 범위는 "어디를 훑을지"만 줄이고, 행마다 WHERE 식 전체를 다시 확인한다. 그러면 범위가 필요보다 넓어도 결과는 맞다(느릴 뿐). 틀릴 수 있는 경우는 범위가 **좁아서 맞는 행을 빠뜨릴 때**뿐이고, 이것을 8절의 속성 테스트가 잡는다.

| 선택지 | 범위로 쓰는 것 | 예: 범위 조회가 되나 | 장점 | 단점 |
|---|---|---|---|---|
| **A. 맨 위 AND의 기본 키 비교** | `pk 연산 리터럴`(또는 `리터럴 연산 pk`)이면서 맨 위 AND들로만 묶인 것. 여러 개면 교집합 | `id > 5 AND id <= 9 AND name = 'a'` 됨 / `id = 1 OR id = 5` 전체 훑기 | 단순. 범위가 언제나 하나 | 기본 키 OR는 느림 |
| B. A + 기본 키 OR를 여러 범위로 | A에 더해 OR의 각 갈래가 기본 키 범위면 범위 여러 개(합치고 정렬) | `id = 1 OR id = 5`, `id < 3 OR id > 90` 됨 | `IN`을 나중에 넣으면 쓸모 큼 | 범위 합치기·겹침 처리·여러 번 훑기. 갈래 하나라도 기본 키가 아니면 결국 전체 훑기 |
| C. 일반 정규화 | NOT을 안으로 밀고(드모르간), OR-AND 형태로 펼친 뒤 B | `NOT (id < 5)`도 됨 | 가장 넓음 | 식이 지수적으로 커질 수 있음. 이 규모에선 과함 |

**추천 A.** 이슈의 완료 기준("기본 키 범위 조건은 범위 조회로 실행된다")을 채우는 가장 작은 규칙이고, "범위는 넉넉하게" 원칙 덕분에 나중에 B로 넓혀도 기존 결과가 바뀌지 않는다. `IN`이 들어올 때(지금은 범위 밖) B를 다시 보자.

A에서 범위로 쓰지 않는 것(전부 거르기에서는 확인함):

| 조건 | 범위에 안 쓰는 이유 |
|---|---|
| `pk != v`, `pk <> v` | 범위 둘(`< v`, `> v`)이 필요 — B의 일 |
| `pk = NULL` 등 NULL 리터럴 | 늘 모름이라 행이 없음. 범위를 비워도 되지만 거르기가 이미 0행을 냄(9절 Q2) |
| `pk = other_col` | 상대가 행마다 다른 값 |
| OR·NOT 안의 기본 키 비교 | A의 범위 밖 |
| `pk IS NOT NULL` | 언제나 참이라 좁힐 것이 없음 |

## 5. 범위의 양 끝 (W7)

엔진의 `txn.scan`은 양 끝을 `Bound::Included(키)`, `Bound::Excluded(키)`, `Bound::Unbounded`로 받는다(#17, Java `subMap(from, fromInclusive, to, toInclusive)`와 같음). 0017의 기본 키 인코딩은 **바이트 순서 = 값 순서**이므로, 값을 키로 바꾸고 포함/제외는 **그대로** 넘기면 된다.

표 `T`의 행 키는 `[01][T u32 BE][인코딩한 기본 키]`다. 기본 키 조건이 한쪽 끝을 정하지 않으면 그 끝은 표의 끝이다.

| 조건 | 시작 | 끝 |
|---|---|---|
| (기본 키 조건 없음) | 표 시작 = `Included([01][T])` | 표 끝 = `Excluded([01][T+1])` |
| `id = v` | `Included(키(v))` | `Included(키(v))` |
| `id > v` | `Excluded(키(v))` | 표 끝 |
| `id >= v` | `Included(키(v))` | 표 끝 |
| `id < v` | 표 시작 | `Excluded(키(v))` |
| `id <= v` | 표 시작 | `Included(키(v))` |
| `5 < id` | `id > 5`로 뒤집어 위 표 | |

**교집합** (AND로 여러 개): 시작은 더 큰 쪽, 끝은 더 작은 쪽. 키가 같으면 `Excluded`가 더 좁다. 비교는 **바이트로** 한다. 타입마다 따로 비교하지 않아도 0017의 순서 보존 속성(속성 테스트로 증명됨)이 값 순서와 같음을 보장한다. `id > 5 AND id < 3`처럼 시작이 끝보다 뒤면 엔진이 빈 범위로 다룬다(`empty_if_backwards`). 따로 처리할 것이 없다.

### i64 끝값과 넘침

| 선택지 | `id > i64::MAX` | 장점 | 단점 |
|---|---|---|---|
| **A. 포함/제외를 그대로 넘김** | `Excluded(FF FF FF FF FF FF FF FF)` → 그 뒤 표 안에 키 없음 → 0행 | +1 계산이 없어 넘침 자체가 없음. TEXT·BLOB도 같은 규칙 | 없음 |
| B. 모두 포함 범위로 바꿈(`> v` → `>= v+1`) | `i64::MAX + 1` 넘침 → 특별 처리 필요 | 범위 모양이 하나 | 넘침 처리. TEXT에는 "다음 값"이 깔끔하지 않음(`'a'` 다음은 `'a\0'`) |

**추천 A.** 끝값 예:

| 식 | 결과 | 왜 |
|---|---|---|
| `id > 9223372036854775807` | 0행 | `Excluded(FF×8)`, 표 안에 더 큰 키 없음 |
| `id >= 9223372036854775807` | i64::MAX 행 하나(있으면) | `Included(FF×8)` |
| `id < -9223372036854775808` | 0행 | `Excluded(00×8)` |
| `id > 9223372036854775808` | 문법 오류 | 리터럴이 i64에 안 들어감(0017 6절 그대로). 9절 Q3 |
| `name > 'a'` | `'a\0'`, `'ab'`, … | `Excluded(61 00 00)`. 끝 표시 덕분에 `'a'` 하나만 정확히 빠짐 |

## 6. 계획 단계와 문장 나무 (W8)

```
SQL 문자열 → 렉서 → 파서 → Statement { where: Expr<String> }
                              ↓
               planner::plan(&Table, Expr<String>) → Plan { range, filter: Expr<usize> }
                 · 열 이름 → 열 번호 (없는 열 = NoSuchColumn)
                 · 타입 검사 (TypeMismatch)            ← 여기까지 행을 하나도 읽지 않음
                 · 맨 위 AND의 기본 키 비교 → 범위
                              ↓
               executor: txn.scan(range) → 행 디코딩 → filter가 참인 행만
```

### 계획을 어디에 두나

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 실행기의 `select` 함수 안 | 파일이 안 늘어남 | 범위 계산을 테스트하려면 DB를 열어야 함. #33의 UPDATE/DELETE가 같은 코드를 복사하거나 꺼내야 함 |
| **B. `planner.rs`의 순수 함수** | 엔진·트랜잭션 없이 `(표 정보, 식) → (범위, 거르기)`라 단위 테스트가 쉬움. #33이 그대로 부름 | 모듈 하나 늘어남 |

**추천 B.** 오류(없는 열, 타입 불일치)가 모두 계획에서 나므로 "오류면 아무것도 읽지 않는다"가 구조로 보장된다.

### 식의 모양 (Rust)

```rust
enum Expr<C> {
    Compare { left: Operand<C>, op: CompareOp, right: Operand<C> },
    IsNull { operand: Operand<C>, negated: bool },
    Not(Box<Expr<C>>),
    And(Box<Expr<C>>, Box<Expr<C>>),
    Or(Box<Expr<C>>, Box<Expr<C>>),
}
enum Operand<C> { Column(C), Literal(Value) }
enum CompareOp { Eq, Ne, Lt, Le, Gt, Ge }   // `!=`와 `<>`는 둘 다 Ne
```

| 고를 점 | 선택지 | 추천과 이유 |
|---|---|---|
| 피연산자 | `Operand`를 따로 둠 / 비교 양쪽도 `Expr` | **따로 둠.** `(a = 1) = (b = 2)` 같은 식이 타입으로 아예 만들어지지 않음(만들 수 없는 상태는 표현하지 않기) |
| 열 이름과 열 번호 | 이름 그대로 두고 행마다 찾기 / 두 열거형 / **`Expr<C>` 하나를 `C = String`·`usize`로** | **`Expr<C>`.** 행마다 이름을 찾지 않고, 같은 모양을 두 번 적지 않음. 파서는 표 정보를 몰라도 됨 |
| AND/OR | 두 갈래(`Box` 둘) / 여러 갈래(`Vec`) | **두 갈래.** 파서가 자연스럽게 만듦. 맨 위 AND 모으기는 재귀 함수 하나 |
| 참·거짓·모름 | `Option<bool>` / `enum Truth` | **`enum Truth`.** `None`이 "모름"인지 "없음"인지 헷갈리지 않음 |

`Plan`의 범위는 `(Bound<Vec<u8>>, Bound<Vec<u8>>)`, 거르기는 `Option<Expr<usize>>`(WHERE가 없으면 `None`).

### 뒤 티켓과 맞추기

| 티켓 | 이 설계에서 쓰는 것 |
|---|---|
| #33 UPDATE/DELETE | 같은 `plan`. 단, `scan`은 트랜잭션을 `&`로 빌리고 `put`/`delete`는 `&mut`가 필요해 Rust가 **"맞는 키를 먼저 모으고, 그다음 고치기"**를 강제한다. 이것이 고치는 도중 고친 행을 다시 만나는 문제(할로윈 문제)도 막는다 |
| #34 타입 오류 | 타입 검사가 `plan` 한곳에 있음. 지원 안 함/문법 오류 경계는 1절 표 |
| #35 BEGIN/COMMIT | `plan`은 트랜잭션을 모르므로 바뀔 것 없음. 읽기는 충돌 판정에 들어가지 않으므로(0016, 쓰기-쓰기만) 범위 SELECT는 충돌을 내지 않음. 범위 UPDATE의 쓰기 치우침(write skew)은 0016에 적힌 그대로 |

## 7. 기존 길 흡수와 WHERE 없는 SELECT (W9)

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. `pk = v`도 양 끝이 같은 범위 조회** | 실행 길이 하나. 테스트할 길이 하나 | `get`보다 아주 조금 느릴 수 있음(커서 하나 만듦) |
| B. 범위가 한 점이면 `get` 지름길 | 한 점 조회가 가장 빠름 | 길이 둘이라 두 길이 같은 답을 내는지 따로 확인해야 함 |

**추천 A.** 둘 다 B+Tree를 한 번 내려가는 일이라 차이는 작다고 예상한다. 검증 단계 벤치마크(8절)에서 차이가 크면 B를 다시 본다.

A로 바뀌면서 달라지는 겉모습:

| 전 (0017) | 후 |
|---|---|
| `WHERE name = 'kim'` → 지원 안 함 | 거르기로 실행 |
| `WHERE id > 1` → 지원 안 함 | 범위 조회 |
| WHERE 없는 SELECT → 지원 안 함 | **표 전체**(추천). 표 범위 훑기에 거르기 없음이라 덤으로 생김 |
| `pk = <엔진 키 길이보다 긴 글자>` → `Engine(KeyTooLarge)` | **0행.** `get`은 키 길이를 검사하지만 `scan`은 하지 않음. #34에 넘긴 질문이 저절로 "0행"으로 정해짐(9절 Q5) |
| 결과는 0행 또는 1행 | 여러 행, **기본 키 순서**(9절 Q4) |

기존 테스트 중 위 "지원 안 함"을 확인하던 것(`tests/sql.rs`의 `>`·`name` 예, `tests/blind_sql.rs`의 `unsupported_statements_say_unsupported`의 WHERE 네 줄)은 새 범위 밖 예(`BETWEEN`, `IN`, `id + 1 = 2`, `LIKE`)로 바꾼다.

## 8. 테스트 계획 (W10)

B+Tree를 `BTreeMap`과 같은 동작을 하는지 무작위로 비교했듯, SQL도 **"전부 읽고 하나씩 거르는" 단순한 모델**과 비교한다.

| 테스트 | 무엇을 |
|---|---|
| 모델 비교 속성 테스트 (proptest, `tests/`) | 무작위 표(INTEGER 기본 키 표와 TEXT 기본 키 표), 무작위 행(작은 값 범위 + i64 끝값, NULL 자주), 무작위 식(깊이 3 정도, 비교·IS NULL·AND·OR·NOT·괄호)을 **SQL 문자열로 찍어** `execute` → 결과 = 모델(`BTreeMap`의 모든 행에 대해 테스트 안에 따로 쓴 3값 논리 평가기로 거름). 모델은 실행기의 평가 코드를 쓰지 않는다(같은 버그를 공유하지 않게) |
| 계획 속성 테스트 (`planner.rs`) | 무작위 식과 행에 대해 "식이 참인 행의 키는 반드시 계획의 범위 안" (범위는 넉넉하게 원칙, 4절) |
| 계획 단위 테스트 | 완료 기준 1 "범위 조회로 실행된다"를 직접 확인: `id > 5 AND name = 'a'` → `(Excluded(키 5), 표 끝)`, `id = 1 OR id = 5` → 표 전체, `5 < id` 뒤집기, 교집합의 포함/제외 동점, 5절 끝값 |
| 파서 단위 테스트 | 1절 우선순위 표, `!=`와 `<>`, 괄호, 비교 연결·`BETWEEN`·`IN`·산술 → 지원 안 함, 닫는 괄호 없음 → 문법 오류(위치) |
| `tests/sql.rs` | 2절 NULL 표대로(`NOT (name = 'kim')`이 NULL 행을 남기지 않음), 3절 타입 불일치(행을 읽기 전, 빈 표에서도 오류), WHERE 없는 SELECT, 7절 바뀐 겉모습 |
| 벤치마크 (`docs/benchmarks/`) | 행 수 N을 늘리며 `id >= a AND id < a+100`(범위 100행)의 시간이 N과 거의 무관하고, `name = …`(전체 훑기)는 N에 비례하는지. `pk = v`의 `get`(main) 대 범위 조회(이 브랜치) A/B, A/A 대조 포함 |

## 9. 작은 질문

| # | 질문 | 추천 | 이유 |
