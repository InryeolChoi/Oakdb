# 0019. WHERE와 범위 조회 — 설계

이슈 #32. 0017에서 SQL 입구가 생겼지만 SELECT는 `WHERE <기본 키> = <값>` 하나만 알아들었다. 이번 티켓에서 WHERE가 **진짜 조건식**이 된다. `id > 10 AND name = 'kim'`, `age BETWEEN 20 AND 29 OR age IS NULL`, `id % 2 = 0` 같은 식을 읽고, 기본 키에 대한 조건은 **범위 조회 한 번**(엔진의 `scan`, #17)으로, 나머지 조건은 **읽은 행마다 확인하는 거르기**로 실행한다. 뒤 티켓인 UPDATE/DELETE(#33)는 같은 WHERE를 그대로 쓰고, 타입 오류 정리(#34)와 BEGIN/COMMIT(#35)도 이 구조 위에 얹힌다. 그래서 이번에 정하는 것은 "WHERE가 무엇을 뜻하고, 어떻게 실행으로 바뀌는가"다.

**비유**: 표는 **청구번호(기본 키) 순으로 꽂힌 도서관 책장**이다.

| 손님의 부탁 | 사서가 하는 일 | DB에서는 |
|---|---|---|
| "청구번호 100~200번 책" | 100번 칸으로 바로 가서 200번까지만 훑는다 | 범위 조회 (`scan`) |
| "저자가 김씨인 책" | 저자순 목록이 없으니 책장 처음부터 끝까지 한 권씩 본다 | 전체 훑기 + 거르기 |
| "100~200번 중 저자가 김씨" | 100~200번만 훑으면서 저자를 본다 | 범위 조회 + 거르기 |

Java로 치면 표는 `TreeMap<Long, Row>`다. 범위 조회는 `map.subMap(100L, true, 200L, true)`, 거르기는 `.values().stream().filter(r -> r.author.equals("kim"))`다. 이번 티켓의 핵심은 WHERE 식을 보고 **`subMap`의 양 끝을 얼마나 좁힐 수 있는지** 알아내는 일(계획, plan)이다. 좁히지 못해도 결과는 맞다. 느릴 뿐이다.

```
"SELECT name FROM users WHERE id >= 10 AND id < 20 AND name <> 'kim'"
  파서   → Select { where: And(And(id >= 10, id < 20), name <> 'kim') }
  계획   → 범위: [10 포함, 20 제외)   거르기: 식 전체
  실행기 → scan(범위) 로 id 10..19 행만 읽고, 행마다 거르기 식이 참인 것만 남김
```

## 1. 문법과 우선순위 (W1, W2, W3)

```
select    := SELECT ("*" | 이름 ("," 이름)*) FROM 이름 [WHERE 식]
식        := and식 (OR and식)*
and식     := not식 (AND not식)*
not식     := NOT not식 | 술어
술어      := 덧셈 [ 비교연산 덧셈
                  | IS [NOT] NULL
                  | [NOT] BETWEEN 덧셈 AND 덧셈
                  | [NOT] IN "(" 식 ("," 식)* ")" ]
덧셈      := 곱셈 (("+" | "-") 곱셈)*
곱셈      := 단항 (("*" | "/" | "%") 단항)*
단항      := "-" 단항 | 기본
기본      := 리터럴 | 이름 | "(" 식 ")"
비교연산  := = | != | <> | < | <= | > | >=
```

재귀 하강에서 우선순위는 **함수가 부르는 순서**다. `식`이 `and식`을, `and식`이 `not식`을 부르므로 아래로 갈수록 단단히 묶인다. 0017과 같은 "규칙 하나에 함수 하나"라 코드도 이 문법을 그대로 따라간다.

| 식 | 읽는 법 | 왜 |
|---|---|---|
| `a = 1 OR b = 2 AND c = 3` | `a = 1 OR (b = 2 AND c = 3)` | AND가 OR보다 단단 (곱셈이 덧셈보다 단단한 것과 같음) |
| `NOT a = 1 AND b = 2` | `(NOT (a = 1)) AND b = 2` | NOT은 비교보다 느슨, AND보다 단단 |
| `a + 2 * 3 = 7` | `(a + (2 * 3)) = 7` | 산술은 비교보다 단단 |
| `a BETWEEN 1 AND 5 AND b = 2` | `(a BETWEEN 1 AND 5) AND b = 2` | BETWEEN의 양 끝은 `덧셈`까지만 읽으므로 그 안의 `AND`가 논리 AND와 헷갈리지 않음 |
| `-a * 2` | `(-a) * 2` | 단항이 가장 단단 |
| `- 9223372036854775808` | 리터럴 i64::MIN | `-` 바로 뒤가 정수 낱말이면 0017처럼 음수 리터럴로 합침 |
| `a < b < c` | 지원 안 함 | 비교 결과(참/거짓)를 다시 비교하는 셈이라 뜻이 헷갈림 |

`(`는 이제 참·거짓 식(`(a = 1 OR b = 2)`)도, 값 식(`(a + 1) * 2`)도 묶는다. 파서는 둘을 가리지 않고 `Expr` 하나로 만들고, 어느 쪽인지는 계획 단계의 타입 검사(3절)가 정한다. 실제 SQL 파서도 이렇게 한다. 파서가 미리 가리려면 괄호 안을 끝까지 내다봐야 해서 재귀 하강이 복잡해진다.

### 연산자 (W1: 사용자가 D를 골랐다)

| 선택지 | 내용 | 결정 |
|---|---|---|
| A | 비교 + AND/OR/NOT + 괄호 | |
| B | A + `IS [NOT] NULL` | 추천이었음 |
| C | B + `BETWEEN`, `IN` | |
| **D** | C + INTEGER 산술 | **사용자 결정** |

D를 고르면서 생긴 일과 그 답:

| 생긴 일 | 답 |
|---|---|
| 피연산자가 아무 식이 됨 (W3) | 값 식과 참·거짓 식을 타입 검사로 가른다 (3절) |
| 실행 중 오류가 생김: 넘침, 0으로 나누기 | 오류로 멈춘다 (W11, 2-2절) |
| 계획이 "기본 키 = 상수"를 알아보기 어려워짐 (`id > 3 + 4`) | 열이 없는 식은 상수. 계획 때 계산해서(접기) 범위에 쓴다 (4절) |
| `BETWEEN x AND y`의 `AND` | 양 끝을 `덧셈` 수준까지만 읽는다 (위 표) |

`LIKE`, `GLOB`, `REGEXP`, `MATCH`, `||`(글자 잇기), `IS` 뒤에 `NULL`이 아닌 것은 "지원 안 함"이다. 렉서는 이미 `<`, `<=`, `>`, `>=`, `<>`, `!=`, `+`, `-`, `*`, `/`를 낱말로 자르므로 `%` 하나만 더한다.

### 1-1. 중첩 깊이 한도 (PR #69 리뷰 S1, 검증 후 추가)

파싱, 계획, 계산, 메모리 해제가 모두 식의 나무를 재귀로 돈다. 그래서 `NOT`을 2만 번 쓰거나, 괄호를 5천 겹 싸거나, `1 + 1 + …`를 2만 번 이으면 스택이 넘친다. 스택 넘침은 패닉과 달리 잡을 수 없다. 프로세스가 그대로 죽는다. 네트워크 서버(ADR 0005)가 생기면 손님 한 명이 서버 전체를 내릴 수 있다는 뜻이다.

| 정한 것 | 내용 |
|---|---|
| 한도 | **200단계.** 넘으면 `Syntax` 오류: "the expression nests more than 200 levels deep" |
| 무엇을 세나 | ① 나무의 높이: 노드를 만들 때마다 잰다. `1 + 1 + …`처럼 반복문으로 만드는 긴 사슬과 `NOT`, 단항 `-`의 연속도 여기서 걸린다. ② 파서 자신의 재귀 깊이: 괄호와 IN 목록. 둘 다 노드를 만들기 **전에** 검사하므로, 너무 깊은 나무는 아예 만들어지지 않는다 |
| 파서 구조 | 우선순위 단계마다 함수 하나를 두던 방식(괄호 한 겹에 스택 프레임 8개)을 **우선순위 오르기(precedence climbing)**로 바꿨다. 괄호 한 겹에 프레임 3개를 쓰고, `NOT`·`-`의 연속은 반복문으로 읽어 재귀하지 않는다. 문법과 우선순위는 그대로다 |
| 계획·계산 | 재귀하는 함수에는 재귀하는 갈래(NOT/AND/OR, 산술)만 남겼다. 나머지 갈래는 `#[inline(never)]` 함수로 뺐다. 그래야 재귀 프레임이 작게 유지된다 |
| 디버그 빌드 | `oakdb-sql`의 dev 프로필을 `opt-level = 1`로 올렸다. 최적화를 전혀 하지 않으면 프레임 하나가 1~2 KB까지 커져서 괄호 50겹 정도에서 256 KiB 스택이 넘쳤다. 이 설정은 테스트와 개발 빌드에만 쓰이고, 릴리스 빌드는 원래 최적화한다 |
| 확인한 여유 | 256 KiB 스레드(서버의 연결당 스택)와 기본 스택에서 2만 단계 입력이 모두 오류로 끝난다. 한도 바로 아래(190~198단계)는 정상 실행된다. 128 KiB에서 가장 스택을 많이 쓰는 경로(NOT 연쇄의 계획)는 약 145단계까지 버텼다. 그러니 256 KiB에서는 한도 200에 약 1.4배 여유가 있다 |

SQLite는 기본 한도가 1000(`SQLITE_MAX_EXPR_DEPTH`)이다. 사람이 쓰는 WHERE는 몇 단계를 넘지 않으므로 200이면 넉넉하다고 봤다.

## 2. NULL: 3값 논리 (W4)

SQL의 조건은 참·거짓 말고 **모름(UNKNOWN)**이 하나 더 있다. Java의 `Boolean`이 `true`/`false`/`null` 세 가지일 수 있는 것과 비슷하다. NULL은 "값을 모른다"라서, 모르는 값과 무엇을 비교해도 결과는 "모름"이다. WHERE는 **참인 행만** 남긴다. 거짓과 모름은 둘 다 버린다.

| A | B | A AND B | A OR B | NOT A |
|---|---|---|---|---|
| 참 | 모름 | 모름 | 참 | 거짓 |
| 거짓 | 모름 | **거짓** | 모름 | 참 |
| 모름 | 모름 | 모름 | 모름 | **모름** |

(참·거짓끼리는 보통 논리와 같다.)

| 선택지 | `name`이 NULL인 행에 `NOT (name = 'kim')` | 장점 | 단점 |
|---|---|---|---|
| **A. 3값 논리** | 모름 → 버림 | SQLite·PostgreSQL·표준과 같은 답 | 값이 셋이라 `bool`이 아니라 작은 열거형이 필요 |
| B. 단순화: NULL 비교는 거짓 | 거짓 → NOT → 참 → **남김** | `bool` 그대로 | 다른 DB와 답이 다름. #33에서 `DELETE ... WHERE NOT (name = 'kim')`이 **NULL 행까지 지움** |

**결정 A.** 규칙:

| 식 | 결과 |
|---|---|
| NULL이 낀 산술 (`NULL + 1`, `-NULL`, `a * NULL`) | NULL |
| NULL이 낀 비교 (`col = NULL`, `NULL <> NULL`) | 모름 → 행 없음. 0017의 `WHERE id = NULL` → 0행과 같다 |
| `x IS NULL` / `x IS NOT NULL` | 언제나 참 또는 거짓 |
| `x BETWEEN a AND b` | `x >= a AND x <= b`와 같다. `x NOT BETWEEN a AND b`는 `NOT (x BETWEEN a AND b)` |
| `x IN (v1, v2, ...)` | 어느 `vi`와 같으면 참. 아니면, `x`나 어느 `vi`가 NULL이면 모름. 아니면 거짓. `x NOT IN (...)`은 그 NOT |
| `3 NOT IN (1, NULL)` | `3 = 1`은 거짓, `3 = NULL`은 모름 → IN은 모름 → NOT IN도 **모름**(결코 참이 아님) |
| `1 NOT IN (1, NULL)` | IN이 참 → NOT IN은 거짓 |
| `5 NOT BETWEEN 1 AND NULL` | `5 >= 1`(참) AND `5 <= NULL`(모름) = 모름 → NOT도 모름 |
| `0 NOT BETWEEN 1 AND NULL` | `0 >= 1`(거짓) AND … = 거짓 → NOT은 **참** (표준과 같음) |

기본 키는 NULL이 될 수 없으므로(0017 C5) `pk IS NULL`은 늘 거짓이다.

### 2-1. 계산 순서

AND는 왼쪽이 거짓이면 오른쪽을 보지 않고, OR은 왼쪽이 참이면 오른쪽을 보지 않는다. IN은 왼쪽부터 보다가 같은 값을 만나면 멈춘다. 이 순서는 **결과(참·거짓·모름)를 바꾸지 않는다**(3값 표가 그렇게 생겼다). 바뀌는 것은 아래 오류가 나느냐뿐이다.

### 2-2. 넘침과 0으로 나누기 (W11)

| 선택지 | `9223372036854775807 + 1` | `5 / 0` | 장점 | 단점 |
|---|---|---|---|---|
| **A. 오류** | `Arithmetic` 오류 | `Arithmetic` 오류 | 틀린 답을 조용히 내지 않음. PostgreSQL과 같음. Rust의 `checked_*`가 그대로 맞음 | 오류가 나느냐가 **어떤 행을 읽었느냐**에 달림(아래) |
| B. SQLite식 | 실수(REAL)로 바뀜 | NULL | 실행이 멈추지 않음. 결과가 읽은 행과 무관 | Oakdb엔 REAL이 없음. `/0`이 NULL이면 `WHERE x / 0 IS NULL`이 모든 행을 고르는 등 오타가 숨음 |
| C. 감싸 돌기 | i64::MIN | — | 빠름 | 틀린 답. DB에서는 받아들일 수 없음 |

**결정 A.** B가 "확실히 낫다"고 보지 않은 이유: B의 장점(오류가 행에 따라 달라지지 않음)은 진짜지만, Oakdb에는 넘침을 받을 REAL이 없어 B의 반쪽(넘침)이 성립하지 않고, 남는 `/0 → NULL`은 오타를 숨긴다.

A의 대가로 받아들이는 것: **범위 밖이라 읽지 않은 행에서는 오류가 나지 않는다.** `WHERE 10 / (id - 3) > 0 AND id > 5`는 `id = 3`인 행이 범위(`id > 5`) 밖이라 읽히지 않으므로 오류가 없다. 전부 훑으면 오류다. PostgreSQL도 계산 순서를 약속하지 않아 같은 일이 생긴다. 약속은 이것 하나다: **모든 행을 모든 식으로 계산해도 오류가 없다면, Oakdb도 오류 없이 정확한 답을 낸다**(8절 속성 테스트가 이것을 확인한다).

세부:

| 연산 | 규칙 |
|---|---|
| `+ - *` | `checked_add/sub/mul`. 넘치면 오류 |
| `/` | 0쪽으로 버림(`-7 / 2 = -3`). 0으로 나누면 오류. `i64::MIN / -1`은 넘침 오류 |
| `%` | 부호는 나뉘는 수를 따름(`-7 % 2 = -1`). 0이면 오류. `i64::MIN % -1`은 넘침 오류(Rust `checked_rem`과 같음) |
| 단항 `-` | `-i64::MIN`은 넘침 오류. 단, `-9223372036854775808`처럼 `-` 바로 뒤 정수 낱말은 리터럴이라 오류가 아님 |
| `NULL / 0`, `NULL % 0` (검증 후 추가) | **NULL.** 오류가 아님. NULL이 끼면 나누는 수를 보기 전에 결과가 NULL로 정해진다. "NULL이 낀 산술은 NULL"(2절)이 0으로 나누기 규칙보다 먼저다. PostgreSQL도 같다. 모르는 값을 0으로 나눈 결과는 여전히 "모른다"이기 때문이다 |

## 3. 타입 검사 (W5)

열 종류는 INTEGER, TEXT, BLOB 하나씩이고, 열 하나에는 그 종류 값 또는 NULL만 있다(0017). 리터럴의 타입도 보면 안다. 그래서 **식 전체의 타입은 행을 하나도 읽기 전에 정해진다.** 계획 단계(6절)가 식을 한 번 훑으며 검사하고, 오류가 나면 아무 행도 읽지 않는다. 빈 표에서도 같은 오류가 난다.

| 식 | 타입 규칙 | 어기면 |
|---|---|---|
| 열 | 그 열의 타입 | |
| 리터럴 | INTEGER/TEXT/BLOB, `NULL`은 "어느 타입과도 맞음" | |
| `a + b` 등 산술, 단항 `-` | 양쪽 INTEGER(또는 NULL) → INTEGER | 타입 오류 |
| `a = b` 등 비교, `BETWEEN`, `IN` | 모든 피연산자가 값 식이고, NULL이 아닌 것끼리 같은 타입 → 참·거짓 | 타입 오류 |
| `x IS [NOT] NULL` | 값 식 → 참·거짓 | 타입 오류 |
| `AND`, `OR`, `NOT`, WHERE 자체 | 참·거짓 식만 | 타입 오류 (`WHERE id`, `WHERE id + 1`, `WHERE NULL`, `(a = 1) = (b = 2)`) |

| 선택지 | `WHERE age = 'ten'` | 장점 | 단점 |
|---|---|---|---|
| **A. 실행 전 오류** | 오류 | 0017의 `WHERE id = 'a'`와 같음. 오타를 바로 알려줌. 타입 오류가 행 내용에 따라 달라지지 않음 | 없음에 가까움 |
| B. 거짓(또는 모름)으로 보고 0행 | 0행 | 실행이 멈추지 않음 | 오타가 "결과 없음"으로 숨음 |
| C. SQLite식 타입 간 순서 | 0행 | SQLite와 같음 | 열에 타입이 하나뿐인 Oakdb에서는 쓸 데가 없음 |

**결정 A.** 오류 종류:

| 경우 | 오류 |
|---|---|
| 비교에서 한쪽이 **열 그대로**이고 다른 쪽 타입이 다름 (`age = 'ten'`, `id IN (1, 'a')`) | 기존 `TypeMismatch { column, expected, found }` (0017 테스트와 같은 모양) |
| 그 밖의 타입 오류 (`name + 1`, `WHERE id`, `id + 1 = 'a'`) | 새 종류 `SqlError::Type(String)`. 무엇이 어긋났는지 문장으로. #34가 다듬는다 |

같은 타입끼리의 순서는 **키 인코딩의 바이트 순서와 같아야 한다**(범위와 거르기가 같은 답을 내려면).

| 타입 | 비교 | 키 인코딩 순서와 같은가 |
|---|---|---|
| INTEGER | i64 크기 | 같음 (부호 비트 뒤집기, 0017 2-1) |
| TEXT | UTF-8 바이트 사전순 (= Rust `String`의 `Ord`). 대소문자·언어별 정렬 없음 | 같음 (`00` 이스케이프 + 끝 표시) |
| BLOB | 바이트 사전순 | 같음 |

## 4. 어떤 조건을 범위 조회로 바꾸나 (W6)

원칙 하나: **범위는 넉넉하게, 판정은 정확하게.** 범위는 "어디를 훑을지"만 줄이고, 행마다 WHERE 식 전체를 다시 확인한다. 그러면 범위가 필요보다 넓어도 결과는 맞다(느릴 뿐). 틀릴 수 있는 경우는 범위가 **좁아서 맞는 행을 빠뜨릴 때**뿐이고, 이것을 8절의 속성 테스트가 잡는다.

| 선택지 | 범위로 쓰는 것 | 결정 |
|---|---|---|
| **A. 맨 위 AND의 기본 키 조건** | 맨 위 AND들로만 묶인 기본 키 조건. 여러 개면 교집합 | **결정** |
| B. A + 기본 키 OR를 여러 범위로 | `id = 1 OR id = 5`, `id < 3 OR id > 90` | 나중에 |
| C. 일반 정규화 (NOT 밀기, OR-AND 펼치기) | `NOT (id < 5)`도 | 과함 |

### 범위가 되는 조건

"상수"는 **열이 없는 값 식**이다(`5`, `3 + 4`, `-(2 * 3)`). 계획 때 행 없이 계산한다(접기).

| 조건 (맨 위 AND 안, NOT 없이) | 범위 |
|---|---|
| `pk = c`, `pk < c`, `pk <= c`, `pk > c`, `pk >= c` | 5절 표 |
| `c < pk` 처럼 상수가 왼쪽 | 뒤집어서 `pk > c` |
| `pk BETWEEN c1 AND c2` | `[c1 포함, c2 포함]` |
| `pk IN (c1, c2, ...)` | `[가장 작은 ci 포함, 가장 큰 ci 포함]`. NULL인 `ci`는 빼고 봄(같을 수 없으므로). 사이의 다른 키도 읽지만 거르기가 정확히 고름 |

**IN을 [최소, 최대] 범위 하나로**(사용자가 맡긴 선택): 선택지는 (가) 범위로 안 씀, (나) [최소, 최대] 하나, (다) 값마다 한 점씩 여러 범위. (다)는 B와 같은 "여러 범위" 기계가 필요하다. (나)는 `IN (1, 2, 3)`처럼 값이 몰려 있으면 (다)와 거의 같고, `IN (1, 1000000)`처럼 퍼져 있어도 표 전체보다 나쁘지 않다. **(나)로 정한다.** 여러 범위는 B와 함께 다시 본다.

### 범위에 쓰지 않는 것 (전부 거르기에서는 확인함)

| 조건 | 이유 |
|---|---|
| `pk != c`, `pk NOT BETWEEN`, `pk NOT IN` | 범위 둘 이상이 필요 — B의 일 |
| 상수가 NULL로 계산됨 (`pk = NULL`, `pk > 1 + NULL`) | 늘 모름이라 행이 없다. 범위를 비워도 되지만 거르기가 이미 0행을 냄(9절 Q2) |
| 상수 계산이 오류 (`pk > 9223372036854775807 + 1`) | 계획 때 오류를 내면 빈 표에서도 오류가 나서 "모든 행을 계산해도 오류 없으면…" 약속(2-2절)이 흐려진다. 범위에 쓰지 않고 거르기에 맡긴다(행이 있으면 거기서 오류) |
| `pk + 1 > 5`, `pk = other_col` | 기본 키가 식 안에 들어 있거나 상대가 행마다 다름. "간단하면만 접기"의 경계: **기본 키는 열 그대로, 상대는 상수**일 때만 |
| OR·NOT 안의 기본 키 조건 | A의 범위 밖 |

## 5. 범위의 양 끝 (W7)

엔진의 `txn.scan`은 양 끝을 `Bound::Included(키)`, `Bound::Excluded(키)`, `Bound::Unbounded`로 받는다(#17, Java `subMap(from, fromInclusive, to, toInclusive)`와 같음). 0017의 기본 키 인코딩은 **바이트 순서 = 값 순서**이므로, 값을 키로 바꾸고 포함/제외는 **그대로** 넘기면 된다.

표 `T`의 행 키는 `[01][T u32 BE][인코딩한 기본 키]`다. 기본 키 조건이 한쪽 끝을 정하지 않으면 그 끝은 표의 끝이다.

| 조건 | 시작 | 끝 |
|---|---|---|
| (기본 키 조건 없음) | 표 시작 = `Included([01][T])` | 표 끝 = `Excluded([01][T+1])` |
| `id = v` | `Included(키(v))` | `Included(키(v))` |
| `id > v` | `Excluded(키(v))` | 표 끝 |
| `id >= v` | `Included(키(v))` | 표 끝 |
| `id < v` | 표 시작 | `Excluded(키(v))` |
| `id <= v` | 표 시작 | `Included(키(v))` |

**교집합** (AND로 여러 개): 시작은 더 큰 쪽, 끝은 더 작은 쪽. 키가 같으면 `Excluded`가 더 좁다. 비교는 인코딩한 **바이트로** 한다. 0017의 순서 보존 속성(속성 테스트로 증명됨)이 값 순서와 같음을 보장하므로 타입마다 따로 비교하지 않는다. `id > 5 AND id < 3`처럼 시작이 끝보다 뒤면 엔진이 빈 범위로 다룬다(`empty_if_backwards`).

### i64 끝값과 넘침

| 선택지 | `id > i64::MAX` | 결정 |
|---|---|---|
| **A. 포함/제외를 그대로 넘김** | `Excluded(FF×8)` → 그 뒤 표 안에 키 없음 → 0행. +1 계산이 없어 넘침 자체가 없음 | **결정** |
| B. 모두 포함 범위로 바꿈(`> v` → `>= v+1`) | `i64::MAX + 1` 넘침 → 특별 처리. TEXT에는 "다음 값"이 깔끔하지 않음 | |

| 식 | 결과 | 왜 |
|---|---|---|
| `id > 9223372036854775807` | 0행 | `Excluded(FF×8)` |
| `id >= 9223372036854775807` | i64::MAX 행 하나(있으면) | `Included(FF×8)` |
| `id < -9223372036854775808` | 0행 | `Excluded(00×8)` |
| `id > 9223372036854775808` | 문법 오류 | 리터럴이 i64에 안 들어감(0017 6절 그대로). 9절 Q3 |
| `id > 9223372036854775807 + 1` | 행이 있으면 넘침 오류, 없으면 0행 | 4절: 접기 실패는 범위에 안 씀 |
| `name > 'a'` | `'a\0'`, `'ab'`, … | `Excluded(61 00 00)`. 끝 표시 덕분에 `'a'` 하나만 정확히 빠짐 |

## 6. 계획 단계와 식의 모양 (W8)

```
SQL 문자열 → 렉서 → 파서 → Statement::Select { filter: Option<Expr> }     (열 이름, 타입 없음)
                              ↓
               planner::plan(&Table, Option<Expr>) → Plan { range, filter: Option<Pred> }
                 · 열 이름 → 열 번호 (없는 열 = NoSuchColumn)
                 · 타입 검사 (TypeMismatch / Type)       ← 여기까지 행을 하나도 읽지 않음
                 · 맨 위 AND의 기본 키 조건 → 범위 (상수는 접기)
                              ↓
               executor: txn.scan(범위의 키) → 행 디코딩 → filter가 참인 행만
```

### 계획을 어디에 두나

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 실행기의 `select` 함수 안 | 파일이 안 늘어남 | 범위 계산을 테스트하려면 DB를 열어야 함. #33이 복사하거나 꺼내야 함 |
| **B. `planner.rs`의 순수 함수** | 엔진·트랜잭션 없이 `(표 정보, 식) → (범위, 거르기)`라 단위 테스트가 쉬움. #33이 그대로 부름 | 모듈 하나 늘어남 |

**결정 B.** 오류(없는 열, 타입)가 모두 계획에서 나므로 "타입 오류면 아무것도 읽지 않는다"가 구조로 보장된다.

### 식의 모양 (Rust)

처음 추천은 `Expr<C>` 하나를 열 이름·열 번호로 함께 쓰는 것이었다. D(산술)가 들어오며 피연산자가 아무 식이 되자, 값 식과 참·거짓 식을 **타입으로 나누는** 쪽이 낫다고 보고 고쳤다.

```rust
// 파서가 만드는 것: 열 이름, 타입을 모름. 괄호 안이 값인지 참·거짓인지 아직 모른다.
enum Expr {
    Literal(Value), Column(String), Neg(Box<Expr>),
    Arith { op: ArithOp, left: Box<Expr>, right: Box<Expr> },
    Compare { op: CompareOp, left: Box<Expr>, right: Box<Expr> },
    IsNull { operand: Box<Expr>, negated: bool },
    Between { operand: Box<Expr>, low: Box<Expr>, high: Box<Expr>, negated: bool },
    In { operand: Box<Expr>, list: Vec<Expr>, negated: bool },
    Not(Box<Expr>), And(Box<Expr>, Box<Expr>), Or(Box<Expr>, Box<Expr>),
}

// 계획이 만드는 것: 열 번호, 타입 검사를 통과한 것만.
enum Scalar { Literal(Value), Column(usize), Neg(Box<Scalar>), Arith { op, left, right } }
enum Pred {
    Compare { op, left: Scalar, right: Scalar },
    IsNull { operand: Scalar, negated: bool },
    Between { operand: Scalar, low: Scalar, high: Scalar, negated: bool },
    In { operand: Scalar, list: Vec<Scalar>, negated: bool },
    Not(Box<Pred>), And(Box<Pred>, Box<Pred>), Or(Box<Pred>, Box<Pred>),
}
enum Truth { True, False, Unknown }
```

| 고를 점 | 선택지 | 결정과 이유 |
|---|---|---|
| 값 식과 참·거짓 식 | 한 열거형 / **`Scalar`와 `Pred` 둘** | **둘.** `(a = 1) + 2`나 `WHERE id`가 타입으로 아예 만들어지지 않는다(만들 수 없는 상태는 표현하지 않기). 계산 함수가 "참·거짓 식의 값은?" 같은 닿을 수 없는 경우를 다루지 않아도 된다 |
| 열 이름과 열 번호 | 행마다 이름 찾기 / **계획 때 번호로** | 번호. 행마다 문자열을 비교하지 않고, 없는 열은 행을 읽기 전에 오류 |
| AND/OR | **두 갈래(`Box` 둘)** / 여러 갈래(`Vec`) | 두 갈래. 파서가 자연스럽게 만듦. 맨 위 AND 모으기는 재귀 함수 하나 |
| 참·거짓·모름 | `Option<bool>` / **`enum Truth`** | `Truth`. `None`이 "모름"인지 "없음"인지 헷갈리지 않음 |
| 저장된 행의 값 타입이 열과 다를 때 | 패닉 / **`Corrupt` 오류** | 행 디코딩은 카탈로그 타입을 모른다. 타입 검사를 통과한 식이라도 망가진 행에서는 다를 수 있으므로 패닉 대신 오류 |

`Plan`의 범위는 값으로 둔다: `(Bound<Value>, Bound<Value>)`, `Unbounded`는 "표의 끝". 실행기가 키로 바꾼다. 단위 테스트가 `(Excluded(Integer(5)), Unbounded)`처럼 읽기 쉽다.

### 뒤 티켓과 맞추기

| 티켓 | 이 설계에서 쓰는 것 |
|---|---|
| #33 UPDATE/DELETE | 같은 `plan`. `scan`은 트랜잭션을 `&`로 빌리고 `put`/`delete`는 `&mut`가 필요해 Rust가 **"맞는 키를 먼저 모으고, 그다음 고치기"**를 강제한다. 이것이 고치는 도중 고친 행을 다시 만나는 문제(할로윈 문제)도 막는다. `SET x = x + 1`은 `Scalar`를 그대로 쓴다. **리뷰 P3(검증 후 추가)**: 지금 `select`는 훑기·거르기·고르기를 한 반복문에서 하고 엔진 키를 버린다. #33에서 `matching_rows(txn, table, plan) -> Vec<(키, 행)>`로 꺼내 SELECT와 함께 쓴다. 쓰는 곳이 하나뿐인 지금 꺼내면 미리 만든 추상화가 되므로 미룬다 |
| #34 타입 오류 | 타입 검사가 `plan` 한곳에 있음. **리뷰 P4(검증 후 추가)**: `Type(String)`, `Arithmetic(String)`은 문자열뿐이라, 오류를 종류로 가르려면 지금은 메시지 글자에 기대야 한다. #34에서 구조를 넣는다. 예: `Arithmetic { kind: Overflow \| DivisionByZero }`, `Type { expected, found }` |
| #35 BEGIN/COMMIT | `plan`은 트랜잭션을 모르므로 바뀔 것 없음. 읽기는 충돌 판정에 들어가지 않으므로(0016, 쓰기-쓰기만) 범위 SELECT는 충돌을 내지 않음 |

## 7. 기존 길 흡수와 WHERE 없는 SELECT (W9)

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. `pk = v`도 양 끝이 같은 범위 조회** | 실행 길이 하나 | `get`보다 아주 조금 느릴 수 있음(커서 하나 만듦) |
| B. 범위가 한 점이면 `get` 지름길 | 한 점 조회가 가장 빠름 | 길이 둘이라 두 길이 같은 답을 내는지 따로 확인해야 함 |

**결정 A.** 둘 다 B+Tree를 한 번 내려가는 일이라 차이는 작다고 예상한다. 검증 단계 A/B 벤치마크(8절)로 확인한다.

**검증 결과 (PR #69, 실험 0014)**: 예상과 달리 한 점 조회가 문장당 **약 0.5 µs(약 20%) 느려졌다.** 있는 키는 2.5 → 3.0 µs, 없는 키는 2.2 → 2.7 µs, 비율 1.215 [1.127, 1.281]이다. 커밋 한 번(약 3 ms)에 비하면 아주 작은 값이다. **사용자는 이것을 받아들였다.** `get` 지름길은 두지 않는다.

달라지는 겉모습:

| 전 (0017) | 후 |
|---|---|
| `WHERE name = 'kim'` → 지원 안 함 | 거르기로 실행 |
| `WHERE id > 1` → 지원 안 함 | 범위 조회 |
| WHERE 없는 SELECT → 지원 안 함 | **표 전체** |
| `WHERE id = 1 AND name = 'a'` → 지원 안 함 | 실행 |
| `pk = <엔진 키 길이보다 긴 글자>` → `Engine(KeyTooLarge)` | **0행.** `get`은 키 길이를 검사하지만 `scan`은 하지 않음(9절 Q5) |
| 결과는 0행 또는 1행 | 여러 행, 지금은 기본 키 순서(9절 Q4) |

기존 테스트 중 위 "지원 안 함"을 확인하던 것(`tests/sql.rs`, `tests/blind_sql.rs`)은 새 범위 밖 예(`LIKE`, `a < b < c`, `ORDER BY`)로 바꾼다. 사용자가 허락했다.

## 8. 테스트 계획 (W10)

B+Tree를 `BTreeMap`과 같은 동작을 하는지 무작위로 비교했듯, SQL도 **"전부 읽고 하나씩 거르는" 단순한 모델**과 비교한다.

| 테스트 | 무엇을 |
|---|---|
| 모델 비교 속성 테스트 (proptest, `tests/where_model.rs`) | 무작위 행(작은 값 + i64 끝값, NULL 자주)과 무작위 식(비교·IS NULL·BETWEEN·IN·NOT·AND·OR·산술, 타입에 맞게 생성)을 **SQL 문자열로 찍어** `execute`. 모델은 테스트 안에 따로 쓴 3값 평가기로 `BTreeMap`의 모든 행을 거른다. 모델은 **모든 행에서 모든 부분식을 다 계산**한다(지름길 없음). 모델이 오류 없이 끝나면 Oakdb 결과가 정확히 같아야 하고, 모델이 오류면 Oakdb는 `Arithmetic` 오류이거나 성공이어야 한다(2-2절 약속). INTEGER 기본 키 표와 TEXT 기본 키 표 둘 다 |
| 계획 단위 테스트 (`planner.rs`) | 완료 기준 1 "범위 조회로 실행된다"를 직접 확인: `id > 5 AND name = 'a'` → `(Excluded(5), 끝)`, `id BETWEEN 2 AND 4`, `id IN (7, 3, 5)` → `[3, 7]`, `id > 3 + 4` → `Excluded(7)`, `5 < id` 뒤집기, 교집합의 포함/제외 동점, `id = 1 OR id = 5` → 표 전체, 접기 오류 → 표 전체 |
| 파서 단위 테스트 | 1절 우선순위 표, `!=`와 `<>`, 괄호, 음수 리터럴, 비교 연결·`LIKE` → 지원 안 함, 닫는 괄호 없음 → 문법 오류 |
| `tests/sql.rs` | 2절 NULL 표(`NOT IN`과 NULL 포함), 3절 타입 오류(빈 표에서도), 2-2절 넘침·0 나누기, WHERE 없는 SELECT, 7절 바뀐 겉모습 |
| 벤치마크 (검증 단계, `docs/benchmarks/`) | `pk = v`의 `get`(main) 대 한 점 범위 조회(이 브랜치) A/B, A/A 대조 포함. 행 수를 늘려도 좁은 범위 조회의 시간이 거의 그대로인지 |

## 9. 작은 질문

| # | 질문 | 결정 | 이유 |
|---|---|---|---|
| Q1 | 예약어 | `AND`, `OR`, `NOT`, `IS`를 더함. `BETWEEN`, `IN`, `LIKE`는 예약하지 않고 연산자 자리에서만 알아봄 | 앞 넷은 문법을 가름. 뒤 셋은 열 이름을 빼앗을 이유가 없음 |
| Q2 | `pk = NULL`이 맨 위 AND에 있으면 범위를 비울까 | 비우지 않음(범위에 안 씀) | 거르기가 이미 0행을 냄. 규칙 하나 줄이기 |
| Q3 | i64 밖 정수 리터럴 | 0017대로 문법 오류 | #34에서 다시 볼 수 있음 |
| Q4 | 결과 행 순서 | 지금은 기본 키 순서로 나오지만 **약속하지 않음**(ORDER BY가 없으므로). 모델 테스트는 정렬 후 비교 | 나중에 여러 범위가 와도 깨지지 않게 |
| Q5 | 긴 키로 찾을 때 `KeyTooLarge` 대신 0행 | 0행 | 그런 키의 행은 존재할 수 없음. #34 질문 하나가 정리됨 |
| Q6 | 표 끝 `[01][T+1]`에서 `T+1` 넘침 | 카탈로그는 `u32::MAX`를 주지 않지만 계산은 `checked_add`, 넘치면 `[02]` | 다른 파일의 암묵적 약속에 기대지 않게 |
| Q7 | 결과를 모두 `Vec`에 모으기 | 그대로(0017 `Output::Rows`) | 큰 표의 스트리밍은 네트워크 서버(ADR 0005) 때 |
| Q8 | `WHERE TRUE`, `WHERE flag` | 타입 오류 | 불리언 타입이 없음(INTEGER/TEXT/BLOB/NULL) |
| Q9 | TEXT 대소문자 | 구별(바이트 비교) | 키 인코딩 순서와 같아야 함(3절) |
