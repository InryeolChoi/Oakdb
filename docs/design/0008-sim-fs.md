# 0008. 가짜 파일시스템 — 설계

이슈 #20. 정전 안전 구간(08~12)의 첫 티켓이다. 엔진이 쓰는 파일 출입구(`Fs` 트레이트)를 메모리 속 **가짜 디스크**로 바꿔 끼운다. 이 가짜 디스크는 원하는 순간에 정전을 일으키고, 무엇이 살아남을지를 **시드**로 정한다. 09번 정전 실험부터 12번까지 모두 이 도구 위에서 돈다.

**비유**: 책상 위 메모지는 운영체제의 캐시이고, 금고 속 장부는 디스크다. `sync`는 메모를 금고에 넣는 일이다. 정전은 바람이 불어 책상 위 메모가 날아가는 일이다. 어떤 메모는 통째로 날아가고, 어떤 메모는 반만 찢겨서 남는다. 금고 속 장부는 그대로다. 어떤 메모가 날아갈지는 시드라는 주사위가 정한다. 같은 시드면 매번 같은 메모가 날아간다.

```
         쓰기 ──▶ 책상 위 (읽기는 여기를 본다)
                    │ sync
                    ▼
                 금고 (정전에도 남음)

정전 = 책상 위 변경 하나하나마다 주사위:
  남음 │ 사라짐 │ 찢김 (512바이트 칸마다 다시 주사위)
```

## 사용자가 정한 것

| # | 질문 | 결정 |
|---|---|---|
| 1 | 정전 때 sync 안 된 쓰기는 | **쓰기마다 남음·사라짐·찢김.** 찢기면 그 쓰기가 닿은 512바이트 칸마다 새 내용이 남을지 정한다. 쓰기마다 따로 정하므로 "나중 쓰기는 남고 먼저 쓰기는 사라짐"(디스크가 순서를 바꿈)도 나온다 |
| 2 | 새 파일·디렉터리 | **부모 디렉터리를 `sync_dir`하기 전에 정전이 나면 파일이 사라질 수 있다.** 디렉터리는 `create_dir_all`이 sync까지 하므로(트레이트 약속) 사라지지 않는다. rename은 트레이트에 없으니 WAL 티켓에서 필요해지면 더한다 |
| 3 | 정전을 일으키는 방법 | **`crash(seed)`** (지금 끊고 다시 켬)와 **`fail_after(n)`** (디스크를 바꾸는 작업 n번 뒤에 끊김, 커밋 도중 정전) |
| 4 | 어디에 둘까 | **크레이트 안의 공개 모듈 `oakdb::fs::sim`.** 의존성 없음. 09번 실험 도구가 예제로 만들어져도 쓸 수 있다 |
| 5 | "같은 테스트를 양쪽에서" | **파일시스템 계약 테스트(처음 9개, 리뷰 뒤 12개)와 정답 모델 테스트를 진짜·가짜 양쪽에서** 돌린다 |

버린 선택지와 이유:

| 결정 | 버린 것 | 이유 |
|---|---|---|
| 1 | sync 안 된 쓰기는 전부 버림 | 너무 친절하다. 실제 디스크는 일부만 쓰거나 순서를 바꾸고, 반쯤 쓴 페이지(실험 0006의 2번)도 만든다 |
| 3 | `crash`만 | 작업과 작업 사이에서만 끊긴다. 09번은 커밋 도중의 아무 시점에서나 끊어야 한다 |
| 4 | 테스트 폴더 안의 도우미 | 예제와 벤치마크에서 쓸 수 없다 |
| 5 | 기존 통합 테스트를 모두 두 번 | 테스트 대부분이 진짜 파일을 직접 고친다(체크섬 테스트 등). 고칠 곳이 많고 얻는 것이 적다 |

## 1. 쓰는 법

```rust
let fs = SimFs::new();                      // 빈 디스크
let db = Db::open_with(fs.clone(), "/oak")?; // 복제본은 같은 디스크를 나눠 쓴다
// ... 커밋 ...
drop(db);
fs.crash(42);                                // 정전, 시드 42로 무엇이 남을지 정함, 다시 켬
let db = Db::open_with(fs.clone(), "/oak")?; // 복구 확인
```

```rust
fs.fail_after(5);   // 디스크를 바꾸는 작업 5번은 성공, 6번째부터 모두 실패
txn.commit();       // 커밋 도중에 오류
fs.crash(7);
```

`exists(path)`는 트레이트 밖의 도우미다. "디렉터리 sync 전에 만든 파일이 정전 뒤 **사라졌는지**"를 보려면 필요하다. `open`은 없는 파일을 새로 만들어 버리기 때문이다.

## 2. 파일 하나가 가진 것

| 필드 | 뜻 |
|---|---|
| `now` | 읽기가 보는 내용 (책상 위) |
| `synced` | 마지막 `sync_data` 때의 내용 (금고) |
| `waiting` | 그 뒤의 쓰기와 길이 변경, 오래된 순 |
| `entry_synced` | 부모 디렉터리를 sync해서 "이 파일이 있음"이 금고에 들어갔나 |
| `locked_by` | 잠금을 가진 손잡이 번호 |

## 3. 정전 (`crash(seed)`)

1. 파일을 경로 순서로 하나씩 본다. 순서가 정해져 있어야 같은 시드가 같은 결과를 낸다.
2. `entry_synced`가 아니면 동전을 던져 파일을 통째로 지울지 정한다.
3. 남은 파일은 `synced`에서 시작해 `waiting`을 순서대로 다시 적용한다. 변경마다 주사위를 던진다.
   - 쓰기: 남음 / 사라짐 / 찢김 중 하나 (각 1/3). 찢기면 512바이트 칸마다 동전을 던진다. 칸은 **파일 맨 앞부터** 센다. 그래서 100~1100바이트 쓰기는 0~512, 512~1024, 1024~1536 세 칸에 걸친다. 끝을 넘는 쓰기가 찢기면 파일 길이는 마지막으로 남은 칸의 끝까지다.
   - 길이 변경: 남음 / 사라짐.
4. 결과를 새 `now`이자 `synced`로 삼고, 잠금은 모두 푼다.
5. 부팅 번호를 올린다. 정전 전에 연 손잡이는 이 번호가 달라서 모든 호출이 오류를 낸다. 프로세스가 죽은 것과 같다.

**512바이트인 이유**: 디스크가 한 번에 통째로 쓰는 가장 작은 단위가 섹터이고, 오래된 디스크와 많은 SSD가 512바이트로 보고한다. 4KiB 섹터 디스크라면 한 페이지(4KiB) 안에서는 찢기지 않는다. 512로 잡으면 그런 디스크보다 더 험하게 시험하는 셈이라 괜찮다.

**주사위**: 외부 crate(`rand`) 대신 SplitMix64를 15줄로 직접 썼다. crate 버전이 바뀌어도 같은 시드는 언제나 같은 디스크를 낸다. 공개된 시험값(시드 1234567)으로 단위 테스트를 둔다.

## 4. 커밋 도중 정전 (`fail_after(n)`)

- **세는 것**: 디스크를 바꾸는 호출만 센다. 쓰기, 길이 변경, `sync_data`, `sync_dir`, `open`(이미 있는 파일을 열어도), `create_dir_all`이 해당한다.
- **세지 않는 것**: 읽기, 크기 확인, 잠금. 그래서 `n`은 "몇 번째 쓰기나 sync에서 끊기나"를 뜻한다.
- **끊기는 순간**: n번 뒤에 오는 첫 "바꾸는 호출"이 전원이 꺼진 것을 발견하고 실패한다. 그 호출은 디스크에 **전혀 닿지 않는다**(찢기지도 않는다). 그 전까지는 읽기가 된다. 그래서 `fail_after(0)`은 "지금 끊음"이 아니라 "다음 바꾸는 호출에서 끊음"이다(리뷰 결정 4).
- **끊긴 뒤**: 읽기까지 모든 호출이 실패하고, `crash(seed)`를 불러야 다시 켜진다. 09번은 `n`과 `seed`를 함께 골라 "커밋의 아무 시점 + 무엇이 남았나"를 만든다.

## 5. 정전 전에는 진짜와 똑같이

계약 테스트(`tests/fs_contract.rs`)가 진짜·가짜 양쪽에서 같은 내용을 확인한다. 처음 9가지는 다음과 같다.

- 쓰고 sync하고 다시 열어 읽기
- sync 전에도 읽힘
- 끝을 넘어 읽으면 `UnexpectedEof`
- 다시 열어도 내용 유지
- 없는 디렉터리의 파일은 `NotFound`
- `create_dir_all`이 부모까지 만듦
- 파일이 길을 막으면 실패
- 잠금
- `set_len`

예전 `fs.rs`의 단위 테스트 6개는 여기로 옮겼다. 리뷰 뒤에 진짜와 다르던 경계 3가지를 맞추고 계약에 더했다(결정 3). 모두 12가지다.

- 끝 너머에서 길이 0 읽기는 성공
- 파일이 닿을 수 없는 큰 offset은 panic 없이 오류
- 부모가 파일이면 `NotADirectory`

**다른 점 하나는 남겼다.** 진짜 파일은 큰 offset에 쓰면 빈 부분을 디스크에 두지 않는다(sparse). 가짜 디스크는 메모리에 0으로 채운다. 엔진은 파일 끝에만 덧붙이므로 문제가 없다.

- **무작위 정전 실험과 "응답한 커밋은 모두 있다" 검사**: 09번(#21). 08은 도구만 만든다.
