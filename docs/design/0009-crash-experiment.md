# 0009. 정전 실험 도구 — 설계

이슈 #21. 08번에서 만든 가짜 디스크로 **충돌 시험**을 한다. 시드 하나로 "작업 → 커밋 도중 아무 데서나 정전 → 다시 열기 → 판정"을 재현하고, 지금 설계가 깨지는 시드를 모아 기록한다. 이번 티켓은 고치지 않는다. 고치는 일은 10번(WAL)이 한다. 결과는 `docs/experiments/0008-power-cuts.md`에 있다.

**비유**: 자동차 충돌 시험. 08번에서 시험장(가짜 디스크)을 지었고, 이번에는 차(엔진)를 여러 각도로 부딪쳐 어디가 찌그러지는지 사진을 남긴다. 에어백(WAL)은 다음 티켓에서 단다.

## 사용자가 정한 것

| # | 질문 | 결정 |
|---|---|---|
| 1 | 도구를 어디에 | **예제 `crash_sim`** (한 시드 재현, 여러 시드 훑기, 모든 시점 훑기) + 찾은 시드는 `#[ignore = "needs the WAL (#22)"]` 회귀 테스트. CI는 초록으로 두고, 10번에서 `ignore`만 떼면 "고쳐졌다"를 증명한다 |
| 2 | 정전 시점 고르기 | **`SimFs`에 작업 카운터(`ops()`)를 더하고**, 연습 실행으로 작업 수를 센 뒤 그 안에서 고른다. 작은 작업은 **모든 시점**을 훑는다 |
| 3 | 작업 내용 | **시드로 만드는 무작위 작업.** 커밋 1~30개, 커밋마다 put·delete 1~8개, 값의 1/6은 부록 페이지에 들어가는 긴 값. 엔진 공개 API만 쓴다 |
| 4 | 시드 하나로 재현 | 시드 하나에서 **작업 시드, 정전 시점, 정전 시드**를 SplitMix64로 뽑는다 |
| 5 | 무엇을 기록하나 | 1만 개 시드의 결과를 종류별로 세고, 종류마다 **가장 짧은 재현 시드**를 골라 어느 페이지가 남고 사라져서 깨졌는지 설명한다 |

## 1. 판정: 무엇을 약속으로 보나

스펙 #12의 "응답한 커밋은 모두 있고, 응답하지 않은 커밋은 전부 있거나 전부 없다"를 그대로 옮겼다. 다시 연 DB에서 키 0~199를 **훑기(scan)와 하나씩 읽기(get) 두 가지로** 읽는다. 둘이 다르면 그것도 실패다.

| 판정 | 뜻 |
|---|---|
| `Intact` | 응답한 커밋은 모두 있고, 정전에 걸린 커밋은 전부 있거나 전부 없음 |
| `OpenFailed` | 다시 열기가 오류 |
| `Panicked` | 다시 열거나 읽다가 panic (실험 중에 더했다, 3절) |
| `ReadFailed` | 열렸지만 읽기가 오류이거나 scan과 get이 다름 |
| `LostAcknowledged` | 정전에 걸린 커밋이 건드리지 않은 키가 응답한 값과 다름 |
| `WrongValue` | 건드린 키가 옛 값도 새 값도 아님 |
| `HalfCommit` | 건드린 키가 옛 값과 새 값으로 섞임 |

키마다 "응답한 상태의 값 / 정전에 걸린 커밋까지 들어간 상태의 값 / 실제 값"을 비교한다. 여러 문제가 함께 있으면 나쁜 쪽(`LostAcknowledged` > `WrongValue` > `HalfCommit`)을 보고한다. 판정기는 순수 함수(`judge`)라서 가짜 상태로 단위 테스트를 했다.

## 2. 가짜 디스크에 더한 것

| 더한 것 | 왜 |
|---|---|
| `ops()` | 지금까지 성공한 "디스크를 바꾸는 작업" 수. `fail_after`와 같은 기준으로 센다. 연습 실행으로 작업 하나의 전체 길이를 알아서 정전 시점을 그 안에서 고른다 |
| `crash()`가 `CrashReport`를 돌려줌 | sync 안 된 쓰기 하나하나가 남았는지, 사라졌는지, 찢겼는지(칸마다)와 사라진 파일. "왜 깨졌나"를 페이지 단위로 설명하는 재료다 |

`Landing`이 공개되면서 `Torn`이 어느 칸이 남았는지(`sectors`)를 들고 다닌다. 주사위를 굴리는 순서는 08번과 같아서, 같은 시드는 08번 때와 같은 디스크를 낸다.

## 3. 실험 중에 바뀐 것

- **`Panicked` 판정.** "응답한 커밋은 사라지지 않는다"를 상시 테스트(시드 0~1999)로 두었더니, 엔진이 debug 빌드에서 panic했다. 처음 훑기는 release 빌드로 돌려서 이 경우를 못 봤다. 다시 열기를 `catch_unwind`로 감싸고 판정 종류를 하나 더했다. panic은 오류보다 나쁘다. DB를 쓰는 프로그램이 멈추기 때문이다.
- **"만드는 도중"과 "커밋 도중"을 나눠 셈.** 첫 훑기에서 열기 실패가 절반 가까이 나왔다. 그중 새 DB를 만드는 도중의 정전은 원인이 달라서 따로 셌다.
- **키별 비교 출력.** 반쪽 커밋을 설명하려고 `one` 명령이 키마다 옛 값 / 새 값 / 실제 값을 보여 준다.

## 4. 테스트

이번에도 **실패하는 테스트를 먼저 커밋했다**(8b3b290). 새 테스트 8개가 모두 실패하는 것을 본 다음 구현했다. 회귀 파일 같은 부산물이 없는지도 `git status`로 확인했다(08 회고).

| 파일 | 무엇을 |
|---|---|
| `tests/sim_fs.rs` (+2) | `ops()`가 `fail_after`와 같이 셈(실패한 작업은 안 셈, 정전 뒤에도 이어 셈), 정전 보고서가 실제 디스크와 칸 단위로 맞음 |
| `tests/crash.rs` (7) | 판정기가 옛·새 상태를 받아들이고 깨지는 종류마다 이름을 붙임, 같은 시드는 같은 경우와 같은 결과, 작업이 분할과 부록 페이지를 일으킴, 정전 없으면 모두 있음, 만드는 도중 맨 처음 끊기면 잃는 것 없음, **시드 0~1999에서 응답한 커밋이 사라지거나 없던 값이 생기지 않음** |
| `tests/crash.rs` (ignore 8) | 깨지는 방식마다 가장 짧은 시드 7개 (WAL을 기다림) + panic 시드 1개 (결정을 기다림) |

**변이 검사.** `sim.rs`에 버그 14개(08번의 12개 + `ops` 잘못 셈, 보고서가 찢긴 칸을 거꾸로 적음)를 심었고 모두 잡혔다. `python3 docs/experiments/scripts/mutants.py sim`.
