# 0027. 타입 검사와 오류 종류 — 설계

이슈 #34. 완료 기준은 둘이다. ① 열 타입에 맞지 않는 값은 **타입 오류**로 거절한다. ② **문법 오류, 타입 오류, 미지원 기능 오류, 제약 위반**(기본 키 중복)이 서로 구분된다. 그리고 #31·#35·#37 검증에서 이 티켓으로 넘긴 숙제가 넷 있다(이슈 댓글, 0023 T11, 0025 Q2).

먼저 밝혀 둘 것: **타입 검사는 이미 거의 다 있다.** #31(0017)이 INSERT 값의 타입을, #33(0019 W5)이 WHERE 식의 타입을 행을 읽기 전에 검사하고, #36(0022)이 UPDATE SET을 같은 길로 검사한다. 그래서 이번 티켓의 몸통은 "검사를 새로 짠다"가 아니라 **오류에 제대로 된 이름표와 번호를 붙이고, 비어 있는 칸을 메우고, 그것을 약속(테스트)으로 굳히는 것**이다.

(문서 번호: 0025는 #37(티켓 25), 0026은 #18 설계, 0028은 티켓 26 설계가 쓴다. 이 문서는 0027.)

## 비유: 병원 접수처와 Spring의 예외 번역

**HTTP 상태 코드**를 떠올리면 쉽다. 404(없음), 409(충돌), 422(내용이 틀림), 500(서버 잘못)은 번호만 봐도 클라이언트가 할 일이 정해진다. 그리고 4xx는 "네가 고쳐서 다시", 5xx는 "내 잘못, 나중에 다시"처럼 **앞자리(범위)만 봐도** 대충 대응할 수 있다. Oakdb의 통신 오류 코드도 이미 이렇게 생겼다(`0x01–0x1F` 문장이 잘못됨, `0x20–0x3F` 엔진이 거절, `0x40–0x5F` 대화가 깨짐).

**Spring의 `DataAccessException` 계층**은 더 가까운 비유다. JDBC 드라이버는 DB마다 다른 오류 번호(SQLSTATE `23505`, MySQL `1062` …)를 던진다. Spring은 이것을 **"무엇을 해야 하나"로 번역**한다.

| Spring 예외 | 뜻 | 프로그램이 할 일 | Oakdb에서 |
|---|---|---|---|
| `BadSqlGrammarException` | SQL 문장이 틀림 | 코드를 고친다 | 문법 오류 `0x01` |
| `InvalidDataAccessApiUsageException` 류 | 이 DB가 못 하는 것 | 다른 방법을 쓴다 | 지원 안 함 `0x02` |
| `TypeMismatchDataAccessException` | 값의 타입이 틀림 | 입력을 고친다 | 타입 오류 `0x09` |
| `DuplicateKeyException` / `DataIntegrityViolationException` | 제약 위반 | 사용자에게 "이미 있음" | 기본 키 중복 `0x08` |
| `CannotAcquireLockException`, `OptimisticLockingFailureException` | 경쟁에서 짐 | **다시 시도** | 충돌 `0x20` |
| `DataAccessResourceFailureException` | DB가 아픔 | 운영자를 부름 | 엔진 멈춤 `0x26` 등 |

Java의 **checked exception**으로 보면, `SqlError` 열거형의 각 종류가 `catch` 블록 하나다. 종류가 너무 거칠면(모두 `Exception`) 프로그램이 대응을 못 하고, 너무 잘면(예외 클래스 50개) 아무도 다 잡지 않는다. 이번 설계의 핵심 질문은 **"몇 칸으로 나눌까, 그리고 그 칸을 통신 번호에 어떻게 옮길까"**다.

ft_malloc으로 치면, `malloc`이 실패를 `NULL` 하나로만 알리는 것(무엇이 잘못됐는지 모름)과 `errno`에 `ENOMEM`/`EINVAL`을 따로 남기는 것의 차이다. 지금 Oakdb는 타입 오류·산술 오류·트랜잭션 상태 오류를 통신에서 **모두 `0x1F`("위에 없는 문장 오류")** 하나로 보낸다. `errno`가 늘 `EUNKNOWN`인 셈이다.

## E1. 타입 검사는 언제 하나

**비유**: 택배 접수. ① 송장 글씨를 읽을 수 있나(파싱), ② 받는 주소가 실제로 있고 물건이 그 주소에 맞나(계획), ③ 배달 중에 상자가 터졌나(실행). 주소가 틀린 걸 배달 도중에 알면 이미 늦다.

| 선택지 | 무엇을 어디서 | 장점 | 단점 |
|---|---|---|---|
| A. 파싱 때 | 파서가 표 정보를 읽어 타입까지 봄 | 한 번에 끝 | 파서가 엔진·트랜잭션을 알아야 함. 0017 C1의 "파서는 순수 문자열 처리"가 깨짐. 트랜잭션 안에서 방금 만든 표(0023 T9)를 파서가 볼 수 없음 |
| **B. 지금처럼: 구조는 파싱, 타입은 계획, 값 오류만 실행** | 파서: 문법·지원 여부. 계획(`planner.rs`): 이름·타입 (행을 읽기 전). 실행: 넘침·0 나누기·중복 키·엔진 오류 | 0019 W5의 약속 "타입 오류는 **행 내용과 무관**, 빈 표에서도 같은 오류"가 그대로. 새 코드 없음 | 산술 오류만은 행에 따라 날 수도 안 날 수도 있음(0019 2-2에서 이미 받아들임) |
| C. 전부 실행 때 | 행을 하나씩 계산하다 막히면 오류 | 구현이 가장 단순 | 빈 표에서는 `WHERE name + 1 = 2`가 통과하고 행이 생기면 실패. 오타가 숨음 |

**추천 B.** 이미 그렇게 되어 있고, 이번 티켓은 이것을 **표로 문서화하고 속성 테스트로 굳힌다**(E13의 "빈 표와 찬 표에서 타입 오류가 같다").

| 단계 | 내는 오류 |
|---|---|
| 렉서·파서 | 문법, 지원 안 함 |
| 계획 (행을 읽기 전) | 없는 표·열, 이미 있는 표, 같은 열 두 번, 값 개수, **타입 오류 전부**, NULL 기본 키(리터럴 NULL일 때) |
| 실행 (행마다) | 산술(넘침·0 나누기), 기본 키 중복, NULL 기본 키(`SET id = 계산식`이 NULL이 될 때), 엔진 오류, 저장 손상 |

## E2. INTEGER와 TEXT: 엄격하게냐, 알아서 바꿔 주냐

**비유**: Java는 `int x = "5";`를 컴파일러가 거절한다. JavaScript는 `"5" == 5`가 `true`이고 `"5" + 1`이 `"51"`이다. 둘 중 어느 쪽 DB가 될 것인가.

| 선택지 | `INSERT INTO t (id) VALUES ('5')` | `WHERE id = '5'` | 장점 | 단점 |
|---|---|---|---|---|
| **A. 엄격 (지금)** | 타입 오류 | 타입 오류 | Java처럼 예측 가능. 키 인코딩이 타입마다 달라(0017 C4) 섞이면 범위 조회가 틀릴 위험이 원천 차단 | 손으로 SQL 칠 때 따옴표 실수가 오류가 됨 |
| B. PostgreSQL식: 따옴표 리터럴만 문맥 타입으로 | `'5'`를 정수 5로 읽음, `'abc'`면 오류 | 5와 비교 | 손 SQL이 편함. PG와 같은 답 | 리터럴에 "아직 타입 모름" 상태가 생김. 계획 단계가 문맥 추론을 해야 함 |
| C. MySQL/SQLite식 자동 변환 | 5로 저장 (SQLite affinity) | `'5'`를 숫자로 바꿔 비교, `'abc'`는 0 | 거의 안 막힘 | `WHERE id = 'abc'`가 `id = 0` 행을 고름. 조용히 틀린 답 |

**추천 A.** 스펙 이야기 39 "값이 열 타입에 맞지 않으면 타입 오류"를 글자 그대로 지키는 쪽이다. 명시적 변환 `CAST(x AS INTEGER)`는 이번 범위 밖이고, 만나면 "지원 안 함"이다.

BLOB도 같다: `X'00'`과 `'a'`는 서로 다른 타입이다(지금도 그렇다).

## E3. NULL과 타입 검사

NULL은 "아직 모르는 값"이라 **어느 타입 칸에도 들어갈 수 있다**(0017, 0019 W5). 이것은 바꾸지 않는다. `WHERE NULL = NULL`은 타입 오류가 아니라 0행, `NULL + 'a'`는 `+`가 TEXT를 받아서 타입 오류(지금과 같음).

남은 질문은 **NULL 기본 키를 어느 칸에 넣나**다. 지금은 `TypeMismatch { found: None }`, 코드 `0x09`.

**비유**: 택배 송장에 **받는 사람 칸을 비워 둔 것**은 "글씨가 숫자 칸에 한글로 적힘"(타입 오류)과 다르다. 칸 형식은 맞는데 **규칙(필수 칸)**을 어겼다. PostgreSQL은 `not_null_violation`(23502), SQLite는 "NOT NULL constraint failed", Spring은 `DataIntegrityViolationException`으로, 셋 다 **제약 위반** 쪽에 둔다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 그대로 `TypeMismatch { found: None }`, `0x09` | 테스트·코드 안 바뀜 | 이슈의 "타입 오류 / 제약 위반 구분"에 비추면 잘못된 칸. 클라이언트는 "입력 타입을 고쳐라"로 오해 |
| **B. 새 종류 `SqlError::NullKey { column }`(이름은 구현 때 다듬음), 새 코드 `0x0D` "NULL 불가 열에 NULL"** | 제약 위반 둘(중복 키 `0x08`, NULL 키 `0x0D`)이 나란히. 나중에 `NOT NULL` 열 제약이 생겨도 같은 칸 | 기존 테스트 10곳이 `TypeMismatch { found: None }`을 찾음(E12) |
| C. 기본 키 중복과 한 코드 `0x08` "기본 키 위반" | 코드가 안 늘어남 | "이미 있다"와 "비었다"는 대응이 다름 |

**추천 B.** `TypeMismatch`의 `found`는 그 뒤로 늘 값이 있으므로 `Option`을 뺄 수 있지만, 바이트·API 변화를 줄이려고 **필드 모양은 두고 `None`을 더는 만들지 않는다**(작은 질문 1).

## E4. 넘침, 0으로 나누기, 너무 큰 리터럴

0019 W11에서 "오류로 멈춘다"는 이미 정했다. 이번 질문은 **어느 칸이냐**다.

**비유**: Java에서 `1 / 0`은 `ArithmeticException`, `Integer.parseInt("99999999999")`는 `NumberFormatException`이다. 둘 다 "문장 구조"(컴파일 오류)가 아니라 **값이 범위를 벗어남**이다. PostgreSQL도 둘을 같은 묶음(class 22 data exception: `22003` 범위 밖, `22012` 0 나누기)에 둔다.

| 선택지 | `1 / 0`, `i64::MAX + 1` | `id = 99999999999999999999` | 장점 | 단점 |
|---|---|---|---|---|
| A. 지금 그대로 | `Arithmetic`, 통신 `0x1F` | `Syntax`, `0x01` | 바뀌는 것 없음 | 클라이언트가 산술 오류를 "기타"로만 봄. 너무 큰 수를 "문장이 깨짐"으로 오해 |
| **B. 둘 다 "값 범위 오류" 한 칸: `Arithmetic`, 새 코드 `0x0C`** | `Arithmetic`, `0x0C` | `Arithmetic` (메시지에 위치 포함), `0x0C` | PG와 같은 묶음. 클라이언트 대응("입력 값을 줄여라")이 하나 | 리터럴은 파서가 내는데 종류는 `Arithmetic` (이름이 약간 어색. 작은 질문 2) |
| C. 셋을 각각 다른 코드 | | | 가장 세밀 | 클라이언트가 할 일이 같아 칸만 늘어남 |

**추천 B.** 0으로 나누기와 넘침은 하나의 코드다. 메시지가 둘을 구분한다("division by zero" / "integer overflow").

## E5. 표·열 이름 오류

이미 칸이 있다: `NoSuchTable 0x03`, `NoSuchColumn 0x04`, `TableExists 0x05`, `DuplicateColumn 0x06`, `ValueCount 0x07`. 바꿀 것은 거의 없다.

| 질문 | 선택지 | 추천 |
|---|---|---|
| 대소문자 | A. 지금처럼 이름은 **정확히 같아야** 함(`Users` ≠ `users`), 키워드만 대소문자 무시 / B. 이름도 무시 | **A.** 바꾸면 카탈로그 키 인코딩(0017 C3)이 바뀜. 범위 밖 |
| "혹시 `name`?" 제안 | A. 없음 / B. 편집 거리로 비슷한 이름 제안 (PG의 HINT) | **A.** 손 SQL 편의는 좋지만 오류 *종류*와 무관. 나중에 메시지만 바꾸면 됨 |
| `NoSuchColumn`의 메시지 `t.nope` | 그대로 | 그대로 |

## E6. Rust 쪽 오류 모양: 몇 칸으로, 어떤 구조로

**비유**: 옷장 정리. 서랍 하나에 다 넣으면(칸 1개) 찾기 어렵고, 양말마다 서랍을 주면(칸 50개) 서랍을 못 연다. 또 "서랍 안에 칸막이"(중첩)를 둘 수도 있다.

지금 `SqlError`는 **평평한 열거형 16칸**이고 `#[non_exhaustive]`다. 이것을 개념으로 묶으면 아래 8묶음이 된다(이 표가 이번 설계의 "분류 체계"다).

| 묶음 | 칸 (`SqlError`) | 클라이언트가 할 일 | 통신 범위 |
|---|---|---|---|
| 문법 | `Syntax` | 문장을 고친다 | `0x01–0x1F` |
| 지원 안 함 | `Unsupported` | 다른 방법을 쓴다 | 〃 |
| 이름 | `NoSuchTable`, `NoSuchColumn`, `TableExists`, `DuplicateColumn`, `ValueCount` | 표·열 이름을 고친다 | 〃 |
| 타입 | `TypeMismatch`, `Type` | 값·식의 타입을 고친다 | 〃 |
| 값 범위 | `Arithmetic` | 값을 줄인다 | 〃 |
| 제약 | `DuplicateKey`, (새) `NullKey` | 사용자에게 알린다 | 〃 |
| 트랜잭션 상태 | `Transaction` | 상태를 다시 맞춘다 (0025 Q3) | 〃 |
| 다시 시도 | `TransactionConflict`, `Engine(Conflict)` | **다시 실행** | `0x20` |
| 엔진·저장 | `Engine(나머지)`, `Corrupt` | 운영자를 부른다 | `0x20–0x3F`, `0x0A` |

| 선택지 | 모양 | 장점 | 단점 |
|---|---|---|---|
| **A. 평평한 칸 유지, 빈 칸만 채움** (`NullKey` 하나 추가) | 지금 그대로 + 1 | 기존 `match` 대부분 그대로. 묶음은 이 문서와 `docs/protocol.md` 표에 있음 | 묶음이 코드에 없음. 클라이언트가 "제약 위반인가?"를 물으려면 칸을 나열해야 함 |
| B. A + `SqlError::category() -> Category` 메서드 | 칸은 그대로, 묶음 열거형을 하나 더 | Spring의 예외 계층처럼 "묶음으로 잡기" 가능. 테스트가 "모든 칸이 정확히 한 묶음"을 확인 | 공개 API가 하나 늘어남. 지금 쓰는 곳이 서버의 코드 대응뿐 |
| C. 중첩 열거형으로 재구성 `SqlError::Constraint(ConstraintError::DuplicateKey)` | 묶음이 타입 | 가장 "정돈됨" | 기존 테스트 수십 곳(타입 관련만 37곳)이 깨짐. 0017 C8 이후 쌓인 눈 가린 테스트를 다시 써야 함. 얻는 것은 모양뿐 |

**추천 A.** 묶음은 클라이언트가 **통신 코드의 범위**로 이미 얻는다(HTTP 4xx처럼). Rust 쪽에서 묶음이 필요해지는 첫 사용처(예: CLI가 묶음별 색)를 만나면 B를 더하는 것은 하위 호환이다. 이미 있는 묶음 도우미 `is_conflict()`는 그대로 둔다.

`TypeMismatch`와 `Type`을 하나로 합칠지는 작은 질문 4.

## E7. 번호 체계: 자체 코드냐 SQLSTATE냐

**SQLSTATE**는 SQL 표준의 다섯 글자 오류 번호다(`23505` = 유일성 위반, `42601` = 문법 오류). 앞 두 글자가 묶음(HTTP의 앞자리)이다. JDBC의 `SQLException.getSQLState()`가 이것을 돌려준다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 자체 u8 코드 유지 + 문서에 SQLSTATE 대응 열만 적음** | 통신 바이트 그대로(버전 1 유지). 1바이트. 우리 칸(결과 모름 `0x25`, 엔진 멈춤 `0x26`)을 그대로 표현. 블로그에 "표준이면 몇 번"을 같이 보여 줄 수 있음 | 표준 도구(JDBC 드라이버 등)가 바로 이해하지 못함. 그런 도구는 Oakdb에 없음 |
| B. ERROR 프레임에 SQLSTATE 5바이트를 더함 | 표준과 연결 | 통신 규칙 버전 2. 서버·`Client`·테스트를 같이 바꿔야 함. 지금 쓸 사람이 없음 |
| C. u8을 버리고 SQLSTATE만 | 표준 하나 | B의 단점 + 1바이트 비교가 문자열 비교로 |

**추천 A.** `docs/protocol.md` 6절 표에 "SQLSTATE 대응(참고)" 열을 더한다. 바이트는 안 바뀐다.

## E8. `SqlError` → 통신 코드: 새 번호

원칙: **이미 나간 번호는 바꾸지 않고 뒤에 붙인다.** 범위 `0x01–0x1F` 안에 자리는 넉넉하다(20개 남음).

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 빈 번호에 이어 붙임** (`0x0B`는 #37, `0x0C`, `0x0D`) | 기존 클라이언트·테스트 그대로. 범위 약속 그대로 | 번호 순서가 묶음 순서와 섞임(묶음은 표의 열로 봄) |
| B. 묶음별 하위 범위로 번호를 다시 매김 (`0x01–0x07` 문장, `0x08–0x0F` 이름, `0x10–0x17` 타입·값, `0x18–0x1E` 제약) | 번호만 봐도 묶음 | 이미 문서화된 `0x03`, `0x08`, `0x09` 등이 바뀜. 통신 버전 1의 약속을 깸 |
| C. A + 앞으로의 번호만 하위 범위로 | 절충 | 규칙이 둘이라 오히려 헷갈림 |

**추천 A.** 결과 표(바뀌는 줄은 **굵게**):

| 코드 | 뜻 | `SqlError` | 묶음 | SQLSTATE 대응(참고) |
|---|---|---|---|---|
| `0x01` | 문법 오류 (메시지에 위치) | `Syntax` | 문법 | `42601` |
| `0x02` | 지원하지 않는 SQL | `Unsupported` | 지원 안 함 | `0A000` |
| `0x03` | 없는 표 | `NoSuchTable` | 이름 | `42P01` |
| `0x04` | 없는 열 | `NoSuchColumn` | 이름 | `42703` |
| `0x05` | 이미 있는 표 | `TableExists` | 이름 | `42P07` |
| `0x06` | 같은 열을 두 번 씀 | `DuplicateColumn` | 이름 | `42701` |
| `0x07` | 행의 값 개수가 열 개수와 다름 | `ValueCount` | 이름 | `42601` |
| `0x08` | 기본 키 중복 | `DuplicateKey` | 제약 | `23505` |
| **`0x09`** | **타입 오류: 값이나 식의 타입이 맞지 않음** | `TypeMismatch`, **`Type`** | 타입 | `42804` |
| `0x0A` | SQL 층이 저장한 표 정보·행을 읽을 수 없음 | `Corrupt` | 엔진·저장 | `XX001` |
| `0x0B` | 트랜잭션 상태에 안 맞는 명령 (#37이 추가, 0025 Q2) | `Transaction` | 트랜잭션 상태 | `25001`/`25P01` |
| **`0x0C`** | **값 범위: 정수 넘침, 0으로 나누기, 64비트 밖 리터럴** | **`Arithmetic`** | 값 범위 | `22003`/`22012` |
| **`0x0D`** | **NULL이 될 수 없는 열(기본 키)에 NULL** | **(새) `NullKey`** | 제약 | `23502` |
| `0x1F` | 위에 없는 문장 오류 (앞으로 생길 칸의 안전망) | `_` | — | — |
| `0x20` | 충돌, 다시 실행하면 될 수 있음 | `TransactionConflict`, `Engine(Conflict)` | 다시 시도 | `40001` |
| `0x21`/`0x22` | 키/값이 너무 김 | `Engine(KeyTooLarge/ValueTooLarge)` | 엔진 | `54000` |
| `0x23`–`0x26`, `0x3F` | 지금 그대로 | `Engine(…)` | 엔진 | `XX001`, `58030`, `08007`, `57P01` |

- **#37과의 순서**: `0x0B`는 #37(0025)이 잡은 번호다. #34가 먼저 머지되면 `0x0B`를 **비워 둔다**(표에 "#37 예약"). 어느 쪽이 먼저든 `0x0C`, `0x0D`는 #34 것이다. #37의 `0x47`(트랜잭션 중 너무 오래 놂)은 `0x40–0x5F` 범위라 겹치지 않는다.
- 이번 티켓이 끝나면 **현재의 어떤 `SqlError` 칸도 `0x1F`로 가지 않는다.** `error_code`의 `_ => OTHER_STATEMENT` 갈래는 `non_exhaustive` 때문에 남지만, 테스트가 "모든 알려진 칸은 `0x1F`가 아니다"를 확인한다(E13).

## E9. 동시에 같은 키를 INSERT하면: 충돌이냐 중복이냐 (W2)

자동 커밋 INSERT 두 개가 같은 키를 동시에 넣으면, 둘 다 "아직 없음"을 보고 쓰고, 나중에 커밋한 쪽이 `0x20` 충돌을 받는다. 사용자 눈에는 "이미 있다"(`0x08`)에 가깝다.

**비유**: 극장 좌석 예매. 둘이 같은 자리를 동시에 눌렀고 한 명이 먼저 결제했다. 늦은 사람에게 "이미 팔린 자리입니다"라고 할까, "다른 손님과 겹쳤습니다, 다시 시도하세요"라고 할까. 다시 시도하면 **그때** "이미 팔림"이 정확히 나온다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 그대로 `0x20` 충돌** | 엔진이 아는 사실 그대로. 다시 실행하면 그때 정확한 답(`0x08` 중복, 또는 상대가 DELETE였다면 **성공**)이 나옴. 재시도 루프가 있는 클라이언트는 자동으로 옳음 | 첫 응답이 "중복"이 아님 |
| B. INSERT의 충돌을 `DuplicateKey`로 번역 | 사람이 보기에 자연스러움 | **틀릴 수 있다**: 충돌은 "같은 키를 누가 먼저 썼다"일 뿐 "지금 있다"가 아니다. 먼저 커밋한 쪽이 그 키를 DELETE했다면 다시 실행한 INSERT는 성공한다. 다시 시도하면 될 일을 "고칠 수 없는 오류"로 바꿈 |
| C. 충돌 뒤 한 번 다시 읽어 판별해서 보고 | 정확한 답 | 자동 커밋이면 사실상 자동 재시도. 트랜잭션 안이면 불가능(이미 롤백됨). 규칙이 둘 |

**추천 A.** PostgreSQL도 REPEATABLE READ에서 같은 상황에 `40001`(serialization_failure)을 준다. 대신 `docs/protocol.md`에 "INSERT가 `0x20`을 받으면 다시 실행하라, 그때 `0x08`이 오면 진짜 중복"을 한 줄 적는다.

## E10. 문법 오류와 "지원 안 함"의 경계 (W3)

**비유**: 외국인 손님이 "아이스 아메리카노 벤티"라고 했다. 점원이 "무슨 말인지 모르겠어요"(문법 오류)라고 하는 것과 "벤티 사이즈는 없어요"(지원 안 함)라고 하는 것은 손님에게 전혀 다르다. 뒤엣것이면 손님은 "그럼 그란데"로 바꾸면 된다.

지금 넷이 "모르겠어요"로 나온다: `CREATE TABLE IF NOT EXISTS`, `SELECT COUNT(*)`, `SELECT t.id`, `-- 주석`.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 그대로 문법 오류 | 할 일 없음 | 표준 SQL을 쓴 사용자가 "내가 틀렸나?" 하고 헤맴. 스펙 이야기 38 "지원 안 하는 SQL에는 분명한 오류" |
| **B. 알려진 꼴만 골라 "지원 안 함"** | 넷 각각에 맞는 메시지: "`IF NOT EXISTS`", "function `COUNT(...)`", "qualified column `t.id`", "comments `--`/`/* */`". 파서 몇 줄 | 목록 밖의 표준 SQL은 여전히 문법 오류(경계는 "목록"이다) |
| C. B + 주석은 아예 지원(렉서가 건너뜀) | SQL 파일·CLI 스크립트가 그대로 돎 | 오류 티켓에 기능이 섞임. 주석 안의 `'`·`*/` 처리 등 렉서 테스트가 늘어남 |
| D. 일반 규칙: "SQL 키워드 목록에 있는 단어를 못 읽으면 지원 안 함" | 목록을 덜 관리 | 키워드 목록(수백 개)을 들고 있어야 함. `SELEC` 같은 오타와 섞임 |

**추천 B.** 경계의 원칙을 문서에 남긴다: **"표준 SQL에 있는 꼴이라고 파서가 알아본 곳에서는 지원 안 함, 알아보지 못한 곳에서는 문법 오류."** 주석 지원(C)은 하지 않는다(사용자 결정: B만).

## E11. 메시지 모양과 위치

지금 문법 오류는 `syntax error at byte 27: expected an expression, found `=``이다. 바이트는 기계엔 정확하지만, 여러 줄 문장에서 사람이 27을 세긴 어렵고, 한글이 섞이면 글자 수와도 다르다(`'김'`은 3바이트).

| 선택지 | 예 | 장점 | 단점 |
|---|---|---|---|
| A. 그대로 바이트 | `at byte 27` | 바뀌는 것 없음 | 여러 줄·한글에서 사람에게 불편 |
| **B. 줄·칸으로 보여 주고, 바이트는 필드에 남김** | `syntax error at line 2, column 12: …` | 편집기와 같은 말. `position`(바이트) 필드는 그대로라 테스트·도구가 계속 씀 | `Syntax`에 `line`, `column` 필드가 늘어남(파서가 만들 때 계산) |
| C. B + 타입·이름 오류에도 위치 | `type error at line 1, column 23: …` | PG처럼 어느 식인지 가리킴 | 파서가 모든 식 노드에 위치를 달아야 함. 식 나무가 커지고(0019 1-1의 깊이 한도 스택 계산을 다시) 손볼 곳이 많음 |

**추천 B.** 줄은 1부터, 칸은 **글자(UTF-8 문자) 수** 1부터(편집기와 같게), 탭은 한 글자. E4의 "64비트 밖 리터럴"도 같은 방식으로 메시지에 위치를 담는다.

메시지 규칙(지금 대부분 이미 지킴, 이번에 문서로 굳힘):

| 규칙 | 예 |
|---|---|
| `묶음: 내용` 꼴, 소문자 시작, 끝에 마침표 없음 | `type error: cannot compare INTEGER with TEXT` |
| 무엇을 만났는지 백틱으로 | ``unsupported: function `COUNT(...)` `` |
| 고칠 방법이 하나면 말함 | `…; COMMIT or ROLLBACK it first` |
| 내부 키·주소·Rust 타입 이름을 내보내지 않음 | (0023 5-2의 충돌 메시지처럼) |
| 영어 유지 | 통신·로그·검색에 안전. 한국어 설명은 문서가 맡음 |

## E12. 하위 호환

| 대상 | 무엇이 바뀌나 | 영향 |
|---|---|---|
| `SqlError` 공개 API | 칸 하나 추가(`NullKey`), `Syntax`에 필드 둘 추가 | `non_exhaustive`라 다른 크레이트의 `match`는 안 깨짐. `Syntax { position, .. }` 꼴 매치도 그대로 |
| NULL 기본 키 테스트 10곳 (`sql.rs` 2, `update_delete.rs` 2, `blind_sql.rs` 2, `blind_update_delete.rs` 3, `where_model.rs` 1) | `TypeMismatch { found: None }` → `NullKey` | 고쳐야 함. 눈 가린 테스트는 당시 스펙(0017 "TypeMismatch")을 따른 것이므로, 고친 줄에 "#34에서 종류가 바뀜" 주석을 남김 |
| 큰 리터럴 테스트 | `Syntax` → `Arithmetic` | 있으면 고침(`where_clause.rs` 위치 테스트 확인) |
| 통신 코드 | `Type`: `0x1F`→`0x09`, `Arithmetic`: `0x1F`→`0x0C`, NULL 키: `0x09`→`0x0D` | 서버 밖 클라이언트는 없음(우리 `Client`와 테스트뿐). 범위(`0x01–0x1F`)는 그대로라 범위로 판단하던 클라이언트는 영향 없음. 통신 **버전은 1 그대로**(바이트 모양 불변) |
| 메시지 문자열 | `at byte N` → `at line L, column C` | 메시지 문자열을 검사하는 테스트는 없음(확인함). `Display`를 보는 곳은 CLI뿐 |
| `docs/protocol.md` | 6절 표 갱신 + SQLSTATE 열 + E9 한 줄 | — |

## E13. 테스트와 검증

| 무엇 | 어디 | 확인 |
|---|---|---|
| 오류 종류 표 테스트 | `oakdb-sql/tests/errors.rs` (새) | 이 문서 "지금 상태" 표의 모든 줄 + 묶음마다 대표 문장이 **기대한 칸**으로 떨어짐. 표 하나를 돌리는 테스트(행 = 문장, 칸) |
| 코드 대응 전수 | `oakdb-server/tests/protocol.rs` | 모든 알려진 `SqlError` 칸 → 코드가 표와 같고 **`0x1F`가 아님**. 코드 값이 겹치지 않음. 각 코드가 문서화된 범위 안 |
| 타입 검사 속성 테스트 | `oakdb-sql/tests/type_model.rs` (새) | 무작위 식(열·리터럴·산술·비교·AND/OR/NOT, NULL 포함)을 만들어 ① 아주 작은 **모델 타입 검사기**(테스트 안에 20줄쯤, 0019 3절 표를 그대로 옮김)와 Oakdb가 "타입 오류냐 아니냐"에서 일치. ② 같은 문장을 **빈 표와 찬 표**에서 돌려 타입 오류 여부가 같음(E1의 약속). ③ 타입 검사를 통과한 식은 실행 중에 `Corrupt`("다른 타입 값")를 절대 내지 않음 |
| 위치 | `oakdb-sql` 단위 | 여러 줄·한글·탭이 섞인 문장에서 줄·칸이 맞음, 바이트 `position`은 전과 같음 |
| W3 경계 | `oakdb-sql/tests/errors.rs` | 네 꼴이 `Unsupported`이고 메시지가 그 꼴을 이름으로 말함. 그 옆의 진짜 오타(`SELECT * FORM t`)는 여전히 `Syntax` |
| 통신 왕복 | `oakdb-server/tests/server.rs` | 묶음마다 문장 하나를 실제 서버에 보내 코드 확인 + **오류 뒤 같은 접속으로 다음 문장이 정상** |
| W2 | `oakdb-sql` 동시성 테스트 하나 | 두 세션이 같은 키를 BEGIN…INSERT…COMMIT, 늦은 쪽 `0x20`, 다시 실행하면 `DuplicateKey` |

검증 단계(CLAUDE.md):

- **두 축 코드 리뷰**(Standards / Spec), PR의 기준점에서.
- **눈 가린 테스터**: 이슈 #34, 스펙 #12 이야기 38·39·45, 이 문서, `docs/protocol.md` 6절만 보고 테스트를 씀. 특히 "어느 문장이 어느 코드로"를 표에서 직접 뽑게 한다.
- **장애 실험** `docs/experiments/`: 오류 폭탄. 한 접속에 모든 묶음의 오류 문장을 무작위로 1만 번 섞어 보내고, 접속이 끊기지 않고(코드 `0x40` 이상 없음), 사이사이의 정상 문장 결과가 모델과 같음. 트랜잭션 안에서도 한 번(0023 T5 "실패한 문장만 없던 일"이 오류 종류와 무관한지).
- **A/B 가설 검정 없음**: 이번 티켓은 성능 주장을 하지 않는다. 오류 경로만 바뀐다. 다만 SELECT·INSERT 벤치 하나를 전후로 돌려 "느려지지 않았다"는 숫자만 남긴다(`docs/benchmarks/`).
