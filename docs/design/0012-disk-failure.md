# 0012. 디스크 기록 실패 처리 — 설계

이슈 #24, ADR 0007. 정전 안전 구간(08~12)의 마지막 티켓이다. 지금까지는 **전원이 꺼지는** 고장만 다뤘다. 이번에는 전원은 멀쩡한데 **디스크가 "못 썼다"고 대답하는** 고장을 다룬다. sync 실패, 쓰기 실패, 디스크 공간 부족(ENOSPC)이 그렇다.

**비유**: 은행 창구 직원이 일지에 거래를 적고 금고에 넣으려는데, 금고가 "넣다가 걸렸어요, 들어갔는지는 모르겠어요"라고 한다. 이때 같은 쪽지를 다시 넣어 보는 직원(재시도)이 가장 위험하다. 금고가 이미 쪽지를 버렸을 수도 있는데 "이번엔 들어갔다"는 대답만 믿게 되기 때문이다. 그래서 직원은 **창구를 닫는다**. 그 손님에게는 "처리됐는지 모릅니다", 뒤에 줄 선 손님에게는 "창구가 닫혔습니다"라고 말한다. 창구를 다시 여는 건 **금고 안을 처음부터 다시 확인한 뒤**(다시 열기 = WAL 재생)다.

```text
커밋 ──▶ WAL 쓰기 ──▶ sync ──✗ 실패
                         │
                         ├─ 이 커밋:      OutcomeUnknown (결과를 알 수 없음)
                         ├─ 그 뒤 모든 요청: Stopped        (엔진 정지)
                         └─ Db를 버리고 다시 열기 → WAL 재생 → 응답한 커밋은 모두 있음,
                                                     실패한 커밋은 통째로 있거나 통째로 없음
```

**왜 재시도하면 안 되나 (fsyncgate, 2018)**: Linux에서 `fsync`가 실패하면 커널은 쓰지 못한 페이지를 "깨끗함"으로 표시하고 오류를 **한 번만** 알린다. 다시 `fsync`를 부르면 성공이 돌아오지만, 처음 실패한 내용은 디스크에 없다. PostgreSQL은 이 일을 겪고 "fsync가 실패하면 서버를 멈추고(PANIC) WAL로 복구한다"로 바꿨다. Oakdb도 ADR 0007에서 같은 길을 골랐다. **fsync가 한 번 실패한 파일은 이 프로세스에서 다시 믿지 않는다.**

## 결정

사용자가 자리에 없어 모두 추천안으로 진행했고, PR #57 리뷰 뒤 사용자가 일곱 개 모두 그대로 두기로 확인했다. 리뷰에서 다듬은 것은 12절.

| # | 질문 | 결정 | 상태 |
|---|---|---|---|
| 1 | 어떤 실패가 엔진을 멈추나 | 엔진이 열린 뒤 **디스크를 바꾸는 호출**(쓰기, 길이 바꾸기, sync)이 실패하면 무엇이든 멈춘다. 짧은 쓰기, ENOSPC도 같다. 열기 도중의 실패는 열기가 오류를 돌려줄 뿐이다(멈출 엔진이 아직 없다) | 사용자 확인함 (PR #57 리뷰 뒤) |
| 2 | 오류 종류 | 새 종류 **두 개**: 실패를 만난 커밋은 `Error::OutcomeUnknown(Arc<io::Error>)`, 그 뒤 요청은 `Error::Stopped(Arc<Error>)`(실패한 호출이 받은 **바로 그 오류**를 나눠 쥠). 직접 부른 `checkpoint()`·`close()`가 실패하면 원인 `Io`를 그대로 돌려준다 | 사용자 확인함 (PR #57 리뷰 뒤) |
| 3 | 읽기도 멈추나 | **멈춘다.** `get`, `scan`, `put`, `delete`, `commit`(빈 커밋 포함), `checkpoint`, `close` 모두 `Stopped`. 값을 돌려주지 않는 `begin()`, `page_count()`, `rollback()`은 그대로 | 사용자 확인함 (PR #57 리뷰 뒤) |
| 4 | 커밋이 WAL에 닿은 뒤 **자동 정리**가 실패하면 | 커밋은 이미 디스크에 있으니 **`Ok`**를 돌려주고 엔진만 멈춘다. #23에서는 `Err`였다 | 사용자 확인함 (PR #57 리뷰 뒤) |
| 5 | 멈춤 표시는 어디에 | `Db` 하나에 `OnceLock`. 쓰는 쪽은 **트리 잠금을 쥔 뒤** 확인한다. `Wal`의 `stopped`는 없앤다 | 사용자 확인함 (PR #57 리뷰 뒤) |
| 6 | 가짜 디스크의 실패 주입 | `SimFs::fail_once_after(n)`: 디스크를 바꾸는 호출 n번 뒤의 **한 번만** 전원이 켜진 채 실패. 실패한 호출은 아무것도 바꾸지 않고, sync 실패면 기다리던 변경은 그대로 기다린다 | 사용자 확인함 (PR #57 리뷰 뒤) |
| 7 | 다시 열 때 OS 캐시를 믿나 | 지금은 **믿는다**(그대로 다시 읽음). Linux에서 같은 부팅 안에 다시 열면 디스크에 없는 바이트를 읽을 수 있다는 한계를 적고, 가짜 디스크 모델은 다음 티켓 후보로 넘긴다 | 사용자 확인함 (PR #57 리뷰 뒤) |

## 1. 어떤 실패가 엔진을 멈추나 (결정 1)

| 언제 | 무엇이 실패 | 하는 일 | 이유 |
|---|---|---|---|
| 커밋 | WAL 쓰기·sync | **정지**, 그 커밋은 `OutcomeUnknown` | 일부나 전부가 디스크에 있을 수 있다 |
| 커밋 뒤 자동 정리 | 데이터 파일·메타·WAL 비우기 | **정지**, 커밋은 `Ok` (결정 4) | 커밋은 sync까지 끝났다 |
| 직접 부른 정리·닫기 | 위와 같음 | **정지**, `Io` 그대로 | 데이터는 바뀌지 않는다. 결과를 모르는 커밋이 없다 |
| 열기 | 잠금, 읽기, 꼬리 자르기, `.cut` 파일, WAL 새로 쓰기, 새 DB의 첫 커밋, 디렉터리 sync | `Io` 등 오류를 돌려줌. 멈출 `Db`가 없다 | 열기는 아무 커밋에도 응답하기 전이다. 다시 열면 디스크를 처음부터 다시 읽는다 |

| 실패 모양 | 다루는 법 |
|---|---|
| sync 실패 | 위 표 그대로 |
| 쓰기 실패 | 같다. 쓰기가 이미 일부 들어갔는지 모르므로 sync 실패와 구별하지 않는다 |
| 짧은 쓰기 | `write_all_at`이 나머지를 이어 쓰다 0바이트면 `WriteZero` 오류가 된다. 결국 쓰기 실패다 |
| ENOSPC (공간 부족) | 쓰기 실패다. 공간을 비운 뒤 다시 열면 된다. 오류 번호(`raw_os_error`)가 `Stopped`까지 그대로 가서 "디스크가 꽉 참"과 "디스크 고장"을 가를 수 있다 |

**짧은 쓰기와 ENOSPC는 논증으로만 다룬다 (리뷰 P2).** 엔진은 쓰기·sync의 오류를 **종류를 보지 않고** 똑같이 다룬다(코드에 갈래가 없다). 그래서 위 표가 맞다는 것은 "모든 `Err`가 같은 길로 간다"는 데서 나온다. 가짜 디스크의 실패는 늘 EIO 하나라서, 짧은 쓰기(앞부분만 쓰고 실패)나 ENOSPC 오류 번호를 따로 만드는 테스트는 없다.
| 길이 바꾸기 실패 | 정리의 WAL 비우기에서만 생긴다. 정리 실패와 같다 |

**버린 선택지**

| 선택지 | 버린 이유 |
|---|---|
| sync만 멈추고 쓰기 실패는 재시도 | 쓰기가 반쯤 들어갔을 수 있다. 다음 커밋이 그 자리를 덮어쓰는 것이 바로 #22의 "사실상 재시도" 구멍이다 |
| ENOSPC는 멈추지 않고 그 커밋만 실패 | 공간이 없다는 오류가 쓰기 **도중**에 나면 앞부분은 이미 파일에 있다. 안전하게 하려면 꼬리를 잘라야 하는데, 자르기도 디스크를 바꾸는 일이라 또 실패할 수 있다. SQLite는 저널 단계에서 공간을 먼저 확보한다. 공간 예약은 이번 범위 밖이다 |
| 열기 실패도 "정지" 상태로 | `Db`가 만들어지지 않았으니 멈출 대상이 없다. 오류를 돌려주는 것으로 충분하다 |

## 2. 오류 종류 (결정 2)

| 선택지 | 실패한 커밋 | 그 뒤 요청 | 장점 | 단점 |
|---|---|---|---|---|
| A. `Io` + `Stopped` 하나 | `Io` | `Stopped` | 새 종류 하나 | 실패한 커밋이 "결과 모름"인지 "아무것도 안 됨"인지 `Io`만 보고는 모른다. 완료 조건 2를 문서로만 지킨다 |
| **B. `OutcomeUnknown` + `Stopped`** | `OutcomeUnknown(io)` | `Stopped(원인)` | 완료 조건 2·3이 **타입으로** 구별된다. 재시도해도 되는지(Stopped: 다시 열면 됨)와 확인이 필요한지(Unknown: 다시 열어 읽어 봐야 앎)가 갈린다 | 새 종류 둘 |
| C. `Stopped { unknown: bool }` | 플래그 | 플래그 | 종류 하나 | 사용자가 플래그를 잊기 쉽다 |

**B로 진행.**

```rust
#[derive(Debug, Clone)]       // 오류는 싸게 복제된다: io::Error를 나눠 쥐므로
pub enum Error {
    Io(Arc<io::Error>),       // 열기 실패, 직접 부른 정리·닫기의 실패
    ...
    /// 이 커밋을 쓰다 디스크가 실패했다. 커밋이 디스크에 있는지 모른다.
    /// 엔진은 멈췄다. Db를 버리고 다시 열어 읽어 보면 안다.
    OutcomeUnknown(Arc<io::Error>),
    /// 앞서 디스크가 실패해 엔진이 멈췄다. 이 요청은 아무것도 하지 않았다.
    /// Db를 버리고 다시 열면 된다. 실패한 호출이 받은 오류를 담는다.
    Stopped(Arc<Error>),
}
```

- `Error`는 `#[non_exhaustive]`라서 종류를 더해도 쓰는 쪽 코드가 깨지지 않는다.
- `Stopped`의 원인은 요청마다 돌려줘야 한다. `io::Error`는 복제가 안 되므로 `Io`와 `OutcomeUnknown`이 `Arc<io::Error>`를 쥐고, `Error` 전체가 `Clone`이다. 멈춤 표시는 실패한 호출이 받은 오류의 **복제본(같은 `Arc`)**이다. 그래서 종류, OS 오류 번호(`raw_os_error`, 예: ENOSPC·EIO), `source()` 사슬이 그대로 남는다 (리뷰 S6·P5). 처음 구현은 종류와 메시지만 베낀 사본이라 오류 번호를 잃었다.
- **직접 부른 정리·닫기는 `Io`다 (리뷰 S8).** 정리는 데이터를 바꾸지 않는다. 실패해도 결과를 모르는 커밋이 없다(응답한 커밋은 이미 WAL에 sync됐고, 정리는 어느 시점에 끊겨도 다시 열면 된다는 것을 #23이 보였다). 그래서 "결과를 알 수 없음"이 아니라 무엇이 실패했는지만 알린다. 엔진은 똑같이 멈춘다.
- #23의 "정리 실패 = `Io(other("a checkpoint failed…"))`"(리뷰 S5)는 이제 `Stopped`로 바뀐다. 정리가 멈춘 원인이 `Corrupt`(회차가 더 커질 수 없음)일 수도 있어서 원인은 `io::Error`가 아니라 `Error`다.
- 실패한 호출의 `source()`는 `io::Error`, `Stopped`의 `source()`는 원인 `Error`다.

## 3. 읽기도 멈추나 (결정 3)

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 모든 요청 멈춤** | 완료 조건 3("이후 모든 요청")을 글자 그대로 지킨다. "멈춘 엔진"이 한 가지 뜻이다. PostgreSQL의 PANIC과 같다 | 메모리의 트리는 응답한 커밋 그대로라 읽어도 안전한데 못 읽는다 |
| B. 쓰기만 멈춤, 읽기는 됨 | 가용성이 높다 | "멈췄는데 읽힌다"를 사용자가 헷갈린다. 디스크에서 페이지를 읽게 되면(필요한 페이지만 읽는 열기) 읽기도 디스크를 믿어야 해서 다시 바뀐다 |

**A로 진행.** 함수별로는 이렇다.

| 함수 | 멈춘 뒤 |
|---|---|
| `Txn::get`, `put`, `delete` | `Err(Stopped)` |
| `Txn::scan` | 첫 항목이 `Err(Stopped)`, 그다음 끝 |
| `Txn::commit` | `Err(Stopped)`. 쓴 것이 없는 커밋도 |
| `Db::checkpoint`, `close` | `Err(Stopped)` |
| `Db::begin`, `page_count`, `Txn::rollback` | 그대로. `Result`를 돌려주지 않고, 디스크에도 트리에도 영향이 없다. 바꾸면 공개 API가 깨진다 |
| 멈추기 **전에** 시작한 `Scan` | 끝까지 돈다. 시작할 때 잡은 트리(응답한 커밋들)만 읽는다 |

## 4. 실패한 커밋의 상태

| 어디 | 상태 |
|---|---|
| 메모리 트리 | 바꿔 끼우지 않는다 (지금도 그렇다: `append`가 실패하면 교체 전에 돌아온다) |
| WAL 꼬리(`tail`) | 옮기지 않는다 |
| 디스크의 WAL | 커밋의 바이트가 **전부·일부·전혀** 없을 수 있다 |
| 다시 연 뒤 | 사슬 체크섬과 커밋 레코드 덕분에 **통째로 있거나 통째로 없다**. 둘 다 `OutcomeUnknown`의 약속 안이다 |

읽기도 멈추므로(결정 3) 실패한 커밋이 메모리에서 보이는지는 밖에서 알 수 없다. 다시 열어 읽은 것이 답이다.

## 5. 멈춤 표시 (결정 5)

```rust
pub struct Db<F: Fs> {
    file, wal, tree,
    /// 디스크가 실패해 엔진이 멈춘 원인. 한 번 정해지면 바뀌지 않는다.
    stopped: OnceLock<Arc<Error>>,
}
```

| 선택지 | 장점 | 단점 |
|---|---|---|
| `Wal` 안의 `stopped` (지금) | 쓰기 바로 앞에서 막는다 | 읽기는 `Wal` 잠금을 잡지 않아서 읽기를 막으려면 어차피 `Db`에 하나 더 필요하다 |
| **`Db`의 `OnceLock`** | 읽기는 잠금 없이 확인. 한 번만 정해짐이 타입으로 드러난다 | 쓰는 쪽이 **잠금을 쥔 뒤** 확인해야 한다 |

**경쟁 조건**: 커밋 B가 "멈춤 아님"을 확인하고 트리 잠금을 기다리는 사이 커밋 A가 실패해 멈추면, B가 잠금을 얻은 뒤 WAL에 또 쓴다. 이것이 재시도다. 그래서 커밋과 정리는 **트리 잠금을 쥔 뒤** 확인한다. 멈춤은 잠금을 쥔 채 정해지므로 빈틈이 없다. 읽기는 잠금 전에 확인해도 된다. 쓰지 않기 때문이다.

## 6. 가짜 디스크의 실패 주입 (결정 6)

```rust
fs.fail_once_after(1);     // 디스크를 바꾸는 호출 1번은 성공, 2번째 한 번만 실패
txn.commit();              // 쓰기 성공, sync 실패 → OutcomeUnknown
// 디스크는 다시 멀쩡하다. 엔진이 믿지 않을 뿐이다.
```

| 실패한 호출 | 가짜 디스크에서 |
|---|---|
| `write_all_at`, `set_len` | 아무것도 바꾸지 않고 실패 |
| `sync_data` | 아무것도 굳히지 않고 실패. 기다리던 변경은 **계속 기다린다**: 정전이 나면 주사위로 정해지고, 나중에 sync가 성공하면 굳는다 |
| `open`, `sync_dir`, `create_dir_all` | 아무것도 바꾸지 않고 실패 |

- `fail_after`처럼 "디스크를 바꾸는 호출"을 센다. 그래서 정전 실험과 같은 방식으로 **모든 시점**을 훑을 수 있다.
- 실패한 호출은 `ops()`에 세지 않는다(`fail_after`와 같다). 전원은 켜진 채라 다음 호출부터 다시 된다.
- 실패는 EIO(`raw_os_error() == Some(EIO)`)로 낸다. 진짜 디스크가 쓰기·sync를 못 했을 때 주는 오류다.
- 정전이 같은 호출이나 그 전에 닥치면 **정전이 이기고**, `crash()`가 남은 실패를 지운다. 다음 부팅으로 넘어가지 않는다 (리뷰 P4).
- 찢어진 쓰기와 주사위는 건드리지 않는다(#56과 겹치지 않게).

| 선택지 | 버린 이유 |
|---|---|
| `fail_next_sync()`처럼 sync만 | 쓰기·길이·열기 실패도 같은 경로로 시험해야 한다. 완료 조건 1(sync 실패)은 n을 sync 자리로 고르면 된다 |
| 실패한 쓰기가 앞부분만 남김(짧은 쓰기) | 엔진에게는 "쓰기 실패 + 찢긴 꼬리"와 같고, 찢긴 꼬리는 정전 실험이 이미 덮는다. sim.rs 변경을 작게 둔다 |
| sync 실패 시 기다리던 변경을 버림(Linux가 페이지를 "깨끗함"으로 표시) | 결정 7 참고. 지금 엔진은 실패 뒤 그 파일에 다시 쓰지 않으므로 이 프로세스 안에서는 차이가 없다. 차이는 같은 부팅에서 다시 열 때만 생긴다 |

## 7. 다시 열기와 "다시 믿지 않는다" (결정 7)

다시 열기는 `Db`를 버리고(잠금이 풀린다) `Db::open_with`를 다시 부르는 것이다. 열기는 WAL과 데이터 파일을 처음부터 읽고 재생한다. 응답한 커밋은 sync가 **성공한** 뒤에 응답했으니 디스크에 있다.

**남는 구멍**: Linux에서 sync가 실패한 페이지는 캐시에 "깨끗함"으로 남아 있을 수 있다. 같은 부팅 안에 다시 열면 엔진은 디스크에 없는 바이트(실패한 커밋)를 읽고 재생한 뒤, 그 뒤에 새 커밋을 붙이고 sync한다. 이 sync는 실패한 커밋의 바이트를 다시 쓰지 않는다. 그 뒤 정전이 나면 디스크의 WAL은 실패한 커밋 자리에서 사슬이 끊기고, **그 뒤의 응답한 커밋까지** 잃는다.

| 선택지 | 막는 것 | 대가 |
|---|---|---|
| **A. 그대로 다시 읽음 (지금)** | — | 위의 구멍. 가짜 디스크에서는 생기지 않는다. macOS는 **확인 안 됨** (아래) |
| B. 열기 끝에 정리 한 번 (PostgreSQL의 "복구 끝 체크포인트") | WAL 쪽 구멍: 읽은 내용을 데이터 파일에 다시 쓰고 sync | 정상 종료가 아닌 열기마다 정리 비용. 정리 **도중** 실패한 메타 슬롯이 캐시에만 있는 경우는 못 막는다 |
| C. 열기에서 캐시를 거치지 않고 읽기(`O_DIRECT`, macOS `F_NOCACHE`) | 둘 다 | OS별 코드, 정렬 제약. 큰 변경 |
| D. 같은 프로세스에서 다시 열기 거부 | 없음 | 프로세스를 새로 띄워도 OS 캐시는 남는다 |

**열기 도중의 실패에도 같은 구멍이 있다 (리뷰 P1).** 열기도 디스크에 쓴다. 이 sync들이 실패하면 열기는 오류를 돌려줄 뿐이지만, 같은 프로세스(같은 부팅)에서 다시 열면 캐시를 읽는다.

| 열기 도중 실패한 곳 | 같은 부팅에서 다시 열면 |
|---|---|
| 새 DB의 첫 커밋 (WAL 쓰기·sync) | 캐시의 첫 커밋을 읽고 "있는 DB"로 연다. 디스크에는 없을 수 있다 |
| `.cut` 파일 쓰기·sync | 보관한 바이트가 캐시에만 있을 수 있다. 데이터에는 영향 없음(조사용 파일) |
| 꼬리 자르기 (`set_len` + sync) | 캐시에선 잘린 WAL을 보고 자르기를 건너뛴다. 디스크에는 옛 꼬리가 남아 있을 수 있고, 그 자리에 새 커밋을 덧쓴다 |
| 실패한 열기 뒤 같은 프로세스에서 다시 열기 | 위 세 경우 모두 캐시의 내용을 믿는다 |

**macOS는 확인 안 됨 (리뷰 P6).** 처음 문서는 "macOS(`F_FULLFSYNC`)에서는 생기지 않는다"고 적었는데 근거가 없었다. 아는 것: Linux의 동작은 PostgreSQL fsyncgate 조사(2018)와 커널 문서로 알려져 있다. 모르는 것: macOS(APFS)가 `F_FULLFSYNC` 실패 뒤 캐시 페이지를 어떻게 다루는지는 공개 문서에서 찾지 못했고 실험도 하지 않았다. 그래서 두 OS 모두 "생길 수 있다"로 본다.

**A로 진행하고, 한계를 문서에 남긴다.** 이 구멍을 시험하려면 가짜 디스크가 "sync 실패 뒤 읽기는 새 내용, 디스크는 옛 내용, 나중 sync도 살리지 못함"을 흉내 내야 한다. #56처럼 가짜 디스크의 고장 모델을 넓히는 일이라 **#59**로 넘겼다(B나 C를 그때 고른다). 운영 지침은 "엔진이 멈추면 프로세스를 다시 띄우기 전에 디스크를 점검하고, 가능하면 재부팅이나 다시 마운트 뒤에 연다"이다.

## 8. "배치"와 그룹 커밋 (#28)

이슈의 "그 배치의 클라이언트"는 그룹 커밋을 전제한다. 지금은 커밋 하나가 sync 하나라서 **배치 = 커밋 하나**다. 그룹 커밋이 오면 이렇게 넓어진다.

| 누구 | 받는 것 |
|---|---|
| 실패한 sync에 함께 실린 커밋 전부 | `OutcomeUnknown` (같은 원인을 하나씩 복제, `Arc`라 싸다) |
| 그 뒤 줄에 선 커밋, 그 뒤 모든 요청 | `Stopped` |

커밋 담당 스레드가 멈춤을 정한 **다음에** 배치에 대답하고, 줄의 다음 배치를 꺼내기 전에 멈춤을 확인하면 된다. 5절의 "잠금을 쥔 뒤 확인"이 "커밋 담당 스레드 안에서 확인"으로 바뀐다.

## 9. 바뀐 공개 API

| 무엇 | 바뀜 |
|---|---|
| `Error::Io(io::Error)` → `Error::Io(Arc<io::Error>)` | 리뷰 뒤 바뀜. `Error`가 `Clone`이 됨. `Error::Io(_)`로 맞추는 코드와 `?`(`From<io::Error>`)는 그대로 된다. 안의 값을 꺼내 쓰던 코드는 `&**e`나 `e.kind()`(자동 역참조)로 |
| `Error::OutcomeUnknown(Arc<io::Error>)` | 새로 |
| `Error::Stopped(Arc<Error>)` | 새로 |
| `Txn::commit` | 디스크 실패 시 `Io` → `OutcomeUnknown`. 자동 정리 실패 시 `Err` → `Ok`(엔진은 멈춤). 멈춘 뒤 `Stopped` |
| `Txn::get`·`put`·`delete`·`scan`, `Db::checkpoint`·`close` | 멈춘 뒤 `Stopped` |
| `SimFs::fail_once_after(n)` | 새로 (가짜 디스크) |
