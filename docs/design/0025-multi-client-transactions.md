# 0025. 여러 클라이언트와 접속별 트랜잭션 — 설계

이슈 #37. 서버 첫 관통(#36, 설계 0020)으로 네트워크 너머에서 SQL을 보낼 수 있게 되었지만, 서버는 `QUERY` 하나마다 `oakdb_sql::execute(&db, sql)`를 불러 **문장 하나 = 트랜잭션 하나**(자동 커밋)로만 돌린다. SQL 트랜잭션 명령(#35, 설계 0023, PR #78)은 `BEGIN`부터 `COMMIT`까지 트랜잭션을 들고 있는 **`Session<'db>`** 를 만들었지만, 서버는 아직 그것을 쓰지 않는다. 지금 서버에 `BEGIN`을 보내면 `execute`가 "세션이 필요하다"(`TransactionError::NeedsSession`)고 거절하고, 서버는 이것을 이름 없는 문장 오류 `0x1F`로 보낸다.

이번 티켓에서 **접속마다 세션 하나**를 붙인다. 여러 클라이언트가 동시에 각자 `BEGIN … COMMIT`을 하고, 한 접속의 미커밋 변경은 다른 접속에 보이지 않으며, 접속이 끊기면 열려 있던 트랜잭션은 롤백된다. 엔진과 SQL 층이 이미 대부분을 해 두었으므로, 새로 정할 것은 **서버 쪽의 정책**이다: 트랜잭션 상태 오류를 어떤 코드로 보낼지, 트랜잭션을 쥔 채 노는 접속을 언제 끊을지, 오래 사는 트랜잭션이 엔진에 무엇을 남기는지, 이것을 어떻게 시험할지.

> 구현은 PR #78(티켓 23)이 `main`에 들어간 뒤 시작한다. 이 문서는 PR #78의 `Session`, `Command`, `SqlError::Transaction`을 그대로 쓴다고 가정한다.
>
> **사용자 결정 (2026-11-25): Q1~Q12 모두 추천안대로.**

## 비유: 접속 = 프로세스, 세션 = 그 프로세스의 주소 공간

OS 시간에 배운 그림이 그대로 들어맞는다.

| OS / ft_malloc | 무슨 일이 생기나 | Oakdb 서버에서는 |
|---|---|---|
| 프로세스를 하나 띄운다 | 자기만의 주소 공간이 생긴다. 다른 프로세스는 그 안을 못 본다 | 접속을 받으면 스레드 하나 + **세션 하나**. 그 세션의 미커밋 쓰기는 다른 접속에 안 보인다 |
| `malloc`으로 메모리를 잡는다 | 내 힙에만 있다 | `BEGIN` 뒤의 `INSERT`/`UPDATE`는 트랜잭션의 쓰기 모음(개인 버퍼)에만 들어간다 |
| `free` 없이 프로세스가 죽는다 | **커널이 주소 공간째 회수한다.** ft_malloc에서 `free`를 빼먹어도 프로세스가 끝나면 메모리가 OS로 돌아가는 것과 같다 | 클라이언트가 `COMMIT` 없이 사라지면 세션이 버려지면서(`Drop`) **트랜잭션이 통째로 롤백된다** |
| 세그폴트로 프로세스 하나가 죽는다 | 그 프로세스만 죽고 다른 프로세스는 멀쩡하다 | 접속 스레드가 패닉하면 그 접속만 `0x7F`로 끊기고(그 트랜잭션은 롤백) 서버와 다른 접속은 그대로 |
| `ps`에서 오래 잠자는 프로세스가 메모리를 쥐고 있다 | 아무 일도 안 하는데 자원을 차지한다 | **"idle in transaction"**: `BEGIN`만 하고 가만히 있는 접속이 옛 스냅샷을 붙잡는다 (Q5, Q7) |

Java/Spring으로 치면, 서버의 접속 하나는 HikariCP 풀에 들어 있는 JDBC `Connection` 하나다. `@Transactional`은 메서드가 시작될 때 풀에서 `Connection`을 꺼내 **현재 스레드에 묶고**(`ThreadLocal`) `setAutoCommit(false)`를 부른다. 그 메서드 안의 모든 SQL은 그 `Connection`, 즉 서버 쪽에서는 **그 접속의 세션** 하나의 트랜잭션 안에서 돈다. 다른 스레드의 `@Transactional`은 다른 `Connection` = 다른 세션이라 서로의 미커밋 변경을 못 본다. 애플리케이션 서버가 죽어 TCP가 끊기면 DB(MySQL, PostgreSQL)는 그 접속의 트랜잭션을 롤백한다. 이번 티켓은 Oakdb에서 그 "DB 쪽"을 만드는 일이다. 또 MySQL의 `wait_timeout`(노는 접속을 8시간 뒤 끊음)과 PostgreSQL의 `idle_in_transaction_session_timeout`이 Q5의 선택지이고, HikariCP 문서가 "`maxLifetime`을 DB의 접속 시간 제한보다 짧게 잡으라"고 하는 이유가 Q5의 trade-off다.

```
클라이언트 A                 서버                                  클라이언트 B
  BEGIN ───────────▶  스레드 A: session_a.execute("BEGIN")   → DONE
  INSERT (1,'x') ──▶  session_a의 쓰기 모음에만               → AFFECTED 1
                                                 ◀──────────── SELECT * FROM t
                      스레드 B: session_b (자동 커밋)       → ROWS []   (1은 안 보임)
  (소켓 끊김) ✂        스레드 A 끝 → session_a Drop → 롤백
                                                 ◀──────────── SELECT * FROM t
                                                    → ROWS []   (영원히 안 보임)
```

## Q1. 세션은 어디에 있고 언제까지 사나

| 선택지 | 모양 | 장점 | 단점 |
|---|---|---|---|
| **A. 접속 스레드의 지역 변수** | `serve()`가 인사(HELLO/READY)를 마친 뒤 `let mut session = Session::new(&shared.db);`, 모든 `QUERY`를 `session.execute(sql)`로 | 수명이 저절로 맞는다: `serve()`가 어떤 길로 끝나든(소켓 닫힘, 깨진 프레임, 패닉) 세션이 `Drop`되어 롤백. 엔진·SQL 층을 안 고침. ADR 0010이 이 모양을 전제로 정해졌다 | 세션을 다른 스레드로 넘기거나 모아 볼 수 없다(지금 필요 없음) |
| B. 서버가 `HashMap<접속 번호, Session>`을 들고 있음 | | 관리자가 "열린 트랜잭션 목록"을 볼 수 있음 | `Session<'db>`가 `Db`를 빌리므로 `Arc<Shared>` 옆에 두면 자기 참조가 된다. 엔진에 소유형 트랜잭션이 필요(설계 0023 T1-B) |
| C. 트랜잭션 중인 접속만 전용 스레드, 나머지는 풀 | | 스레드 수 절약 | ADR 0010을 뒤집는다. #66(async A/B)의 몫 |

**추천 A.** 세션이 끝나는 모든 경우를 표로 고정하고, 각 줄을 테스트 하나로 만든다(Q10).

| 접속이 끝나는 경우 | 서버가 보는 것 | 트랜잭션 |
|---|---|---|
| 클라이언트가 소켓을 정상으로 닫음 | `read_frame`이 `Ok(None)` | 롤백 |
| 프레임 도중에 끊김 | `FrameError::Truncated` | 롤백 |
| 깨진 프레임·16 MiB 초과로 서버가 끊음 (`0x40`, `0x41`) | `send_error` → `Next::Close` | 롤백 |
| 접속 스레드 패닉 (`0x7F`) | `catch_unwind`까지 되감기 | 롤백 (Q8) |
| 노는 시간 초과로 서버가 끊음 (Q5) | 읽기 시간 초과 | 롤백 |
| 클라이언트가 FIN 없이 사라짐(랜선 뽑힘, 프로세스 정지) | **아무것도 안 옴.** 스레드는 영원히 읽기에서 기다린다 | Q5가 없으면 **영원히 열림** |
| 서버 프로세스가 죽음 | — | 미커밋 쓰기는 메모리에만 있었으므로 다시 열면 없음 (WAL에 간 적 없음) |
| `COMMIT`을 보낸 직후 클라이언트가 끊김 | 커밋은 끝까지 진행, 응답 쓰기만 실패 | **커밋될 수 있다.** 클라이언트는 결과를 모른다. 모든 DB가 같고, 문서에 적는다 |

## Q2. 트랜잭션 상태 오류의 통신 코드

세션을 쓰면 `NeedsSession`은 서버에서 더 이상 나오지 않는다. 남는 것은 둘이다: 트랜잭션 중 `BEGIN`(`AlreadyBegun`), 트랜잭션 밖 `COMMIT`/`ROLLBACK`(`NotBegun`). 둘 다 **열린 트랜잭션은 그대로**다(0023 T4).

| 선택지 | 코드 | 장점 | 단점 |
|---|---|---|---|
| A. 지금처럼 `0x1F`(위에 없는 문장 오류) | | 통신 규칙을 안 고침 | 클라이언트가 "트랜잭션이 이미 끝났다"(예: `COMMIT`이 충돌로 실패한 뒤 습관적 `ROLLBACK`)를 메시지 글자로만 구분 |
| **B. 새 코드 하나 `0x0B` "트랜잭션 상태에 안 맞는 명령"** | 메시지가 둘을 구분 ("already in a transaction" / "no transaction is open") | 범위 `0x01–0x1F`(문장이 잘못됨, 접속 유지)에 맞음. 0023 T11이 이미 "새 종류 하나, 서버 코드는 #37에서"로 정함 | 표에 한 줄 |
| C. 둘로 나눔 `0x0B`, `0x0C` | | 메시지를 안 봐도 구분 | 클라이언트가 할 일이 둘 다 "상태를 다시 맞춘다"로 같다. 세분은 #34의 몫 |

**추천 B.** `Type`·`Arithmetic`이 `0x1F`로 가는 것은 이번에 건드리지 않는다(#34).

## Q3. BEGIN/COMMIT/ROLLBACK의 응답, 클라이언트가 트랜잭션 중인지 아는 법

세션은 성공한 세 명령에 `Output::Done`을 돌려준다(0023 Q2). 통신 규칙의 `DONE`(`0x84`, 데이터 없음)이 이미 있다. 남는 질문은 **CLI 프롬프트를 `oakdb*>`로 바꾸는 것처럼, 클라이언트가 지금 트랜잭션 중인지 어떻게 아나**다.

| 선택지 | 하는 일 | 장점 | 단점 |
|---|---|---|---|
| **A. 응답은 `DONE`, 통신 규칙 그대로. 상태는 클라이언트가 규칙으로 안다** | 규칙(0023 T6): `BEGIN`이 `DONE`이면 트랜잭션 중. `COMMIT`/`ROLLBACK`은 **어떤 응답이든** 트랜잭션을 끝낸다(`0x0B`면 원래 없었음). 나머지 문장은 상태를 안 바꾼다. 접속이 끊기면 트랜잭션은 없다 | 바이트가 하나도 안 바뀜. 서버가 상태를 몰래 바꾸는 길이 없도록(Q5에서 롤백 대신 **끊기**를 고르면) 규칙이 언제나 맞음 | 클라이언트가 보낸 문장이 BEGIN/COMMIT/ROLLBACK인지 알아야 함. `Client` 라이브러리가 `oakdb_sql`의 파서로 판별(이미 의존함) |
| B. 모든 응답 끝에 상태 바이트 1개 (PostgreSQL `ReadyForQuery`의 `I`/`T`처럼) | 통신 규칙 버전 2 | 클라이언트가 추측할 필요 없음. 서버가 언젠가 상태를 혼자 바꾸게 되어도 맞음 | `ROWS`·`AFFECTED`·`DONE`·`ERROR` 인코딩과 그 테스트를 모두 고침. 버전이 올라 옛 CLI는 인사에서 거절됨 |
| C. 새 요청 `STATUS` | 물어보면 답함 | 기존 응답 그대로 | 왕복이 하나 더. 쓸 일이 프롬프트뿐 |

**추천 A.** 규칙이 단순하고 엔진 API 모양(`commit(self)`가 트랜잭션을 가져감)과 같아서 추측이 아니라 계산이다. B는 서버가 접속을 유지한 채 트랜잭션을 끝내는 길(예: 시간 초과 롤백 후 유지)이 생길 때 한다. `docs/protocol.md` 2절의 "QUERY 하나 = 트랜잭션 하나"는 이 규칙으로 바꿔 쓴다.

## Q4. 충돌을 클라이언트에 어떻게 알리나

이슈 완료 기준 "충돌 등 오류가 종류별로 클라이언트에 전달된다". 트랜잭션이 생기면 **같은 오류라도 클라이언트가 다시 할 일이 달라진다.**

| 오류 | 언제 | 트랜잭션은 | 클라이언트가 할 일 |
|---|---|---|---|
| `0x01–0x0A` 문장 오류 | 트랜잭션 중 아무 문장 | **열린 채**, 그 문장만 없던 일 (0023 T5) | 고쳐서 다시, 또는 ROLLBACK |
| `0x0B` 상태 오류 (Q2) | 엉뚱한 BEGIN/COMMIT/ROLLBACK | 그대로 | 상태를 다시 맞춤 |
| `0x20` 충돌 | 트랜잭션 안의 `COMMIT` | **끝남, 아무것도 안 씀** | **BEGIN부터** 다시 |
| `0x20` 충돌 | 자동 커밋 문장 | 그 문장의 트랜잭션이 끝남 | 그 문장만 다시 |
| `0x25` 결과 모름 / `0x26` 멈춤 | 디스크 실패 | 끝남 / 열린 채(어차피 커밋 불가) | 서버 재시작 |
| `0x7F` 내부 오류 (끊김) | 패닉 | 롤백됨 | 다시 접속해 BEGIN부터 |
| 새 시간 초과 코드 (끊김, Q5) | 놀다가 | 롤백됨 | 다시 접속해 BEGIN부터 |

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. `0x20` 하나. 메시지가 "트랜잭션 전체가 롤백됨, BEGIN부터"를 덧붙임(0023 Q4가 세션에서 이미 덧붙임)** | 코드 그대로. 클라이언트는 자기가 트랜잭션 중이었는지 Q3-A로 안다 → 무엇을 다시 할지 계산 가능 | 메시지를 안 보는 클라이언트는 위 표를 스스로 적용해야 함 |
| B. 둘로 나눔: `0x20`(문장 다시), `0x27`(트랜잭션 다시) | 코드만 보고 다시 할 일을 앎 | 같은 원인(먼저 커밋한 쪽이 이김)에 코드 둘. "다시 실행하면 될 수 있다"는 뜻은 같음 |
| C. A + 충돌한 키(표 이름, 기본 키)를 메시지에 | 디버깅이 쉬움 | 엔진 키 바이트를 SQL 이름으로 되돌리는 코드가 필요. #34에서 |

**추천 A.** 위 표를 `docs/protocol.md`에 "트랜잭션 안에서 오류가 오면" 절로 넣는다. Spring으로 치면 `CannotAcquireLockException`/`ConcurrencyFailureException`을 받으면 `@Retryable`이 **메서드 전체**(= BEGIN부터)를 다시 돌리는 것과 같다.

## Q5. 트랜잭션을 쥔 채 노는 접속의 시간 제한

지금 서버는 읽기 시간 제한이 없다. 그래서 `BEGIN`만 하고 사라진(FIN 없이) 클라이언트의 트랜잭션은 **서버가 다시 뜰 때까지** 열려 있고, 그동안 옛 스냅샷과 충돌 칠판을 붙잡는다(Q7). 접속 자리(512개 중 하나)도 계속 차지한다.

| 선택지 | 하는 일 | 장점 | 단점 |
|---|---|---|---|
| A. 없음, 문서로만 | | 할 일 없음 | 위 문제가 그대로. 이슈 "끊기면 롤백"이 **FIN 없는 끊김**에선 지켜지지 않음 |
| **B. 트랜잭션 중에만 시간 제한** `--idle-in-transaction-timeout`, 기본 **60초**, `0`이면 끔. 넘으면 새 코드 **`0x47` "트랜잭션 중 너무 오래 놀았음"** 을 보내고 **접속을 끊는다**(세션 Drop → 롤백) | 세션이 트랜잭션 중일 때만 소켓에 `set_read_timeout(Some(t))`, 아니면 `None` | 자원을 쥔 접속만 끊음. PostgreSQL `idle_in_transaction_session_timeout`과 같은 동작(그쪽 기본값은 꺼짐). 끊으므로 Q3-A의 규칙이 계속 맞음 | 느린 사람이 CLI에서 BEGIN 뒤 커피를 마시면 끊김. 그래서 값은 옵션 |
| B'. B와 같되 끊지 않고 롤백만, 접속 유지 | | 사람에게 친절 | 클라이언트는 아직 트랜잭션 중이라 믿는데 다음 문장이 자동 커밋으로 반영된다. 0023 5-1절이 피하려 한 SQLite의 함정 그대로. Q3-B(상태 바이트)가 필요 |
| C. B + 트랜잭션 밖의 노는 접속도 `--idle-timeout` (기본 끔) | | 설계 0020이 남긴 slowloris(노는 접속 512개가 자리를 다 차지) 대비 수단이 생김 | 기본값을 켜면 커넥션 풀이 일부러 열어 둔 접속이 끊긴다. MySQL `wait_timeout` 8시간 때문에 HikariCP가 "Connection is not available"을 내던 고전적 사고 |

**추천 B + C(기본 끔).** 트랜잭션 밖의 노는 접속은 엔진 자원을 쥐지 않으므로(자리 하나 + 스택 256 KiB) 기본은 끄고 옵션만 준다. 몇 가지는 같이 정한다.

| 세부 | 추천 | 이유 |
|---|---|---|
| 무엇을 "논다"고 보나 | **다음 프레임의 첫 바이트를 기다리는 시간**만. 문장 실행 시간(커밋 sync 포함)은 안 센다 | 서버가 느린 것을 클라이언트 탓으로 끊으면 안 됨 |
| 프레임 도중에 멈춘 경우 | 같은 시간 제한으로 끊음 | 반쯤 보낸 프레임은 어차피 쓸 수 없음 |
| 아주 천천히 흘리는 클라이언트(59초마다 1바이트) | 이번엔 막지 않음, 기록만 | 읽기 한 번마다의 시간 제한이라 못 잡음. 프레임 전체 마감 시각은 #38 이후 |
| 응답 쓰기 시간 제한 | 트랜잭션 중이면 같은 값으로 `set_write_timeout` | 큰 `ROWS`를 보내는데 클라이언트가 안 읽으면 스레드가 쓰기에서 영원히 멈추고 트랜잭션도 열린 채 |
| 시간 초과 오류 종류 | macOS·Linux는 `WouldBlock`, 다른 OS는 `TimedOut`일 수 있음 → **둘 다** 시간 초과로 처리 | ADR 0003 (두 OS에서 같은 동작) |
| 끊을 때 로그 | `oakdb: <peer> idle in a transaction for 60s; rolled back and closed` | 운영자가 원인을 앎 |

## Q6. 열린 트랜잭션 수의 상한

접속 하나에 트랜잭션은 많아야 하나이므로 **열린 트랜잭션 수 ≤ 접속 수 ≤ 512**가 이미 성립한다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 따로 두지 않음. 접속 상한이 곧 트랜잭션 상한** | 할 일 없음. 512개가 모두 BEGIN한 상태를 테스트로 보임 | 트랜잭션 하나의 쓰기 모음 크기는 여전히 무제한(클라이언트가 16 MiB INSERT를 계속 보내면 메모리가 계속 큼) |
| B. `--max-transactions` (< 접속 상한), 넘는 BEGIN은 새 코드 `0x27` | 읽기 전용 접속은 많이, 쓰는 트랜잭션은 적게 | 실제로 줄일 근거(측정)가 아직 없음. 기다리게 할지 거절할지라는 새 질문이 생김 |
| C. 트랜잭션 하나의 쓰기 모음 상한 (예: 64 MiB, 넘으면 문장 오류) | 클라이언트 하나가 메모리를 다 먹는 것을 막음 | 엔진 `Txn`에 크기 세기가 필요. 이 티켓의 주제(접속별 트랜잭션)와 거리가 있음 |

**추천 A.** C는 위험으로 기록하고 Q12의 실험에서 "트랜잭션 하나가 쓰기 모음에 쌓을 수 있는 양"을 한 번 재서 남긴다. 실제로 문제가 되면 따로 티켓.

## Q7. 오래 사는 트랜잭션(옛 스냅샷)이 엔진에 주는 부담

자동 커밋에서는 트랜잭션이 몇 ms만 살았다. 이제는 클라이언트가 원하는 만큼 산다. 엔진에서 무엇이 늘어나나:

| 붙잡는 것 | 왜 | 얼마나 | 언제 풀리나 |
|---|---|---|---|
| **옛 트리 페이지** | 스냅샷 = `BEGIN` 때 잡은 `Arc<Tree>`(설계 0015). 커밋은 바뀐 페이지만 복사해 새 트리를 만든다. 옛 페이지는 그것을 가리키는 스냅샷이 있는 한 메모리에 남는다 | 스냅샷 하나당 최대 "그 뒤 바뀐 페이지 수". 최악은 트리 하나 크기만큼 더. **시작 시점이 다른** 오래된 스냅샷이 여럿이면 각자 다른 판을 붙잡는다 | 그 트랜잭션이 끝날 때 |
| **충돌 칠판**(`RecentWrites`) | 가장 오래 열린 트랜잭션이 시작한 뒤의 모든 커밋의 키를 남긴다(설계 0016) | 그동안의 커밋 수 × 키 수. 초당 1000커밋이면 60초에 6만 커밋 분 | 가장 오래된 트랜잭션이 끝날 때 |
| 충돌 확률 | 스냅샷이 오래될수록 "그 뒤 남이 쓴 키"가 많다 | 트랜잭션 길이에 비례 | — |
| 디스크(WAL, 체크포인트) | 미커밋 쓰기는 WAL에 안 가고, 체크포인트는 최신 트리만 씀 | 영향 없음 (검증에서 확인) | — |

Java로 치면 GC 루트가 옛 객체 그래프를 붙잡아 Old 영역이 커지는 것과 같다. PostgreSQL에서는 오래된 트랜잭션이 VACUUM을 막아 표가 부푸는 문제("bloat")로 나타난다. Oakdb는 디스크가 아니라 **메모리**에서 같은 일이 일어난다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. Q5의 시간 제한만 | 노는 트랜잭션은 60초로 묶임 | **쉬지 않고 문장을 보내는** 긴 트랜잭션은 못 묶음 |
| **B. A + 보이게 하기: 엔진 `Stats`에 `open_transactions`(열린 수)와 `kept_commits`(칠판에 남은 커밋 수)를 더하고, 서버가 가장 오래된 트랜잭션이 일정 시간(예: 5분)을 넘으면 경고 로그** | 운영자가 원인을 찾을 수 있음. 테스트가 "끊긴 뒤 열린 트랜잭션이 0으로 돌아왔다"를 숫자로 확인할 수 있음(Q10) | 엔진에 숫자 둘 (`Stats`가 이미 있어 작음) |
| C. 최대 트랜잭션 나이 `--max-transaction-age`, 넘으면 끊음 | 메모리 상한이 생김 | 정상적인 긴 보고서 쿼리도 끊김. 근거(측정) 없음 |

**추천 B.** 그리고 Q12의 실험에서 "트랜잭션 하나를 열어 두고 다른 접속이 계속 커밋할 때 메모리와 칠판 크기가 어떻게 자라나, 그 트랜잭션이 끝나면 돌아오나"를 재서 숫자로 남긴다. C는 그 숫자가 나쁠 때 한다.

## Q8. 세션 안의 패닉

지금도 접속 스레드의 패닉은 `serve_guarded`의 `catch_unwind`가 받아 `0x7F`를 보내고 접속만 끊는다. 세션은 `serve()`의 지역 변수이므로 되감기 중에 `Drop`되어 롤백된다. `Txn::drop`이 잡는 잠금은 독이 들어도 `into_inner`로 계속하고, 커밋 스레드의 패닉은 엔진이 이미 `OutcomeUnknown`/`Stopped`로 바꾼다(설계 0018).

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 지금 그대로: 접속을 끊고(0x7F) 롤백** | 프로세스처럼 "한 접속의 사고는 그 접속에서 끝난다". 클라이언트는 끊김 = 트랜잭션 없음으로 단순하게 앎 | 사람이 CLI에서 오래 쌓은 트랜잭션을 잃음 (버그일 때만) |
| B. 문장마다 `catch_unwind`, 접속 유지 | 접속이 살아남음 | 패닉 뒤의 세션 상태를 믿을 수 없어 어차피 롤백해야 함 → 서버가 접속 유지 중에 트랜잭션을 몰래 끝내는 길(Q3·Q5에서 피한 것)이 생김 |
| C. 패닉이면 서버 전체를 멈춤(`panic = "abort"`) | 상태가 확실 | 접속 하나의 버그가 모든 접속을 죽임 |

**추천 A.** 테스트로 고정한다: 지금의 `a_panic_while_serving_sends_0x7f` 단위 테스트 옆에, **트랜잭션 중인 세션을 가진 채** 패닉해도 그 트랜잭션의 쓰기가 남지 않고 `open_transactions`가 0으로 돌아오는 테스트를 더한다(패닉은 테스트 전용 훅으로 심는다. 지금 테스트가 심을 수 있는 실제 패닉 경로는 없다).

## Q10. 테스트

| 테스트 | 어디 | 무엇을 |
|---|---|---|
| 두 접속 결정적 시나리오 | `oakdb-server/tests/transactions.rs` (새 파일), 실제 서버 + `Client` 둘 | ① A의 미커밋 INSERT가 B에 안 보임, A COMMIT 뒤엔 보임. ② A BEGIN 뒤 B가 커밋한 행이 A에 안 보임(스냅샷). ③ A·B가 같은 행 UPDATE → 나중 COMMIT이 `0x20`, 그 뒤 A는 자동 커밋 상태(`Client::in_transaction() == false`), 표는 이긴 쪽 값. ④ `0x0B` 둘(BEGIN 두 번, 밖의 COMMIT) 뒤에도 열린 트랜잭션이 살아 있음 |
| 끊김 = 롤백 (Q1 표의 각 줄) | 같은 파일 | 정상 닫기, 프레임 도중 끊기, 깨진 프레임(`0x40`), 시간 초과(`0x47`, 시간을 200ms로 줄여서). 확인 방법: (가) 다른 접속에서 그 쓰기가 **끝까지** 안 보임, (나) `--max-connections 1`로 띄워 끊긴 뒤 새 접속이 받아들여짐 = 스레드와 세션이 끝났음, (다) 서버 단위 테스트에서 `Stats::open_transactions`가 0으로 돌아옴 |
| 여러 접속 카운터 | 같은 파일 | 접속 8개가 각자 `BEGIN; SELECT n; UPDATE … n = n+1; COMMIT`을 `0x20`이면 BEGIN부터 다시 하며 N번 → 최종 n = 8N (잃어버린 갱신 없음, 네트워크 너머에서) |
| 수백 접속이 동시에 트랜잭션 | 같은 파일 | 접속 300개(ADR 0010의 CI 숫자)가 모두 BEGIN, 각자 다른 키 INSERT, 모두 열린 채 장벽, 그다음 모두 COMMIT → 300행 모두 있음 |
| **모델 비교 속성 테스트** | `oakdb-server/tests/txn_model.rs` | proptest가 "(접속 0~2 중 하나, 문장)" 열을 만든다: BEGIN/COMMIT/ROLLBACK/INSERT/UPDATE/DELETE/SELECT, 가끔 끊기. **한 번에 하나씩** 실제 서버로 보내 순서가 결정적이다. 모델 = 커밋된 표 + 접속별 (스냅샷, 쓰기 모음), 충돌은 "내 스냅샷 뒤 남이 커밋한 키를 썼나". 매 단계 ① 응답(행·개수·오류 코드), ② 접속별 트랜잭션 여부가 모델과 같은지 |
| 이력 검사기 재사용 (선택) | PR #79(티켓 17)가 들어오면 | 0024의 무작위 작업을 `Client`로 돌려 같은 검사기에 넣는다. 들어오지 않았으면 이번엔 건너뛴다 |
| 두 OS | CI | 시간 초과 테스트가 macOS·Linux에서 같은 코드(`0x47`)를 받는지 (Q5 `WouldBlock`/`TimedOut`) |

모든 테스트 소켓에는 지금처럼 읽기 시간 제한(10초)을 걸어, 버그로 서로 기다리면 CI가 멈추지 않고 실패하게 한다.

## Q11. 완료 기준

| 이슈 완료 기준 | 이 설계에서 무엇으로 채우나 | 확인하는 테스트 |
|---|---|---|
| 여러 클라이언트가 동시에 SQL을 실행한다 | Q1-A: 접속마다 세션 | 카운터, 300접속 동시 트랜잭션 |
| 한 접속의 미커밋 변경이 다른 접속에 보이지 않는다 | 엔진 스냅샷 격리 + 접속별 세션 | 시나리오 ①②, 모델 테스트 |
| 접속이 끊기면 진행 중인 트랜잭션이 롤백된다 | 세션 `Drop` + Q5(FIN 없는 끊김) + Q8(패닉) | 끊김 = 롤백 묶음, 장애 실험 |
| 충돌 등 오류가 종류별로 클라이언트에 전달된다 | `0x20`, `0x0B`(Q2), `0x47`(Q5), Q4 표 | 시나리오 ③④, 모델 테스트의 오류 코드 비교 |
| 설계 → 구현 → 검증 → 회고 기록 | 이 문서, `docs/experiments/`, `docs/retros/0025-…` | — |

여기에 이 설계가 더하는 기준: `docs/protocol.md` 갱신(Q9), 두 OS CI 통과, `Stats`의 숫자 둘(Q7).

## Q12. 검증 계획

| 검증 | 무엇을 | 결과 위치 |
|---|---|---|
| 두 축 코드 리뷰 (Standards / Spec) | PR의 기준점(base)부터. Rust 쪽 관점: 세션 수명이 `serve()` 안에 갇혔나, `set_read_timeout`을 트랜잭션 상태가 바뀔 때마다 맞게 다시 거나, `0x47`이 `closes()`에 들어갔나, 잠금을 쥔 채 소켓 I/O를 하지 않나 | PR 댓글 |
| 눈 가린 테스터 | 이슈 #37, 이 문서, ADR 0006·0010, `docs/protocol.md`만 보고 `Client`로 테스트를 씀. 구현은 안 봄 | PR 댓글, `review/blind-ticket25` 브랜치 |
| 장애 실험 1: 서버를 죽이기 | 접속 여럿이 트랜잭션 중이거나 COMMIT을 보낸 순간 서버를 `kill -9` → 다시 띄움. **응답받은 커밋은 모두 있고, 미커밋·응답 못 받은 커밋은 전부 있거나 전부 없음** | `docs/experiments/` |
| 장애 실험 2: 클라이언트가 FIN 없이 사라짐 | 트랜잭션 중인 클라이언트 프로세스를 `SIGSTOP`(멈춤) → 서버가 Q5 시간 뒤 끊고 롤백하는지, 그동안 `kept_commits`가 자라다 돌아오는지 | 같은 문서 |
| 메모리 측정 | Q7: 트랜잭션 하나를 연 채 다른 접속이 10만 번 커밋할 때 서버 RSS·`kept_commits`, 끝난 뒤 돌아오는지. Q6: 트랜잭션 하나에 쌓을 수 있는 쓰기 양 | 같은 문서 |
| 벤치마크 / A/B | **이번 티켓은 성능 주장을 하지 않으므로 A/B는 하지 않는다.** 자동 커밋 경로가 `execute` → `Session::execute`로 바뀌므로, 자동 커밋 한 줄 INSERT 왕복 시간만 전후로 재어 기록(참고). 네트워크 처리량은 #39 | `docs/benchmarks/` (참고 기록) |

성능 주장을 하게 되면(예: "세션을 붙여도 자동 커밋이 느려지지 않는다"를 완료 기준에 넣기로 하면) 그때 A/A 대조와 함께 A/B를 한다.
