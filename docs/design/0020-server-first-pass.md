# 0020. 서버 첫 관통: 통신 규칙과 CLI — 설계

이슈 #36. 지금까지 Oakdb는 **같은 프로그램 안에서만** 쓸 수 있었다. 엔진과 SQL 층(#31)은 라이브러리라서, `oakdb_sql::execute(&db, "SELECT ...")`를 부르는 코드가 DB와 같은 프로세스에 있어야 한다. 이번 티켓에서 처음으로 **네트워크 너머**에서 SQL을 보낼 수 있게 된다. 서버가 포트를 열고 기다리면, CLI 클라이언트가 접속해 SQL 문장을 보내고, 서버는 `execute`를 부른 결과(행, 바뀐 행 수, 오류)를 돌려준다. 그 사이에서 오가는 바이트의 모양이 **통신 규칙**이고, 이슈 #4에서 "직접 만든 간단한 이진 규칙(길이 + 명령 + 데이터)"으로 정했다. 여러 접속이 각자 트랜잭션을 갖는 것(#37), 정상 종료(#38), 네트워크 벤치마크(#39)는 뒤 티켓이다. 이 문서는 그 셋이 얹힐 자리를 남겨 두되 설계하지는 않는다.

**비유**: 서버는 **전화 주문을 받는 식당**이다.

- **접속 처리 방식**은 직원 배치다. Java로 치면 **Tomcat(예전 BIO 커넥터)**은 손님(접속)마다 직원(스레드) 하나를 붙인다. 직원은 손님이 말할 때까지 수화기를 들고 기다린다. 단순하고, 직원이 주방(디스크) 앞에서 기다려도 다른 손님에게 피해가 없다. 대신 손님이 만 명이면 직원도 만 명이다. **Netty(이벤트 루프)**는 직원 몇 명이 여러 전화를 번갈아 받는다. 손님이 많아도 직원 수가 늘지 않지만, 한 직원이 주방 앞에서 오래 서 있으면 그 직원이 맡은 다른 전화가 전부 멈춘다. 그래서 "오래 걸리는 일"은 따로 빼서 맡겨야 한다. Oakdb의 커밋은 디스크 기록(sync)을 기다리는 **오래 걸리는 일**이다.
- **통신 규칙**은 주문서 양식이다. 택배 상자에 **무게를 먼저 적어 두면** 받는 쪽은 상자를 열기 전에 얼마나 받아야 하는지 안다. 프레임 맨 앞의 **길이**가 그 역할이다. 길이 다음의 **명령 바이트**는 "주문인지, 영수증인지, 항의인지"를 적는 칸이다.
- **CLI**는 손님용 전화기다. 손님이 한 줄씩 말하다 `;`로 "주문 끝"을 알리면 주문서를 보내고, 영수증(결과)을 표로 읽어 준다.

```
CLI                                              서버 (oakdb serve)
 │  HELLO  "OAKDB" 버전 1                           │
 │ ───────────────────────────────────────────────▶ │
 │                                    READY 버전 1   │
 │ ◀─────────────────────────────────────────────── │
 │  QUERY "SELECT name FROM users WHERE id = 1"     │
 │ ───────────────────────────────────────────────▶ │  oakdb_sql::execute(&db, sql)
 │                       ROWS [name] [('kim')]      │
 │ ◀─────────────────────────────────────────────── │
 │  QUERY "INSERT INTO users VALUES (1, 'lee')"     │
 │ ───────────────────────────────────────────────▶ │
 │            ERROR 0x08 "a row with this primary…" │
 │ ◀─────────────────────────────────────────────── │

바이트로 (모든 수는 빅엔디언):
QUERY  00 00 00 24 | 02 | 53 45 4c 45 43 54 20 …          길이 36 = 명령 1 + SQL 35바이트
ROWS   00 00 00 15 | 82 | 00 01 | 00 04 6e 61 6d 65 | 00 00 00 01 | 02 00 00 00 03 6b 69 6d
       길이 21       명령  열 1개   "name"              행 1개        TEXT 'kim'
```

## 1. 접속 처리: 스레드냐 비동기냐 (S1)

지도(#1)의 "아직 안 정한 것"에 남아 있던 질문이다. 스펙(#12)은 "접속마다 스레드 하나(잠정)"라고 적어 두었다. 이번에 확정한다.

| | A. 접속마다 스레드 (Tomcat BIO식) | B. 비동기 런타임 tokio (Netty식) | C. 스레드 풀 + 대기열 |
|---|---|---|---|
| 모양 | `accept()`할 때마다 `thread::spawn`. 그 스레드가 읽기 → `execute` → 쓰기를 반복 | 작업(task) 수천 개를 스레드 몇 개가 번갈아 돌림 | 정해진 수의 스레드가 접속을 나눠 맡음 |
| 커밋의 디스크 기록(블로킹) | 그 스레드만 기다린다. 다른 접속은 영향 없음 | 그대로 부르면 **같은 일꾼 스레드의 다른 작업이 전부 멈춘다.** `spawn_blocking`으로 따로 빼야 함 | A와 같음. 단 풀이 다 차면 새 접속이 기다림 |
| #37 접속별 트랜잭션 | `Txn<'db>`가 `Db`를 빌린다. 스레드가 `Arc<Db>`를 쥐고 그 안에서 `begin()`하면 끝 | 작업은 `'static`이어야 해서 `Db`를 빌리는 `Txn<'db>`를 `.await` 너머로 들고 다니기 어렵다. 엔진 API를 바꾸거나(소유하는 트랜잭션) 트랜잭션마다 전용 스레드 | A와 같음 |
| 접속 수 한계 | 스레드 하나에 스택(기본 2 MiB 예약, 실제로 쓰는 만큼만 메모리). 수백~수천은 무리 없음 | 수만도 가능 | 풀 크기만큼 동시 처리 |
| 코드·의존성 | `std::net`만. 읽기 쉬움 | tokio + async 함수. 배울 것이 많아짐 | std만, 풀 코드 직접 작성 |
| 정상 종료(#38) | 스레드마다 끝났는지 기다림(`join`). 읽기에 걸린 스레드는 소켓 닫기로 깨움 | 취소 토큰 등 도구가 풍부 | A와 비슷 |

**추천: A.** 이유:

1. **엔진이 이미 블로킹이다.** 커밋은 WAL을 sync할 때까지 돌아오지 않고, 그동안 엔진 잠금(`committed`)을 쥐고 있어 다른 접속의 `begin()`도 기다린다(`db.rs`, #27·#28에서 풀 예정). 비동기로 가도 결국 블로킹 일을 스레드로 빼야 하니 얻는 것이 적다.
2. **목표 규모가 작다.** #39 벤치마크는 클라이언트 1~N개, N은 수십 수준이다. 접속 만 개를 버틸 이유가 아직 없다.
3. **#37이 단순해진다.** 접속 하나 = 스레드 하나 = 그 스레드가 쥔 `Txn` 하나. 접속이 끊기면 스레드가 끝나고 `Txn`이 drop되어 자동 롤백된다(엔진이 이미 보장). 비동기라면 이 수명을 따로 설계해야 한다.

**나중에 바꾸는 비용**: 통신 규칙(S2~S5)과 CLI는 **그대로**다. 바뀌는 것은 서버 모듈의 접속 루프(읽기·쓰기 함수가 async가 됨)와 #37의 트랜잭션 보관 방식이다. 엔진의 `Txn<'db>` 수명 때문에 엔진 API까지 건드릴 수 있어서 "쉽게 되돌릴 수 있다"고는 못 한다. 그래서 **ADR 0010**(`docs/adr/0010-thread-per-connection.md`)으로 남기고, 다시 볼 조건을 "#39에서 스레드 수가 처리량의 병목으로 보일 때"로 적는다.

## 1-1. 손님 수백 명 (S1에 더한 요구)

사용자 요구: **"손님 수백 명도 감당."** 접속마다 스레드 방식으로 충분하다. 다만 "몇 명까지, 넘으면 어떻게"를 숫자로 정해 둔다. 식당으로 치면 **좌석 수를 정하고, 꽉 차면 문 앞에서 "자리가 없습니다"라고 말하는 것**이다. 좌석 수를 안 정하면 손님이 끝없이 들어와 주방(메모리, 파일 기술자)이 먼저 무너진다.

| 무엇 | 정한 것 | 이유 |
|---|---|---|
| 접속 상한 | `--max-connections`, **기본 512** | "수백"의 위쪽 끝을 덮고(300접속 테스트보다 넉넉), 스레드 512개 × 256 KiB = 스택 예약 128 MiB로 작다. 파일 기술자도 약 580개면 되어 어느 OS에서든 한도를 올려 맞출 수 있다. 1024 이상은 #39가 필요를 보여 줄 때 |
| 상한을 넘으면 | 받아들인 직후 `ERROR 0x45 "too many connections (max 512)"`를 보내고 끊는다. 인사(HELLO)를 기다리지 않는다 | 클라이언트가 이유를 안다. OS 대기열에 조용히 쌓아 두면 손님은 멈춘 서버와 구별할 수 없다 |
| 접속 스레드 스택 | **256 KiB** (Rust 기본은 2 MiB) | 접속 스레드가 하는 일은 얕다: 프레임 읽기(재귀 없음), SQL 파서(재귀 하강이지만 문법에 중첩이 없어 깊이가 상수), 엔진 트리 내려가기(반복문), 큰 값은 힙. 512 × 2 MiB = 1 GiB를 예약할 이유가 없다. 실제 메모리는 쓰는 만큼만 잡히므로 평소 이득은 주소 공간과, 메모리 예약을 엄격히 세는 Linux 설정(`vm.overcommit_memory=2`)에서의 여유다. 넘치면 Rust는 보호 페이지에서 **분명한 메시지와 함께 프로세스를 멈춘다**(조용한 손상 없음). 1 MiB BLOB 왕복 테스트로 확인 |
| 파일 기술자 한도 | 서버가 시작할 때 soft 한도를 `상한 + 64`까지 올린다(hard 한도 안에서, macOS는 `OPEN_MAX` 10240도 넘지 않게). 올려도 모자라면 **시작을 거부**하고 "`ulimit -n`을 올리거나 `--max-connections`를 줄이라"고 말한다 | macOS의 기본 soft 한도는 **256**이라 그대로면 접속 250개쯤에서 `accept`가 `EMFILE`로 실패한다. 조용히 덜 받는 것보다 시작할 때 분명히 실패하는 편이 낫다. Linux CI의 기본은 보통 넉넉하다 |
| `accept` 실패 | stderr에 적고 10 ms 쉰 뒤 계속 | 일시적 실패(기술자 부족 등)에 바쁜 루프를 돌지 않게 |

같은 함수(`raise_fd_limit`)를 종단 테스트도 부른다. 테스트는 **한 프로세스 안에** 서버 쪽 300개와 클라이언트 쪽 300개, 합쳐 600개 넘는 소켓을 연다.

## 2. 프레임 (S2)

```
┌──────────────┬─────────┬────────────────────┐
│ 길이 u32 BE  │ 명령 u8 │ 데이터 (길이 - 1)   │
└──────────────┴─────────┴────────────────────┘
  길이 = 명령 1바이트 + 데이터 바이트 수. 1 이상 16 MiB(16 777 216) 이하.
```

| 질문 | 선택지 | 추천 | 이유 |
|---|---|---|---|
| 길이 칸 크기 | u16(최대 64 KiB) / **u32** / 가변 길이(varint) | u32 | u16은 BLOB 하나도 못 담는다. varint는 아끼는 바이트(3)보다 코드가 늘어난다. PostgreSQL·MySQL도 고정 4바이트(MySQL은 3) |
| 바이트 순서 | **빅엔디언** / 리틀엔디언 | 빅엔디언 | 0017의 키·행 인코딩이 전부 빅엔디언이고 "네트워크 바이트 순서"의 관례다. 덤프를 사람이 읽기도 쉽다 |
| 길이가 세는 것 | 프레임 전체 / **명령 + 데이터** / 데이터만 | 명령 + 데이터 | "길이만큼 더 읽으면 프레임 끝"이라 읽는 코드가 한 줄. 길이 0은 명령이 없으니 오류로 잡힌다 |
| 최대 크기 | 없음 / 4 MiB / **16 MiB** / 64 MiB | 16 MiB | 길이 칸만 믿고 4 GiB를 잡으면 이상한 바이트 하나로 서버 메모리가 터진다. 예: HTTP 요청 `GET `을 길이로 읽으면 약 1.2 GB. 넘으면 `ERROR 0x41`을 보내고 접속을 끊는다 |
| 인사(버전 확인) | 없음 / **접속 직후 한 번** / 프레임마다 버전 바이트 | 접속 직후 한 번 | 7바이트로 "Oakdb 클라이언트가 맞는지"와 "같은 버전인지"를 처음에 걸러 낸다. #37·#38에서 명령이 늘어도 버전 숫자로 구분된다. 프레임마다 넣는 것은 낭비 |

**명령 바이트**. 응답은 맨 앞 비트를 켠다(`0x80` 이상). 덤프에서 방향이 바로 보인다.

| 값 | 이름 | 방향 | 데이터 |
|---|---|---|---|
| `0x01` | `HELLO` | 클라이언트 → 서버 | 매직 `4f 41 4b 44 42`("OAKDB") + 버전 u16 BE(지금 `00 01`) |
| `0x02` | `QUERY` | 클라이언트 → 서버 | SQL 문장 하나, UTF-8. 끝 세미콜론은 있어도 없어도 됨(0017 C7) |
| `0x81` | `READY` | 서버 → 클라이언트 | 서버 버전 u16 BE. 이후 QUERY를 받는다 |
| `0x82` | `ROWS` | 서버 → 클라이언트 | 3절 |
| `0x83` | `AFFECTED` | 서버 → 클라이언트 | 바뀐 행 수 u64 BE |
| `0x84` | `DONE` | 서버 → 클라이언트 | 없음 (CREATE TABLE) |
| `0x85` | `ERROR` | 서버 → 클라이언트 | 4절 |

끝내기 명령은 두지 않는다. **소켓을 닫는 것이 끝**이다. 이유: 끝내기 명령을 둬도 클라이언트가 그냥 죽는 경우를 처리해야 하므로 길이 하나로 모은다(#37의 "끊기면 롤백"도 같은 길).

**인사 규칙**: 서버는 첫 프레임이 `HELLO`가 아니거나 매직이 다르면 `ERROR 0x42`를 보내고 끊는다. 버전이 다르면 `ERROR 0x42`(메시지에 서버 버전)를 보내고 끊는다. 지금은 버전이 1 하나뿐이라 "같아야 한다"로 충분하다.

## 3. 응답 (S3)

| `execute` 결과 | 응답 |
|---|---|
| `Output::Rows { columns, rows }` | `ROWS` |
| `Output::Affected(n)` | `AFFECTED` n |
| `Output::Done` | `DONE` |
| `Err(SqlError)` | `ERROR` 코드 + 메시지 |

**`ROWS` 데이터**

```
열 개수 u16 BE
열마다: 이름 길이 u16 BE, 이름 UTF-8
행 개수 u32 BE
행마다, 열마다: 값 (0017 2-2절의 행 값 인코딩 그대로)
  00            NULL
  01 + i64 BE   INTEGER
  02 + u32 길이 + UTF-8   TEXT
  03 + u32 길이 + 바이트  BLOB
```

행마다 값 개수는 적지 않는다. 열 개수와 같다. 값 인코딩을 **0017의 행 값 인코딩과 똑같이** 하는 이유: 이미 테스트된 규칙이고, 디스크와 통신에서 같은 모양이라 블로그 글에서도 한 번만 설명하면 된다. 단, 코드는 SQL 크레이트의 비공개 모듈을 끌어오지 않고 서버 크레이트가 `Value`를 보고 직접 쓴다(디스크 형식과 통신 형식이 따로 바뀔 수 있도록).

**결과를 프레임 하나에 담을까, 나눠 보낼까**

| | **A. 프레임 하나에 전부** | B. 머리 + 행마다 프레임 + 끝 프레임 |
|---|---|---|
| 지금 | `execute`가 이미 `Vec`으로 다 모아 준다. 그대로 쓰면 됨 | 모아 둔 것을 굳이 나눔 |
| 큰 결과 | 16 MiB를 넘으면 `ERROR 0x44`(결과가 너무 큼) | 크기 제한 없이 흘려 보냄 |
| #32 범위 검색 | 큰 범위면 제한에 걸릴 수 있음 | 문제 없음 |

**추천: A.** 지금 SELECT는 기본 키로 최대 1행이다(0017). 범위 검색(#32)으로 큰 결과가 실제로 생기고, 엔진·SQL 층이 행을 하나씩 내주는 반복자(iterator)를 가질 때 B로 바꾼다. 그때는 새 명령 바이트와 버전 2를 쓰면 되므로 지금 정할 필요가 없다.

## 4. 오류 코드 (S4)

`ERROR` 데이터: `코드 u8` + `메시지 UTF-8`(프레임 끝까지). 메시지는 `SqlError`의 `Display` 그대로다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 큰 분류 셋(사용자 잘못 / 재시도 가능 / 치명적) | 단순 | 스펙 이야기 45("오류를 종류별로 받아 프로그램이 맞게 대응")에 비해 거칠다. 테스트가 메시지 문자열에 기대게 됨 |
| **B. 종류마다 코드 하나, 범위로 묶음** | 프로그램은 정확한 종류로도, 범위로도 대응 가능. 테스트가 코드로 검사 | 종류가 늘 때마다 표를 고쳐야 함 |
| C. 오류 이름 문자열(`"conflict"`) | 사람이 읽기 쉬움 | 바이트가 늘고 오타가 오류가 되지 않음 |

**추천: B.**

| 코드 | 원래 오류 | 접속 유지? |
|---|---|---|
| `0x01` | `SqlError::Syntax` (위치는 메시지 안에) | 유지 |
| `0x02` | `Unsupported` | 유지 |
| `0x03` | `NoSuchTable` | 유지 |
| `0x04` | `NoSuchColumn` | 유지 |
| `0x05` | `TableExists` | 유지 |
| `0x06` | `DuplicateColumn` | 유지 |
| `0x07` | `ValueCount` | 유지 |
| `0x08` | `DuplicateKey` | 유지 |
| `0x09` | `TypeMismatch` | 유지 |
| `0x0A` | `SqlError::Corrupt` (저장된 표 정보를 못 읽음) | 유지 |
| `0x1F` | 문장 오류 중 위에 없는 새 종류 (`SqlError`는 `#[non_exhaustive]`, #34가 종류를 더함) | 유지 |
| `0x20` | `Engine(Conflict)` — **다시 시도하면 될 수 있음** | 유지 |
| `0x21` | `Engine(KeyTooLarge)` | 유지 |
| `0x22` | `Engine(ValueTooLarge)` | 유지 |
| `0x23` | `Engine(Corrupt)` (데이터 파일 손상) | 유지 |
| `0x24` | `Engine(Io)` | 유지 |
| `0x25` | `Engine(OutcomeUnknown)` — 이 커밋이 남았는지 모름, 엔진 정지 | 유지 |
| `0x26` | `Engine(Stopped)` — 엔진이 멈춤, 서버를 다시 띄워야 함 | 유지 |
| `0x3F` | 엔진 오류 중 위에 없는 것 (`oakdb::Error`도 `#[non_exhaustive]`) | 유지 |
| `0x40` | 프레임이 깨짐: 길이 0, 모르는 명령, 데이터가 모양과 다름 | **끊음** |
| `0x41` | 프레임이 16 MiB를 넘음 | **끊음** |
| `0x42` | 인사 실패: 매직·버전이 다름, 첫 프레임이 HELLO가 아님 | **끊음** |
| `0x43` | SQL이 UTF-8이 아님 | 유지 (프레임 경계는 멀쩡하므로) |
| `0x44` | 결과가 16 MiB를 넘음 | 유지 |
| `0x45` | 접속 상한을 넘음 (인사 전에 보냄) | **끊음** |
| `0x46` | 허용 목록에 없는 주소 (인사 전에 보냄) | **끊음** |
| `0x7F` | 서버 내부 오류(있어선 안 되는 일) | 끊음 |

- **범위의 뜻**: `0x01–0x1F`는 "문장을 고치세요", `0x20–0x3F`는 "엔진이 거절했거나 멈췄어요", `0x40–0x5F`는 "대화 규칙이 깨졌어요". 클라이언트는 모르는 코드를 받아도 범위로 대충 대응할 수 있다.
- **통신 오류에서 끊는 이유**: 길이를 믿을 수 없으면 다음 프레임이 어디서 시작하는지 모른다. 이어 읽으면 쓰레기를 SQL로 실행할 수 있다.
- `AlreadyOpen`, `PageSizeMismatch`는 엔진을 **여는 순간**에만 나므로 서버 시작이 실패하는 것으로 처리하고 코드를 주지 않는다(문장 실행 중에는 `0x3F`로 간다).

## 5. 주고받는 순서 (S5)

| | **A. 하나씩 순서대로** | B. 파이프라이닝 약속 | C. 요청 번호로 섞어 보내기(멀티플렉싱) |
|---|---|---|---|
| 모양 | 보내고 → 답 받고 → 다음 | 답을 기다리지 않고 여러 개 보냄, 답은 순서대로 | 요청마다 번호, 답은 아무 순서 |
| 서버 | 읽기 → 실행 → 쓰기 반복 | A와 같은 코드로도 사실상 됨. 대신 "보장"을 테스트해야 함 | 접속 안에서 동시 실행. 트랜잭션과 엮이면 복잡 |
| 이득 | 단순 | 왕복 지연을 줄임 | 접속 하나로 여러 일 |

**추천: A.** 접속 하나는 트랜잭션 하나(#37)라서 그 안에서 순서가 섞이면 안 된다. 처리량은 접속을 여러 개 여는 것으로 늘린다(#39가 재는 것이 바로 그것). 서버는 프레임을 순서대로 읽으므로 B가 우연히 동작하겠지만 **약속하지 않는다**고 `docs/protocol.md`에 적는다.

## 6. 실행 파일 모양 (S6)

| | **A. 실행 파일 하나 `oakdb`, 하위 명령** | B. 한 크레이트에 실행 파일 둘 (`oakdb-server`, `oakdb-cli`) | C. CLI를 별도 크레이트로 |
|---|---|---|---|
| 쓰는 법 | `oakdb serve --data d`, `oakdb cli --port 7878` | `oakdb-server --data d`, `oakdb-cli` | B와 같음 |
| 예 | `git`, `cargo` | `redis-server`/`redis-cli`, `postgres`/`psql` | |
| 장단점 | 빌드 결과물 하나, 테스트에서 경로 하나. 하위 명령 파싱 몇 줄 | 각자 이름이 분명. 옵션 파싱이 둘 | 크레이트 하나 더, 공유 코드(통신 규칙)를 또 라이브러리로 빼야 함 |

**추천: A.** 어느 쪽이든 서버 크레이트를 **라이브러리 + 얇은 `main`**으로 나눈다. 라이브러리에 `protocol`(프레임 읽기·쓰기), `server`(접속 루프), `client`(접속·인사·질의) 모듈을 두면 종단 테스트와 #39 벤치마크가 프로세스를 띄우지 않고 그대로 쓴다. 스펙(#12)의 "서버 크레이트가 통신 규칙, 접속 관리, CLI 클라이언트를 맡는다"와 맞는다.

- 지금 `oakdb-server`는 `oakdb`(엔진)에만 기대고 `oakdb-sql`에는 기대지 않는다. 이번에 `oakdb-sql`을 더한다.
- 실행 파일 이름을 `oakdb`로 하면 엔진 라이브러리 크레이트 이름과 같아 `cargo doc`이 "출력 파일 이름 충돌" 경고를 낼 수 있다. 그러면 `[[bin]] doc = false`로 끈다(13절).

## 7. CLI (S7)

```
$ oakdb cli --port 7878
connected to 127.0.0.1:7878 (oakdb protocol 1)
oakdb> CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT, photo BLOB);
OK
oakdb> INSERT INTO users VALUES
   ...> (1, 'kim', X'ab01'), (2, 'it''s; fine', NULL);
INSERT 2
oakdb> SELECT * FROM users WHERE id = 2;
 id | name       | photo
----+------------+-------
  2 | it's; fine | NULL
(1 row)
oakdb> SELECT * FROM nope WHERE id = 1;
ERROR 0x03 no such table: nope
oakdb> \q
```

| 질문 | 추천 | 이유 |
|---|---|---|
| 입력 단위 | 줄을 모으다가 **작은따옴표 밖의 `;`**로 줄이 끝나면 한 문장으로 보냄. 이어지는 줄의 프롬프트는 `   ...> ` | 위 예의 `'it''s; fine'`처럼 글자 안의 `;`에서 자르면 안 된다. 따옴표 세기 정도의 작은 스캐너면 충분(`''`는 따옴표 둘이라 홀짝이 그대로 맞음) |
| 끝내기 | `\q` 또는 입력 끝(Ctrl-D) | psql과 같음 |
| 행 출력 | psql식: 칸 맞춘 표, 정수는 오른쪽 정렬, 끝에 `(N rows)` | 사람이 읽기 쉽고 흔한 모양 |
| 값 표시 | NULL은 `NULL`, BLOB은 `X'ab01'`, 글자는 따옴표 없이 | BLOB을 SQL 리터럴 꼴로 보여 주면 그대로 복사해 다시 쓸 수 있음 |
| 다른 결과 | `AFFECTED n` → `INSERT n`(지금은 INSERT만 행 수를 냄. #34 이후 UPDATE·DELETE도), `DONE` → `OK` | |
| 오류 | `ERROR 0x03 <메시지>`를 stderr로 | 코드가 보이면 블로그·테스트에서 종류를 바로 안다 |
| 옵션 | `--host`(기본 `127.0.0.1`), `--port`(기본 `7878`) | 서버 기본값과 같게 |
| 파이프 입력 | 표준 입력이 터미널이 아니면(`oakdb cli < script.sql`) 인사·프롬프트를 찍지 않고, 오류가 하나라도 있었으면 종료 코드 1 | 스크립트로 쓰고, 실행 파일 종단 테스트가 이 길을 탄다 |
| 서버가 끊김 | "connection closed by server" 출력 후 종료 코드 1. 자동 재접속 없음 | #37 이후 재접속하면 트랜잭션이 사라졌다는 사실이 숨겨진다 |

터미널인지 알아내는 것은 표준 라이브러리 `std::io::IsTerminal`로 된다(외부 크레이트 불필요).

| 시작 실패 | `AlreadyOpen`(다른 서버가 이미 열었음), `PageSizeMismatch`, `Corrupt`, 포트 사용 중 → 메시지 출력, 종료 코드 1 | |

### 8-1. 허용 목록 (사용자 결정으로 바뀐 부분)

처음 추천은 `--host`로 묶을 주소를 고르는 것이었다. 사용자는 **"평소엔 닫혀 있고, 필요할 때 열 수 있는 목록 하나"**를 원했다. PostgreSQL의 `pg_hba.conf`를 아주 작게 줄인 것이다. 아파트로 치면 **출입 명단**이다. 명단이 없으면 집 안 사람(같은 컴퓨터, 루프백)만 들어온다. 명단에 바깥 주소를 적으면 그때 현관을 열고, 경비가 주소를 보고 명단에 없으면 돌려보낸다.

```
# /etc/oakdb/allow  — 한 줄에 하나, # 뒤는 주석
10.0.0.5          # 앱 서버 한 대 (= 10.0.0.5/32)
192.168.1.0/24    # 사무실 네트워크
```

```
oakdb serve --data ./db --allow-file /etc/oakdb/allow --allow 172.16.0.9
```

| 질문 | 정한 것 | 이유 |
|---|---|---|
| 목록을 주는 법 | `--allow <항목>`(여러 번 가능)과 `--allow-file <파일>`. 둘 다 주면 합친다 | 테스트·임시로는 플래그, 운영은 파일 |
| 항목 모양 | IPv4 주소(`10.0.0.5`, 곧 `/32`) 또는 CIDR(`10.0.0.0/24`, 접두어 0~32). 앞뒤 공백 무시, 빈 줄 무시, `#`부터 줄 끝은 주석 | `pg_hba.conf`의 주소 칸과 같은 표기 |
| 잘못된 줄 | **시작 거부**, 메시지에 `파일:줄 번호`와 그 줄 | 오타로 문이 열리거나 닫힌 채 떠 있는 것보다 낫다 |
| CIDR의 호스트 비트 | `10.0.0.5/24`처럼 접두어 뒤에 1이 있으면 시작 거부 | 사람이 뜻한 것이 `10.0.0.0/24`인지 `10.0.0.5/32`인지 모른다 |
| IPv6 | 이번엔 **지원 안 함**: IPv6 항목은 시작 거부("IPv6 is not supported yet") | 서버가 IPv4로만 연다(아래). 듀얼 스택 동작이 OS마다 달라 두 OS 약속(ADR 0003)을 지키려면 따로 설계해야 함 |
| 루프백 | `127.0.0.0/8`은 **항상 허용** | "목록이 없으면 루프백만"과 이어진다. 같은 컴퓨터의 운영자가 목록 실수로 잠기지 않게 |
| 어디에 여나 | 목록에 루프백 밖의 항목이 **하나도 없으면 `127.0.0.1`**, 하나라도 있으면 **`0.0.0.0`** | 바깥 손님을 받을 필요가 없으면 문 자체를 열지 않는다(1차 방어). `--host`는 없앴다 |
| `0.0.0.0/0` | 허용하되 시작할 때 stderr에 "모든 주소를 허용" 경고 | 막을 이유는 없지만 실수일 수 있다 |
| 거절 방식 | 받아들인 직후 주소를 보고, 없으면 `ERROR 0x46 "address 10.1.2.3 is not allowed"`를 보내고 끊는다. stderr에도 한 줄 | 설정을 잘못한 정상 손님이 이유를 안다. 조용히 끊으면 "서버가 죽었나?"와 구별이 안 된다. 서버가 Oakdb라는 사실은 숨길 비밀이 아니다 |
| 거절 순서 | 허용 목록 → 접속 상한 | 명단에 없는 손님이 좌석을 세는 데 끼지 않게 |
| 주소 표기 | 손님 주소가 IPv4-mapped IPv6(`::ffff:10.0.0.5`)로 오면 IPv4로 바꿔 비교 | OS에 따라 이렇게 올 수 있다 |

**이것은 인증이 아니다.** `docs/protocol.md`와 `oakdb serve --help`에 적는다.

- IP 주소는 **누구인지가 아니라 어디서 왔는지**만 말한다. 같은 공유기 뒤(NAT)의 모든 사람은 같은 주소로 보이고, 같은 네트워크 안에서는 주소를 흉내 낼 수 있다.
- 통신은 **암호화되지 않는다.** 중간에서 SQL과 결과를 그대로 읽을 수 있다.
- 허용된 주소에서 온 손님은 **무엇이든 할 수 있다**(표 만들기, 모든 행 읽기). 사용자·권한은 스펙 범위 밖이다.

그래서 믿을 수 있는 내부 네트워크에서만 연다. 인증과 암호화(TLS)는 v1 범위 밖이다.

**엔진이 디스크 실패로 멈추면** (ADR 0007, design 0012: 커밋하던 문장은 `OutcomeUnknown`, 그 뒤 모든 요청은 `Stopped`)

| | **A. 서버는 떠 있고 오류로 답함** | B. 서버 프로세스를 끝냄 | C. 서버가 DB를 다시 엶 |
|---|---|---|---|
| 클라이언트가 보는 것 | 커밋하던 쪽은 `0x25`, 이후 모두 `0x26` "서버를 다시 띄우세요" | 접속이 끊김. 이유는 서버 로그에만 | 잠깐 뒤 다시 정상 |
| 만드는 일 | 없음. 엔진이 이미 그렇게 답한다 | 다른 접속을 정리하고 끝내는 길이 필요 → #38의 일 | 다시 열기 + 모든 접속에 새 `Db`를 나눠 주는 교체 장치 |
| 위험 | 서버가 멀쩡해 보이지만 일을 못 함 → stderr 로그로 알림 | 재시작은 사람(또는 감시 프로그램) 몫 | 디스크가 계속 고장이면 열고 멈추기를 무한 반복. 디스크 실패가 묻힘 |

**추천: A.** 엔진의 약속("멈춘 뒤엔 아무 일도 안 하고, 다시 열면 응답한 커밋은 다 있다")을 그대로 클라이언트에 전한다. 정지를 처음 본 순간 stderr에 한 번 적는다. B는 #38(정상 종료)이 종료 절차를 만든 뒤 "엔진 정지 → 정상 종료"로 이어 붙일 수 있다.

## 9. 이번 티켓의 동시성 (S9)

| | A. 한 번에 접속 하나 | **B. 여러 접속, 자동 커밋만** |
|---|---|---|
| 모양 | `accept` 루프가 한 접속을 끝까지 처리. 나머지는 OS 대기열에서 기다림 | 접속마다 스레드(S1). 모두 `Arc<Db>` 하나를 나눔 |
| 맞는가 | 문제 없음 | 엔진은 여러 스레드에서 쓸 수 있고(스펙), 문장마다 트랜잭션 하나(0017 C9)라 접속끼리 상태를 나누지 않음 |
| #37로 갈 때 | 접속 루프를 다시 짜야 함 | 접속 스레드에 "열린 트랜잭션" 하나를 더하면 됨 |

**추천: B.** S1을 고르면 거의 공짜다. 접속별 `BEGIN`/`COMMIT`과 끊김 롤백은 #35(SQL 트랜잭션 명령)와 #37의 일이다.

- 두 접속이 동시에 `CREATE TABLE`을 하면 뒤 커밋이 `Conflict`(`0x20`)를 받을 수 있다(0017 6절). 받아들이고, 동시 접속 테스트 하나로 확인한다.
- 접속 수 상한은 1-1절(기본 512).

## 10. 테스트 (S10)

| 테스트 | 무엇을 | 어떻게 |
|---|---|---|
| `protocol` 단위·속성 테스트 | 모든 프레임 종류의 인코딩 → 디코딩 왕복(무작위 `Value`, 빈 결과, 열 0개). **무작위 바이트를 디코더에 넣어도 패닉 없이 오류.** 길이 0, 16 MiB 초과, 잘린 프레임, 모르는 명령 | proptest(이미 dev 의존성) |
| `tests/server.rs` (프로세스 안) | 서버를 `127.0.0.1:0`에 묶어 스레드로 띄우고 `client`로 접속. CREATE → INSERT → SELECT 왕복, 오류 종류별 코드(문법, 없는 표, 기본 키 중복), 인사 실패, 깨진 프레임 뒤 끊김, 접속 여러 개가 동시에 다른 표에 INSERT, 서버를 내렸다 다시 띄워도 데이터 남음 | 임시 디렉터리, 실제 파일시스템 |
| `tests/server.rs` 엔진 정지 | `SimFs`에서 sync를 실패시킨 서버 → 그 문장은 `0x25`, 다음 문장은 `0x26`, 서버는 접속을 계속 받음 | 서버를 `Db<F>`에 대해 일반화(엔진 테스트와 같은 방식) |
| `tests/server.rs` 수백 접속 | 파일 기술자 한도를 올리고 접속 **300개를 동시에** 열어 둔 채(전부 인사까지 마침), 접속마다 스레드에서 자기 행을 INSERT → SELECT해 자기 값을 받는지. 그 뒤 상한을 작게(예: 4) 둔 서버에서 다섯 번째 접속이 `0x45`를 받는지 | macOS 기본 한도 256을 넘는 숫자라 한도 올리기가 실제로 필요하다 |
| `tests/server.rs` 허용 목록 | 루프백을 뺀 목록으로 서버를 띄우면(라이브러리 수준에서만 가능) 127.0.0.1 손님이 `0x46`을 받고 끊기는지. 루프백 손님은 기본 설정에서 받아들여지는지 | 루프백 밖의 손님은 CI에서 만들 수 없어 거절 경로를 이렇게 탄다 |
| `allow` 단위 테스트 | CIDR 맞추기(`/0`, `/8`, `/24`, `/32`, 경계 주소), 파일 파싱(주석, 빈 줄, 공백, 잘못된 줄의 줄 번호, 호스트 비트, IPv6 거부), IPv4-mapped 주소, 여는 주소 고르기 | |
| `tests/cli.rs` (실제 실행 파일) | `env!("CARGO_BIN_EXE_oakdb")`로 `oakdb serve --data <임시> --port 0`을 띄워 첫 줄에서 주소를 읽고, `oakdb cli --port <p>`에 SQL을 파이프로 넣어 출력 표와 종료 코드 확인 | 자식 프로세스, 끝나면 kill |

- **멈추지 않게**: 모든 테스트 소켓에 읽기 타임아웃(예: 10초)을 건다. 버그로 서로 기다리면 CI가 멈추는 대신 실패한다.
- **두 OS**: 루프백 TCP와 포트 0은 GitHub Actions의 macOS·Linux 모두에서 된다. CI 설정은 바꿀 것이 없다(`cargo test --all`이 그대로 돈다).
- 정전 실험은 엔진·SQL 층에서 이미 하므로 이번에는 하지 않는다. 서버가 더한 것은 바이트 운반뿐이라, 검증 단계의 장애 실험은 "통신 중 끊기·깨진 프레임" 쪽으로 잡는다(검증 단계에서 정함).

## 11. 외부 크레이트 (S11)

| 필요한 것 | 표준 라이브러리로 | 크레이트로 | 추천 |
|---|---|---|---|
| TCP | `std::net::TcpListener`/`TcpStream` | tokio | **std** (S1과 짝) |
| 옵션 파싱 | `std::env::args`를 손으로, 옵션 대여섯 개 | clap | **std**. 옵션이 적고, 0017의 손으로 쓴 렉서와 같은 태도 |

지금 엔진의 의존성은 `crc32c`, `libc` 둘뿐이다. 서버는 **`libc` 하나만** 더한다. 파일 기술자 한도를 올리는 `setrlimit`이 표준 라이브러리에 없기 때문이다(엔진이 이미 쓰는 크레이트). 손으로 쓴 프레임 읽기가 이번 티켓의 배울 거리이기도 하다.

## 12. 통신 규칙 문서 (S12)

이슈의 완료 기준 "통신 규칙(길이 + 명령 + 데이터)을 docs에 문서화"를 **`docs/protocol.md`** 로 채운다. 이 설계 문서는 선택의 이유를 담고 한 번 쓰면 거의 안 바뀌지만, 참조 문서는 바이트 표(2~4절의 표)만 담고 #37·#38에서 명령이 늘 때마다 고친다. 클라이언트를 새로 쓰는 사람(블로그 독자, #39 벤치마크 코드)이 이 문서 하나만 보면 되게 한다.
