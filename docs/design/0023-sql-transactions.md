# 0023. SQL 트랜잭션 명령 — 설계

이슈 #35. 지금까지 Oakdb의 SQL 문장은 **하나하나가 각자 트랜잭션**이었다(0017, 자동 커밋). `execute(&db, sql)`가 엔진 트랜잭션을 열고, 문장을 돌리고, 바로 커밋한다. 이번 티켓에서 **`BEGIN`으로 여러 문장을 한 트랜잭션에 묶고, `COMMIT`으로 한꺼번에 반영하거나 `ROLLBACK`으로 흔적 없이 버린다.** 엔진은 이미 트랜잭션을 안다(스냅샷 읽기 0015, 충돌 판정 0016, 커밋 창구 0018, 묶음 커밋 0021). 새로 정할 것은 SQL 층이 **열린 트랜잭션을 문장과 문장 사이에 어디에, 어떤 상태로 들고 있나**, 그리고 **도중에 무언가 실패하면 그 트랜잭션은 어떻게 되나**다. 다음 티켓 #37(서버의 접속별 트랜잭션)은 이 위에 그대로 얹히고, #34(오류 종류)는 이번에 생기는 오류에 이름을 붙인다.

**비유**: 인터넷 쇼핑몰의 **장바구니**다.

| 쇼핑몰 | 무슨 일이 생기나 | DB에서는 |
|---|---|---|
| 장바구니 없이 "바로 구매"만 누른다 | 물건 하나마다 결제가 하나 | 자동 커밋 (지금) |
| **장바구니를 연다** | 담기 시작 | `BEGIN` |
| 물건을 담는다 | 내 장바구니에만 보인다. 다른 손님은 모른다 | `INSERT`/`UPDATE`/`DELETE`가 트랜잭션의 쓰기 모음(`Txn.writes`)에만 들어감 |
| 장바구니를 보며 "지금 몇 개 담았지?" | 담은 것까지 합쳐 보인다 | 트랜잭션 안의 `SELECT`는 자기 쓰기를 봄 |
| 품절된 물건을 담으려 했다 | **그 물건만** 안 담기고, 이미 담은 건 그대로 | 문장 하나가 실패해도 앞 문장은 살아 있음 (3절) |
| **결제** | 한꺼번에 내 것이 된다 | `COMMIT` |
| 결제하려니 마지막 한 개를 남이 먼저 샀다 | 결제 실패. 장바구니는 비워지고 처음부터 다시 | 커밋 때 `Conflict` (5절) |
| **장바구니 비우기** / 창을 그냥 닫음 | 아무것도 안 산 것과 같다 | `ROLLBACK` / 세션을 버림 (6절) |

Java/Spring으로 치면, 지금의 Oakdb는 JDBC의 **`autoCommit = true`** 상태다. `conn.setAutoCommit(false)` 뒤에 `executeUpdate`를 여러 번 하고 `conn.commit()`/`conn.rollback()`을 부르는 것이 이번 티켓이다. Spring의 `@Transactional`은 메서드 시작에 이것을 열고, 정상 종료면 커밋, 예외면 롤백한다. 다만 `@Transactional`은 "예외 하나면 전체 롤백"이고, SQL 콘솔의 `BEGIN`은 "실패한 문장만 취소하고 계속"인 경우가 많다(SQLite, MySQL). PostgreSQL은 그 중간이다(3절). 이 차이를 어떻게 할지가 이번 설계의 가장 큰 질문이다.

```
세션 하나 (접속 하나, #37)
  "BEGIN"                      → 엔진 txn 열기, 세션이 들고 있음        → Done
  "INSERT INTO t VALUES (1)"   → 들고 있는 txn에 apply (커밋 안 함)    → Affected(1)
  "SELECT * FROM t"            → 같은 txn에서 읽기 (방금 넣은 1이 보임) → Rows
  "INSERT INTO t VALUES (1)"   → 중복 키 오류. 이 문장만 없던 일, txn은 열린 채
  "COMMIT"                     → txn.commit() → 성공이면 Done, Conflict면 오류. 어느 쪽이든 txn은 끝남
  "INSERT INTO t VALUES (2)"   → txn 없음 → 자동 커밋 (지금과 같음)
```

## 1. 세션: 열린 트랜잭션을 들고 있는 것 (T1)

`BEGIN`과 `COMMIT` 사이에는 **문장과 문장 사이에도 살아 있는 엔진 트랜잭션**이 있어야 한다. 지금의 `execute(&db, sql)`는 함수 안에서 `Txn`을 만들고 끝에 커밋하므로 그런 자리가 없다. 그 자리를 **세션**이라 부른다. #37에서는 접속 하나가 세션 하나를 가진다.

엔진의 트랜잭션은 `Txn<'db, F>`다. `'db`는 "이 트랜잭션은 `Db`를 빌리고 있다"는 표시로, Rust는 `Db`보다 `Txn`이 오래 살 수 없게 막는다(Java로 치면 `Connection`이 닫힌 뒤 그 `Statement`를 쓰는 실수를 **컴파일러가** 막는 셈). 그래서 "트랜잭션을 들고 있는 것"도 `Db`를 빌려야 한다.

| 선택지 | 모양 | 장점 | 단점 |
|---|---|---|---|
| **A. 세션이 `Db`를 빌림** | `Session<'db, F>` = `&'db Db<F>` + `Option<Txn<'db, F>>`. `Session::new(&db)`, `session.execute(sql)` | 엔진을 안 고침. 빌림 규칙이 "세션은 `Db`보다 먼저 사라진다"를 보장. #37의 접속 스레드는 이미 `Arc<Shared>`를 끝까지 쥐고 있으므로 `serve()` 안에서 `Session::new(&shared.db)`로 만들면 수명이 저절로 맞음 | 세션을 `Db`와 떨어뜨려 보관(예: `HashMap<접속 번호, Session>`)할 수 없음. 지금 구조(접속당 스레드, ADR 0010)에선 필요 없음 |
| B. 세션이 `Arc<Db>`를 가짐 | `Session` = `Arc<Db>` + `Option<Txn<'?>>` | 어디에나 보관 가능 | 한 구조체 안에서 `Txn`이 옆 칸의 `Db`를 빌리는 **자기 참조**가 됨. Rust에선 안전하게 못 씀. 엔진 `Txn`이 `Arc<Db>`를 갖도록 엔진 API를 바꿔야 함 |
| C. 세션 없음, 서버가 `Option<Txn>`을 직접 들고 SQL 층은 `execute_in(&mut Txn, sql)`만 냄 | | SQL 층이 작음 | BEGIN/COMMIT의 뜻(4·5절의 규칙)이 서버에 들어가 SQL 층 테스트로 확인할 수 없음. CLI·테스트·서버가 같은 규칙을 각자 짬 |

**추천 A.** 겉모양(공개 API) 초안:

| 항목 | 모양 | 뜻 |
|---|---|---|
| 만들기 | `Session::new(db: &'db Db<F>) -> Session<'db, F>` | 자동 커밋 상태로 시작 |
| 실행 | `Session::execute(&mut self, sql: &str) -> Result<Output, SqlError>` | 문장 하나. 4·5절의 규칙을 모두 여기서 |
| 상태 보기 | `Session::in_transaction(&self) -> bool` | CLI 프롬프트(`oakdb*>`)와 테스트용 |
| 버리기 | 따로 없음 (`Drop`) | 열린 `Txn`이 함께 버려져 롤백 (6절) |

`&mut self`인 이유: 세션 하나는 한 번에 문장 하나만 돌린다. 같은 세션을 두 스레드가 동시에 쓰는 일은 컴파일 단계에서 막힌다. 동시성은 **세션을 여러 개** 만들어 얻는다(접속당 하나).

### 1-1. 세션의 상태

세션의 상태는 둘뿐이다: **자동 커밋**(`txn = None`)과 **트랜잭션 중**(`txn = Some`). PostgreSQL에는 셋째 상태 "트랜잭션 실패(aborted)"가 있는데, T5에서 추천안을 고르면 필요 없다(3절, 5절).

```
           BEGIN                    
 자동 커밋 ───────────▶ 트랜잭션 중 ──┐ 문장 (성공이든 오류든)
     ▲                     │   ◀────┘
     └─────────────────────┘
       COMMIT (성공이든 실패든), ROLLBACK
```

### 1-2. 자동 커밋은 지금과 똑같이

트랜잭션 밖의 문장은 지금 `executor::run`이 하는 일 그대로다: `db.begin()` → `apply(&mut txn, 문장)` → 성공이면 `commit()`, 오류면 버림. 0022가 이미 `apply(&mut Txn, Statement)`를 따로 꺼내 두었으므로, 트랜잭션 중이면 **들고 있는 txn에 `apply`만 하고 커밋하지 않는다.** 길이 둘이 아니라 "커밋을 지금 하나, 나중에 하나"만 다르다.

### 1-3. 한 번에 하나 실행하는 `execute(&db, sql)` (T12)

| 선택지 | `execute(&db, "BEGIN")` | 장점 | 단점 |
|---|---|---|---|
| A. 없앰, 모두 세션으로 | — | 길 하나 | 기존 테스트·문서 예제를 모두 고침 |
| B. "세션 하나를 만들어 한 문장 돌리고 버림"과 같게 | `Done`을 돌려주고 바로 롤백됨 | 구현이 한 줄 | **조용히 아무 일도 안 함**. 사용자는 트랜잭션이 열렸다고 믿음 |
| **C. 남기되 BEGIN/COMMIT/ROLLBACK은 오류** | "BEGIN needs a Session" 같은 오류 | 기존 코드 그대로. 실수가 바로 드러남. #37 전까지 서버(지금 `execute`를 부름)로 BEGIN을 보내면 이 오류가 감 | 함수가 둘 |

## 2. 문법과 파서 (T2, T3)

```
begin    := BEGIN [TRANSACTION]
commit   := COMMIT [TRANSACTION]
rollback := ROLLBACK [TRANSACTION]
```

| 들어오는 것 | 처리 | 참고 |
|---|---|---|
| `BEGIN`, `BEGIN TRANSACTION`, `COMMIT`, `ROLLBACK` (끝 `;` 허용) | 지원 | SQLite·PostgreSQL 공통 |
| `START TRANSACTION`, `END`, `COMMIT WORK` | "지원 안 함" | 같은 뜻의 다른 이름. 필요하면 나중에 한 줄로 추가 |
| `BEGIN DEFERRED/IMMEDIATE/EXCLUSIVE` (SQLite), `BEGIN ISOLATION LEVEL ...` (PostgreSQL), `READ ONLY` | "지원 안 함" | Oakdb의 격리 수준은 스냅샷 격리 하나(ADR 0006) |
| `SAVEPOINT`, `RELEASE`, `ROLLBACK TO` | "지원 안 함" | 3절 선택지 A를 고르면 나중에 열 수 있음 |
| `BEGIN; INSERT ...` (한 문자열에 둘) | 기존 규칙대로 문법 오류 | 0017: 문자열 하나에 문장 하나 |

예약어에 `BEGIN`, `COMMIT`, `ROLLBACK`, `TRANSACTION`을 더한다. 0019 Q1처럼 문법을 가르는 낱말만 예약하는 원칙이고, `TRANSACTION`은 선택이라 예약하지 않고 BEGIN 뒤에서만 낱말로 비교해도 된다(11절 Q1).

### 파서가 내는 모양 (T3)

| 선택지 | 모양 | 장점 | 단점 |
|---|---|---|---|
| A. `Statement`에 `Begin`, `Commit`, `Rollback` 갈래를 더함 | 한 enum | 파서가 단순 | `executor::apply(&mut Txn, Statement)`가 `Begin`을 받으면 할 수 있는 일이 없음 → `unreachable!` 또는 오류 갈래가 생김 |
| **B. 위에 한 겹: `Command { Begin, Commit, Rollback, Run(Statement) }`** | 파서는 `Command`를 내고, 세션이 앞의 셋을 처리하고 `Run`만 `apply`로 넘김 | **"트랜잭션 안에서 BEGIN을 실행"하는 길이 타입에 없음.** `apply`는 지금 그대로 | enum 하나 더 |

**추천 B.** "잘못된 상태를 타입으로 표현할 수 없게" 하는 Rust다운 모양이다. Java로 치면 `Statement`와 `Connection.commit()`이 다른 객체인 것과 같다.

## 3. 트랜잭션 안에서 문장이 도중에 실패하면 (T5)

0022 6절이 미뤄 둔 질문이다. 자동 커밋에서는 문장이 실패하면 트랜잭션째 버리니 문제가 없다. 그런데 `BEGIN` 안에서는 트랜잭션이 **문장 여러 개의 것**이라 버릴 수 없다.

```
BEGIN;
INSERT INTO t VALUES (1, 'a');           -- 성공
INSERT INTO t VALUES (2, 'b'), (1, 'c'); -- 둘째 행이 중복 키
COMMIT;
```

지금의 INSERT는 행마다 검사하고 **바로** `txn.put`한다. 그래서 둘째 문장은 `(2, 'b')`를 쓰기 모음에 넣은 뒤 `(1, 'c')`에서 오류를 낸다. 아무것도 안 하면 COMMIT 때 **실패한 문장의 앞 절반(`2`)이 반영된다.** 이것은 막아야 한다. UPDATE는 0022 U10 덕분에 이미 안전하다(`SET n = n * 2`가 셋째 행에서 넘쳐도, 넘침은 1단계에서 나고 쓰기는 2단계에서만 함).

방법은 셋이다.

| 선택지 | 하는 일 | 위 예의 결과 | 누가 |
|---|---|---|---|
| A. 세이브포인트 (문장 단위 되돌리기) | 문장을 시작할 때 엔진 txn에 표시를 하고, 실패하면 그 표시 뒤의 쓰기만 되돌림 | 1만 반영. txn은 계속 | SQLite, MySQL(InnoDB), Oracle이 내부에서 이렇게 함 |
| **B. 쓰기 전에 모든 검사를 끝냄** | 모든 문장을 "1단계: 읽고 계산하고 검사 → 2단계: 쓰기만"으로. 2단계는 실패할 수 없게 | 1만 반영. txn은 계속 | 0022의 UPDATE/DELETE가 이미 이 모양 |
| C. 트랜잭션 전체를 실패 상태로 | 문장 하나가 실패하면 txn은 "실패". 그 뒤 모든 문장은 "current transaction is aborted" 오류, COMMIT은 ROLLBACK처럼 동작 | 아무것도 반영 안 됨 | PostgreSQL |

| 비교 | A. 세이브포인트 | B. 검사 먼저 | C. 전체 실패 |
|---|---|---|---|
| 고칠 곳 | **엔진**에 새 API (`Txn`의 쓰기 모음에 되돌리기 기록). 이 티켓은 SQL 층인데 엔진 크레이트를 건드림 | SQL 층의 INSERT 하나를 0022처럼 두 단계로 | SQL 층 세션에 상태 하나 |
| 비용 | 쓰기마다 그 키의 **이전 쓰기**를 한 번 더 복사해 기록. 문장마다 쓰기 모음 전체를 복사하는 방식(가장 쉬운 구현)은 긴 트랜잭션에서 O(n²)이라 안 됨 | 거의 없음. INSERT가 행을 한 번 모았다 씀(0022 1-1절과 같은 메모리 차수) | 없음 |
| 보장의 근거 | **구조**: 어떤 문장이 어디서 실패하든 되돌림 | **규율**: 문장마다 "2단계는 실패하지 않는다"를 지켜야 함. 새 문장이 생길 때마다 다시 확인 | 구조 |
| 사용자가 느끼는 것 | 콘솔에서 오타 하나 내도 계속 | A와 같음 | 오타 하나에 트랜잭션 전체를 처음부터. JDBC에서 PostgreSQL을 쓰다 만나는 "current transaction is aborted, commands ignored until end of transaction block"이 이것 |
| `@Transactional`과의 관계 | | | Spring은 예외가 나면 어차피 전체 롤백이라 C와 잘 맞음. 다만 그건 **클라이언트**의 선택이고, A·B에서도 클라이언트가 ROLLBACK을 보내면 같은 결과 |
| 나중에 `SAVEPOINT` SQL | 바로 열 수 있음 | 따로 A를 만들어야 함 | 따로 A를 만들어야 함 |

**추천 B.** 이유:

1. **이미 반쯤 되어 있다.** UPDATE/DELETE는 0022에서 이렇게 만들었고, CREATE TABLE도 쓰기(`next_table_id`의 카운터, `catalog::put`) 전에 검사가 모두 끝난다. 남은 것은 INSERT뿐이다: 모든 행의 타입·기본 키 NULL·문장 안 중복(집합)·이미 있는 키(`txn.get`)·키와 값 길이를 먼저 확인하고, 그다음 모두 `put`한다.
2. **2단계에서 남는 실패는 엔진 정지뿐이다.** `Txn::put`/`delete`가 실패하는 경우는 `check_running`(엔진이 멈춤), 키 길이, 값 길이 셋인데, 뒤의 둘은 1단계에서 미리 본다. 엔진이 멈춘 트랜잭션은 어차피 커밋할 수 없으므로(`commit`이 `Stopped`), 반쯤 쓴 쓰기 모음은 디스크에 닿을 길이 없다.
3. **A의 구조적 보장은 좋지만 지금 값을 치를 이유가 없다.** 엔진 크레이트 변경, 쓰기마다 추가 복사, 테스트 범위 확대. 나중에 1단계에서 미리 검사할 수 없는 문장(예: 외래 키, 트리거)이 생기면 그때 A를 만든다. 그때도 B의 두 단계 모양은 그대로 쓸모 있다.
4. C는 "오류 = 처음부터"라 대화형 사용에 가혹하고, 다른 두 방법이 이미 문장 단위 원자성을 주므로 상태를 하나 더 만들 이유가 없다.

B의 약점(규율)은 **테스트로 계약을 만든다**: 10절 모델 테스트가 "트랜잭션 안에서 오류가 난 문장 뒤의 표는 문장 전과 똑같다"를 매 문장 확인한다. 0022 8절이 자동 커밋에서 확인한 것을 BEGIN 안으로 넓힌다.

### 3-1. 문장별로 다시 보기

| 문장 | 1단계에서 나는 오류 | 2단계(쓰기) | 이번에 할 일 |
|---|---|---|---|
| INSERT | 값 개수, 타입, 기본 키 NULL, 문장 안 중복, 이미 있는 키, 키·값 길이 | `put`만 | **두 단계로 고침** |
| UPDATE | 0022 4-2절 표 전부, 중복 키(3-1절) | `delete`/`put`만 | 없음 |
| DELETE | 거르기 계산 오류, 망가진 행 | `delete`만 | 없음 |
| CREATE TABLE | 열 수·이름 길이, 열 중복, 기본 키 개수, 이미 있는 표(긴 이름은 `catalog::find`의 `txn.get`이 `KeyTooLarge`로 먼저 거름), 표 번호 다 씀 | 카운터 `put`, 표 정보 `put` | 없음 (검사 순서가 이미 맞음. 테스트로 고정) |
| SELECT | 계획·거르기·망가진 행 | 없음 | 없음 |

## 4. 상태에 안 맞는 명령 (T4)

| 상황 | SQLite | PostgreSQL | MySQL |
|---|---|---|---|
| 트랜잭션 중 `BEGIN` | 오류 "cannot start a transaction within a transaction", 열린 txn은 그대로 | **경고**("there is already a transaction in progress"), 아무 일 없음 | 열린 txn을 **조용히 커밋**하고 새로 시작 |
| 트랜잭션 밖 `COMMIT` | 오류 "cannot commit - no transaction is active" | 경고("there is no transaction in progress") | 아무 일 없음 |
| 트랜잭션 밖 `ROLLBACK` | 오류 | 경고 | 아무 일 없음 |

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 오류, 상태는 그대로** | 실수가 드러남(`BEGIN` 두 번은 대개 코드의 버그: 앞 트랜잭션을 닫는 걸 잊음). 통신 규칙(docs/protocol.md)에 경고를 실을 자리가 없으므로 "성공 + 경고"를 표현하려면 프로토콜을 바꿔야 함 | 스크립트 끝에 습관처럼 `ROLLBACK`을 붙이면 오류가 남 |
| B. 성공으로 보고 무시 (PostgreSQL에서 경고만 뺀 것) | 너그러움 | 실수가 **완전히** 숨음. PostgreSQL은 경고라도 보이지만 Oakdb는 그 길이 없음 |
| C. MySQL처럼 열린 txn을 커밋 | | 사용자가 모르는 사이에 커밋이 일어남. 가장 위험 |

**추천 A.** 오류가 나도 **열린 트랜잭션은 건드리지 않는다**: 트랜잭션 중 `BEGIN`이 오류를 내도 앞의 쓰기는 그대로 살아 있고 COMMIT할 수 있다. 오류 종류는 9절.

## 5. 무엇이 트랜잭션을 끝내나, 끝난 뒤 세션은 (T6)

규칙 하나로 정리하고 싶다: **트랜잭션을 끝내는 것은 COMMIT과 ROLLBACK뿐이고, COMMIT은 성공하든 실패하든 트랜잭션을 끝낸다.** 엔진의 `Txn::commit(self)`가 `self`를 가져가므로(소유권 이동) 실패한 뒤에 같은 txn을 다시 커밋할 길이 원래 없다. 규칙이 엔진 API의 모양과 같다.

| 오류 | 언제 | 트랜잭션 | 세션 상태 | 클라이언트가 할 일 |
|---|---|---|---|---|
| 문장 오류 (문법, 타입, 중복 키, 넘침, 없는 표…) | 트랜잭션 중 아무 문장 | **계속 열림**, 그 문장만 없던 일 (T5) | 트랜잭션 중 | 고쳐서 다시, 또는 ROLLBACK |
| `Conflict` | **COMMIT 때만** (엔진은 커밋할 때 충돌을 판정, 0016) | 끝남, 아무것도 안 씀 | 자동 커밋 | **BEGIN부터 다시** (재시도할 만함) |
| `Conflict` | 자동 커밋 문장 | 그 문장의 txn이 끝남 | 자동 커밋 | 그 문장을 다시 |
| `OutcomeUnknown` | COMMIT 때 (디스크 실패, 0012·0021 G4) | 끝남, **남았는지 모름** | 자동 커밋. 엔진이 멈춰 다음 문장은 모두 `Stopped` | 서버를 다시 띄우고 확인 |
| `Stopped` | 엔진이 멈춘 뒤의 아무 문장, 또는 COMMIT | 문장: 열린 채(어차피 커밋 불가). COMMIT: 끝남 | 문장: 트랜잭션 중. COMMIT: 자동 커밋 | 서버를 다시 띄움 |
| `Corrupt` (저장된 것을 못 읽음) | 문장 1단계 | 열린 채 (문장 오류와 같음) | 트랜잭션 중 | 대개 ROLLBACK |

### 5-1. 문장 오류에서 트랜잭션을 끝내지 않는 이유

SQLite는 일부 오류(디스크 가득 참, I/O 오류, 메모리 부족)에서 트랜잭션을 **저절로 롤백**한다. 그러면 클라이언트는 아직 BEGIN 안이라고 믿는데 뒤 문장들이 **자동 커밋으로** 하나씩 반영된다. 잘 알려진 함정이다. Oakdb는 이 일을 만들지 않는다: 문장이 실패해도 세션은 트랜잭션 중으로 남고, 엔진이 멈춘 경우에도 트랜잭션을 버리지 않고 들고 있으므로 뒤 문장은 자동 커밋으로 새지 않고 `Stopped`를 받는다.

### 5-2. COMMIT 실패 뒤의 오류 메시지

엔진의 `Conflict` 메시지는 "begin again and retry"다. 트랜잭션 안의 COMMIT에서 났다면 "트랜잭션 전체가 롤백되었으니 **BEGIN부터** 다시"라는 뜻이 분명해야 한다. 오류의 종류는 같게 두고(9절), 세션이 COMMIT에서 난 충돌임을 알 수 있게 메시지만 덧붙일지는 11절 Q4.

## 6. 세션을 버리면 (T10)

`Txn`은 `Drop`에서 쓰기를 버리고, 충돌 판정용 기록에서 자기를 지운다(`recent.end`, 0016). 세션이 `Option<Txn>`을 들고 있으므로 **세션을 버리면 열린 트랜잭션이 롤백된다.** 따로 코드가 필요 없다.

| 세션이 사라지는 경우 (#37) | 일어나는 일 |
|---|---|
| 클라이언트가 소켓을 닫음 | `serve()`가 끝나며 세션 `Drop` → 롤백 |
| 깨진 프레임으로 접속을 끊음 (`0x40` 등) | 같음 |
| 접속 스레드가 패닉 | `catch_unwind`(서버의 `serve_guarded`)까지 되감기면서 세션 `Drop` → 롤백 |
| 프로세스가 죽음 | 커밋하지 않은 쓰기는 메모리에만 있었으므로 다시 열면 없음 (WAL에 간 적이 없음, 0010) |

**추천: 그대로 씀.** 검증 단계에서 "BEGIN 안에서 프로세스를 죽였다 다시 열면 흔적이 없다"를 장애 실험(docs/experiments/)으로 한 번 확인한다.

한 가지 기록할 비용: 열린 트랜잭션은 **BEGIN 때의 트리 스냅샷을 붙잡고**, 그 뒤 커밋들의 충돌 기록도 남겨 두게 한다(0016). BEGIN만 하고 오래 가만히 있는 접속("idle in transaction")은 메모리를 붙잡는다. 시간 제한은 #37 이후의 일로 남긴다(11절 Q6).

## 7. 시작 시점과 읽기 (T7, T8)

### 엔진 트랜잭션은 언제 시작하나 (T7)

| 선택지 | 스냅샷 | 장점 | 단점 |
|---|---|---|---|
| **A. BEGIN 때** | BEGIN 순간의 데이터 | 단순. "BEGIN 때 찍은 사진"이라 설명하기 쉬움 | BEGIN 뒤 첫 문장까지 시간이 길면 충돌 창이 그만큼 넓음 |
| B. 첫 문장 때 (늦게) | 첫 문장 순간 | 충돌 창이 조금 좁음. PostgreSQL의 REPEATABLE READ가 첫 문장 때 스냅샷을 찍음 | 세션에 "BEGIN 했지만 txn은 아직 없음" 상태가 하나 더 생김 |

**추천 A.** 차이는 BEGIN과 첫 문장 사이의 짧은 틈뿐이고, 상태 하나를 아낀다.

### 트랜잭션 안의 읽기 (T8)

엔진의 `Txn::get`과 `Txn::scan`은 이미 **스냅샷 + 자기 쓰기**를 합쳐 읽는다(0015, scan의 두 흐름 합치기). 그래서 SQL 층에서 할 일은 없다. 사용자에게 보이는 약속만 적는다.

| 상황 | 결과 |
|---|---|
| `BEGIN; INSERT (1); SELECT` | 1이 보임 (자기 쓰기) |
| `BEGIN; DELETE id=1; SELECT` | 1이 안 보임 |
| 세션 A가 BEGIN 뒤, 세션 B가 행을 넣고 커밋, A가 SELECT | **안 보임** (A의 스냅샷은 BEGIN 때). A가 COMMIT/ROLLBACK 하고 다시 읽으면 보임 |
| 세션 A가 BEGIN 뒤 INSERT, B가 SELECT | **안 보임** (#37 완료 기준 "미커밋 변경이 다른 접속에 안 보임") |
| 같은 트랜잭션에서 같은 SELECT 두 번 | 자기가 그사이 쓰지 않았다면 같은 결과 (반복 읽기) |

ADR 0006의 스냅샷 격리 그대로다: 같은 키를 쓴 두 트랜잭션 중 나중 커밋이 `Conflict`, 쓰기 비틀림(write skew)은 허용.

## 8. 트랜잭션 안의 CREATE TABLE (T9)

표 정보도 엔진의 키와 값이다(0017: 카탈로그 키 `[00][표 이름]`, 표 번호 카운터 키 `[00]`). 그래서 CREATE TABLE도 다른 쓰기처럼 쓰기 모음에 들어가고, 같은 트랜잭션의 뒤 문장은 `txn.get`으로 새 표를 본다. `BEGIN; CREATE TABLE t ...; INSERT INTO t ...; ROLLBACK`은 표까지 흔적 없이 사라진다. PostgreSQL·SQLite와 같은 "트랜잭션 안의 DDL"이다(MySQL·Oracle은 DDL이 열린 트랜잭션을 저절로 커밋한다).

남는 문제는 **표 번호 카운터**다. `next_table_id`는 카운터 키 하나를 읽고 1 올려 쓴다. 그래서:

| 상황 | 결과 | 좋은가 |
|---|---|---|
| A와 B가 동시에 **같은 이름** 표를 만듦 | 나중 COMMIT이 `Conflict` (표 정보 키가 같음) | **필요함**. 아니면 같은 이름의 표가 둘 |
| A와 B가 동시에 **다른 이름** 표를 만듦 | 나중 COMMIT이 `Conflict` (카운터 키가 같음) | 필요 없는 충돌. 같은 번호를 두 표가 받지 않게 해 주는 것은 맞음 |
| A가 BEGIN, B가 표 t를 만들고 커밋, A가 t를 읽음 | A는 `NoSuchTable` (스냅샷) | 스냅샷 격리 그대로 |
| A가 BEGIN 안에서 표를 만들고 행을 많이 넣음, B가 다른 표를 만들고 먼저 커밋 | A의 COMMIT이 `Conflict`, **넣은 행까지 전부** 버려짐 | 아픔. 다만 표 만들기는 드묾 |

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 허용, 카운터 충돌을 받아들이고 문서로 남김** | 할 일 없음. 같은 번호 문제가 구조로 막힘 | 동시 CREATE TABLE이 서로 충돌 |
| B. 트랜잭션 밖에서 번호를 나눠 줌 (PostgreSQL 시퀀스처럼 롤백돼도 되돌리지 않음) | 다른 이름 표끼리는 충돌 없음 | 엔진에 "트랜잭션에 안 묶이는 카운터"가 필요. 롤백된 표의 번호는 빈 번호로 남음 |
| C. BEGIN 안의 CREATE TABLE을 막음 ("지원 안 함") | 문제 자체가 없음 | `BEGIN; CREATE; INSERT; COMMIT`으로 표와 첫 데이터를 함께 만드는 흔한 쓰임을 못 함 |

**추천 A.** 동시에 표를 만드는 일은 드물고, 충돌이 나도 "다시 실행"으로 풀린다(오류 `0x20`이 "다시 실행하면 될 수 있다"고 이미 말함). B는 동시 DDL이 실제로 문제가 될 때 한다.

## 9. 오류가 SQL로 오는 모양 (T11)

이슈 완료 기준 "충돌 오류가 SQL 오류로 전달된다"는 **이미 길이 있다**: 엔진의 `Error::Conflict`는 `SqlError::Engine(Conflict)`가 되고(0022 7절 테스트), 서버는 이것을 코드 `0x20`("충돌, 다시 실행하면 될 수 있다")으로 보낸다. 이번에 하는 일은 그 길이 **COMMIT 문장에서도** 지나가는지 확인하는 것이다.

| 오류 | 지금 | 이번 추천 | #34가 정할 것 |
|---|---|---|---|
| 충돌 | `SqlError::Engine(Conflict)`, 코드 `0x20` | 그대로 | 독립 종류로 꺼낼지, "다시 시도할 만함" 분류에 넣을지 |
| 트랜잭션 상태에 안 맞는 명령 (4절) | 없음 | **새 종류 하나** (예: `SqlError::Transaction(…)`: 이미 트랜잭션 중 / 트랜잭션이 없음 / `execute`에 BEGIN), 서버 코드는 `0x01–0x1F` 범위에 새로 하나 (#37에서 docs/protocol.md에 추가) | 이름과 세분 |
| 같은 기본 키 동시 INSERT | 트랜잭션 안이면 COMMIT 때 `Conflict` (#34 이슈 댓글의 W2와 같은 현상) | 그대로 | "중복"과 "충돌"을 어떻게 보여 줄지 |

| 선택지 (상태 오류의 종류) | 장점 | 단점 |
|---|---|---|
| A. 기존 `Unsupported`에 넣음 | 종류가 안 늘어남 | "지원 안 함"이 아니라 "지금 상태에서 틀림". 클라이언트가 구분할 수 없음 |
| **B. 새 종류 하나** | #37 클라이언트가 "트랜잭션이 이미 끝났다"를 알아챌 수 있음 (예: COMMIT 실패 뒤 습관적 ROLLBACK) | 종류와 서버 코드가 하나씩 늘어남 |

**추천 B.** #34가 오류 체계를 다시 짜면 그 안으로 옮긴다.

## 10. 테스트 계획 (T13)

| 테스트 | 무엇을 |
|---|---|
| 모델 비교 속성 테스트 (`tests/txn_model.rs` 또는 0022의 `write_model` 확장) | 세션 하나에 무작위 문장 열: INSERT / UPDATE / DELETE / SELECT에 **BEGIN / COMMIT / ROLLBACK**을 섞음(상태에 안 맞는 것도 일부러). 모델 = 커밋된 `BTreeMap` + 트랜잭션 중이면 작업용 복사본. 문장마다 ① 결과, ② 오류 종류, ③ `in_transaction()`이 같은지. **오류가 난 문장 뒤 작업용 표는 문장 전과 똑같아야** 함(T5의 계약). COMMIT/ROLLBACK 뒤에는 **둘째 세션**의 자동 커밋 `SELECT *`로 커밋된 표 전체를 비교 |
| 생성기 | 중복 키가 뒤 행에 있는 여러 행 INSERT, 셋째 행에서 넘치는 UPDATE를 자주 만들어 3절 경계를 두드림 |
| `tests/sql.rs` 예제 | 3절 첫 예(BEGIN 안의 중복 INSERT → 1만 남음), BEGIN 안의 CREATE TABLE + INSERT + ROLLBACK → 표도 없음, 4절 표의 상태 오류 셋(열린 txn이 살아 있는지까지), `execute(&db, "BEGIN")` 오류, 세션 Drop → 롤백 |
| 두 세션 결정적 테스트 | ① A BEGIN, A UPDATE id=1, B 자동 커밋 UPDATE id=1 → A COMMIT `Conflict`, A는 자동 커밋 상태, 표는 B의 값. ② 미커밋 INSERT가 B에 안 보임. ③ A BEGIN 뒤 B의 커밋이 A에 안 보이고 A COMMIT 뒤엔 보임. ④ 다른 이름 표 동시 CREATE → 나중이 `Conflict`(8절, 받아들인 동작을 고정) |
| 여러 스레드 | 스레드마다 세션 하나: `BEGIN; SELECT n; UPDATE n = n + 1; COMMIT`을 `Conflict`면 BEGIN부터 재시도하며 N번 → 최종 n = N (잃어버린 갱신 없음) |
| 디스크 실패 (`SimFs::fail_after`) | BEGIN 안 COMMIT이 `OutcomeUnknown` → 세션은 자동 커밋, 다음 문장 `Stopped`. 다시 열면 그 트랜잭션은 전부 있거나 전부 없음 |
| 장애 실험 (검증 단계, docs/experiments/) | BEGIN 안에서 프로세스를 죽이고 다시 열기 → 흔적 없음 |
| 블라인드 테스터 (검증 단계) | 이 문서·이슈·ADR만 보고 테스트를 씀 (CLAUDE.md) |
| 벤치마크 | 성능 주장이 없으므로 A/B는 하지 않음. INSERT를 두 단계로 바꾼 뒤 큰 INSERT의 시간만 전후로 재어 기록 |
