# 0029. 벤치마크: 네트워크 다중 클라이언트 — 설계

이슈 #39 (스펙 #12의 "네트워크 다중 클라이언트 처리량"). 스펙 #12가 내건 증거는 "**클라이언트 수를 늘릴 때** SQLite 대비 쓰기 처리량"이다. 티켓 18(#30, 설계 0026)은 같은 질문을 **한 프로세스 안의 스레드**로 잰다. 이번 티켓은 그 사이에 **네트워크**(TCP, 통신 규칙, 접속 스레드, 세션)를 끼워 넣고, 실제 사용자가 보게 될 모습을 잰다. 그리고 ADR 0010이 남긴 숙제가 하나 있다. "**#39에서 스레드 수나 문맥 전환이 처리량의 병목으로 보이면** 하이브리드(tokio) 길을 먼저 검토한다." 이 벤치마크가 그 판정의 근거이고, 티켓 28(#66, async 서버 A/B)이 그대로 다시 쓸 측정 도구다.

> 이 문서는 티켓 18(설계 0026, `crates/oakdb-bench`, `bench_concurrent.py`, CSV + SVG 그림)과 티켓 25(#37, 접속마다 세션, PR #82)가 `main`에 들어간 뒤 구현한다고 가정한다. 티켓 18의 결정이 바뀌면 이 문서의 "재사용" 부분도 따라 바꾼다.

## 비유: 식당에 손님을 몇 명까지 받을 수 있나

티켓 18이 **주방 안에서** 요리사 여럿이 동시에 요리할 때 시간당 몇 접시가 나오나를 쟀다면, 이번 티켓은 **홀까지 포함한 식당 전체**를 잰다. 손님(클라이언트)이 문을 열고 들어와(접속 + 인사), 자리에 앉아 웨이터(접속 스레드) 한 명을 배정받고, 주문(QUERY)을 넣고, 음식(응답)을 받는다. 주방(엔진)은 그대로인데 홀이 끼어들면 무엇이 달라지나가 질문이다.

| 식당 | Oakdb | 이번에 볼 것 |
|---|---|---|
| 손님 한 명에 웨이터 한 명 | 접속 하나 = 접속 스레드 하나 (ADR 0010) | 웨이터가 512명이 되면 웨이터끼리 부딪혀(문맥 전환) 느려지나 |
| 웨이터의 유니폼과 사물함 | 스레드 스택 256 KiB, 버퍼, 세션 | 손님 한 명이 메모리를 얼마나 차지하나 |
| 문 앞 대기 의자 | `listen` 대기열(backlog) | 손님 500명이 한꺼번에 몰리면 문 앞에서 돌아가나 |
| 좌석 수 | 접속 상한 512, 코드 `0x45` | 513번째 손님이 정중히 거절되고, 안의 손님은 영향이 없나 |
| 주방의 오븐 한 번 | 완전 sync (macOS 약 3 ms) | 홀을 거쳐도 오븐이 여전히 전부인가 |

**Java·Spring으로 치면** JMeter나 Gatling으로 Spring 서버에 가상 사용자 1명, 2명, … 512명을 붙여 TPS와 p99를 보는 부하 시험이다. 가상 사용자 수는 곧 **HikariCP 풀 크기**다. HikariCP 문서의 유명한 "About Pool Sizing"이 말하듯, 풀을 키우면 TPS가 오르다가 어느 점에서 평평해지고 응답 시간만 늘어난다. 이번 벤치마크가 찾는 것이 Oakdb의 그 **꺾이는 점**이다. 응용 개발자에게 "Oakdb에는 풀 크기를 몇으로 두라"고 말할 근거가 된다.

**OS로 치면** 프로세스(스레드) 수백 개를 띄웠을 때 스케줄러가 버티나, 그리고 스택 256 KiB를 `mmap`으로 잡아도 실제로 손댄 페이지만 물리 메모리를 먹는(demand paging) 것을 RSS로 확인하는 일이다. ft_malloc에서 큰 덩어리를 `mmap`으로 받아도 건드린 페이지만 실제로 잡히던 것과 같다.

## Q1. 무엇을 재나

식당으로 치면 볼 숫자는 다섯이다. **시간당 손님 수**(처리량), **주문부터 음식까지 걸린 시간**(지연), **문을 열고 앉기까지 걸린 시간**(접속 비용), **손님 한 명이 차지하는 자리**(메모리, 파일 기술자), **웨이터가 바쁜 정도**(CPU).

| 지표 | 무엇 | 왜 | 비용 |
|---|---|---|---|
| **처리량** (응답/초) | 측정 창 안에서 성공 응답을 받은 질의 수 ÷ 시간. 트랜잭션 작업은 COMMIT 성공 수 | 이슈의 본 질문. 그래프의 세로축 | 없음 |
| **지연 p50·p99·p999** | QUERY를 보낸(열린 고리면 **보내려 했던**, Q4) 순간부터 응답을 다 읽은 순간까지. 트랜잭션은 BEGIN부터 COMMIT 응답까지, 충돌로 다시 한 것 포함 | 처리량만 보면 "많이 팔았지만 한 손님은 오래 기다렸다"를 놓친다. p999는 체크포인트 같은 가끔 오는 멈춤을 본다 | 요청마다 `Instant` 두 번 + 히스토그램 칸 하나 |
| **접속 비용** | `connect` + HELLO/READY까지. (가) 하나씩 차례로, (나) N개를 한꺼번에(폭주) 열 때 마지막 접속까지 걸린 시간과 실패 수 | 매 요청마다 새로 접속하는 응용(풀 없는 PHP·CGI 방식)이 얼마를 내나. 폭주 때 `listen` 대기열이 넘치는가 | 없음 |
| **접속당 메모리** | 노는 접속 0·64·128·256·512개일 때 서버 RSS. 기울기 = 접속 하나의 비용 | 스택 256 KiB는 **예약**일 뿐 실제로는 손댄 페이지만 잡힌다(ADR 0010). 그 실제 값을 숫자로 | 바깥에서 `ps`로 읽음 |
| **스레드 수·파일 기술자 수** | 같은 순간의 서버 스레드 수, 열린 기술자 수 | "접속 하나 = 스레드 하나 = 기술자 하나"가 실제로 지켜지나. 상한 + 64 여유가 맞나 | Linux `/proc/<pid>/status`·`/proc/<pid>/fd`, macOS `ps -M`·`lsof -p` (측정 창 밖에서만) |
| **CPU** | 측정 창 동안 서버·부하 발생기 각각의 사용자+시스템 CPU 시간 | 같은 기계라 둘이 코어를 나눠 쓴다. 부하 발생기가 병목이 아닌지 확인(Q5). 질의 하나에 서버 CPU 몇 µs | `getrusage`(부하 발생기), `ps -o time`(서버) |
| (선택) 문맥 전환 수 | Linux `/proc/<pid>/status`의 `voluntary_ctxt_switches` | ADR 0010의 "문맥 전환이 병목" 판정을 직접 보는 숫자. macOS에는 쉬운 길이 없어 Linux만 | 측정 창 앞뒤로 한 번씩 |
| 엔진 통계 | `Stats`(커밋, 충돌, 묶음, sync 수; 티켓 18이 더한 묶음 분포) | 네트워크 너머에서도 묶음이 커지나(그룹 커밋) | 서버가 끝날 때 한 줄 출력 |

**p999를 언제 말하나.** 3 ms짜리 쓰기를 5초 재면 클라이언트 하나에 약 1 600개라 p999는 표본 1~2개다. 그래서 **표본이 1만 개 이상일 때만** p999를 적고, 아니면 "표본 부족"으로 적는다. 라운드마다 따로 계산하지 않고 라운드들의 히스토그램을 합쳐 계산한다(Q10).

**추천: 처리량 + p50·p99(·p999 규칙) + 접속 비용(차례·폭주) + 접속당 메모리·스레드·기술자 + CPU(양쪽) + 엔진 통계. 문맥 전환은 Linux에서만.** 처리량과 지연이 주인공이고 나머지는 "왜 그 숫자인가"와 "ADR 0010을 다시 볼 때인가"를 말해 주는 조연이다.

## Q2. 클라이언트 수, 상한 너머

| | A. 1·2·4·8·16·32·64 (티켓 18과 같음) | **B. 1·2·4·8·16·32·64·128·256·512 + 상한 너머 한 점** | C. 1~512 촘촘히 |
|---|---|---|---|
| 보이는 것 | 티켓 18과 겹치는 범위만 | 꺾이는 점, 그리고 ADR 0010이 약속한 "수백 접속"의 끝(512) | 같지만 오래 걸림 |
| 한 곡선 (10라운드 × 약 7초) | 약 8분 | 약 12분 | 1시간 넘음 |

**상한 너머는 어떻게 재나.** 서버는 상한(512)을 넘는 접속에 인사 전에 `0x45`를 보내고 끊는다. 재고 싶은 것은 "**거절이 안의 손님을 방해하지 않나**"다.

| | A. 안 잼 | **B. 512개가 일하는 동안 100개가 계속 접속을 시도** | C. 상한을 바꿔 가며 |
|---|---|---|---|
| 보는 것 | — | 거절 수, 거절 하나에 걸린 시간, 안쪽 512개의 처리량이 거절 없는 때와 같은가 | 상한 자체의 비용 |
| 주의 | — | 거절된 접속은 잠깐 머물다 닫힌다(`LINGER` 1초, 동시에 32개까지). 머무는 스레드가 성능에 보이는지도 함께 | 상한은 이번 질문이 아님 |

**추천: B + 상한 너머 B.** 128·256·512는 macOS 기본 파일 기술자 soft 한도(256)를 넘으므로 **부하 발생기도** 시작할 때 자기 soft 한도를 올린다(서버의 `rlimit::raise_fd_limit`을 그대로 부름).

## Q3. 어떤 작업으로 재나

모두 SQL이다. 네트워크 너머에는 SQL밖에 없기 때문이다. 표는 `t(id INTEGER PRIMARY KEY, v TEXT)`, 측정 전에 1만 행을 미리 넣는다(티켓 18 Q2와 같은 이유). 값은 100바이트.

| 작업 | 내용 | sync | 역할 |
|---|---|---|---|
| **N1. 자동 커밋 쓰기** (본 작업) | `INSERT INTO t VALUES (<난수 id>, '<100B>')`. id는 시드 고정 난수, 클라이언트끼리 안 겹침 | 있음 | 스펙의 "쓰기 처리량". 그룹 커밋이 네트워크 너머에서도 일하나 |
| **N2. 자동 커밋 점 읽기** (본 작업) | `SELECT v FROM t WHERE id = <있는 id>` | **없음** (읽기 전용은 커밋 스레드를 안 거침) | 디스크를 뺀 "홀만의 천장": 통신 + SQL + 접속 스레드 + CPU. **스레드 수가 병목인지** 가장 잘 보이는 곳 (H3) |
| N3. 섞기 | 읽기 90% + 쓰기 10% | 일부 | 흔한 웹 서비스 모양. 몇 점만 기록 |
| N4. 짧은 트랜잭션 | `BEGIN; SELECT …; UPDATE … WHERE id = <내 행>; COMMIT` (왕복 4번), 행은 안 겹침 | 있음 | 왕복 수가 늘면 지연이 어떻게 쌓이나. 세션이 일하는 길(티켓 25). 몇 점만 기록 |
| N5. 충돌 | N4와 같되 뜨거운 행 16개 중 하나를 +1. `0x20`(충돌)이면 BEGIN부터 다시 | 있음 | Oakdb가 불리한 곳(먼저 커밋한 쪽이 이김). 처리량과 **다시 한 비율**만 기록, 주장 없음 |

| 서버의 디스크 | 무엇 | 쓰는 곳 |
|---|---|---|
| **실제 디스크** (`StdFs`, 완전 sync) | 사용자가 겪는 그대로 | 모든 작업의 본 곡선 |
| 가짜 디스크 (`SimFs`, 메모리) | sync 없음. 쓰기에서도 엔진·홀의 천장 | N1 몇 점 참고선. 티켓 18의 "sync 없음" 선과 짝 |

**추천: N1·N2 전 곡선, N3·N4·N5는 1·16·64·256·512 다섯 점. 실제 디스크가 본, 가짜 디스크는 N1 참고선.**

## Q4. 부하를 어떻게 거나: 닫힌 고리와 열린 고리

가장 많이 틀리는 곳이다.

**닫힌 고리(closed loop)**: 손님 N명이 각자 "주문 → 음식 받음 → 바로 다음 주문"을 되풀이한다. JMeter의 스레드 그룹(생각 시간 0)이 이것이다. 손님 수가 곧 동시에 걸린 요청 수라서 "클라이언트 수 대 처리량"을 재기에 딱 맞다.

**열린 고리(open loop)**: 손님이 **정해진 속도로**(예: 초당 2 000명) 문을 열고 들어온다. 주방이 밀려도 손님은 계속 온다. Gatling의 `constantUsersPerSec`, wrk2가 이것이다.

**coordinated omission(조율된 누락).** 주방이 체크포인트로 0.5초 멈췄다고 하자. 닫힌 고리 측정기의 손님은 음식을 기다리느라 그동안 **새 주문을 안 넣는다.** 그래서 기록에는 "0.5초 걸린 주문 1건"만 남고, 실제 세상이었다면 그 0.5초 동안 들어와 줄을 섰을 수백 명의 기다림은 **아예 기록되지 않는다.** 측정기가 서버와 "조율해서" 나쁜 순간을 덜 재는 것이다. 그래서 닫힌 고리의 p99·p999는 실제보다 좋게 나온다. Gil Tene이 이름 붙였고, wrk2와 HdrHistogram은 "보내려 했던 시각"부터 재서 이를 고친다.

| | A. 닫힌 고리만 | **B. 닫힌 고리로 곡선 + 열린 고리로 지연 몇 점** | C. 열린 고리만 |
|---|---|---|---|
| 처리량 대 클라이언트 수 | 정확 (이슈의 질문 그대로) | 정확 | "클라이언트 수"가 축이 아니게 됨 (속도가 축) |
| 꼬리 지연 | **과소평가** (coordinated omission) | 열린 고리 점에서 정직하게 | 정직 |
| 구현 | 쉬움 | 둘 다. 열린 고리는 접속마다 일정표를 두고, 늦어도 **보내려 했던 시각**부터 잰다 | 같음 |
| 주의 | — | 통신 규칙은 파이프라이닝을 약속하지 않으므로(`docs/protocol.md` 2절) 접속 하나에 요청은 하나씩. 그래서 열린 고리도 접속 수가 충분해야 함 | 같음 |

**열린 고리를 어디서 재나.** 클라이언트 64개를 붙이고, 그 64개로 닫힌 고리에서 잰 최대 처리량의 **50%·80%·95%** 속도로 요청을 넣는다. 그래프는 "속도 대 p99"(하키 스틱 모양: 한계 근처에서 꼬리가 치솟음). 닫힌 고리 p99와 열린 고리 p99를 같은 표에 두어, 차이가 곧 coordinated omission의 크기임을 보인다.

**리틀의 법칙으로 측정기를 점검한다.** 닫힌 고리에서는 `동시 요청 수(N) = 처리량(X) × 평균 응답 시간(R)`이 거의 맞아야 한다. 은행 창구로 치면 "줄에 선 사람 수 = 초당 들어오는 사람 × 한 사람이 머무는 시간". 크게 어긋나면 측정기가 시간을 잘못 재고 있다는 뜻이다. 라운드마다 `N ÷ (X × R)`을 계산해 0.95~1.05를 벗어나면 그 라운드에 표시한다.

**추천: B.** 이슈의 질문(클라이언트 수 1~N)은 닫힌 고리, 꼬리 지연의 정직한 숫자는 열린 고리 세 점. 둘 다 결과에 "닫힌 고리 p99는 과소평가될 수 있다"를 적는다.

| 지연 보고 | 라운드마다 p50·p99 → 그 중앙값 + CI. p999는 라운드 히스토그램을 합쳐서, 표본 1만 이상일 때만 | 지연은 주장하지 않음 (기록) |
| A/A | 없음 | 가설마다 하나 |

**히스토그램.** 지연은 µs 단위로 로그 칸(2의 거듭제곱을 다시 16칸으로 나눔, 오차 약 6%)에 셈해 라운드마다 CSV 한 줄로 남긴다. 새 크레이트(`hdrhistogram`)를 쓰는 것과 손으로 짜는 것(수십 줄)이 있는데, **손으로 짠다**(측정기를 async로 바꿀 때도 같은 코드를 쓰고, 칸이 CSV에 그대로 나가야 다시 그릴 수 있다).

## Q11. 무엇을 주장하고, 각 주장의 A/A는

미리 적고, 숫자를 본 뒤 바꾸지 않는다. 예상치는 벤치마크 0009(왕복 24 µs, 디스크 3 ms)와 실험 0015의 그룹 커밋 배수에서 왔다. 모두 내 Mac, 실제 디스크.

| 가설 | 비교 | 예상 | 판정 기준 |
|---|---|---|---|
| **H1. 네트워크의 값은 작다** (디스크 쓰기) | N1 16클라이언트 처리량 ÷ 티켓 18의 SQL 자동 커밋 INSERT 16스레드 처리량(같은 날, 같은 Mac) | 0.95 근처. sync(3 ms)에 비하면 왕복(수십 µs)은 작다 | 비율 CI 하한 ≥ **0.90** |
| **H2. 네트워크 너머에서도 그룹 커밋이 일한다** | N1 64클라이언트 ÷ N1 1클라이언트 | 10배 이상 (실험 0015) | 비율 CI 하한 > 1, p < 0.05 |
| **H3. 512 접속에서 스레드가 병목이 아니다** (ADR 0010 판정) | N2(읽기) 512클라이언트 ÷ N2 64클라이언트 | 0.8~1.0. 코어 8개가 이미 64에서 다 차고, 512에서는 문맥 전환만큼 조금 줄어든다 | 비율 CI 하한 ≥ **0.80**이면 "병목 아님". 미달이면 **ADR 0010의 다시 볼 조건 충족**으로 기록하고 티켓 28에 넘긴다 (실패가 아니라 결과) |
| **H4. 네트워크 너머에서도 Oakdb가 SQLite보다 쓰기 처리량이 높다** | N1 64클라이언트: Oakdb ÷ K2-S1, Oakdb ÷ K2-S2 | 5배 이상 (SQLite는 쓰기를 한 번에 하나, sync도 커밋마다) | 두 비교 모두 비율 CI 하한 > 1, p < 0.05 |
| (기록만) | 상한 너머의 영향, 접속당 메모리, 접속 비용, N3~N5, 열린 고리 지연, 가짜 디스크 선, Linux 곡선·인공 지연 | — | 주장 없음 |

| A/A 대조군 | 무엇 | 쓰는 규칙 |
|---|---|---|
| H1 | N1 16클라이언트 대 같은 것 | 비율 CI가 1을 품고 p > 0.1. 아니면 그 가설은 **판정하지 않고** 잡음 원인부터 찾는다 |
| H2 | N1 1클라이언트, N1 64클라이언트 각각 자기 자신과 | 같음 |
| H3 | N2 512클라이언트 대 같은 것 | 같음. 읽기는 CPU에 묶여 흔들림이 다를 수 있다 |
| H4 | K2-S1 64클라이언트 대 같은 것 (SQLite의 `busy_timeout` 졸기가 흔들림을 키울 수 있음) | 같음 |

**Linux에서는** H2·H4의 방향(비율 > 1)과 H3 비율의 값만 본다. 러너는 코어가 적어 H3의 512점이 측정기와 다툰다. 그 해석은 회고에 적는다.

**H3이 왜 이 모양인가.** ADR 0010의 다시 볼 조건은 "스레드 수나 문맥 전환이 병목으로 보일 때"다. 이것을 숫자로 바꾸면 "접속을 64개에서 512개로 늘렸을 때, 일은 같은데 처리량이 20% 넘게 떨어지나"다. 쓰기(N1)는 sync가 지배해 스레드의 비용이 가려지므로, 커밋 스레드를 안 거치는 읽기(N2)로 본다. 0.8이라는 선은 측정 전에 정한 약속이다. 사용자가 측정 전에 **0.80을 그대로** 정했다.

## Q12. 티켓 28(async A/B)이 어떻게 다시 쓰나

티켓 28의 완료 조건은 "클라이언트 수(수십 ~ 수천)에 따른 처리량·지연·메모리를 스레드 방식과 A/B로 비교하고, A/A와 함께 docs/benchmarks에". 이번에 만드는 도구를 **그대로** 쓰려면 경계를 미리 정해 둔다.

| 부품 | 이번 티켓 | 티켓 28이 하는 일 |
|---|---|---|
| `net_server` | `--server threads` (지금 서버), `--fs disk|mem`, `--max-connections`, `--port 0`. 포트와 끝날 때의 `Stats`를 정해진 한 줄로 출력 | `--server async`를 더함. 출력 형식은 그대로 |
| `net_load` | 통신 규칙만 앎 (서버가 무엇인지 모름). `--clients`, `--workload`, `--mode closed|open --rate`, `--warmup`, `--window`. 결과 한 줄 + 히스토그램 | 그대로. 수천 접속에서 측정기 한계(Q6 점검)에 닿으면 클라이언트 함수만 async로 바꾼 `--driver async`를 더함 |
| `bench_network.py` | "설정" = (서버 종류, 디스크, 작업, 클라이언트 수). 설정 목록을 받아 라운드마다 돌아가며 실행 | 서버 종류 `threads`/`async`를 A/B로. A/A는 `threads` 대 `threads` |
| CSV 열 | 설정 열에 `server` 열을 **처음부터** 둠 (이번엔 늘 `threads`) | 같은 CSV에 `async` 줄이 더해짐. 그림은 서버 종류별 선 |
| 클라이언트 수 | 512까지. 서버 상한도 512 | 상한을 4096 등으로 올려 띄움. 측정기·서버 모두 기술자 한도 올림 |
| 메모리 측정 | 노는 접속 N개의 RSS | async의 "접속당 메모리"(작업 하나의 크기)와 바로 비교 |

이렇게 하면 티켓 28은 서버 쪽만 만들고 측정은 명령 한 줄을 바꿔 돌린다. 같은 측정기, 같은 작업, 같은 통계라서 "async가 빨라진 건 측정 방법이 달라서"라는 반론이 생기지 않는다.

**추천: 위 표 그대로.** 이번 티켓의 기준 숫자(스레드 서버 곡선)가 티켓 28의 A가 된다.
