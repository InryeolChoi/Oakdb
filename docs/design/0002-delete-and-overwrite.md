# 0002. 삭제와 덮어쓰기: 설계

이슈 #14. 같은 키에 다시 쓰면 값이 바뀌고, `delete`로 키를 지울 수 있으며, 지워진 공간은 페이지 안에서 다시 쓴다.

01번(#13)이 Merge 전 검증에서 **덮어쓰기와 페이지 정리(compact)를 이미 넣었다**(설계 0001, 회고 0001). 그래서 이번 티켓은 삭제를 더하고, 삭제와 덮어쓰기가 섞인 커밋이 **순서와 상관없이** 올바르게 들어가게 하는 데 집중했다.

## 1. API

```rust
let mut txn = db.begin();
txn.delete(b"oak")?;               // 커밋할 때 지운다
assert_eq!(txn.get(b"oak")?, None); // 내가 지운 것은 바로 안 보인다
txn.commit()?;
```

- **없는 키를 지워도 오류가 아니다.** "이 키가 없는 상태로 만든다"는 뜻으로 본다. SQL의 `DELETE ... WHERE`가 0행을 지워도 오류가 아닌 것과 같다.
- **지웠는지 여부(`bool`)를 돌려주지 않는다.** 돌려주려면 `delete`가 페이지를 읽어야 하는데, 지금 트랜잭션은 쓰기를 커밋까지 미루기만 한다(ADR 0006). 필요하면 `get`으로 먼저 확인하면 된다.
- 키 길이 검사(512바이트)는 `put`, `get`과 같다.

## 2. 트랜잭션 버퍼: 지운 것도 "쓰기"다

트랜잭션의 개인 버퍼를 `BTreeMap<키, 값>`에서 `BTreeMap<키, Option<값>>`으로 바꿨다. `Some(값)`은 put, `None`은 delete다. 키마다 **마지막 쓰기만** 남는다.

| 같은 트랜잭션 안에서 | 버퍼 | `get` | 커밋 결과 |
|---|---|---|---|
| put → delete | `None` | 없음 | 지워짐 |
| delete → put | `Some(새 값)` | 새 값 | 새 값 |
| delete만 (원래 있던 키) | `None` | 없음 | 지워짐 |

`None`을 "버퍼에 없음"과 구분하는 게 핵심이다. 버퍼에 없으면 페이지를 읽고, 버퍼에 `None`이 있으면 페이지에 값이 있어도 "없음"이다. 이런 표시를 흔히 **묘비(tombstone)** 라고 부른다.

## 3. 페이지에서 지우기

`LeafPage::delete`는 슬롯을 빼고, 셀이 차지하던 바이트를 `frag_bytes`에 더한다. 덮어쓰기에서 옛 셀을 치우는 것과 **똑같은 동작**(`remove_slot`)이다. 그래서 공간 재사용도 이미 있는 정리(compact)가 그대로 해 준다. 새 셀이 가운데 빈칸에 안 들어갈 때 살아 있는 셀을 끝으로 당겨 붙이면, 지운 셀의 자리가 빈칸으로 모인다.

## 4. 커밋 순서: 키 순서대로 적용하면 틀린다

처음 떠올린 방법은 버퍼를 키 순서대로 돌며 put은 넣고 delete는 지우는 것이다. 그런데 이러면 **결과는 페이지에 들어가는데도 `PageFull`이 날 수 있다.**

> 페이지가 거의 찼다. 한 트랜잭션에서 `"z"`(큰 값)를 지우고 `"a"`(큰 값)를 넣는다. 키 순서로는 `"a"`가 먼저라서, `"z"`가 아직 자리를 차지하고 있을 때 `"a"`를 넣으려다 `PageFull`.

이삿짐을 넣을 때, 버릴 짐을 먼저 빼야 새 짐이 들어가는 것과 같다. 그래서 커밋을 두 단계로 나눴다.

1. 이 트랜잭션이 쓰는 **모든 키를 먼저 뺀다**(delete든 put이든).
2. put한 키만 다시 넣는다.

1단계가 끝나면 남은 페이지는 "이 트랜잭션과 상관없는 키들"뿐이고, 정리를 하면 빈 공간이 모두 모인다. 그러면 2단계는 **최종 결과가 들어가는지**만으로 성공과 실패가 갈린다. 어떤 순서로 정렬되든 상관없다.

어느 단계에서든 실패하면 고치던 복사본을 버린다. 01번과 마찬가지로 커밋은 전부 아니면 전무다. `PageFull`이면 같은 커밋에 들어 있던 delete도 반영되지 않는다.

## 5. 이번에 하지 않은 것

- **지운 값의 바이트를 0으로 덮지 않는다.** 실험 0003에서 확인했듯이, 지운 값은 정리가 일어날 때까지 파일에 남는다. WAL에 남는 페이지 사본도 같은 문제를 갖기 때문에, 페이지와 WAL을 함께 다루도록 WAL 티켓(#22)으로 넘겼다(PR #44에서 결정).
- 페이지가 비어도 페이지를 돌려주지 않는다. 페이지가 한 장뿐이라 돌려줄 곳이 없다. 페이지 병합과 해제는 분할(#15) 뒤의 일이다.
