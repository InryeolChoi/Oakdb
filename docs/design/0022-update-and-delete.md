# 0022. UPDATE와 DELETE — 설계

이슈 #33. 지금까지 Oakdb의 SQL은 표를 만들고(CREATE), 행을 넣고(INSERT), 찾기(SELECT)만 했다. 이번 티켓에서 **이미 있는 행을 고치고(UPDATE) 지운다(DELETE)**. 어떤 행을 고를지는 0019의 WHERE를 그대로 쓴다. 그러면 새로 정할 것은 "고른 행을 **어떤 순서로, 언제** 고치나"다. 행을 찾는 일과 고치는 일이 같은 표 위에서 겹치기 때문에, 찾기만 할 때는 없던 문제가 생긴다. 다음 티켓 #34(오류 종류)와 #35(BEGIN/COMMIT)도 이 위에 얹히므로, 그 둘과 부딪히지 않는 모양을 고른다.

**비유**: 표는 0019처럼 **청구번호(기본 키) 순으로 꽂힌 도서관 책장**이다. 사서에게 "100번대 책의 청구번호를 전부 1000씩 올려 주세요"라고 부탁했다고 하자.

| 사서가 일하는 방식 | 무슨 일이 생기나 | DB에서는 |
|---|---|---|
| 책장을 앞에서부터 훑으며, 만나는 책마다 번호를 고쳐 **바로 새 자리에 꽂는다** | 1100번대로 옮긴 책을 훑다가 다시 만나 2100번대로 또 옮긴다. 끝나지 않는다 | **할로윈 문제** (1절) |
| 먼저 **목록표에 고칠 책을 전부 적고**, 다 적은 뒤 목록을 보며 옮긴다 | 한 권을 한 번씩만 옮긴다 | 키를 먼저 모으고 고치기 (추천) |
| 옮기다 보니 1100번 자리에 이미 다른 책이 있다 | 하던 일을 **전부 되돌리고** "중복 번호"라고 알린다 | 기본 키 중복 → 문장 전체 취소 (3절, 6절) |

Java/Spring으로 치면 `for (Row r : list) { if (...) list.remove(r); }`가 `ConcurrentModificationException`을 내는 것과 같은 문제다. Java가 예외로 막듯이, Rust는 **컴파일 단계에서** 막는다. 엔진의 `scan`은 트랜잭션을 `&txn`(공유 빌림)으로 잡고 있고 `put`/`delete`는 `&mut txn`(배타 빌림)이 필요하다. 그래서 "훑으면서 고치기"는 애초에 컴파일되지 않고, **"모으고, 그다음 고치기"** 모양이 강제된다(0019 6절 끝, #32 리뷰). 이번 설계는 그 모양 위에서 세부를 정한다.

```
"UPDATE users SET age = age + 1 WHERE id BETWEEN 10 AND 19 AND age IS NOT NULL"
  파서   → Update { table, set: [(age, age + 1)], filter: And(...) }
  계획   → 0019의 plan(): 범위 [10, 19], 거르기 식 전체 / SET 식 타입 검사 (행을 읽기 전)
  1단계  → scan(범위)로 맞는 행을 모두 모으고, 행마다 새 행을 계산하고, 중복 키까지 검사 (아직 쓰지 않음)
  2단계  → 모은 목록대로 put/delete
  결과   → Affected(고른 행 수), 커밋
```

## 1. 할로윈 문제 (U3)

이름의 유래: 1976년 할로윈 무렵 IBM System R 팀이 "급여가 25,000달러 미만인 직원의 급여를 10% 올려라"를 돌렸더니, **모든 직원이 25,000달러를 넘을 때까지** 계속 올랐다. 급여 순 인덱스를 훑으면서 고치니, 올린 직원이 인덱스의 뒤쪽으로 옮겨가 다시 훑어졌기 때문이다.

Oakdb에서 같은 일이 생기는 곳은 **기본 키를 고칠 때**다. 행은 기본 키 순으로 B+Tree에 있으므로, `UPDATE t SET id = id + 1000 WHERE id >= 100`을 훑으면서 고치면 옮긴 행을 다시 만난다. 기본 키가 아닌 열만 고치면 행이 자리를 옮기지 않으니 이 문제는 없지만, 같은 길로 실행하는 편이 단순하다.

| 선택지 | 하는 일 | 장점 | 단점 |
|---|---|---|---|
| **A. 모으고 고치기** | 1단계: `scan`으로 맞는 행을 모두 목록에 모음. 2단계: 목록대로 `put`/`delete` | Rust 빌림 규칙이 원래 강제하는 모양. 한 행을 한 번만 고침이 구조로 보장됨. 2단계 전에 모든 검사를 끝낼 수 있음(6절) | 맞는 행 수만큼 메모리 (아래) |
| B. 스냅샷만 훑기 | 트랜잭션이 시작할 때의 스냅샷(`Arc<Tree>`)을 따로 들고 훑으며, 쓰기는 트랜잭션에 바로 넣음. 스냅샷은 변하지 않으므로 옮긴 행을 다시 만나지 않음 | 목록이 필요 없음 | 엔진에 "커밋된 것만 훑기" API를 새로 내야 함. **같은 트랜잭션에서 앞서 쓴 것을 못 봄**: #35에서 `BEGIN; INSERT ...; UPDATE ...`의 UPDATE가 방금 넣은 행을 놓친다. 중복 키 검사도 따로 해야 함 |
| C. 조각내 훑기 | 100행씩 모아 고치고, 마지막 키 다음부터 다시 훑기 | 메모리가 조각 크기로 묶임 | 다시 훑을 때는 내가 고친 것이 보이므로 기본 키를 고치면 할로윈 문제가 **돌아옴** |

**추천 A.** B는 지금은 맞지만 #35에서 틀리고, C는 문제를 다시 불러온다.

### 1-1. A의 메모리 비용

"큰 표의 모든 행을 UPDATE하면 목록이 표만큼 커진다"는 걱정은 맞다. 다만 Oakdb에서는 **어차피 그만큼 쓰고 있다**.

| 이미 있는 것 | 크기 |
|---|---|
| 엔진의 트랜잭션 쓰기 모음(`Txn.writes`, `BTreeMap`) | 커밋 전까지 **고친 행 전부의 새 값**을 메모리에 들고 있음 |
| 데이터베이스 자체 | 엔진은 트리 전체를 메모리에 둠(0015 스냅샷 읽기) |
| SELECT 결과 | 0019 Q7대로 모든 결과 행을 `Vec`에 모음 |

그래서 A의 목록은 "고친 행 수 × 행 크기"를 **두 배쯤**으로 만들 뿐, 메모리가 커지는 차수는 바꾸지 않는다. 정말 큰 문장(수백만 행)을 다루려면 엔진의 쓰기 모음부터 디스크로 흘려야 하는데, 그것은 이번 범위 밖이다. 검증 단계 벤치마크(8절)에서 행 수에 따른 시간과 메모리를 재어 기록만 한다.

### 1-2. 무엇을 모으나 (U4)

| 선택지 | 목록 한 칸 | 장점 | 단점 |
|---|---|---|---|
| A. 키만 | 엔진 키 | 가장 작음 | 2단계에서 `get`으로 다시 읽어야 함(트리를 한 번 더 내려감). 1단계에서 이미 디코딩한 행을 버림 |
| B. 키 + 옛 행 | 키, 옛 행 | 계산은 2단계에서 | SET 계산 오류가 2단계(쓰는 도중)에 남. 6절과 어긋남 |
| **C. 키 + 새 행** (UPDATE) / 키만 (DELETE) | 키, 새 행 | 1단계에서 SET 계산과 모든 검사를 끝내고, 2단계는 쓰기만 함 | 없음에 가까움 |

**추천 C.** "키"는 **엔진에서 읽어 온 키 그대로** 쓴다. 행의 기본 키 값으로 `row_key`를 다시 만들어도 같아야 하지만, 망가진 행(키와 행 안의 기본 키가 다름)이 있으면 엉뚱한 키를 지우고 원래 키는 남게 된다. 읽은 것을 지우는 편이 안전하다. 지금 `select`는 `scan`에서 받은 키를 버리므로(#32 리뷰), "범위를 훑어 거르기를 통과한 (키, 행)을 모으는" 함수 하나를 꺼내 SELECT·UPDATE·DELETE가 함께 쓴다.

## 2. 문법 (U1, U2)

```
update  := UPDATE 이름 SET 대입 ("," 대입)* [WHERE 식]
대입    := 이름 "=" 식
delete  := DELETE FROM 이름 [WHERE 식]
```

`식`은 0019 1절의 `식` 그대로다. 대입의 오른쪽도 `식`으로 읽고, 값 식(`Scalar`)인지는 계획 단계가 가른다(4절). 그래서 `SET a = b = 1`은 파싱은 되고 "참·거짓 식은 열에 넣을 수 없음" 타입 오류가 된다. 0019의 파서 깊이 제한(#32 후속 PR, 아직 main에 없음)이 들어오면 SET 식에도 저절로 걸린다.

예약어에 `UPDATE`, `SET`, `DELETE`를 더한다. 문장 첫 낱말이라 문법을 가르고, `SET`은 표 이름 뒤에서 열 이름과 헷갈리면 안 된다.

| 들어오는 것 | 처리 |
|---|---|
| `UPDATE t SET a = 1, b = a + 1 WHERE id = 3` | 지원 |
| `DELETE FROM t` / `UPDATE t SET a = 0` | U2에 따라 |
| `SET a = 1, a = 2` (같은 열 두 번) | 오류 `DuplicateColumn` (PostgreSQL과 같음. SQLite는 뒤의 것을 씀) |
| `UPDATE OR REPLACE`, `UPDATE ... FROM`, `RETURNING`, `DELETE ... LIMIT`, `ORDER BY`, `SET (a, b) = (1, 2)`, `SET a = DEFAULT`, `DELETE t`(FROM 없음) | "지원 안 함" (무엇인지 이름을 댐) |
| `TRUNCATE` | 첫 낱말이 모르는 문장 → 기존 "지원 안 함" |

### WHERE 없는 UPDATE/DELETE (U2)

| 선택지 | 장점 | 단점 |
|---|---|---|
| **A. 허용 (표 전체)** | SQL 표준, SQLite·PostgreSQL과 같음. 0019 W9(WHERE 없는 SELECT 허용)와 맞음. 모델 테스트가 단순 | 실수로 표를 비울 수 있음 |
| B. 막음 (MySQL `--safe-updates`처럼) | 실수 방지 | 표를 비우려면 `WHERE TRUE`… 인데 Oakdb엔 불리언이 없어 `WHERE id IS NOT NULL` 같은 꼼수가 필요. 표준과 다름 |

**추천 A.** 실수 방지는 DB 엔진이 아니라 클라이언트(CLI 확인창 등)의 일로 본다.

## 3. 기본 키 고치기 (U5, U6)

기본 키는 행이 B+Tree의 **어디에 있는지**를 정한다(엔진 키 = `[01][표 번호][인코딩한 기본 키]`, 0017). 그래서 기본 키를 고친다는 것은 "그 자리에서 값을 바꾸기"가 아니라 "**옛 자리에서 지우고 새 자리에 넣기**"다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 막음 (`SET` 대상이 기본 키면 "지원 안 함") | 단순. 할로윈 문제가 실제로는 안 생김 | 표준 SQL과 다름. 번호를 다시 매기려면 DELETE + INSERT를 손으로 해야 함 |
| **B. 허용, 지우고 넣기** | 표준과 같음. 1절의 A가 이미 할로윈 문제를 막으므로 추가 비용이 작음 | 중복 검사의 뜻을 정해야 함(아래) |

**추천 B.**

### 3-1. 중복 검사는 언제? (U6)

`id`가 1, 2, 3인 표에서 `UPDATE t SET id = id + 1`. 끝난 뒤의 표는 2, 3, 4라 중복이 없다. 그런데 **행마다 바로** 검사하면 1→2를 옮길 때 아직 안 옮긴 2가 있어서 오류다.

| 선택지 | `SET id = id + 1` (1, 2, 3) | 장점 | 단점 |
|---|---|---|---|
| A. 행마다 바로 | **오류** (순서에 따라 다름: 큰 키부터 옮기면 성공) | 구현이 INSERT와 같음 | 결과가 처리 순서에 달림. `SET id = id - 1`은 성공, `+ 1`은 실패 같은 이상한 비대칭 |
| **B. 문장이 끝난 상태 기준** | 성공 (2, 3, 4) | SQL 표준의 뜻(제약은 문장 끝에서 검사). 순서와 무관 | 검사 방법이 조금 다름(아래) |

참고로 SQLite·MySQL은 A라서 오류가 나고, PostgreSQL도 기본 설정에선 A이며 `DEFERRABLE` 제약일 때만 B로 동작한다. Oakdb는 제약이 기본 키 하나뿐이고 1단계에서 모든 새 행을 이미 들고 있으므로 B가 어렵지 않다.

**추천 B.** 규칙: 문장이 끝난 표 = (문장 전 표) − (고른 행의 옛 키) + (고른 행의 새 키). 새 키가 다음 중 하나와 같으면 `DuplicateKey`.

| 겹치는 상대 | 예 (`id` 1, 2, 3) | 결과 |
|---|---|---|
| 같은 문장의 다른 새 키 | `UPDATE t SET id = 0` (세 행이 모두 0) | 중복 오류 |
| 고르지 **않은** 행의 키 | `UPDATE t SET id = id + 1 WHERE id < 3` → 2→3이 남아 있는 3과 겹침 | 중복 오류 |
| 고른 행의 옛 키 (그 행도 옮겨 감) | `UPDATE t SET id = id + 1` | 성공 |
| 고른 행의 옛 키 (그 행은 키를 안 바꿈) | `{0, 5}`에서 `SET id = id * 0` → 0은 그대로, 5→0 | 중복 오류 |

검사 방법(설계 수준): 1단계 끝에 "옮겨 가는 옛 키" 집합과 "새 키" 집합을 만든다. 새 키마다 ① 새 키 집합 안에서 겹치지 않는지, ② 옮겨 가는 옛 키가 아니라면 `txn.get`으로 이미 있는지 본다. 트랜잭션은 자기 쓰기를 보므로(#35의 BEGIN 안에서 앞서 넣은 행까지) 같은 규칙이 그대로 맞다. 전부 통과해야 2단계로 간다.

2단계 순서: **키가 바뀌는 행의 옛 키를 모두 지운 뒤, 새 행을 모두 넣는다.** 키가 그대로인 행은 지우지 않고 같은 키에 덮어쓴다. 중복이 1단계에서 이미 걸러졌으므로 이 순서에서는 덮어써서 행을 잃는 일이 없다.

## 4. SET 식과 타입 (U7, U8)

### 4-1. SET 식은 옛 행을 본다 (U7)

| 선택지 | `UPDATE t SET a = b, b = a` (a=1, b=2) | 누가 |
|---|---|---|
| **A. 모든 SET 식이 옛 행을 봄** | a=2, b=1 (맞바꿈) | SQL 표준, SQLite, PostgreSQL |
| B. 왼쪽부터 고친 값을 봄 | a=2, b=2 | MySQL |

**추천 A.** 1단계가 "옛 행을 읽고 → 모든 SET 식을 옛 행으로 계산 → 새 행을 만든다"이므로 자연스럽게 A가 된다. Java로 치면 `Row next = new Row(old.b, old.a)`처럼 옛 객체에서 새 객체를 만드는 것이고, B는 `old.a = old.b; old.b = old.a;`처럼 제자리에서 고치는 것이다. WHERE도 옛 행으로 계산한다(고르기가 고치기보다 먼저).

### 4-2. SET 타입 검사는 행을 읽기 전에 (U8)

0019 W5와 같은 원칙이다. 열 타입과 리터럴 타입을 알면 SET 식의 타입이 행 없이 정해지므로, **계획 단계에서** 검사하고 하나라도 어긋나면 아무 행도 읽지 않는다(빈 표에서도 같은 오류).

| 경우 | 언제 | 오류 |
|---|---|---|
| 없는 열 (`SET nope = 1`, `SET a = nope`) | 계획 | `NoSuchColumn` |
| 같은 열 두 번 | 계획 | `DuplicateColumn` |
| 값 식의 타입 ≠ 열 타입 (`SET age = 'ten'`, `SET name = id + 1`) | 계획 | `TypeMismatch { column, expected, found }` (INSERT와 같은 모양) |
| 참·거짓 식 (`SET a = (b = 1)`) | 계획 | `Type` (불리언 타입이 없음, 0019 Q8) |
| 기본 키에 리터럴 NULL (`SET id = NULL`) | 계획 | `TypeMismatch { found: None }` (INSERT와 같음) |
| 기본 키 식이 **실행 중에** NULL (`SET id = other_col`, 그 행의 값이 NULL) | 1단계, 행마다 | 같은 `TypeMismatch { found: None }`. #34가 "제약 위반"으로 옮길 수 있음 |
| 넘침, 0으로 나누기 (`SET n = n * 2`) | 1단계, 행마다 | `Arithmetic` (0019 W11) |
| 새 행이 엔진의 값 길이 한도를 넘음 | 1단계 (인코딩해서 길이 확인) | 엔진과 같은 오류. 9절 Q4 |

계획 단계는 0019의 `planner.rs`에 "SET 목록을 열 번호와 `Scalar`로 바꾸는" 순수 함수 하나를 더한다. WHERE의 `plan()`은 그대로 쓴다.

## 5. 영향받은 행 수 (U9)

완료 기준 "영향받은 행 수를 돌려준다". 이미 INSERT가 쓰는 `Output::Affected(u64)`가 있고, 서버 프로토콜과 CLI(`UPDATE 3` 꼴로 찍음)도 이것을 안다. 바꿀 것은 "무엇을 세나"뿐이다.

| 선택지 | `UPDATE t SET a = 1` (3행 중 2행이 이미 a=1) | 누가 | 장점 | 단점 |
|---|---|---|---|---|
| **A. 고른 행 수 (matched)** | 3 | SQLite, PostgreSQL, 표준 | 뜻이 단순(WHERE가 고른 수). 모델로 확인하기 쉬움 | "실제로 바뀐 것"은 알 수 없음 |
| B. 실제로 값이 바뀐 행 수 (changed) | 1 | MySQL 기본값 | 바뀐 것만 알려 줌 | 값을 비교해야 함. 같은 값이면 쓰지 않을지(아래)까지 정해야 함 |

그리고 함께 정할 것: **값이 그대로인 행도 쓸까?**

| 선택지 | 장점 | 단점 |
|---|---|---|
| **가. 고른 행은 언제나 씀** | "고른 행 = 쓴 행 = 센 행"으로 셋이 같음. 충돌 판정(7절)이 사용자가 부탁한 행 그대로 | 쓰기 양이 조금 많음 |
| 나. 같으면 건너뜀 | 쓰기가 줄고 충돌이 줄어듦 | 같은 행을 동시에 고치던 트랜잭션과 충돌이 안 나는 경우가 생겨, 결과를 설명하기 어려워짐 |

**추천 A + 가.** DELETE는 지운 행 수 = 고른 행 수라 고민이 없다.

## 6. 문장의 원자성 (U10)

0017부터 문장 하나는 엔진 트랜잭션 하나다(자동 커밋). 문장이 오류로 끝나면 트랜잭션을 커밋하지 않고 버리므로, **세 번째 행에서 넘침 오류가 나도 앞의 두 행은 반영되지 않는다.** UPDATE/DELETE도 이 성질을 그대로 받는다. 즉 지금은 따로 할 일이 없다.

문제는 #35다. `BEGIN; INSERT ...; UPDATE ...(도중 오류); COMMIT`에서 UPDATE가 실패하면, **UPDATE만** 없던 일이 되고 앞의 INSERT는 살아 있어야 한다(SQLite·PostgreSQL과 같은 "문장 단위 원자성"). 그런데 트랜잭션은 BEGIN 전체의 것이라 버릴 수 없다.

| 선택지 | 하는 일 | 장점 | 단점 |
|---|---|---|---|
| A. 버리기에 맡김 | 지금처럼 | 할 일 없음 | #35에서 문장 단위 원자성이 깨짐. 그때 엔진에 세이브포인트가 필요 |
| **B. 쓰기 전에 모든 검사를 끝냄** | 1단계에서 SET 계산, 타입, 기본 키 NULL, 중복 키, 길이 한도를 모두 확인. 2단계는 쓰기만 | 2단계가 실패할 수 있는 것은 엔진 정지(`Stopped`) 같은 엔진 고장뿐 → 그때는 트랜잭션 전체가 어차피 못 씀. #35가 UPDATE/DELETE 때문에 세이브포인트를 만들 필요가 없음 | 1단계가 조금 복잡(3-1절의 집합 검사) |

**추천 B.** 1절의 A(모으고 고치기)와 1-2절의 C(새 행까지 1단계에서 계산)를 고르면 거의 저절로 따라온다. 지금의 INSERT는 행마다 검사하고 바로 쓰므로 같은 문제가 있는데, 그것은 #35에서 같은 방식(검사 먼저)으로 고치거나 엔진 세이브포인트를 만들지 정한다(9절 Q7).

## 7. 동시에 도는 트랜잭션과의 충돌 (U11)

엔진은 스냅샷 격리다(ADR 0006, 0016): 두 트랜잭션이 **같은 키를 쓰면** 나중에 커밋하는 쪽이 `Error::Conflict`로 실패한다. 읽기는 비교하지 않는다. UPDATE/DELETE에 옮기면:

| 상황 | 결과 | 이유 |
|---|---|---|
| A와 B가 동시에 `UPDATE t SET n = n + 1 WHERE id = 1` | 하나는 성공, 하나는 `Conflict` | 같은 키를 씀. **잃어버린 갱신(lost update)이 없다**: 둘 다 성공해서 +1만 남는 일은 없음 |
| A는 `DELETE ... WHERE id = 1`, B는 그 행을 UPDATE | 나중 커밋이 `Conflict` | delete도 쓰기 |
| A와 B가 같은 행을 둘 다 DELETE | 나중 커밋이 `Conflict` | 결과는 같아도 엔진은 키만 봄. 그대로 둠 |
| A가 `UPDATE ... WHERE age > 30`, 그사이 B가 age 40인 새 행을 INSERT하고 먼저 커밋 | 둘 다 성공. 새 행은 A가 고치지 않음 | A는 자기 스냅샷의 행만 봄(유령 행). 스냅샷 격리의 약속 그대로 |
| 쓰기 비틀림(write skew): 서로 상대가 읽는 행을 고침 | 둘 다 성공 | ADR 0006이 받아들인 것 |

U9의 "가"(고른 행은 언제나 씀)를 고르면, 고른 행을 남이 동시에 고쳤을 때 **언제나** 충돌이 난다. 결과를 설명하기 쉽다.

| 선택지 | 충돌한 자동 커밋 문장 | 장점 | 단점 |
|---|---|---|---|
| **A. 오류로 돌려줌** | `SqlError::Engine(Conflict)`, 서버는 기존 `CONFLICT` 코드 | 단순. #35 완료 기준 "충돌 오류가 SQL 오류로 전달된다"와 같은 길. 재시도 정책은 클라이언트가 앎 | 클라이언트가 재시도를 짜야 함 |
| B. 자동 커밋 문장만 실행기가 몇 번 다시 돌림 | 사용자는 거의 못 봄 | 편함 | 몇 번? 사이에 기다림? 명시적 트랜잭션에선 못 함(앞 문장을 다시 돌릴 수 없음) — 길이 둘로 갈림 |

**추천 A.** 오류의 종류 이름(`Conflict`를 `SqlError`의 독립 종류로 꺼낼지)은 #34/#35가 정한다.

## 8. 테스트 계획 (U12)

0019는 무작위 표와 무작위 WHERE를 "전부 읽고 거르는" 모델과 비교했다(`tests/where_model.rs`). 이번엔 모델에 UPDATE/DELETE를 더하고, **문장 여러 개를 이어** 돌려 표의 상태를 계속 비교한다.

| 테스트 | 무엇을 |
|---|---|
| 모델 비교 속성 테스트 (`tests/write_model.rs` 또는 기존 파일 확장) | 무작위 문장 열(INSERT / UPDATE / DELETE / SELECT). 모델은 `BTreeMap<기본 키, 행>`이고 UPDATE를 **집합 단위**로 적용(옛 표에서 모든 새 행을 계산 → 3-1절 규칙으로 중복 확인 → 한 번에 교체). 문장마다 ① 영향받은 행 수, ② 오류 종류, ③ `SELECT *` 전체가 모델과 같은지 본다. 오류가 나면 표가 **문장 전과 똑같아야** 한다(6절) |
| 오류 판정의 엄격함 | WHERE 계산 오류는 0019처럼 느슨(Oakdb는 범위 밖 행을 안 읽으므로 성공할 수도 있음). 그 경우 모델은 Oakdb의 표로 다시 맞춘다. WHERE에 오류가 없으면 고른 행이 정확히 정해지고, SET 식에는 AND/OR 같은 지름길이 없으므로 **SET의 넘침, 기본 키 NULL, 중복 키는 엄격히** 같아야 함 |
| 생성기 | 기본 키 열을 SET하는 경우를 자주(`id = id + 1`, `id = id - 1`, `id = 0`, `id = other`), 연속 키 표를 자주 만들어 3-1절 경계를 두드림 |
| `tests/sql.rs` 예제 | 3-1절 표 네 줄, `SET a = b, b = a`, `SET id = id + 1000 WHERE id >= 100`(할로윈), 빈 표에서 타입 오류, WHERE 없는 UPDATE/DELETE, 세 번째 행 넘침 → 표 그대로, 2절 "지원 안 함" 목록 |
| 동시성 | 스레드 여럿이 `UPDATE t SET n = n + 1 WHERE id = 1`을 충돌 시 재시도하며 N번 → 최종 n = N (잃어버린 갱신 없음) |
| 블라인드 테스터 (검증 단계) | 이 문서와 이슈만 보고 테스트를 씀(CLAUDE.md) |
| 벤치마크 (검증 단계) | 행 수(1만, 10만)를 늘리며 전체 UPDATE/DELETE의 시간과 최대 메모리. 1-1절 "두 배쯤" 예상을 확인. 성능 주장은 없으므로 A/B는 하지 않음 |
