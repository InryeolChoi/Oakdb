# 0001. 한 장짜리 저장: 설계

이슈 #13. Oakdb의 첫 기능이다. 데이터베이스를 열고, 트랜잭션 안에서 키-값을 넣고 읽고, 커밋한 뒤 닫았다 다시 열어도 데이터가 남는다. 이 단계는 일부러 작게 잡았다. 스레드 하나, 리프 페이지 한 장, 그리고 로그 없이 데이터 파일에 바로 쓴다. 나머지는 뒤 이슈들이 하나씩 채운다.

| 이번에 하지 않는 것 | 맡는 이슈 |
|---|---|
| 삭제, 지운 공간 재사용(페이지 정리) | #14 |
| 페이지가 차면 분할 | #15 |
| 페이지 체크섬 | #19 |
| 가짜 파일시스템과 정전 실험 | #20 |
| WAL, 그룹 커밋, 스냅샷 격리 | 이후 이슈 (ADR 0006, 0007) |

## 1. 엔진 API

스펙(#12)이 정한 모양 그대로다. 앞으로 거의 모든 테스트가 이 입구로 들어온다.

```rust
let db = Db::open("data/mydb")?;          // 없으면 디렉터리와 빈 DB를 만든다
let mut txn = db.begin();
txn.put(b"oak", b"tree")?;
assert_eq!(txn.get(b"oak")?, Some(b"tree".to_vec())); // 내가 쓴 것은 바로 보인다
txn.commit()?;                             // 디스크에 기록된 뒤에야 Ok
db.close()?;
```

- **쓰기는 커밋 전까지 트랜잭션 안의 개인 버퍼(`BTreeMap`)에만 있다.** ADR 0006의 "쓰기는 개인 버퍼에 모은다"를 처음부터 따른다. 그래서 커밋하지 않고 트랜잭션을 버리면(drop) 아무 일도 일어나지 않는다. 별도의 되돌리기 코드가 없다.
- **커밋은 페이지의 복사본에 쓰기를 모두 적용해 보고**, 다 들어가면 파일에 쓰고 `sync`한 뒤 메모리의 페이지와 바꾼다. 하나라도 안 들어가면 `PageFull` 오류를 내고 아무것도 바꾸지 않는다. 커밋은 "전부 아니면 전무"다.
- **`Db::open_with(fs, path)`** 로 파일시스템을 바꿔 끼울 수 있다. `Db::open`은 실제 파일시스템(`StdFs`)을 쓰는 지름길이다. #20의 가짜 파일시스템이 여기에 끼워진다.
- 오류: `KeyTooLarge`(키 > 512바이트), `PageFull`(임시, #15가 없앤다), `PageSizeMismatch`, `Corrupt`, `Io`. `#[non_exhaustive]`로 두어 나중에 충돌·엔진 정지 같은 종류를 더해도 사용자 코드가 깨지지 않는다.
- 엔진은 여러 스레드에서 쓸 수 있어야 하므로(스펙), 페이지를 `Mutex`로 감쌌다. 커밋은 잠금을 쥔 채로 쓰고 기록하므로 한 번에 하나씩 일어난다. ADR 0006의 "커밋 대기열 하나"의 가장 단순한 형태다.

## 2. 파일 배치

데이터베이스 하나 = 디렉터리 하나, 그 안의 `oakdb.data` 파일 하나. 파일은 4KB 페이지의 배열이다.

```
페이지 0  메타 슬롯 A
페이지 1  메타 슬롯 B  (지금은 A와 같은 내용)
페이지 2  루트 리프
```

메타 슬롯을 처음부터 두 개 둔 이유는 ADR 0007이 체크포인트 위치를 두 슬롯에 번갈아 쓰기로 했기 때문이다. 지금 자리를 잡아 두면 파일 형식을 나중에 덜 바꾼다. 연구 문서 0005가 짚었듯 페이지 0, 1이 메타이므로 "다음 페이지 번호 = 0"을 "없음"으로 써도 겹치지 않는다.

### 메타 페이지

```
offset  크기  필드
0..4    u32   checksum        CRC-32C 자리 (#19 전까지 0)
4..12   [u8]  magic           "oakdb\0\0\0"
12..16  u32   format_version  1
16..20  u32   page_size       4096
20..28  u64   root_page
28..36  u64   page_count
```

열 때 확인하는 순서가 중요하다. **magic → page_size → 나머지** 순서다. 체크섬은 "페이지 전체"에 대해 계산하는데, 페이지 크기를 모르면 어디까지가 페이지인지도 모른다. 그래서 페이지 크기는 체크섬을 보기 전에, 파일 맨 앞 몇 바이트만 읽어서 확인한다. 크기가 다르면 `PageSizeMismatch`로 거절한다.

### 리프 페이지 (SQLite 방식, ADR 0008)

장부 한 장을 떠올리면 된다. 맨 위에 머리말, 그 아래에 목차(슬롯 배열)를 위에서 아래로 적고, 실제 항목(셀)은 맨 아래부터 위로 채운다. 가운데 빈칸이 줄다가 두 쪽이 만나면 장이 꽉 찬 것이다.

```
0..40     머리 (연구 문서 0005의 40바이트 배치 그대로)
40..      슬롯 [offset u16, len u16] × cell_count   ← 키 순서, 앞에서부터
...       빈 공간
...4096   셀: key_len u16 | value_len u16 | key | value   ← 뒤에서부터
```

- 정렬된 자리에 끼워 넣을 때 **4바이트짜리 슬롯만 한 칸씩 민다.** 셀 자체는 옮기지 않는다. 키를 찾을 때는 슬롯을 이진 탐색한다.
- SQLite는 슬롯에 offset(2바이트)만 두지만, 연구 문서 0005의 권고대로 **길이도 함께 둔다.** 셀을 해석하기 전에 경계 검사를 할 수 있다.
- 같은 키를 다시 쓰면 옛 슬롯을 빼고 새 셀을 넣는다. 옛 셀이 차지하던 바이트는 `frag_bytes`에 더해 둔다.
- **새 셀이 가운데 빈칸에 안 들어가면 페이지를 정리(compact)한다.** 살아 있는 셀을 페이지 끝으로 빈틈없이 당겨 붙이면, 셀 사이에 흩어져 있던 조각이 가운데 빈칸으로 모인다. 서랍 속 물건을 한쪽으로 몰아 빈자리를 한데 모으는 것과 같다. 슬롯 순서는 그대로고 offset만 바뀐다. 빈칸 + 조각을 다 합쳐도 모자랄 때만 `PageFull`이다. (처음에는 이 정리를 #14로 미뤘는데, Merge 전 검증에서 덮어쓰기만으로 DB가 영구히 꽉 차는 것이 드러나 01번에서 넣었다. 회고 참고.)
- 모든 정수는 리틀 엔디언으로 고정한다.

### 읽을 때 검사

체크섬(#19) 전에도, 디스크에서 읽은 페이지가 앞뒤가 맞는지는 확인한다. 깨진 페이지가 엉뚱한 메모리를 읽게 만드는 일을 막기 위해서다.

- `kind`가 리프인가, `flags`가 0인가
- `free_start = 40 + 4 × cell_count`, `free_start ≤ free_end ≤ 4096`
- 모든 슬롯이 셀 영역 `[free_end, 4096)` 안에 있고, 셀 머리의 `4 + key_len + value_len`이 슬롯의 길이와 같은가
- 키가 오름차순인가

하나라도 틀리면 `Corrupt`다. 이 검사는 "구조가 말이 되는가"만 본다. 값 바이트가 바뀐 것은 잡지 못한다(실험 0001 참고).

## 3. 모든 파일 접근은 Fs 트레이트로

기존 `Fs` 트레이트에 **`create_dir_all`** 을 더했다. 지금까지는 파일 열기와 디렉터리 sync만 있었는데, "디렉터리가 없으면 만든다"를 하려면 엔진이 `std::fs`를 직접 부르거나 트레이트를 넓혀야 했다. 직접 부르면 가짜 파일시스템이 디렉터리 생성을 볼 수 없으므로 트레이트를 넓혔다.

새로 만든 디렉터리도 부모 디렉터리를 sync해야 정전 뒤에 남는다. 이 책임을 **`create_dir_all` 안에 넣었다.** 만든 디렉터리마다 부모를 sync한다. 엔진은 "어느 디렉터리를 새로 만들었는지" 알 필요가 없고, 데이터 파일을 만든 뒤 그 디렉터리만 sync하면 된다.

새 데이터베이스를 만드는 순서:

1. `create_dir_all(dir)` (만든 디렉터리는 내부에서 sync)
2. `open(dir/oakdb.data)`, 그 파일에 **잠금(`try_lock`)**, 크기가 0이면 새 DB
3. 메타 A, 메타 B, 빈 리프를 쓰고 `sync_data`
4. `sync_dir(dir)`: 새 파일의 디렉터리 항목을 디스크에 기록

테스트(`file_access_goes_through_the_given_file_system`)는 호출을 기록하는 `Fs`를 끼워 넣고, 엔진이 위 순서대로 트레이트만 거쳤는지 확인한다.

### 한 번에 한 곳에서만 열기

같은 디렉터리를 `Db` 두 개가 열면, 둘 다 자기 메모리의 페이지를 고쳐서 파일에 덮어쓴다. 나중에 쓴 쪽이 먼저 쓴 쪽의 커밋을 **소리 없이** 지운다. 그래서 열 때 데이터 파일에 배타적 잠금을 건다. 이미 잠겨 있으면 기다리지 않고 `Error::AlreadyOpen`을 돌려준다.

- 잠금은 `flock` 방식(Rust `File::try_lock`)이다. 잠금이 "열린 파일 하나"에 붙기 때문에, 다른 프로세스뿐 아니라 **같은 프로세스 안에서 두 번 여는 것도** 막는다. (`fcntl` 방식 잠금은 같은 프로세스 안에서는 막지 못한다.)
- 잠금은 파일이 닫히면 풀린다. `close`나 drop은 물론이고, 프로세스가 죽어도 운영체제가 풀어 준다. 그래서 "잠금 파일이 남아서 못 여는" 문제가 없다.
- 잠금도 파일 접근이라 `FsFile::try_lock`으로 트레이트를 거친다.

## 4. 알려진 한계 (의도적으로 미룬 것)

- **커밋이 데이터 파일의 페이지를 제자리에서 덮어쓴다.** 정전으로 페이지가 반쯤 쓰이면(torn page) 고칠 방법이 없다. 이 단계의 목표는 "닫았다 열어도 남는다"까지이고, 정전 안전성은 WAL(ADR 0007)과 가짜 파일시스템(#20)이 맡는다.
- **새 DB를 만드는 도중에 죽으면** 크기가 0이 아닌데 메타가 없는 파일이 남고, 다음에 열 때 `Corrupt`가 난다. 이것도 WAL·복구 단계에서 다룬다.
- **스냅샷 격리가 아니다.** 트랜잭션은 커밋된 최신 페이지를 읽는다. 스레드 하나 단계라서 아직 차이가 드러나지 않는다.
- **디스크 기록 실패 후 엔진 정지**(스펙)는 아직 없다. 실패하면 `Io` 오류만 돌려준다.
