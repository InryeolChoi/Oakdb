# 0026. 벤치마크: 동시 쓰기와 그룹 커밋 — 설계

이슈 #30 (스펙 #12의 사용자 이야기 51·52). ADR 0005가 Oakdb의 첫 번째 차별점으로 내건 것은 "서로 다른 행을 고치는 트랜잭션이 줄 서지 않는다"이고, 그 증거로 약속한 것이 **"쓰는 스레드 수를 늘릴 때 SQLite 대비 쓰기 처리량"** 그래프다. 지금까지 숫자는 실험 0015 하나뿐이다. 그것은 그룹 커밋 **전후의 Oakdb끼리** 비교였고, 티켓 17(#29)이 커밋 루프를 `commit_queue`로 옮기기 **전** 코드였다(설계 0024 Q9). 이번 티켓은 세 가지를 같은 자리에서 잰다. (1) 스레드 1~N에 따른 Oakdb 처리량 곡선, (2) 같은 조건의 SQLite 곡선, (3) 그룹 커밋을 켠 것과 끈 것. 그리고 측정 환경(OS, 디스크)을 함께 남긴다.

**비유: 놀이공원 롤러코스터 두 곳.** 롤러코스터 한 바퀴(sync, macOS에서 약 3ms)는 손님 수와 상관없이 시간이 같다. SQLite 놀이공원은 **1인승**이다. 줄이 아무리 길어도 한 바퀴에 한 명이다. Oakdb는 **다인승**(최대 128석)이고, 열차가 돌아오면 줄 선 사람을 다 태운다(그룹 커밋). 우리가 재려는 것은 "줄이 길어질수록(스레드가 많을수록) 시간당 몇 명이 타나"다. 공정하게 재려면 두 놀이공원의 **안전벨트 기준이 같아야** 한다. SQLite가 벨트를 대충 채우고(약한 sync) 빨리 출발하면 이긴 것처럼 보여도 의미가 없다.

Java·Spring으로 치면 JMH로 메서드 하나를 재는 것(지금의 criterion 벤치마크)이 아니라, `ExecutorService`에 스레드 N개를 띄워 실제 DB에 `@Transactional` 쓰기를 퍼붓고 TPS와 p99 응답 시간을 보는 **부하 시험**(Gatling, JMeter)에 가깝다. OS 수업으로 치면 "디스크 I/O 한 번이 비싸니 여러 요청을 모아 한 번에 처리한다"(엘리베이터 스케줄링, 버퍼 캐시의 지연 쓰기)가 실제로 몇 배를 버는지 숫자로 보는 일이다. ft_malloc에 빗대면 `mmap`을 할당마다 부르지 않고 큰 덩어리를 받아 나눠 쓰는 것이 얼마나 빠른지 재는 것과 같다.

## 1. 무엇을 재나 (Q1)

비유하면 롤러코스터에서 볼 숫자는 넷이다. **시간당 탑승객**(처리량), **한 사람이 줄 서서 내릴 때까지 걸린 시간**(지연), **한 바퀴에 몇 명 탔나**(묶음 크기), **몇 바퀴 돌았나**(sync 횟수).

| 지표 | 무엇 | 왜 필요한가 | 비용 |
|---|---|---|---|
| **처리량** (커밋/초) | 측정 구간 동안 `Ok`를 받은 커밋 수 ÷ 시간 | 이슈의 본 질문. 그래프의 세로축 | 없음 |
| **지연 p50·p99** | 트랜잭션 하나의 시작(`begin`)부터 성공 응답까지. 충돌·바쁨으로 다시 한 것도 포함 | 처리량만 보면 "많이 태웠지만 한 사람은 오래 기다렸다"를 놓친다. p99는 서버(#37·#39)의 응답 시간 약속과 이어진다 | 커밋마다 `Instant` 두 번(수십 ns) |
| **묶음 크기 분포** | 묶음이 1명, 2~3명, 4~7명 … 128명인 횟수 | 평균만 보면 "두 대의 버스를 번갈아 탄다"(실험 0015) 같은 모양이 안 보인다. `MAX_BATCH`에 닿는지 본다 | 엔진에 계수기 몇 개 (아래 표) |
| **sync 수** | `Stats::wal_syncs` (이미 있음) | "커밋 수 ÷ sync 수 = 한 sync에 몇 커밋"이 그룹 커밋의 직접 증거 | 없음 |
| (선택) sync에 쓴 시간 | 커밋 스레드가 sync에서 보낸 시간의 합 | Linux처럼 sync가 짧을 때 **sync가 아닌 무엇이** 상한을 만드는지(트리 복제? 잠금?) 가늠. ADR 0006의 "벤치마크로 병목이 확인되면 래치 크래빙"의 근거 | 묶음마다 `Instant` 두 번 |

**지연을 어디서 어디까지 재나.** 커밋 호출(`commit()`)만 재면 SQLite와 비교가 틀어진다. SQLite는 `BEGIN IMMEDIATE`에서 쓰기 잠금을 기다리므로 기다림이 **시작** 쪽에 있고, Oakdb는 **커밋** 쪽(줄 서기)에 있다. 그래서 둘 다 "트랜잭션을 시작해서 성공 답을 받을 때까지, 다시 한 것 포함"으로 잰다. 은행으로 치면 "창구에서 처리한 시간"이 아니라 "번호표 뽑고 나올 때까지"다.

**묶음 크기 분포를 어떻게 얻나.** 묶음은 커밋 스레드 안에서만 보인다.

| | A. 지금 있는 평균·최대만 | **B. `Stats`에 2의 거듭제곱 칸(1, 2~3, 4~7, …, 128) 계수기** | C. 기능 플래그로 묶음마다 기록 남기기 |
|---|---|---|---|
| 보이는 것 | 평균, 최대 | 모양(한 봉우리? 두 봉우리?) | 전부 |
| 엔진 변경 | 없음 | `Stats`에 배열 하나(이미 `#[non_exhaustive]`라 깨지지 않음), 묶음마다 원자 증가 한 번 | 기록 버퍼, 플래그 |
| 측정에 주는 영향 | 없음 | 무시할 만함 | 기록이 커지면 흔듦 |

**추천: 처리량 + 지연 p50·p99 + B(묶음 분포) + sync 수. sync 시간 합은 넣는다**(묶음마다 두 번이라 싸고, Linux 해석에 꼭 필요하다). 처리량이 주인공이고 나머지는 "왜 그 숫자가 나왔나"를 설명하는 조연이다.

## 2. 어떤 작업으로 재나 (Q2)

ADR 0005의 약속은 정확히 "**서로 다른 행**을 고치는 트랜잭션"이다. 그래서 본 작업은 겹치지 않는 키다. 같은 키를 두고 싸우면 Oakdb는 낙관적 방식(먼저 커밋한 쪽이 이김, 설계 0016)이라 진 쪽이 다시 해야 하고, SQLite는 처음부터 한 줄로 세우므로 다시 할 일이 없다. 이것은 **Oakdb가 불리한 곳**이고, 숨기지 않고 따로 남기는 것이 정직하다.

| 작업 | 내용 | 역할 |
|---|---|---|
| **W1. 겹치지 않는 쓰기** (본 작업) | 트랜잭션 하나 = 새 키 하나 `put`. 키는 스레드마다 다름. 값 100바이트 | 주장(H1·H2·H3)의 무대 |
| W2. 큰 값 | W1과 같되 값 4KB (페이지 하나를 넘어 overflow 페이지가 생김, 설계 0006) | 묶음이 커질 때 **바이트**가 늘어 sync가 길어지는지. 기록만 |
| W3. 뜨거운 키 | 키 16개 중 하나를 골라 읽고 +1 해서 쓰기(카운터). 충돌·바쁨이면 처음부터 다시 | Oakdb가 불리한 곳. 처리량과 **다시 한 비율**을 기록만. 주장 없음 |
| (안 함) 읽기 섞기 | 읽기는 sync가 없어 이 질문과 무관. 읽기가 안 막히는 것은 실험 0015 H4가 봤다 | — |
| (안 함) 트랜잭션당 여러 쓰기 | 커밋 수보다 sync 수가 중요한 질문이라 1개로 충분. 필요하면 회고 때 | — |

**키 모양.** 지금 `threads_tput`은 스레드마다 `[스레드, 순번]`으로 **오른쪽 끝에만** 붙인다. 실제 응용은 키가 흩어진다. 흩어지면 커밋마다 다른 잎 페이지를 고치고, 묶음 하나가 쓰는 페이지 수가 늘어난다(WAL 바이트 증가).

| | A. 순서대로 (지금) | **B. 시드 고정 난수 키 (16바이트)** |
|---|---|---|
| 현실성 | 로그·시계열 같은 덧붙이기 | 일반 기본키(UUID 등) |
| 묶음당 바이트 | 작음 (같은 잎을 여럿이 고침) | 큼 |
| SQLite 쪽 | 같은 키를 그대로 씀 | 같음 |

**추천: W1(난수 키 B) 본 작업 + W2·W3는 몇 점만 기록.** 시작 상태는 빈 DB가 아니라 **1만 행을 미리 넣은 DB**로 한다(트리가 두세 층이 되어야 현실적이다). 미리 넣기는 두 DB 모두 측정 전에, 같은 키로 한다.

## 3. 스레드 수 (Q3)

| | A. 1·2·4·8·16 (실험 0015와 같음) | **B. 1·2·4·8·16·32·64 + 128·256 두 점** | C. 1~256 촘촘히 |
|---|---|---|---|
| 보이는 것 | 이미 본 범위 | 곡선이 **어디서 꺾이나**. 서버(ADR 0010, 접속마다 스레드)에서 생길 수백 스레드. `MAX_BATCH`(128)에 닿는지 | 같지만 오래 걸림 |
| 시간 (세 설정 × 10라운드 × 3초) | 약 8분 | 약 15분 | 1시간 넘음 |

M3는 코어가 8개다. 하지만 이 작업에서 스레드는 대부분 **sync를 기다리며 잠들어** 있으므로 코어 수보다 많아도 된다. 꺾이는 점이 코어 수 근처인지 sync 근처인지가 오히려 볼거리다.

**추천: B.** 128·256은 `MAX_BATCH`를 보려는 점이라 Oakdb(묶음 켬)만 잰다. **`MAX_BATCH`는 이번에 바꾸지 않는다.** 256스레드에서 묶음이 128에 자주 닿고 처리량이 평평해지면, 값을 바꾸는 후속 이슈를 연다(바꾸는 것은 성능 주장이 되므로 따로 A/B가 필요하다).

## 4. 한 번의 측정을 얼마나, 어떻게 끊나 (Q4)

| | A. 스레드마다 커밋 n개 (지금 `threads_tput`) | **B. 정해진 시간 창** |
|---|---|---|
| 방법 | 모두 n개를 끝내면 멈춤 | 데우기 0.5초 → 3초 동안 센다 → 멈춤 신호. 창 안에서 응답받은 것만 센다 |
| 꼬리 문제 | 끝 무렵 일찍 끝난 스레드가 빠져 **묶음이 작아짐** → 처리량 과소평가. 스레드가 많을수록 심함 | 없음. 창 안에서는 모든 스레드가 계속 일함 |
| 스레드 수 바뀔 때 | 총량이 스레드 수에 비례해 실행 시간이 들쭉날쭉 | 늘 3.5초 |

## 5. "그룹 커밋 끔"을 어떻게 만드나 (Q5)

이슈는 "그룹 커밋 유무 비교"를 요구한다. 끔 = 좌석이 1개인 열차 = 티켓 15(커밋 스레드만 있던 때)와 같은 동작이다.

| | A. 옛 버전과 비교 (`fcb3ed2` 대 main, `ab_versions.py`) | **B. 기능 플래그 `bench-knobs`로 좌석 수를 정하는 숨은 열기 함수** | C. 공개 설정 `Options { max_batch }` |
|---|---|---|---|
| 비유 | 작년 놀이공원과 올해 놀이공원 비교 | 같은 놀이공원에서 좌석을 1개로 막아 보기 | 손님이 좌석 수를 고르게 함 |
| 같은 바이너리 | 아님. 그 사이 바뀐 것(`commit_queue`, SQL, 스냅샷 수정 등)이 섞임 | **같음**. 바뀐 것은 좌석 수 하나 | 같음 |
| SQLite와 한 그래프에 | 어려움 (다른 프로그램) | 쉬움 | 쉬움 |
| 엔진 변경 | 없음 | `planted-bugs`처럼 기본 꺼짐 기능 하나. 켜면 `Db::open_with_max_batch` 같은 함수 하나가 생김 | 공개 API. 그런데 좌석 1개를 원할 사용자는 없다 |
| 주의 | — | 워크스페이스에서 벤치마크 크레이트가 이 기능을 켜면 `cargo test --all`에서도 함께 켜진다(기능 합치기). 기본값이 128이라 동작은 같다 | 문서·테스트 부담 |

**추천: B.** 묶음 켬·끔을 같은 바이너리, 같은 DB 조건에서 번갈아 재야 비율을 믿을 수 있다. A는 실험 0015가 이미 했다. 좌석 1개로 열었을 때도 기존 정전 실험 하나(`group_commit.rs`의 무작위 정전)를 돌려 "끔"이 내구성을 깨지 않는지 확인한다(Q15).

## 6. SQLite를 어떻게 공정하게 세우나 (Q6)

가장 쉽게 틀리는 곳이다. **SQLite의 기본 설정은 macOS에서 정전 내구성이 Oakdb보다 약하다.** `PRAGMA fullfsync`의 기본값이 꺼져 있어서, macOS에서 SQLite는 `F_FULLFSYNC`가 아니라 보통 `fsync`를 부른다. 실험 0002에서 보듯 macOS `fsync`는 드라이브 캐시까지 비우지 않아 훨씬 빠르다. 이대로 비교하면 SQLite는 안전벨트를 안 맨 채 달리는 셈이다.

**고정할 설정 (두 OS 공통, 측정 전에 PRAGMA를 다시 읽어 기록):**

| 설정 | 값 | 왜 |
|---|---|---|
| `journal_mode` | `WAL` | Oakdb도 WAL. SQLite의 가장 빠른 내구 모드. 읽기가 쓰기를 안 막음 |
| `synchronous` | `FULL` | 커밋마다 WAL을 sync. `NORMAL`은 WAL 모드에서 정전 시 마지막 커밋을 잃을 수 있어 Oakdb 약속(응답한 커밋은 남음)과 다르다 |
| `fullfsync` / `checkpoint_fullfsync` | `ON` (macOS에서 의미 있음, Linux에서는 무시됨) | Oakdb의 `F_FULLFSYNC`와 같은 벨트 |
| 표 | `CREATE TABLE kv(k BLOB PRIMARY KEY, v BLOB) WITHOUT ROWID` | Oakdb와 같은 "키로 정렬된 B+Tree 하나". rowid 표는 인덱스가 하나 더 생겨 불리 |
| 문장 | 준비된 문장(prepared statement)을 연결마다 한 번 만들어 재사용 | SQL 해석 비용을 빼서 저장 엔진끼리 비교 |
| 페이지 크기 | 4096 (기본값과 같음, Oakdb와 같음) | ADR 0008 |
| 체크포인트 | 기본값 (`wal_autocheckpoint` 1000페이지) | Oakdb도 기본값(4MiB)으로 둔다. 둘 다 "평소 모습" |

**여러 스레드가 SQLite에 쓰는 방법:**

| | **S1. 스레드마다 연결 + `BEGIN IMMEDIATE` + `busy_timeout`** | S2. 연결 하나를 `Mutex`로 나눠 씀 | S3. S1을 기본 설정(약한 sync)으로 |
|---|---|---|---|
| 비유 | 손님마다 따로 줄에 섬. 자리가 없으면 잠깐 졸다가 다시 확인 | 놀이공원 입구에 경비원이 한 명씩 들여보냄 | 벨트 없이 탑승 |
| 현실성 | SQLite 문서가 권하는 보통 쓰임 | 응용이 직접 줄 세우는 흔한 방식 | 많은 사람이 모르고 쓰는 모습 |
| 성질 | 바쁨 처리기가 **1, 2, 5, 10, … ms씩 잠들며** 기다려서, 스레드가 많을수록 손해가 큼 | 잠들지 않고 바로 다음 차례. SQLite가 낼 수 있는 **최선**에 가까움 (≈ 1 ÷ sync 시간) | 빠르지만 내구성이 다름 |
| 비교 자격 | 있음 | 있음 | **없음**. 참고선으로만, 그래프에 "내구성 다름"이라고 표시 |

S1만 재면 "Oakdb가 이긴 건 SQLite가 졸아서"라는 반론을 막을 수 없다. S2는 그 반론에 대한 답이다. SQLite는 연결이 몇 개든 쓰기를 한 번에 하나만 하고, 커밋마다 sync를 따로 한다(연결 사이 그룹 커밋이 없다). 그러면 S2가 SQLite의 천장이다.

**추천: S1과 S2를 둘 다 본 그래프에 넣는다. S3는 1·16스레드 두 점만 참고로.** SQLite 버전은 Rust 크레이트 `rusqlite`의 `bundled` 기능으로 **두 OS에서 같은 버전**을 빌드하고, 버전 문자열(`sqlite_version()`)을 결과에 적는다. 시스템 SQLite(macOS 내장, Ubuntu `libsqlite3`)는 OS마다 버전과 빌드 옵션이 달라 쓰지 않는다.

## 8. sync를 OS별로 어떻게 다루나 (Q8)

Oakdb의 `full_sync`는 macOS에서 `F_FULLFSYNC`, Linux에서 `fdatasync`다(ADR 0003). 같은 "벨트"지만 걸리는 시간이 매우 다르다. 실험 0002 기준 macOS M3는 3~5ms, Linux CI는 그보다 훨씬 짧다. 열차 한 바퀴가 짧으면 그동안 줄이 덜 쌓여 묶음이 작고, 그룹 커밋의 이득도 작아진다.

| | **A. 각 OS의 진짜 sync 그대로, OS별로 따로 보고** | B. sync 없음(`none`)도 한 줄 | C. 가짜 지연 sync (예: 3ms 잠들기)로 OS를 맞춤 |
|---|---|---|---|
| 의미 | 그 기계에서 실제로 나오는 숫자 | "sync가 공짜면 엔진의 천장은 어디인가" | 엔진 비교는 깔끔하지만 **현실이 아님** |
| 내구성 | 같음 | 없음. 참고선 | 없음 |

**추천: A + B를 Oakdb에만 참고선으로.** B는 `ab_commit_sync.rs`의 `none` 파일 시스템을 재사용하며, "sync를 빼면 커밋 스레드가 초당 몇 개를 처리하나"를 보여 준다. 이 선이 낮다면 다음 병목은 sync가 아니라 엔진(트리 복제, 잠금)이다. C는 하지 않는다. **OS 사이의 숫자는 서로 비교하지 않는다**(디스크도, 기계도 다르다). 각 OS 안에서 "Oakdb ÷ SQLite", "켬 ÷ 끔" 비율만 말한다.

## 15. 검증 계획 (Q15)

| 단계 | 무엇 | 이번 티켓에서 볼 곳 |
|---|---|---|
| 코드 리뷰 (두 축) | Standards / Spec. PR의 기준점에서 | 측정이 공정한가(같은 키, 같은 시작 상태, PRAGMA 실제 적용), 충돌로 진 커밋을 처리량에 세지 않는가, 시간 창 밖 응답을 세지 않는가, Rust: 스레드 사이 공유(`Arc`·`Barrier`·멈춤 신호의 `Ordering`), SQLite 연결이 스레드를 넘지 않는가 |
| 눈 가린 테스터 | 이슈·이 설계·ADR만 보고 테스트를 씀 | 예: "좌석 1개면 `wal_syncs == commits`", "묶음 분포 칸의 합 = `batches`", "S1 설정이면 `PRAGMA synchronous`가 FULL로 읽힌다", "시간 창이 0이면 처리량 0, 오류 아님" |
| 장애 실험 | 새 실험이 크지 않다 | 좌석 1개 열기에서 기존 무작위 정전 실험을 돌려 "끔"도 응답한 커밋을 지키는지. 결과는 `docs/benchmarks/0010`의 한 절로 (따로 실험 번호를 쓰지 않음) |
| A/B 가설검정 + A/A | Q12의 H1~H3·R1 | 내 Mac 30라운드. Linux 방향은 `measure.yml` |
| 결과 게시 | 각 결과를 PR 댓글로 | 사용자가 결정하기 전에는 아무것도 고치지 않는다 |
