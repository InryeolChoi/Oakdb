# 0003. 첫 분할: 2층 트리 — 설계

이슈 #15. 리프가 가득 차면 둘로 나누고, 그 위에 목차 역할을 하는 내부 페이지를 만든다. 이제 데이터가 한 장보다 많아도 저장할 수 있다.

```
분할 전:  [리프: a b c d e f]          ← 꽉 참

분할 후:        [내부(루트): d]
                /           \
        [리프: a b c] → [리프: d e f]
```

## 사용자가 정한 것

| # | 질문 | 결정 |
|---|---|---|
| 1 | 큰 값 | overflow(#18) 전까지 **키+값 1006바이트** 제한 (`ValueTooLarge`) |
| 2 | 나누는 기준 | **바이트**가 반씩 되게 |
| 3 | 목차에 적는 키 | 오른쪽 리프의 **첫 키 그대로** |
| 4 | 페이지를 어디에 둘까 | **전부 메모리에** |
| 5 | 분할 중 정전 | 지금은 **깨질 수 있음을 인정**, #21·#22에서 고침 |

## 1. 크기 제한: 왜 1006바이트인가

한 장에 4개는 들어가도록 정했다. 페이지 헤더를 빼면 4056바이트가 남고, 항목 하나는 키와 값 말고도 슬롯 4바이트와 셀 헤더 4바이트를 더 쓴다.

```
4 × (8 + 키 + 값) ≤ 4056   →   키 + 값 ≤ 1006
```

**왜 이 제한이 필요한가.** 값이 3000바이트까지 된다면, 1500 + 3000 + 1500바이트짜리 셋은 어떻게 둘로 나눠도 한쪽이 4056을 넘는다. 셋으로 나눠야 하는데, 그 코드는 overflow 페이지(#18)가 들어오면 버리게 된다. 항목 하나가 페이지의 1/4 이하면 **둘로 나누기가 항상 성공한다.** 꽉 찬 리프에 항목 하나를 더해도 합이 4056 + 1014 이하이고, 반씩 나누면 한쪽이 많아야 약 3042바이트이기 때문이다.

SQLite도 페이지 안에 두는 크기를 제한하고, 넘치는 부분은 overflow 페이지로 보낸다. #18이 오면 이 오류가 "overflow로 보내기"로 바뀐다.

- 검사는 `Txn::put`에서 바로 한다. 키 길이 검사(`KeyTooLarge`)와 같은 자리다.
- 오류는 `ValueTooLarge { len, max }`이고, `max`는 1006에서 키 길이를 뺀 값이다. 키가 512바이트면 값은 494바이트까지 된다.
- 이 계산은 `page.rs`에 컴파일 시간 검사(`const _: () = assert!(...)`)로 묶어 두었다. 페이지 크기나 헤더가 바뀌면 빌드가 실패한다.

## 2. 내부 페이지 형식

리프와 **같은 배치**(헤더, 슬롯, 셀)를 쓰고, 셀의 "값" 자리에 자식 페이지 번호(u64, 8바이트)를 넣었다. 덕분에 탐색, 넣기, 정리 코드를 리프와 그대로 나눠 쓴다. SQLite의 내부 페이지와 같은 구조다.

| 헤더 필드 | 리프 | 내부 페이지 |
|---|---|---|
| `kind` (12) | 1 | 2 |
| `right_sibling` (24..32) | 오른쪽 옆 리프, 없으면 0 | 항상 0 |
| `rightmost_child` (32..40) | 항상 0 | 가장 오른쪽 자식 |

**목차 읽는 법.** 셀 `(K, 자식)`은 "K보다 작은 키는 이 자식에"라는 뜻이다. 앞 셀의 키 이상이라는 조건도 함께 붙는다. 마지막 키 이상은 `rightmost_child`로 간다. 구분 키와 **같은** 키는 오른쪽으로 간다. 구분 키가 오른쪽 리프의 첫 키이기 때문이다.

```
내부: [ (d, 2) ]  rightmost = 3
      d 미만 → 페이지 2,  d 이상 → 페이지 3
```

## 3. 분할 순서

리프 `L`에 넣으려다 `PageFull`이 나면:

1. `L`의 모든 항목과 새 항목을 키 순서로 모은다.
2. 왼쪽과 오른쪽 중 더 큰 쪽이 가장 작아지는 위치를 찾는다. 양쪽에 적어도 하나씩은 남긴다.
3. **왼쪽 절반은 `L`의 페이지 번호를 그대로 쓴다.** 그래야 `L` 앞의 리프가 가리키던 화살표를 고치지 않아도 된다. 오른쪽 절반은 파일 끝의 새 페이지 `R`에 둔다.
4. 옆 포인터: `R`은 `L`이 가리키던 곳을 가리키고, `L`은 `R`을 가리킨다.
5. 부모:
   - `L`이 루트였으면 새 내부 페이지를 만들어 새 루트로 삼는다. 셀은 `(R의 첫 키, L)` 하나이고, `rightmost`는 `R`이다.
   - 부모가 있으면 `L`을 가리키던 자리를 `R`로 바꾸고, 셀 `(R의 첫 키, L)`을 더한다. 원래 그 자리가 맡던 범위의 위쪽 절반은 이제 `R`에 있기 때문이다.
6. 부모에 자리가 없으면 `PageFull`을 낸다. 3층 트리는 #16에서 다룬다.

키가 작으면 루트 하나에 자식이 수백 개 들어간다. 키가 512바이트이면 자식이 8개뿐이라 약 20개 항목에서 `PageFull`이 난다. 테스트 `a_commit_that_overflows_the_root_fails_and_changes_nothing`이 이 경우다.

## 4. 메모리와 커밋

트리 전체를 메모리에 둔다(`Tree`). 페이지는 `Vec<Arc<Page>>`에 담는다.

- **커밋은 지금까지처럼 "복사본을 고치고 마지막에 바꿔 끼운다."** 트리를 복제해도 `Arc`의 참조 수만 늘어서 싸다. 페이지를 고칠 때 `Arc::make_mut`가 그 페이지만 복사한다(copy-on-write).
- 고친 페이지 번호는 `dirty`에 모아 두고, 커밋할 때 그 페이지만 쓴다.
- 쓰는 순서: **바뀐 페이지를 먼저 쓰고 sync한다. 페이지가 늘었으면 메타 페이지를 쓰고 한 번 더 sync한다.** 분할이 없는 커밋은 지금처럼 sync를 한 번만 한다.
- 다시 열 때는 모든 페이지를 읽고 트리 구조를 검사한다.

| 열 때 검사하는 것 | 막는 것 |
|---|---|
| 자식 번호가 파일 안에 있다 | 엉뚱한 곳 읽기 |
| 어떤 페이지도 두 번 닿지 않는다 | 무한 반복 (자식이 조상을 가리키는 경우) |
| 키가 부모가 정한 범위 안에 있다 | 있는 키를 못 찾기 |
| 모든 리프의 깊이가 같다 | 균형이 깨진 트리 |
| 리프들이 왼쪽부터 차례로 서로를 가리킨다 | 범위 조회(#17)가 빠뜨리거나 되돌아가기 |

## 5. 정전과 프로세스 중단: 알고도 두는 것

분할 커밋은 페이지 여러 장을 **제자리에 덮어쓴다.** 중간에 멈추면 깨진다(실험 0004).

- 분할하다 멈추면 `L`은 왼쪽 절반만 남았는데 메타는 여전히 옛 루트 `L`을 가리킨다. 오른쪽 절반의 키를 잃는다. 지금은 옆 포인터 검사가 이를 잡아내서 **DB가 열리지 않는다.**
- 리프 두 장을 고치는 커밋이 한 장만 쓰고 멈추면 **커밋이 절반만 반영된다.**

이 두 문제는 WAL(#22)이 "한 커밋의 페이지를 모두 로그에 쓴 뒤에야 성공"으로 고친다. 설계 결정 5에 따라 여기서는 따로 대비하지 않았다. 대신 메타를 마지막에 써서, 메타가 아직 쓰지 않은 페이지를 가리키는 일은 없게 했다.

## 6. 이번에 하지 않은 것

- 내부 페이지 분할(3층 이상): #16
- 빈 리프 합치기, 페이지 재사용: 페이지는 파일 끝에 붙이기만 한다. 다 지워서 빈 리프도 그대로 남는다.
- 분할 위치를 넣는 패턴에 맞추기: 키를 오름차순으로 넣으면 왼쪽 리프는 반만 찬 채로 남는다. SQLite는 오른쪽 끝에 넣을 때 치우치게 나눈다. 필요하면 벤치마크를 보고 나중에 정한다.
- 파일 형식 ADR: 내부 페이지 형식은 나중에 ADR 0009(#43)로 정리한다.
