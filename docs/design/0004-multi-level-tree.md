# 0004. 여러 층 트리와 정답 모델 비교 — 설계

이슈 #16. 03번에서는 루트가 차면 `PageFull`로 멈췄다. 이번에는 **내부 페이지도 나눠서** 트리가 몇 층이든 자라게 하고, **빈 리프를 빼서** 줄어들게 한다. 그리고 무작위 연산을 `BTreeMap`과 똑같이 적용해 답을 비교하는 테스트를 붙인다.

```
루트가 차면:     [루트: b d f h ...]          ← 꽉 참
                         ↓ 나누고 가운데 키 하나를 위로
                     [새 루트: f]
                     /          \
            [b d] (왼쪽)      [h ...] (오른쪽)   ← f는 양쪽 어디에도 없다
```

## 사용자가 정한 것

| # | 질문 | 결정 |
|---|---|---|
| 1 | 키를 지워 리프가 비면 | **빈 리프만 뺀다.** 옆 리프와 합치거나 빌려 오지는 않는다 |
| 2 | 리프용·목차용 메서드가 섞인 `Page` (03 리뷰 결정 6) | **`Page` 하나를 유지하고 정리만 한다.** 한쪽 전용 메서드는 debug 빌드에서 종류를 검사한다 |
| 3 | 더 이상 생기지 않는 `Error::PageFull` | **공개 오류 종류에서 뺀다** |

표준을 그대로 따른 것: 내부 페이지도 **바이트**가 반씩 되게 나누고(03 결정 2와 같음), 가운데 구분 키는 **부모로 올려 보낸다**(돛단배 책과 SQLite 모두 이렇게 한다).

## 1. 내부 페이지 분할

리프가 나뉘면 부모에 `(구분 키, 새 오른쪽 페이지)`를 더해야 한다. 부모에 자리가 없으면 부모도 나눈다. 이것이 위로 번져 루트까지 차면, 루트 위에 새 루트를 만들고 트리가 한 층 자란다.

```
부모의 목차:  키    k0   k1   k2        (셀 3개)
              자식  c0   c1   c2   c3   (c3은 rightmost)

c1이 L(=c1)과 R로 나뉘고 구분 키가 s이면:
              키    k0   s    k1   k2
              자식  c0   L    R    c2   c3
```

1. 셀 `(s, L)`을 넣는다. `s`는 `k0`와 `k1` 사이에 정렬되므로 1번 자리에 들어간다. 그다음 1번 자리 뒤의 자식(원래 `c1`)을 `R`로 바꾼다. 셀을 넣는 데 실패하면 페이지는 그대로다 (`Page::insert_split_child`).
2. 자리가 없으면 키와 자식을 모두 모은 다음 가운데 키 `m`을 고른다. 왼쪽은 `m` 앞의 키들과 그 자식들, 오른쪽은 `m` 뒤의 키들과 그 자식들을 가진다. **`m`은 어느 쪽에도 남지 않고 부모로 올라간다** (`Page::split_internal`).
3. 왼쪽은 원래 페이지 번호를 그대로 쓰고, 오른쪽은 파일 끝의 새 페이지에 둔다. 리프 분할과 같은 방식이다.
4. `m`의 위치는 "더 큰 쪽이 가장 작아지는" 곳이다. 양쪽에 키가 적어도 하나씩 남게 한다.

**리프와 다른 점.** 리프에서는 구분 키가 오른쪽 리프의 첫 키로 **남는다**. 키에는 값이 붙어 있기 때문이다. 내부 페이지의 키는 길 안내일 뿐이라서, 올려 보내면 아래에 남길 이유가 없다. 남기면 같은 키가 두 층에 있게 되고, `m`의 자식이 갈 자리도 없다.

**항상 둘로 나뉘는가.** 내부 셀 하나는 길어야 `4 + 4 + 512 + 8 = 528`바이트(슬롯, 셀 헤더, 키, 자식 번호)다. 페이지의 4056바이트에 이런 셀이 적어도 일곱 개 들어가므로, 넘친 페이지에는 키가 여덟 개 이상 있다. 가운데 키를 빼고 반씩 나누면 한쪽이 많아야 `(4056 + 528) / 2 + 528 ≈ 2820`바이트라 늘 들어간다. 이 근거는 03번에서 넣은 컴파일 시간 검사 `2 × 528 ≤ 4056`과 같다.

## 2. 빈 리프 빼기

delete로 리프가 비면(루트가 아니면) 트리에서 뺀다.

1. **바로 앞 리프의 옆 포인터를 건너뛰게 고친다.** 앞 리프는 내려온 길(`path`)에서 찾는다. "왼쪽 형제가 있는 가장 깊은 갈림길"까지 올라가서, 그 왼쪽 형제로 내려간 다음 계속 가장 오른쪽으로 내려가면 된다.
2. **부모에서 그 자식을 지운다.** 일반 칸이면 그 칸의 셀을 지운다. 그러면 다음 자식이 범위를 넘겨받는다. 맨 오른쪽 칸이면 마지막 셀의 자식을 `rightmost`로 올리고 그 셀을 지운다 (`Page::remove_child`).
3. 부모에 셀이 하나도 없었다면, 이 리프가 부모의 유일한 자식이었으므로 부모도 함께 비었다. 셀이 있는 조상을 만날 때까지 올라가서 거기서 지운다.
4. **루트에 셀이 없고 자식만 하나 남으면 그 자식이 새 루트가 된다.** 트리가 한 층 낮아진다. 반복한다.

```
지우기 전:        [루트: d]                 지운 뒤:   [리프: a b c]  ← 새 루트
                  /       \
         [리프: a b c] → [리프: (비었음)]
```

**자식이 하나뿐인 내부 페이지.** 루트가 아닌 내부 페이지는 셀이 0개(자식 하나)인 채로 남을 수 있다. 합치기를 하지 않기로 했기 때문이다(결정 1). 트리 검사는 이런 페이지를 받아들인다. 범위만 맞으면 찾기에는 문제가 없다. 03번의 깊이 상한(64)의 근거도 바뀌었다. 전에는 "내부 페이지는 자식이 적어도 둘"이라고 썼다. 이제는 "트리는 루트가 나뉠 때만 한 층 자라고, 페이지는 재사용하지 않으므로 64층이 되려면 2^64장이 넘게 필요하다"로 바꿨다.

**빠진 페이지는 파일에 남는다.** 재사용 목록(free list)이 없어서 파일은 줄지 않는다. 다시 넣으면 새 페이지가 파일 끝에 붙는다. 페이지 재사용은 나중 티켓이다.

## 3. `Page` 정리 (결정 2)

리프와 내부 페이지가 **같은 배치**를 쓰는 것은 03번의 의도적인 선택이다. 그래서 타입을 나누지 않고 다음만 했다.

| 종류 | 메서드 | 검사 |
|---|---|---|
| 리프 전용 | `get`, `split_leaf`, `right_sibling`, `set_right_sibling` | `debug_assert!(is_leaf)` |
| 내부 전용 | `child_index`, `child_at`, `set_child_at`, `insert_split_child`, `split_internal`, `remove_child` | `debug_assert!(!is_leaf)` |
| 공용 | `put`, `delete`, `key_at`, `cell_count` | — |

- `Page::put`은 이제 공개 오류 대신 crate 안에서만 쓰는 `Full`을 돌려준다. 페이지가 찼다는 것은 트리가 처리할 일이지 사용자에게 알릴 일이 아니다.
- `PageNo` 타입은 만들지 않았다(사용자 결정 2).

## 4. `Error::PageFull` 삭제 (결정 3)

이제 어떤 커밋도 공간 때문에 실패하지 않으므로 이 오류는 생길 수 없다. `Error`는 `#[non_exhaustive]`라서 종류를 **더하는** 것은 깨지지 않는 변경이지만, **빼는** 것은 이 이름을 쓰던 코드를 깨뜨린다. 아직 0.1이고 외부 사용자가 없어서 뺐다. `Tree::put`도 더 이상 `Result`를 돌려주지 않는다.

## 5. 정답 모델 비교 테스트

`tests/model.rs`. proptest가 무작위 연산 목록을 만들고, 엔진과 `BTreeMap`에 똑같이 적용한다. **엔진 API(`Db`, `Txn`)만** 쓴다.

| 연산 | 엔진 | 모델 |
|---|---|---|
| put / delete | `txn.put` / `txn.delete` | 커밋 전 사본에 반영 |
| 연속 delete | 키 최대 N개를 차례로 delete | 같음 |
| get | `txn.get` 결과를 바로 비교 | — |
| commit | `txn.commit` | 사본을 확정 |
| rollback | 트랜잭션 버림 | 사본 버림 |
| 다시 열기 | 트랜잭션 버리고 `close` → `open` | 사본 버림 |

끝나면 모든 키를 비교하고, 다시 열어서 한 번 더 비교한다.

- **키를 길게(200~512바이트) 했다.** 내부 페이지 하나에 키가 열 개 안팎만 들어가서, 키 몇백 개로도 4층이 된다. 키 길이가 제각각이라 페이지마다 차는 속도가 다르다.
- **테스트를 둘로 나눴다.** 처음 하나로 돌렸을 때 경로마다 몇 번 지나갔는지 세어 보니 **4층으로 자라기와 루트 낮아지기를 한 번도 지나가지 않았다.** 트랜잭션의 약 1/3이 롤백이나 다시 열기로 버려져 키가 쌓이지 않았기 때문이다.

| 테스트 | 연산 수 | 섞는 비율 | 64가지 경우에서 지나간 경로 |
|---|---|---|---|
| `a_growing_tree_…` | 최대 3000 | 주로 put, 트랜잭션의 80%가 커밋 | 3층 61번, **4층 44번** |
| `a_shrinking_tree_…` | 최대 1500 | 가끔 키 최대 1000개를 연속 delete | **루트 낮아지기 48번** |

- **실패한 사례는 `tests/model.proptest-regressions`에 저장된다.** proptest가 실패를 찾으면 가장 짧은 사례로 줄여서 이 파일에 기록하고, 다음부터는 이 사례를 먼저 돌린다. 이 파일은 저장소에 커밋한다. 아직 실제 실패가 없어서 파일도 없다.
- **테스트가 정말 버그를 잡는지 확인했다.** 버그를 하나씩 일부러 심어 봤다(변이 검사).

| 심은 버그 | 결과 |
|---|---|
| 빈 리프를 뺄 때 앞 리프의 옆 포인터를 안 고침 | 잡음 |
| 맨 오른쪽 자식을 뺄 때 `rightmost`를 안 바꿈 | 잡음 |
| 내부 분할에서 가운데 키를 오른쪽에도 남김 | 잡음 |
| 루트가 나뉠 때 새 루트가 엉뚱한 페이지를 가리킴 | 잡음 |
| 셀이 하나인 부모를 빈 부모로 취급 | 잡음 |

## 6. 커밋 중 멈추면 (알고도 두는 것)

03번과 같은 종류의 문제가 더 늘었다. 커밋이 페이지 여러 장을 제자리에 덮어쓰기 때문이다.

- 내부 분할이 번지면 한 커밋이 리프, 내부 페이지 여러 장, 새 루트, 메타를 쓴다.
- 빈 리프를 빼면 앞 리프와 부모를 고친다. 둘 중 하나만 써지고 멈추면 옆 포인터 사슬과 부모의 목차가 어긋나서, 다시 열 때 트리 검사가 열기를 거부한다.

둘 다 WAL(#22)이 고친다. 03번 결정 5를 그대로 따른다.

## 7. 이번에 하지 않은 것

- 반쯤 빈 페이지를 옆 페이지와 합치거나 빌려 오기 (결정 1)
- 빠진 페이지 재사용(free list), 파일 줄이기
- 오름차순 넣기의 치우친 분할: 순서대로 넣으면 페이지가 반만 찬 채로 남는다. 가장 큰 항목 1000개를 넣으면 오름차순이든 흩어진 순서든 **5층**이 된다.
- `PageNo` 타입 (결정 2)
- 파일 형식 ADR 0009(#43): 셀이 없는 내부 페이지를 허용한다는 점을 거기에 함께 적는다.
