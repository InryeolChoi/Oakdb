# 0030. async 서버와 스레드 방식 A/B 비교 — 설계

이슈 #66 (티켓 28), 부모 #12. 지금 서버는 **접속마다 스레드 하나**다(ADR 0010, 설계 0020). ADR 0010은 tokio를 버린 이유와 함께 "다음에 갈 길"을 적어 두었다: 접속의 읽기·쓰기는 tokio의 일꾼 스레드 풀이 맡고, 커밋은 커밋 스레드에 채널로 보내 답을 `.await`로 기다리는 **섞은 모양(하이브리드)**. 이번 티켓은 그 길을 실제로 만들어, 같은 벤치마크로 두 방식을 A/B 비교하고, 결과에 따라 ADR 0010을 유지하거나 새 ADR로 바꾼다. 통신 규칙(`docs/protocol.md`)과 CLI는 바꾸지 않는다.

> **구현 순서**: 이 설계는 티켓 25(#37, 설계 0025: 접속마다 `Session`, `0x47`·`0x48` 노는 시간 제한), 티켓 26(#38, 설계 0028: 정상 종료, 신호 스레드, 유예 시간), 티켓 27(#39, 네트워크 벤치마크의 부하 발생기)이 `main`에 들어간 뒤 구현한다. 지금 `main`에는 셋 다 없다. 27번 설계는 `docs/design/0029-network-benchmark.md`(브랜치 `ticket/27-network-benchmark`)이고, 그 결과 기록은 `docs/benchmarks/0013-network-clients.md`다. 이 문서는 **27번이 "클라이언트 N개를 띄워 처리량·지연·메모리를 재는 부하 발생기"를 만들고 28번이 그것을 그대로 쓴다**고 가정한다(Q9).
>
> **오류 코드 번호**: 설계 0028은 종료 코드를 `0x48`로 적었지만, 그 뒤 티켓 25 구현이 `0x48`을 "트랜잭션 밖에서 너무 오래 놀았음"(`code::IDLE`)에 썼다. 이 문서는 종료 중 코드를 **`0x49`** 로 부른다. 26번 구현이 다른 번호를 쓰면 그 번호를 따른다.

## 비유 1: 식당의 웨이터 (그림책 3-3의 이어지는 이야기)

그림책 3-3에서 물었던 두 질문의 답이 이번 티켓의 출발점이다. "손님 수백 명은 async나 멀티스레딩으로 하면 되지 않나?" → 지금 방식이 바로 멀티스레딩이다. "스레드 풀과 async를 섞을 수는 없나?" → tokio가 바로 그 모양이다. 이번에는 그 섞은 모양을 **진짜로 만들어서 재 본다.**

| 식당 | 스레드 방식 (지금, A) | async 방식 (이번, B) |
|---|---|---|
| 손님이 앉는다 | 손님마다 **전담 웨이터** 한 명(접속 스레드) | 웨이터 몇 명(CPU 코어 수만큼의 일꾼 스레드)이 홀 전체를 돈다 |
| 손님이 메뉴를 고민한다 | 전담 웨이터가 옆에 서서 기다린다(`read`에서 잠듦) | 웨이터는 다른 테이블로 간다. 손님이 손을 들면(소켓이 읽을 수 있게 되면) 누군가 온다 |
| 주문이 주방에 들어간다 | 웨이터가 주방 앞에서 요리가 나올 때까지 기다린다(커밋이 sync를 기다림) | 웨이터는 **번호표**만 받아 두고 홀로 돌아간다. 요리가 나오면 번호가 불린다(커밋 결과를 `await`) |
| 손님 1만 명 | 웨이터 1만 명. 탈의실(메모리)과 동선(문맥 전환)이 문제 | 웨이터는 그대로 몇 명. 대신 테이블마다 주문서(작은 상태 기계)만 늘어난다 |
| 주방(커밋 스레드) | 하나. 몰린 주문을 한 번에 굽는다(그룹 커밋) | **똑같이 하나.** 이번 티켓은 주방을 바꾸지 않는다 |

**핵심 질문 하나**: 웨이터가 "주방 앞에서 기다리는 것"을 멈추게 하려면 무엇을 바꿔야 하나? 그리고 코스 요리(`BEGIN … COMMIT`) 중인 손님의 주문서는 누가 들고 다니나? 이것이 Q2·Q3이다.

## 비유 2: Java로 보면

| Java 세계 | 무엇 | Oakdb에서 |
|---|---|---|
| **Spring MVC + Tomcat** (요청마다 스레드, 기본 풀 200) | 평범한 순서대로 코드. 막히면 그 스레드만 멈춤 | A: 접속마다 스레드 (상한 512) |
| **Spring WebFlux + Netty** (이벤트 루프 스레드 몇 개) | `Mono`/`Flux`. 이벤트 루프에서 막는 호출(JDBC)을 하면 **전체가 멈춘다.** 그래서 막는 일은 `Schedulers.boundedElastic()`으로 뺀다 | B: tokio 일꾼 스레드 몇 개. 막는 일은 `spawn_blocking`(= boundedElastic)으로 빼거나, 아예 막지 않게 만든다(Q3) |
| **`@Transactional` + `ThreadLocal`** | 트랜잭션(JDBC `Connection`)을 **현재 스레드에 묶는다** | A의 `Session<'db>`가 접속 스레드의 지역 변수인 것과 같다 |
| **WebFlux + R2DBC의 트랜잭션** | 스레드가 계속 바뀌므로 `ThreadLocal`을 못 쓴다. 트랜잭션을 **Reactor `Context`에 넣어 들고 다닌다** | B의 문제 그대로. 세션이 스레드에 묶이지 않고 작업(task)이 들고 다녀야 한다 → `'static`이 필요(Q2) |
| **Java 21 가상 스레드** (Loom) | 막는 코드를 그대로 쓰는데, 런타임이 수많은 가상 스레드를 적은 OS 스레드(carrier)에 얹는다 | Rust 표준에는 없다. async/await가 같은 일을 **컴파일러가 상태 기계로** 한다 |
| 가상 스레드의 **pinning** | `synchronized` 안에서 막으면 carrier 스레드가 통째로 붙잡혀 다른 가상 스레드가 못 돈다 | tokio 일꾼에서 커밋 sync를 그냥 기다리면 일꾼이 붙잡혀 그 일꾼의 다른 접속이 모두 멈춘다. 이슈의 완료 기준 "디스크 sync가 일꾼 스레드를 막지 않는다"가 이것을 막으라는 말이다 |

## 비유 3: ft_malloc으로 보는 "접속 하나의 메모리"

| ft_malloc | 스레드 방식 (A) | async 방식 (B) |
|---|---|---|
| `mmap`으로 큰 영역을 **예약**하고, 실제로 만진 페이지만 물리 메모리가 된다 | 접속 스레드마다 스택 256 KiB를 예약(`CONNECTION_STACK`). 실제로 만지는 건 수십 KiB. 커널의 스레드 구조체와 보호 페이지가 따로 붙는다 | 스택이 없다 |
| TINY 존에서 딱 필요한 크기만 `malloc` | — | 접속 하나 = 힙에 할당된 **future 하나**(컴파일러가 정한 정확한 크기, 대개 수 KiB) + 읽기·쓰기 버퍼 |
| `show_alloc_mem`으로 실제 사용량 확인 | RSS, 스레드 수 | RSS, 작업 수 |

가설 H1(Q10)이 이것을 잰다: "예약"이 아니라 "실제로 만진" 메모리로 비교해야 공정하다.

## Q1. 런타임: tokio / smol / 직접 짠 이벤트 루프

**쉽게 말하면**: 홀을 도는 웨이터들을 누가 관리할까. 이미 있는 인력 회사(tokio)를 쓸지, 작은 회사(smol)를 쓸지, 웨이터 교육부터 직접 할지(epoll/kqueue를 직접 부름).

| 선택지 | 하는 일 | 장점 | 단점 |
|---|---|---|---|
| **R1. tokio** (멀티스레드 런타임) | 일꾼 스레드 풀(코어 수) + 일 훔치기 + `spawn_blocking` 전용 풀 + 타이머 + `TcpListener`/`TcpStream` | 이슈와 ADR 0010이 이름으로 정한 것. Rust 서버의 사실상 표준(Netty 자리). 문서·예제가 가장 많아 블로그 독자도 익숙. `select!`, `timeout`, `watch`가 25·26번 기능을 짧게 만든다. 안에서 mio가 macOS kqueue / Linux epoll을 갈라 준다(ADR 0003) | 의존성이 커진다(필요한 기능만 켜서 줄임). 런타임 내부가 블랙박스 |
| R2. smol (async-executor + async-io) | 작은 실행기 + 블로킹 풀 | 코드가 작아 읽고 배우기 좋음 | 일꾼 풀·일 훔치기를 직접 조립. 생태계가 작고, 비교 결과를 "보통의 async Rust"로 일반화하기 어렵다 |
| R3. 직접 짠 이벤트 루프 (mio 또는 `libc` kqueue/epoll) | 소켓을 논블로킹으로 두고 루프 하나가 "읽을 수 있는 소켓"을 받아 상태 기계를 손으로 돌린다 | OS 바닥을 제일 깊이 배움. 의존성 0(libc만) | macOS·Linux 코드가 갈라진다(ADR 0003 부담). 접속마다 상태 기계를 손으로 짜야 해 25·26번 기능을 다시 구현하는 양이 가장 많다. 일꾼 여러 개로 나누는 것까지 하면 tokio를 다시 만드는 일. 측정 차이가 "async냐"가 아니라 "내 루프가 얼마나 잘 짜였나"가 된다 |

**추천 R1 tokio.** 비교하려는 것은 "접속마다 스레드 vs **보통의** async 서버"이므로 가장 보통인 것을 쓴다. 세부:

| 세부 | 추천 | 이유 |
|---|---|---|
| 켤 기능 | `rt-multi-thread`, `net`, `io-util`, `time`, `sync`. `signal`·`macros`·`fs`는 안 켬 | 신호는 26번의 신호 스레드를 그대로 씀(Q6). 파일은 엔진이 맡음 |
| 버전 | `tokio = { version = "1", default-features = false, features = [...] }`, `Cargo.lock`으로 고정 | 저장소의 다른 의존성과 같은 방식 |
| 일꾼 수 | 기본(코어 수). 측정 때 `--async-workers <n>` 옵션으로 기록·조절 가능하게 | A/B에서 "일꾼 몇 개였나"를 결과에 적어야 함 |
| 엔진에 tokio를 넣나 | **안 넣는다.** tokio는 서버 크레이트에만 | ADR 0005: 엔진은 서버 없이도 쓰는 라이브러리. Q3의 추천도 엔진을 런타임과 무관하게 둔다 |

## Q2. 열린 트랜잭션을 `.await` 너머로 들고 다니는 법 (`Session<'db>`의 수명)

**쉽게 말하면**: 코스 요리 손님의 주문서(`Session`)에는 "이 식당 장부(`Db`)를 잠깐 빌려 봄"이라는 도장이 찍혀 있다. 전담 웨이터 방식에서는 웨이터가 퇴근할 때까지 장부가 있다는 게 확실하니 문제가 없다. 그런데 홀을 도는 방식에서는 주문서가 웨이터 손을 떠나 **언제까지 살지 모르는 곳**(tokio 작업)에 놓인다. Rust 컴파일러는 "장부가 그때까지 있다는 걸 증명하라"고 한다(`'static`). Spring으로 치면 `ThreadLocal`에 두던 트랜잭션을 Reactor `Context`로 옮기는 일이다.

| 선택지 | 하는 일 | 장점 | 단점 |
|---|---|---|---|
| L1. `Db`를 `Box::leak`으로 `&'static Db`로 | 서버가 끝날 때까지 `Db`를 놓지 않는다고 선언 | 엔진·SQL 층 변경 0. 한 줄 | 26번의 정상 종료가 깨진다: `Arc::try_unwrap` → `Db::close()`(마지막 체크포인트, 파일 잠금 해제)를 할 수 없다. 테스트에서 서버를 여러 번 띄우면 `Db`가 쌓인다 |

| L4. 세션을 엔진 전용 스레드 K개에 나눠 보관 | `thread::scope` 안에서 엔진 스레드 K개가 `&Db`를 빌리고, 접속 번호로 나눠 세션을 `HashMap`에 둔다. async 작업은 "이 SQL 실행해 줘" 메시지만 보낸다 | 엔진·SQL 층 변경 0. 세션이 `.await`를 아예 건너지 않음 | 한 엔진 스레드가 커밋 sync를 기다리면 같은 칸의 다른 세션이 모두 멈춘다(줄 앞 막힘). 동시에 날아가는 커밋이 K개로 묶여 그룹 커밋의 묶음이 작아진다 → 처리량이 스레드 방식보다 나빠질 수 있다. Q3의 C2와 같은 문제 |
| L5. `unsafe`로 수명을 `'static`으로 속임 | | | 거절. `Db`가 먼저 사라지면 정의되지 않은 동작 |

## Q3. 커밋의 sync 기다림이 일꾼 스레드를 막지 않게 하는 법

**쉽게 말하면**: 웨이터가 주방 앞에 서서 요리를 기다리면, 그 웨이터가 맡은 다른 테이블이 전부 멈춘다(가상 스레드의 pinning). 막는 방법은 셋이다. ① 기다리는 일만 하는 **알바**를 따로 부른다(`spawn_blocking`). ② 주방 앞 대기 전담 직원 몇 명을 둔다(엔진 스레드 풀). ③ **번호표**를 받고 홀로 돌아간다(커밋을 기다릴 수 있는 표로 바꿈).

0절에서 봤듯 문장 실행에서 막는 곳은 **커밋 기다림 하나**다(트리는 메모리에 있음). 그래서 이 질문은 "커밋 기다림을 어떻게 하나"로 좁혀진다.

| 선택지 | 하는 일 | 장점 | 단점 |
|---|---|---|---|
| C1. 문장마다 `spawn_blocking` | 소유형 세션(Q2-L2)을 블로킹 풀에 넘겨 문장 하나를 통째로 실행하고 돌려받는다 | 엔진·SQL 층의 커밋 경로는 그대로. 코드 몇 줄 | 커밋이 sync를 기다리는 동안 **블로킹 풀의 스레드 하나**를 붙잡는다. tokio 블로킹 풀 상한은 기본 512 → 동시 커밋 512개면 결국 "커밋 중인 접속마다 스레드". 그 이상은 줄을 서서 그룹 커밋 묶음도 작아짐. A/B가 "스레드 vs 스레드를 감춘 async"가 됨 |
| C2. 엔진 전용 스레드 풀 + 채널 | 고정 K개 스레드가 요청을 받아 실행 | 스레드 수가 고정이라 예측 가능 | Q2-L4와 같은 줄 앞 막힘. 동시 커밋 ≤ K라 그룹 커밋이 덜 묶인다. 25번에서 버린 "고정 크기 스레드 풀"(ADR 0010) 문제가 되살아남 |
| **C3. 커밋을 "기다릴 수 있는 표"로 바꿈 (async 커밋 경로)** | 엔진: 커밋 요청을 대기열에 넣고 **번호표**(`CommitTicket`, 가칭)를 돌려준다. 번호표는 (가) 막고 기다리기(`wait()`)와 (나) 표준 `std::future::Future`로 `await`하기 둘 다 된다. 커밋 스레드는 지금처럼 답을 보내기만 함. SQL 층: 문장 실행을 "끝남(결과)" 또는 "커밋 대기 중(번호표 + 결과 만드는 법)"으로 돌려주는 함수를 더한다. 서버가 번호표를 `await` | sync 동안 **어떤 스레드도 붙잡지 않는다.** 이슈의 "커밋은 커밋 창구에 채널로 보내고 `await`" 그대로. 10,000 접속이 동시에 커밋해도 모두 커밋 대기열에 들어가 그룹 커밋이 크게 묶인다(스레드 방식과 같은 조건). 엔진은 여전히 tokio를 모른다(표준 `Future`만) | 엔진(번호표 + 깨우기)과 SQL 층(실행을 두 단계로) 둘 다 바뀐다. 기존 `Txn::commit()`은 `ticket.wait()`로 감싸 그대로 둠 |

**추천 C3.** 이것이 이번 티켓이 실제로 해 보려는 "섞은 모양"이다. C1은 만들기 쉽지만 측정 결과가 "스레드를 숨긴 것"이 되어 비교의 의미가 줄어든다. 세부:

| 세부 | 추천 | 이유 |
|---|---|---|
| 번호표 내부 | `Mutex<상태> + Condvar`(막고 기다리기용) + `Waker`(await용)를 한 구조에. 지금의 `mpsc::channel` 답장을 이것으로 바꿈 | 한 경로로 두 방식을 다 지원. loom 검증 대상(설계 0024 V8)에 번호표를 더함 |
| 기존 동기 API | `Txn::commit()` = `submit` + `wait()`. 이름·동작 그대로 | 스레드 서버, SQL 층 테스트, 엔진 벤치마크가 안 바뀜 |
| SQL 층 모양 | `Session::execute`는 그대로. 새 `Session::start(sql) -> Step`(가칭): `Step::Done(Result<Output>)` 또는 `Step::Committing { ticket, then }` | SQL 층은 기다리지 않고 "무엇을 기다려야 하는지"만 돌려준다. 런타임을 몰라도 됨 |
| 번호표를 버리면 | 커밋은 이미 대기열에 있으므로 **그대로 진행**된다. 결과만 아무도 못 봄 = 25번의 "COMMIT 직후 끊기면 결과 모름"과 같은 약속 | 접속 작업이 취소돼도 엔진 상태는 깨지지 않음 |
| C1을 세 번째 팔로 잴까 | **선택 사항.** C3가 SQL 층에서 너무 커지면 C1로 물러서는 비상구로 둔다. 시간이 되면 H1·H3만 C1로도 재서 "spawn_blocking이 왜 스레드와 비슷해지는지"를 블로그에 보인다 | 학습 가치는 있지만 필수는 아님 |

## Q6. 두 서버가 나눠 쓰는 것과 따로 만드는 것

**쉽게 말하면**: 식당 규칙(통신 규칙, 출입 명단, 좌석 수, 마감 절차)은 하나여야 한다. 웨이터가 일하는 방식만 다르다.

| 부분 | 나눠 씀 / 따로 | 어떻게 |
|---|---|---|
| 프레임 해석 (`Request::decode`, `Response::encode`) | 나눠 씀 | 이미 바이트만 다룸 |
| 프레임 읽기·쓰기 (`read_frame`/`write_frame`) | **규칙은 나눠 쓰고 I/O만 따로** | 머리말(길이 + 명령) 검사와 "길이는 주장일 뿐이라 미리 잡지 않는다"(설계 0020, `frame_memory` 테스트)를 I/O 없는 함수로 뽑고, 동기 읽기와 async 읽기가 그것을 부른다. 두 읽기 모두 `frame_memory` 테스트를 통과해야 함 |
| 허용 목록, 좌석(`Slot`), 거절 프레임, `closes()` | 나눠 씀 | 그대로 |
| 거절 뒤 linger(쓰기 닫고 1초 읽어 버리기) | 따로 | async 버전은 작업 하나 + `timeout`. 동시 linger 32개 상한도 같게 |
| 노는 시간 제한 `0x47`/`0x48` (25번) | 규칙은 나눠 씀, 구현은 따로 | "첫 바이트를 기다리는 시간만 센다", "트랜잭션 중이면 쓰기에도 시간 제한"은 같게. async는 `fill_buf` + 소켓 시간 제한 대신 `tokio::time::timeout` |
| 정상 종료 `0x49` (26번) | 신호 스레드·손잡이는 나눠 씀, 깨우는 법은 따로 | async는 손잡이가 `tokio::sync::watch`를 켜고, accept와 첫 바이트 기다리기가 `select!`로 그것을 함께 본다. **자기에게 접속하기(깨우기 손님)와 100 ms 틱이 필요 없다.** 유예 시간·종료 코드·마지막 `Db::close()`는 같음 |
| 패닉 → `0x7F` | 따로 | 접속 작업을 `catch_unwind`로 감싸는 작은 future(표준 라이브러리만)로 같은 동작 |
| 엔진 정지 로그 한 번, 접속·끊김 로그 | 나눠 씀 | 같은 문구 |
| 접속 상한·fd 올리기 | 나눠 씀 | 같은 `raise_fd_limit` |

**한 가지 함정을 박아 둔다 (취소 안전성)**: tokio의 `select!`는 이긴 쪽이 아닌 future를 **버린다.** 프레임을 읽는 도중의 future를 버리면 이미 읽은 바이트가 사라져 프레임 경계를 잃는다. 26번이 `read_exact` 대신 `fill_buf`를 쓴 이유와 같은 함정이다. 그래서 `select!`는 **다음 프레임의 첫 바이트를 기다릴 때만** 쓰고(버퍼에서 들여다보기만 하므로 버려도 잃는 게 없음), 첫 바이트가 온 뒤의 읽기와 문장 실행·커밋 기다림은 `select!` 밖에서 끝까지 한다. 26번의 "실행 중인 문장은 끝까지 + 응답"과 같은 약속이 된다.

**추천: 위 표대로.** 프레임 규칙을 I/O 없는 함수로 뽑는 리팩터링은 스레드 서버에 먼저 하고(동작 변화 없음, 기존 테스트가 지킴), 그 위에 async 서버를 얹는다.

**쉽게 말하면**: 한쪽 식당만 마감 정리를 안 하면 당연히 빠르다. 재기 전에 두 식당이 **같은 일을 하는지** 먼저 확인한다.

| 기능 | 스레드 (A) | async (B) 조건 |
|---|---|---|
| 인사, `0x40`–`0x44` | 있음 | 같은 코드, 같은 끊김 여부 |
| 접속 상한 512 + `0x45`, 허용 목록 `0x46`, linger | 있음 | 같은 순서(인사 전), 같은 linger, 같은 상한 |
| 접속별 세션, 끊기면 롤백 (25번) | 있음 | 같음 |
| `0x47` 트랜잭션 중 노는 시간 제한(기본 60초), `0x48` 밖(기본 끔), 쓰기 시간 제한 | 있음 | 같은 기본값, 같은 "첫 바이트만 센다" |
| 정상 종료 `0x49`, 유예 10초, 종료 코드 (26번) | 있음 | 같음 |
| 패닉 `0x7F` | 있음 | 같음 |
| `TCP_NODELAY` | 켬 | 켬 |
| listen 대기열 길이(backlog) | `std`의 값 | **같은 값으로 맞춤.** `std::net`과 tokio가 쓰는 기본값이 다를 수 있다(확인해서 기록). 다르면 접속이 몰릴 때의 결과가 섞인다 |

**추천: 위 표 전부를 측정 전 필수로.** 판정은 Q8의 "같은 테스트를 두 서버에" 하나로 한다. 하나라도 다르면 측정하지 않는다.

## Q8. 테스트

**쉽게 말하면**: 지금 있는 서버 테스트 전부를 두 식당에서 똑같이 돌린다. 그리고 "웨이터가 주방 앞에서 기다리지 않는다"를 직접 보이는 테스트를 하나 더한다.

| 무엇 | 어떻게 |
|---|---|
| 기존 종단 간 테스트 (`tests/server.rs`, `allow.rs`, `protocol.rs`, `frame_memory.rs`, `blind_server.rs`, 25·26번 테스트) | 테스트 도우미 `start(db, config)`가 `Io`를 받게 하고, 매크로로 테스트마다 `…_thread`, `…_async` 두 개를 만든다. 실패하면 이름으로 어느 쪽인지 바로 보인다 |
| CLI 테스트 (`tests/cli.rs`) | 실행 파일을 `--io thread`/`--io async`로 각각 띄움 |
| 300 접속 동시 테스트 | 두 서버 모두. CI 두 OS |
| **sync가 일꾼을 막지 않음** (이슈 완료 기준) | async 서버를 **일꾼 1개**로 띄우고 `SimFs::hold_syncs`로 커밋의 sync를 붙잡는다. 그 상태에서 다른 접속의 `SELECT`가 답을 받으면 통과. C1(문장마다 `spawn_blocking`)이나 막는 커밋이면 일꾼이 하나라서 실패한다 → 테스트가 진짜 일하는지도 보인다 |
| 소유형 트랜잭션 (Q2) | 엔진 단위 테스트: `Arc<Db>`를 쥔 트랜잭션이 다른 스레드로 옮겨 가 커밋, 버리면 롤백, 살아 있는 동안 `Arc::try_unwrap`이 실패 |
| 번호표 (Q3) | 단위 테스트: `wait()`과 `await` 둘 다 같은 결과, 번호표를 버려도 커밋은 진행. loom 모델에 번호표 추가 |
| 2,000 접속 | async 서버만, `#[ignore]`(손으로·검증 때 실행). 스레드 서버는 상한을 올려 같은 테스트를 시도하고 결과를 기록 |

**추천: 위 표대로.** 이력 검사기(설계 0024)로 "네트워크 너머 스냅샷 격리"를 두 서버 모두 돌리는 것은 검증(Q14)에서 한 번 한다.

## Q9. 부하 발생기와 실험 환경

**쉽게 말하면**: 손님 1만 명을 흉내 내려면 **손님 쪽도** 1만 명을 감당해야 한다. 손님 역할 프로그램이 손님마다 스레드를 쓰면, macOS에서는 4,096명에서 손님 쪽이 먼저 무너져 서버를 잰 게 아니게 된다.

| 세부 | 추천 | 이유 |
|---|---|---|
| 부하 발생기 | 27번의 것(설계 0029 Q12: `net_server`·`net_load`·`bench_network.py`)을 그대로 쓴다. 27번이 손님마다 스레드라면, 28번에서 **async 클라이언트 모드**를 더한다(같은 통신 규칙, 같은 측정 코드) | 이 머신의 `kern.num_taskthreads` = 4,096: 한 프로세스가 4,096개 넘게 스레드를 못 띄움 |
| 프로세스 분리 | 서버와 부하 발생기는 다른 프로세스. 같은 머신, 루프백 | 서버 RSS·CPU를 따로 재기 위해 |
| fd 한도 | 서버·부하 발생기 모두 `상한 + 64`. macOS는 `OPEN_MAX` 10,240이 천장(rlimit.rs) → **macOS에서 10,000이 최대**. `kern.maxfilesperproc`(이 머신 61,440)도 기록 | 1만을 넘기면 macOS에서는 측정 불가. 결과 문서에 적음 |
| 스레드 상한 | macOS 스레드 방식은 4,096 근처에서 **띄우지 못한다.** 이것 자체를 결과로 기록("A: 10,000 실패 — 스레드 상한") | 공정하게 실패 이유를 남김 |
| Linux 쪽 한도 | `ulimit -n`, `/proc/sys/kernel/threads-max`, `vm.max_map_count`(스레드마다 매핑 2개), `net.core.somaxconn` 기록 | 같은 숫자로 두 OS를 비교 |
| 임시 포트 | macOS 49152–65535(약 16,000개), Linux 기본 32768–60999(약 28,000개). 회차 사이에 TIME_WAIT가 빠질 때까지 기다리거나(Linux 60초) 수를 확인하고 시작 | 1만 접속을 여러 번 열고 닫으면 포트가 바닥남 |
| 두 OS | 주 측정은 macOS(사용자 머신). Linux는 CI 러너나 다른 머신에서 같은 스크립트를 돌려 **경향만** 비교 | CI 러너는 이웃 소음이 커서 절대값은 믿기 어려움 |
| 디스크 | 실제 디스크(`StdFs`). macOS `F_FULLFSYNC`는 수 ms라 쓰기 부하에서는 sync가 지배 | 그래서 Q10에 sync 없는 읽기 부하를 꼭 넣음 |
| 기록 | CPU 모델·코어 수, OS 버전, 전원 연결, 다른 앱 종료, 커밋 해시, 옵션 전부 | 27번과 같은 양식 (설계 0029 Q8, 벤치마크 0013) |

**추천: 위 표대로.** 27번 설계(`docs/design/0029-network-benchmark.md`)와 겹치는 부분은 그쪽을 따르고, 여기서는 "1만 접속을 만들 수 있는 손님 쪽"만 더한다.

## Q10. A/B 가설과 A/A 대조군

**쉽게 말하면**: "async가 빠르다"를 막연히 재지 않고, 먼저 **무엇이 얼마나 다를지 예측을 적고** 잰다. 그리고 같은 식당을 두 번 재서(A/A) 원래 얼마나 들쭉날쭉한지 먼저 안다. 그 들쭉날쭉함보다 큰 차이만 "차이"로 친다.

부하 네 가지:

| 부하 | 무엇 | 왜 |
|---|---|---|
| W1. 점 조회 | 각 손님이 `SELECT … WHERE id = ?`를 쉬지 않고 | sync가 없어 **접속 처리 방식 자체의 비용**이 가장 잘 보임 |
| W2. 자동 커밋 INSERT | 각 손님이 `INSERT`를 쉬지 않고 | sync·그룹 커밋이 지배. "수백 명일 때 진짜 병목은 커밋 창구"(그림책 3-3)를 확인 |
| W3. 노는 손님 | 손님 N명이 접속 후(일부는 `BEGIN` 후) 가만히 | 접속 하나의 **메모리** |
| W4. 섞기 + 큰 SELECT | W1 손님들 사이에 큰 표 전체 `SELECT` 손님 몇 명 | Q4(P1)의 위험 확인 |

손님 수: 1, 16, 64, 512, 2,000, 10,000 (10,000은 async만 가능할 수 있음, Q9).

가설(측정 전에 적어 두는 예측):

| # | 가설 | 지표 | 예측 |
|---|---|---|---|
| H1 | 노는 접속 하나의 메모리는 async가 훨씬 작다 | W3에서 (RSS − 접속 0일 때 RSS) / N | async가 스레드의 **1/4 이하** |
| H2 | 512명까지는 차이가 없다 | W1·W2 처리량, p50/p99 | 차이가 A/A 범위 안 |
| H3 | 2,000명 이상에서 스레드 방식의 꼬리 지연이 나빠진다 | W1 p99, p99.9 | 2,000에서 async p99가 A/A 범위 밖으로 낮음. 10,000에서 A는 macOS에서 못 띄움 |
| H4 | 쓰기 처리량은 커밋 창구가 정한다 | W2 처리량, 평균 묶음 크기(`Stats`) | 모든 N에서 차이가 A/A 범위 안(Q3-C3라서 동시 커밋 수가 같음) |
| H5 | 요청 하나의 CPU 비용은 async가 작다 | (user + sys CPU 시간) / 요청 수, 문맥 전환 수(`getrusage`) | 2,000 이상에서 async가 낮음 |
| H6 | 큰 SELECT가 작은 문장을 붙잡지 않는다 | W4의 작은 문장 p99 | async의 악화가 스레드보다 A/A 범위 이상 크지 않음. 크면 Q4를 P2로 |

A/A 대조와 반복:

| 세부 | 추천 |
|---|---|
| A/A | 스레드 vs 스레드, async vs async를 같은 방식으로 돌려 각 지표의 "원래 흔들림"을 잰다 |
| 반복 | 조합마다 5회, **A B B A B A A B …처럼 번갈아** 돌려 노트북 발열·배경 작업을 양쪽에 고르게 |
| 판정 | A/B 차이가 A/A에서 본 가장 큰 차이보다 클 때만 "차이". 5회의 중앙값으로 비교하고 최솟값·최댓값을 같이 적음 |
| 회차 길이 | 예열 5초 버리고 30초 측정(27번 양식이 있으면 그것: 설계 0029 Q7) |
| 기록 | `docs/benchmarks/`에 표 + 원자료(CSV) + 환경. 예측이 틀린 가설도 그대로 남김 |

**추천: 위 표대로.** 가설 H2·H4는 "차이가 없다"는 예측이다. 결과가 그대로 나오면 그것이 ADR 0010을 지키는 근거가 된다.

## Q11. async에서 접속 상한을 올릴까

**쉽게 말하면**: async 식당은 좌석을 더 놓을 수 있다. 그런데 이번 티켓에서 기본 좌석 수까지 바꾸면 비교가 섞인다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| **M1. 이번 티켓은 두 서버 모두 기본 512 그대로. 측정 때만 `--max-connections`로 같이 올림** | 비교가 공정. 기본값 변경은 결과를 본 뒤 ADR에서 | 당장 async의 장점을 기본값으로 못 누림 |
| M2. async만 기본 10,000 | async의 장점을 바로 씀 | macOS 천장(10,240)과 겹쳐 fd 여유 64가 빠듯. 노는 접속 1만 개는 slowloris 대비가 필요(`0x48` 기본 끔) |
| M3. 상한을 io별로 다르게 자동 계산 | | 옵션 의미가 io마다 달라져 사용자가 헷갈림 |

**추천 M1.** 기본값을 바꿀지는 Q12의 규칙에 따라 ADR에서 정한다. 바꾼다면 `0x48`(트랜잭션 밖 노는 시간 제한)의 기본값도 함께 다시 본다.

## Q12. 결과 뒤 어느 쪽을 기본으로 둘까 (결정 규칙, ADR)

**쉽게 말하면**: 결과를 보고 나서 규칙을 정하면 원하는 결론에 끼워 맞추기 쉽다. **지금 규칙을 정해 두고** 결과를 그 규칙에 넣는다.

| 선택지 | 규칙 |
|---|---|
| **D1. 미리 정한 규칙** | async가 기본이 되려면 셋 다: (가) Q7 동등성 100%, 두 OS CI 통과, (나) 512명 이하에서 W1·W2의 처리량·p99가 A/A 범위보다 나쁘지 않음, (다) 2,000명 이상에서 메모리(H1) 또는 p99(H3)가 A/A 범위보다 확실히 좋음. 하나라도 빠지면 스레드가 기본 |
| D2. v1 목표(수백 명)에서만 판단 | H2·H4만 봄. 거의 확실히 스레드 유지 |
| D3. 사용자가 결과를 보고 판단 | 규칙 없음 |

**추천 D1.** 결정 뒤 할 일:

| 결과 | ADR | 코드 |
|---|---|---|
| 스레드 유지 | ADR 0010에 "#66 결과: 유지" 절과 숫자, 다시 볼 조건 갱신 | async는 `--io async` 옵션으로 남김 |
| async로 바꿈 | 새 ADR 0011 "서버는 tokio 위의 async로 처리한다"가 0010을 대체(superseded). 소유형 트랜잭션·번호표(Q2·Q3)도 함께 기록 | 기본값 `async`, 스레드는 옵션으로 남김 |
| 진 쪽을 지울까 | **v1 끝까지는 남긴다.** 테스트가 둘 다 돌고 있어 유지 비용이 작고, 다음 서버 기능마다 A/B를 다시 해 볼 수 있다. v1 회고에서 다시 판단 | 서버 기능이 늘 때마다 두 번 구현하는 비용은 회고에 적음 |

## Q14. 검증 계획

| 무엇 | 어떻게 | 결과 |
|---|---|---|
| 두 축 코드 리뷰 (Standards / Spec) | PR의 기준점(base)부터. Rust 관점: 일꾼에서 막는 호출이 없나(`std::sync::Mutex`를 `.await` 너머로 쥐지 않나), `select!` 안의 future가 취소 안전한가(Q6 함정), 소유형 세션이 `Send`인가, 번호표의 깨우기가 잃어버리는 순간이 없나(loom), 스레드 서버의 동작이 리팩터링 뒤 그대로인가 | PR 댓글 |

| 이력 검사기 | 네트워크 너머로 덧붙이기 작업을 두 서버에서 돌려 스냅샷 격리 위반 0 | 검증 기록 |
