# 0006. 큰 값: overflow 페이지와 빈 페이지 목록 — 설계

이슈 #18. 지금까지는 키와 값을 합쳐 1006바이트가 넘으면 `ValueTooLarge`로 거절했다(03 결정 1). 이번에는 **페이지보다 큰 값**(예: 100KB)도 넣고 읽는다. 그리고 덮어쓰거나 지워서 **안 쓰게 된 페이지를 다시 쓸 수 있게** 목록으로 관리한다.

장부 한 장에 안 들어가는 긴 메모를 떠올리면 된다. 장부에는 "부록 37쪽부터, 총 100KB"라고만 적는다. 본문은 부록 페이지에 줄줄이 이어 쓴다.

```
리프 페이지                      overflow 페이지 (부록)
┌──────────────────┐           ┌──────┐   ┌──────┐   ┌──────┐
│ apple → "작은 값" │           │ p37  │ → │ p38  │ → │ p52  │ → 끝
│ photo → 📎 p37,  │ ────────▶ │ 4056B│   │ 4056B│   │ 나머지│
│        100KB     │           └──────┘   └──────┘   └──────┘
│ zebra → "작은 값" │
└──────────────────┘
```

## 사용자가 정한 것

| # | 질문 | 결정 |
|---|---|---|
| 1 | 큰 값을 어떻게 나눌까 | **기준(키+값 1006바이트)을 넘으면 값 전체를 부록으로.** 리프에는 "첫 부록 페이지, 길이" 12바이트만 남긴다 (InnoDB DYNAMIC 방식) |
| 2 | 빈 페이지를 어떻게 기억할까 | **빈 페이지 사슬.** 메타에 첫 빈 페이지를 적고, 빈 페이지마다 다음 빈 페이지를 적는다 |
| 3 | 무엇을 재사용할까 | **모든 빈 페이지.** overflow 페이지와, 04번에서 트리에서 빠진 빈 리프·내부 페이지 모두 |
| 4 | 값은 최대 몇 바이트까지 | **길이 필드(u32)의 한계, 약 4GiB** (`MAX_VALUE_LEN`). 지금은 DB 전체가 메모리에 있으니 실제 한계는 메모리다 |

버린 선택지와 이유:

| 결정 | 버린 것 | 이유 |
|---|---|---|
| 1 | 앞부분은 리프에, 나머지만 부록 (SQLite) | 엔진은 값을 늘 통째로 읽는다. 앞부분을 리프에 남겨도 얻는 게 없고, 값이 두 곳에 나뉘어 코드만 복잡해진다 |
| 1 | 별도 테이블 (PostgreSQL TOAST) | 테이블 개념이 아직 없다 |
| 2 | 목록 페이지 (SQLite 트렁크) | 지울 때 고쳐 쓰는 페이지는 적지만 코드와 테스트가 는다. 벤치마크로 비용을 보고 필요하면 올린다 |
| 2 | 파일에 적지 않고 열 때 계산 | 완료 조건("재사용할 수 있게 표시한다")과 어긋난다. 페이지를 그때그때 읽게 되면 열 때 파일 전체를 훑어야 한다 |
| 3 | overflow 페이지만 재사용 | 같은 목록에 트리 페이지를 넣는 것은 몇 줄이면 된다. 04번 회고에서 넘긴 "파일이 줄지 않고 늘기만 한다"도 함께 푼다 |
| 4 | 따로 상한 (예: 16MB) | ADR 0008의 "값은 크기 제한이 없다"를 바꿔야 하고, 한번 정하면 바꾸기 어려운 사용자 약속이 된다 |

## 1. 셀: "값이 밖에 있다"는 표시

리프 셀은 `key_len u16 | value_len u16 | key | value`다. 값이 부록에 있으면:

- `value` 자리에 **`OverflowRef`** 12바이트를 둔다: 첫 overflow 페이지 번호(u64) + 값 길이(u32).
- `value_len`의 **맨 위 비트(0x8000)** 를 켠다. 페이지 안의 값은 4096바이트보다 짧아서 이 비트는 원래 비어 있다.

연구 문서 0005는 페이지 머리의 `flags`에 이 비트 자리를 남겨 두자고 했다. 그런데 `flags`는 **페이지에 하나**뿐이라 어느 셀이 밖에 있는지 말할 수 없다. 그래서 셀마다 있는 `value_len`을 쓴다. 페이지 머리의 `flags`는 지금처럼 0이다.

**기준은 지금과 같다.** 키 + 값 ≤ 1006바이트(`MAX_ENTRY_LEN`)면 리프에, 넘으면 부록에 간다. 그래서 1006바이트 이하의 값은 06 전과 똑같이 저장된다. 부록을 가리키는 셀은 많아야 4 + 512 + 12 = 528바이트라 1006보다 작다. 03번의 "꽉 찬 리프는 늘 둘로 나뉜다" 보장은 그대로이고, 이 사실은 컴파일 시간 검사(`MAX_KEY_LEN + REF_LEN <= MAX_ENTRY_LEN`)로 묶었다.

읽을 때는 "부록이 필요 없는 값을 부록에 둔 셀"(`키 + 길이 ≤ 1006`)도 손상으로 본다. 같은 값은 늘 같은 모양으로 저장된다.

## 2. overflow 페이지와 빈 페이지

둘 다 다른 페이지와 같은 40바이트 머리를 쓰고, 종류(`kind`)만 다르다.

```text
offset  size  field
12      u8    kind       3 = 빈 페이지, 4 = overflow
14..16  u16   data_len   overflow만: 이 페이지에 담긴 값의 바이트 수
24..32  u64   next       사슬의 다음 페이지, 0 = 마지막
40..    값의 일부 (overflow), 나머지는 0
```

- overflow 페이지 한 장에 값 **4056바이트**(4096 − 40)가 들어간다. 마지막 장에는 나머지가 들어간다. 100KB는 26장이다.
- `next`는 리프의 옆 포인터와 같은 자리(24..32)다.
- 나머지 바이트는 **모두 0**이어야 하고, 읽을 때 확인한다. 그래서 빈 페이지에는 예전 내용이 하나도 남지 않는다. 실험 0003("지운 값은 파일에 남는다")의 절반이 해결된다. 리프 안에서 지운 작은 값은 여전히 정리 전까지 남는다.
- 새 값의 부록은 빈 페이지가 없으면 파일 끝에 **페이지 번호 순서로** 붙는다.

## 3. 빈 페이지 목록 (free list)

도서관의 "빈 책장 목록"이다. 새 책장이 필요하면 건물을 넓히기 전에 이 목록부터 본다.

- 메타 페이지에 **`free_head`(첫 빈 페이지, 0 = 없음)와 `free_count`(빈 페이지 수)** 를 더했다. 각 빈 페이지의 `next`가 다음 빈 페이지다.
- **빼기(`free`)**: 페이지를 빈 페이지로 바꿔 목록 **맨 앞**에 끼운다. 그 페이지는 커밋 때 0으로 덮어써진다.
- **얻기(`alloc`)**: 목록 맨 앞을 꺼내 쓴다. 목록이 비었을 때만 파일 끝에 붙인다.
- 트리의 새 페이지(리프 분할의 오른쪽 절반, 내부 분할의 오른쪽 절반, 새 루트)도 `alloc`을 쓴다.

**무엇이 빈 페이지가 되나**

| 언제 | 빠지는 페이지 |
|---|---|
| 부록에 있던 값을 덮어씀 | 옛 값의 부록 전부 (새 값이 바로 다시 쓸 수 있다) |
| 부록에 있던 값을 지움 | 그 부록 전부 |
| 리프가 비어 트리에서 빠짐 (04) | 그 리프, 함께 빈 부모들 |
| 루트가 자식 하나만 남아 물러남 (04) | 옛 루트 |

**비용.** 빈 페이지를 목록에 넣을 때마다 그 페이지를 한 장 고쳐 쓴다. 100KB 값을 지우면 26장을 쓴다. WAL이 페이지 전체 사본을 남기면(ADR 0007) 로그도 그만큼 커진다. 벤치마크 0006에서 재고, 문제가 되면 SQLite처럼 목록 페이지(트렁크)로 바꾼다.

## 4. 열 때 검사: 모든 페이지는 정확히 한 가지 용도

04번까지는 트리에서 빠진 페이지가 파일에 그냥 남아 있어도 괜찮았다. 이제는 그런 페이지가 있으면 **빈 페이지 목록이 하나를 잃어버린 것**이다. 그래서 열 때 모든 페이지가 다음 중 **정확히 한 곳**에서만 닿는지 확인한다.

1. 루트에서 내려가는 트리 (리프, 내부 페이지)
2. 리프 셀 하나의 부록 사슬
3. 빈 페이지 목록

| 새로 잡아내는 것 | 막는 일 |
|---|---|
| 어디에도 안 닿는 페이지 | 공간을 영영 잃음 |
| 두 곳에서 닿는 페이지 (사슬이 목록으로, 목록이 사슬로, 목록이 원을 그림) | 쓰고 있는 페이지를 새 값에 내줘서 데이터가 덮어써짐 |
| 사슬의 길이·장마다 담긴 양이 값 길이와 안 맞음 | 값이 잘리거나 엉뚱한 바이트가 붙음 |
| 트리가 overflow·빈 페이지를 자식으로 가리킴 | 엉뚱한 페이지를 목차로 해석 |
| 목록 길이가 메타의 `free_count`와 다름 | 목록이 중간에 끊김 |

## 5. 깊이 상한(64)의 근거를 다시 씀

03·04번에서는 "페이지를 재사용하지 않으니, 64층이 되려면 파일이 2^64장보다 커야 한다"가 근거였다. 재사용이 들어오면서 이 근거는 틀리게 됐다. 새 근거는 **페이지 수가 아니라 분할 횟수**다.

- 트리는 루트가 나뉠 때만 한 층 자라고, 지우기는 층을 늘리지 않는다.
- 내부 페이지가 나뉘면 양쪽 절반은 4056바이트 중 많아야 약 2820바이트를 쓴다. 그래서 가장 큰 구분 키(528바이트) 두 개가 더 들어갈 자리가 있고, 다시 나뉘려면 그 아래에서 분할이 적어도 두 번 일어나야 한다.
- 그래서 한 층 더 자라는 데는 앞 층의 두 배가 넘는 리프 분할이 들어간다. 64층에는 2^63번이 넘는 분할, 즉 그만큼의 커밋이 필요하다.

## 6. 형식 버전 2

메타 페이지에 두 칸이 늘어서 `format_version`을 2로 올렸다. 버전 1 파일은 열지 않는다. 버전 1 파일에는 04번 이후 "어디에도 안 닿는 페이지"가 있을 수 있어서, 그대로 받으면 4절 검사에 걸린다. 실제 사용자 파일이 없으니 변환기는 만들지 않았다.

## 7. API

| 무엇 | 전 | 후 |
|---|---|---|
| `Txn::put`의 값 | 키 + 값 ≤ 1006 | 값 ≤ `MAX_VALUE_LEN` (u32 최대, 약 4GiB) |
| `Error::ValueTooLarge { len, max }` | `max` = 1006 − 키 길이 | `max` = `MAX_VALUE_LEN` |
| `MAX_ENTRY_LEN` | 받을 수 있는 키 + 값의 최대 | 리프에 그대로 두는 키 + 값의 최대 |
| `MAX_VALUE_LEN` | 없음 | 새로 공개 |

- `Txn::get`은 긴 값을 부록에서 모을 때 트리 잠금을 쥐지 않는다. 트리의 `Arc`를 하나 복제한 다음 잠금을 놓고 읽는다. 100KB를 복사하는 동안 커밋이 기다리지 않는다. 처음 코드는 `let tree = Arc::clone(&tree);`로 **이름만 가리고 잠금은 쥔 채**였다. 리뷰 두 개가 함께 찾았고, 잠금을 블록 안에서만 쥐게 고쳤다(벤치마크 0006의 "잠금 확인"). 짧은 값은 예전처럼 잠금 안에서 바로 복사한다. 처음에는 짧은 값도 `Arc`를 복제했는데, A/B에서 `get/hit`가 14% 느려져서 고쳤다(벤치마크 0006).
- 넣기와 지우기는 리프를 한 번만 찾는다. 처음에는 "옛 값이 부록에 있었나"를 따로 한 번 더 찾았는데, 2층 트리 커밋이 13% 느려져서 `Page::put_value`·`Page::delete`가 옛 값의 부록 위치를 돌려주게 바꿨다.
- 범위 조회는 키가 범위 안일 때만 값을 모은다.

## 8. 조회 중에 커밋이 부록을 재사용하면

커밋은 옛 값의 부록을 빈 페이지로 돌리고, 같은 커밋 안에서 바로 새 값에 내줄 수 있다. 그래도 진행 중인 조회는 망가지지 않는다. 05번처럼 커밋은 **새 트리**에서 페이지를 바꿔 끼우고, 조회는 옛 트리의 `Arc<Page>`를 들고 있기 때문이다(`a_scan_started_before_a_commit_still_reads_the_long_value_it_saw`).

다만 이것은 **모든 페이지가 메모리에 있어서** 성립한다. 페이지 캐시가 들어와 디스크에서 그때그때 읽게 되면, 스냅샷이 아직 읽을 수 있는 페이지를 재사용하면 안 된다. 스냅샷 티켓(#25)과 페이지 캐시에서 "가장 오래된 스냅샷이 끝날 때까지 재사용 미루기"를 다룬다.

## 10. 정전과 프로세스 중단 (알고도 두는 것)

03번 결정 5를 그대로 따른다. 커밋은 지금도 페이지를 제자리에 덮어쓰고, WAL(#22)이 고친다. 실험 0005에서 긴 값을 쓰거나 지우는 커밋을 중간에 멈춰 봤더니 **9가지 모두 DB가 열리지 않았다.**

- 새 페이지에 쓰다 멈춤: 리프(페이지 2)가 번호 순서상 가장 먼저 써져서, 메타가 모르는 새 페이지를 가리킨다.
- 빈 페이지를 재사용하다 멈춤: 한 페이지가 "빈 페이지이자 부록"이 된다. 그대로 열면 쓰고 있는 페이지를 다시 내줄 수 있어서, 4절 검사가 막는다.
- 지우다 멈춤: 부록이 리프에서도 빈 페이지 목록에서도 빠진다. 공간만 잃는 경우지만 4절 검사가 열기를 거부한다. 이 대가를 받아들일지는 이번 PR에서 정한다.

조용히 틀린 값을 돌려준 경우는 없었다.

**변이 검사.** 버그 9개를 하나씩 심어 봤다.

| 심은 버그 | 잡은 테스트 |
|---|---|
| 덮어쓰거나 지운 값의 부록을 빈 페이지로 안 돌림 | 단위, overflow, 모델 |
| 부록을 거꾸로 씀 | 단위, overflow, 모델 |
| 빈 페이지를 꺼내고 개수를 안 줄임 | 단위, overflow, multi_level, 모델 |
| `Tree::put`이 덮어쓴 긴 값의 부록을 안 돌림 | **처음엔 아무것도 못 잡음** → 단위 테스트 추가 후 잡음 |
| 빈 리프를 빈 페이지 목록에 안 넣음 | 단위, multi_level, 모델 |
| 부록 첫 장만 읽음 | 단위, overflow, 모델 |
| 지운 값의 부록을 안 돌림 (`delete`만) | 단위, overflow, 모델 |
| 셀에 "밖에 있음" 표시를 안 씀 | 단위, overflow, 모델 |
| 리프에 두는 기준을 1바이트 어긋나게 | 단위, overflow, multi_level, 모델 |

네 번째는 커밋이 쓰는 키를 늘 먼저 지우기 때문에 공개 API로는 닿지 않는 코드였다. `Tree`를 직접 부르는 단위 테스트(`putting_over_a_long_value_frees_its_pages`)를 더해서 잡게 했다.
