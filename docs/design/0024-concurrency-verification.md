# 0024. 동시성 검증 — 설계

이슈 #29. 지금까지 동시성 티켓 넷이 규칙을 하나씩 쌓았다. 스냅샷 읽기(#25, 설계 0015)는 "트랜잭션은 시작 순간의 사진을 읽는다", 충돌 판정(#26, 설계 0016)은 "같은 키는 먼저 커밋한 쪽이 이긴다", 커밋 창구(#27, 설계 0018)는 "커밋은 한 직원이 한 줄로 처리한다", 그룹 커밋(#28, 설계 0021)은 "직원이 줄 선 전표를 한꺼번에 처리한다"이다. 각 티켓은 자기 규칙을 **손으로 짠 시나리오**로 시험했다. 카운터 증가, write skew 한 번, sync 문으로 만든 묶음 같은 것들이다. 이번 티켓은 두 가지를 더한다. 첫째, 스레드 여럿이 **무작위로** 트랜잭션을 돌리고 누가 무엇을 읽고 썼는지 전부 기록한 뒤, 그 기록이 스냅샷 격리 규칙을 어겼는지 기계가 찾는 **이력 검사기**다. 둘째, 커밋 창구의 작은 부품을 떼어 스레드가 번갈아 갈 수 있는 **모든 순서**를 돌려 보는 **loom 검증**이다. 그리고 검사기가 진짜로 일한다는 증거로, 엔진에 **일부러 버그를 심고** 검사기가 그것을 찾아내는지 본다.

**비유: 회계 감사.** 은행 창구 직원(커밋 스레드)이 잘 일하는지 확인하는 방법은 둘이다. 하나는 감사관이 하루치 **거래 장부 전체**를 받아 "입금된 돈이 사라졌나", "취소된 거래가 잔액에 들어갔나", "한 손님이 같은 계좌를 두 번 봤는데 금액이 달랐나"를 맞춰 보는 것이다(이력 검사기). 감사관은 창구 안을 들여다보지 않는다. 장부만 본다. 다른 하나는 **창구 절차서 한 장**을 놓고 "손님 둘이 동시에 오면? 직원이 퇴근하는 순간 손님이 오면?"을 경우의 수 하나도 빼지 않고 따져 보는 것이다(loom). 감사가 진짜 일하는지는 **모의 횡령**을 심어 보면 안다. 감사관이 그걸 못 찾으면 감사가 엉터리다(심은 버그).

Java로 치면 이력 검사기는 Jepsen이 하는 일이다. 여러 클라이언트가 DB를 두드리고, 각 요청의 시작·끝·결과를 기록하고, 끝나고 나서 기록만으로 격리 수준 위반을 찾는다. loom은 Java의 `jcstress`에 가깝다. 다만 jcstress는 "많이 돌려서 운 좋게 걸리길" 바라고, loom은 **가능한 순서를 체계적으로 전부** 돈다. OS 교과서로 치면 1장의 "두 스레드가 `count++`를 하면 결과가 1일 수도 있다"를 사람이 표로 그려 보는 대신 기계가 모든 끼어들기를 실행해 보는 것이다. 그림책 1-5, 1-6이 약속한 것이 바로 이 둘이다.

## 0. 지금 무엇이 시험되고 무엇이 비었나

| 이미 있는 것 | 어디 | 한계 |
|---|---|---|
| 카운터 증가 8스레드 × 50 | `blind_conflict.rs` | 키 하나, 연산 하나. "개수가 맞다"만 본다. 누가 무엇을 봤는지는 모른다 |
| write skew 허용 | `conflict.rs`, `blind_conflict.rs` | 손으로 짠 두 트랜잭션 한 번 |
| 스냅샷이 커밋을 안 본다 | `blind_snapshot.rs` | 한 스레드에서 순서를 정해 놓고 확인 |
| 무작위 단계 + 모델 | `conflict.rs`, `snapshot.rs`의 proptest | **한 스레드**가 여러 트랜잭션을 번갈아 연다. 진짜 동시 실행이 아니다 |
| sync 문으로 만든 묶음 | `group_commit.rs` | 묶음 구성을 테스트가 정한다. 결정적이지만 경우가 몇 개 |

비어 있는 것은 **진짜 여러 스레드가 마구 섞일 때** 규칙이 지켜지는지다. 그리고 커밋 루프 자체(받기 → 묶기 → 답하기 → 버리기)가 모든 순서에서 맞는지다. 지금 테스트는 "운 좋은 순서 몇 개"만 돌았다.

엔진 쪽 사실 몇 가지가 설계를 정한다.

- **쓰기는 커밋 전까지 트랜잭션 안에만 있다**(`Txn.writes`). 그래서 정상 엔진에서 "남이 아직 커밋 안 한 값 읽기"는 구조상 일어날 수 없다. 검사기는 그것이 **심은 버그로만** 나타난다는 것을 보여 준다.
- **트랜잭션 안에서는 마지막 쓰기만 남는다**(`BTreeMap`). 그래서 "중간값 읽기"도 정상 엔진에서는 불가능하다.
- **커밋 번호는 엔진 안에만 있다**(`begun_after`, `RecentWrites`). 밖에서는 누가 먼저 커밋했는지 알 수 없다. 이것이 V1에서 "덧붙이기 목록"을 고르는 이유다.
- **`SimFs`의 sync는 즉시 끝난다.** 그래서 `SimFs`로 무작위 작업을 돌리면 묶음이 거의 생기지 않는다. 묶음 관련 버그(V7의 4·5)를 잡으려면 묶음이 생기게 만들어야 한다(작은 질문 Q3).

## 1. 이력의 모양 (V1)

### 1.1 기록 단위

| | A. 사건 하나 = 한 줄 | **B. 트랜잭션 하나 = 한 줄** |
|---|---|---|
| 모양 | `begin`, `read`, `write`, `commit`을 각각 시각과 함께 | 스레드, 순번, 연산 목록, 결과, 시작·끝 시각 |
| 정보량 | 연산마다 시각이 있다 | 연산 사이 시각은 없다 |
| 쓰임 | 연산 하나하나가 언제 일어났는지가 중요한 격리 수준(읽기 커밋 등) | 스냅샷 격리는 **시작 순간 하나**로 읽기가 정해지므로 연산마다 시각이 필요 없다 |
| Elle와 | 다르다 | Elle의 "트랜잭션 = 마이크로 연산 목록"과 같은 모양 |

**추천: B.** 스냅샷 격리에서는 트랜잭션이 무엇을 읽는지가 `begin` 한 순간으로 정해진다. 그래서 연산마다 시각을 찍을 이유가 없고, 한 줄짜리 기록이 블로그에 그대로 보여 주기도 좋다. 한 줄은 이런 모양이다(형식은 구현 때 정한다).

```
t2#17 ok  begin=+1.203ms end=+1.977ms  r(k3)=[t0#4,t1#9]  a(k3,t2#17)  r(k5)=[]
```

`r`은 읽기, `a`는 덧붙이기, 범위 조회는 키마다 `r`을 여러 개 남긴 것과 같다. 결과는 셋이다. `ok`(커밋 성공), `fail`(`Conflict`: 확실히 안 들어감), `info`(`OutcomeUnknown`: 들어갔는지 모름). 읽기만 한 트랜잭션도 `commit`을 부르고 기록한다.

### 1.2 쓰는 값: 왜 "덧붙이기 목록"인가

검사기의 핵심 질문은 "이 읽기는 **누가 쓴 값**을 봤나"와 "키 하나에 쓰기들이 **어떤 순서**로 쌓였나"다. 엔진은 커밋 번호를 밖에 알려 주지 않는다.

| | A. 그냥 고유값 (레지스터) | **B. 덧붙이기 목록** | C. 엔진이 커밋 번호를 알려 줌 |
|---|---|---|---|
| 방법 | 쓰는 값마다 다른 이름 (`t2#17`) | 키를 읽고, 그 목록 끝에 내 이름을 붙여 쓴다. `[t0#4,t1#9]` → `[t0#4,t1#9,t2#17]` | 테스트용 훅이 `begin`의 스냅샷 번호와 커밋 번호를 돌려줌 |
| "누가 썼나" | 안다 (값 = 이름) | 안다 (목록의 마지막) | 안다 |
| "쓰기 순서" | **모른다.** 마지막 값만 보이니 중간 순서는 추측 | **안다.** 목록 자체가 그 키의 역사다 | 안다 |
| 엔진을 믿나 | 안 믿음 | 안 믿음 | **믿음.** 번호를 만드는 코드가 틀리면 검사기도 같이 틀릴 수 있다 |
| 잃어버린 업데이트 | 간접적으로만 | 바로 보임: 두 목록이 서로의 앞부분이 아니다 | 보임 |
| 값 크기 | 작다 | 키마다 쓴 횟수만큼 자란다 | 작다 |
| 나중에 서버(#37)에 | 그대로 | 그대로 (SQL 문자열 열로) | 쓸 수 없음 (네트워크 너머라) |

Elle 논문이 같은 이유로 덧붙이기(list-append)를 가장 강한 작업으로 꼽는다. 목록이 쓰기 순서를 **직접 드러내기** 때문이다. 레지스터는 순서를 추측해야 해서 놓치는 위반이 있다.

대가는 두 가지다. 값이 자란다: 키 8개에 트랜잭션 2000개, 그중 45%가 덧붙이기면 키 하나에 약 110개, 이름 하나 8바이트면 1KB 안팎이다. Oakdb는 넘침 페이지(설계 0006)가 있어 문제없고, 오히려 넘침 경로를 함께 시험한다. 그리고 덧붙이기는 **항상 먼저 읽는다**. 그래서 "읽지 않고 덮어쓰기"(blind write)는 이 작업에 없다. 하지만 충돌 판정은 쓰기 키만 보므로(설계 0016 B4) 읽기가 끼어도 판정은 똑같이 시험된다.

**추천: B, 고유 이름은 `t<스레드>#<순번>`.** C는 검사기를 단순하게 만들지만 감사관이 직원의 장부를 믿는 꼴이다. 작은 질문 Q1에서 C를 **보조 확인**으로만 쓸지 정한다.

| 같은 키 두 번 덧붙이기 | 허용 (트랜잭션 안) | 두 번째 덧붙이기가 첫 번째를 봐야 한다. 내 쓰기 보기(read-your-writes)와 중간값 시험 |
| 충돌이 나면 | 재시도하지 않고 `fail`로 기록, 다음 트랜잭션으로 | 재시도는 같은 계획을 두 번 기록해 이력을 복잡하게 한다. 충돌한 트랜잭션도 검사 대상이다(그 값이 어디서도 보이면 안 된다) |
| 한 번에 | 트랜잭션 약 2000개 (스레드 수와 무관하게 합계) | 그래프 검사가 1초 안에 끝나는 크기 |
| 디스크 | `SimFs` | 빠르고, 버그 3(sync 실패)에 필요한 고장 주입이 있다 |
| 끝나고 | 모든 키를 마지막으로 한 번 읽는다 | 최종 목록이 각 키의 "완성된 역사"다. 버그 3에서는 **다시 연 뒤** 읽는다 |

이렇게 하면 시나리오를 사람이 짜지 않아도 잃어버린 업데이트(두 스레드가 같은 키에 덧붙임), write skew(서로 다른 키를 읽고 다른 키에 덧붙임), 읽기 비틀림(두 키를 읽는 사이 남이 둘 다 고침)이 저절로 생긴다.

## 3. 무엇을 위반으로 잡나 (V3)

스냅샷 격리의 약속을 한 문장으로 하면: **각 트랜잭션은 시작 순간까지 커밋된 것을 통째로 보고, 자기가 쓴 키를 그 뒤 남이 먼저 커밋했으면 진다.** 어기는 모양마다 이름이 있다(Adya 1999, Elle 2020의 이름을 따른다).

| 이름 | 장부에서 보이는 모양 | 정상 Oakdb에서 | 잡나 |
|---|---|---|---|
| **잃어버린 업데이트** | 키 하나의 두 목록이 서로의 앞부분이 아니다. 예: `[t0#1,t1#3]`과 `[t0#1,t2#5]` | 충돌 판정이 막는다 | 잡는다 |
| **취소·미확정 데이터 읽기** (G1a) | 읽은 목록에 `fail` 트랜잭션의 이름이 있다. 또는 `info` 트랜잭션의 이름이 있는데 다시 연 뒤 최종 목록에 없다 | 쓰기가 개인 버퍼에 있어 불가능 | 잡는다 |
| **중간값 읽기** (G1b) | 남의 트랜잭션이 같은 키에 두 번 덧붙였는데, 첫 번째까지만 든 목록을 읽었다 | 마지막 쓰기만 남아 불가능 | 잡는다 |
| **커밋 순환** (G1c, G0) | 쓰기·읽기 화살표만으로 사이클 | 불가능 | 잡는다 |
| **반복 불가능한 읽기** | 한 트랜잭션이 같은 키를 두 번(읽기·조회) 읽었는데, 그 사이 자기가 안 썼는데 목록이 다르다 | 사진을 읽어 불가능 | 잡는다 |
| **읽기 비틀림 / 조각난 읽기** (G-single) | x에서는 U의 쓰기를 봤는데 같은 U가 쓴 y에서는 U 이전 목록을 봤다. 또는 x는 옛날, y는 새것 | 사진이 한 순간이라 불가능 | 잡는다 |
| **자기 커밋을 못 봄** | 같은 스레드에서 `ok`를 받은 다음 트랜잭션이 그 쓰기를 못 봤다. 또는 다른 스레드라도 `ok` 시각보다 늦게 `begin`했는데 못 봤다 | 답을 공개 뒤에 해서 불가능(설계 0021 G5) | 잡는다 (작은 질문 Q4) |
| **write skew** (G2) | rw 화살표 둘로 된 사이클. T1은 y를 읽고 x에 쓰고, T2는 x를 읽고 y에 씀 | **일어난다.** ADR 0006이 허용 | **잡지 않는다.** 몇 번 일어났는지만 센다 |

"묶음이 반만 보임"은 따로 줄을 두지 않는다. 같은 묶음의 트랜잭션 T1, T2가 서로 무관하면, T1만 보고 T2는 못 보는 것은 "T1과 T2 사이 순간의 사진"과 구별되지 않아 스냅샷 격리 위반이 아니다. 묶음을 한 번에 공개하는 것(설계 0021 G5)은 **구현을 단순하게 지키는 방법**이지 약속 자체가 아니다. 그 대신 공개를 잘못 나누면 칠판과 트리의 짝이 깨져 잃어버린 업데이트나 조각난 읽기로 나타난다. 검사기는 그 결과를 잡는다(V7 버그 5). **트랜잭션 하나**의 쓰기가 반만 보이는 것은 위의 "조각난 읽기"로 잡는다.

write skew를 "잡지 않음"이 왜 중요한가. 검사기가 write skew까지 위반이라고 하면 정상 엔진에서도 빨간불이 켜진다. 그러면 사람들은 빨간불을 무시하기 시작하고, 진짜 위반도 묻힌다. 그래서 정상 엔진 실행은 "위반 0, 허용된 write skew **1개 이상**"을 함께 단언한다. 0개면 작업이 write skew조차 못 만들 만큼 약하다는 뜻이다.

## 4. 어떻게 찾나 (V4)

| | A. 직접 검사만 | B. 의존 그래프 (Elle·Adya) | **C. A 다음 B** |
|---|---|---|---|
| 방법 | 값만 보고 표 3의 모양을 하나씩 확인 | 트랜잭션을 점, 의존을 화살표로 그리고 사이클을 찾아 분류 | 직접 검사로 쉬운 것을 읽기 좋은 말로, 그래프로 나머지를 |
| 잡는 것 | 잃어버린 업데이트, G1a·b, 반복 불가능한 읽기, 자기 커밋 못 봄 | 전부. 특히 여러 트랜잭션에 걸친 읽기 비틀림 | 전부 |
| 오류 메시지 | "k3: t1#3과 t2#5가 같은 앞부분 위에 덧붙였다" 처럼 바로 읽힘 | "사이클: t1#3 -ww-> t2#5 -rw-> t1#3" | 둘 다 |
| 코드 | 작다 | 중간 | 중간 |

### 4.1 그래프의 세 화살표

키마다 최종 목록이 쓰기 순서다. 그 위에서

| 화살표 | 뜻 | 비유 |
|---|---|---|
| **ww** T1 → T2 | T2가 T1 바로 뒤에 같은 키에 썼다 | 장부에서 T1 다음 줄이 T2 |
| **wr** T1 → T2 | T2가 T1이 쓴 판을 읽었다 | T2가 T1의 영수증을 봤다 |
| **rw** T1 → T2 | T1이 읽은 판 **바로 다음 판**을 T2가 썼다 (T1은 T2를 못 봤다) | T1이 본 장부는 T2가 쓰기 전 것 |

**분류 규칙 (Adya의 PL-SI, Elle의 SI 검사):**

- ww·wr만으로 된 사이클 → G0·G1c. 위반.
- rw가 **정확히 하나**인 사이클 → G-single(읽기 비틀림). 위반.
- rw가 **둘 이상이고 그중 둘이 이어져** 있는 사이클 → G2(write skew 꼴). 스냅샷 격리에서 허용.

왜 "rw 둘 이어짐"은 괜찮나. write skew는 T1이 T2를 못 보고 T2도 T1을 못 본 것이다. 둘 다 같은 옛 사진을 봤으니 서로에게 rw 화살표가 있다. 각자 다른 키를 썼으니 충돌 판정에 안 걸린다. 스냅샷 격리가 원래 이렇게 생겼다.

### 4.2 비용

| 단계 | 방법 | 비용 (트랜잭션 n, 화살표 e) |
|---|---|---|
| 목록에서 쓰기 순서 만들기 | 키마다 가장 긴 목록, 나머지는 앞부분인지 확인 | 읽기 수 × 목록 길이. 2000개에 수 ms |
| 화살표 만들기 | 위 표대로 | O(e). e는 n의 몇 배 |
| ww·wr 사이클 | 강하게 연결된 묶음(Tarjan) | O(n + e) |
| rw 하나 사이클 | rw 화살표 a → b마다, b에서 a로 ww·wr만 타고 가는 길이 있나(BFS) | O(rw 수 × (n + e)). 2000개에서 수십 ms~1초 |
| 사이클 예시 하나 뽑기 | BFS 경로 | 위반이 있을 때만 |

트랜잭션 2000개 한 번이 1초 안이면, 시드 20개를 몇십 초에 돈다.

**추천: C.** 직접 검사는 블로그에 그대로 옮길 수 있는 말로 위반을 설명하고, 그래프는 사람이 미처 이름 붙이지 못한 위반까지 잡는다. 둘이 같은 버그를 서로 다른 말로 잡으면 검사기 자체의 오류도 줄어든다.

## 7. 어떤 버그를 심나 (V7)

버그마다 "이 위반으로 잡혀야 한다"를 정한다. "뭔가 잡혔다"로는 부족하다. 엉뚱한 이유로 빨간불이 켜져도 통과해 버리기 때문이다.

| # | 심는 버그 | 엔진에서 바꾸는 곳 | 잡혀야 할 위반 | 필요한 조건 |
|---|---|---|---|---|
| 1 | **충돌 확인 건너뛰기** | `check_conflict`가 언제나 통과 | 잃어버린 업데이트 | 없음. 거의 매번 |
| 2 | **사진 대신 최신 트리 읽기** | `get`·`scan`이 `begin`의 `Arc` 대신 지금 트리를 잡음 | 반복 불가능한 읽기, 읽기 비틀림(G-single) | 없음 |
| 2b | 조회만 최신 트리 | `scan`만 | 같음 (범위 조회가 있어야 함) | 범위 조회 10% |
| 3 | **sync 전에 공개** | `publish`를 `write` 앞으로 | 미확정 데이터 읽기: 누가 읽은 이름이 `info`였고, 다시 연 뒤 없다 | **sync 실패가 있어야 보인다.** `SimFs::fail_once_after`로 sync를 한 번 실패시키고, 다시 연 뒤 최종 읽기. 실패가 없으면 이 버그는 장부에 흔적이 없다(맞는 결과다. 내구성 버그라서) |
| 4 | **묶음 안 충돌 건너뛰기** | `check_conflict`가 묶음 안 키 목록(`written`)을 안 봄 | 잃어버린 업데이트 | **묶음이 생겨야 한다.** 같은 키를 쓴 두 커밋이 한 묶음에 들어가야 한다(Q3) |
| 5 | **묶음 공개를 두 번에 나누기** | 키를 먼저 기록하고(번호가 오름) 잠금을 놓은 뒤, 다시 잠가서 트리를 바꿔 끼움 (구현 메모 1) | 잃어버린 업데이트: 그 틈에 `begin`한 트랜잭션은 **새 번호와 옛 트리**를 받아, 옛 값을 고쳐 써도 충돌하지 않는다 | 틈이 짧아 **확률적**. 틈을 50µs 쉬기로 넓힌다(Q5) |
| 6 | **공개 전에 답하기** | `Ok` 답을 `publish` 앞으로 | 자기 커밋을 못 봄 (같은 스레드의 다음 트랜잭션) | 확률적. 답 받은 스레드가 공개보다 먼저 `begin`해야 함 |

판정 기준은 실험 기록에 남긴다.

| 실행 | 단언 |
|---|---|
| 정상 엔진, 시드 N개 | 위반 0. write skew ≥ 1. 묶음이 생기는 설정에서는 `stats().largest_batch > 1` (묶음 경로를 정말 지났다) |
| 버그 1·3·4 | 시드 N개 **모두**에서 정해진 위반이 나온다 |
| 버그 2·2b·5·6 (확률적) | 시드 N개 중 **하나 이상**에서 정해진 위반. 발견률(N개 중 몇 개)을 기록 (구현 메모 3) |

## 8. loom으로 무엇을 검사하나 (V8)

loom은 `Mutex`, 채널, 원자 변수, 스레드를 자기 가짜로 바꾸고, 스레드가 번갈아 갈 수 있는 순서를 전부 실행한다. 순서 수가 폭발하므로(그림책 1-5의 계산기) 검사할 부품은 **작아야** 한다. 디스크 입출력은 loom이 다루지 못한다.

| | A. `Db` 전체를 loom 아래 | **B. 커밋 루프를 떼어 실제 코드가 그대로 쓰게** | C. 커밋 루프를 흉내 낸 별도 모델 |
|---|---|---|---|
| 범위 | `SimFs`·WAL·트리까지 | 요청 받기 → 묶기 → 처리기 호출 → 답하기, 그리고 `Drop`의 채널 닫기·`join` | 같은 범위를 테스트 안에서 다시 짬 |
| 순서 수 | 폭발 (`SimFs` 안의 `Mutex`, 페이지마다) | 작음 | 작음 |
| 실제 코드를 검사하나 | 예 | **예** | 아니다. 모델과 실제가 달라져도 모른다 |
| 바꿀 것 | 엔진 전체를 loom 호환으로 | `Committer::run`의 루프를 `commit_queue` 모듈로 뺌. 처리(충돌 확인·쓰기·공개)는 트레잇 뒤로 | 없음 |

B의 모양: `commit_queue`는 "요청 채널에서 첫 요청을 기다리고, 기다리지 않고 꺼낼 수 있는 커밋을 최대 `MAX_BATCH`까지 모으고, 정리 요청에서 끊고, 처리기에 묶음을 넘기고, 처리기가 답하지 않은 요청이 있으면 대신 답한다"만 안다. 실제 커밋 스레드는 지금의 `commit_batch`·`checkpoint`를 처리기로 넘긴다. loom 테스트는 디스크 없는 **가짜 처리기**를 넘긴다. 가짜 처리기는 메모리 지도에 쓰고, 공개는 진짜와 같은 `Mutex<Committed>` 모양으로 한다.

loom이 확인할 성질:

| 성질 | 모델 |
|---|---|
| 모든 요청이 **정확히 한 번** 답을 받는다 (안 받거나 두 번 받지 않음) | 손님 2~3명이 커밋 하나씩 보내고 답을 기다림 |
| `Ok`를 받은 손님이 바로 `begin`하면 자기 쓰기를 본다 | 손님이 답을 받은 뒤 `Committed`를 읽음 |
| 정리 요청은 앞서 보낸 커밋 **뒤에**, 뒤에 보낸 커밋 **앞에** 돈다 | 손님 하나는 커밋, 하나는 정리 |
| 처리기가 엔진을 멈추면 그 뒤 요청은 모두 `Stopped` | 가짜 처리기가 첫 묶음에서 실패 |
| `Db`를 버리면 커밋 스레드가 끝나고 `join`이 돌아온다 (교착 없음) | 모든 손님이 끝난 뒤 요청 채널을 닫음 |
| `received` 수가 오르면 그 요청은 이미 채널 안에 있다 (설계 0021 Q6) | 손님이 보내는 동안 테스트 스레드가 수를 읽음 |

**추천: B.** C가 가장 쉽지만, 모델과 실제가 갈라지면 loom이 맞다고 해도 실제 코드에 대해 아무 말도 하지 않는다. 그림책이 약속한 "커밋 대기열만 작게 떼어"가 B다.

## 9. `mpsc`와 `Mutex`를 어떻게 바꿔 끼우나 (V9)

| | **A. `sync` 모듈 하나로 다시 내보내기** | B. 처리기처럼 트레잇으로 추상화 | C. 매번 `#[cfg(loom)]` |
|---|---|---|---|
| 방법 | `crate::sync`가 `cfg(loom)`이면 `loom::sync::{Arc, Mutex, mpsc, atomic}`을, 아니면 `std::sync`의 같은 이름을 내보냄. 엔진은 `std::sync` 대신 이것만 씀 | 채널·잠금을 제네릭 매개변수로 | 쓰는 곳마다 둘 다 적음 |
| 쓰는 곳 | tokio, crossbeam 등이 쓰는 표준 요령 | 드묾 | 지저분 |
| 일반 빌드 비용 | 없음 (같은 std 타입) | 없음 | 없음 |

걸리는 것 셋. 구현 때 loom 문서로 확인하고, 안 되면 아래 대안으로 간다.

| 지금 쓰는 것 | loom에 | 대안 |
|---|---|---|
| `mpsc::channel` + `try_recv` (요청) | loom에 `mpsc`가 있다 | — |
| `mpsc::sync_channel(1)` (답) | 없을 수 있다 | 답 채널을 보통 `channel`로 (답은 한 번뿐이라 같은 동작) |
| `OnceLock` (멈춤 원인) | 없을 수 있다 | `Mutex<Option<…>>`. 멈춤 확인은 요청마다 한 번이라 비용 차이가 없다 |
| `catch_unwind` (`guarded`) | loom 아래에서도 동작은 하지만 모델에 넣지 않음 | 가짜 처리기는 패닉하지 않는다. 패닉 경로는 기존 테스트가 덮는다 |

`cfg(loom)`을 쓰면 Rust 1.80부터 "모르는 cfg" 경고가 난다. CI는 `clippy -D warnings`라서 `Cargo.toml`의 `[lints.rust]`에 `cfg(loom)`을 알려 줘야 한다.

**추천: A.** 엔진이 std를 직접 부르는 곳을 `crate::sync`로 바꾸는 기계적인 변경이고, 일반 빌드의 기계어는 그대로다.

## 10. 상태 공간과 CI (V10)

loom의 순서 수는 스레드 수와 각 스레드의 동기화 지점 수에 따라 폭발한다. 그래서 두 손잡이를 쓴다.

| 손잡이 | 뜻 |
|---|---|
| 스레드 수 | 손님 수 + 커밋 스레드. loom은 스레드 수에 작은 상한이 있다 |
| 끼어들기 상한 (`LOOM_MAX_PREEMPTIONS`) | 한 실행에서 "자발적이지 않은 전환"을 최대 몇 번까지 볼지. 동시성 버그 대부분은 끼어들기 2~3번 안에 드러난다는 연구 결과에 기댄다 |

| | A. 수동 실행만 | **B. 작은 모델은 CI, 큰 모델은 수동** | C. 큰 모델도 CI |
|---|---|---|---|
| CI 시간 | 0 | 1~2분 이하 목표 | 수십 분 가능 |
| 회귀를 잡나 | 누가 돌려야 | 커밋 루프를 고치면 바로 | 바로 |
| 모델 | — | 손님 2 + 커밋 스레드, 상한 2 / 손님 3, 상한 3은 `workflow_dispatch` | 둘 다 |

CI는 `ci.yml`에 단계 하나를 더한다. `RUSTFLAGS="--cfg loom"`으로 `cargo test -p oakdb --release --test loom_commit_queue`. loom은 느려서 `--release`로 돈다. `--cfg loom`은 빌드를 따로 하므로 캐시가 하나 더 생긴다. ADR 0003에 따라 두 OS 모두에서 돈다. 큰 모델은 `measure.yml`처럼 수동 워크플로로 두고, 결과는 실험 기록으로 옮긴다.

**추천: B.** 작은 모델에서 시간이 2분을 넘으면 상한을 줄이고 그 사실을 실험 기록에 남긴다.

## 구현 메모 (#29 구현)

결정은 그대로이고, 만들면서 바뀐 것만 적는다.

1. **버그 5의 순서를 뒤집었다.** 설계 때 적은 "트리 먼저, 키 기록 나중"은 위험하지 않았다. 그 틈에 시작한 트랜잭션은 새 트리와 옛 번호를 받는데, 뒤이은 키 기록이 더 큰 번호를 매기므로 같은 키를 쓰면 **괜히 충돌할 뿐** 값을 잃지 않는다. 값을 잃는 쪽은 "키 기록(번호 올림) 먼저, 트리 나중"이다. 새 번호와 옛 트리를 받은 트랜잭션은 옛 값을 고쳐 쓰는데도 충돌하지 않는다. 설계 0021 G2의 A안(sync 전에 칠판 번호를 올림)과 같은 구멍이다.
2. **요청 채널을 손으로 짠 대기열로 바꿨다(V9).** loom의 `mpsc`는 보내는 쪽이 모두 사라져도 받는 쪽을 깨우지 않는다. `Db`를 버리면 커밋 스레드가 `recv()`에서 영원히 기다리는 것으로 보여, loom이 교착이라고 멈춘다. 그래서 `commit_queue::Queue`(잠금 + 조건 변수 + 닫힘 표시)를 만들어 실제 엔진과 loom 모델이 함께 쓴다. 답 채널은 그대로 `mpsc::channel`이다(`sync_channel(1)`에서 바꿈. 답은 한 번뿐이라 같다).
3. **"최신 트리 읽기"(버그 2·2b)는 확률적이었다.** 트랜잭션 한 개가 수 µs면 그 사이에 커밋이 끼어들 일이 드물다. 작업 생성기의 단계 절반 뒤에 0~50µs 쉼을 넣었고(클라이언트의 일·네트워크 대기를 흉내), 그래도 시드마다 몇 개뿐이라 버그 5·6처럼 "시드 10개 중 하나 이상"으로 판정한다. 잡히는 이름은 G-single과 반복 불가능한 읽기 둘 다로 센다.
4. **충돌로 진 커밋의 답 시점**: 티켓 16의 후속(#77)이 "묶음 안에서 진 커밋은 묶음이 공개된 뒤 답한다"로 바꿨다. 이 검증은 그 위에서 돈다.
