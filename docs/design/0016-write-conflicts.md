# 0016. 충돌 판정 — 설계

이슈 #26. 두 트랜잭션이 같은 키를 썼다면 **나중에 커밋하는 쪽이 충돌 오류를 받는다**(first-committer-wins, ADR 0006). #25(설계 0015)의 스냅샷 읽기와 합쳐져 스냅샷 격리가 된다. 이것이 없으면 "잃어버린 갱신"이 생긴다. 두 트랜잭션이 같은 잔고를 읽고 각자 더해 쓰면, 나중 커밋이 앞 커밋을 소리 없이 덮어쓴다.

**비유**: 커밋 창구에 **칠판**이 있다. 커밋이 통과할 때마다 번호를 하나씩 붙이고, 그 커밋이 고친 칸 옆에 번호를 적는다. 트랜잭션은 시작할 때 "지금 몇 번까지 통과했나"를 받아 둔다. 커밋하러 오면 창구는 내가 고친 칸 옆의 번호를 본다. 내가 받아 둔 번호보다 큰 번호가 적혀 있으면, 내가 사진을 찍은 뒤 누가 그 칸을 고친 것이다. 그러면 나는 진다.

## 정한 것

| # | 질문 | 결정 | 상태 |
|---|---|---|---|
| B1 | "내 사진 이후 남이 고쳤나"를 어떻게 아나 | **커밋에 메모리 속 번호를 붙이고 "키 → 마지막으로 쓴 커밋 번호" 표를 둔다.** 내 키의 번호가 내 스냅샷 번호보다 크면 충돌 | 사용자 결정 (추천안) |
| B2 | 표를 언제 비우나 | **열린 트랜잭션 중 가장 오래된 것이 시작하기 전의 커밋은 지운다** | 사용자 결정 (추천안) |
| B3 | 커밋 번호를 재시작 뒤에도 이어 가나 | **아니다. 메모리에만 둔다** | 사용자 결정 (추천안) |
| B4 | 무엇을 충돌로 보나 | **같은 키에 대한 쓰기(put·delete)끼리만.** 읽기·범위 조회는 비교하지 않는다. write skew는 허용하고 테스트와 문서에 남긴다 | 사용자 결정 (추천안) |

## 1. 칠판 (`conflict.rs`의 `Writes`)

| 필드 | 무엇 |
|---|---|
| `last` | 마지막으로 무언가를 쓴 커밋의 번호. 1부터 센다 |
| `by_key` | 키 → 그 키를 마지막으로 쓴 (아직 남긴) 커밋 번호 |
| `commits` | 남긴 커밋들, 오래된 것부터, 각자 쓴 키 목록. 지울 때 이것을 앞에서부터 본다 |
| `open` | 커밋 번호 → 그 번호 직후에 시작해 아직 열린 트랜잭션 수 |

| 언제 | 무엇을 |
|---|---|
| `begin` | 스냅샷 번호 = `last`를 받고, `open`에 센다 |
| 커밋 | 내 키 중 `by_key`의 번호가 내 스냅샷 번호보다 큰 것이 있으면 `Error::Conflict { key }`. 아니면 트리에 반영하고 WAL에 쓴 뒤 `last + 1` 번으로 키들을 적는다 |
| 트랜잭션이 끝남 (커밋·롤백·버리기, `Drop`) | `open`에서 빼고, 지울 수 있는 커밋을 지운다 |
| 지우기 | 가장 오래된 열린 스냅샷 번호(없으면 `last`) 이하의 커밋은 열린 트랜잭션이 모두 본 것이라 아무와도 충돌하지 않는다. 앞에서부터 지운다. 그 뒤에 같은 키를 또 쓴 커밋이 있으면 그 키는 남긴다 |

**스냅샷과 번호를 한 잠금 안에서**: 트리(`Arc<Tree>`)와 칠판을 같은 `Mutex` 안의 `Committed`에 둔다. `begin`이 받는 트리와 번호가 언제나 짝이 맞는다. 커밋이 반영한 트리와 적은 번호도 짝이 맞는다.

## 2. 버린 선택지

| | 칠판 (택함) | 스냅샷 값과 최신 값 비교 |
|---|---|---|
| A→B→A (남이 바꿨다가 되돌림) | **충돌** (두 커밋이 그 키를 씀) | 값이 같아 **놓침** → 잃어버린 갱신 |
| 비용 | 내 키마다 해시 조회 한 번 | 내 키마다 트리 조회 두 번 |
| 메모리 | 가장 오래 열린 트랜잭션이 시작한 뒤의 커밋들이 쓴 키 | 없음 |

## 3. 세부 규칙

| 경우 | 동작 | 이유 |
|---|---|---|
| 쓰기 없는 커밋 | 번호를 안 받고, 충돌도 없음 | 아무것도 안 바꿨다 |
| 쓰기는 있는데 트리가 안 바뀜 (없는 키 지우기, 같은 값 쓰기) | **번호를 받고 키를 적음** | 쓰기는 쓰기다. 그 키를 쓰던 다른 트랜잭션은 져야 한다 |
| 충돌한 커밋 | 아무것도 안 씀. 엔진은 계속 돈다 | 다시 시작해 재시도하면 된다 |
| WAL 기록 실패 | 엔진이 멈추고 번호를 안 받음 | 설계 0012 |
| 정리(체크포인트) | 칠판과 무관 | 정리는 데이터를 바꾸지 않는다 |
| 재시작 | 칠판은 빈 채로 시작 | 재시작 전에 연 트랜잭션은 남지 않는다 |

## 4. API 변화

| 무엇 | 변화 |
|---|---|
| `Error::Conflict { key: Vec<u8> }` | 새로. 두 트랜잭션이 함께 쓴 키 하나. 메시지에는 키를 글자(인쇄 가능하면) 또는 16진수로, 64바이트까지 보인다 |
| `Txn`에 `Drop` | 새로. 끝날 때 칠판에서 빠진다. 그래서 **`Txn`을 담은 변수는 스코프 끝까지 `&Db`를 빌린다.** 트랜잭션을 연 채로 `db.close()`를 부르면 컴파일되지 않는다(`drop(txn)` 먼저). 열린 트랜잭션을 두고 닫는 것을 막아 주는 셈이라 받아들였다 |

## 5. 테스트 계획

| 테스트 | 무엇을 |
|---|---|
| `tests/conflict.rs` 예시 10개 | 같은 키 → 나중 커밋 실패, 다른 키 → 둘 다 성공, 재시도 성공, put·delete 어느 쪽이 먼저든 충돌, 시작 전 커밋과는 무관, 충돌한 커밋은 아무것도 안 씀, 읽기는 충돌 아님, **write skew 허용**, A→B→A도 충돌, 정리 뒤에도 충돌 |
| `tests/conflict.rs` proptest 128회 | 한 스레드에서 트랜잭션 여럿을 무작위로 열고 쓰고 커밋·롤백. 커밋은 "시작 뒤 성공한 커밋이 내 키를 썼는가"와 정확히 같을 때만 충돌. 끝의 DB는 성공한 커밋의 모델과 같음 |
| `conflict.rs` 단위 테스트 5개 | 스냅샷 뒤 커밋만 충돌, 열린 트랜잭션이 없으면 칠판이 빔, 오래된 트랜잭션이 끝나면 비워짐, 다시 쓴 키는 남김, 같은 번호에 시작한 둘을 따로 셈 |
