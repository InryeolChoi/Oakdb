# 0028. 서버 정상 종료 — 설계

이슈 #38 (티켓 26). 지금 `oakdb serve`는 멈추는 길이 없다. `Server::run`은 `listener.incoming()`을 영원히 돌고, Ctrl-C나 `kill`(SIGTERM)을 받으면 운영체제의 기본 동작대로 **그 자리에서 프로세스가 죽는다.** 데이터는 잃지 않는다. 응답한 커밋은 모두 WAL에 sync된 뒤라(ADR 0007, 설계 0010), 다시 열면 WAL을 재생해 되살린다. 그러나 이것은 "정전처럼 죽기"다. 클라이언트는 커밋 도중이었는지, 트랜잭션이 어떻게 됐는지 모른 채 연결 리셋만 보고, 다음 시작은 WAL 재생부터 한다.

이번 티켓은 **"종료 신호를 받으면 새 접속을 막고, 진행 중인 커밋을 끝내거나 명확히 실패시킨 뒤 종료"** 를 만든다. 엔진은 이미 필요한 것을 다 갖고 있다(`Db::close` = 마지막 체크포인트, `Drop` = 커밋 스레드 정리와 파일 잠금 해제). 새로 정할 것은 **서버 쪽의 순서와 약속**이다: 어떤 신호를 받나, 문을 어떻게 닫나, 앉아 있는 손님(열린 접속·트랜잭션)을 어떻게 내보내나, 그 손님에게 무슨 말을 하나, 얼마나 기다리나, 어떤 종료 코드로 끝나나.

> **사용자 결정 (2026-11-26): Q1~Q13 모두 추천안대로.** 바뀐 것은 하나다. 이 문서의 초안은 "서버 종료 중" 코드를 `0x48`로 적었지만, 티켓 25(PR #82)가 `0x48`을 트랜잭션 밖 노는 시간 초과(`--idle-timeout`)에 이미 썼으므로 **`0x49`** 로 옮겼다. 아래 본문은 모두 `0x49`로 고쳐 두었다.

> 이 설계는 티켓 25(#37, 설계 0025, 브랜치 `ticket/25-multi-client-transactions`)가 `main`에 들어간 뒤 구현한다. 0025의 **접속 스레드의 지역 변수 `Session`**(Q1-A), **트랜잭션 중에만 거는 노는 시간 제한과 `0x47`**(Q5-B), **`Stats::open_transactions`**(Q7-B)를 그대로 쓴다고 가정한다.

## 비유: 식당 마감

설계 0020이 서버를 "전화 주문을 받는 식당"에 빗댔다. 정상 종료는 **식당 마감**이다.

| 식당 마감 | Oakdb 서버 정상 종료 |
|---|---|
| 사장이 "마감!"을 외친다 | 운영자가 Ctrl-C(SIGINT)를 누르거나 Kubernetes·systemd가 SIGTERM을 보낸다 |
| 현관에 "영업 종료" 팻말을 걸고 문을 잠근다 | 듣는 소켓(listener)을 닫는다. 새 손님은 문 앞에서 돌아간다(접속 거절) |
| 주방에서 만들던 요리는 끝까지 만들어 내준다 | 실행 중인 문장(커밋 포함)은 끝까지 실행하고 그 응답을 보낸다. 커밋은 중간에 끊을 수 없다 |
| 차만 마시던 손님에게는 "마감입니다" 하고 바로 안내한다 | 트랜잭션 밖에서 노는 접속은 바로 `ERROR 0x49 "서버가 종료 중"`을 받고 끊긴다 |
| 코스 요리 중인 손님에게는 10분을 드린다 | 트랜잭션 중인 접속은 **유예 시간**(기본 10초) 동안 `COMMIT`/`ROLLBACK`을 마칠 수 있다 |
| 10분이 지나면 정중히 내보내고, 계산은 안 받는다 | 유예가 끝나면 남은 트랜잭션은 **롤백**하고 `0x49` 후 끊는다 |
| 주방 정리, 장부 정리 | 마지막 체크포인트: WAL의 페이지를 데이터 파일로 옮기고 sync, WAL을 비운다 |
| 셔터를 내리고 열쇠를 반납한다 | 커밋 스레드를 끝내고 파일 잠금을 푼다. 바로 다시 띄워도 `AlreadyOpen`이 안 난다 |
| 사장이 한 번 더 "당장 닫아!"를 외친다 | 두 번째 Ctrl-C: 기다리지 않고 바로 프로세스를 끝낸다(정전과 같지만 응답한 커밋은 안전) |

### Spring Boot와 Kubernetes로 보면

이 그림은 Java/Spring에서 이미 본 것과 거의 같다.

| Spring Boot / Kubernetes | 하는 일 | Oakdb에서 |
|---|---|---|
| `server.shutdown=graceful` | 톰캣이 새 요청을 받지 않고, 처리 중인 요청은 끝낸다 | 문 닫기 + 실행 중인 문장 끝내기 |
| `spring.lifecycle.timeout-per-shutdown-phase=30s` | 그 시간 안에 안 끝난 요청은 버리고 넘어간다 | `--shutdown-grace <초>` (Q4) |
| `@PreDestroy`, `DisposableBean`, HikariCP `close()` | 빈을 정리하고 커넥션 풀을 닫는다 | `Db::close()` = 마지막 체크포인트 + 커밋 스레드 정리 |
| JVM shutdown hook (`Runtime.addShutdownHook`) | SIGTERM/SIGINT를 받으면 hook 스레드가 정리 순서를 돌린다 | 신호를 기다리는 전용 스레드가 종료 절차를 시작한다 (Q1) |
| Kubernetes: 파드 삭제 → SIGTERM → `terminationGracePeriodSeconds`(기본 30초) 뒤 SIGKILL | 30초 안에 못 끝내면 강제로 죽인다 | 유예(10초) + 체크포인트 + 여유가 30초 안에 끝나야 한다. SIGKILL을 받으면 "정전 경로"(WAL 재생)로 간다 |
| Spring의 기본 30초 = Kubernetes의 기본 30초 | 정리가 조금만 늦어도 SIGKILL을 맞는 흔한 사고 | 그래서 기본 유예를 30초보다 **짧게** 잡는다 (Q4) |

PostgreSQL에도 같은 세 단계가 있다: `pg_ctl stop -m smart`(손님이 모두 스스로 나갈 때까지 기다림), `-m fast`(열린 트랜잭션을 바로 롤백하고 끊음, 기본값), `-m immediate`(정리 없이 죽음, 다음 시작에 복구). Q3의 선택지가 이 셋이다.

| 0025가 더하는 것 | 접속마다 `Session`, 트랜잭션 중 노는 시간 제한(`0x47`), `Stats::open_transactions` | 이 설계의 Q3·Q5가 그 위에 얹힌다 |

**지금 SIGTERM을 받으면**: 프로세스가 바로 죽는다. 응답한 커밋은 WAL에 있으므로 안전하고, 미커밋 트랜잭션은 메모리에만 있었으므로 사라진다(= 롤백). 커밋을 보내고 응답을 못 받은 클라이언트는 결과를 모른다. 다음 시작은 WAL을 재생한다. 즉 **정상 종료가 더하는 것은 데이터 안전이 아니라 "명확함"과 "깔끔한 다음 시작"** 이다. 이 점이 아래 선택의 기준이다: 데이터 안전은 이미 WAL이 지키니, 정상 종료 코드가 망가져도(버그, 강제 종료) 데이터는 안전해야 하고, 실제로 그렇다.

## Q1. 어떤 신호를 어떻게 받나

**쉽게 말하면**: 운영체제가 프로그램에 보내는 "쪽지"를 누가 어떻게 읽을지다. SIGINT는 터미널에서 Ctrl-C, SIGTERM은 `kill <pid>`·systemd·Kubernetes가 보내는 "정리하고 끝내라", SIGKILL(`kill -9`)은 프로그램이 받을 수조차 없는 즉사다.

| 신호 | 누가 보내나 | 추천 동작 |
|---|---|---|
| SIGINT | 터미널 Ctrl-C | 정상 종료 시작 |
| SIGTERM | `kill`, systemd `stop`, Kubernetes 파드 삭제, Docker `stop` | 정상 종료 시작 |
| 종료 중 두 번째 SIGINT/SIGTERM | 기다리다 지친 사람 | **강제 종료**: 정리 없이 바로 끝냄(종료 코드 128+신호 번호) |
| SIGKILL | `kill -9`, Kubernetes 유예 초과 | 받을 수 없음. 정전과 같고 다음 시작에 WAL 재생 |
| SIGHUP | 터미널이 닫힘 | 이번엔 손대지 않음(기본 동작 = 죽음 = 정전 경로). 설정 다시 읽기 같은 뜻을 붙일 일이 생기면 그때 |
| SIGQUIT (Ctrl-\\) | 디버깅 | 손대지 않음(코어 덤프) |
| SIGPIPE | 닫힌 소켓에 쓰기 | Rust 실행 파일은 시작할 때 이미 무시로 바꿔 둔다 → 쓰기가 `EPIPE` 오류로 돌아옴. 그대로 |

**신호를 받는 방법**이 진짜 질문이다. 여기서 ft_malloc 경험이 바로 쓰인다.

> 신호 처리기(signal handler)는 프로그램이 **아무 곳에서나** 멈춘 순간에 끼어들어 실행된다. 그 순간 프로그램이 `malloc` 안에서 힙 잠금을 쥐고 있었다면? 처리기 안에서 `malloc`(또는 `println!`, `Mutex::lock`)을 부르면 같은 잠금을 다시 잡으려다 **영원히 멈춘다.** ft_malloc에 스레드 안전을 위해 뮤텍스를 넣어 봤다면 정확히 이 그림이다. 그래서 POSIX는 처리기 안에서 부를 수 있는 함수를 "async-signal-safe" 목록(`write`, `_exit` 등 소수)으로 좁혀 놓았다.

| 선택지 | 모양 | 장점 | 단점 |
|---|---|---|---|
| A. `sigaction` 처리기 + 원자 플래그 | 처리기는 `AtomicBool`만 켬. 다른 곳이 그 플래그를 주기적으로 봄 | 가장 작음 | 처리기가 아무도 깨우지 못함(블로킹 `accept`는 계속 잠들어 있음). 결국 폴링이 필요 |
| B. `sigaction` 처리기 + self-pipe | 처리기는 파이프에 1바이트 `write`(async-signal-safe). accept 루프가 `poll(listener, pipe)` | 고전적이고 즉시 깨움 | 처리기 코드는 `unsafe`이고 규칙이 까다로움. accept 루프를 `libc::poll`로 바꿔야 함 |
| **C. 신호를 막고(`pthread_sigmask`) 전용 스레드가 `sigwait`** | `main`의 맨 앞, **스레드를 하나라도 만들기 전에** SIGINT·SIGTERM을 막는다. 그 뒤 만든 모든 스레드(엔진의 커밋 스레드 포함)가 막힌 마스크를 물려받는다. 신호 스레드 하나가 `sigwait`으로 신호를 "평범한 함수의 반환값"으로 받는다 | 처리기가 없으니 async-signal-safe 걱정이 없다: 신호 스레드는 보통 스레드라 로그를 찍고, 잠금을 잡고, 소켓에 접속해도 된다. 두 번째 신호도 같은 루프에서 센다. POSIX 표준이라 macOS·Linux가 같다 | 마스크를 **`Db::open`보다 먼저** 걸어야 한다(커밋 스레드가 거기서 생김). 순서를 어기면 신호가 커밋 스레드로 가서 기본 동작(즉사)이 된다 → 테스트로 고정 |
| D. 크레이트 `signal-hook` | B를 안전하게 감싼 것 | 검증된 코드 | 설계 0020 S11(외부 크레이트 최소)에 어긋남. 하는 일이 C로 수십 줄 |
| E. 크레이트 `ctrlc` (`termination` 기능) | 처리기 스레드에서 콜백 | 가장 짧음 | 두 번째 신호, 어떤 신호였는지(종료 코드 128+n)를 직접 세야 함. 의존성 추가 |
| F. Linux `signalfd` / macOS `kqueue EVFILT_SIGNAL` | OS별 전용 | 이벤트 루프에 잘 맞음 | 두 OS 코드가 갈림(ADR 0003). 이벤트 루프가 없는 이 서버엔 이득 없음 |

**추천 C.** JVM의 shutdown hook과 같은 모양이다: 신호를 받는 "평범한 스레드"가 종료 절차를 시작한다. 구조는 둘로 나눈다.

| 층 | 무엇 | 어디 | 테스트 |
|---|---|---|---|
| 신호 → 손잡이 | 마스크 걸기, `sigwait` 루프, 첫 신호면 `handle.shutdown()`, 두 번째면 `std::process::exit(128 + n)` | `main.rs` + 작은 `signal.rs` (`#[cfg(unix)]`) | 실제 실행 파일에 신호를 보내는 종단 테스트 |
| 손잡이 → 종료 절차 | `ShutdownHandle::shutdown()`이 플래그를 켜고 accept를 깨움. 나머지는 Q2~Q7 | `server.rs`, 신호와 무관 | 프로세스 안 테스트가 신호 없이 `handle.shutdown()`을 부름 |

이렇게 나누면 종료 절차 대부분을 신호 없이(= 빠르고 결정적으로) 시험할 수 있고, 라이브러리로 서버를 쓰는 코드(테스트, #39 벤치마크)는 신호 마스크를 건드리지 않는다.

`Server::run(self)`은 `Server::run(self) -> Shutdown`으로 바뀌어, 손잡이가 당겨질 때까지 돌고 종료 절차를 마친 뒤 **무엇이 일어났는지**(끊은 접속 수, 롤백한 트랜잭션 수, 체크포인트 결과, 시간 안에 안 끝난 접속 수)를 돌려준다. `main`은 그것으로 로그와 종료 코드(Q8)를 정한다. 손잡이는 `run` 전에 `server.shutdown_handle()`로 받는다(`Clone + Send`).

## Q2. 문을 어떻게 닫나 (accept 멈추기)

**쉽게 말하면**: accept 스레드는 "다음 손님이 올 때까지 문 앞에서 잠든" 상태다. 누군가 깨워야 루프를 빠져나온다. 표준 라이브러리에는 "잠든 `accept`를 다른 스레드에서 취소"하는 함수가 없다.

| 선택지 | 하는 일 | 장점 | 단점 |
|---|---|---|---|
| L1. 논블로킹 accept + 짧은 잠 | `set_nonblocking(true)`, `WouldBlock`이면 50 ms 자고 플래그 확인 | 표준 라이브러리만. 단순 | **평소 경로가 느려진다**: 손님이 와도 최대 50 ms 뒤에 받는다(#39 접속 지연에 그대로 보임). 노는 동안 초당 20번 깨어남. 그리고 **macOS에서는 논블로킹 listener가 받은 소켓이 논블로킹을 물려받는다**(Linux는 안 물려받음). 접속마다 `set_nonblocking(false)`를 잊으면 macOS에서만 깨진다 |
| **L2. "깨우기 손님": 자기 자신에게 접속** | 손잡이가 플래그를 켠 뒤 `TcpStream::connect(127.0.0.1:<port>)`. accept가 그 접속으로 깨어나 **플래그부터** 확인하고 루프를 나감 | 평소 경로는 한 줄도 안 바뀜(블로킹 accept 그대로). 표준 라이브러리만. listener가 `0.0.0.0`에 열려 있어도 루프백으로 닿음. 루프백은 허용 목록에서 항상 허용 | 접속이 실패할 수 있다(fd가 바닥난 순간 등) → 손잡이가 짧게 몇 번 다시 시도하고, 끝내 실패하면 L1처럼 accept 루프가 자체 틱을 켠다(아래 "보험") |
| L3. `poll(listener, 깨우기 파이프)` | `libc::poll`로 둘 중 먼저 오는 것을 기다림 | 즉시, 확실 | accept 루프를 `unsafe` FFI로 다시 씀. fd 하나 더(파이프) |
| L4. 다른 스레드에서 listener를 닫거나 `shutdown` | | 한 줄 | **두 OS가 다르다.** Linux에서는 listen 소켓에 `shutdown()`을 부르면 잠든 `accept`가 오류로 깨어나지만, macOS에서는 확실하지 않다. 닫힌 fd 번호를 다른 스레드가 재사용하는 경쟁도 생김. ADR 0003 위반 |

**추천 L2**, 보험으로 "깨우기 접속이 끝내 실패하면 listener를 논블로킹으로 바꿔 틱으로 확인". 세부:

| 세부 | 추천 | 이유 |
|---|---|---|
| 깨어난 뒤 첫 일 | 받은 소켓이 무엇이든 **플래그부터** 본다. 켜져 있으면 그 소켓(깨우기 손님이거나 진짜 손님)은 `0x49`로 거절 | 깨우기 손님이 자리(`Slot`)를 차지하거나 로그에 "connected"로 찍히지 않게 |
| 이미 OS 대기열(backlog)에 있던 손님 | listener를 버리기 전에 논블로킹으로 **대기열을 비우며** 각자 `0x49`를 보냄(`refuse`와 같은 길, 동시 32개 제한도 같음) | 그냥 버리면 그 손님들은 "연결 리셋"만 본다. 한 번 쓸고 버리면 이유를 안다 |
| 그 뒤 새 손님 | listener를 drop → OS가 바로 거절(`ECONNREFUSED`) | 이슈 기준 "종료 시 새 접속을 거절한다". 유예 내내 문을 열어 두고 `0x49`를 말해 주는 길(아래 표)보다 단순 |

| 유예 동안 문을 | 장점 | 단점 |
|---|---|---|
| **닫는다 (추천)** | 새 손님은 즉시 `connection refused` → 클라이언트·로드밸런서가 바로 다른 곳으로. Kubernetes도 SIGTERM과 함께 파드를 엔드포인트에서 뺀다. 자원이 더 들지 않음 | 거절 이유가 "서버 종료"인지 "서버 없음"인지 클라이언트는 구분 못 함 |
| 열어 두고 오는 손님마다 `0x49` | 이유가 분명 | 유예 내내 accept 루프와 거절 스레드가 돈다. 쏟아지는 재접속이 종료를 방해 |

## Q3. 실행 중인 문장과 열린 트랜잭션

**쉽게 말하면**: 마감 순간 손님은 세 부류다. ① 차만 마시는 손님(트랜잭션 밖에서 노는 접속), ② 주문한 요리가 나오는 중인 손님(문장 실행 중, 커밋 sync 중 포함), ③ 코스 중간인 손님(`BEGIN`은 했고 `COMMIT`은 아직).

②는 선택지가 없다. 엔진에는 문장을 중간에 멈추는 길(취소)이 없고, 커밋은 커밋 스레드에 들어가면 sync까지 간다. **실행 중인 문장은 언제나 끝까지 실행하고 그 응답을 보낸다.** 이것이 이슈 기준 "진행 중인 커밋은 완료되거나 명확한 오류를 받는다"의 "완료"쪽이다. 엔진이 멈춘 상태라면 그 커밋은 `0x25`/`0x26`을 받는다(= "명확한 오류"쪽).

①도 쉽다. 잃을 것이 없으니 바로 `0x49`를 보내고 끊는다.

## Q5. 노는 접속 스레드를 어떻게 깨우나

**쉽게 말하면**: 노는 접속 스레드는 `read`에서 "손님이 말할 때까지" 잠들어 있다. 종료 플래그가 켜져도 손님이 아무 말을 안 하면 영원히 모른다. 누가, 어떻게 깨울까. 이 질문이 이번 설계에서 가장 미묘하다. 깨우는 방법에 따라 **`0x49`가 클라이언트에 도착하느냐가 갈리기 때문이다.**

| 선택지 | 하는 일 | 장점 | 단점 |
|---|---|---|---|
| W1. 조정자가 각 소켓에 `shutdown(Read)` | 열린 접속 목록(소켓의 `Arc`)을 들고 있다가 종료 때 읽기 쪽을 닫음 → 잠든 `read`가 0을 받고 깨어남 | 즉시 깨어남. 설계 0020 P4가 떠올린 그림 | **`0x49`가 사라질 수 있다.** 읽기 쪽을 닫은 소켓은 클라이언트가 그 뒤 보낸 바이트를 더 읽어 낼 수 없다(OS마다 버리거나 쌓아 둠). 읽지 않은 데이터를 남긴 채 소켓을 닫으면 OS가 RST를 보내고, RST는 클라이언트가 아직 읽지 않은 `0x49`까지 지운다. 지금의 `linger`가 피하려는 바로 그 일이다. 그리고 SHUT_RD의 세부 동작은 macOS와 Linux가 다르다(ADR 0003) |
| **W2. 첫 바이트를 기다릴 때만 짧은 틱** | 다음 프레임의 **첫 바이트를 기다리는 동안** 소켓 읽기 시간 제한을 100 ms로 걸고, 깨어날 때마다 종료 플래그와 마감 시각(0025의 노는 시간 제한, Q3의 유예)을 본다. 첫 바이트가 오면 나머지 프레임은 지금처럼 읽는다 | 소켓을 건드리지 않으니 `0x49` + `linger`(쓰기 쪽 닫기 → 남은 것 읽어 버리기 → 닫기)가 그대로 통해 **RST가 없다.** 표준 라이브러리만. 접속 목록이 필요 없음(누가 남았는지는 `active`로 셈). 0025가 이미 "노는 시간 = 첫 바이트를 기다리는 시간"으로 정했으므로 같은 자리에 얹힌다 | 노는 접속마다 초당 10번 깨어남(512개면 초당 약 5천 번의 짧은 시스템 호출, 측정해서 기록). 종료가 최대 100 ms 늦게 알려짐 |
| W3. 접속마다 `poll(소켓, 깨우기 파이프)` | | 즉시, RST 없음 | 접속마다 fd가 하나 더(512 → 1024, `--max-connections` 계산이 바뀜). `unsafe` FFI가 접속 루프 깊숙이 |
| W4. 조정자가 각 소켓에 직접 `0x49`를 씀 | | 즉시 | 접속 스레드도 같은 소켓에 응답을 쓰고 있을 수 있어 **프레임이 섞인다.** 쓰기 잠금이 필요 |

**추천 W2.** 한 가지 함정을 설계에 박아 둔다: **틱은 첫 바이트 전에만** 건다. `BufReader` 위의 `read_exact`가 프레임 중간에서 시간 초과로 실패하면 이미 읽은 바이트가 사라져 프레임 경계를 잃는다. 그래서 "첫 바이트 기다리기"는 `BufReader::fill_buf`(바이트를 소비하지 않고 들여다보기)로 하고, 시간 초과면 아무것도 잃지 않은 채 플래그를 본다. 첫 바이트가 버퍼에 들어온 뒤에는 0025가 정한 대로(트랜잭션 중이면 같은 시간 제한, 아니면 없음) 나머지를 읽는다.

결과적으로 0025의 "다음 프레임 기다리기"를 함수 하나로 모은다.

```
wait_for_frame(...) -> 다음 중 하나
  Frame(프레임)        → 실행
  Closed               → 클라이언트가 닫음
  IdleInTransaction    → 0x47 후 끊음 (0025)
  ShuttingDown         → 0x49 후 끊음 (이번)
```

`ShuttingDown`이 되는 조건: 플래그가 켜졌고, (트랜잭션 밖이거나 유예 마감이 지났다). 문장을 실행한 뒤 응답을 보내고 나서도 같은 조건을 한 번 본다(자동 커밋 문장이 끝난 직후, `COMMIT` 직후 바로 끊기 위해).

`--max-connections`의 fd 계산(`상한 + 64`)은 바뀌지 않는다(W2는 fd를 더 쓰지 않음, 깨우기 손님 1개는 여유 64에 들어감).

## Q6. 클라이언트가 받는 것

| 선택지 | 하는 일 | 장점 | 단점 |
|---|---|---|---|
| A. 말없이 끊기 | 소켓을 닫음 | 통신 규칙 그대로 | 클라이언트는 "서버가 죽었나, 네트워크인가, 내 트랜잭션은?"을 모른다. 이슈의 "명확한 오류"를 못 채움 |
| **B. 새 코드 `0x49` "서버가 종료 중", 끊음** | `ERROR 0x49 "server is shutting down"`을 보내고 `linger` 후 닫음. 범위 `0x40–0x5F`(대화 규칙, 끊음)에 들어감. `closes(0x49) == true` | 이유가 분명. 기존 `0x45`/`0x46`과 같은 길(`send_error` → `linger`). 클라이언트 라이브러리·CLI가 "재접속하면 될 수도"를 안다 | 표에 한 줄, 아래 약속 하나 |
| C. B + 메시지에 "트랜잭션이 롤백됨"을 붙임 | | 사람에게 친절 | 클라이언트는 0025 Q3-A 규칙으로 자기가 트랜잭션 중이었는지 이미 안다. 메시지 문자열에 의미를 싣지 않는다 |

**추천 B.** `0x47`(트랜잭션 중 노는 시간 초과)과 `0x48`(트랜잭션 밖 노는 시간 초과, `--idle-timeout`)은 0025가 쓰므로 다음 번호 `0x49`. 통신 규칙에 넣을 약속:

| 약속 | 뜻 |
|---|---|
| **`0x49`는 요청 없이 올 수 있다** | 지금까지 응답은 요청 하나에 하나였고, 요청 없이 오는 것은 인사 전 거절(`0x45`/`0x46`)뿐이었다. `0x49`(와 0025의 `0x47`·`0x48`)는 인사 뒤에도 요청 없이 온다. 클라이언트는 응답을 기다리다 `0x49`를 받으면 그것을 "내 요청에 대한 답"으로 읽어도 된다(아래 줄 덕분에 뜻이 맞다) |
| **`0x49`를 받았다면, 그 앞에서 응답을 받지 못한 요청은 실행되지 않았다** | 서버는 실행한 문장의 응답을 **반드시 먼저** 보내고 나서 `0x49`를 보낸다. 그러니 마지막으로 보낸 `QUERY`의 답이 `0x49`이면 그 문장은 실행 안 됨. 커밋도 마찬가지 |
| **`0x49`를 받으면 열려 있던 트랜잭션은 없다** | 롤백되었거나, 직전 응답(`COMMIT`의 `DONE`)으로 이미 끝났다 |
| 정상 종료에서는 "결과 모름"이 없다 | 강제 종료(두 번째 신호, 여유 시간 초과, SIGKILL)일 때만 응답 없는 끊김이 생긴다. 그때는 0025 Q1 표의 "COMMIT 직후 끊김"과 같다 |

CLI(`oakdb cli`)는 `0x49`를 받으면 `server is shutting down` (트랜잭션 중이었으면 `; the open transaction was rolled back`)을 stderr에 찍고 종료 코드 1로 끝난다. 자동 재접속은 없다(0020 7절, 0025 Q9 그대로).

## Q7. 커밋 스레드 비우기와 마지막 체크포인트

모든 접속 스레드가 끝나면(`active == 0`) 접속이 쥐던 `Arc<Shared>`도 모두 놓인다. accept 스레드가 `Arc::try_unwrap`으로 `Db`를 꺼내 닫는다. 커밋 스레드를 "비우는" 따로의 절차는 필요 없다. **요청하는 쪽은 답을 받을 때까지 `Db`를 빌리고 있으므로**, `Db`를 꺼낼 수 있다는 것 자체가 큐에 남은 커밋이 없다는 뜻이다. 컴파일러가 순서를 보장한다.

| 선택지 | 하는 일 | 장점 | 단점 |
|---|---|---|---|
| A. 그냥 drop | 커밋 스레드 종료, 잠금 해제 | 가장 빠른 종료 | 다음 시작이 WAL(많아야 수 MiB)을 재생. 정상 종료와 정전의 다음 시작이 같아짐 |
| **B. `Db::close()` = 마지막 체크포인트 후 drop** | WAL의 페이지를 데이터 파일로, sync, WAL을 비움 | 다음 시작은 재생할 것이 없다(PostgreSQL의 shutdown checkpoint와 같음). WAL이 4 MiB 상한이라 오래 안 걸림 | 체크포인트가 실패할 수 있다 → 아래 |
| C. B + 데이터 파일 압축(빈 페이지 반납) | | 파일이 작아짐 | 이번 주제 밖 |

**추천 B.** 실패하면:

| 경우 | 동작 | 종료 코드 |
|---|---|---|
| 체크포인트 성공 | "checkpointed; closed" 로그 | 0 |
| 엔진이 이미 멈춰 있었음(`0x26` 상태) | `close`가 `Stopped`로 실패 → "the engine had stopped; the next start replays the WAL" 로그. 응답한 커밋은 모두 WAL에 있음(엔진의 약속) | 1 |
| 체크포인트 중 디스크 실패 | 엔진이 멈추고 `close`가 `Io` → 같은 로그. 체크포인트는 데이터를 바꾸지 않으므로 응답한 커밋은 그대로(설계 0011) | 1 |
| 여유 시간 초과(Q4) | `Db`를 꺼낼 수 없음 → 닫지 않고 끝냄 | 1 |

엔진이 멈추면 서버가 **스스로** 종료를 시작할지(설계 0020 8절의 선택지 B)는 이번에 하지 않는다. 0020이 고른 "떠 있으면서 `0x26`으로 답하기"를 그대로 두고, 운영자(또는 감시 프로그램)가 SIGTERM을 보내면 이 절차를 탄다. 필요하면 나중에 `--exit-on-engine-stop` 옵션으로 손잡이만 당기면 된다(이번 설계가 그 손잡이를 만든다).

## Q8. 종료 코드

| 끝난 모양 | 추천 코드 | 이유 |
|---|---|---|
| 정상 종료 완료 (유예 뒤 트랜잭션을 롤백했어도) | **0** | 설계대로 끝남. 롤백은 약속된 동작이지 실패가 아님. systemd·Kubernetes가 "정상"으로 봄 |
| 마지막 체크포인트 실패, 엔진 멈춤, 여유 시간 초과 | **1** | 운영자가 볼 일이 있음(디스크). 다음 시작은 WAL 재생 |
| 시작 실패(지금 그대로) | 1 | 0020 8절 |
| 옵션 오류(지금 그대로) | 2 | 0020 |
| 두 번째 신호로 강제 종료 | **128 + 신호 번호** (SIGINT 130, SIGTERM 143) | 셸 관례: 신호로 죽은 프로세스의 `$?`. 스크립트가 "누가 강제로 끊었다"를 안다 |

| 다른 선택지 | 왜 안 고르나 |
|---|---|
| 정상 종료도 130/143 (JVM이 SIGTERM 뒤 143으로 끝나는 것처럼) | 정리가 다 끝났는데 실패처럼 보인다. systemd는 `SuccessExitStatus=143`을 따로 적어야 함 |
| 롤백이 있었으면 1 | 배포할 때마다 "실패"가 찍힌다. 롤백 수는 로그와 `Shutdown` 보고로 충분 |

강제 종료는 신호 스레드에서 `std::process::exit(128 + n)`. 다른 스레드의 소멸자는 돌지 않지만, 파일 잠금은 OS가 프로세스와 함께 풀고, 응답한 커밋은 WAL에 있다. 커밋 스레드가 WAL을 쓰던 중이었다면 그 꼬리는 다음 시작이 잘라 낸다(설계 0010).

외부 크레이트:

| 선택지 | 추천 |
|---|---|
| `libc`만 (이미 있음) — `sigwait`, `pthread_sigmask` | **추천.** 표준 라이브러리에는 신호 API가 아예 없으므로 "표준 라이브러리만"은 불가능하다. 0020 S11의 정신(새 크레이트 없이)은 지킨다. `unsafe`는 마스크 걸기·`sigwait` 두 곳, 각각 `SAFETY:` 주석 |

| 대기열 손님 | 같은 파일 | 손잡이 직전에 접속만 해 둔(HELLO 안 보낸) 소켓 여럿 → 모두 `0x49` 또는 거절, 연결 리셋은 없음 |
| **실제 신호** | `oakdb-server/tests/signal.rs`, `oakdb serve --port 0`을 자식으로 | `libc::kill(pid, SIGTERM)` → 종료 코드 0, stderr에 종료 로그. SIGINT도 0. 종료 중 두 번째 SIGTERM → 143. 끝난 직후 **같은 디렉터리로 바로 다시 띄워** 데이터가 온전한지(`AlreadyOpen` 없음) |
| 마스크가 커밋 스레드에도 걸렸나 | 같은 파일 | 커밋이 쉬지 않는 부하 중에 SIGTERM을 여러 번(서로 다른 실행) 보내 **항상** 정상 종료(0)인지. 마스크가 늦게 걸리면 가끔 신호가 커밋 스레드로 가 즉사(코드 없이 신호로 죽음)한다 |
| **부하 중 종료 불변식** | 같은 파일 | 클라이언트 8개가 각자 고유 id로 자동 커밋 INSERT와 짧은 트랜잭션을 쉬지 않고 보냄. 무작위 순간 SIGTERM. 각 클라이언트는 요청마다 결과를 적는다: 성공 / 오류 코드 / `0x49` / **응답 없이 끊김**. 다시 띄워서: 성공한 id는 모두 있음, `0x49`를 받은 id는 없음, **"응답 없이 끊김"은 0개**(Q6의 약속). 두 OS CI에서 여러 번(예: 20회) |
| `0x49` 인코딩 | `protocol.rs` 단위 | `closes(0x49)`, 표의 범위 |
| CLI | `tests/cli.rs` | 서버를 SIGTERM한 뒤 CLI가 "server is shutting down"과 코드 1로 끝남 |

모든 테스트 소켓에는 지금처럼 읽기 시간 제한(10초)을 걸고, 자식 프로세스 테스트는 끝나지 않으면 일정 시간 뒤 SIGKILL로 치우고 실패한다.
