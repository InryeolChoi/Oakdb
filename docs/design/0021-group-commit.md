# 0021. 그룹 커밋 — 설계

이슈 #28. #27(설계 0018)이 커밋 창구에 **직원 한 명**(커밋 스레드 `oakdb-commit`)을 앉혔다. 손님(스레드)은 전표(쓰기)를 바구니(`std::sync::mpsc` 채널)에 넣고 답을 기다린다. 지금 직원은 전표를 **한 장씩** 처리한다. 한 장마다 금고 문을 잠그는 sync를 한 번 하고, macOS의 `F_FULLFSYNC`는 한 번에 약 3ms다. 그래서 스레드를 몇 개 붙여도 **초당 약 330 커밋이 상한**이다(실험 0002). 이번 티켓은 바구니에 쌓인 전표를 **한꺼번에** 꺼내 WAL에 한 번 쓰고 sync도 한 번만 한 뒤, 모두에게 같이 답한다. 내구성 약속(이슈 #2)은 그대로다. **`Ok`를 받은 커밋은 정전이 나도 남는다.**

**비유: 셔틀버스.** 지금은 손님 한 명이 오면 버스가 그 한 명만 태우고 출발한다(sync). 왕복 3ms 동안 정류장에는 다음 손님들이 줄을 선다. 버스가 돌아오면 또 **맨 앞 한 명만** 태운다. 그룹 커밋은 버스가 돌아왔을 때 **줄 선 사람을 전부 태우고** 출발하는 것이다. 버스 한 번 왕복(sync 한 번)에 열 명이 가면 처리량은 열 배가 된다. 결정할 것은 셋이다. 버스가 정류장에서 **조금 더 기다렸다** 출발할지, **좌석 수**(최대 인원)를 둘지, 그리고 가는 길에 사고가 나면(sync 실패) **탄 사람 모두**에게 뭐라고 말할지다.

Java로 치면 `BlockingQueue.take()`로 하나를 받고 `drainTo(list)`로 쌓인 것을 다 꺼낸 뒤, 묶음 전체를 한 번에 처리하고 각자의 `CompletableFuture`를 완료하는 모양이다. ft_malloc에 빗대면 `write`를 한 바이트마다 부르지 않고 버퍼에 모아 한 번에 부르는 것과 같다. 시스템 호출 한 번의 고정 비용을 여럿이 나눠 낸다.

## 0. 지금 코드에서 무엇이 한 장씩인가

PR #70(#27 검증 반영, 아직 머지 전)은 `Committer::commit`을 다섯 단계로 나눴다. 그룹 커밋은 이 단계를 **여러 커밋에 걸쳐** 다시 묶는 일이다.

| 단계 | 지금 (커밋 하나) | 그룹 커밋 (묶음 하나) |
|---|---|---|
| 확인 | `check_running` → `check_conflict` | 묶음 맨 앞에서 `check_running` 한 번. 커밋마다 `check_conflict` + 묶음 안 키 확인(G2) |
| 만들기 | 최신 트리를 복제해 고침 | 트리를 **한 번** 복제하고, 통과한 커밋을 차례로 그 위에 쌓음 |
| 쓰기 | 바뀐 페이지 + COMMIT, sync 한 번 | 묶음 전체에서 바뀐 페이지 + COMMIT 하나, **sync 한 번**(G3) |
| 공개 | 키 기록 → 트리 바꿔 끼우기 | 커밋마다 키 기록(순서대로) → 트리 바꿔 끼우기 한 번(G5) |
| 정리 | WAL이 4MiB를 넘으면 정리 후 답 | 답한 뒤 정리(G6) |

PR #70에서 이 설계에 닿는 것:

- **`guarded`(패닉을 요청마다 잡음)**: 지금은 요청 하나를 감싼다. 묶음이면 묶음 처리 전체를 감싸고, 패닉이 나면 아직 답하지 않은 묶음 안 커밋이 모두 `OutcomeUnknown`을 받는다(G4).
- **`commits_waiting_behind_a_failed_commit_write_nothing`**: "실패한 커밋 뒤에 줄 선 커밋은 쓰지 않는다"는 그대로다. 다만 "뒤에 줄 선"이 이제 "**다음 묶음**"을 뜻한다. 같은 묶음 안의 커밋은 실패한 그 쓰기에 들어 있었다.
- **`threads` 모드 안정화**(데우기 + 장벽 + 커밋마다 시간 + 중앙값): G9가 그 위에 처리량 측정을 더한다.
- 설계 0018 테스트 표의 "실패를 만난 커밋 **하나만** `OutcomeUnknown`"은 "실패한 **묶음 전체**"로 바뀐다.

## 1. 바구니를 어떻게 비우나 (G1)

커밋 스레드는 `recv()`로 첫 요청을 기다린다. 그 뒤가 선택이다.

| | **A. 있는 것 다 (기다리지 않음)** | B. 조금 기다리기 | C. A + 좌석 수 | D. A + 바이트 상한 |
|---|---|---|---|---|
| 비유 | 버스가 돌아오면 줄 선 사람을 다 태우고 바로 출발 | 1ms 더 기다렸다 출발 | 다 태우되 128명까지 | 다 태우되 짐 무게 제한 |
| 코드 | `recv()` + `try_recv()` 반복 | `recv_timeout`, 시간 설정값 | A + 개수 세기 | 쓰기 전에 크기를 알아야 함 |
| 한 스레드 커밋 시간 | **그대로** | 기다린 만큼 **늘어남** | 그대로 | 그대로 |
| 여러 스레드 처리량 | 높음. sync 동안 쌓인 만큼 자연히 묶임 | 조금 더 높을 수 있음 | A와 같음 (상한에 닿기 전까지) | A와 같음 |
| 위험 | 묶음이 끝없이 커질 수 있음 | 시간이 테스트와 벤치마크를 흔듦 | 없음 | 큰 값 하나가 상한을 넘으면 따로 처리해야 함 |
| 쓰는 곳 | — | PostgreSQL `commit_delay`, MySQL `binlog_group_commit_sync_delay` (둘 다 **기본값 0**) | RocksDB(묶음 바이트 상한) | RocksDB |

**왜 기다리지 않아도 묶이나.** 커밋 스레드가 sync하는 3ms 동안 다른 스레드는 계속 요청을 넣는다. 다음 차례에 `try_recv()`로 꺼내면 그것이 곧 묶음이다. 손님이 없으면 묶음은 1이고, 지금과 똑같이 바로 출발한다. B의 "조금 기다리기"는 sync 동안 아무도 오지 않을 만큼 한가할 때만 도움이 되는데, 그때는 처리량이 문제가 아니다.

**왜 좌석 수는 두나.** 설계 0018 Q3에서 바구니 길이는 "스레드 수 이하"였다. 서버(#37, ADR 0010)가 접속마다 스레드를 쓰면 스레드가 수백이 될 수 있다. 상한이 없으면 묶음 하나의 쓰기가 몇 MB가 되고, 정리 기준(4MiB)도 묶음 하나만큼 넘는다(G6). 개수 상한은 코드 한 줄이고 시간과 무관해서 결정적이다. 바이트 상한(D)은 트리를 고쳐 봐야 크기를 알아서, 이번에는 두지 않는다.

**추천: C.** `try_recv()`로 기다리지 않고 꺼내되 128개에서 멈춘다. 128은 측정 전 임시값이고 티켓 18에서 다시 본다. 남은 요청은 다음 묶음이 된다(순서 유지).

## 2. 같은 묶음 안의 충돌 (G2)

지금의 충돌 판정(설계 0016)은 칠판(`RecentWrites`)에 기록된 커밋과만 비교한다. 묶음 안의 앞 커밋은 **아직 칠판에 없다**(sync 전이라 기록하지 않았다). 그래서 그대로 두면 같은 키를 쓴 두 커밋이 한 묶음에서 둘 다 통과한다. 이것은 **잃어버린 갱신**이다. 카운터 증가 테스트가 깨진다.

| | A. 앞 커밋 키를 칠판에 먼저 기록 | **B. 묶음 안 키 목록을 따로 둠** | C. 같은 키가 겹치면 묶음을 끊음 |
|---|---|---|---|
| 방법 | 커밋마다 확인 직후 `record` | 커밋 스레드가 `HashSet<키>`를 묶음 동안 쥠. 확인 = 칠판 확인 **또는** 이 목록에 있음 | 겹치는 커밋을 다음 묶음으로 미룸 |
| 맞나 | **틀림.** sync 전에 칠판 번호가 올라감 → 그 사이 `begin`한 트랜잭션은 옛 트리와 새 번호를 받아, 같은 키를 써도 충돌하지 않음(설계 0016 Y2가 막은 바로 그 구멍) | 맞음 | 맞음. 미뤄도 다음 묶음에서 결국 충돌 |
| 코드 | 작음 | 작음 | 큼. 순서 바꾸기 규칙 |

**B가 왜 맞나.** 묶음 안의 모든 트랜잭션은 이 묶음이 공개되기 **전에** 시작했다(아직 답을 못 받았으니 당연하다). 그래서 앞 커밋이 쓴 키는 뒤 커밋의 스냅샷에 들어 있을 수 없다. 즉 "묶음 안 앞 커밋이 같은 키를 썼다"는 그 자체로 "내 스냅샷 이후에 남이 먼저 썼다"이고, first-committer-wins 규칙의 정의 그대로다. 번호를 비교할 필요도 없다.

순서: 바구니에서 꺼낸 **도착 순서**대로 확인한다. 통과한 커밋만 트리에 쌓고 키를 목록에 넣는다. 탈락한 커밋은 아무것도 쓰지 않으므로 묶음의 다른 커밋에 영향이 없다.

**추천: B.** `conflict.rs`는 바뀌지 않는다. 공개 단계에서 통과한 커밋마다 지금처럼 `record`를 한 번씩, 도착 순서로 부른다. 커밋 번호는 커밋마다 하나씩이라 설계 0016의 번호 의미도 그대로다.

## 3. WAL에 묶음을 어떻게 적나 (G3)

지금 WAL 커밋 하나 = 페이지 레코드 여러 개 + COMMIT 레코드 하나(바뀐 메타). 재생은 "COMMIT이 뒤따라야 페이지가 유효", "체크섬이 처음 깨진 곳에서 멈춤"이다.

| | **A. 묶음 하나 = COMMIT 하나** | B. 트랜잭션마다 COMMIT, 쓰기·sync는 한 번 | C. 새 BATCH 레코드(개수 + 내용) |
|---|---|---|---|
| WAL 형식 | **그대로** | 그대로 | 새 레코드 종류, 형식 번호 올림 |
| 재생 규칙 | 그대로 | 그대로 | 새 규칙 |
| 반쯤 쓰인 묶음 (정전) | 묶음 전체가 없던 일. 응답한 커밋은 없음 | 묶음의 **앞부분 몇 개**가 살아남을 수 있음. 역시 응답한 커밋은 없음 | A와 같음 |
| 같은 페이지를 두 커밋이 고치면 | **한 번만** 씀 (마지막 모습) | 커밋마다 씀 | 한 번 |
| 만들기 | 트리 한 번 복제, 바뀐 페이지 한 번 꺼냄 | 커밋마다 바뀐 페이지를 꺼내 따로 인코딩 | A와 같음 + 새 코드 |
| ADR 0007 문구 | "그룹 커밋 **배치마다** 바뀐 페이지의 전체 사본과 COMMIT 레코드" 그대로 | 다름 | 다름 |

**반쯤 쓰인 묶음.** 묶음의 바이트는 `write_all_at` 한 번 + sync 한 번이다. 그 사이 정전이면 앞부분만 디스크에 닿거나 칸이 찢긴다. A에서는 COMMIT 레코드가 묶음 맨 끝에 하나뿐이라, 그것까지 사슬 체크섬이 맞아야 묶음이 산다. 아니면 재생이 묶음 앞에서 멈추고 꼬리는 `oakdb.wal.cut`으로 간다. 그 묶음의 커밋은 **아무도 `Ok`를 받지 않았으므로** 잃어도 약속 위반이 아니다. 이미 있는 실험 0009·0010의 "커밋 하나가 반쯤" 경우와 똑같은 모양이라, 재생 쪽 시험이 그대로 이 경우를 덮는다.

B의 "앞부분만 산다"도 틀리지는 않다(응답 전이니까). 하지만 묶음 쪽 코드는 커밋마다 페이지 목록을 따로 들고 있어야 하고, 같은 페이지를 여러 번 써서 WAL이 빨리 차고 정리가 잦아진다. 얻는 것이 없다. 페이지 사본 방식(ADR 0007)에서는 WAL이 "어느 트랜잭션이 무엇을 했나"를 원래 남기지 않는다.

**추천: A.** 디스크 형식·재생 코드·`commit_len`이 그대로라서 이번 티켓의 위험이 커밋 스레드 안에 갇힌다. 지금의 `append(&mut wal, &mut next)`가 이미 "트리 하나의 바뀐 페이지 + 메타"를 쓰므로, 묶음 트리를 넘기기만 하면 된다.

## 4. sync가 실패하면 (G4)

설계 0012와 ADR 0007이 이미 정했다. "디스크 기록이 실패하면 재시도하지 않고 엔진을 멈춘다. **그 배치의 클라이언트**에는 결과를 알 수 없음을 돌려준다." 그룹 커밋은 그 "배치"를 실제로 만드는 티켓이다.

| 누가 | 받는 답 | 왜 |
|---|---|---|
| 묶음에서 충돌 확인을 통과한 커밋 모두 | `OutcomeUnknown` (같은 `Arc<io::Error>`를 나눠 쥠) | 쓰기가 디스크에 닿았는지 모른다. 다시 열면 묶음 전체가 있거나 전체가 없다(G3 A) |
| 묶음에서 `Conflict`로 떨어진 커밋 | `Conflict` | 아무것도 쓰지 않았다는 사실은 sync 결과와 무관하다(작은 질문 Q2) |
| 다음 묶음부터 | `Stopped` | 커밋 스레드가 묶음 맨 앞에서 `check_running` |
| 커밋 스레드 패닉 (버그) | 아직 답 못 받은 묶음 안 커밋 모두 `OutcomeUnknown`, 엔진 멈춤 | PR #70의 `guarded`를 묶음 단위로 |

`Error`는 이미 `Clone`이라(설계 0012) 같은 오류를 묶음 전체에 나눠 주는 것은 `clone()` 한 번씩이다.

비유하면 버스가 사고를 당하면 **탄 사람 모두**에게 "도착했는지 확인 못 함"이라고 알린다. 한 명만 운 나쁜 게 아니다. 묶음이 클수록 한 번의 디스크 고장이 더 많은 손님에게 `OutcomeUnknown`을 주지만, 그 손님들은 어차피 같은 sync를 기다리고 있었다. 한 장씩 처리했어도 첫 손님은 `OutcomeUnknown`, 나머지는 `Stopped`였을 것이다. 손님 쪽에서 할 일(다시 열고 확인)은 같다.

**추천: 표 그대로.** 새 규칙은 없고, 설계 0012의 "그 배치"가 이제 진짜 묶음이 된다.

## 5. 언제 보이고, 언제 답하나 (G5)

| 순서 | 무엇 | 잠금 |
|---|---|---|
| 1 | 묶음 전체를 WAL에 쓰고 **sync** | 없음. 그동안 `begin`·`Drop`·읽기는 옛 트리로 진행 |
| 2 | 통과한 커밋마다 도착 순서로 `recent.record(키)` → 트리 `Arc` 한 번 바꿔 끼우기 | `committed` 잠깐 |
| 3 | 묶음의 손님들에게 `Ok` | 없음 |

- **sync 전에는 아무것도 안 보인다.** 디스크에 없을 수도 있는 값을 남이 읽는 일이 없다(설계 0018과 같다).
- **2를 한 번의 잠금 안에서 한다.** 묶음 중간까지만 보이는 순간이 없다. 다른 트랜잭션은 묶음 전체 전 또는 전체 후를 본다. 키 기록 → 트리 순서는 설계 0016 Y2 그대로다.
- **답은 공개 뒤에 한다.** `Ok`를 받은 손님이 곧바로 `begin`하면 자기 쓰기를 본다(read-your-writes). 답을 공개보다 먼저 하면 이것이 깨진다.

**추천: 표 그대로.**

## 6. 정리(체크포인트)와의 관계 (G6)

세 가지를 정한다.

**(1) 언제 정리를 확인하나.** 지금은 커밋마다 "WAL > 4MiB면 정리"다. 묶음 안에서는 확인하지 않고 **묶음 뒤에 한 번** 한다. 그래서 WAL은 4MiB + 묶음 하나까지 자랄 수 있다. ADR 0007 메모의 "재생은 `CHECKPOINT_AFTER` + 커밋 하나 이하"가 "+ 묶음 하나 이하"가 된다. G1의 좌석 수 상한이 이 크기를 묶는다.

**(2) 바구니에 `checkpoint()` 요청이 섞여 있으면.** 요청은 도착 순서대로 처리한다(설계 0018 Q5: 정리도 창구를 거친다). 그래서 `try_recv()`로 꺼낸 것이 정리 요청이면 **묶기를 거기서 끊는다.** 앞의 커밋 묶음을 먼저 처리하고, 그다음 정리, 그다음 새 묶음이다. 정리 요청을 앞당기거나 묶음 뒤로 미루면 "정리는 그 전 커밋 뒤에 돈다"(`Db::checkpoint` 문서)가 깨진다.

**(3) 답을 정리 전에 하나, 뒤에 하나.** 설계 0018 Q6은 "지금처럼 정리한 뒤 답한다. #28에서 다시 본다"였다.

| | 정리 뒤 답 (지금) | **답 먼저, 그다음 정리** |
|---|---|---|
| 묶음 손님의 기다림 | sync + 정리(sync 4번 이상) | sync 한 번 |
| 정리가 실패하면 | `Ok` + 엔진 멈춤 (#24 메모) | `Ok` + 엔진 멈춤. **같다** |
| 다음 묶음 | 정리를 기다림 | 정리를 기다림. 같다 |

이미 #24에서 "커밋이 WAL에 sync된 뒤 정리가 실패해도 그 커밋은 `Ok`"로 정했다. 그래서 답을 먼저 해도 손님이 받는 답은 하나도 바뀌지 않고, 기다림만 준다. 묶음이 크면 정리 하나가 여러 손님을 붙잡으므로 차이가 커진다.

**추천: 묶음 뒤에 한 번 확인, 정리 요청에서 끊기, 답 먼저.** 위험은 하나다. "커밋이 돌아왔으면 정리도 끝났다"를 가정한 기존 테스트가 있으면 깨진다. 구현할 때 그런 테스트를 찾아 "정리 뒤 상태"는 `checkpoint()`나 다음 요청 뒤에 보도록 고친다.

## 7. 묶음 크기와 sync 횟수 재기 (G7)

완료 조건 "배치 크기와 sync 횟수를 측정할 수 있다".

| | **A. `Db::stats()` 공개 API** | B. 로그·`tracing` | C. 테스트에서만 (`SimFs` 셈) |
|---|---|---|---|
| 무엇 | 커밋 스레드가 `AtomicU64` 몇 개를 올리고, `stats()`가 한 번에 읽어 돌려줌 | 묶음마다 한 줄 | 가짜 디스크가 sync를 셈 |
| 운영 중 보기 | 됨. 서버(#37)가 그대로 내보낼 수 있음 | 됨, 파싱 필요 | 안 됨 |
| 비용 | 묶음마다 원자 연산 몇 번(ns) | 묶음마다 문자열 | 없음 |
| 의존성 | 없음 | 크레이트 하나 | 없음 |

담을 숫자(모두 `Db`를 연 뒤부터 센다):

| 필드 | 뜻 |
|---|---|
| `commits` | `Ok`로 답한 쓰기 커밋 수 |
| `conflicts` | `Conflict`로 떨어진 수 |
| `batches` | 처리한 묶음 수 (충돌만 있어 아무것도 안 쓴 묶음 포함) |
| `wal_syncs` | WAL 커밋 쓰기의 sync 수. **완료 조건 "여러 커밋이 하나의 sync"는 `wal_syncs < commits`** |
| `largest_batch` | 가장 큰 묶음의 커밋 수 |

평균 묶음 크기는 `commits / batches`로 계산한다. 분포(히스토그램)는 이번에 넣지 않는다. 티켓 18에서 필요하면 2의 거듭제곱 칸 몇 개로 더한다. 정리의 sync는 `wal_syncs`에 넣지 않는다(커밋 하나당 sync를 묻는 숫자라서).

A/B 하네스(`commit_time.rs`)는 **두 버전 모두에서 빌드돼야** 하므로 `stats()`를 부를 수 없다(옛 버전에 없다). 묶음 크기는 별도 예제(`examples/group_commit_stats.rs` 같은 것)로 재서 실험 기록에 남긴다.

**추천: A + C.** 공개 숫자는 운영과 벤치마크에, `SimFs`의 sync 수는 테스트에서 "커밋 N개, sync 1번"을 정확히 단언하는 데 쓴다.

## 8. 정전 실험: 응답한 커밋은 항상 남는다 (G8)

지금 정전 실험(`examples/crash_sim/harness.rs`, 실험 0008~0010)은 **한 스레드**다. 한 스레드에서는 묶음이 늘 1이라 그룹 커밋을 시험하지 못한다. 두 가지를 더한다.

| 테스트 | 방법 | 확인 | 왜 결정적인가 |
|---|---|---|---|
| **sync 문으로 만든 묶음** | 커밋 A를 sync 문(`SimFs::hold_syncs`, 설계 0018 C6)에 붙잡는다. 그동안 스레드 N개가 서로 다른 키로 커밋을 보낸다. 모두 바구니에 들어간 것을 확인하고 문을 연다 | 두 번째 sync 하나에 N개가 들어간다 (`wal_syncs`, `largest_batch`, `SimFs` sync 수) | 시간이 아니라 문으로 순서를 만든다. "바구니에 다 들어갔다"를 아는 테스트용 훅(바구니 길이 또는 받은 요청 수)이 필요하다 |
| **묶음 쓰기의 모든 지점에서 정전** | 위 묶음을 만든 뒤 `fail_after(k)`를 k = 0, 1, 2, …로 바꿔 가며 묶음의 쓰기·sync 각 지점에서 전원을 끄고 `crash(seed)` → 다시 열기 | `Ok` 받은 커밋은 모두 있다. 묶음의 커밋은 **모두 있거나 모두 없다** | 묶음 구성이 고정이라 같은 k, 같은 seed면 같은 결과 |
| **sync 실패** | 같은 묶음에서 `fail_once_after`로 sync를 실패시킴 (`FailedSync::Forgets` 포함) | 묶음 전원 `OutcomeUnknown`, 그 뒤 `Stopped`, 다시 열면 묶음 전체가 있거나 전체가 없다 | 위와 같다 |
| **같은 묶음 안 충돌** | 문에 붙잡힌 동안 같은 키를 쓰는 두 커밋 B, C를 차례로 보냄 | 먼저 도착한 쪽만 `Ok`, 다른 쪽 `Conflict`. 다시 열어도 `Ok` 쪽 값 | 도착 순서를 테스트가 정한다 |
| **여러 스레드 무작위 정전** | 스레드마다 자기 키 접두사로 무작위 커밋, 받은 `Ok`를 기록. 무작위 지점에서 전원 끄기, 여러 seed | 판정: 다시 연 DB = (`Ok` 받은 커밋 전부) + (답 못 받은 커밋 중 일부, 각각 통째로) | 스케줄은 흔들려도 **판정이 순서와 무관**하다. 실패하면 seed와 함께 기록 |
| 카운터 증가 (기존 blind 테스트) | 겹치는 키 | 잃어버린 갱신 없이 정확히 `스레드 × 횟수` | G2가 틀리면 바로 깨진다 |

판정 함수 `judge`는 지금 "잘린 커밋 하나가 들어갔거나 안 들어갔다"만 안다. 여러 스레드용은 "답 못 받은 커밋들 각각이 통째로 있거나 없다"로 넓힌다. 묶음 구성을 아는 결정적 테스트에서는 더 강하게 "묶음 통째로"를 본다.

**추천: 표 전부.** 결과는 실험 기록 `docs/experiments/`에 "정전과 그룹 커밋"으로 남긴다.

## 9. 티켓 18의 A/B 가설과 `threads` 모드 (G9)

A/B 하네스(`ab_versions.py`)는 두 버전을 ABBA 순서로 번갈아 돌리고 Mann-Whitney U로 비교하며, A/A 대조군을 함께 돌린다. 그룹 커밋 전후를 같은 방식으로 잰다.

| 가설 | 모드 | 기대 | 판정 기준 |
|---|---|---|---|
| H1. 여러 스레드 처리량이 sync 상한(약 330/s)을 넘는다 | `threads_tput` 4·8·16스레드 (새 모드) | 스레드 수에 따라 늘어남. 4스레드 ≥ 2배 | 처리량 비율의 95% CI 하한 > 1, p < 0.05 |
| H2. 여러 스레드 커밋 하나의 기다림이 준다 | `threads` (PR #70판, 커밋마다 시간의 중앙값) | 4스레드 약 11ms → 약 6ms (내 앞 sync 하나 + 내 sync 하나) | 중앙값 비율 CI 상한 < 1 |
| H3. 혼자 커밋할 때 느려지지 않는다 | `overwrite`, `grow` | 그대로 (기다리지 않으므로, G1) | 비율 CI가 [0.95, 1.05] 안 |
| H4. 남이 커밋하는 동안 읽기는 여전히 안 막힌다 | `begin_busy` | 그대로 | 비율 CI가 1을 포함 |
| A/A | 모든 모드 | 차이 없음 | p > 0.1. 아니면 그 모드의 결과는 쓰지 않는다 |

**`threads` 모드 안정화.** #67 검증에서 A/A의 `threads` 중앙값이 2822 대 4480µs로 흔들렸다. PR #70이 데우기, 장벽, 커밋마다 시간, 중앙값 비교로 고쳤다(8번 실행 중앙값 11006~11967µs). 그 위에 더할 것:

| 무엇 | 왜 |
|---|---|
| 스레드 수를 인자로 (`threads 8` 등). 기본 4는 그대로 | 옛 버전과 같은 파일로 빌드되고, 스레드 수에 따른 늘어남(H1)을 본다 |
| **처리량은 따로** (`threads_tput`): 장벽 뒤부터 마지막 커밋까지 벽시계 시간으로 커밋/초 | 커밋마다 시간(H2)과 처리량(H1)은 다른 질문이다. 하나에 섞으면 해석이 흔들린다 |
| 라운드당 커밋 수를 스레드당 300 이상으로 | 데우기 뒤 묶음 크기가 자리 잡을 시간 |
| 라운드를 늘림(20 → 30), 한 라운드 = 새 DB | 느린 sync 한 번이 라운드 전체를 끄는 일을 줄임 |
| 측정 중 다른 무거운 작업 금지, 전원 연결, 같은 Mac(M3) | macOS `F_FULLFSYNC` 시간은 디스크 상태에 민감 |
| Linux CI에서도 한 번 (참고용) | ADR 0003. Linux `fdatasync`는 빨라서 묶음이 작게 나올 수 있다. 판정은 macOS로만 |

**추천: 표 전부.** 측정 자체는 티켓 18에서 하고, 이번 티켓은 모드 추가와 H3(한 스레드 그대로)만 검증 단계에서 확인한다.
