# 0013. 가짜 디스크: 길이만 닿고 내용은 0인 쓰기 — 설계

이슈 #56. #23(체크포인트) 검증에서 가짜 디스크(`SimFs`)가 **만들지 못하는 고장**이 나왔다. WAL 머리말을 쓰다 정전이 나면 "파일 길이는 20바이트로 늘었는데 내용은 0"인 WAL이 남을 수 있다. 리뷰어와 눈 가린 테스터는 코드를 읽고 이걸 찾았지만(리뷰 P1), 정전 실험 10만 시드는 찾지 못했다. 같은 이유로 변이 C3(비우기와 머리말 사이의 sync 빼기)도 아무 테스트가 잡지 못했다(실험 0010 2절). 이번 티켓은 가짜 디스크의 정전에 이 고장을 더한다.

**비유**: 공책에 새 장을 붙여 글을 쓰는 중이다. 정전이 나면 지금까지는 "글이 다 남음 / 다 사라짐 / 줄마다 일부만 남음" 셋 중 하나였다. 그런데 실제로는 **"공책에 빈 장은 붙었는데 글씨는 하나도 안 남음"**도 있다. 목차(파일 길이)는 먼저 고쳐 적고 본문(내용)은 나중에 쓰는 파일 시스템이 있어서다. 그 빈 장은 0으로 읽힌다.

```
쓰기 전:   [옛 내용 ......]                     ← 파일 끝
쓰기:      [옛 내용 ......][새 내용 새 내용]
정전 뒤:   [옛 내용 ......][0 0 0 0 0 0 0 0]    ← 길이만 닿음
```

## 1. 실제 파일 시스템은 어떤가

| 파일 시스템·모드 | 길이가 내용보다 먼저 닿을 수 있나 | 확신 |
|---|---|---|
| Linux ext4 `data=writeback` | 예. 메타데이터(길이 포함)만 저널에 넣고, 데이터 블록은 순서 보장 없이 나중에 쓴다. 정전 뒤 늘어난 자리가 0이나 **옛 블록의 쓰레기**로 보일 수 있다 | 높음 (모드의 정의) |
| XFS | 예. 정전 뒤 파일 끝 쪽이 0(NULL 바이트)으로 보이는 일이 오래 알려져 있다. 커널 버전마다 고친 것이 있어 지금도 같은 빈도인지는 모른다 | 중간 |
| Linux ext4 `data=ordered` (기본값) | 보통은 아니다. 데이터 블록을 먼저 쓰고 나서 그 블록을 가리키는 메타데이터를 저널에 넣는다. 지연 할당(delayed allocation)과 얽힌 경우까지 모두 막는지는 확인하지 못했다 | 중간 |
| macOS APFS | 모른다. copy-on-write라 길이와 내용이 한 번에 바뀔 것 같지만, 공개 자료로 확인하지 못했다 | 낮음 |

Oakdb는 macOS와 Linux 둘 다에서 같은 보장을 지켜야 한다(ADR 0003). 그래서 **가장 험한 쪽(ext4 writeback, XFS)에 맞춘다.** 가짜 디스크는 원래 실제 디스크보다 험하게 시험하는 도구다(설계 0008의 512바이트 칸과 같은 생각).

**모델 밖에 남긴 것**: ext4 writeback은 0 대신 **옛 블록 내용**을 보일 수도 있다. 이건 "옛 WAL 머리말이 새 자리에 보임" 같은 다른 고장을 만든다. 이번에는 0만 다룬다. 회고에서 다음 티켓 후보로 넘긴다.

## 2. 어떤 쓰기가, 어디까지 (결정 1·2·3·4)

| 선택지 | 장점 | 단점 |
|---|---|---|
| **(가) 쓸 때의 끝으로 잼 (추천)** | 엔진이 "끝에 덧붙인다"고 믿은 쓰기만 해당. C3를 잡는다 (아래) | 앞선 비우기(`set_len(0)`)가 정전으로 사라진 경우, 0이 **옛 내용을 덮는다**. 실제 저널은 비우기와 길이 늘리기를 보통 같이 잃으므로 실제보다 험할 수 있다 |
| (나) 정전 때 디스크의 끝으로 잼 | 더 현실적 | C3를 못 잡는다. 비우기가 사라지면 머리말 쓰기가 "끝 안쪽"이 되어 "길이만"이 될 수 없다 |

**C3를 잡으려면 (가)여야 한다.** 체크포인트의 마지막은 이렇다.

```text
set_len(0) → [sync ← C3가 지우는 것] → 머리말 20바이트 쓰기(0번 바이트, 끝을 넘음) → sync
```

| sync 있음 (지금 코드) | sync 없음 (C3) |
|---|---|
| 비우기는 이미 디스크에 있다. 머리말이 "길이만"이면 **20바이트 0** → P1 수정이 "머리말 없음"으로 보고 새로 씀 → 열림 | 비우기가 사라지고 머리말이 "길이만"이면 **옛 WAL의 앞 20바이트가 0** → 머리말이 깨진 긴 WAL → `Corrupt`로 거절 → 정상 DB가 안 열림 |

지금 SimFs의 "쓰기마다 따로 주사위"는 원래 순서 바꿈(나중 쓰기는 남고 앞 쓰기는 사라짐)을 허용한다. (가)도 같은 원칙이다: 비우기와 머리말의 운명은 따로 정해진다.

- **0이 되는 자리** = `max(쓰기 시작, 쓸 때의 끝)` ~ 쓰기 끝. 이걸 `zeros_from`이라 부른다. 끝 안쪽 부분은 "쓰기가 안 닿음"과 같다(그 자리에 디스크가 들고 있던 것이 남음).
- **찢김과 섞지 않는 이유**: 찢김은 "칸마다 새 내용이 닿았나"다. 칸마다 "0"까지 섞으면 경우가 늘어나지만, 엔진에 새로 보여 주는 것은 "끝을 넘는 자리에 0"이 전부다. 단순한 쪽을 골랐다.
- **`set_len` 늘리기**: 늘어난 자리는 원래 0이라 "길이만"과 결과가 같다. 그 자리에 쓰는 쓰기는 쓸 때 끝 **안쪽**이므로 "길이만"이 되지 않는다.
- **적용 순서**: 다른 변경과 똑같이, 파일의 `waiting` 목록 순서대로 하나씩 적용한다.

## 3. 주사위와 시드의 뜻 (결정 5·6)

정전 실험의 시드는 "어떤 작업에서, 언제 끊고, 무엇이 남나"를 정한다. 주사위를 하나라도 더 던지면 **그 뒤의 모든 주사위가 밀려서** 같은 시드가 다른 디스크가 된다. 실험 0008~0010의 기록과 `tests/crash.rs`의 고정 시드가 모두 뜻을 잃는다.

| 선택지 | 시드의 뜻 | 확률 (끝을 넘는 쓰기) |
|---|---|---|
| (가) 주사위를 하나 더 던짐 | 거의 **모든 시드가 바뀜** | 원하는 대로 |
| (나) `below(3)` → `below(4)` | 끝을 넘는 쓰기마다 결과가 바뀜 (3으로 나눈 나머지와 4로 나눈 나머지가 다름) | 각 1/4 |
| **(다) 같은 주사위의 다른 비트 (추천)** | 끝을 넘는 쓰기가 "사라짐"을 뽑았을 때만 바뀜. **나머지는 예전과 똑같은 디스크** | 남음 1/3, 찢김 1/3, 사라짐 1/6, 길이만 1/6 |

(다)는 주사위 값을 3으로 나눈 나머지로 지금처럼 셋 중 하나를 고르고, "사라짐"이면 같은 값의 맨 위 비트로 "길이만"인지 정한다. 던지는 횟수가 그대로라서 그 뒤의 주사위도 그대로다.

**끄는 옵션 (결정 6)**

| 선택지 | 장점 | 단점 |
|---|---|---|
| **(가) 두지 않음 (추천)** | 공개 API가 늘지 않는다. (다) 덕분에 대부분의 시드가 그대로다 | 예전 실험을 **글자 그대로** 다시 내려면 예전 커밋으로 돌아가야 한다 |
| (나) `SimFs`에 스위치 | 예전 디스크를 지금 코드로 그대로 재현 | 쓰지 않을 API와 테스트가 하나씩 는다 |

## 4. 보고 (결정 7)

```rust
pub enum Landing {
    Lost,
    Kept,
    Torn { sectors: Vec<bool> },
    /// 새 길이만 닿음: zeros_from부터 쓰기 끝까지 0
    LengthOnly { zeros_from: u64 },
}
```

`zeros_from`이 없으면 보고만 보고는 "앞부분은 옛 내용, 뒷부분은 0"인 쓰기(2절)를 구별할 수 없다. `crash_sim one <seed>`은 이렇게 찍는다. 이번에 파일 이름과 **길이 변경의 운명**도 함께 찍게 했다. C3 같은 경우는 "비우기가 사라짐"이 함께 보여야 이해된다. 체크포인트 도중 정전이면 "power cut in the checkpoint after commit N"이라고 찍는다(예전에는 "while opening"으로 잘못 찍혔다).

```text
unsynced writes at the crash:
  oakdb.wal page 0: length only, zeros from byte 0
  oakdb.wal set to 0 bytes: lost
```

`sweep`은 마지막 줄에 "길이만"이 하나라도 나온 시드 수를 찍는다. 시드의 뜻이 얼마나 바뀌었는지를 바로 볼 수 있다.
