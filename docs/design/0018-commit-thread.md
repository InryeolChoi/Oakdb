# 0018. 여러 스레드와 커밋 창구 — 설계

이슈 #27. 여러 스레드가 한 `Db`를 나눠 쓰며 트랜잭션을 동시에 실행하고, 커밋은 **커밋 창구 하나가 순서대로** 처리한다(ADR 0006). #25(스냅샷, 설계 0015)와 #26(충돌 판정, 설계 0016)이 "실행은 동시에"와 "같은 키는 먼저 커밋한 쪽이 이김"을 만들었다. 이번에는 **커밋이 디스크를 기다리는 동안 다른 스레드가 멈추지 않게** 한다. 바로 다음 #28(그룹 커밋)이 이 창구 위에 "여러 커밋을 묶어 sync 한 번"을 얹는다. 그래서 #28이 얹히기 쉬운 모양을 고르는 것도 이번 설계의 일이다. #28 자체는 설계하지 않는다.

**비유**: 은행이다. 손님(스레드)은 각자 자리에서 장부 사진(스냅샷)을 보며 전표(쓰기)를 작성한다. 다 쓰면 **커밋 창구**에 낸다. 지금은 창구 직원이 없고 **열쇠가 하나**뿐이다. 전표를 낸 손님이 열쇠를 들고 직접 칠판을 확인하고, 장부를 고치고, 금고(디스크)에 넣고 금고 문이 잠길 때(sync)까지 열쇠를 쥔다. 그동안 **다른 손님은 장부 사진도 못 찍고, 볼일을 끝내고 나가지도 못한다.** 이번 티켓은 창구에 **직원 한 명**(커밋 스레드)을 앉힌다. 손님은 전표를 창구 바구니(채널)에 넣고 번호표(응답 통로)를 받아 기다린다. 직원이 금고 앞에 있는 동안에도 다른 손님은 사진을 찍고 전표를 쓴다. #28은 직원이 바구니에 쌓인 전표를 **한꺼번에** 금고에 넣는 것이다.

Java로 치면 `Executors.newSingleThreadExecutor()`에 커밋을 `submit`하고 `Future.get()`으로 기다리는 모양이다.

## 0. 지금 코드에서 무엇이 막히나

`Txn::commit`은 `committed` 잠금을 잡은 채 충돌 확인 → 트리 복제·수정 → WAL 쓰기 → **sync** → 칠판 기록 → 트리 바꿔 끼우기 → (필요하면) 정리까지 한다. 같은 잠금을 쓰는 곳:

| 호출 | 잠금을 왜 잡나 | 남의 sync 동안 |
|---|---|---|
| `begin` | 트리 `Arc` 복제 + 칠판에 "열림" 등록 | **기다린다** |
| `Txn`의 `Drop` (커밋·롤백·**읽기만 한 트랜잭션**도) | 칠판에서 "열림" 해제 | **기다린다** |
| `page_count` | 트리 메타 읽기 | 기다린다 |
| `checkpoint`·`close` | 트리를 데이터 파일에 씀 | 기다린다 (정리 동안 `begin`도 막는다) |
| `get`·`scan`·`put`·`delete` | 잡지 않음 (스냅샷·개인 버퍼) | 안 기다린다 |

이미 `Db<StdFs>`는 `Sync`라서 `std::thread::scope`로 나눠 쓸 수 있다(blind 테스트 `concurrent_read_modify_write_increments_lose_no_updates`가 8스레드로 돈다). 즉 "공유"는 되는데 **"서로 막지 않는다"가 안 된다.** macOS의 `F_FULLFSYNC`는 수 ms라서, 남이 커밋 중이면 읽기만 하는 트랜잭션도 시작과 끝에서 그만큼 선다.

## 1. 커밋을 누가 처리하나 (C1)

| | A. 지금 그대로 | B. 잠금 둘로 나누기 | **C. 커밋 스레드 + 채널** | D. 리더-팔로워 |
|---|---|---|---|---|
| 모양 | 잠금 하나를 sync까지 쥠 | "커밋 줄" 잠금(WAL을 품음)은 sync까지, 트리·칠판 잠금은 잠깐만 | 스레드 하나가 WAL·작업 트리를 독차지. 손님은 요청을 보내고 기다림 | 스레드 없음. 먼저 온 커밋이 대표가 되어 줄 선 커밋들의 sync를 대신 함 |
| `begin`·`Drop`이 sync를 기다리나 | 기다림 | 안 기다림 | 안 기다림 | 안 기다림 |
| 새로 생기는 것 | 없음 | 잠금 하나, 잠금 순서 규칙 | 스레드 수명, 채널, `'static` 경계 | 조건 변수, 대표 넘기기 규칙 |
| #28(그룹 커밋) 얹기 | 구조를 다시 짜야 함 | D를 더 얹어야 함 | **바구니에 쌓인 요청을 한꺼번에 꺼내면 끝** | 그 자체가 그룹 커밋 |
| 커밋 하나의 추가 비용 | 없음 | 없음 | 스레드 넘김(수 µs) | 없음 |
| 이슈·ADR 문구와 | 다름 | 다름 | **같음** ("커밋 담당 스레드", "커밋 대기열") | 다름 |
| 쓰는 곳 | SQLite(쓰기 잠금) | — | 많은 DB의 WAL writer, Java 단일 스레드 executor | RocksDB write thread, MySQL binlog group commit |

**실제로 어디서 틀어지나**

- **A**: 완료 조건 "트랜잭션 실행은 서로 막지 않는다"를 못 지킨다. 위 0절 표 그대로다.
- **B**: #15만 보면 가장 작다. 하지만 두 잠금을 잡는 순서를 어기면 교착(deadlock)이 생기고, #28에서 결국 D의 대표 넘기기를 얹어야 한다. D는 "대표가 sync하는 동안 들어온 커밋은 다음 대표를 기다린다"를 조건 변수로 맞춰야 해서 틀리기 쉽다(놓친 깨움, 대표 없는 줄).
- **C**: 커밋 로직 전체가 **스레드 하나 안에서 순서대로** 돈다. 커밋끼리 경쟁이 없으니 잠금 규칙도 없다. 대신 스레드를 만들고, 멈추고, 패닉을 다루는 일이 생긴다(5절). 커밋마다 스레드를 한 번 건너는 비용은 sync(수 ms)에 비하면 작다.

**C에서 커밋 하나의 순서** (#15. #28은 이것을 여러 개 묶는다)

| 단계 | 누가 | 잠금 | 무엇 |
|---|---|---|---|
| 1 | 손님 스레드 | 없음 | 쓰기가 비었으면 여기서 끝(지금과 같음). 아니면 `(쓰기, 스냅샷 번호, 응답 통로)`를 요청 채널에 넣고 기다림 |
| 2 | 커밋 스레드 | 없음 | 엔진이 멈췄으면 `Stopped`로 답함 |
| 3 | 커밋 스레드 | `committed` 잠깐 | 칠판으로 충돌 확인. 충돌이면 `Conflict`로 답함 |
| 4 | 커밋 스레드 | 없음 | 자기가 쥔 최신 트리를 복제해 고침. WAL에 쓰고 **sync** |
| 5 | 커밋 스레드 | `committed` 잠깐 | 칠판에 키 기록 → 새 트리 바꿔 끼우기 (설계 0016 Y2 순서 그대로) |
| 6 | 커밋 스레드 | 없음 | `Ok`로 답함. WAL이 길면 정리 |

- 칠판에 쓰는 것은 커밋 스레드뿐이다. 그래서 3과 5 사이에 잠금을 놓아도 그 사이에 남이 같은 키를 기록할 수 없다. 그 사이에 `begin`한 트랜잭션은 이 커밋 전 트리와 번호를 받으므로, 같은 키를 쓰면 나중에 정확히 충돌한다.
- 새 트리는 **sync가 끝난 뒤에** 보인다. 디스크에 없을 수도 있는 값을 남이 읽는 일이 없다.
- WAL과 데이터 파일은 커밋 스레드만 만진다. 그래서 `wal`의 `Mutex`는 없어지고, `checkpoint()`·`close()`도 채널로 보내는 요청이 된다. 정리하는 동안에도 `begin`은 막히지 않는다.

**추천: C.** 이슈와 ADR이 이미 이 모양을 말하고, #28이 "바구니를 한 번에 비우기"로 가장 작게 얹힌다. 커밋 쪽 코드가 한 스레드 안의 순서 있는 코드로 남아 리뷰와 장애 실험이 쉽다. 리더-팔로워(D)는 스레드 넘김 비용이 벤치마크에서 문제로 보일 때 다시 본다.

## 2. 트리 `RwLock`이 아직 필요한가 (C2)

ADR 0006은 "트리 전체를 `RwLock` 하나로"였다. 그 뒤 #17에서 `Mutex<Arc<Tree>>`로 바뀌었고, #25부터 트랜잭션은 자기 `Arc<Tree>`를 쥐고 **잠금 없이** 읽는다. 잠금이 지키는 것은 "트리 `Arc` 바꿔 끼우기"와 "칠판"뿐이다.

| | **`Mutex<Committed>`를 잠깐만** | `RwLock<Committed>` | 잠금 없는 바꿔 끼우기(`arc-swap` 크레이트) |
|---|---|---|---|
| `begin` | 잠깐 잡음 | **쓰기 잠금**이 필요함: 칠판에 "열림"을 세기 때문 | 트리는 잠금 없이, 칠판은 따로 잠금 → 둘의 짝이 어긋날 수 있음 |
| 얻는 것 | 단순, 지금 코드 그대로 | 없음 (읽기 전용 경로가 없다) | 잠금 몇십 ns |
| 잃는 것 | 커밋·`begin`이 아주 짧게 겹칠 수 있음 | 복잡함만 늘어남 | 크레이트 하나, 스냅샷과 번호 짝(설계 0016) 깨질 위험 |

**추천: RwLock 없이 지금 `Mutex<Committed>`를 그대로 두고, 잡는 시간만 짧게 한다**(1절 3·5단계). ADR 0006에 "트리 RwLock → 짧은 Mutex"를 구현 메모로 남긴다. 결정 자체(실행은 동시에, 커밋은 한 줄)는 바뀌지 않는다.

## 3. 결과를 어떻게 기다리나 (C3)

요청을 보내는 통로(손님 여럿 → 직원 하나)와 답을 받는 통로(직원 → 그 손님 하나)가 필요하다.

| | **`std::sync::mpsc` 채널** | `Mutex` + `Condvar` 칸 | `thread::park`/`unpark` + 칸 | `crossbeam-channel` 등 크레이트 |
|---|---|---|---|---|
| Java로 치면 | `BlockingQueue` / `CompletableFuture` | `wait()`/`notify()` | `LockSupport.park` | 외부 라이브러리 |
| 코드 | 가장 짧음. 상대가 사라지면 `RecvError`로 알려 줌 | 놓친 깨움·가짜 깨움을 직접 다룸 | 같은 문제 + 칸 관리 | 짧음 |
| 성능 | Rust 1.67부터 std 채널은 crossbeam 구현을 가져왔다 (`Sender: Sync`는 1.72부터) | 비슷 | 비슷 | 비슷 |
| 의존성 | 없음 | 없음 | 없음 | 하나 늘어남 |

- 요청 통로: `mpsc::channel()` 하나. `Sender`는 `Sync`라서 `Db` 안에 하나 두고 여러 스레드가 함께 쓴다.
- 응답 통로: 커밋마다 `mpsc::sync_channel(1)` 하나(일회용 번호표). 할당이 커밋마다 한 번 생기지만 sync 비용에 묻힌다.
- #28: 직원이 `recv()`로 하나를 받은 뒤 `try_recv()`로 바구니를 비우면 한 묶음이 된다. 묶음 전체에 같은 `OutcomeUnknown`을 돌려주는 것도 `Error`가 이미 `Clone`(설계 0012)이라 쉽다.

**추천: std `mpsc`만 쓴다.** 새 크레이트는 넣지 않는다. 더 빠른 것이 필요하다는 숫자가 나오면 그때 바꾼다.

## 4. 여러 스레드에서 `Db` 나눠 쓰기 (C4)

| | **`Txn<'db>` 유지, 공유는 `&Db`·`Arc<Db>`** | `Db`를 안에서 `Arc`로 감싸 `Clone` 가능한 핸들로 | `Txn`이 `Arc<Db>`를 쥐는 소유 핸들 |
|---|---|---|---|
| Java로 치면 | 하나의 `DataSource` 빈을 주입받아 씀 | 같음, 복제가 공짜 | 커넥션이 풀을 붙잡음 |
| `thread::scope` | 됨 (지금 blind 테스트가 이미 그렇게 씀) | 됨 | 됨 |
| `thread::spawn` (접속마다 스레드, #37) | `Arc<Db>`를 넘기고 그 스레드 안에서 `begin` → 됨 | 됨 | 됨 |
| async 태스크가 `.await`를 넘겨 `Txn`을 쥐어야 할 때 | 안 됨 (`'static`이 아님) | 안 됨 | 됨 |
| 바뀌는 API | 없음 | `Db` 타입 의미가 바뀜 | `Txn`, SQL 계층 시그니처 전부 |
| `db.close()` 앞에 열린 `Txn`이 있으면 | 컴파일 오류 (설계 0016이 고른 안전장치) | 런타임에 판단해야 함 | 런타임에 판단해야 함 |

- 커밋 스레드는 `std::thread::spawn`이라 `'static`이어야 한다. 그래서 `Db` 안의 공유 상태(`committed`, `stopped`)는 `Arc<Shared>`로 옮기고, 스레드가 쥐는 파일에는 `Send + 'static`이 필요하다. **`FsFile` 트레이트에 `Send + Sync + 'static`을 붙이는 것을 추천한다.** `Db`에 붙이면 SQL 계층의 `F: Fs` 시그니처가 모두 바뀐다. `StdFile`과 `SimFile`(`Arc<Mutex<Disk>>`)은 이미 만족한다. 테스트의 `RecordingFs`는 `Rc`지만 `Db`는 `F`를 보관하지 않으므로 상관없다.
- `Db: Send + Sync`, `Txn: Send`를 컴파일 시점 단언 테스트로 못 박는다. 나중에 `Rc`나 `RefCell`이 섞이면 바로 깨진다.
- 서버(#37)는 접속마다 OS 스레드를 쓰면 이대로 된다. async로 가면 그때 소유 핸들을 더한다.

**추천: `Txn<'db>`를 유지한다.** 지금 쓰는 곳 모두와 #37의 스레드 방식에 충분하고, "열린 트랜잭션을 두고 닫기"를 컴파일러가 막아 주는 장점(설계 0016)을 지킨다.

## 5. 엔진이 멈출 때, `Db`를 버릴 때 (C5)

**엔진이 멈출 때** (디스크 실패, 설계 0012)

| | **스레드는 살아서 `Stopped`로 답함** | 스레드가 끝나고, 손님이 "채널 닫힘"을 `Stopped`로 바꿈 |
|---|---|---|
| 실패를 만난 커밋 | `OutcomeUnknown` | `OutcomeUnknown` |
| 그 뒤 바구니에 있던 요청 | 하나씩 `Stopped` | 채널이 닫히며 버려짐 → 손님이 `Stopped`로 바꿈 |
| 경로 | 하나 (2단계 확인) | 둘 (정상 응답, 닫힘) |
| #28 | 묶음 전체가 `OutcomeUnknown`, 그 뒤는 `Stopped` | 같음 |

손님 쪽 `check_running`은 지금처럼 요청을 보내기 전에도 한다. 멈춘 엔진에 요청이 덜 쌓인다. 지금의 "잠금을 쥔 뒤 다시 확인"(설계 0012 결정 5)은 "커밋 스레드가 요청을 꺼낸 뒤 확인"이 된다. 같은 보장이다: 실패 뒤에 처리되는 요청은 아무것도 쓰지 않는다.

**`Db`를 버릴 때**

- `Db`의 `Drop`이 요청 `Sender`를 버린다 → 커밋 스레드의 `recv()`가 끝을 알고 나온다 → `Drop`이 `join`한다.
- 이때 **처리 중인 요청은 있을 수 없다.** 커밋하는 손님은 `Txn<'db>`로 `&Db`를 빌린 채 답을 기다리므로, 그동안 `Db`를 버리는 코드는 컴파일되지 않는다.
- `close(self)`는 정리 요청을 보내고 답을 받은 뒤 버린다. 지금과 같이 실패하면 `Io`.
- 버리기는 지금처럼 정리하지 않는다. 다음 열기가 WAL을 재생한다.

**커밋 스레드가 패닉하면** (버그일 때만)

| | **손님도 패닉** | `Error`로 바꿔 돌려줌 |
|---|---|---|
| 지금과 비교 | 지금은 커밋 중 패닉이 그 손님 스레드에서 터진다. 같은 결과 | 새 오류 종류가 필요함 |
| 그 뒤 | 요청 채널이 닫혀 모든 커밋이 패닉 | 엔진 멈춤으로 처리 |

추천은 손님도 패닉. 응답 통로가 답 없이 닫히면 "커밋 스레드가 죽었다"는 메시지로 패닉한다. `Drop`의 `join` 결과는 무시한다(되감기 중 두 번째 패닉 방지).

**추천: 멈춰도 스레드는 살아서 `Stopped`로 답하고, `Drop`에서 채널을 닫고 join한다.**

## 6. 테스트 계획 (C6)

| 테스트 | 무엇을 | 왜 결정적인가 |
|---|---|---|
| **sync 문** (`SimFs`에 테스트용 훅 추가) | 커밋 A가 sync 안에 붙잡힌 것을 훅이 알려 주면, 다른 스레드가 `begin`·`get`·`scan`·`put`·롤백·읽기 전용 트랜잭션 끝내기·`page_count`를 모두 마친다. A는 문을 연 뒤에야 `Ok` | 잠과 시간에 기대지 않는다. "A가 sync 안에 있다"를 훅이 보장한다. 막히면 테스트가 멈추므로 감시 스레드가 `recv_timeout`으로 실패시킨다(시간은 실패를 알리는 데만 씀) |
| sync 문 + 두 번째 커밋 | A가 붙잡힌 동안 커밋 B는 끝나지 않는다. 문을 열면 A, B 순으로 WAL에 있다 | "커밋은 순서대로" 완료 조건 |
| sync 문 + 아직 안 보임 | A가 sync 안에 있는 동안 새로 `begin`한 트랜잭션은 A의 값을 못 본다 | 디스크보다 먼저 보이지 않음 |
| 여러 스레드 모델 테스트 (proptest) | 스레드마다 자기 키 접두사로 무작위 put·delete·scan·커밋·롤백. 끝의 DB = 스레드별 모델의 합. 다시 열어도 같음 | 결과가 실행 순서와 무관하게 정해지도록 키를 나눈다 |
| 겹치는 키 (blind 테스트 확장) | 카운터 증가가 잃어버린 갱신 없이 정확히 `스레드 × 횟수` | 이미 있는 테스트가 커밋 스레드 위에서도 통과 |
| 여러 스레드 + 디스크 실패 | 실패를 만난 커밋 하나만 `OutcomeUnknown`, 그 뒤 모두 `Stopped`, 실패 뒤 `Ok`는 없음. 다시 열면 `Ok` 받은 커밋은 다 있음 | `SimFs::fail_after` |
| 기존 테스트 전체 | 모든 커밋이 커밋 스레드를 지나므로, 한 스레드 테스트도 그대로 새 경로를 시험한다 | 손님은 답을 받을 때까지 기다리므로 한 스레드 테스트의 순서는 변하지 않는다 |
| `Send`·`Sync` 단언 | `Db<StdFs>`, `Db<SimFs>`가 `Send + Sync`, `Txn`이 `Send` | 컴파일 시점 |

`loom`(모든 실행 순서 검사, 스펙 사용자 이야기 50)은 std 채널과 OS 스레드를 그대로 다루지 못해 이번 범위 밖이다. 커밋 쪽이 스레드 하나 안의 순서 있는 코드라서 검사할 경쟁이 `committed` 잠금 두 곳뿐이다.
