# B+Tree vs LSM-Tree: 정리 방식의 차이와 탐색 시간복잡도

> Oakdb 학습 노트 #1 (2026-10-09). 저장 구조를 고르기 전에 두 방식의 차이를 정리했다.

## 한 줄 비유

- **B+Tree**: 도서관 책장. 새 책이 오면 **항상 제자리를 찾아 바로 꽂는다.** 찾을 때 빠르지만, 꽂을 때마다 책장을 뒤적여야 한다.
- **LSM-Tree**: 새 책은 일단 **책상 위 바구니**(memtable, 메모리)에 넣는다. 바구니가 차면 정렬해서 **상자**(SSTable, 디스크의 불변 파일)에 담아 창고에 쌓는다. 상자가 많아지면 **몰아서 합친다**(compaction). 넣기는 빠르지만, 찾을 때는 바구니와 여러 상자를 확인해야 할 수 있다.

## 구조 비교

| | B+Tree | LSM-Tree |
|---|---|---|
| 쓰기 | 해당 페이지를 찾아 **제자리 수정** | 메모리에 쓰고, 나중에 **순차적으로** 디스크에 내림 |
| 읽기 | 루트에서 리프까지 한 경로 | 메모리 → 작은 레벨 → 큰 레벨 순으로 확인 |
| 디스크 파일 | 계속 수정됨 | 한 번 쓰면 수정 안 함(불변) |
| 강점 | 읽기, 범위 조회 | 쓰기 처리량 |
| 대표 | PostgreSQL, MySQL InnoDB | RocksDB, LevelDB, Cassandra |

## 탐색 시간복잡도

기호: N = 전체 키 개수, B = 한 페이지에 들어가는 키 개수, L = LSM 레벨 수, k = 범위 조회 결과 개수.

### B+Tree

- 모든 리프가 같은 깊이에 있는 균형 트리이고, 탐색·삽입·삭제가 O(log n)이다 ([CMU 15-445 Lecture #08 노트](https://15445.courses.cs.cmu.edu/fall2022/notes/08-trees.pdf)).
- 디스크 I/O로 세면 트리 높이만큼 페이지를 읽는다: **O(log_B N)**. B가 수백이라 높이는 보통 3~4 정도로 아주 낮다. *(높이 수치는 일반적인 추정이며 위 출처의 직접 인용은 아니다.)*
- 범위 조회: 시작 키까지 내려간 뒤 연결된 리프를 따라 읽는다: **O(log_B N + k/B)**.

### LSM-Tree (leveled compaction 기준)

- 레벨 수 L은 **O(log_T(N·E / M_buf))** 이다. T는 레벨 간 크기 비율, E는 항목 크기, M_buf는 메모리 버퍼 크기다 ([Dayan et al., Monkey](https://nivdayan.github.io/monkey-journal.pdf)). 즉 데이터가 T배 늘 때마다 레벨이 하나 는다.
- **점 조회**: 버퍼(메모리)에서 시작해 작은 레벨부터 큰 레벨로 내려가며, 처음 찾은 값에서 멈춘다. 더 오래된 레벨의 같은 키는 덮어써진 값이기 때문이다 (같은 논문).
  - 각 레벨의 페이지별 최소/최대 키(fence pointer)를 메모리에 두므로 레벨마다 페이지 1개만 읽으면 된다 (같은 논문). → 최악 **O(L)** 번의 디스크 읽기.
  - **없는 키를 찾을 때가 가장 비싸다**: 모든 레벨을 다 확인해야 한다 (같은 논문).
  - **Bloom filter**가 이를 해결한다. "이 파일에 이 키는 확실히 없다"를 메모리에서 판정해 디스크 읽기를 건너뛴다. 키당 약 10비트면 오탐률 약 1%다 ([RocksDB Bloom Filter 위키](https://github.com/facebook/rocksdb/wiki/RocksDB-Bloom-Filter)). → 실제로는 **디스크 읽기 약 1번 + 작은 오탐 비용**.
- **범위 조회**: 레벨마다 한 번씩 찾아 들어간 뒤(L번) 겹치는 범위를 병합하며 읽는다 (같은 논문). → **O(L + k/B)**. Bloom filter는 범위 조회에는 도움이 안 된다.

### 한눈에

| 연산 | B+Tree | LSM (Bloom filter 없음) | LSM (Bloom filter 있음) |
|---|---|---|---|
| 있는 키 조회 | O(log_B N) | O(L) | 약 1번 + 오탐 |
| 없는 키 조회 | O(log_B N) | O(L), 가장 나쁨 | 거의 0번 + 오탐 |
| 범위 조회 | O(log_B N + k/B) | O(L + k/B) | O(L + k/B) |

## Oakdb에 주는 의미

- LSM은 쓰기가 빠른 대신 읽기에 "레벨 수만큼"의 비용이 붙는다. 그래서 **Bloom filter와 compaction(레벨 수 관리)** 이 읽기 성능의 핵심이 된다.
- 없는 키 조회는 모든 레벨을 봐야 해서 가장 비싸다. Bloom filter가 이 비용을 거의 없애 주지만, 범위 조회에는 도움이 안 되므로 레벨 수 자체를 compaction으로 관리해야 한다.
