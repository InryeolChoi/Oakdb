# 0028. 서버 정상 종료 — 회고

이슈 #38 (티켓 26). 설계는 `docs/design/0028-graceful-shutdown.md`. 사용자는 Q1~Q13을 모두 추천안대로 정했고, 바꾼 것은 하나다: "서버 종료 중" 코드를 `0x48`이 아니라 **`0x49`** 로. 티켓 25(PR #82)가 `0x48`을 트랜잭션 밖 노는 시간 초과에 먼저 썼기 때문이다. 이 티켓은 #82 위에 지었다.

## 만든 것

- **신호 스레드** (`oakdb-server/src/signal.rs`, `#[cfg(unix)]`): `oakdb serve`가 `Db::open`보다 먼저 SIGINT·SIGTERM을 `pthread_sigmask`로 막고, 전용 스레드가 `sigwait`로 받는다. 첫 신호는 `ShutdownHandle::shutdown()`, 두 번째는 `process::exit(128 + n)`(130/143). `libc`만 쓰고, `unsafe`는 마스크 걸기와 `sigwait` 두 곳.
- **`ShutdownHandle`과 `Shutdown` 보고** (`server.rs`): `Server::run(self) -> Shutdown`. 손잡이는 `server.shutdown_handle()`로 받거나, 신호가 `Db::open` 도중에 와도 잃지 않도록 `ShutdownHandle::new()`로 먼저 만들어 `Server::bind_with`에 넘긴다. 보고에는 접속 수, 열린 트랜잭션 수, `0x49`로 닫은 접속, 롤백 수, 시간 안에 안 끝난 접속, 체크포인트 결과, 걸린 시간이 들어 있다.
- **종료 순서**: 깨우기 손님(자기 listener에 루프백 접속) → accept 스레드가 플래그를 보고 루프를 나옴 → 대기열 손님에 `0x49` → listener 닫기 → 접속 스레드들이 100 ms 틱에 플래그를 봄 → 트랜잭션 밖이면 바로, 안이면 유예 뒤 롤백하고 `0x49` → 모두 끝나면 `Arc::try_unwrap`으로 `Db`를 꺼내 `close()`(마지막 체크포인트).
- **옵션**: `--shutdown-grace <초>`(기본 10, 0이면 바로 롤백). 여유 시간 5초는 상수. `--help`에 종료 코드 표.
- **`Config`는 `#[non_exhaustive]`**: 사용자 결정. 티켓마다 필드가 늘기 때문이다. 크레이트 밖에서는 구조체 식(`Config { port: 0, ..Config::default() }`)을 아예 쓸 수 없게 되어(E0639), `Config::default().with(|c| c.port = 0)`를 더했다. 테스트·예제의 24곳을 이 모양으로 바꿨다. `Shutdown`도 같은 이유로 `#[non_exhaustive]`.
- **`Monitor`는 `Weak`를 든다**: 테스트가 들고 있는 `Monitor`가 `Arc<Shared>`를 쥐고 있으면 `try_unwrap`이 영원히 실패해 마지막 체크포인트를 못 한다. 서버가 끝난 뒤에는 0을 읽는다.
- **CLI**: `0x49`를 받으면 `ERROR 0x49 server is shutting down`, 트랜잭션 중이었으면 "the open transaction was rolled back", 종료 코드 1. `0x49`가 답한 `COMMIT`은 실행되지 않았으므로 "커밋되었을 수도"가 아니라 "롤백"이라고 말한다.
- **문서**: `docs/protocol.md` 2-4절(종료 때 받는 것, 약속 셋, 종료 코드)과 코드 표 한 줄. ADR 0010·0003에 구현 메모.
- **테스트**:
  - 프로세스 안 시나리오 14개 (`tests/shutdown.rs`): 노는 접속, 문 닫힘, HELLO 전, 대기열 손님, `run` 전에 당긴 손잡이, 유예 안의 `COMMIT`, 유예 초과 롤백, 유예 0, `0x49` 뒤 보낸 문장은 실행 안 됨, 클라이언트의 트랜잭션 상태, `hold_syncs`로 붙잡은 커밋, 끝나지 않는 sync(여유 초과), 멈춘 엔진, `Monitor`가 닫기를 막지 않음.
  - 실제 신호 5개 (`tests/signal.rs`): SIGTERM·SIGINT → 0 + 바로 다시 띄우기 + WAL 20바이트, 두 번째 SIGTERM → 143, 두 번째 SIGINT → 130, 부하 중 SIGTERM 5라운드("응답 없는 끊김 0").
  - CLI 2개, 통신 규칙 1개 확장.

## 배운 것

- **신호 처리기를 안 쓰는 길이 가장 단순했다.** ft_malloc에서 처리기 안의 `malloc`이 잠금을 다시 잡는 그림을 떠올리면, "처리기에서 할 수 있는 일"을 지키는 것보다 처리기를 없애는 편이 낫다. 신호를 막아 두고 `sigwait`로 "평범한 함수의 반환값"으로 받으니, 신호 스레드에서 `eprintln!`도, 잠금도, 소켓 접속도 자유롭다. 대가는 하나: **마스크는 스레드가 태어날 때 물려받는다.** 그래서 `Db::open`(커밋 스레드가 태어나는 곳)보다 먼저 걸어야 한다. 부하 중 SIGTERM 100번이 모두 exit 0이었던 것이 이 순서의 증거다. 순서를 바꾸면 가끔 커밋 스레드가 신호를 받아 프로세스가 기본 동작으로 즉사한다.
- **"블로킹 accept를 깨우는 표준 방법"은 없다.** 다른 스레드에서 listener를 닫는 것은 Linux와 macOS가 다르게 동작한다. 자기 자신에게 접속하는 "깨우기 손님"이 평소 경로를 한 줄도 안 바꾸면서 두 OS에서 같았다. 깨어난 accept가 **받은 소켓보다 플래그를 먼저** 봐야 깨우기 손님이 자리를 차지하지 않는다.
- **macOS의 논블로킹 상속은 실제로 밟을 뻔했다.** 대기열을 비우려고 listener를 논블로킹으로 바꾸면, macOS에서는 거기서 받은 소켓도 논블로킹이 된다. 그대로 `0x49`를 보내고 linger하면 읽기가 바로 `WouldBlock`으로 끝나 소켓이 닫히고, 클라이언트는 `0x49` 대신 리셋을 볼 수 있다. 설계에 적어 둔 함정이라 받은 소켓마다 `set_nonblocking(false)`를 넣었다.
- **`Arc::try_unwrap`은 "모두 놓았나"를 컴파일러와 함께 센다.** `Db::close(self)`가 `self`를 가져가므로 누군가 `Db`를 빌리고 있으면 부를 수 없다. 이것이 "큐에 남은 커밋이 없다"는 보장이 되지만, 반대로 **`Monitor` 하나**가 `Arc`를 쥐고 있어도 닫기가 막힌다. 테스트를 쓰다 이것을 알아 `Monitor`를 `Weak`로 바꿨다. Java로 치면 `WeakReference`로 든 관찰자다.
- **"응답 없이 끊김 0"은 서버 혼자 지키는 약속이 아니다.** 처음 짠 테스트 둘이 실패했다. 손잡이를 당긴 **직후** 보낸 문장이 실행되어 `AFFECTED`가 왔기 때문이다. 버그가 아니다. 접속 스레드는 틱(100 ms) 사이에 잠들어 있다가 그 문장의 첫 바이트로 깨어났고, 플래그를 보기 전에 도착한 문장은 "실행 중인 문장"이다. 약속은 "응답이 온 문장은 실행됨, `0x49`가 답한 문장은 실행 안 됨"이지 "신호 뒤의 문장은 실행 안 됨"이 아니다. 테스트를 "접속이 닫힌 뒤 보낸 문장"으로 고쳤다. 이 구분을 protocol.md 2-4절에 그대로 적었다.
- **틱은 공짜가 아니다.** 512개가 놀 때 코어 하나의 4.5%. 설계가 "측정이 나쁘면 250 ms"라고 남겨 둔 것이 옳았다. 이번에는 100 ms를 그대로 두고 숫자만 남긴다.

## 아쉬운 것

- **테스트 먼저가 아니었다.** 이번에는 구현(`server.rs`, `main.rs`, `signal.rs`)을 먼저 쓰고 바로 뒤에 테스트를 썼다. 테스트 둘이 처음에 실패한 것(위의 "응답 없이 끊김" 이야기)은 테스트 쪽의 잘못이었고, 구현 쪽을 잡아낸 실패는 없었다. 그래서 "테스트가 구현을 잡을 수 있나"를 따로 확인하지 못했다. 리뷰의 변이 검사가 그 대가를 보여 줬다: 14개 중 3개(M6·M11·M14)가 살아남았다. **다음 티켓부터는 실패하는 테스트를 먼저 커밋해 이력에 남긴다**(결정 D6). 아래 리뷰 수정이 그 첫 번째다.
- **Linux의 숫자가 없다.** 장애 실험과 측정은 macOS에서만 돌렸다. Linux는 CI의 `tests/signal.rs`(5라운드)가 같은 불변식을 본다.
- **멈춘 엔진 실험은 프로세스 안에서만** 했다. 실제 프로세스에 디스크 실패를 일으킬 도구가 없다.
- **linger가 종료를 늘린다.** `0x49`를 보낸 뒤 클라이언트가 소켓을 닫지 않으면 접속마다 최대 1초를 기다린다(벤치마크 0012에서 1.14초). 유예 10초 + 여유 5초 안이라 문제는 없지만, 닫지 않는 클라이언트가 많으면 종료가 1초 늦어진다.

- **D2의 세 변이는 모두 "바깥에서 순간을 고정"해야 잡혔다.** M14(롤백 전에 `0x49`)는 "`0x49`를 읽은 그 순간, 소켓을 닫지 않은 채 열린 트랜잭션 수를 본다"(티켓 25의 `0x47` 테스트와 같은 모양). M6(macOS 논블로킹 상속)은 "`0x49`를 받은 **뒤에** 바이트를 더 보낸다": linger가 기다리지 않으면 닫힌 소켓에 쓰게 되어 macOS에서 `BrokenPipe`. 리뷰가 "HELLO를 미리 보내도 살아남았다"고 한 것은 이미 도착한 바이트는 linger가 읽어 버리기 때문이었다. M11(HELLO와 READY 사이의 플래그)은 HELLO의 첫 바이트를 종료 **전에**, 나머지를 **직후에** 보내 그 좁은 창을 만든다. 이 테스트는 D1의 "틱 하나 더" 덕분에 결정적이 되었다.
- **D1을 고치며 설계의 함정 하나를 다시 읽었다.** 설계는 "프레임 중간에 시간 초과로 실패하면 바이트를 잃는다"며 틱을 첫 바이트 전에만 걸었다. 바이트를 잃는 것은 **시간 초과 오류가 `read_exact` 밖으로 나갈 때**다. 시간 초과로 끝난 `read` 한 번은 아무것도 읽지 않았으므로, `Read` 구현 안에서 플래그를 보고 다시 읽으면 잃는 것이 없다. ft_malloc에서 `EINTR`이면 같은 호출을 다시 하던 것과 같은 그림이다. 덤으로 문장마다 읽기 시간 제한을 두 번 바꾸던 호출이 사라졌다(측정 주장은 아님).
- **10회 반복에서 M6 테스트가 2번 리셋으로 실패했다.** 서버 쪽 로그를 찍어 보니 대기열 비우기가 **아무도 못 받았다**(`WouldBlock`, 0명). macOS의 루프백은 연결 맺기를 비동기로 마치므로, 바쁜 기계에서는 `connect`가 돌아온 뒤에도 서버 쪽이 아직 accept 대기열에 없을 수 있다. 그 순간 listener를 닫으면 그 손님은 "문이 닫힌 뒤 온 손님"과 같아 리셋을 본다. 서버의 약속(대기열에 **있는** 손님에게 `0x49`)은 그대로이고, 테스트가 손님을 대기열에 앉힐 시간(100 ms)을 주도록 고쳤다. 같은 모양의 기존 테스트 `clients_waiting_at_the_door_get_0x49_not_a_reset`에도 넣었다.
- **남은 비슷한 구멍**: 큰 결과를 읽지 않는 클라이언트에게 응답을 **쓰는** 쪽은 트랜잭션 밖에서 여전히 제한이 없다(`write` 시간 제한 = 노는 시간 제한). 종료를 유예 + 5초 붙잡을 수 있다는 점은 D1과 같다. 이번 결정 범위 밖이라 고치지 않고 적어 둔다.
