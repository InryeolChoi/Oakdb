# 0002. 삭제와 덮어쓰기: 회고

이슈 #14. 설계는 `docs/design/0002-delete-and-overwrite.md`, 실험은 `docs/experiments/0003-deleted-bytes-on-disk.md`, 벤치마크는 `docs/benchmarks/0002-delete-and-overwrite.md`.

## 만든 것

- `Txn::delete`. 트랜잭션 버퍼에 묘비(`None`)로 남고, 같은 트랜잭션의 `get`에도 바로 반영된다.
- `LeafPage::delete`. 덮어쓰기와 같은 `remove_slot`을 쓰고, 공간은 기존 페이지 정리가 돌려준다.
- 커밋을 "쓰는 키를 모두 뺀 다음 put만 다시 넣기"로 바꿔, 키 순서 때문에 생기던 가짜 `PageFull`을 없앴다.
- 테스트 52개(단위 27, 통합 25). 이번에 12개를 더했다. 그중 하나는 `BTreeMap`과 비교하는 무작위 put/delete 400라운드이고, 중간중간 닫았다 다시 연다.
- 실험 0003: 지운 값이 파일에 남는지 확인했다.
- 벤치마크 0002: `main`과 번갈아 재서 느려지지 않았음을 확인했다.

## 배운 것

**01번에서 미리 한 일이 이번 일을 작게 만들었다.** 덮어쓰기와 페이지 정리가 이미 있었기 때문에, 삭제는 "슬롯을 빼고 조각으로 센다"는 기존 동작(`remove_slot`)을 재사용하는 것으로 끝났다. 공간 재사용 테스트도 처음부터 통과했다. 새로 생각할 것은 페이지가 아니라 **커밋 순서** 쪽에 있었다.

**`BTreeMap`을 순서대로 도는 것은 자연스러워 보여서 함정이었다.** 버퍼가 정렬돼 있으니 앞에서부터 적용하는 게 당연해 보였다. 하지만 "중간 상태가 들어가는가"와 "최종 상태가 들어가는가"는 다른 질문이다. 커밋이 약속하는 것은 최종 상태뿐이므로, 중간 상태가 실패의 원인이 되면 안 된다. 먼저 다 빼고 나서 넣으면, 성공 조건이 "최종 결과가 들어가는가" 하나로 줄어든다.

**무작위 테스트도 판정 기준이 느슨하면 버그를 놓친다.** 키 순서대로 적용하는 코드로 일부러 되돌려 봤더니, 이 경우만 노려서 쓴 테스트는 실패했지만 무작위 400라운드 테스트는 **통과했다.** 무작위 테스트가 "`PageFull`은 언제든 나올 수 있다"고 너그럽게 봐줬기 때문이다. 그래서 "최종 결과가 한 장에 들어가면 커밋은 반드시 성공해야 한다"는 기준을 더했고, 그러자 같은 버그를 라운드 104에서 잡았다. 무작위 테스트의 힘은 입력의 양보다 **판정이 얼마나 정확한가**에서 나온다.

**"안 보인다"와 "없다"는 다르다.** 실험 0003에서 지운 값이 파일에 그대로 남아 있었다. 엔진 API로만 테스트하면 절대 보이지 않는 성질이다. 01번 실험에서 배운 "구조가 말이 되는 것"과 "원래 그 내용인 것"의 차이와 비슷한 교훈이다. 바깥에서 보이는 동작만 테스트하는 원칙은 옳지만, **디스크 바이트를 직접 보는 실험**이 따로 있어야 하는 이유이기도 하다.

**Rust 쪽에서 눈여겨본 점**

- `Option<Vec<u8>>`로 묘비를 표현하니 `get`이 `write.clone()` 한 줄이 됐다. "버퍼에 없음"(`self.writes.get(key)`가 `None`)과 "지웠음"(`Some(None)`)을 타입이 갈라 준다. 따로 `enum Write { Put, Delete }`를 만들지 않아도 됐다.
- 커밋의 두 단계는 `next`라는 복사본 위에서만 일어난다. 그래서 `?`로 어디서 빠져나가도 원본은 그대로다. 01번에서 정한 "복사본을 고치고 마지막에 바꿔 끼운다"는 구조 덕분에, 단계를 하나 늘려도 원자성을 따로 신경 쓸 필요가 없었다.

## 다음 이슈로 넘기는 것

- **지운 값 덮어쓰기 → #22 (WAL)**: 페이지만 0으로 덮으면 WAL 사본에 값이 남으므로, WAL을 설계할 때 둘을 함께 정한다.
- **값을 바꾸지 않는 커밋의 쓰기·sync 생략 → #22 (WAL)**: 없는 키만 지우는 커밋도 지금은 페이지를 쓰고 sync한다. WAL에서 무엇을 로그에 남길지 정할 때 함께 본다.
- **#15 (분할)**: 무작위 테스트의 `fits_in_one_page`는 "한 장짜리"라는 가정에 기대고 있다. 분할이 들어오면 `PageFull` 자체가 사라지므로, 이 판정도 함께 지운다.
- 커밋이 쓰는 키를 모두 뺐다가 다시 넣으므로, 값이 그대로인 덮어쓰기도 셀을 새로 쓴다. 한 장짜리에서는 비용이 작지만, 분할 뒤에는 "같은 값이면 건너뛰기"를 검토할 수 있다.
