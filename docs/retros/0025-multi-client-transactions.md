# 0025. 여러 클라이언트와 접속별 트랜잭션 — 회고

이슈 #37. 설계는 `docs/design/0025-multi-client-transactions.md`. 사용자는 Q1~Q12를 모두 추천안대로 정했다.

## 만든 것

- **접속마다 세션 하나**: 서버의 접속 스레드가 인사(HELLO/READY) 뒤 `Session::new(&shared.db)`를 만들고, 모든 `QUERY`를 그 세션으로 돌린다. 트랜잭션 밖의 문장은 예전처럼 문장 하나가 트랜잭션 하나다. `serve()`가 어떤 길로 끝나든 세션이 `Drop`되어 열린 트랜잭션이 롤백된다.
- **새 오류 코드 셋**:
  - `0x0B` 트랜잭션 상태에 맞지 않는 명령(트랜잭션 중 `BEGIN`, 밖의 `COMMIT`/`ROLLBACK`). 접속 유지, 열린 트랜잭션 그대로.
  - `0x47` 트랜잭션 중 너무 오래 놂. 롤백한 **뒤** 알리고 끊는다.
  - `0x48` 트랜잭션 밖에서 너무 오래 놂. 옵션을 켰을 때만.
- **서버 옵션 셋**: `--idle-in-transaction-timeout <초>`(기본 60, 0이면 없음), `--idle-timeout <초>`(기본 0), `--warn-transaction-age <초>`(기본 300). 초는 소수도 받는다(`0.5`).
- **엔진 `Stats`에 숫자 둘**: `open_transactions`(열린 트랜잭션 수), `kept_commits`(충돌 칠판에 남은 커밋 수). 칠판 잠금을 잠깐 쥐고 읽는다.
- **서버 `Monitor`**: `Server::monitor()`가 돌려주는 손잡이. 서버가 도는 동안 다른 스레드에서 `stats()`와 `connections()`를 읽는다. 테스트가 "끊긴 뒤 열린 트랜잭션이 0으로 돌아왔다"를 숫자로 확인하는 데 쓴다.
- **클라이언트가 상태를 계산**: `oakdb_sql::transaction_command(sql)`이 "이 문장이 세션에서 BEGIN/COMMIT/ROLLBACK으로 읽히나"를 알려 주고, `Client::in_transaction()`이 통신 규칙의 네 줄로 상태를 계산한다. 서버에 묻지 않는다.
- **CLI**: 트랜잭션 중이면 프롬프트가 `oakdb*>`. 서버가 트랜잭션 중에 끊으면 "connection closed by server; the open transaction was rolled back"을 찍고 종료 코드 1. `COMMIT`의 답을 못 받고 끊기면 "커밋되었을 수도, 아닐 수도"라고 따로 말한다. 트랜잭션을 연 채 입력이 끝나면 "롤백된다"고 알린다.
- **문서**: `docs/protocol.md`에 2-1(트랜잭션 규칙과 끊김 표), 2-2(시간 제한), 2-3(트랜잭션 안의 오류 표)절과 코드 세 줄. ADR 0010·0006에 구현 메모.
- **테스트**:
  - 서버 통합 테스트 16개 (`oakdb-server/tests/transactions.rs`): 두 접속 시나리오 5개, 끊김 = 롤백 6가지, 시간 제한 3개, 카운터 1개, 300접속 1개.
  - 모델 비교 속성 테스트 1개 (`oakdb-server/tests/txn_model.rs`): 256개 사례, 접속 3개, 사례마다 최대 47걸음.
  - 패닉 단위 테스트 1개, CLI 테스트 4개, 통신 규칙 테스트 1개(+기존 1개 확장), 엔진 `Stats` 1개, `transaction_command` 1개.

| 확인 | 결과 |

## 배운 것

**ADR 0010이 이 티켓을 위해 내려 둔 결정이 그대로 맞았다.** "접속 하나 = 스레드 하나"로 정할 때의 이유 하나가 "트랜잭션(`Txn<'db>`)이 `Db`를 빌리므로 #37이 수명 문제 없이 풀린다"였다. 실제로 엔진과 SQL 층의 수명은 한 줄도 고치지 않았다. 세션은 접속 스레드의 스택에 태어나 거기서 버려진다. OS로 치면 프로세스가 죽으면 커널이 주소 공간째 회수하는 것처럼, 스레드가 끝나면 Rust가 세션째 정리한다. "롤백을 잊는" 길이 타입에 없다.

**"노는 시간"을 재는 방법이 설계보다 하나 더 필요했다.** 설계는 `set_read_timeout`으로 다음 프레임을 기다린다고 적었다. 그런데 오래된 트랜잭션 경고(5분)를 내려면 기다리는 도중에 한 번 깨어나야 한다. `read_frame`은 깨어나는 순간 이미 길이 칸 몇 바이트를 꺼냈을 수 있어서, 다시 읽으면 프레임 경계를 잃는다. 그래서 첫 바이트는 `BufReader::fill_buf()`로 기다린다. `fill_buf`는 바이트를 버퍼에 채우기만 하고 꺼내지 않으므로, 몇 번을 깨어나도 잃는 것이 없다. 첫 바이트가 오면 그때 `read_frame`으로 프레임을 읽는다. 이 덕분에 "논다 = 다음 프레임의 첫 바이트를 기다리는 시간"이라는 설계의 정의가 코드에 그대로 나타났다.

**롤백 → 알림 → 끊기의 순서가 중요했다.** 시간 초과 때 `0x47`을 먼저 보내고 세션을 나중에 버리면, 클라이언트가 그 오류를 읽자마자 새로 접속해 같은 행을 고칠 때 아직 열린 옛 트랜잭션과 겹칠 수 있다. 그래서 `drop(session)`을 먼저 하고 오류를 보낸다. 실험 2에서 서버가 `0x47`을 보낸 뒤에도 1초(`LINGER`) 동안 접속 수가 줄지 않았는데, 그동안 칠판은 이미 비어 있었다. 이 순서 덕분이다.

**`Config`에 필드를 더하면 외부 코드의 구조체 리터럴이 깨진다.** 눈 가린 테스터가 쓴 `blind_server.rs`가 `Config { port, allow, max_connections }`로 모든 필드를 적고 있어서 컴파일이 깨졌다. `..Config::default()`를 붙여 고쳤다. 공개 설정 구조체는 처음부터 `#[non_exhaustive]`로 두거나 빌더를 쓰는 것이 낫다는 것을 배웠다(Java의 생성자 대신 빌더를 쓰는 이유와 같다). 지금은 고치지 않고 기록만 한다.

**클라이언트의 상태 계산은 파서 전체가 필요했다.** "BEGIN으로 시작하면 BEGIN"이라고 하면 `COMMIT now`(파서가 거절, 서버의 트랜잭션은 열린 채)를 COMMIT으로 오해해 클라이언트만 상태를 잃는다. 그래서 `transaction_command`는 첫 낱말이 셋 중 하나일 때만 문장 끝까지 파서를 돌린다. 16 MiB INSERT라도 첫 낱말에서 멈추므로 비용이 거의 없다. 서버와 클라이언트가 **같은 파서**를 쓴다는 점이 이 규칙(설계 Q3-A)을 안전하게 만든다.

**오래 열린 트랜잭션의 대가는 디스크가 아니라 칠판이었다.** 실험 3-1에서 트랜잭션 하나가 10만 커밋 동안 약 10 MiB(커밋 하나에 약 100바이트)를 붙잡았고, 대부분은 옛 트리 페이지가 아니라 충돌 칠판이었다. PostgreSQL에서는 오래된 트랜잭션이 VACUUM을 막아 표가 디스크에서 부풀고, Oakdb에서는 같은 일이 메모리의 칠판에서 일어난다. 끝나면 칠판은 0으로 돌아왔지만 RSS는 그대로였다. 할당기가 메모리를 바로 돌려주지 않기 때문이다. "숫자가 돌아왔다"와 "메모리가 돌아왔다"는 다른 말이다.

## 남긴 것

- **쓰기 모음 크기 상한 없음**: 트랜잭션 하나가 쌓는 양의 약 1.6배를 서버 메모리에 쓴다. 클라이언트 하나가 서버 메모리를 다 먹을 수 있다(설계 Q6-C). 따로 티켓 감.
- **아주 천천히 흘리는 클라이언트**: 시간 제한은 읽기 한 번마다라, 59초마다 1바이트씩 보내면 못 막는다. 프레임 전체의 마감 시각은 #38(정상 종료) 뒤에.
- **쉬지 않고 문장을 보내는 긴 트랜잭션**: 시간 제한에 걸리지 않는다. 경고 로그와 `Stats`로 보이게만 했다. 숫자가 나쁘면 `--max-transaction-age`(설계 Q7-C).
- **공개 `Config`가 `#[non_exhaustive]`가 아님**: 필드를 더할 때마다 외부의 구조체 리터럴이 깨진다.
- **이력 검사기 재사용(설계 Q10 선택 항목)**: PR #79가 main에 들어왔으므로 0024의 무작위 작업을 `Client`로 돌려 검사기에 넣을 수 있다. 이번에는 접속 3개 모델 비교로 갈음하고 다음 검증 티켓으로 남긴다.
