# 0027. 타입 검사와 오류 종류 — 회고

이슈 #34. 설계는 `docs/design/0027-type-checks-and-errors.md`이고, 결정 E1~E13을 모두 추천안대로 정했다. 주석 지원(E10 C)은 하지 않았다.

## 만든 것

| 무엇 | 어디 | 한 줄 |
|---|---|---|
| 새 칸 `SqlError::NullKey { column }` | `error.rs`, `catalog.rs` | NULL 기본 키는 타입 오류가 아니라 **제약 위반**. 통신 `0x0D` |
| 큰 정수 리터럴 → `Arithmetic` | `parser.rs` | "문장이 깨짐"이 아니라 "값이 범위 밖". 메시지에 줄·칸. 통신 `0x0C` |
| `Type` → `0x09`, `Arithmetic` → `0x0C` | `protocol.rs` | 통신에서 "기타"(`0x1F`)로 가던 두 칸에 제 번호 |
| 네 꼴은 "지원 안 함" | `lexer.rs`, `parser.rs` | `IF NOT EXISTS`, `COUNT(*)` 같은 함수, `t.id`, `--`·`/* */` 주석 |
| 줄·칸 위치 | `lexer.rs` | `syntax error at line 2, column 12: …`. 바이트 `position` 필드는 그대로 |
| `every_kind()` | `error.rs` | 칸마다 오류 하나. 서버 테스트가 "어떤 칸도 `0x1F`로 가지 않는다"를 전수로 확인 |
| 문서 | `docs/protocol.md` 6절 | 묶음·SQLSTATE 대응 열, "INSERT가 `0x20`이면 다시 실행" 한 줄 |

## 배운 것

**타입 검사기는 이미 있었고, 없던 것은 "이름표"였다.** 설계를 쓰며 돌려 보니 타입 검사는 #31·#33·#36이 다 해 두었다. 이번 티켓의 일은 오류를 **분류**하고 그 분류를 **번호**로 옮기는 것이었다. Spring이 SQLSTATE를 `DuplicateKeyException`으로 번역하는 일과 같다. 검사 코드는 거의 안 바뀌고(`check_fits` 한 군데), 바뀐 것은 대부분 "이 오류는 어느 서랍인가"였다.

**같은 오류가 Rust 칸과 통신 번호 두 군데에서 따로 살면, 둘 사이가 새기 쉽다.** `Type`과 `Arithmetic`은 Rust에서는 제 칸이 있었는데 서버의 `match`가 `_ => 0x1F`로 받고 있었다. 컴파일러는 `non_exhaustive` 때문에 이것을 알려 주지 못한다. 그래서 `oakdb-sql` 안에 **catch-all 없는 `match`**(크레이트 안에서는 `non_exhaustive`가 적용되지 않는다)를 두고, 같은 크레이트의 `every_kind()`가 칸을 하나씩 내놓게 했다. 새 칸을 만들면 그 `match`가 컴파일되지 않으니 `every_kind()`에 넣게 되고, 그러면 서버 테스트가 새 칸의 번호를 묻는다. ft_malloc으로 치면 `errno` 값을 새로 만들 때마다 `strerror` 표에도 넣지 않으면 빌드가 깨지게 한 셈이다.

**"지원 안 함"의 경계는 규칙이 아니라 목록이다.** 처음에는 "SQL 키워드면 지원 안 함" 같은 일반 규칙을 생각했지만, 그러면 `SELEC` 같은 오타와 섞인다. 결국 **파서가 알아본 꼴만** 지원 안 함으로 했다. 알아보는 조건을 좁게 잡는 데 시간이 들었다. `t.` 뒤에 `FROM`이 오면(예약어) 그것은 이름 앞의 표가 아니라 오타라서 문법 오류로 남긴다. `if`라는 표 이름은 `IF NOT`이 이어질 때만 `IF NOT EXISTS`로 본다. `--`는 SQL 표준에서 언제나 주석이므로 `a --1`(빼기 음수)도 이제 지원 안 함이다. 띄어 쓴 `- -1`은 그대로 된다.

**테스트의 기대값을 손으로 세면 틀린다.** 줄·칸 테스트의 기대값 하나를 손으로 셌다가 한 칸 틀렸다(빈 줄 뒤의 칸). 또 `'é' = = 1`은 문법 오류일 줄 알았는데, 파서는 그것을 "비교를 이어 씀"(지원 안 함)으로 먼저 알아봤다. 기대값은 코드보다 먼저 쓰되, 틀렸을 때 어느 쪽이 틀렸는지 **매번 따져 본다**. 둘 다 테스트 쪽이 틀렸다.

**옛 눈 가린 테스트가 옛 약속을 지키고 있었다.** 바뀐 종류(`NullKey`, 큰 리터럴) 때문에 테스트 13곳이 깨졌다. 설계가 예상한 10곳보다 많았다(`transactions.rs`, `blind_where.rs`, 서버의 `blind_server.rs` 두 곳). 모두 "당시 스펙대로" 쓴 것이라 지우지 않고 기대값만 바꾸고 `Issue #34 …, was …` 주석을 남겼다. 약속을 바꾸는 티켓은 옛 약속의 증인을 찾아다니는 일이기도 하다.

**실험의 모델도 약속을 지켜야 한다.** 오류 폭탄(실험 0020)이 처음에 "WRONG"을 수십 번 냈다. 원인은 Oakdb가 아니라 모델이었다. 모델은 "행 1이 없으면 `UPDATE t SET id = NULL WHERE id = 1`은 0행"이라고 했지만, Oakdb는 리터럴 NULL 키를 **행을 읽기 전에** 거절한다. 바로 이번 티켓이 굳힌 약속(E1)이다. 속성 테스트도 같은 문제를 안는다. 그래서 타입 모델 테스트는 일부러 모델을 한 줄 망가뜨려(NULL 비교 규칙) 실패하는지 확인했다. 실패했다.

## 검증

| 검증 | 결과 |
|---|---|
| 오류 표 테스트 (`tests/errors.rs`) | 설계 "지금 상태" 표 전부 + 묶음마다 대표, 48문장. 모두 기대한 칸 |
| 타입 모델 속성 테스트 (`tests/type_model.rs`) | 무작위 식 1000개: 모델과 일치, 빈 표 = 찬 표, 통과한 식은 실행 중 타입·`Corrupt` 오류 0 |
| 코드 전수 (`oakdb-server/tests/protocol.rs`) | 칸 26개(엔진 9개 포함). `0x1F`는 `Transaction` 셋뿐(#37 예약), 번호 겹침 없음, `0x0B`·`0x47`–`0x49` 비어 있음 |
| 오류 폭탄 (실험 0020) | seed 6개 × 1만 문장 × 2(서버, 트랜잭션 안): 틀린 답 0, 접속 끊김 0 |
| 전후 벤치 (벤치 0011) | 점 조회·INSERT 차이 없음(측정이 거칠어 ±30% 수준까지만 말할 수 있음) |
| 워크스페이스 테스트 | 936개 모두 통과 |
