# 0024. 동시성 검증 — 회고

이슈 #29. 설계는 `docs/design/0024-concurrency-verification.md`이고, 결정 V1~V13과 작은 질문 Q1~Q9를 모두 추천안대로 정했다. 티켓 16의 후속(#77, 묶음 안에서 진 커밋은 공개 뒤에 답함)이 아직 머지 전이라, 그 브랜치를 먼저 합친 위에서 만들었다.

## 만든 것

- **`oakdb-history` 크레이트**: 엔진을 모르고 장부(이력)만 받는다. 값만 보는 직접 검사(취소·중간값 읽기, 잃어버린 업데이트, 반복 불가능한 읽기, 자기 커밋을 못 봄)를 먼저 하고, 의존 그래프(ww·wr·rw)의 사이클을 Adya 규칙으로 나눈다. rw가 하나인 사이클은 G-single이고, rw가 이어진 사이클은 write skew라서 세기만 한다. 손으로 짠 이력 19개로 위반마다 시험했다. 의존성은 없다.
- **작업 생성기**(`tests/workload`): 키 8개, 덧붙이기 목록, 읽기·덧붙이기·범위 조회, 단계 사이 쉼, 시드 고정(splitmix64 열 줄). 위반이 나오면 장부를 파일로 남긴다.
- **`SimFs::set_sync_delay`**: sync마다 쉬어서, `SimFs`에서도 묶음이 생긴다.
- **`planted-bugs` 기능**: 버그 여섯 개(조회만 최신 트리 읽기까지 일곱 가지). 공개 API(`PlantedBug`, `open_with_bug`)는 기능을 켤 때만 생긴다. 엔진 안의 분기는 일반 빌드에서도 컴파일되지만, 조건이 늘 거짓인 상수라 컴파일러가 최적화로 지운다.
- **`commit_queue` + `crate::sync`**: 커밋 스레드의 대기열을 떼어 냈다. 엔진의 잠금과 채널은 `crate::sync`에서 가져오고, `--cfg loom`이면 loom 것이 된다. loom 모델 세 개를 두었다. CI는 두 OS에서 2·2 모델을 돌리고, `loom.yml`은 손으로 돌린다.

| 검증 | 결과 |
|---|---|
| 손으로 짠 이력 19개 | 위반마다 정해진 이름, write skew는 통과하고 세어짐 |
| 정상 엔진, 4·8스레드 × 시드 20개 | 위반 0, write skew 시드마다 336개 이상, 가장 큰 묶음 4·7 (실험 0016) |
| 심은 버그 6개 | 모두 정해진 이름으로 20/20 (sync 전 공개는 결정적 시나리오) |
| loom 2·2 / 3·3 | 순서 1.3만 개 0.5초 / 1,190만 개 약 15분, 모두 통과. 대기열에 심은 버그 3개는 모두 교착으로 잡힘 (실험 0017) |
| 워크스페이스 테스트 | 828개 모두 통과 |

## 배운 것

**검사기를 믿으려면 검사기가 잡는 것부터 봐야 한다.** "최신 트리 읽기" 버그는 처음에 시드 20개 중 2~8개에서만 잡혔다. 트랜잭션이 몇 µs 만에 끝나니 그 사이에 커밋이 끼어들 일이 없었다. 버그를 심지 않았다면 "위반 0"을 엔진이 맞다는 증거로 읽었을 것이다. 단계 사이에 sync 한 번쯤의 쉼을 넣자 20/20이 됐다. 작업이 약하면 검사기는 거짓으로 안심시킨다. write skew를 세어 "작업이 최소한 이만큼은 만든다"를 함께 보여 주는 것도 같은 이유다.

**값을 잃는 순서는 직관과 반대였다.** 설계 때 버그 5를 "트리 먼저, 키 기록 나중"으로 적었다. 만들어 보니 그 순서는 괜히 충돌을 낼 뿐 값을 잃지 않았다. 늦게 기록된 키가 더 큰 번호를 받기 때문이다. 값을 잃는 쪽은 "번호 먼저, 트리 나중"이다. 새 번호와 옛 사진을 받은 트랜잭션은 옛 값을 고쳐 써도 충돌하지 않는다. 설계 0016이 "키 기록 → 트리" 순서를 정한 이유를, 그 반대를 일부러 만들어 보고 나서야 정확히 이해했다.

**loom은 실제 코드를 돌려야 의미가 있다.** loom의 채널은 "보내는 쪽이 다 사라졌다"를 모른다. 그래서 표준 채널을 그대로 쓰면 `Db`를 버리는 순간이 loom에게는 교착으로 보였다. 모델에서만 다른 채널을 쓰면 loom이 검증한 코드와 실제 코드가 달라진다. 그래서 대기열을 잠금 + 조건 변수로 직접 짜서 둘이 같이 쓰게 했다. 손으로 짠 동시성 코드가 늘었지만, 그 코드는 이제 모든 순서에서 확인된다. Java로 치면 `BlockingQueue`를 직접 구현하고 jcstress 대신 모든 끼어들기를 실행해 본 셈이다.

**순서 수는 정말 폭발한다.** 손님 2명·끼어들기 2번은 1.3만 순서에 0.5초, 3명·3번은 1,190만 순서에 15분이었다. 그림책 1-5의 계산기가 말한 그대로다. 그래서 loom 대상은 작아야 하고, 엔진 전체는 이력 검사기가 맡는다. 두 도구는 역할이 다르다. loom은 작은 부품의 모든 순서를, 검사기는 큰 시스템의 많은 순서를 본다.
