# 0001. 한 장짜리 저장: 회고

이슈 #13. 설계는 `docs/design/0001-single-page-storage.md`, 검증은 `docs/experiments/0001-single-page-storage.md`.

## 만든 것

- 엔진 API: `Db::open` / `open_with(fs, path)`, `begin`, `Txn::get` / `put` / `commit` / `rollback`, `close`
- 4KB 페이지 파일: 메타 슬롯 두 개(페이지 크기 기록) + SQLite 방식 리프 한 장
- 512바이트를 넘는 키 거절(`put`과 `get` 모두), 다른 페이지 크기의 파일 거절, 앞뒤가 안 맞는 페이지 거절
- 덮어쓴 자리를 돌려받는 페이지 정리(compact), 같은 DB를 두 곳에서 여는 것을 막는 잠금
- `Fs` 트레이트에 `create_dir_all` 추가 (새 디렉터리의 sync 책임까지 포함)
- 테스트 40개 (단위 25, 엔진 API 통합 15; 처음 32개에 Merge 전 검증 뒤 8개 추가), 장애 실험 2개

## 배운 것

**"쓰기를 커밋까지 미룬다"는 결정 하나로 많은 것이 공짜가 됐다.** 쓰기를 트랜잭션의 개인 버퍼에만 모으니 롤백은 버퍼를 버리는 것뿐이고, drop하면 자동으로 롤백된다. 커밋도 "페이지 복사본에 다 적용해 보고, 다 들어가면 바꿔 끼운다"라서 `PageFull`일 때 반쯤 적용된 상태가 생기지 않는다. ADR 0006에서 동시성 때문에 고른 구조가, 스레드 하나짜리 첫 단계에서 이미 코드를 줄여 줬다.

**"실패했다"와 "안 됐다"는 다르다.** 처음 `commit`의 문서에 "실패하면 아무것도 반영되지 않는다"라고 썼다. 리뷰에서 틀렸다는 지적을 받았다. `write`는 성공하고 `sync`가 실패하면, 새 페이지가 이미 디스크에 갔을 수 있다. 메모리는 옛 페이지를 들고 있는데 다시 열면 새 값이 보일 수 있다. 결과를 알 수 없는 것이다. 스펙이 "디스크 기록이 실패하면 엔진을 정지하고 '결과를 알 수 없음'을 돌려준다"고 정한 이유를 코드를 쓰고 나서야 실감했다. 지금은 문서에 정직하게 적어 두고, WAL 단계에서 엔진 정지를 넣는다.

**SIGKILL 실험은 생각보다 약한 실험이다.** 프로세스만 죽고 운영체제 캐시는 살아 있으니, `sync`를 통째로 빼먹어도 통과한다. 실험이 "통과"했다는 것보다, 이 실험이 **무엇을 잡을 수 없는지** 아는 게 더 중요했다. 정전을 흉내 내는 가짜 파일시스템(#20)이 왜 필요한지 분명해졌다.

**구조 검사는 체크섬을 대신하지 못한다.** 바이트를 하나씩 뒤집어 보니 머리와 슬롯이 망가진 것은 다 잡혔지만, 값 바이트가 망가지면 틀린 값을 그대로 돌려줬다. "말이 되는 페이지"와 "원래 그 페이지"는 다르다. #19의 체크섬이 그 차이를 메운다.

**손상된 데이터로 패닉이 나면 안 된다.** 리뷰가 `frag_bytes`가 망가진 페이지에서 덮어쓰기를 하면 u16이 넘쳐 패닉이 난다는 것을 찾았다. 읽을 때 검사를 "범위 안에 있는가"에서 "바이트 수가 정확히 맞아떨어지는가"로 강화해 고쳤다. 디스크에서 온 값은 모두 적이 보낸 입력처럼 다뤄야 한다는 것을 다시 배웠다.

**Rust 쪽에서 눈여겨본 점**

- `Db<F: Fs = StdFs>`: 기본 타입 매개변수 덕분에 보통 사용자는 `Db`만 쓰고, 테스트는 `Db<RecordingFs>`를 쓴다. 제네릭이 사용자 코드에 새어 나오지 않는다.
- `Txn<'db>`가 `&Db`를 빌리므로, 트랜잭션이 살아 있는 동안 `db.close()`를 부르면 컴파일이 안 된다. "열린 트랜잭션을 두고 닫기"라는 버그를 타입 검사가 막는다.
- `Mutex`가 독(poison)이 되어도 그대로 쓴다(`PoisonError::into_inner`). 커밋은 복사본을 고치고 마지막에 한 번에 바꿔 끼우므로, 패닉이 나도 페이지가 반쯤 바뀐 상태로 남지 않기 때문이다. 이런 근거가 있을 때만 독을 무시해도 된다.
- `#[non_exhaustive]` 오류 enum: 충돌, 엔진 정지 같은 오류 종류를 나중에 더해도 사용자 코드의 `match`가 깨지지 않는다.

## Merge 전 검증에서 드러난 것과 고친 것

PR #40에서 Merge 전에 다른 AI 셋(규칙 리뷰, 스펙 리뷰, 코드를 보지 않고 약속만 보고 테스트를 쓰는 테스터)을 붙였다. 고친 것:

| 발견 | 고친 방법 | 확인 |
|---|---|---|
| 같은 키를 덮어쓰기만 해도 DB가 영구히 꽉 참 (8바이트 값 311번, 100~149바이트 값 31번이면 `PageFull`, 다시 열어도 그대로) | 새 셀이 안 들어가면 페이지 정리(compact) | 2,000번 덮어쓰기 통과, `BTreeMap`과 비교하는 무작위 2만 번 테스트 통과 |
| 같은 디렉터리를 두 번 열면 한쪽 커밋이 소리 없이 사라짐 | 열 때 데이터 파일에 `flock` 잠금, 이미 잠겨 있으면 `AlreadyOpen` | 같은 프로세스에서 두 번 열기 거절, 닫으면 다시 열림 |
| `get`이 512바이트 넘는 키를 거절하지 않음 | `put`과 같은 검사(`check_key`)를 `get`에도 | 513바이트 `get`이 `KeyTooLarge` |
| 새 DB 디렉터리의 부모를 sync하지 않음 | **고칠 것 없음.** `StdFs::create_dir_all`이 안에서 부모를 sync한다. 테스터의 가짜 `Fs`가 그 안쪽 호출을 볼 수 없어서 생긴 오탐이다. | 코드 확인 |

**"나중 티켓에서 정리"는 그 사이에 무엇이 깨지는지 확인하고 미뤄야 한다.** 처음 회고에서 페이지 정리를 #14로 넘길 때, "공간이 좀 낭비된다" 정도로만 생각했다. 실제로는 카운터 하나를 계속 올리는 것만으로 DB가 영구히 쓰기 불가가 됐다. 자리만 세어 두고 돌려주지 않으면, 한 장짜리 DB에서는 그게 곧 용량이다. 미루기 전에 "미룬 동안 사용자가 평범하게 쓰면 어떻게 되나"를 테스트 하나로 확인했어야 했다.

**코드를 안 본 테스터가 코드를 본 리뷰어보다 이 버그를 잘 잡았다.** 리뷰어 둘은 코드와 회고를 읽고 "02번에서 한다"는 설명에 납득했다. 테스터는 약속("커밋한 값은 다시 읽힌다")만 보고 덮어쓰기를 수천 번 돌렸다. 설명을 읽으면 설명에 끌려간다.

**오탐도 결과다.** 부모 디렉터리 sync 실패는 가짜 `Fs`가 `StdFs`에 일을 넘기면서 안쪽 호출을 놓친 것이었다. 테스터가 틀렸다기보다, "부모 sync가 `create_dir_all` 안에 숨어 있다"는 설계가 밖에서 확인하기 어렵다는 신호다. 정전 실험(#20)의 가짜 파일시스템은 `create_dir_all`도 직접 흉내 내야 한다.

## 다음 이슈로 넘기는 것

- **#14**: 같은 키를 다시 쓰는 것과 페이지 정리(compact)는 이미 된다. #14는 삭제에 집중하면 된다. 삭제한 셀도 `frag_bytes`에 더하면 지금의 정리가 그대로 공간을 돌려준다.
- **#19**: 메타의 `page_size`가 망가지면 "손상"이 아니라 "크기 다름"으로 보고된다. 체크섬 범위가 페이지 크기에 달려 있어서 생기는 문제다. 다른 메타 슬롯과 비교하는 방법을 검토한다.
- **WAL 단계**: 디스크 기록 실패 후 엔진 정지, 새 DB를 만드는 도중에 죽었을 때의 복구.
- 커밋이 `sync` 동안 페이지 잠금을 쥐고 있어서 그동안 읽기가 기다린다. 스레드가 여럿이 되면 다시 본다.
