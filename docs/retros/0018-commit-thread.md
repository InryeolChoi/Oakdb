# 0018. 여러 스레드와 커밋 창구 — 회고

이슈 #27. 설계는 `docs/design/0018-commit-thread.md`이고, 결정 C1~C6과 작은 질문 Q1~Q9는 모두 추천안대로 정했다. ADR 0006에 "#27 구현 메모"를 더했다.

## 만든 것

- **커밋 스레드 `oakdb-commit`**: `Db::open`이 띄운다. WAL과 데이터 파일은 이 스레드만 쥔다. 커밋과 정리(`checkpoint`)는 `std::sync::mpsc` 채널로 들어오고, 하나씩 순서대로 처리된다. 요청마다 응답 채널이 하나씩 있다.
- **sync 동안 잠금을 쥐지 않는다**: 트리·칠판 잠금(`Mutex<Committed>`)은 두 번만 잠깐 잡는다. 충돌을 확인할 때, 그리고 키를 기록하고 새 트리를 바꿔 끼울 때다. 새 트리는 sync가 끝난 뒤에 보인다.
- **`Db`의 `Drop`**: 요청 채널을 닫고 스레드를 `join`한다. 그래서 `Db`를 버리고 나면 파일 잠금이 풀려 있다.
- **`FsFile: Send + Sync + 'static`**: 파일이 커밋 스레드로 넘어가기 때문이다. 이미 있던 파일 타입은 모두 만족해서 고칠 곳이 없었다.
- **`SimFs::hold_syncs`**: sync를 문 앞에 붙잡아 두는 테스트 도구다. `wait_for_sync`는 붙잡힌 sync를 부른 **스레드 이름**도 알려 준다.
- **A/B 하네스**: `commit_time`에 `begin_busy`(남이 계속 커밋하는 동안 읽기 전용 트랜잭션 하나에 걸리는 시간)와 `threads`(4스레드가 동시에 커밋) 모드를 더했다.

| 검증 | 결과 |
|---|---|
| 실패하는 테스트 먼저 | 새 테스트 13개 중 7개 실패. `begin`·트랜잭션 끝내기·`page_count`가 남의 sync를 기다렸고, 커밋은 부른 스레드에서 돌았다 |
| 구현 뒤 | 워크스페이스 테스트 487개 모두 통과. 새 테스트 파일은 15번 되풀이해도 모두 통과 |
| 눈 가린 테스터 | 26개 모두 통과(20번 반복). main에서는 sync 문 없는 17개만 돌 수 있고 모두 통과: 공유는 이미 됐고, 차이는 "막지 않음"뿐이다 |
| 리뷰 | 규칙: 위반 0 · 판단 8 / 완료 조건: 4/5, 부분 1(검증 기록) |
| 변이 검사 | 10개 중 9개 잡음. 1개(M1)는 실패 대신 **멈춤**으로, 1개(M7)는 놓침 → 둘 다 고침 |
| A/B | `begin_busy` 5837 → 0.2 µs **채택**. `overwrite`·`grow`·`threads` 차이 없음. A/A 정상, 다만 `threads`가 불안정 → 고침 |

## 배운 것

**"공유할 수 있다"와 "막지 않는다"는 다르다.** 이 티켓을 시작할 때 `Db`는 이미 `Sync`였다. 눈 가린 테스터도 8스레드 테스트를 돌리고 있었다. 첫 완료 조건은 사실상 이미 충족돼 있었다. 진짜 문제는 잠금 하나가 너무 오래 쥐어진다는 것이었다. 커밋이 fsync를 기다리는 동안, **읽기만 하는 트랜잭션도 끝나지 못했다**(`Drop`이 칠판에서 빠지려고 같은 잠금을 잡기 때문). 한 스레드 테스트로는 이것이 절대 보이지 않는다.

**"안 기다린다"를 잠 없이 시험하는 법.** "B가 A를 기다리지 않는다"는 보통 `sleep`을 넣고 시간을 재서 확인한다. 그런 테스트는 느린 CI에서 흔들린다. 여기서는 sync를 문 앞에 **붙잡아 두는** 도구를 만들었다. "A가 지금 sync 안에 있다"가 확실한 상태에서 B가 끝나야 통과다. 시간 제한은 B가 멈췄을 때 테스트가 끝없이 매달리지 않게 할 때만 쓴다. Java로 치면 `CountDownLatch`로 순간을 맞추는 테스트다.

**스레드 이름 하나가 테스트를 만들어 준다.** "커밋은 커밋 스레드가 처리한다"를 바깥에서 어떻게 확인할까. sync를 부른 스레드의 이름을 문에서 기록하는 것으로 충분했다. 커밋도, 손으로 부른 `checkpoint()`도 `oakdb-commit`에서 sync한다. 이름이 디버거와 `top -H`에서도 보이니 덤으로 얻는 것도 있다.

**잠금을 쪼갤 수 있었던 이유는 "쓰는 사람이 하나뿐"이라서다.** 충돌을 확인하고 나서 잠금을 놓으면, 기록하기 전까지 누가 같은 키를 기록하지 않을까? 칠판에 쓰는 것은 커밋 스레드 하나뿐이라 그럴 수 없다. 그 사이에 시작한 트랜잭션은 이 커밋 앞의 번호를 받으므로 같은 키를 쓰면 나중에 충돌한다. 이 경우도 테스트로 남겼다(`a_transaction_that_began_during_a_commit_conflicts_with_it`). 이 단순함이 커밋 스레드를 고른 가장 큰 이유였다. 커밋하는 스레드가 여럿이었다면 이 추론은 성립하지 않는다.

**Rust 쪽에서 눈여겨본 점**

- **빌림이 종료 순서를 증명해 준다**: `Db`의 `Drop`은 채널을 닫고 `join`할 뿐, "처리 중인 요청"을 따로 다루지 않는다. 커밋하는 쪽은 `Txn<'db>`로 `&Db`를 빌린 채 답을 기다린다. 그러니 그동안 `Db`를 버리는 코드는 컴파일조차 되지 않는다.
- **`PhantomData<fn() -> F>`**: `Db`는 이제 `F::File`을 직접 갖지 않는다. 그래도 `Db<F>`라는 타입은 남겨야 한다. `fn() -> F` 꼴이라서 `F`가 `Sync`가 아니어도 `Db`는 `Send + Sync`다(테스트의 `RecordingFs`는 `Rc`를 쓴다).
- **경계는 트레이트에 한 번**: `Send + Sync + 'static`을 `Db`의 `impl`이 아니라 `FsFile` 트레이트에 붙였다. 그래서 SQL 계층의 `F: Fs` 시그니처가 하나도 바뀌지 않았다.
- **`clippy`와 `&&` 사슬**: `cargo clippy ... | tail`로 출력을 줄였더니, 실패해도 파이프의 종료 코드가 0이라 커밋이 그대로 됐다. 바로 고쳐 다시 커밋했다. 검사는 파이프 없이 돌린다.

## 검증 뒤 고친 것 (PR #67, "추천대로")

| 리뷰 | 무엇을 | 어떻게 |
|---|---|---|
| S8·M1 | 단언이 실패하면 테스트가 멈춤 | sync를 붙잡는 손잡이를 스레드 scope **안에서** 쥔다. 되감기가 손잡이를 버려 붙잡힌 커밋이 풀린다. "sync 전에 트리 공개"를 심으니 0.2초 만에 3개 실패 |
| M7 | 실패한 커밋 뒤에 줄 선 커밋이 WAL에 쓰는지 안 봄 | 줄 선 두 커밋이 `Stopped`를 받고 WAL 길이가 그대로인지 보는 테스트. 커밋 스레드의 멈춤 확인을 빼면 실패 |
| P3 | WAL 순서를 안 봄 | WAL 안에서 첫 커밋의 값이 둘째보다 앞에 있는지 본다 |
| S1·S2·P4 | 커밋 스레드가 패닉하면 그 뒤 커밋이 부른 쪽에서 패닉 | 요청마다 `catch_unwind`. 그 요청은 `OutcomeUnknown`, 엔진은 멈추고 그 뒤는 `Stopped`. `SimFs::panic_at_next_sync`로 시험 |
| S5·S7 | 커밋 함수가 너무 많은 일을 함 | 확인 → 만들기 → 쓰기(sync) → 공개 → 정리로 나눴다. #28은 쓰기와 공개 사이에 sync를 한 번 둔다 |
| S4 | `FsFile`의 `Sync`는 필요 없음 | `Send + 'static`만 |
| S6 | `COMMIT_THREAD`를 왜 공개하나 | 테스트·도구가 스레드를 가려내도록. 문서에 적음 |
| S3 | MSRV 선언 없음 | 리뷰는 1.72(`Sender: Sync`)를 말했지만 `File::try_lock`이 1.89부터라 **1.89**로 선언하고 `cargo +1.89 check`로 확인 |
| A/B | `threads` 모드의 A/A 중앙값이 2822와 4480으로 흔들림 | 스레드마다 10번 데워 두고 장벽에서 같이 출발해 커밋 하나하나의 시간을 재고, 중앙값으로 비교. 8번 돌려 중앙값 11006~11967 µs |

**멈춤으로 잡히는 버그는 잡힌 게 아니다.** 변이 검사에서 "sync 전에 트리 공개"는 테스트를 실패시키지 않고 150초 넘게 멈추게 했다. 붙잡아 둔 sync를 단언이 실패한 뒤에도 쥐고 있었기 때문이다. Rust의 `thread::scope`는 클로저가 패닉해도 안의 스레드를 다 기다린다. 그러니 "되감기 때 풀려야 하는 것"은 scope 안에 두어야 한다.

**리뷰가 적어 준 MSRV도 확인해야 한다.** 리뷰는 `Sender: Sync`만 보고 1.72를 제안했다. 하지만 데이터 파일 잠금에 쓴 `File::try_lock`은 1.89부터다. 실제 도구로 컴파일해 보기 전에는 아무 숫자도 믿지 않는다.

## 다음 이슈로 넘기는 것

- **#28 그룹 커밋**: `Committer::run`에서 `recv()` 뒤에 `try_recv()`로 쌓인 요청을 모아, WAL 쓰기는 각자 하고 sync는 한 번만 한다. 한 묶음 안의 뒤 커밋은 아직 안 보이는 앞 커밋 위에 쌓인다. 커밋 스레드가 최신 트리(`Committer::tree`)를 따로 쥐고 있는 것이 이때 쓰인다. 충돌 확인도 묶음 안의 앞 커밋 키를 함께 봐야 한다.
- **Q6 자동 정리와 응답 순서**: 지금은 정리한 뒤에 응답한다. #28에서 측정한 뒤 다시 본다.
- **스냅샷 격리 검사기(스펙 사용자 이야기 49)와 `loom`(이야기 50)**: 이번 범위 밖이다.
