# 0022. UPDATE와 DELETE — 회고

이슈 #33. 설계는 `docs/design/0022-update-and-delete.md`. 사용자는 U1~U12와 Q1~Q10을 모두 추천안대로 정했다. 그중 U6(기본 키 중복을 문장이 끝난 상태로 검사)은 SQLite·MySQL·PostgreSQL의 기본 동작과 **일부러 다르게** 한 결정이다.

## 만든 것

- **문법**: `UPDATE 표 SET 열 = 식, ... [WHERE 식]`, `DELETE FROM 표 [WHERE 식]`. 식은 0019 파서를 그대로 쓰므로 깊이 제한(200)도 SET 식에 저절로 걸린다. `UPDATE OR ...`, `SET (a, b) = ...`, `DEFAULT`, `FROM`, `RETURNING`, `LIMIT`, `DELETE t`는 "지원 안 함"이다.
- **계획**: `planner::assignments`가 SET 목록을 열 번호와 `Scalar`로 바꾼다. 없는 열, 같은 열 두 번, 타입이 다른 값, 기본 키에 넣는 NULL 리터럴은 행을 하나도 읽기 전에 오류가 된다.
- **실행은 두 단계**:
  - 1단계: `matching`으로 맞는 행을 엔진 키와 함께 모두 모은다. SELECT도 이제 이 함수를 쓴다. 행마다 옛 행에서 새 행을 계산하고, 넘침, 기본 키 NULL, 키·값 길이, 중복 키를 모두 검사한다.
  - 2단계: 쓰기만 한다. 키가 바뀌는 행의 옛 키를 먼저 모두 지우고, 그다음 새 행을 넣는다.
- **영향받은 행 수**: 고른 행 수다. 값이 그대로인 행도 쓰고 센다.
- **테스트 31개 추가**:
  - 통합 테스트 19개 (`tests/update_delete.rs`).
  - 단위 테스트 6개: 파서 3개, 계획 2개, 실행기 충돌 1개.
  - 모델 비교 속성 테스트 2개: INTEGER 키 표와 TEXT 키 표. 각 256개 사례이고, 사례마다 INSERT·UPDATE·DELETE를 최대 7개 이어 돌린다.

## 배운 것

**할로윈 문제는 Rust가 먼저 막아 줬다.** `scan`은 트랜잭션을 공유 빌림(`&`)으로, `put`은 배타 빌림(`&mut`)으로 잡는다. 그래서 "훑으면서 고치기"는 컴파일되지 않는다. Java라면 `ConcurrentModificationException`을 런타임에 만나서야 알았을 문제를 타입 검사기가 미리 알려 준 셈이다. 덕분에 설계 질문이 "어떻게 막을까"에서 "모은 다음 무엇을 할까"로 바뀌었다. `id`가 0~29인 표에 `SET id = id + 10 WHERE id < 30`을 돌리면 행마다 정확히 한 번씩만 옮겨진다.

**"문장이 끝난 상태로 중복 검사"는 생각보다 싸다.** 1단계에서 이미 모든 새 행을 들고 있으므로 집합 두 개면 된다. 하나는 "옮겨 가며 비우는 옛 키", 다른 하나는 "새 키"다. 새 키가 다른 새 키와 겹치거나, 비워지지 않는 자리(고르지 않은 행, 또는 키를 안 바꾸는 행)에 떨어지면 중복이다. 나머지는 2단계의 순서(지우기 먼저, 넣기 나중)가 맞춰 준다. 그래서 연속 키에 `SET id = id + 1`을 해도 처리 순서와 상관없이 성공한다.

**쓰기 전에 모든 검사를 끝내 두면 #35가 가벼워진다.** 지금은 오류가 나면 트랜잭션을 버려서 원자성을 공짜로 얻는다. 하지만 BEGIN 안에서는 트랜잭션을 버릴 수 없다. 2단계에서 실패할 수 있는 것을 엔진 고장뿐으로 줄여 두었으므로, #35는 UPDATE/DELETE 때문에 세이브포인트를 만들 필요가 없다. 행마다 검사하고 바로 쓰는 INSERT에는 이 문제가 아직 남아 있다.

**모델이 먼저 틀렸다.** 첫 모델 실행에서 `UPDATE t SET id = NULL WHERE ...`가 빈 표에서 실패했다. 고친 것은 Oakdb가 아니라 모델이었다. 기본 키에 NULL 리터럴을 넣는 것은 행을 읽기 전에 나는 타입 오류(U8)라서 행이 없어도 오류다. 그런데 모델은 행마다 NULL을 확인했기 때문에 "0행 성공"을 기대했다. 0019에서 정한 "타입 오류는 행 내용과 무관하다"는 약속이 모델에도 들어가야 했다.

**오류 판정의 엄격함을 둘로 나눴다.** WHERE 식의 넘침은 0019처럼 느슨하게 본다. Oakdb는 범위 밖 행을 읽지 않으므로 성공할 수도 있다. WHERE에 오류가 없으면 고른 행이 정확히 정해진다. SET 식에는 AND/OR 같은 지름길도 없다. 그러므로 SET의 넘침, 기본 키 NULL, 중복은 **엄격하게** 모델과 같은 종류여야 하고, 오류 뒤의 표는 문장 전과 똑같아야 한다.

**Rust 쪽에서 눈여겨본 점**

- **`Change<'a>`가 읽은 키를 빌린다**: 1단계의 변경 목록은 `matching`이 돌려준 키를 복사하지 않고 `&[u8]`로 빌린다. 중복 검사의 `HashSet<&[u8]>`도 마찬가지다. 늘어나는 메모리는 새 키와 새 값뿐이다.
- **읽은 키로 지운다**: 행의 기본 키로 키를 다시 만들지 않고, 엔진에서 읽은 키를 그대로 지운다. 망가진 행이 있어도 엉뚱한 키를 지우지 않는다.
- **`apply(&mut Txn, Statement)`로 꺼냄**: `run`이 "시작 → apply → 커밋"이 됐다. 충돌 테스트가 먼저 시작한 트랜잭션 안에서 문장을 돌릴 수 있게 됐고, #35의 BEGIN도 이 함수를 그대로 부를 수 있다.

**뜻밖의 것**

- 블라인드 서버 테스트 파일은 따로 없었다. "UPDATE는 지원 안 함" 줄은 `crates/oakdb-server/tests/server.rs`에 있었다.
- 동시 증가 테스트(스레드 4개 × 25번, 충돌하면 재시도)는 늘 최종값 100으로 끝났다. 갱신을 잃지 않는다는 뜻이다. 다만 충돌이 실제로 났는지는 실행마다 다르다. 그래서 "충돌이 SQL 오류로 온다"는 것은 실행기 단위 테스트에서 결정적으로 확인한다. 먼저 시작한 트랜잭션이 커밋할 때 `Engine(Conflict)`를 받는 것을 본다.

## 다음 티켓에 넘기는 것

- **#34 오류 종류**: 실행 중에 기본 키가 NULL이 되는 경우는 지금 `TypeMismatch { found: None }`다. 이것을 "제약 위반"으로 옮길지 정한다. `Conflict`를 `SqlError`의 독립 종류로 꺼낼지도 정한다.
- **#35 BEGIN/COMMIT**: `executor::apply`를 그대로 쓴다. INSERT의 문장 단위 원자성(설계 0022 Q7)을 같이 정한다.
