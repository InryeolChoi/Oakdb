# 0013. 가짜 디스크: 길이만 닿고 내용은 0인 쓰기 — 회고

이슈 #56. 설계는 `docs/design/0013-length-only-writes.md`, 실험은 `docs/experiments/0012-length-only-writes.md`. 사용자가 자리에 없어 설계의 결정 8개를 추천안으로 진행했고, PR #58 리뷰 뒤 사용자가 확인했다. 결정 1("끝"을 언제 재나)만 리뷰에서 바뀌었다.

## 만든 것

- **새 운명 `Landing::LengthOnly { zeros_from }`**: 정전 때 디스크의 파일 끝을 넘는 쓰기가 "새 길이만 닿음"으로 끝날 수 있다. 끝을 넘는 부분은 0, 안쪽 부분은 디스크에 있던 그대로다. 디스크가 들고 있는 바이트는 0이 되지 않는다(리뷰 뒤).
- **주사위를 늘리지 않음**: "사라짐"을 뽑은 끝 넘는 쓰기의 절반을 같은 주사위의 맨 위 비트로 "길이만"으로 바꾼다. 그 밖의 시드는 예전과 같은 디스크를 낸다.
- **`crash_sim`**: "길이만"·길이 변경의 운명·파일 이름을 찍고, `one`과 `sweep` 모두 체크포인트 도중 정전을 따로 부르고, `sweep`이 "길이만" 시드 수를 센다.
- **테스트**: SimFs 5개, 체크포인트 2개(정전이 20바이트 0 WAL을 직접 만듦), 고정 시드 1개(C16). 고정 시드 9개의 주석을 지금 하는 일로 다시 씀.
- **엔진 코드는 바꾸지 않았다.** 새 고장에서 엔진 버그는 나오지 않았다.

## 배운 것

**고장 모델이 실제보다 험하면, 필요 없는 코드를 "필요하다"고 증명해 준다.** 처음 모델은 "쓸 때 엔진이 본 끝"으로 쟀다. 그래야 C3(비우기 뒤 sync 빼기)가 깨졌고, 나는 그걸 "드디어 C3를 잡았다"로 읽었다. 리뷰(P4)가 짚은 건 그 316건이 모두 **실제 파일 시스템이 만들 수 없는 상태**라는 점이었다. 저널은 자르기와 그 뒤의 늘리기를 순서대로 남기므로, 늘리기만 남고 자르기를 잃는 일은 없다. 나는 "어떤 버그를 드러내야 하나"를 먼저 묻고 그 답에 맞춰 모델을 골랐다. 순서가 거꾸로였다. **모델은 실제를 먼저 따르고, 그 모델에서 잡히지 않는 변이는 "필요 없는 코드일 수 있다"는 신호로 읽어야 한다.**

**잡히지 않는 변이에도 두 종류가 있다.** 0010에서 C3를 놓친 건 "모델이 모자라서"였다. 이번 리뷰 뒤 C3가 살아남는 건 "그 sync가 실제로 지키는 게 없어서"다. 겉보기는 같은 "missed"라서, 그 차이를 경우를 하나씩 따진 표(설계 0013 2절)로 보이고, C3를 심은 채 시점별 테스트와 10만 시드가 0건임을 확인한 다음에야 "예상된 생존"이라고 적었다. 그래도 sync는 싸서 방어용으로 남겼다.

**시드는 공유 자원이다.** 주사위 하나를 더 던지면 그 뒤가 모두 밀려, 지난 실험 세 개의 표와 고정 시드 테스트가 한꺼번에 뜻을 잃는다. 같은 주사위 값의 다른 비트를 쓰니 87%의 시드가 그대로였다. "새 무작위 선택을 더할 때는 기존 선택을 쪼개 쓴다"는 결정적 시뮬레이션의 습관으로 가져간다.

**실험이 이제 리뷰가 찾은 걸 스스로 찾는다.** PR #55의 P1은 사람이 코드를 읽고 찾았다. 이번에 P1 수정을 빼고 정전 실험을 돌리니 10만 중 811시드가 깨졌다. 그동안 "실험 100%"는 엔진이 튼튼해서가 아니라 **디스크가 친절해서**였던 부분이 있었다.

**작업 표의 이름표도 틀릴 수 있다.** `crash_sim one`은 체크포인트 도중 정전을 "while opening"으로, `sweep`은 "cut in a commit"으로 찍고 있었다. 앞의 것은 내가 찾았고 뒤의 것은 리뷰(P3)가 찾았다. 같은 잘못을 한 곳만 고친 셈이었다. 도구의 출력도 검증 대상이고, 고칠 때는 같은 판단을 하는 곳을 모두 찾아야 한다.

**고정 시드의 주석은 시간이 지나면 거짓말이 된다.** 고정 시드 9개의 주석은 WAL 전 설계의 모습을 설명하고 있었는데, WAL부터 연산 순서가 바뀌어 그 모습은 이미 재현되지 않았다(리뷰 P2). `crash_sim one`으로 지금 하는 일을 보고 "예전엔 / 지금은"으로 다시 썼다. C3용으로 고정한 시드 349는 변이가 연산 수를 바꿀 때만 뜻이 있던 시드라 지웠다(리뷰 P1). 시드에 뜻을 붙이는 테스트는 엔진이 바뀔 때마다 그 뜻도 다시 확인해야 한다.

**Rust 쪽에서 눈여겨본 점**

- **enum 변형 하나가 모든 `match`를 찾아 준다**: `Landing`에 변형을 더하자 컴파일러가 `sim.rs`, `crash_sim`, 테스트의 `match`를 전부 짚었다. 실패하는 테스트 커밋에서는 변형만 더하고 `unreachable!`로 막아 두어 테스트가 컴파일은 되고 실행에서 실패하게 했다.
- **`Option::then`으로 "해당할 때만 값"**: `(end > disk_len).then(|| offset.max(disk_len))`가 "끝을 넘는가"와 "어디부터 0인가"를 한 줄에 담는다.
- **`#[non_exhaustive]`**: 공개 `Landing`에 변형이 또 생길 수 있어 붙였다(리뷰 S1). 크레이트 밖의 `match`(테스트, 예제)는 와일드카드 갈래가 있어야 컴파일되고, 크레이트 안은 지금처럼 빠짐없이 검사된다.
- **패턴 가드로 확률 쪼개기**: `0 => match zeros_from { Some(z) if draw >> 63 == 1 => …, _ => Lost }`. 가드가 거짓이면 다음 갈래로 떨어지는 성질 덕분에 "해당 안 되면 예전 그대로"가 코드 모양으로 보인다.
- **저장하지 않고 다시 계산하기**: 처음엔 `Change::Write`에 쓸 때의 길이(`old_len`)를 넣었다. 리뷰 뒤에는 정전 때 디스크 길이(`data.len()`)를 보면 되므로 필드가 사라졌다. 옛 규칙은 필드를 되살리는 여러 군데 치환이라, `mutants.py sim`이 한 버그에 치환 여러 개를 받도록 했다.

## 다음 이슈로 넘기는 것

- **늘어난 자리에 옛 블록 내용이 보이는 경우** (리뷰 뒤에도 그대로): ext4 writeback은 0 대신 쓰레기를 보일 수 있다. 옛 WAL 머리말이 다시 보이는 것 같은 경우를 만든다. 새 이슈 후보.
- **`mutants.py`가 첫 실패 파일에서 멈춤**: cargo 기본 동작이라 `crash.rs`가 잡는지는 보이지 않는다. `--no-fail-fast`로 바꾸면 느려진다. 필요할 때 정한다.
