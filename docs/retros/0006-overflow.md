# 0006. 큰 값: overflow 페이지와 빈 페이지 목록 — 회고

이슈 #18. 설계는 `docs/design/0006-overflow.md`, 결정은 ADR 0009. 검증 결과는 PR #50 코멘트에 있다.

## 만든 것

- **긴 값은 부록으로**: 키 + 값이 1006바이트를 넘으면 값 전체를 overflow 페이지 사슬(장당 4056바이트)에 쓴다. 리프 셀에는 첫 페이지와 길이 12바이트만 남기고, `value_len`의 맨 위 비트로 표시한다. 값은 약 4GiB(u32)까지 받는다.
- **빈 페이지 목록**: 덮어쓰거나 지운 값의 부록, 트리에서 빠진 리프·부모·옛 루트를 빈 페이지 사슬에 넣는다. 새 페이지는 파일을 늘리기 전에 여기서 꺼낸다. 빈 페이지는 0으로 덮어쓴다.
- **열 때 검사 강화**: 모든 페이지가 트리, 값 하나의 사슬, 빈 페이지 목록 중 정확히 한 곳에만 속해야 한다.
- 파일 형식 버전 2. 테스트 93개 → 121개.

| 검증 | 결과 |
|---|---|
| CI macOS · Linux | 통과 |
| 일부러 심은 버그 9개 | 처음엔 8개 잡음 → 테스트를 더해 9/9 |
| 눈 가린 테스터 | 20 통과 / 0 실패 |
| 리뷰 | 버그 1 · 위반 2 · 판단 8 (결정에 따라 버그·위반·작은 정리 반영) |
| 장애 실험 0005 | 긴 값을 쓰거나 지우다 멈추면 9가지 모두 열리지 않음. 틀린 값은 0 |
| A/B | 세 번 잼. 남은 대가: 짧은 `get` +1.7%, 조회 +6% (받아들임) |

## 배운 것

**느려진 이유를 짐작으로 고치면 안 된다.** 처음 A/B에서 짧은 값 `get`이 14% 느려졌다. 나는 "긴 값 때문에 넣은 `Arc` 복제가 짧은 값에도 붙어서"라고 짐작했고, 그걸 고친 뒤 다시 쟀더니 오히려 **19%** 느려졌다. 진짜 원인은 값을 꺼낼 때 셀의 슬롯을 **두 번** 읽는 것이었다. 그걸 고치자 +1.7%로 돌아왔다. A/B를 한 번만 하고 "고쳤다"고 했다면 틀린 설명이 문서에 남았을 것이다. 고칠 때마다 다시 재야 한다.

**`let`으로 다시 선언해도 잠금은 풀리지 않는다.** 긴 값을 읽는 동안 커밋이 기다리지 않게 하려고, 트리의 `Arc`를 복제한 다음 잠금을 놓으려 했다. 그런데 `let tree = Arc::clone(&tree);`는 이름을 가렸을 뿐, 앞의 `MutexGuard`는 함수 끝까지 살아 있었다. 테스트는 모두 통과했고, 리뷰 두 개가 따로따로 찾았다. 재 보니 다른 스레드가 짧은 값 하나를 읽는 데 **최대 4초**를 기다렸다. 잠금을 블록 안에서만 쥐게 고치자 2.25µs가 됐다. Java로 치면 `synchronized` 블록을 나왔다고 믿었는데 아직 그 안에 있었던 셈이다. Rust에서 잠금이 풀리는 시점은 **변수 이름이 아니라 스코프**가 정한다.

**공개 API로는 닿지 않는 코드도 있다.** 변이 검사에서 "`Tree::put`이 덮어쓴 값의 부록을 안 돌림"은 어떤 테스트도 잡지 못했다. 커밋은 쓰는 키를 늘 먼저 지우기 때문에, `Tree::put`이 긴 값을 덮어쓰는 길은 공개 API로 지나갈 수 없었다. 지금은 쓰이지 않는 길이어도, 커밋 순서가 바뀌는 날 바로 공간이 샌다. `Tree`를 직접 부르는 단위 테스트를 더했다.

**엄격한 검사에는 값이 있고 대가도 있다.** "모든 페이지는 정확히 한 곳" 검사 덕분에 "빈 리프를 목록에 안 넣음" 같은 버그를 테스트가 잡았다. 그 대신 긴 값을 지우다 멈추면 공간만 잃는 경우인데도 DB가 열리지 않는다(실험 0005 ③). 곧 올 WAL이 모든 경우를 고치므로 엄격한 쪽을 택했다(결정 2).

**내 예측도 실험으로 확인해야 한다.** 설계를 쓸 때는 "새 페이지에 쓰다 멈추면, 메타가 모르는 페이지라 그냥 무시된다"고 적었다. 실제로는 리프(페이지 2)가 번호 순서상 **가장 먼저** 써져서, 메타가 모르는 새 페이지를 가리키게 됐다. 그래서 DB가 열리지 않았다. 실험 0004의 교훈("순서만으로는 한계가 있다")을 다시 확인했다.

**워크플로에서 지키지 못한 것: 테스트 먼저.** 부록과 빈 페이지 목록의 핵심 구조는 구현을 먼저 하고 테스트를 바로 뒤에 붙였다. 결과적으로 테스트는 충분하고 변이 검사로 확인도 했지만, "테스트가 먼저 실패하는 것을 본다"는 단계를 건너뛰었다. 다음 티켓에서는 실패하는 테스트부터 커밋한다.

**Rust 쪽에서 눈여겨본 점**

- `Value<'a>`는 짧은 값이면 페이지 안의 바이트를 **빌리고**(`&'a [u8]`), 긴 값이면 위치(`OverflowRef`)만 들고 있다. 그래서 짧은 값은 복사 없이 넘기고, 긴 값만 `Cow::Owned`로 모은다. 빌림 검사기 덕분에 "페이지가 바뀐 뒤에도 옛 바이트를 들고 있는" 실수는 컴파일되지 않는다.
- `Option<Option<OverflowRef>>`는 "키 없음"과 "짧은 값을 지움"을 호출하는 쪽이 외워야 구분할 수 있었다. 리뷰를 따라 `Option<Removed>`(`Removed::Inline` / `Removed::Overflow`)로 바꾸니 `if let Some(Removed::Overflow(old))`가 그대로 읽힌다.
- 사슬 순회는 `std::iter::successors`로 하나만 뒀다. 다음 페이지를 **필요할 때만** 읽으므로, 열 때 검사에서 "이 페이지를 확인한 뒤에야 다음을 읽는다"는 순서가 자연스럽게 지켜진다.
- `Page::kind`의 `_ => Kind::Free`를 `unreachable!`로 바꿨다. 알 수 없는 종류는 `from_bytes`가 이미 거르므로 여기 올 수 없다. 조용히 다른 종류로 바꾸는 것보다 "올 수 없다"를 코드로 말하는 편이 낫다.

## 다음 이슈로 넘기는 것

- **#22 (WAL)**: 실험 0005의 9가지 경우를 시험 목록에 더한다. 빈 페이지 목록에 넣을 때마다 한 장씩 쓰는 비용이 WAL에서 얼마나 커지는지 다시 재고, 크면 목록 페이지(트렁크)로 바꾼다.
- **#25 (스냅샷)와 페이지 캐시**: 스냅샷이 아직 읽을 수 있는 페이지는 재사용을 미뤄야 한다. 지금은 모든 페이지가 메모리의 `Arc`라 안전하다.
- **#43**: 기본 파일 형식 ADR은 0010으로 쓴다.
- 스펙 #12의 "넘치는 부분을 overflow 페이지로" 문구는 ADR 0008·0009에 고친 점을 적었고, 이슈 본문은 그대로 두었다.
- 남겨 둔 작은 판단(결정 9): `Page::next`·`data`의 종류 검사는 debug 빌드에서만, `write_overflow`의 버퍼 두 번 만들기, 테스트 전용 `Tree::get`.
