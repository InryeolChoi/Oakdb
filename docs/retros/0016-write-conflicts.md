# 0016. 충돌 판정 — 회고

이슈 #26. 설계는 `docs/design/0016-write-conflicts.md`. 결정 B1~B4는 추천안대로 정했다. #25(스냅샷 읽기) 브랜치 위에 쌓아 만들었다.

## 만든 것

- **칠판 `conflict.rs`의 `Writes`**: 메모리 속 커밋 번호, "키 → 마지막으로 쓴 커밋 번호", 열린 트랜잭션 수. 가장 오래 열린 트랜잭션이 시작하기 전의 커밋은 지운다.
- **트리와 칠판을 한 잠금에**: `Mutex<Committed { tree, writes }>`. `begin`이 받는 스냅샷과 번호가 언제나 짝이 맞는다.
- **`Error::Conflict { key }`**, 그리고 트랜잭션이 끝날 때 칠판에서 빠지는 **`Drop for Txn`**.
- **테스트**:
  - 예시 10개 (write skew 허용 포함).
  - 한 스레드에서 여러 트랜잭션을 섞는 proptest 128회.
  - 칠판 단위 테스트 5개.

## 배운 것

**"값이 같으면 안 바뀐 것"은 틀린 지름길이다.** 설계에서 버린 "스냅샷 값과 최신 값 비교"는 A→B→A를 놓친다. 이것을 테스트로 남겼다(`a_write_another_transaction_undid_still_conflicts`). 같은 이유로 "트리가 안 바뀐 쓰기"(없는 키 지우기, 같은 값 쓰기)도 번호를 받게 했다. 충돌은 값이 아니라 **누가 썼나**의 문제다.

**잃어버린 갱신을 숫자로 보면 설득력이 다르다.** 눈 가린 테스터가 충돌 판정이 없는 #25 브랜치에서 같은 테스트를 돌렸다. 8스레드가 카운터를 400번 올렸고 커밋은 모두 성공했는데 값은 51이었다. "스냅샷만으로는 부족하다"는 말보다 이 숫자 하나가 이 티켓이 왜 필요한지 더 잘 보여 준다.

**같은 측정도 함께 도는 일에 따라 결과가 바뀐다.** 첫 A/B는 +4.5%(p 0.007)였다. 그때 다른 티켓의 눈 가린 테스터가 컴파일 중이었다. 조용할 때 40라운드로 다시 재니 +1.3%였다. A/A 대조가 두 번 다 "차이 없음"이었으니 측정 자체는 믿을 만했지만, 비교한 두 쪽이 같은 시간대를 지나도 순서(ABBA)만으로는 다 지워지지 않는 잡음이 있었다. 동시에 여러 일을 돌리는 날은 A/B를 마지막에 홀로 돌린다.

**잠금 하나가 하는 일이 늘면 기다리는 쪽도 는다.** 이제 `begin`과 `Drop`도 커밋 잠금을 잡는다. 커밋은 sync가 끝날 때까지 그 잠금을 쥐므로, 트랜잭션을 버리는 일조차 남의 fsync를 기다린다(리뷰 Y5). 한 스레드 테스트에서는 안 보인다. #27(여러 스레드)에서 커밋이 sync 동안 잠금을 놓도록 바꿀 때 함께 다룬다.

**Rust 쪽에서 눈여겨본 점**

- **수명이 있는 타입의 `Drop`은 빌림을 길게 만든다**: `Txn<'db>`에 `Drop`을 붙이자, 트랜잭션 변수는 스코프 끝까지 `&Db`를 빌린다. 테스트 하나에서 `db.close()` 앞에 `drop(txn)`이 필요해졌다. 열린 트랜잭션을 두고 DB를 닫는 것을 컴파일러가 막아 주는 셈이라 받아들였다.
- **매개변수는 지역 변수보다 늦게 해제된다**: `commit(self)` 안에서 잠금 가드(지역 변수)가 먼저 풀리고, 끝에서 `self`의 `Drop`이 다시 잠금을 잡는다. 이 순서 덕분에 교착이 없다. 리뷰도 따로 확인했다.
- **`HashMap`은 조회에만**: 순회 순서가 결과에 영향을 주지 않으니 결정적이다. 지우기 순서는 `VecDeque`(커밋 순)가 정한다.

## 다음 이슈로 넘기는 것

- **#27 여러 스레드와 커밋 창구**: `begin`·`Drop`이 커밋 sync를 기다리는 문제. 커밋 번호 체계는 그대로 쓴다.
- **공개 문서**: `commit`의 오류 목록에 `Conflict`, `Txn` 문서에 write skew (리뷰 X1·X2 → PR 판단할 것).
- **패닉 안전성**: 트리를 바꿔 끼운 뒤 키를 적기 전에 패닉하면, 키가 안 적힌 새 트리가 보인다(리뷰 Y2). 순서를 바꿀지 PR에서 정한다.
