# 0019. WHERE와 범위 조회 — 회고

이슈 #32. 설계는 `docs/design/0019-where-and-range-scan.md`. 결정 W1~W11 가운데 W1(연산자)은 사용자가 추천(B)이 아니라 **D(BETWEEN·IN·INTEGER 산술까지)**를 골랐고, 나머지는 추천안대로 정했다. D 때문에 W3(피연산자), W5(타입 검사), W8(식의 모양)을 다시 썼고, W11(넘침과 0으로 나누기)을 새로 정했다.

## 만든 것

- **WHERE 식**: 비교 6종, `IS [NOT] NULL`, `[NOT] BETWEEN`, `[NOT] IN (...)`, `AND`/`OR`/`NOT`, 괄호, INTEGER 산술 `+ - * / %`와 단항 `-`. NULL은 3값 논리(참·거짓·모름)를 따른다.
- **계획 단계** `planner.rs`: 엔진을 모르는 순수 함수. 열 이름을 번호로 바꾸고, 타입을 검사하고, 맨 위 AND로 묶인 기본 키 조건으로 범위를 좁힌다. `id > 3 + 4`처럼 상수 쪽 산술은 계획 때 미리 계산(접기)한다.
- **실행**: `txn.scan(범위)`로 그 범위의 행만 읽고, 행마다 WHERE 전체를 다시 확인한다. 기존 `WHERE pk = 값`도 양 끝이 같은 범위 조회 하나로 합쳤다. WHERE 없는 SELECT는 표 전체를 돌려준다.
- **새 오류 종류 둘**: `Type`(식의 타입이 안 맞음, 행을 읽기 전에 남), `Arithmetic`(넘침, 0으로 나누기).
- **테스트 38개 추가**:
  - 단위 19개: 3값 표, 산술, 계획 범위, 파서 우선순위.
  - SQL 문자열 17개.
  - 모델 비교 속성 테스트 2개: INTEGER 기본 키 표와 TEXT 기본 키 표, 각 256개 사례 × 조건 최대 7개.

## 배운 것

**"범위는 넉넉하게, 판정은 정확하게"는 버그의 종류를 바꾼다.** 계획이 범위를 넓게 잡으면 느리기만 하고 답은 맞는다. 행마다 WHERE 전체를 다시 확인하기 때문이다. 답이 틀릴 수 있는 경우는 범위가 좁아서 맞는 행을 빠뜨릴 때 하나뿐이다. 돌연변이 시험이 이것을 그대로 보여 줬다. 범위를 넓히는 망가뜨림은 모델 테스트를 통과하고, 좁히는 망가뜨림은 걸린다. 그래서 "기본 키 조건이 정말 범위 조회로 실행되는가"(완료 기준 1)는 결과만 보는 모델 테스트로는 확인할 수 없다. 계획 단위 테스트가 범위 자체를 확인해야 한다. **정확성 테스트와 "일을 덜 하는가" 테스트는 서로 다른 테스트다.**

**산술을 넣자 오류가 "어떤 행을 읽었느냐"에 달리게 됐다.** `WHERE 10 / (id - 3) > 0 AND id > 5`는 `id = 3`인 행을 읽지 않으므로 오류가 나지 않는다. 표 전체를 읽는다면 오류가 난다. 모델과 Oakdb를 "같은 답"으로 비교할 수 없게 된 것이다. 그래서 약속을 한 방향으로만 세웠다. **모든 행을 모든 식으로 계산해도 오류가 없다면, Oakdb도 오류 없이 같은 답을 낸다.** 모델은 지름길 없이 모든 행의 모든 부분식을 계산하고, 모델이 오류를 낸 경우에는 Oakdb가 오류든 성공이든 받아들인다. 같은 이유로, 상수를 접다가 넘치면(`id > 9223372036854775807 + 1`) 계획 단계에서 오류를 내지 않고 거르기에 맡긴다. 그렇게 해야 빈 표에서는 오류가 나지 않는다.

**괄호 하나가 문법을 바꿨다.** 산술이 없을 때 `(`는 늘 "조건 묶음"이었다. 산술이 들어오자 `(a = 1 OR b = 2)`와 `(a + 1) * 2`를 파서가 미리 가릴 수 없게 됐다. 실제 SQL 파서처럼 둘을 한 `Expr`로 읽고, 계획 단계의 타입 검사에서 값(`Scalar`)과 조건(`Pred`)으로 나눴다. 나눈 뒤에는 `WHERE id`나 `(a = 1) + 2` 같은 식이 **타입으로 아예 만들어지지 않는다.** 그래서 계산 함수에는 "조건의 값은?" 같은, 닿을 수 없는 경우가 없다.

**NOT이 끼어야 3값 논리가 보인다.** `NOT IN (1, NULL)`은 어떤 값에도 참이 되지 않는다. 3을 넣으면 `3 = 1`은 거짓, `3 = NULL`은 모름이라 IN 전체가 모름이 되고, NOT을 붙여도 모름이기 때문이다. NULL을 거짓으로 단순화했다면 이 경우 3이 결과에 들어왔을 것이다. #33(DELETE)에서는 이것이 "지우면 안 되는 행을 지움"이 된다.

**Rust 쪽에서 눈여겨본 점**

- **`Cow<Value>`로 계산**: 열이나 리터럴 값은 빌려 쓰고, 산술 결과만 새로 만든다. 행마다 TEXT를 복사하지 않는다.
- **`Bound<Value>`로 범위**: 계획은 엔진 키가 아니라 값으로 범위를 들고 있다. 단위 테스트가 `(Excluded(5), Unbounded)`처럼 읽히고, 키로 바꾸는 일은 실행기의 `row_range` 한곳에서 한다.
- **망가진 행은 패닉이 아니라 `Corrupt`**: 타입 검사를 통과한 식이라도 저장된 값의 타입이 열과 다르면 계산에서 걸린다. 행 디코딩은 카탈로그 타입을 모르기 때문이다.
- **빌림 규칙이 #33의 설계를 정한다**: `scan`은 트랜잭션을 `&`로, `put`은 `&mut`로 빌린다. UPDATE/DELETE는 "맞는 키를 먼저 모으고 그다음 고치기"로 짤 수밖에 없다. 이 구조가 할로윈 문제도 함께 막는다.

**뜻밖의 것**

- **`get`과 `scan`의 키 길이 검사가 달랐다.** `get`은 키 길이를 검사하지만 `scan`은 하지 않는다. `pk = <아주 긴 글자>`를 범위 조회로 바꾸자 `KeyTooLarge` 오류 대신 0행이 나왔다. #34에 넘겨 둔 질문이 저절로 "0행"으로 정해졌다.
- **표 끝 경계는 카탈로그 규칙에 기대고 있었다.** 표 끝 `[01][T+1]`이 넘치지 않는 것은 카탈로그가 표 번호 `u32::MAX`를 주지 않아서다. 이 약속에 기대지 않으려고 `checked_add`로 계산하고, 넘치면 `[02]`를 쓴다.

## 다음 이슈로 넘기는 것

- **#33 UPDATE/DELETE**: `planner::plan`과 `Scalar`(`SET x = x + 1`)를 그대로 쓴다.
- **#34 오류 종류**: 새 `Type`과 `Arithmetic`의 메시지를 다듬는다. i64 밖 정수 리터럴은 지금 문법 오류다.
- **여러 범위(설계 4절의 B)**: `id = 1 OR id = 5`, `id != 3`, 값이 퍼진 `IN`은 지금 표 전체나 넓은 범위로 실행된다. 느리면 그때 넓힌다.
- **검증 단계**: `pk = 값`을 `get` 대신 범위 조회로 실행해도 느려지지 않는지 A/B 벤치마크로 확인한다.
