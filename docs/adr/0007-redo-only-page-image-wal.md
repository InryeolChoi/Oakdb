# 장애 복구: 페이지 전체 사본을 남기는 redo 전용 WAL

커밋 전까지 트리를 건드리지 않으므로(ADR 0006) 커밋되지 않은 내용은 디스크에 가지 않고, 되돌리기 로그가 필요 없다. 그래서 복구는 "다시하기"만 한다. 커밋 담당은 그룹 커밋 배치마다 바뀐 페이지의 **전체 사본**과 COMMIT 레코드를 WAL에 쓰고 디스크 기록을 한 번 한 뒤 응답한다. 데이터 파일은 체크포인트 때만 쓰고, 체크포인트 위치는 파일 앞의 메타 슬롯 두 개에 번갈아 기록한다. 재시작하면 유효한 메타 슬롯에서 시작해 WAL을 앞에서부터 다시 적용하고, 체크섬이 처음 깨진 레코드에서 멈춘다. 근거는 `docs/research/0004-btree-crash-recovery.md`.

## Considered Options

- **ARIES**: steal/no-force, undo, 보상 레코드까지 필요해 2개월 범위에 너무 크다.
- **롤백 저널(SQLite 기본)**: 그룹 커밋, 동시 쓰기와 맞지 않는다.
- **로그 + 복사형 체크포인트(WiredTiger 방식)**: 가능하지만 더 복잡하다.

## Consequences

- 반쯤 쓴 페이지는 체크섬으로 감지하고, 이전 체크포인트부터 WAL을 다시 적용해 복구한다. 메타 슬롯이 깨지면 다른 슬롯을 쓴다.
- 디스크 기록이 실패하면 재시도하지 않고 엔진을 정지시킨다. 그 배치의 클라이언트에는 "결과를 알 수 없음" 오류를 돌려준다. 짧은 쓰기와 디스크 공간 부족도 같은 방식으로 다룬다.
- 작은 변경도 4KB 페이지 전체를 로그에 쓰므로 WAL이 커진다. 벤치마크로 확인하고, 필요하면 PostgreSQL처럼 체크포인트 후 첫 변경에만 전체 사본을 쓰는 방식으로 줄인다.

## 구현 메모 (#22 WAL, PR #54)

결정은 그대로이고, 순서와 경계만 적는다. 자세한 형식은 `docs/design/0010-wal.md`.

- **체크포인트(#23) 전까지 데이터 파일은 비어 있다.** 새 DB 만들기도 WAL의 첫 커밋이다. 메타 슬롯 두 개는 #23부터 쓴다.
- **"기록이 실패하면 엔진 정지"는 아직 아니다.** #24 전까지는 실패 뒤 다음 커밋이 같은 자리에 다시 쓴다.
- **재생은 첫 체크섬 실패에서 멈추고, 그 뒤는 잘라 낸다.** 잘라 낸 바이트는 `oakdb.wal.cut`에 보관한다. 정전이 아닌 손상(WAL 중간)으로 그 뒤의 응답한 커밋을 잃을 수 있다는 뜻이고, SQLite WAL도 같다.
- 커밋 시간: 페이지가 늘어나는 커밋은 sync가 두 번에서 한 번이 되어 23% 빨라졌다(실험 0009).

## 구현 메모 (#23 체크포인트, PR #55)

결정은 그대로이고, 형식과 경계만 적는다. 자세한 것은 `docs/design/0011-checkpoint.md`.

- **디스크 형식이 바뀌었다.** 메타 페이지 형식 4: 오프셋 52에 체크포인트 회차(u64). WAL 앞에 20바이트 머리말(magic `oakwal\0\0`, 회차, crc)을 두고, 레코드의 사슬 체크섬은 머리말의 crc에서 시작한다. 형식 3 파일은 버전으로 거절한다.
- **메타 슬롯 두 개**: 첫 정리는 두 슬롯 모두, 그 뒤로는 회차 `n`을 슬롯 `n % 2`에 쓴다. 열 때는 성한 슬롯 중 회차가 큰 쪽을 쓰되, WAL 머리말의 회차와 같을 때만 WAL을 재생한다. 머리말이 더 크면 거절한다(최신 슬롯이 정리 뒤 깨진 경우).
- **WAL 비우기**는 파일 삭제가 아니라 길이 0 + sync, 머리말 + sync다. 이 순서 덕분에 20바이트 이하 WAL에는 레코드가 없다.
- **정리가 실패하면 엔진을 멈춘다.** 위 Consequences의 "기록이 실패하면 엔진 정지"를 정리 경로에 먼저 적용했다. 커밋 경로는 #24.
- 재시작 시간: WAL 재생은 `CHECKPOINT_AFTER`(4MiB) + 커밋 하나 이하. 장부 전체를 메모리로 읽는 시간은 남는다.

## 구현 메모 (#24 디스크 기록 실패, PR #57)

결정은 그대로이고, 경계와 공개 API만 적는다. 자세한 것은 `docs/design/0012-disk-failure.md`. 아래는 사용자 부재 중 추천안으로 진행했고, PR #57 리뷰 뒤 사용자가 확인했다.

- **멈추는 실패**: 엔진이 열린 뒤 디스크를 바꾸는 호출(쓰기, 길이 바꾸기, sync)의 실패는 무엇이든 엔진을 멈춘다. 짧은 쓰기·ENOSPC도 쓰기 실패로 같다. 열기 도중의 실패는 열기가 오류를 돌려줄 뿐이다.
- **오류 종류 두 개**: 실패를 만난 커밋은 `Error::OutcomeUnknown(Arc<io::Error>)`, 그 뒤의 모든 요청(읽기 포함)은 `Error::Stopped(Arc<Error>)`. `Stopped`는 실패한 호출이 받은 오류를 그대로 나눠 쥐어 OS 오류 번호가 남는다. 그래서 `Error::Io`도 `Arc<io::Error>`가 되고 `Error`는 `Clone`이다. #23의 "정리 실패 = `Io(other(..))`"(리뷰 S5)를 대신한다. 직접 부른 정리·닫기의 실패는 원인 `Io`를 그대로 돌려준다.
- **자동 정리 실패**: 커밋은 이미 WAL에 sync됐으므로 `Ok`를 돌려주고 엔진만 멈춘다(#23에서는 `Err`).
- **멈춘 뒤 다시 쓰지 않는다**: 쓰는 쪽은 트리 잠금을 쥔 뒤 멈춤을 확인한다. 그래서 실패와 다음 커밋 사이에 재시도가 끼어들 틈이 없다. 다시 열기는 `Db`를 버리고 `open`을 다시 부르는 것이다.
- **남은 구멍**: Linux에서 sync가 실패한 페이지는 캐시에 남을 수 있어, 같은 부팅에서 다시 열면 디스크에 없는 바이트를 읽을 수 있다. 열기 도중 실패한 뒤 같은 프로세스에서 다시 열 때도 같다. 가짜 디스크가 이 고장을 흉내 내지 못한다. #59.

## 구현 메모 (#59 같은 부팅의 캐시 구멍, PR #60)

결정은 그대로이고, 열기 순서만 바뀐다. 자세한 것은 `docs/design/0014-same-boot-cache.md`.

- **열기는 읽은 것을 굳힌 뒤에 붙인다**: WAL은 마지막 온전한 커밋까지(새로 시작하면 머리말만) `oakdb.wal.new`에 쓰고 sync한 뒤 `oakdb.wal`로 rename하고 디렉터리를 sync한다. 위 #24 메모의 "남은 구멍"을 막는다.
- **하나뿐인 사본은 덮어쓰지 않는다**: 메타 슬롯은 WAL이 더 옛 회차를 가리킬 때만 제자리에 다시 쓴다. 그때는 다른 슬롯과 금고 속 WAL이 짝으로 남는다. 정리 경로도 원래 이 규칙을 지킨다(오래된 슬롯에 쓰기, 정리하는 페이지는 WAL에 사본).
- **`Fs::rename` 추가**: 같은 디렉터리 안에서 한 번에 바꾸고, 열린 손잡이는 파일을 따라간다. 디렉터리 sync 뒤 durable하다. 기본 구현이 없어서 **`Fs`를 직접 구현한 코드는 고쳐야 한다**(깨지는 변경). 원자적으로 바꿀 수 없는 파일 시스템이 조용히 넘어가지 않게 일부러 그렇게 했다.
- **디렉터리의 파일**: `oakdb.data`, `oakdb.wal`, `oakdb.wal.cut`(잘린 꼬리 보관)에 더해 `oakdb.wal.new`가 열기 도중 잠깐 생긴다. 열기가 끊겨 남으면 다음 열기가 덮어쓰고 길이를 맞춘다.
- **가짜 디스크**: sync 실패가 변경을 잊는 방식(`FailedSync::Forgets`), 찢긴 칸이 쓰레기가 되는 방식(`TornSector::Garbled`), 순서대로 닿는 rename을 더했다.

## 구현 메모 (#28 그룹 커밋)

결정은 그대로다. 위 첫 문단의 "그룹 커밋 배치마다 … COMMIT 레코드"를 문자 그대로 구현했다. 자세한 것은 `docs/design/0021-group-commit.md`.

- **묶음 하나 = COMMIT 레코드 하나**: 커밋 스레드가 기다리는 커밋을 최대 128개까지 꺼내, 바뀐 페이지의 마지막 모습과 COMMIT 하나를 한 번에 쓰고 sync를 한 번 한다. **WAL 형식과 재생 규칙은 바뀌지 않았다.** 반쯤 쓰인 묶음은 통째로 버려지고, 그 커밋들은 아직 응답 전이다.
- **재생 상한**: 정리는 커밋마다가 아니라 묶음 뒤에 확인하므로, WAL은 `CHECKPOINT_AFTER`(4MiB) + **묶음 하나**까지 자랄 수 있다. 위 #23 메모의 "+ 커밋 하나 이하"를 대신한다.
- **묶음의 sync 실패**: 충돌 확인을 통과한 묶음의 커밋이 모두 `OutcomeUnknown`을 받는다. 위 Consequences의 "그 배치의 클라이언트"가 이제 실제 묶음이다.
- **응답 먼저, 정리 뒤**: 묶음은 sync한 뒤 응답하고, 그다음 정리한다. 정리 실패에도 커밋은 `Ok`(#24)라서 답은 같고 기다림만 준다.
