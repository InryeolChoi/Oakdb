# 서버는 접속마다 스레드 하나로 처리하고, 접속 수에 상한을 둔다

Oakdb 서버(#36)는 접속을 받을 때마다 스레드 하나를 띄운다. 그 스레드가 접속이 끝날 때까지 프레임 읽기 → SQL 실행 → 응답 쓰기를 반복한다. 네트워크와 디스크 기다림은 모두 블로킹이다(`std::net`). 비동기 런타임(tokio)은 쓰지 않는다.

사용자 요구 "손님 수백 명도 감당"에 맞춰 숫자를 정한다.

- 접속 상한 `--max-connections`, 기본 **512**. 넘는 접속은 받아들인 직후 오류 프레임(`0x45`)을 받고 끊긴다.
- 접속 스레드의 스택은 **256 KiB**(Rust 기본 2 MiB). 접속 스레드의 호출은 얕고(재귀하는 곳은 깊이가 상수), 큰 값은 힙에 있다.
- 서버는 시작할 때 파일 기술자 soft 한도를 `상한 + 64`까지 올리고, 그래도 모자라면 시작을 거부한다. macOS의 기본 soft 한도는 256이다.
- 접속 300개를 동시에 여는 종단 테스트가 macOS와 Linux CI에서 돈다.

이유는 세 가지다. 엔진의 커밋은 디스크 기록(sync)이 끝날 때까지 돌아오지 않는 블로킹 호출이라, 비동기로 가도 결국 별도 스레드로 빼야 한다. 목표 규모가 수백 접속이라 스레드로 충분하다. 그리고 엔진의 트랜잭션(`Txn<'db>`)은 `Db`를 빌리므로, 접속 하나 = 스레드 하나 = 트랜잭션 하나로 두면 #37(접속별 트랜잭션, 끊기면 롤백)이 수명 문제 없이 풀린다. 비동기 작업은 `'static`이어야 해서 엔진 API를 바꿔야 할 수 있다.

## Considered Options

- **비동기 런타임(tokio)**: 접속 수만 개도 감당하지만 블로킹 커밋을 `spawn_blocking`으로 빼야 하고, `Txn<'db>`를 `.await` 너머로 들고 다니기 어렵다. 지금 규모에서 얻는 것보다 배우고 고칠 것이 많다.
- **스레드 풀과 비동기를 섞는 길(하이브리드)**: 접속의 읽기·쓰기는 tokio의 멀티스레드 런타임(일꾼 스레드 풀 + 일 훔치기)이 맡고, 커밋은 티켓 15(#27)의 커밋 스레드에 채널로 보내 답을 `.await`로 기다린다. 어려운 곳은 `Txn<'db>`를 `.await` 너머로 들고 있을 수 없다는 점이다. 엔진에 `Db`를 빌리지 않는 소유형 트랜잭션을 만들거나, 명시적 트랜잭션(`BEGIN` 뒤) 안에 있는 접속에만 전용 스레드를 붙여야 한다. 아래 "다시 볼 조건"에 해당할 때 이 길을 먼저 본다.
- **고정 크기 스레드 풀**: 동시 처리 수가 풀 크기로 묶여 #37에서 트랜잭션을 쥔 채 노는 접속이 풀을 다 차지할 수 있다. 상한 있는 접속마다 스레드와 효과가 같고 코드는 더 많다.

## Consequences

- 통신 규칙(`docs/protocol.md`)과 CLI는 접속 처리 방식과 무관하다. 바꾸게 되면 서버의 접속 루프와 #37의 트랜잭션 보관 방식이 바뀌고, 엔진 API(`Txn`의 수명)까지 번질 수 있다.
- **다시 볼 조건**: #39(네트워크 벤치마크)에서 스레드 수나 문맥 전환이 처리량의 병목으로 보일 때, 또는 목표가 약 1만 접속이 될 때. 그때는 위의 하이브리드 길을 먼저 검토한다.
- 스택을 줄였으므로, 접속 스레드에서 깊은 재귀를 더하는 변경(예: 중첩 표현식 파서)은 스택 크기를 다시 본다. 넘치면 Rust는 보호 페이지에서 분명한 메시지와 함께 프로세스를 멈춘다.

## 구현 메모 (#37 접속별 트랜잭션)

결정은 그대로다. 자세한 것은 `docs/design/0025-multi-client-transactions.md`.

- **세션 = 접속 스레드의 지역 변수**: 인사(HELLO/READY)를 마치면 `serve()` 안에서 `Session::new(&db)`를 만들고, 모든 `QUERY`를 그 세션으로 돌린다. `serve()`가 어떤 길로 끝나든(소켓 닫힘, 깨진 프레임, 시간 초과, 패닉의 되감기) 세션이 `Drop`되어 열린 트랜잭션이 롤백된다. 이 ADR이 기대한 대로 엔진·SQL 층의 수명(`Txn<'db>`)은 하나도 고치지 않았다.
- **노는 접속의 시간 제한**: 트랜잭션 중에는 다음 프레임의 첫 바이트를 기다리는 시간을 `--idle-in-transaction-timeout`(기본 60초)으로 묶고, 넘으면 롤백 → `0x47` → 끊는다. 기다림은 `BufReader::fill_buf`로 해서 바이트를 꺼내지 않으므로, 오래된 트랜잭션 경고를 위해 중간에 깨어나도 잃는 것이 없다. 트랜잭션 밖은 `--idle-timeout`(기본 끔, `0x48`). 응답 쓰기에도 같은 값의 쓰기 시간 제한을 건다. 소켓 옵션은 값이 바뀔 때만 다시 건다.
- **두 OS**: 시간 초과는 macOS·Linux 모두 `WouldBlock`으로 오지만 `TimedOut`도 같이 받는다(ADR 0003). 시간 초과 테스트가 두 OS CI에서 돈다.
- **트랜잭션 상한은 따로 없다**: 접속 하나에 트랜잭션은 많아야 하나라서 접속 상한(512)이 곧 상한이다. 접속 300개가 모두 `BEGIN`한 채 장벽에서 만난 뒤 모두 `COMMIT`하는 테스트가 돈다.

## 구현 메모 (#38 정상 종료)

결정은 그대로다. 자세한 것은 `docs/design/0028-graceful-shutdown.md`.

- **접속 목록 없이 멈춘다**: 종료는 공유 플래그 하나(`ShutdownHandle`이 켬)와 접속 스레드의 **첫 바이트 틱**(다음 프레임의 첫 바이트를 기다릴 때만 100 ms마다 깨어나 플래그를 봄)으로 한다. 다른 스레드가 소켓을 `shutdown`하지 않는다. 그러면 RST가 `0x49`를 지울 수 있다. 누가 남았는지는 지금처럼 `active`로만 센다.
- **accept는 "깨우기 손님"으로 깨운다**: 손잡이가 자기 listener에 루프백으로 접속하고, accept 스레드는 받은 소켓보다 플래그를 먼저 본다. 평소의 블로킹 accept는 한 줄도 바뀌지 않았다.
- **스레드 하나당 비용**: 노는 접속마다 초당 10번의 짧은 `recv` 시간 초과가 더해지고, 문장마다 읽기 시간 제한 설정이 두 번 더해진다(틱 ↔ 프레임 나머지). 측정은 `docs/benchmarks/0012-graceful-shutdown.md`.
- **엔진을 닫는 순서는 컴파일러가 지킨다**: 접속 스레드가 모두 끝나 `Arc<Shared>`가 하나만 남아야 `Arc::try_unwrap`으로 `Db`를 꺼내 `close()`(마지막 체크포인트)할 수 있다. 그래서 `Monitor`는 `Weak`를 들도록 바꿨다.
