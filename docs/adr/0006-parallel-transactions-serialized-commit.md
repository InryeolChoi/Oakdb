# 트랜잭션은 동시에 실행하고, 커밋만 한 줄로 처리

Oakdb의 "동시 쓰기"는 이렇게 구현한다. 각 트랜잭션은 시작 순간의 스냅샷을 읽고, 쓰기는 트랜잭션 안의 개인 버퍼에만 모아 둔다. 커밋할 때 하나의 커밋 대기열에서 순서대로, 이 트랜잭션이 **쓴 키**를 스냅샷 이후에 다른 트랜잭션이 먼저 커밋했는지만 확인한다(first-committer-wins). 통과하면 커밋 담당 스레드가 트리에 반영하고, 실패하면 충돌 오류를 돌려준다. 트리는 커밋 담당만 고치므로 처음에는 트리 전체를 `RwLock` 하나로 보호한다.

SQLite는 쓰기 트랜잭션 하나가 시작부터 커밋까지 DB 잠금을 쥔다. Oakdb는 실행 중(네트워크 대기 포함)에는 아무 잠금도 쥐지 않고, 충돌을 페이지가 아닌 키 단위로 판정하며, 디스크 기록을 여러 커밋이 나눠 쓴다(그룹 커밋). 이것이 ADR 0005가 말하는 "동시 쓰기"의 의미다. 근거는 `docs/research/0003-concurrent-btree-writes.md`.

## Considered Options

- **페이지 단위 래치 크래빙**: 여러 스레드가 트리를 동시에 고친다. 벤치마크에서 트리 잠금이 병목으로 확인되면 이 방식으로 올리고, 잠금 규칙은 `loom`으로 검증한다. 처음부터 하지는 않는다.
- **B-link 트리, 낙관적 잠금, 행 잠금 + 되돌리기 로그**: 2개월 범위에서 정확하게 만들기 어려워 제외했다.
- **복사해서 쓰는 트리(LMDB 방식)**: 쓰기가 한 번에 하나뿐이고 ADR 0004의 제자리 수정 가정을 바꿔야 해서 제외했다.

## Consequences

- 스냅샷 격리이므로 write skew(서로 다른 키를 읽고 써서 규칙이 깨지는 이상 현상)는 허용되며, 이 사실을 사용자 문서에 적는다.
- 커밋 전까지 트리가 바뀌지 않으므로 장애 복구에 되돌리기(undo)가 필요 없다(ADR 0007).
