# 트랜잭션은 동시에 실행하고, 커밋만 한 줄로 처리

Oakdb의 "동시 쓰기"는 이렇게 구현한다. 각 트랜잭션은 시작 순간의 스냅샷을 읽고, 쓰기는 트랜잭션 안의 개인 버퍼에만 모아 둔다. 커밋할 때 하나의 커밋 대기열에서 순서대로, 이 트랜잭션이 **쓴 키**를 스냅샷 이후에 다른 트랜잭션이 먼저 커밋했는지만 확인한다(first-committer-wins). 통과하면 커밋 담당 스레드가 트리에 반영하고, 실패하면 충돌 오류를 돌려준다. 트리는 커밋 담당만 고치므로 처음에는 트리 전체를 `RwLock` 하나로 보호한다.

SQLite는 쓰기 트랜잭션 하나가 시작부터 커밋까지 DB 잠금을 쥔다. Oakdb는 실행 중(네트워크 대기 포함)에는 아무 잠금도 쥐지 않고, 충돌을 페이지가 아닌 키 단위로 판정하며, 디스크 기록을 여러 커밋이 나눠 쓴다(그룹 커밋). 이것이 ADR 0005가 말하는 "동시 쓰기"의 의미다. 근거는 `docs/research/0003-concurrent-btree-writes.md`.

## Considered Options

- **페이지 단위 래치 크래빙**: 여러 스레드가 트리를 동시에 고친다. 벤치마크에서 트리 잠금이 병목으로 확인되면 이 방식으로 올리고, 잠금 규칙은 `loom`으로 검증한다. 처음부터 하지는 않는다.
- **B-link 트리, 낙관적 잠금, 행 잠금 + 되돌리기 로그**: 2개월 범위에서 정확하게 만들기 어려워 제외했다.
- **복사해서 쓰는 트리(LMDB 방식)**: 쓰기가 한 번에 하나뿐이고 ADR 0004의 제자리 수정 가정을 바꿔야 해서 제외했다.

## Consequences

- 스냅샷 격리이므로 write skew(서로 다른 키를 읽고 써서 규칙이 깨지는 이상 현상)는 허용되며, 이 사실을 사용자 문서에 적는다.
- 커밋 전까지 트리가 바뀌지 않으므로 장애 복구에 되돌리기(undo)가 필요 없다(ADR 0007).

## 구현 메모 (#17 범위 조회, PR #48)

결정은 그대로이고, 메모리에서 트리를 지키는 방법만 바뀌었다.

- `Db`는 트리를 `RwLock<Tree>`가 아니라 **`Mutex<Arc<Tree>>`** 로 든다. 커밋은 트리를 복제해 고친 뒤 `Arc`를 새 트리로 통째로 바꿔 끼운다. 페이지가 이미 `Arc`라서 복제는 바뀐 페이지만 복사한다. 읽는 쪽은 `Arc`를 하나 복제해 들고 잠금 없이 읽는다. 그래서 조회 중에 커밋이 와도 조회가 보는 트리는 바뀌지 않는다.
- 이것은 위에서 제외한 "복사해서 쓰는 트리(LMDB 방식)"가 **아니다.** 바꿔 끼우는 것은 메모리 안의 트리뿐이고, 디스크의 페이지는 지금도 제자리에서 덮어쓴다(ADR 0004). LMDB 방식은 디스크에도 새 페이지를 쓰고 루트만 바꾸는 방식이라, 제외한 이유(쓰기 하나뿐, 제자리 수정 가정 변경)는 그대로 유효하다.
- (#25에서 바뀜: 아래 #25 메모) 이 메모를 쓸 때는 `get`과 `scan`이 **부를 때마다** 최신 트리를 잡았다. 스냅샷 티켓(#25)에서 `begin`이 `Arc`를 한 번 잡아 두면, 이 구조가 그대로 "시작 순간의 스냅샷"이 된다.
- 커밋은 sync가 끝날 때까지 이 `Mutex`를 쥔다. 그동안 새 조회의 **시작**도 기다린다. 커밋 담당 스레드와 그룹 커밋(#27, #28)에서 다시 본다.
- 대가: `get`이 포인터 한 단계를 더 따라가서 한 장짜리 `get/hit`가 약 2ns(2.6%) 느려졌다(벤치마크 0005). 받아들였다.

## 구현 메모 (#25 스냅샷 읽기)

결정은 그대로다. 자세한 것은 `docs/design/0015-snapshot-reads.md`.

- **스냅샷 = `begin`이 잡은 `Arc<Tree>`**: 위 #17 메모가 말한 대로다. `get`과 `scan`은 최신 트리 대신 이 트리를 읽고, `get`은 더 이상 트리 잠금을 잡지 않는다. 키마다 버전을 붙이지 않았다. 트리 전체가 메모리에 있는 동안은 필요 없다.
- **대가**: 오래 사는 트랜잭션은 그 사이 커밋이 바꾼 페이지의 옛 판을 메모리에 붙잡는다. 또 `begin`이 트리 잠금을 잡으므로, 다른 커밋이 sync하는 동안에는 **트랜잭션 시작이 기다린다**. #27·#28에서 커밋이 sync 동안 잠금을 놓게 할 때 함께 본다.
- **커밋은 아직 최신 트리에 덮어쓴다**: 같은 키를 남이 먼저 커밋했어도 모른다. #26이 막는다.

## 구현 메모 (#26 충돌 판정)

결정은 그대로다. 자세한 것은 `docs/design/0016-write-conflicts.md`.

- **커밋 번호와 칠판**: 커밋에 메모리 속 번호를 붙이고 "키 → 마지막으로 쓴 커밋 번호"를 둔다. 내 키의 번호가 내 스냅샷 번호보다 크면 `Error::Conflict`. 가장 오래 열린 트랜잭션이 시작하기 전의 커밋은 지운다. 번호는 저장하지 않는다.
- **트리와 칠판은 한 잠금**: `Mutex<Committed { tree, recent }>`. 스냅샷과 번호가 언제나 짝이 맞는다.
- **`Txn`에 `Drop`**: 끝날 때 칠판에서 빠진다. 그래서 트랜잭션을 연 채로 `Db::close`를 부를 수 없다.

## 구현 메모 (#27 여러 스레드와 커밋 창구)

결정은 그대로다. 자세한 것은 `docs/design/0018-commit-thread.md`.

- **트리 `RwLock`은 쓰지 않는다**: 트랜잭션은 자기 스냅샷(`Arc<Tree>`)을 잠금 없이 읽는다. 잠금이 지키는 것은 트리 바꿔 끼우기와 칠판뿐이고, `begin`도 칠판에 "열림"을 세느라 쓰기가 필요하다. 그래서 `Mutex<Committed>`를 그대로 두되 **잠깐만** 쥔다.
- **커밋 담당 스레드**: `Db`가 스레드 하나(`oakdb-commit`)를 띄운다. 커밋과 정리는 `std::sync::mpsc` 채널로 요청하고, 커밋마다 응답 채널 하나로 답을 받는다. WAL과 데이터 파일은 이 스레드만 만지므로 `wal`의 `Mutex`가 없어졌다.
- **sync 동안 잠금을 쥐지 않는다**: 충돌 확인과 "키 기록 → 트리 바꿔 끼우기"만 잠금 안에서 한다. 새 트리는 sync가 끝난 뒤에 보인다. 그래서 남이 커밋하는 동안에도 `begin`, 트랜잭션 끝내기(`Drop`), `page_count`가 기다리지 않는다.
- **멈춤과 버리기**: 엔진이 멈춰도 스레드는 살아서 `Stopped`로 답한다. `Db`의 `Drop`이 요청 채널을 닫고 스레드를 `join`한다. 커밋 스레드가 패닉해도(버그) 엔진이 멈춘 것으로 처리한다. 그 요청은 `OutcomeUnknown`, 그 뒤는 `Stopped`.
- 그룹 커밋(#28)은 이 스레드가 쌓인 요청을 한꺼번에 꺼내는 것으로 얹는다. (#28에서 그렇게 했다: 아래 #28 메모)

## 구현 메모 (#28 그룹 커밋)

결정은 그대로다. 자세한 것은 `docs/design/0021-group-commit.md`.

- **묶음 안 충돌**: 묶음의 커밋은 도착 순서대로 확인한다. 칠판에 더해 **같은 묶음에서 앞서 통과한 커밋의 키**와도 비교한다. 묶음의 트랜잭션은 모두 묶음이 공개되기 전에 시작했으므로, 앞 커밋이 쓴 키는 곧 "스냅샷 이후 남이 먼저 쓴 키"다. 칠판 번호는 sync 뒤 공개 때에만 올린다(설계 0016 Y2). 묶음 안 앞 커밋에 진 커밋은 묶음이 공개된 **뒤에** `Conflict`를 받는다. 그래야 답을 받고 바로 시작한 트랜잭션이 승자의 쓰기를 읽는다(#28 검증 반영).
- **공개는 묶음마다 한 번**: sync 뒤 한 잠금 안에서 커밋마다 키를 기록하고 트리를 한 번 바꿔 끼운다. 다른 트랜잭션은 묶음 전체 전이나 전체 후를 본다.

## 구현 메모 (#29 동시성 검증)

결정은 그대로다. 자세한 것은 `docs/design/0024-concurrency-verification.md`.

- **write skew는 실제로 일어나고, 검사기는 허용으로 센다**: 무작위 작업을 돌린 장부를 `oakdb-history`로 검사하면 write skew(rw 화살표가 이어진 사이클)가 나온다. 위 Consequences대로 허용이므로 위반이 아니라 횟수만 센다(실험 0016).
- **`loom` 검증은 지금 커밋 루프에 있다**: Considered Options의 "잠금 규칙은 `loom`으로 검증"은 래치 크래빙을 할 때의 말이지만, 그 전에 커밋 스레드의 대기열(`commit_queue`)이 먼저 loom 아래 들어갔다. CI가 두 OS에서 작은 모델을 돌린다(실험 0017).

## 구현 메모 (#37 접속별 트랜잭션)

결정은 그대로다. 달라진 것은 **트랜잭션의 길이를 이제 클라이언트가 정한다**는 점이다. 자동 커밋에서는 몇 ms였지만, 네트워크 너머의 `BEGIN`은 클라이언트가 `COMMIT`할 때까지 옛 트리 페이지와 칠판의 커밋 기록을 붙잡는다. 그래서 `Stats`에 `open_transactions`(열린 트랜잭션 수)와 `kept_commits`(칠판에 남은 커밋 수)를 더했고(칠판 잠금을 잠깐 쥐고 읽음), 서버는 노는 트랜잭션을 60초에 끊고 오래된 트랜잭션을 로그로 알린다. 자세한 것은 `docs/design/0025-multi-client-transactions.md` Q7.
