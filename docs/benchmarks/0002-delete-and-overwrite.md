# 0002. 벤치마크: 삭제를 더한 뒤에도 느려지지 않았나

이슈 #14. 02번은 커밋을 "쓰는 키를 모두 뺀 다음 put만 다시 넣기"로 바꿨다(설계 0002). 덮어쓰기 한 번이 이제 "지우기 + 넣기" 두 동작이 된다. 이 변경으로 0001의 숫자가 나빠지지 않았는지 다시 잰다.

## 어떻게 쟀나

- 벤치마크는 0001과 같은 `crates/oakdb/benches/single_page.rs`를 그대로 썼다. 코드는 바꾸지 않았다.
- **A** = `main`(6ef59e7, 01번까지), **B** = 이 브랜치.
- 같은 기계에서 A → B → A → B 순서로 번갈아 돌렸다. **A끼리의 차이(A/A)** 가 이 측정의 잡음 크기다. B와 A의 차이가 이보다 작으면 "차이 없음"으로 본다.
- 환경: 로컬 Mac(Apple M3, macOS 27.0.1, APFS, `F_FULLFSYNC`). 숫자는 criterion 95% 구간의 가운데 값이다.

## 결과

| 벤치마크 | A1 | B1 | A2 | B2 | A/A 차이 | 판정 |
|---|---|---|---|---|---|---|
| `get/hit` | 78.1 ns | 76.7 ns | 76.6 ns | 76.1 ns | 2% | 차이 없음 |
| `get/miss` | 30.7 ns | 31.8 ns | 30.8 ns | 31.7 ns | 0% | B가 1ns(3%) 느림 |
| `commit/no_sync` | 2.88 µs | 2.38 µs | 2.42 µs | 2.86 µs | **16%** | 차이 없음 |
| `commit/durable` | 3.00 ms | 3.01 ms | 3.01 ms | 3.01 ms | 0.3% | 차이 없음 |

## 해석

1. **커밋은 느려지지 않았다.** `commit/no_sync`가 2.4µs와 2.9µs 두 값 사이를 오가는데, A와 B 모두 두 값을 한 번씩 냈다. 같은 `main`을 두 번 잰 A/A만으로도 16% 차이가 나므로, 이 값은 버전이 아니라 실행마다 갈린다(메모리 배치나 CPU 코어 배정으로 보인다). 그 안에서 A와 B는 구분되지 않는다.
2. **"지우기 + 넣기"가 비싸지 않은 이유.** 0001의 덮어쓰기도 이미 옛 셀을 치우고(`remove_slot`) 새 셀을 넣었다. 02번은 같은 일을 두 단계로 나눠 했을 뿐, 하는 일의 양은 같다. 이진 탐색이 한 번 더 들지만 8번 비교라 수십 ns다.
3. **사용자가 기다리는 시간(`durable`)은 그대로 3ms다.** 0001과 같이 거의 전부 sync다.
4. **`get/miss`는 두 번 다 1ns 느렸다.** A/A 차이가 0이라 우연이라고 하기는 어렵다. 다만 `get`의 코드 경로는 버퍼가 비어 있으면 01번과 같다. 트랜잭션 버퍼의 값 타입이 `Option<Vec<u8>>`로 바뀐 것과 코드 배치가 달라진 것 정도가 후보이고, 1ns라 더 파지 않았다.

## 한계

- 로컬 Mac 한 대에서 두 번씩만 돌렸다. CI(Linux)에서는 재지 않았다. 판정이 갈리는 숫자가 없어서 필요하지 않다고 봤다.
- 삭제 자체의 속도를 재는 벤치마크는 없다. 삭제는 덮어쓰기와 같은 `remove_slot`을 쓰므로 `commit/no_sync`가 대신 보여 준다.
