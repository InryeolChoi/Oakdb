# 0008. 벤치마크: 두 단계 INSERT 전후의 큰 INSERT 시간

이슈 #35, 설계 `docs/design/0023-sql-transactions.md` 10절. INSERT가 "행마다 검사하고 바로 쓰기"에서 **"모든 행을 검사한 뒤 한꺼번에 쓰기"**로 바뀌었다(T5). 성능 주장은 없으므로 설계는 A/B를 요구하지 않았다. 다만 행을 모두 메모리에 모아 두었다가 쓰므로, 큰 INSERT가 느려지지 않았는지 전후 시간을 기록한다. PR #78 리뷰(P1)가 이 기록이 빠졌다고 짚었다.

**비유**: 택배 상자를 하나씩 검사하고 바로 트럭에 싣던 것을, 전부 검사한 다음 한꺼번에 싣도록 바꿨다. 상자를 잠시 바닥에 쌓아 두는 시간이 더 드는지 쟀다.

## 어떻게 쟀나

- `AB_SQL_EXAMPLE=sql_insert python3 docs/experiments/scripts/ab_sql.py <A> <B> 20 <행 수> insert`
- 도우미 `docs/experiments/scripts/ab_versions/sql_insert.rs`: 새 DB에 표 하나를 만들고 `INSERT INTO t VALUES (...), ...` **문장 하나**로 n행(정수 키 + 32바이트 텍스트)을 넣는다. 그 문장의 시간을 커밋(sync)까지 포함해 잰다. 같은 파일을 두 버전에 넣어 빌드했다.
- 20라운드, ABBA 순서, 라운드마다 새 DB. Mann-Whitney U 검정, 중앙값 비율의 95% 신뢰구간은 부트스트랩. A/A 대조군을 함께 돌렸다.
- Apple M3, macOS 27.0.1, APFS, `F_FULLFSYNC`.
- 두 가지 A로 비교했다.
  - **A1 = `1aff225`**: 이 PR의 원래 기준점(리뷰의 merge-base).
  - **A2 = `0360608`**: 지금의 main(#76, #77 포함). PR 브랜치가 main을 merge했으므로, **이 PR만의 차이**는 A2와 비교해야 보인다.
- B = `92b5359` (이 PR, 리뷰 수정 반영).

## 해석

- **느려지지 않았다.** 걱정했던 것은 "행을 모두 모아 두는 비용"이었는데, 10만 행에서도 오히려 4% 안팎 빨라졌다. A/A가 1.000~1.001이라 이 차이는 믿을 만하다.
- 1만 행은 sync 한 번(약 4ms)이 전체(약 12ms)의 큰 몫을 차지하고 흔들림도 커서, A/A도 2~5% 벗어났다. 차이를 말할 수 없다.
- **빨라진 까닭(추정, 따로 재지 않음)**: 예전에는 행을 쓸 때마다 다음 행의 중복 검사(`txn.get`)가 점점 커지는 쓰기 모음(`BTreeMap`)을 뒤졌다. 이제는 검사하는 동안 쓰기 모음이 비어 있고, 같은 문장 안의 중복은 `HashSet`이 본다. `BTreeMap` 탐색보다 해시 탐색이 싸다.
- 메모리: 검사가 끝난 행(키와 인코딩된 값)을 한꺼번에 들고 있다. 쓰기 모음도 어차피 같은 바이트를 커밋 때까지 들고 있으므로, 문장이 도는 동안 최대 약 두 배가 된다. 10만 행 × 약 50바이트면 몇 MB라서 이번에는 재지 않았다.

## 측정 한계

- 로컬 Mac 한 대에서만 쟀다. Linux에서는 sync가 훨씬 짧아(실험 0002) 문장 시간에서 INSERT 처리 몫이 더 크다. 비율은 달라질 수 있다.
- 문장 하나에 넣는 행 수만 바꿨다. 행이 매우 크거나(긴 텍스트) 표가 이미 클 때는 재지 않았다.
