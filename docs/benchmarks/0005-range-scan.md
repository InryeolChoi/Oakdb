# 0005. 벤치마크: 범위 조회

이슈 #17. 두 가지를 잰다.

1. 범위 조회는 항목 하나에 얼마나 걸리나 (새 기준선)
2. 트리를 `Arc`로 감싼 뒤 `get`과 커밋이 느려지지 않았나 (A/B)

## 어떻게 쟀나

- `crates/oakdb/benches/single_page.rs`에 `scans` 묶음을 더했다. 트리는 0003과 같이 4바이트 키·값 2만 개(리프 약 157장 + 루트)다. sync는 끈다(`NoSyncFs`).
- 환경: 로컬 Mac(Apple M3, macOS 27.0.1, APFS). 숫자는 criterion 95% 구간의 가운데 값이다.

| 벤치마크 | 하는 일 |
|---|---|
| `scan/100_two_levels` | 매번 다른 시작 키에서 100개 읽기 |
| `scan/all_two_levels` | 2만 개 전부 읽기 |

## 결과 1: 범위 조회 (새 기준선)

| 벤치마크 | 시간 | 항목 하나당 |
|---|---|---|
| `scan/100_two_levels` | 3.40 µs | 34 ns |
| `scan/all_two_levels` | 633 µs | 32 ns |

- 100개 읽기와 2만 개 읽기의 항목당 시간이 거의 같다. 시작 위치를 찾는 비용(루트에서 리프까지 한 번)은 100개에 나눠 내면 거의 보이지 않는다.
- 항목 하나에 키와 값을 `Vec`으로 두 번 복사한다. 32ns의 대부분이 이 복사와 할당으로 보인다. 같은 트리의 `get/hit_two_levels`(약 180ns)와 비교하면, 하나씩 찾는 것보다 이어서 읽는 것이 약 5배 빠르다.

## 결과 2: `Arc<Tree>`로 바꾼 뒤 (A/B)

**A** = `main`(3619263, 04번까지), **B** = 이 브랜치. 같은 Mac에서 A → B → A′로 번갈아 돌렸다. A′는 A를 한 번 더 돌린 A/A 대조군이다.

| 벤치마크 | A | B | 판정 |
|---|---|---|---|
| `get/hit` (A·B·A′를 번갈아 돌린 5라운드의 중앙값) | 75.6 ns | 77.6 ns | **2.0ns(2.6%) 느림**. 앞선 2라운드까지 7라운드 모두 B가 느림 (부호 검정 p ≈ 0.016) |
| `get/hit` A/A (같은 5라운드) | 75.6 ns | A′ 75.7 ns | 0.2%, 측정 믿을 만함 |
| `get/miss` | 30.2 / 30.2 ns | 30.2 / 30.2 ns | 차이 없음 |
| `get/hit_two_levels` | 185.5 / 177.2 ns | 178.5 / 178.8 ns | 차이 없음 (흔들림 안) |
| `commit/no_sync` | 2.50 / 2.44 µs | 2.95 / 2.50 µs | 흔들림이 커서 판정 못 함 |
| `commit/no_sync_two_levels` | 1.72 / 2.22 µs | 1.76 / 1.77 µs | 흔들림이 커서 판정 못 함 |

- `get/hit`의 2ns는 `Arc`를 거치는 포인터 한 단계로 보인다. 잠금 안에서 `Mutex` → `Arc` → `Tree` → 페이지 순으로 따라간다.
- 2층 트리의 `get`(약 180ns)에서는 2ns가 흔들림에 묻힌다.
- 커밋은 이번에도 0003처럼 크게 흔들렸다. `Arc::new` 할당이 하나 늘었지만, 트리 복제와 페이지 쓰기에 비하면 작다.
- 이 티켓은 성능을 주장하지 않는다. 바꾼 구조의 대가를 기록하려고 쟀다.

## 측정 한계

- 로컬 Mac에서만 A/B를 했다. PR에서 측정 워크플로가 macOS·Linux의 `scan` 기준선을 함께 남긴다.
- `get/hit` 판정은 라운드마다 criterion 가운데 값 하나를 쓴 부호 검정이다. 실험 0002의 Mann-Whitney 도구는 커밋 시간용이라 쓰지 않았다.
