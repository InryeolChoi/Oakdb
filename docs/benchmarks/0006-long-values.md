# 0006. 벤치마크: 긴 값과 빈 페이지 목록

이슈 #18. 두 가지를 잰다.

1. 100KB 값을 읽고, 덮어쓰고, 넣었다 지우는 데 얼마나 걸리나 (새 기준선)
2. 셀마다 "값이 밖에 있나"를 확인하게 된 뒤, 짧은 값의 읽기·커밋·조회가 느려지지 않았나 (A/B)

## 어떻게 쟀나

- `crates/oakdb/benches/single_page.rs`에 `long` 묶음을 더했다. 나머지는 0001·0003·0005와 같다.
- 환경: 로컬 Mac(Apple M3, macOS 27.0.1, APFS). 숫자는 criterion 95% 구간의 가운데 값이다.
- A/B: **A** = `main`(ce3ee2a, 05번까지), **B** = 이 브랜치. 한 라운드에 A → B → A′ 순서로 돌리고 5라운드 반복했다. A′는 A를 한 번 더 돌린 A/A 대조군이다. 표의 숫자는 5라운드의 중앙값이다.

## 결과 1: 긴 값 (새 기준선)

| 벤치마크 | 하는 일 | 시간 |
|---|---|---|
| `long/get_100k` | 100KB 값 읽기 (부록 26장을 모아 복사) | 2.06 µs |
| `long/overwrite_100k_no_sync` | 100KB 값 덮어쓰기: 옛 부록 26장을 빈 페이지로 돌리고, 같은 26장을 새 값에 다시 씀. sync 없음 | 41.9 µs |
| `long/put_then_delete_100k_no_sync` | 다른 키에 100KB 넣고 지우기, 커밋 2번 | 75.3 µs |
| `long/overwrite_100k_durable` | 덮어쓰기, 실제 디스크 기록(`F_FULLFSYNC`) | 2.12 ms |

- 100KB 읽기는 2µs로, 짧은 값 하나 읽기(약 80ns)의 25배쯤이다. 대부분 메모리 복사다.
- 디스크까지 기록하면 2.1ms인데, sync 없이는 42µs다. **긴 값도 커밋 시간의 98%는 sync**다(실험 0002와 같은 결론). 페이지 27장(부록 26장 + 리프)을 써도 sync는 한 번이다. 덮어쓰기는 빈 페이지를 바로 다시 가져가서 빈 페이지 목록이 그대로이므로, 메타 페이지를 쓰지 않는다.
- 넣었다 지우기(75µs)는 덮어쓰기 두 번보다 조금 싸다. 지우기는 부록 26장을 0으로 덮어쓰고 메타도 쓴다.

## 결과 2: 짧은 값은 느려지지 않았나 (A/B, 세 번 쟀다)

처음 잰 결과가 나빠서 코드를 두 번 고치고 다시 쟀다.

| 벤치마크 | 1차 B/A | 2차 B/A | **3차 B/A** | 3차 A → B | 3차 A/A |
|---|---|---|---|---|---|
| `get/hit` | 1.141 | 1.192 | **1.017** | 78.0 → 79.3 ns | 1.002 |
| `get/miss` | 1.027 | 0.986 | **0.998** | 30.4 → 30.3 ns | 1.001 |
| `get/hit_two_levels` | 1.025 | 1.080 | **0.981** | 183.3 → 179.8 ns | 1.008 |
| `commit/no_sync` | 1.054 | 1.018 | **1.007** | 2.47 → 2.48 µs | 0.999 |
| `commit/no_sync_two_levels` | 1.130 | 1.005 | **1.000** | 2.27 → 2.27 µs | 1.005 |
| `scan/100_two_levels` | 1.091 | 1.085 | **1.060** | 3.39 → 3.59 µs | 1.007 |

**무엇을 고쳤나**

1. **1차 → 2차: 커밋.** 넣기와 지우기가 "옛 값이 부록에 있었나"를 보려고 리프를 한 번 더 찾았다. 리프를 한 번만 찾고, 페이지가 옛 값의 부록 위치를 돌려주게 바꿨다. 2층 커밋이 +13%에서 +0.5%가 됐다.
2. **1차 → 2차: 읽기의 `Arc`.** 긴 값을 모으는 동안 커밋이 기다리지 않게, `get`이 모든 값에 대해 트리의 `Arc`를 복제하고 잠금을 놓았다. 짧은 값은 잠금 안에서 바로 복사하고, 긴 값만 `Arc`를 복제하게 바꿨다. 그런데 `get/hit`는 오히려 +19%가 됐다.
3. **2차 → 3차: 셀을 두 번 읽음.** 진짜 원인은 `Page::value`였다. "밖에 있음" 표시를 보려고 슬롯을 읽고, 값 위치를 구하려고 슬롯을 또 읽었다. 한 번만 읽게 고치자 `get/hit`가 +1.7%로 돌아왔다.

**남은 대가**

| 벤치마크 | 크기 | 판정 |
|---|---|---|
| `get/hit` | +1.3 ns (1.7%) | 5라운드 모두 B가 느림 (부호 검정 단측 p ≈ 0.031). A/A는 0.2%. 작지만 진짜 차이로 본다 |
| `scan/100_two_levels` | +2 ns/항목 (6%) | 5라운드 모두 B가 느림 (p ≈ 0.031). A/A는 0.7%. 항목마다 "밖에 있나"를 확인하고 값을 꺼내는 비용으로 보인다 |
| 나머지 4개 | −2% ~ +0.7% | A/A 범위 안. 차이 없음 |

## 측정 한계

- 로컬 Mac에서만 A/B를 했다. 라운드가 5개뿐이라 부호 검정으로 낼 수 있는 가장 작은 p가 0.031이다.
- 1차와 2차 사이에 두 가지를 함께 고쳤다. 그래서 2차의 `get/hit` +19%가 `Arc` 변경 때문인지, 그 전부터 있던 셀 두 번 읽기 때문인지는 따로 재지 않았다. 3차에서 셀 읽기를 고친 뒤 원래대로 돌아온 것으로 보아, 셀 두 번 읽기가 주된 원인이었다.
- 빈 페이지 목록에 넣는 비용이 WAL에서 얼마나 커질지는 WAL(#22) 뒤에 다시 잰다.
