# 0011. 벤치마크: 오류 종류를 나눈 전후의 조회·INSERT 시간

이슈 #34, 설계 `docs/design/0027-type-checks-and-errors.md` E13. 이번 티켓은 성능 주장을 하지 않으므로 A/B 가설 검정은 요구되지 않았다. 다만 렉서·파서가 문장마다 확인하는 것이 늘었다(주석 `--`·`/*`, 이름 뒤의 `.`과 `(`). 이것이 정상 문장을 느리게 하지 않았는지 전후 숫자만 남긴다.

**비유**: 접수처에 "주석 금지", "약칭 금지" 확인 칸을 두 개 더 붙였다. 정상 접수증 처리 시간이 늘었는지 시계로 재 봤다.

## 어떻게 쟀나

| 항목 | 값 |
|---|---|
| A | `9ba59b4` (main, 이 PR의 기준점) |
| B | `f4946f1` (이 PR의 구현) |
| 도구 | `python3 docs/experiments/scripts/ab_sql.py <A> <B> 20 2000 hit,miss` / `AB_SQL_EXAMPLE=sql_insert … 20 10000 insert` |
| 무엇 | `sql_point`: 1000행 표에 `SELECT * FROM t WHERE id = k` 2000번, 있는 키(hit)·없는 키(miss). `sql_insert`: 1만 행 INSERT 문장 하나(sync 포함) |
| 방식 | 20라운드, ABBA 순서, 라운드마다 새 DB. Mann-Whitney U, 중앙값 비율의 95% 부트스트랩 CI, A/A 대조군 |
| 기계 | Apple M3, macOS 27.0.1, APFS, `F_FULLFSYNC`. **같은 시간에 다른 워크트리의 테스트가 돌고 있었다** |

## 결과

| 측정 | 중앙값 A → B | B/A (95% CI) | p | A/A (95% CI), p | 판정 |
|---|---|---|---|---|---|
| 점 조회, 있는 키 | 4.4 → 4.2 µs | 0.950 [0.778, 1.206] | 0.35 | 1.053 [0.669, 1.550], 0.96 | 차이 없음 |
| 점 조회, 없는 키 | 2.7 → 2.9 µs | 1.090 [0.891, 1.336] | 0.32 | 0.951 [0.737, 1.409], 0.88 | 차이 없음 |
| INSERT 1만 행 | 15.7 → 16.3 ms | 1.035 [0.948, 1.116] | 0.37 | 0.925 [0.775, 1.098], 0.50 | 차이 없음 |

## 해석

- **느려졌다는 증거는 없다.** 세 측정 모두 p > 0.3이고 CI가 1을 품는다.
- 다만 **측정이 거칠다.** A/A의 CI가 ±30~50%로 넓다. 다른 워크트리의 `cargo test`가 같은 CPU를 쓰고 있었기 때문이다. 이 숫자로 말할 수 있는 것은 "수십 % 단위로 느려지지는 않았다"까지다. 몇 % 단위의 차이를 보려면 기계가 한가할 때 다시 재야 한다.
- 이론으로도 차이는 작아야 한다. 늘어난 확인은 토큰 하나를 볼 때 바이트 한두 개 비교(`--`, `/*`)와, 이름 하나를 읽을 때 다음 토큰 하나 보기(`.`, `(`)뿐이다. 점 조회 한 번(약 3~4 µs)의 대부분은 트랜잭션 시작과 트리 탐색이다.
