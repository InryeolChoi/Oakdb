# 0009. 벤치마크: 세션을 붙인 뒤의 자동 커밋 왕복 시간 (참고 기록)

이슈 #37, 설계 `docs/design/0025-multi-client-transactions.md` Q12. 서버가 문장을 `oakdb_sql::execute(&db, sql)`로 돌리던 것을, 접속마다 가진 `Session`의 `execute`로 돌리게 바뀌었다. 그리고 문장을 읽기 전에 "트랜잭션 중인가, 시간 제한을 걸까"를 보고, 첫 바이트를 `fill_buf`로 기다린다. **성능 주장은 없으므로** 설계는 A/B를 요구하지 않았다. 다만 트랜잭션 밖의 문장, 즉 지금까지의 모든 문장이 지나는 길이 바뀌었으므로 전후 시간을 기록해 둔다.

**비유**: 손님마다 전용 장바구니를 주기로 했다. 장바구니 없이 물건 하나만 사 가는 손님(자동 커밋)의 계산 줄이 길어지지 않았는지 쟀다.

## 어떻게 쟀나

- 도우미 `crates/oakdb-server/examples/autocommit_roundtrip.rs`. 같은 프로세스 안에 서버를 띄우고, 클라이언트 하나가 루프백 TCP로 `INSERT INTO t VALUES (i, 'row i')`를 하나씩 보낸다. `QUERY`를 보낸 순간부터 `AFFECTED`를 읽은 순간까지를 잰다. 처음 200개는 데우기로 버린다.
  - **mem**: 메모리 파일 시스템(`SimFs`), 2만 문장. 디스크를 빼고 통신 + SQL + 엔진 길만 본다.
  - **disk**: 실제 디스크(APFS, `F_FULLFSYNC`), 2천 문장. 사용자가 실제로 겪는 시간.
- A = `95757fc` (main, #37 전), B = 이 PR. 이 파일은 #37 전에도 있던 API만 써서 같은 파일을 두 버전에 넣어 빌드했다.
- 10라운드, 라운드마다 ABBA 또는 BAAB, 각 실행은 새 DB. 버전마다 20번 실행. A/A는 같은 라운드 안의 A 두 번을 비교했다.
- Apple M3, macOS 27.0.1, release 빌드.

## 해석

- **중앙값은 그대로다.** 메모리 길에서 24.4µs → 24.4µs. 세션을 거치는 비용(`Option` 하나 확인)과 상태를 보는 비용은 재는 눈금 아래다. 시간 제한을 바꾸는 시스템 호출(`setsockopt`)은 값이 바뀔 때만 하도록 했으므로, 트랜잭션 밖 문장은 예전과 같은 수의 시스템 호출을 한다.
- **실제 디스크에서는 sync가 전부다.** 3ms 중 통신과 SQL은 25µs, 1% 아래다. A/A가 0.95로 5% 흔들리는 것도 sync 시간의 흔들림이다.
- **p99는 말할 수 없다.** 메모리 길의 p99는 두 버전 모두 32~36µs 무리와 45~150µs 무리로 갈렸다(운영체제 스케줄링, 커밋 스레드 깨우기). B의 중앙값이 뒤쪽 무리에 걸린 것이지, 두 무리의 위치는 같다. 실행마다 p99를 뽑아 A가 B보다 작을 확률을 세면 0.57로 반반에 가깝다. p90의 1.3%(0.3µs)도 같은 정도의 흔들림 안이다.
- 성능 주장을 하려면(예: "세션을 붙여도 자동 커밋이 느려지지 않는다"를 완료 기준에 넣으려면) 그때 가설을 적고 Mann-Whitney 검정과 신뢰구간으로 다시 잰다. 네트워크 처리량(여러 접속, 처리량)은 #39.
